## 1. 设计结论

维护管理采用“流程优先的统一内容工作台”。一个中屏后台壳承接六类企业发展 CMS 内容，内容编辑、内容审核、发布管理员分别负责起草、复核和上线治理。企业工商、资质等主数据只读引用；CMS 仅维护门户展示补充内容。技术力与商业力 Top30 采用人工策展，不在 CMS 内计算分数，也不伪装成算法排名。

本规格只定义核心产品包，不声明门 1 PDR 已通过，不声明实际交付 Tier，也不解锁工程任务。

## 2. 来源与范围

### 2.1 原始需求

E-37 的 Bid 原始能力为：

1. 企业基础档案维护；
2. 企业成长轨迹内容维护；
3. 重点企业全景图内容维护；
4. 企业技术力与商业力榜单维护；
5. 明星企业介绍内容维护；
6. 深圳企业介绍内容维护。

TRACE 计数保持 `leaves_required: 1`、`leaves_mapped: 1`。六类能力是同一 Bid 叶子内部的产品归位，不构成叶子新增、删除、合并或拆分。

### 2.2 补充约束

- `scope-baseline.yaml` 与 acceptance catalog 只用于范围索引和遗漏检查，不产生业务行为。
- SRS 仅使用 `## 6. 其他需求` 的系统性约束和 `## 7. 需求-验收追溯矩阵` 的 E-37 映射；不继承其他章节的产品定义。
- `data-lineage-policy.md` 约束评审追溯与统计字段治理。本模块不产生统计指标，因此指标语义卡为 `N/A`。
- 权限与架构文件只约束入口、屏幕、服务边界和主数据分治，不充当原始需求。

### 2.3 明确排除

- 直接修改企业工商、资质、专利、财务等主数据；
- 计算技术力、商业力或竞争力分数；
- 自动生成并直接发布算法榜单；
- 企业搜索、分析、推荐、对比、导出等应用侧能力；
- 用户、角色、数据源和图谱的系统级管理；
- 大屏和小屏维护入口。

## 3. 已批准产品解释

以下解释由 human:高颖 在 2026-07-22 当前会话确认，并须写入四件套：

1. 三角色分离：内容编辑提交，内容审核复核，发布管理员发布、下线和回滚。
2. 主数据分治：企业主数据只读同步；发现错误时发起纠错，不在 CMS 覆盖数据真源。
3. 人工策展榜单：维护评估维度、企业顺序、评估依据和专家评述，不在 CMS 内自动计算分数。
4. IA 采用流程优先的统一工作台，六类内容作为稳定导航和筛选维度。
5. 已发布版本再次编辑时生成新草稿，不覆盖线上版本。
6. 发布、下线、回滚和批量关系变更必须填写原因、二次确认并保留审计链。

这些结论均分类为 `product_interpretation`，不改写 Bid 历史原文。

## 4. 产品角色与权限边界

| 产品角色 | 默认入口 | 可执行动作 | 禁止动作 |
| --- | --- | --- | --- |
| 内容编辑 | 待我处理 / 内容类型 | 新建、编辑、保存草稿、预览、提交审核、发起主数据纠错 | 审核自己的提交、发布、覆盖主数据 |
| 内容审核 | 审核中心 | 查看差异和来源说明、填写意见、审核通过、退回 | 修改正文、直接发布、审核自己的提交 |
| 发布管理员 | 发布中心 / 版本与审计 | 查看影响摘要、立即或定时发布、退回、下线、回滚 | 修改正文、绕过审核发布、删除审计历史 |

三个角色均属于中屏后台 L4 子角色。权限 persona 只用于实现映射，不替代产品角色来源与当前批准决定。

## 5. 信息架构

主路由为 `/enterprise/content-management`。

```text
维护管理
├─ 内容工作台
│  ├─ 待我处理
│  └─ 全部内容
├─ 内容类型
│  ├─ 企业基础档案
│  ├─ 成长轨迹事件
│  ├─ 重点企业全景
│  ├─ 能力榜单
│  ├─ 明星企业介绍
│  └─ 深圳企业介绍
└─ 内容治理
   ├─ 审核中心
   ├─ 发布中心
   └─ 版本与审计
```

列表上下文使用 `view`、`type`、`status`、`page` 等查询参数保存。编辑、审核、发布和版本详情使用同一 `content_id` 的子路由；返回列表时恢复筛选与页码。

## 6. 内容模型与数据边界

### 6.1 公共内容对象

每条内容具有以下逻辑字段：

- `content_id`
- `content_type`
- `title`
- `enterprise_ref`（逻辑企业引用，不在产品层指定物理主键）
- `workflow_status`
- `version`
- `owner`
- `effective_at`
- `audit_ref`

`enterprise_ref` 只引用企业主数据。物理键映射由后续数据/架构设计确定，不影响本产品流程。

### 6.2 六类载荷

| 内容类型 | 可维护载荷 | 只读或禁止内容 |
| --- | --- | --- |
| 企业基础档案 | 展示名称、简介、展示标签、媒体 | 工商、信用代码、资质、财务等主数据只读 |
| 成长轨迹事件 | 事件日期、标题、摘要、类型、媒体、来源说明 | 不生成统计趋势或自动推断事件 |
| 重点企业全景 | 重点标识、专属档案、合作/供应链/竞争关系描述 | 不计算图谱关系或供应链风险 |
| 能力榜单 | 技术力/商业力类型、期次、维度说明、Top30 顺序、依据、专家评述 | 不计算分数，不声称算法排名 |
| 明星企业介绍 | 详细介绍、核心成果、代表产品、荣誉资质、媒体 | 不自动决定明星企业身份 |
| 深圳企业介绍 | 详细档案、区域定位、优势、竞争力分析意见、媒体 | 不生成区域统计或竞争力分数 |

### 6.3 三源分治

1. 企业主数据提供只读身份和事实字段；
2. 维护管理 CMS 保存叙事、排序、关系描述与人工策展内容；
3. 门户只消费 `published` 版本，不读取草稿、审核意见或内部规则。

应用侧计算事实与 CMS 内容必须分开保存、分开标识、分开审计。

## 7. 治理状态机

```text
草稿 --提交--> 待审核 --通过--> 待发布 --发布--> 已发布
  ^               |退回          |退回
  └---------------┴--------------┘
```

规则如下：

- 审核退回或发布退回必须填写原因，内容回到草稿；
- 编辑已发布内容时创建新草稿版本，线上版本保持不变；
- 发布可立即生效或设置生效时间；
- 发布、下线、回滚和批量关系变更属于高风险操作；
- 回滚以历史发布版本生成新的已发布版本，不倒写或删除历史；
- 任何并发版本冲突都保留当前输入，要求刷新比较后重新保存；
- 失败响应不得提前改变前端流程状态。

## 8. Frame 设计

| Frame | 目的 | 核心结构 |
| --- | --- | --- |
| F-OPS-01 内容工作台 | 管理待办和全部内容 | 计数卡、统一列表、搜索、类型/状态筛选、新建入口 |
| F-OPS-02 内容编辑器 | 创建或编辑分型内容 | 主数据只读区、CMS 表单、门户预览、完整性检查 |
| F-OPS-03 审核详情 | 完成复核 | 版本差异、来源说明、审核意见、通过/退回 |
| F-OPS-04 发布确认 | 控制上线风险 | 发布范围、生效时间、影响摘要、原因、二次确认 |
| F-OPS-05 版本与审计 | 追溯和恢复 | 版本时间线、操作人、原因、差异、下线/回滚 |
| F-OPS-06 冲突处理 | 保护并发输入 | 服务端新版本、本地输入、刷新比较、重新保存 |

F-OPS-02 采用三栏布局：左侧企业主数据只读区，中间 CMS 编辑表单，右侧门户预览和完整性检查。视口窄于 1280px 时，预览栏收为抽屉，主数据区和编辑区不得互相覆盖。

## 9. 页面状态与错误处理

所有 Frame 按适用性覆盖：

- 默认；
- 加载；
- 空数据；
- 错误；
- 无权限；
- 保存中、保存成功、保存失败；
- 审核退回；
- 发布失败；
- 草稿与线上版本并存；
- 只读锁定；
- 并发冲突。

禁止行为：

- 加载或保存失败时清空用户输入；
- 无权限时仅隐藏按钮而不解释；
- 发布失败时显示“已发布”；
- 用 Mock 内容填充空列表；
- 物理删除已发布内容或审计历史。

## 10. 内部评审追溯

Wireframe 必须声明机器可读 `review_trace_contract`，并为 F-OPS-01～F-OPS-06 分别登记 `review_mounts`。每个 `mount_id` 在模块内唯一。

- 需求追溯只挂在 Frame 标题或稳定区块标题；
- 发布风险说明可使用独立 `review_copy`；
- 评审标识不得挂在输入框标签、操作按钮、表格单元格、流程状态标签或确认弹窗主按钮；
- 业务模式不渲染任何评审标识，且不改变业务字段、权限或流程。

## 11. 指标与开放项

本模块维护内容及人工榜单，不产生统计字段：

- `metrics_required: 0`
- `metrics_mapped: 0`
- 指标语义卡：`N/A`
- Top30 名次是人工策展顺序，不是 `metric_id`

当前设计没有未决的业务、权限或范围问题。物理企业主键、接口和存储结构属于后续架构/数据设计，不在产品四件套内虚构。

## 12. 验收与测试设计

### 12.1 来源与一致性

- E-37 精确 Bid 锚点存在；
- `leaves_mapped == leaves_required == 1`；
- 每个 TRACE story 都有 USM 验收、IA 落点和 Wireframe Frame；
- 六类内容、角色、状态、路由和排除项在四件套中一致。

### 12.2 权限与职责分离

- 编辑者不能审核自己的提交；
- 审核者不能直接发布；
- 发布管理员不能修改正文；
- 无权限状态可解释且不泄露敏感草稿内容。

### 12.3 流程与审计

- 草稿、提交、退回、审核通过、发布、下线、回滚逐项可测试；
- 高风险操作记录操作人、时间、原因和版本差异；
- 已发布版本不可覆盖或物理删除；
- 并发冲突不会丢失当前输入。

### 12.4 状态与评审模式

- 默认、加载、空数据、错误、无权限和操作失败均有稳定反馈；
- 6 个 Frame 均有明确 `review_mounts` 数组；
- 所有 `mount_id` 唯一并落在已命名宿主；
- 业务模式下评审标识完全缺席。
