# 数据库设计（lumen 正式交付 · 支持层总纲）

> **读者**：data-agent、algorithm-agent、api-agent、devops-agent  
> **作用**：七要素支持层 + 展示系统 + 专题服务的**统一存储契约**；子域 DDL 在本总纲下扩展，不得各自为政。  
> **关联**：`graph-engine.md`（NebulaGraph）· `system-wbs.yaml` · `repo-registry.yaml`

---

## 1. 设计原则

### 1.1 三引擎分工

| 引擎 | 产品 | 职责 | 读写方 |
|------|------|------|--------|
| **RDBMS** | MySQL 8.0（主）；demo 企业仓可用 PostgreSQL | 维表、明细 DWD、主题 DWM、**ADS 物化读模型**、配置、用户态 | Python 写 ADS/DWD；**Java 只读 ADS**（+ `app_user` 读写） |
| **Graph** | **NebulaGraph 3.x** | 实体关系网络、多跳子图、路径、图算法运行时 | Python 灌数/查询；Java **禁止**直连 nGQL |
| **Search** | Elasticsearch 8.x | 事件/全文检索、快速筛选聚合 | Python 写；Java 只读（或通过 Python 代理） |

辅助：**Redis**（API 热点缓存）、**MinIO**（模型/报告附件，可选）。

原则来源：`2-概要设计/2-2概要设计/关系型数据库与图数据库在企业-科研机构-政策三维场景中的使用说明.md`

```text
展示/专题页面 → Java REST（只读 ADS + 缓存）→ MySQL innov_ads / ads
                      ↘ Feign → Python → NebulaGraph（图谱解释）
Python 流水线：ODS → DWD → DWM → ADS；并行写 Nebula + ES
```

### 1.2 架构铁律

1. **契约面 = ADS 层**：Java 业务 API **仅**查询 ADS（及 `app_user`）；禁止 Java 扫 ODS/DWD。  
2. **算法写、API 读**：ETL、NLP、图谱灌数、模型推理一律 **Python** 写入。  
3. **图谱主存 NebulaGraph**：关系穿透走图库；**禁止**新引入 Neo4j。MySQL `dwm_graph_*` 仅作快照/排查/重建（见 innov 承接包）。  
4. **统一实体键**：`org_uid`、政策 ID、产业链节点 ID 等在 RDBMS 与 Nebula `vid` 对齐（见 §5）。  
5. **变更会签**：`innov_ads` / `innov_dim` / 平台 `ads` / `gkx_dim` 结构变更需 **Python + Java** 双方 handoff 会签。

## 4. 平台层核心表（gkx_* 初版规划）

> 以下由 **E-PLATFORM-P0-L01** 落地为 `scripts/sql/gkx_platform_*.sql`；字段可随 handoff 增补，变更走 §7。

### 4.1 配置与指标字典（gkx_cfg）

```sql
-- 指标字典（对接 gkxlumen-metrics）
CREATE TABLE cfg_metric (
  metric_id       VARCHAR(64)  NOT NULL COMMENT '全局指标编码，如 POL_FOCUS_CNT',
  element         VARCHAR(16)  NOT NULL COMMENT 'E1..E7：enterprise/industry/org/tech/talent/service/policy',
  name_zh         VARCHAR(128) NOT NULL,
  unit            VARCHAR(32)  NULL,
  calc_version    VARCHAR(32)  NOT NULL DEFAULT 'v1',
  formula_ref     VARCHAR(255) NULL COMMENT '算法文档章节或脚本路径',
  PRIMARY KEY (metric_id)
) COMMENT='七要素基础指标注册';

-- 模型注册（与 Python cfg_model_registry 对齐）
CREATE TABLE cfg_model_registry (
  model_id        VARCHAR(64)  NOT NULL,
  element         VARCHAR(16)  NOT NULL,
  model_name_zh   VARCHAR(128) NOT NULL,
  engine          VARCHAR(16)  NOT NULL COMMENT 'rule|bert|llm|hybrid',
  version         VARCHAR(32)  NOT NULL,
  status          VARCHAR(16)  NOT NULL DEFAULT 'active',
  PRIMARY KEY (model_id)
) COMMENT='深度分析模型注册';

-- 降级开关（G-x 缺口映射，与 innov cfg_degrade_switch 同模式）
CREATE TABLE cfg_degrade_switch (
  switch_key      VARCHAR(64)  NOT NULL,
  element         VARCHAR(16)  NULL,
  enabled         TINYINT      NOT NULL DEFAULT 1,
  fallback_desc   VARCHAR(512) NULL,
  PRIMARY KEY (switch_key)
) COMMENT='数据/能力降级开关';
```

### 4.2 物化指标读模型（ads · 示例）

```sql
-- 通用时序指标（多要素复用）
CREATE TABLE metric_timeseries (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  metric_id       VARCHAR(64)  NOT NULL,
  element         VARCHAR(16)  NOT NULL,
  dim_key         VARCHAR(128) NOT NULL COMMENT '区域/产业/政策等维度键',
  stat_date       DATE         NOT NULL,
  metric_value    DECIMAL(20,4) NOT NULL,
  yoy             DECIMAL(8,4) NULL,
  calc_batch_id   VARCHAR(64)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_metric_dim_date (metric_id, dim_key, stat_date),
  KEY idx_element_date (element, stat_date)
) COMMENT='基础指标时序 ADS（Java 只读）';

-- 政策要素示例（E7 Wave1）
CREATE TABLE policy_focus (
  policy_id       VARCHAR(64)  NOT NULL,
  title           VARCHAR(512) NOT NULL,
  focus_score     DECIMAL(8,4) NOT NULL,
  region_code     VARCHAR(20)  NULL,
  publish_date    DATE         NULL,
  calc_batch_id   VARCHAR(64)  NOT NULL,
  PRIMARY KEY (policy_id),
  KEY idx_region_date (region_code, publish_date)
```

## 12. 数据源解耦与 Mock 策略（数据工厂）

> **背景**：三方原始数据源的表结构尚未确定。为不阻塞 Java/前端，采用 **数据契约先行 + Mock 先行**：先冻结应用层标准表（ADS 契约面），用 Mock 填充；待三方源表结构落地后，由"数据工厂"贴源转换进标准表，**上层零改动**。与 `architecture-baseline.md#D7` 一致。

### 12.1 易变 / 稳定的切分

```text
三方源(待定) ──贴源──> ODS ──清洗──> DWD ──聚合──> DWM ──物化──> ADS(契约面·冻结)
└──────────── 数据工厂：易变，随三方源 ────────────┘        └── Java 只读，稳定 ──┘
```

只有 `ODS→DWD` 这一段随三方源变化；**ADS 标准表是稳定契约**，Java/前端只依赖它，三方源变动不得传导到此面。

| 层 | 当前阶段（源未定） | 三方源就绪后 |
|----|--------------------|--------------|
| ODS 贴源 | **暂不建**（仅留命名占位） | 按真实源建贴源表 + 增量接入 |
| DWD/DWM | **暂不建** | 数据工厂实现"源→标准"清洗/聚合 |
| **ADS / dim / cfg** | **现在冻结 + DDL 落地** | 内容由 Mock 切真实，结构不变 |

### 12.2 Mock 承载方式（定稿）

- **由 Python 写入 ADS**（与真实流水线同一出口），**禁止** Java/前端内存造假数据 —— 这样"换真源"只替换流水线上游，契约面与上层零改动。
- Mock 批次用 `calc_batch_id` 前缀 `mock_` 标识，可与真实批次区分、可整批回滚。
- Mock 须**贴近真实**：枚举值、量级、分布、空值率对齐需求口径；用固定随机种子保证可重复生成。
- ADS 每张表预留 `ext JSON` 扩展列，兜底当前无法预见的三方字段，避免后续改表。
- 稳定业务主键（`org_uid`/`policy_id` 等，见 §8）**现在定死**，不依赖三方源。

### 12.3 数据源映射登记表（占位）

新建 `agent-delivery/data-source-mapping-registry.yaml`，现在留空骨架；三方源到位后是**填表**而非重构。字段：

| 字段 | 含义 |
|------|------|
| `source_system` / `source_table` / `source_field` | 三方源（待定） |
| `std_table` / `std_field` | 标准表（ADS/DWD）目标 |
| `transform_rule` | 清洗/类型/口径转换规则 |
| `status` | `pending_source`（源未定）→ `mapped`→`verified` |

### 12.4 验收挂钩

- Mock-ADS 阶段：按验收分层属 **DEMO / INTEG**，登记 `demo-fallback-registry.yaml`，并用 `cfg_degrade_switch`（§4.1）标记"数据源未就绪降级"。
- 三方源接入、数据工厂跑通后：去开关、`status: verified`，升 **FULL**。

### 12.5 任务对应

- `E-PLATFORM-P0-L01`：产出**标准表 DDL + Mock 生成器 + 映射登记表占位**，**不依赖三方源 schema**。
- `E-PLATFORM-P1-L01`（数据工厂接入，三方源就绪后）：建 ODS/DWD + 写转换 + Mock 切真实。
