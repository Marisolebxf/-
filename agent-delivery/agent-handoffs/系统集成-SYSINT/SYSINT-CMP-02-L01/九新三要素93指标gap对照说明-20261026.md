## 2. 更正后的核心 gap（对比初版）

### G1 指标划分：从「久新只有模型名」更正为「实现已落库，划分疑议消除大半」

久新不是「只有一堆没实现的接口」。28 条深度模型（130–140 / 149–155 / 156–165）绝大多数已有落库结果表（如全景技术链 = `ads_technology_graph_node/edge`、发展历程 = `ads_technology_evolution_*`、人才流动 = `ads_talent_mobility_*`）。真正的划分 gap 收窄为：

- 6 条久新库也没有（上面清单）；
- 42 条只有原料表，算不算久新的活要谈；
- 51 行「交付形态」三分（SQL/Python/API）与我方「读库 ETL」的事实路径不一致，需改判对接模式。

### G2 定义口径：从「零口径」更正为「口径未对齐」——这是当前最大工作量所在

久新有公式（19 条完整 + 若干边界声明），我方 8 件套也有 definition / formula / calc-logic。**两边是两套独立口径，逐条等不等没有比对过**。典型：

- 学术力：久新五维权重制（0.20/0.30/0.30/0.15/0.05，OpenAlex MVP core 口径）vs 我方 8 件套判「部分支持、交三维学术力指数」——同名指标，分数不可直接互换；
- 技术「成熟度」：久新明确「不是 TRL、不是大模型结论，是规则基线」，我方需求文档若按 TRL 理解即为 gap；
- 机构-Topic 实力：被引未按年龄/FWCI 校正，我方口径若要求校正即不等。

调研记录铁律仍然有效：**「结果表在」≠「口径已对齐」，不标已接入**。45+42=87 条都要走逐条口径比对，对账通过才能把 D4 从 mock 升 ingesting/live。

### G3 接口形态：42 个 API 实为假设，事实交付是「读库」

久新没有交付任何 API / 鉴权 / SLA。我方 SCI-INT 设计的 IP-08（Python 适配层调久新 API + 快照）**需要改判**：主体改为 IP-06 类「ETL 读久新库 → 落我方 ADS 快照」，除非郭万迎谈出 API 供数。这也意味着「51 行待确认」的正确问法变了：不是「请交 SQL/Python/API」，而是「确认以读库方式供数 + 是否承诺 SLA/时效 + 补 26 条计算方法」。

### G4 实体 ID：维持且加重

- 人才：久新主键 `talent_id` vs 我方 `dwd_scholar`，不同套（调研记录：`patent_id` 同名不同义同理）；
- 技术：`tech_id` 现为空、`mapping_status='UNMAPPED'`，久新自己也只有候选簇（`RESEARCH_CLUSTER_CANDIDATE`），正式映射发布前图谱联动做不了；
- 机构：久新把企业收在 `institution_type_id='company'`，我方口径「企业≠科研机构」，机构 22 条必须统一过滤规则；
- 地理位置：用对端稳定 ID（如深圳 `loc_E16782C21F18EBF8A59C1E98F9C9860B`），不得页面写死城市名。

### G5 双方都无的硬缺口

6 条双方都没有；另久新 schema §24.10 自列 12 项数据缺口（政策、市场、产品落地、供应链、专家验证、中文译名审核、正式技术映射等）——DS-16 四条与「技术投资额」就卡在这里，不是久新藏了不交，是其上游事实未接入。

## 3. 修订后的行动清单（xlsx sheet 6）

1. **口径对齐攻坚**（最大项）：45 条「结果表在」逐条比久新公式/结果 vs 8 件套，对账通过才升 D4；
2. 26 条「公式未展开」：向久新要方法，或接受黑盒对账策略；
3. 42 条「原料在」：定由谁算（我方照 8 件套自算 vs 久新补算）；
4. 6 条双方无：降级/砍需求/第三方数据（范围调整 ±10% 走 PM）；
5. 对接模式改判：IP-06 读库为主，51 行清单按新口径重谈；
6. 实体 ID 桥：talent/institution/tech/location 四套主键映射方案，tech_id 等久新正式发布；
7. 机构含企业的过滤口径统一；
8. registry 事实更正：84 条 third_party 中实际可读库满足的，走 data-agent 正式化改判（algorithm_type / D4）。
