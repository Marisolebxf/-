## 1. 为什么做

排查「产业链分析算法库 → 基础指标」时发现：

| 路径 | 实际打到的库/表 | 页面看到的 ID |
|------|-----------------|---------------|
| 灌数（新主路径） | `demo_gkxlumenx_ods` → `demo_gkxlumenx_dwd.industry_chain*` → `demo_gkxlumenx_ads.industry_chain_metric_*` | **INB**（如 `INB1303` 集成电路） |
| 改之前的列表接口 | 旧表名 qualify 到 **`gkxlumenx_dwd.chain`**（正式库 mock） | **CH\***（如 `CH003` 量子信息） |

所以会出现：灌数成功、页面仍是 CH\*。根因不是主机（都是 `192.168.88.43`），而是 **库名 + 表名没对齐**。

同期口径（应用开发端，**不含 GDF**）：

- 开发 / 联调默认读 **`demo_gkxlumenx_*`**
- GDF 按数据域逐个切正式库；未切的域继续写正式库目标，**本次不动 GDF / `lumen-etl-es-py`**
- 团队反馈「界面上切换的需求很强烈」→ 做成联调台受控开关，而不是 Helm 改一次全员重启、也不是前端手填库名

## 3. 机制（给开发）

调用链不变：**浏览器 → Java REST / 网关 → Python `/internal/*` 或 `/v1/*`**。前端不直连 MySQL、不直连 Python、不直连 nGQL。产业服务走网关 `/entan/**` 到 `entan-py`（与企业同进程，但切库头不同）。

每个请求带枚举头（不是库名字符串）：

```text
X-GKX-PLANE-CHAIN:    demo | live
X-GKX-PLANE-ENT:      demo | live
X-GKX-PLANE-POLICY:   demo | live
X-GKX-PLANE-SVC:      demo | live
X-GKX-PLANE-INNOV:    demo | live
```

| 层 | 行为 |
|----|------|
| 联调台 axios | 从 localStorage 读五档，自动加头 |
| `gkx-innov` Feign | 把 `X-GKX-PLANE-*` 透传到 Python（含 `X-GKX-PLANE-SVC`） |
| 产业链 Python | `demo` → `read_v2`（INB / DWD v5 / ADS v2）；`live` → 正式库旧 `chain_*` |
| 企业 / 政策 / **产业服务** Python | 同仓 `entan-py`；`connect("ent"\|"svc")` / 政策 `apply_plane("policy")` 按各自头切库；**cfg 库共享不切**。产业服务正式库可能没有 `svc_*`，读空不建表 |
| 创新监测 Java SQL | 仅当头为显式 `demo` 时，把 `gkxlumenx_{ads\|dwd\|dim\|ods}.` 改写成 `demo_gkxlumenx_*`；**无头保持原 SQL**（产品页不受影响）；`live` 保持正式库 |
| 所有灌数 / pipeline | `live` 直接 `code=1` 拒绝 |

服务端可用环境变量关「正式」读面（默认开）：`GKX_PLANE_LIVE_CHAIN` / `_ENT` / `_POLICY` / `_SVC` / `_INNOV`，设 `0` 则即使头是 live 也落回 demo。
