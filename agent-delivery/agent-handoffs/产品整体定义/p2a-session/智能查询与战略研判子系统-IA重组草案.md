# 科技专题服务系统 · 智能查询与战略研判子系统-IA 重组草案

## 版本

Draft v0.3

## 一、核心判断

当前 IA 不应把实施文档中的需求模块完整平铺到左侧导航菜单。

原因：

1. 需求模块用于定义能力边界和验收追溯，不等于用户完成任务的路径。
2. 左侧导航如果按“技术链、产业链、企业、科研机构、人才、政策、产业服务链、综合智能分析”逐项平铺，会让用户先选择组织分类，而不是先进入任务。
3. 当前原型是前台工作台，用户更可能围绕“找对象、看态势、做研判、出结论”完成工作，而不是按实施文档目录逐个打开功能。
4. 文档侧八个战略分析子域仍必须保留，但应进入追溯矩阵和二级页面归位，不应全部成为一级导航。

## 二、IA 重组原则

| 原则 | 含义 |
| --- | --- |
| 用户路径优先 | 一级导航按真实工作路径组织，而不是按需求模块平铺 |
| 能力追溯保留 | 文档侧能力不丢，放入“导航 -> 页面 -> 能力”追溯矩阵 |
| 查询作为底座 | 数据查询不应只是某几个页面的搜索框，应作为进入对象和分析的底层工作方式 |
| 研判按问题组织 | 战略分析不只按对象分类，还要按用户要回答的问题组织 |
| 专业模式保留 | 平台应保留“专业模式/按分析对象浏览”入口，服务专家用户、验收演示和文档能力追溯 |
| 页面原型名不强改 | 页面展示名可保留“科技专题服务系统”，文档中注明实际为子系统原型实验 |

## 三、建议用户路径

本子系统的真实用户路径建议定义为：

```text
进入专题 -> 找对象/建对象集 -> 看态势/链路 -> 做专题研判 -> 形成决策输出 -> 沉淀复用
```

| 路径阶段 | 用户问题 | 对应能力 |
| --- | --- | --- |
| 进入专题 | 我现在要看哪个专题、产业、区域、时间范围？ | 工作台首页、上下文选择 |
| 找对象/建对象集 | 我要找哪些企业、产业链、政策、机构、人才、服务机构？ | 智能查询、对象检索、画像 |
| 看态势/链路 | 这个专题的技术、产业、主体、政策、服务现状如何？ | 全景图谱、空间分布、关系链、趋势图 |
| 做专题研判 | 机会、瓶颈、阶段、竞争力、供需、协同问题在哪里？ | 技术研判、产业研判、主体研判、政策研判、协同研判 |
| 形成决策输出 | 应该招引谁、培育谁、补什么链、优化什么政策？ | 推荐清单、对比篮、决策建议、报告导出 |
| 沉淀复用 | 本次分析能否保存、复用、导出、形成面板？ | 图表面板、报告、收藏、团队空间 |

## 四、建议左侧导航结构

### 4.1 一级导航建议

| 一级导航 | 目的 | 当前页面/能力归入 |
| --- | --- | --- |
| 专题工作台 | 进入专题，设置产业、区域、时间、研究对象上下文 | 当前可用企业中心概览、产业概览、综合看板能力承载 |
| 智能查询 | 统一进入企业、产业链、政策等对象检索；后续扩展机构、人才、服务机构 | 企业检索、产业链检索、政策检索、对象画像 |
| 态势全景 | 看技术链、产业链、主体、政策、服务、区域创新的总体态势 | 技术链全景、产业链全景、企业全景、科研机构概况、人才空间、政策地图、服务链图谱、区域创新活力 |
| 专题研判 | 围绕核心问题做深度分析，不按对象机械分类 | 技术阶段/潜力/瓶颈、产业周期/评价/瓶颈、企业能力/供应链/痛难点、科研合作/技术力、人才供需/关系链、政策对比 |
| 决策支持 | 输出招引、培育、补链、政策优化等行动建议 | 企业引育、科研机构引育、人才引育、服务机构引培、产业发展建议、对比篮 |
| 成果沉淀 | 保存分析过程和输出结果 | 图表面板、报告导出、收藏、团队空间；当前多为缺口或雏形 |

### 4.2 当前菜单到新 IA 的迁移建议

| 当前菜单 | 建议归入 | 说明 |
| --- | --- | --- |
| 技术链分析 | 态势全景 + 专题研判 | 全景进“态势全景”；热点、潜力、阶段、瓶颈进“专题研判” |
| 企业中心 | 专题工作台 + 智能查询 + 态势全景 + 专题研判 + 决策支持 | 企业中心不是一个需求子域名，实际承载多个用户任务 |
| 门户-产业服务 | 专题工作台 + 智能查询 + 态势全景 | 门户属性可弱化，按用户任务拆分 |
| 产业链 | 智能查询 + 态势全景 + 专题研判 | 产业链检索进智能查询，全景/周期/评价/瓶颈按任务归位 |
| 科研机构 | 态势全景 + 专题研判 + 决策支持 | 概况/领域进全景，合作/能力/痛难点进研判，引育进决策 |
| 人才分析 | 态势全景 + 专题研判 + 决策支持 | 空间布局进全景，综合评价/关系链/供需进研判，引育进决策 |
| 门户-政策扶持 | 智能查询 + 态势全景 + 专题研判 | 政策检索进智能查询，政策地图/产业覆盖进全景，政策对比/深圳现状进研判 |
| 政策分析 | 专题研判 | 时序、对比、现状属于研判任务 |
| 产业服务链分析 | 态势全景 + 专题研判 + 决策支持 | 服务链图谱/短板/机构研判/引培拆分归位 |
| 综合智能分析 | 态势全景 + 专题研判 | 区域创新活力偏全景，要素/协同偏研判 |

## 五、推荐 IA 形态

### 5.1 一级导航不超过 6 个

建议一级导航控制在 5-6 个，避免当前 10 个一级菜单造成分类负担。

推荐顺序：

1. 专题工作台
2. 智能查询
3. 态势全景
4. 专题研判
5. 决策支持
6. 成果沉淀

### 5.2 二级导航按任务和对象混合

一级导航按任务路径，二级导航允许带对象：

| 一级导航 | 二级示例 |
| --- | --- |
| 智能查询 | 企业查询、产业链查询、政策查询、科研机构查询、人才查询、服务机构查询 |
| 态势全景 | 技术链全景、产业链全景、企业全景、科研机构全景、人才空间、政策地图、服务链图谱、区域创新活力 |
| 专题研判 | 技术研判、产业研判、企业研判、科研机构研判、人才研判、政策研判、服务链研判、区域协同研判 |
| 决策支持 | 招引企业、培育企业、引入机构、培育机构、引入人才、培育人才、引培服务机构、产业发展建议 |

### 5.3 专业模式切换

平台应保留一个“专业模式”切换位置，用于承接文档侧的专业分析对象路径。

默认模式：

```text
任务模式：专题工作台 / 智能查询 / 态势全景 / 专题研判 / 决策支持 / 成果沉淀
```

专业模式：

```text
按分析对象浏览：技术链 / 产业链 / 企业 / 科研机构 / 人才 / 政策 / 产业服务链 / 综合智能分析
```

推荐放置位置：

| 位置 | 推荐程度 | 理由 |
| --- | --- | --- |
| 顶部工作区切换 | 推荐 | 用户能清楚知道当前是在“任务模式”还是“专业模式”，不污染左侧主导航 |
| 左侧导航顶部的模式切换器 | 可选 | 易发现，但会占用导航空间 |
| 专题研判页内的“按分析对象浏览”入口 | 可选 | 适合专家分析，但不够全局 |
| 用户偏好设置中切换 | 不推荐作为唯一入口 | 发现成本高，不适合演示和频繁切换 |

专业模式不应替代默认任务路径。它的作用是：

1. 支持专业研究人员按技术链、产业链、企业等对象域进入。
2. 支持实施文档能力验收和演示。
3. 支持后续二级能力追溯。
4. 支持对当前已有页面进行低成本重组，而不是强制全部重写。

### 5.4 门户入口语义口径

当前原型中存在“门户-产业服务”“门户-政策扶持”等入口。结合实施文档和当前实现，默认不把它理解为“从科技专题服务系统跳转到独立门户系统”，而理解为“承接门户层内容来源 / 门户展示能力”。

| 口径 | 含义 | 对 IA 的影响 |
| --- | --- | --- |
| 默认口径 | 门户代表内容来源、展示层或运营侧内容承接 | 不作为用户侧一级导航，按任务拆入智能查询、态势全景、专题研判、成果沉淀 |
| 例外口径 | 后续确认存在真实门户系统 URL、跨系统登录边界或独立门户产品 | 可作为外部入口 / 关联入口处理，不纳入本子系统核心 IA |

因此，用户侧 IA 不建议保留“门户-产业服务 / 门户-政策扶持”作为一级菜单。它们应拆分到任务路径中，同时在追溯矩阵中保留“门户层来源”字段，方便后续验收说明其来源和边界。

## 六、必须保留的追溯关系

IA 重组后，必须额外维护追溯矩阵：

```text
文档侧一级能力 -> 文档侧二级能力 -> 用户路径阶段 -> 新 IA 位置 -> 当前路由/页面 -> 覆盖状态
```

这样可以同时满足：

1. 用户看到的是任务路径。
2. 产品和验收能追溯到文档侧能力。
3. 当前实现的聚合页面不会被误判为能力缺失。
4. 当前缺口不会被导航重命名掩盖。

## 七、已确认决策点

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| IA-01 | 一级导航是否按“专题工作台、智能查询、态势全景、专题研判、决策支持、成果沉淀”组织？ | 确认采用 |
| IA-02 | “企业中心”是否继续作为一级导航？ | 不作为一级导航，拆入多个任务路径 |
| IA-03 | “门户-产业服务 / 门户-政策扶持”是否继续出现在一级导航？ | 不作为一级导航，拆入查询、全景、研判、成果沉淀 |
| IA-04 | “科技专题数据查询”是否需要一级入口？ | 作为“智能查询”一级入口；可先从企业查询落地，后续扩展产业、政策等对象 |
| IA-05 | 是否先产出追溯矩阵再改 UI？ | 先产出追溯矩阵，再改 UI |
| IA-06 | 是否保留专业模式切换？ | 保留；默认任务模式，专业模式按分析对象浏览 |
| IA-07 | 门户入口是跳转到门户系统，还是承接门户内容来源？ | 默认按门户层内容来源处理；除非后续确认存在独立门户系统边界 |

## 八、下一轮决策点：企业查询 MVP

智能查询可以先实现企业查询部分。当前已确认查询 / 筛选口径：

| 能力 | 首版口径 |
| --- | --- |
| 关键词检索 | 保留，作为明确企业名、关键词、标签检索入口 |
| 智能多字段检索 | 保留，后续演进为自然语言 / 大模型检索 |
| 高级筛选 | 保留，但首批字段按业务筛选范围控制 |
| 暂不进入 | 复杂组合条件、筛选模板、权重配置、完整 AI 查询能力 |

首批落地范围已确认：

| 决策项 | 首批范围 | 后续阶段 |
| --- | --- | --- |
| 查询场景 | 找企业 + 筛候选 + 初步判断信号 | 完整企业研判 |
| 结果字段 | 基础识别字段 + 创新摘要为必做；关联线索为首批增强 | 研判评分、完整画像字段 |
| 高级筛选字段 | 区域、产业 / 技术方向、企业类型、资质 / 标签、创新能力、成长阶段 / 规模 | 复杂组合条件、筛选模板、权重配置 |
| 后续动作 | 查看企业画像、加入全系统对比篮、进入企业对比 | 进入完整企业研判、导出、保存对象集 |

### 8.1 对比篮定位

对比篮已确认不作为企业查询页内局部组件，而作为全系统常驻复层模块。

| 项目 | 口径 |
| --- | --- |
| 产品定位 | 跨菜单分析对象篮 / 研判对象集 |
| 首版接入 | 企业对象优先接入 |
| 全局形态 | 全系统固定入口，支持展开为抽屉或复层面板 |
| 状态范围 | 至少在本次会话内跨菜单、跨路由保留 |
| 基础动作 | 加入对象、查看已选、移除、清空、进入对比或研判 |
| 预留对象 | 政策、机构、人才、产业链节点 |
| 后续阶段 | 多篮管理、长期保存、团队共享、跨对象混合高级分析 |

因此，企业查询 MVP 中的“加入对比篮”应理解为接入全局对比篮，而不是在企业查询页面内新建一个局部对比组件。
