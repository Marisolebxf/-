# 科技专题数据查询与科技专题战略分析产品核对草案

## 版本

Draft v0.1

## 核对对象

提取文件：

`p2a-session/科技专题数据查询与科技专题战略分析-实施方案摘录.md`

该提取文件是当前阶段产品核对的直接基准；完整 `科技专题服务系统-实施方案摘录.md` 仅作为上游来源和完整系统差距参照。

当前实现对照：

`repos/demo-ui-topic`

本次核对只看两块：

1. 科技专题数据查询
2. 科技专题战略分析

不重新讨论项目管理、信息发布管理、内容运营中心、系统管理中心。

## 核对结论

当前提取结果基本可以作为 `demo-ui-topic` 当前前台实现范围的产品基准，但需要加一个限制语：

> 当前实现主要覆盖“科技专题战略分析”，并局部覆盖“科技专题数据查询”；尚不能代表完整科技专题服务系统。

## 一、科技专题数据查询核对

### 源文档结构

| 一级能力 | 二级能力 | 三级能力 |
| --- | --- | --- |
| 数据智能呈现 | 综合智能查询 | 关键词与语义融合探查；结构化条件与图谱联动探查 |
| 数据智能呈现 | 统一结构化结果展示 | 多模态结果展示与交互；专业术语与主体详情呈现；查询结果智能导出 |
| 数据智能分析 | 推荐图表分析 | 人才与科研产出分析视图；技术、服务与资讯热度视图 |
| 数据智能分析 | 自定义图表创建 | 多维数据筛选与组合；图表类型与坐标配置 |
| 数据智能分析 | 图表面板管理 | 多图表集成与模板应用；可视化布局与对齐控制；面板保存与多格式导出 |

### 产品核对

| 核对项 | 判断 | 产品含义 |
| --- | --- | --- |
| 是否是一个统一入口 | 源文档倾向统一数据查询入口 | 当前实现更像分散式专题检索 |
| 是否只等于搜索 | 否 | 它包含搜索、结果展示、图谱联动、导出、图表推荐、自定义图表、面板管理 |
| 是否已被当前实现完整覆盖 | 否 | 当前实现有企业/产业/政策等局部检索，但没有统一查询总入口和完整图表面板管理闭环 |
| 是否可以作为当前版本 P0 | 部分可以 | 搜索和结果展示是 P0；自定义图表与面板管理可作为 P1/P2 |

### 产品风险

如果把“科技专题数据查询”简单理解为几个搜索页，会漏掉源文档中的“查询结果 -> 智能图表 -> 自定义分析 -> 面板沉淀 -> 导出”的分析闭环。

## 二、科技专题战略分析核对

### 源文档结构

科技专题战略分析包含 8 个子域：

| 子域 | 源文档能力 |
| --- | --- |
| 技术链分析 | 全景图谱、热点、产业化潜力、阶段研判、深圳发展、转化瓶颈 |
| 产业链分析 | 全景图谱、周期、区域指数、关键环节、瓶颈、深圳对比、发展建议、竞争力 |
| 企业分析 | 类型、领域、技术力、商业力、深圳现状、招引、培育、供应链、痛难点、竞争力 |
| 科研机构分析 | 涉及产业、技术领域、新增动态、深圳现状、合作关系、技术力、引入培育、优势、痛难点 |
| 人才分析 | 区域、机构、供给、关系链、深圳现状、学术力、产业力、引入培育、高校新培育、供需 |
| 政策分析 | 政策时序、区域对比、深圳政策现状 |
| 产业服务链分析 | 服务机构领域、新增趋势、技术力、短板、图谱、引入培育、深圳现状 |
| 综合智能分析 | 区域创新活力、创新要素、创新协同 |

### 产品核对

| 核对项 | 判断 | 产品含义 |
| --- | --- | --- |
| 是否是当前实现主体 | 是 | `demo-ui-topic` 的主导航和路由基本围绕这一块展开 |
| 是否应完整保留八个子域 | 倾向是 | 因为当前实现已覆盖大部分子域，删减会破坏专题服务的完整性 |
| 是否必须逐条对应源文档三级功能 | 不一定 | 可允许按页面聚合，但需要产品确认聚合口径 |
| 是否存在命名/IA 重组 | 是 | 当前有“企业中心”“门户-产业服务”“门户-政策扶持”等重组，需要确认是否仍属于战略分析前台 |

### 产品风险

战略分析部分虽然当前实现覆盖较强，但存在两个风险：

1. 源文档按“分析对象”拆分，当前实现按“前台导航/门户/中心”重组，名称和层级不完全一致。
2. 科研机构、人才、产业服务链等子域当前实现有聚合倾向，可能没有逐项覆盖源文档全部细分能力。

## 三、当前实现边界判断

建议将当前 `demo-ui-topic` 的产品边界临时定义为：

> 科技专题服务系统前台分析工作台，覆盖战略分析主体，并提供分专题数据查询能力。

这一定义比“完整科技专题服务系统”更准确，也能解释为什么项目管理、信息发布、内容运营、系统支撑未进入当前实现。

## 四、需要 Ask_Why 决策的问题

以下 5 个问题已按推荐项确认：

### Question 1: 当前实现边界是否按“前台分析工作台”定义？

A. 是，当前 `demo-ui-topic` 只代表前台分析工作台。  
B. 否，它应代表完整科技专题服务系统，因此缺失模块必须补齐。  
C. 暂时双口径：当前实现按前台分析工作台验收，完整系统按实施文档另列差距。

推荐：C。这样既不否认实施文档完整范围，也不强行要求当前 demo 立刻覆盖全部系统。

已确认：C。

### Question 2: 数据查询是否需要统一总入口？

A. 需要，建立“科技专题数据查询”统一入口。  
B. 暂不需要，允许企业/产业/政策等专题内分散检索。  
C. 先定义统一查询规范，但实现上继续分散入口。

推荐：C。这样能保证交互和结果态一致，又不一定马上新增总页面。

已确认：C。

### Question 3: 战略分析八个子域是否全量保留？

A. 全量保留，作为战略分析的产品边界。  
B. 允许合并，按当前前端 IA 组织。  
C. 全量保留为需求边界，但页面层允许合并。

推荐：C。源文档边界不丢，前端 IA 仍可聚合。

已确认：C。

### Question 4: 当前“门户-产业服务 / 门户-政策扶持 / 企业中心”是否纳入战略分析前台？

A. 纳入，视为战略分析的门户/中心化表达。  
B. 不纳入，门户层另算系统。  
C. 暂纳入，但标注为 IA 重组项，后续由 product-agent 确认。

推荐：C。当前实现已经这样组织，直接排除会让差距分析失真。

已确认：C。

### Question 5: 是否把本核对结论同步更新到差距分析？

A. 更新，将当前实现边界改成“前台分析工作台”。  
B. 暂不更新，先等 product-agent 确认。  
C. 只在 product-agent 派单中增加此核对结论。

推荐：B。边界定义会影响后续验收口径，先确认再改主差距表。

已确认：B。

## 五、已确认核对口径

1. 当前实现采用双口径：`demo-ui-topic` 按“前台分析工作台”验收，完整系统按实施文档另列差距。
2. 数据查询先定义统一查询规范，入口可以继续分散在企业/产业/政策等专题内。
3. 战略分析八个子域全量保留为需求边界，页面层允许聚合。
4. 门户-产业服务、门户-政策扶持、企业中心暂纳入战略分析前台，并标注为 IA 重组项。
5. 主差距分析暂不更新，等待 product-agent 确认后再同步。
