# 基于提取文档的 Ask_Why 产品重梳理

## 版本

Draft v0.3

## 直接依据

`p2a-session/科技专题数据查询与科技专题战略分析-实施方案摘录.md`

## 重梳理约束

本轮只以提取文档为需求输入。

不使用以下内容作为需求来源：

- 完整实施方案中的项目管理、信息发布、内容运营、系统管理等其它模块。
- `demo-ui-topic` 当前路由、菜单、页面命名。
- 既有 `gap-analysis.md` 的差距判断。
- 之前“前台分析工作台”的临时命名。

这些材料后续可以作为实现对照或背景，但不能反向定义本轮产品边界。

## 当前任务理解

提取文档描述的不是完整“科技专题服务系统”，而是其中两个强相关能力域：

1. 科技专题数据查询
2. 科技专题战略分析

这两个能力共同构成一个从“数据发现”到“专题研判”的智能分析服务链路。

文档自身的产品主线更接近：

> 探查 -> 展示 -> 分析 -> 洞察/导出 -> 专题研判

而不是此前完整系统口径里的：

> 查询 -> 分析 -> 管理 -> 发布 -> 运营

## 基于文档自身的产品结构

### A. 科技专题数据查询

文档定义的数据查询不是单纯搜索，而是一个“查询结果继续分析”的入口能力。

| 层级 | 能力 | 文档含义 |
| --- | --- | --- |
| 一级 | 数据智能呈现 | 把复杂科技数据变成可理解、可交互、可导出的结构化视图 |
| 二级 | 综合智能查询 | 关键词、语义、结构化条件、图谱关系等多模式探查 |
| 二级 | 统一结构化结果展示 | 列表、图谱、详情、术语解释、导出 |
| 一级 | 数据智能分析 | 基于查询结果自动转成图表、面板和分析洞察 |
| 二级 | 推荐图表分析 | 系统自动推荐图表和分析主题 |
| 二级 | 自定义图表创建 | 用户自定义字段、维度、图表类型和坐标 |
| 二级 | 图表面板管理 | 多图表集成、布局、模板、保存、导出 |

产品判断：

数据查询应被看作“智能数据分析入口”，不是普通列表检索，也不是某个专题页面里的搜索框。

### B. 科技专题战略分析

文档定义的战略分析是“按科技创新要素/对象展开的专题研判矩阵”。

| 子域 | 核心问题 |
| --- | --- |
| 技术链分析 | 技术从哪里来、处于什么阶段、能否产业化、转化瓶颈在哪里 |
| 产业链分析 | 产业链结构、周期、关键环节、区域竞争力和深圳发展路径是什么 |
| 企业分析 | 哪些企业重要、强在哪里、弱在哪里、该招引或培育谁 |
| 科研机构分析 | 哪些机构在哪些产业/技术领域有价值，如何引入、培育和合作 |
| 人才分析 | 人才在哪里、供需如何、关系如何、谁应引入或培育 |
| 政策分析 | 政策如何演变、区域差异如何、深圳政策现状如何 |
| 产业服务链分析 | 服务机构和服务链哪里强、哪里短板、应引入或培育哪些服务机构 |
| 综合智能分析 | 区域创新活力、创新要素、创新协同的综合评价 |

产品判断：

战略分析不是页面菜单列表，而是一组围绕“技术-产业-企业-机构-人才-政策-服务-区域协同”的决策问题矩阵。

## 可能存在的既有偏差

1. 把当前实现的“企业中心 / 门户-产业服务 / 门户-政策扶持”当成需求结构。  
   偏差：这些是实现 IA 或演示 IA，不是提取文档中的原始产品结构。

2. 把“数据查询”理解成分散搜索框。  
   偏差：文档要求的是“查询 -> 结构化结果 -> 图谱/详情 -> 图表分析 -> 面板沉淀”的完整链路。

3. 把战略分析八个子域机械等同于八个菜单。  
   偏差：文档描述的是八类研判对象和决策问题，页面层可以重组，但需求边界不能丢。

4. 用完整系统六大模块继续解释当前提取文档。  
   偏差：当前提取文档只包含数据查询和战略分析，不应继续引入项目管理、信息发布、内容运营、系统支撑作为本轮主范围。

5. 过早使用“前台分析工作台”命名。  
   偏差：这是对当前实现的可能归纳，不是提取文档中的原始产品名称。

## 本轮已确认产品口径

提取文档对应的产品边界命名为：

> 科技专题服务系统 · 智能查询与战略研判子系统。

它包含：

1. 一个横向底座能力：科技专题数据查询。
2. 一个纵向研判矩阵：科技专题战略分析八个子域。

两者关系：

```text
科技专题数据查询
  -> 发现对象、生成结构化结果、形成可视分析材料
科技专题战略分析
  -> 围绕技术/产业/企业/机构/人才/政策/服务/协同进行专题研判
```

该命名的含义：

- “科技专题服务系统”是上级完整系统，覆盖六大模块。
- “智能查询与战略研判子系统”是当前提取文档和当前实现主要对应的范围。
- 当前实现不应再假装是完整科技专题服务系统。

## 需要 Ask_Why 重新确认的问题

### Question 1: 数据查询应该如何定位？

A. 独立基础能力，服务所有战略分析子域。  
B. 各专题内的搜索入口，不需要独立成域。  
C. 先作为独立能力定义，允许实现时分散嵌入各专题。  

推荐：C。文档上它是独立能力，工程上可以分散承载。

已确认：C。

### Question 2: 战略分析八个子域如何处理？

A. 八个子域全部作为需求边界保留。  
B. 按当前前端 IA 合并，保留主要页面即可。  
C. 需求边界保留八个子域，页面实现允许聚合，但必须能追溯到每个子域。

推荐：C。保留需求完整性，同时允许后续设计重组。

已确认：C。

### Question 3: 当前实现对照应放在什么阶段？

A. 先完成文档侧产品结构，再做实现对照。  
B. 立即用 `demo-ui-topic` 路由校验每个功能。  
C. 只看当前实现，不再做文档侧产品结构。

推荐：A。先排除需求结构偏差，再看实现缺口。

已确认：A。

### Question 4: 是否暂停修改既有 `gap-analysis.md` 和派单？

A. 暂停，等本轮重梳理口径确认后再改。  
B. 立即按本轮草案改写。  
C. 只改派单，不改差距表。

推荐：A。否则会把尚未确认的新口径写进执行材料。

已确认：A。

## 已确认重梳理口径

1. 当前子系统命名为：科技专题服务系统 · 智能查询与战略研判子系统。
2. 数据查询作为独立基础能力定义，允许实现时分散嵌入各专题。
3. 战略分析八个子域全部保留为需求边界，页面实现允许聚合，但必须可追溯到每个子域。
4. 先完成文档侧产品结构，再做当前实现对照。
5. 暂停修改既有 `gap-analysis.md` 和 product-agent 派单，待本轮文档侧结构确认后再同步。
