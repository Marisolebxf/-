## Decision 155

旧原型中的 `重点企业概览 / 重点企业全景` 是否已被当前企业总览完整承接；若存在缺口，应恢复旧 Tab、单独设置菜单，还是作为企业总览分析区补回？

User choice:

确认作为企业总览内第五个纵向分析区补回，命名为 `重点企业产业链全景`。不恢复旧 `重点企业概览 -> 企业全景 / 类型分布 / 领域分布` 双层 Tab，不新增 `企业全景` 左侧菜单。该区块承接门户·企业发展来源的 `E-33`：继承顶部产业领域、地域、企业类型和时间 / 数据批次形成的企业集合，按上游 / 中游 / 下游和具体链位展示重点企业基础卡；链位点击进入企业总览内下钻结果页态；企业卡提供查看画像和加入对比。产业链 / 链位是产业领域的二级细化条件，不与产业领域混为同一级筛选。

Rationale:

当前 `企业类型与区域分布` 已承接 E-33 的类型 / 规模统计重叠部分，`重点企业领域覆盖` 已承接领域统计重叠部分，但“沿产业链展示全链重点企业 + 企业基础信息卡”没有等价承接。恢复旧 Tab 会破坏已确认的单页纵向结构；单独恢复企业全景菜单会重新造成展示层与分析层重复。作为独立分析区补回既保留原需求，又保持当前企业总览的对象发现与下钻闭环。

Impact on plan:

`企业完整深化规格.md`、`企业模块深化UE规格.md`、IA / 追溯规范和企业总览前端验收统一从四个分析区调整为五个分析区。`E-33` 保留原始门户需求编号，不伪造 `REQ-ENT-011`。前端在区域分布之后、领域覆盖之前增加新区块，复用当前 ContextBar、企业主数据、画像抽屉、对比篮和企业总览下钻结果页态。

## Decision 103

Question:

发现 `重点企业类型分析`、`重点企业领域分布分析`、`深圳企业现状分析` 等原需求未在企业总览中充分展开后，是否应暂停继续深化风险洞察，先回补企业总览？

User choice:

可以。先回到 `企业总览`，把遗漏的原需求做深度归位。`风险洞察` 仍只承接 `企业供应链关系分析` 和 `企业发展痛难点分析`；`重点企业类型分析`、`重点企业领域分布分析`、`深圳企业现状分析`、`深圳企业产业链定位`、`多城市横向对标分析` 应回补到 `企业总览`。企业总览建议采用长页面分区 + 顶部锚点导航，而不是把 `类型分布 / 领域覆盖 / 深圳现状 / 城市对标` 做成互斥页签。

Rationale:

这些需求关注企业生态结构、区域分布、领域覆盖、本地产业链位置和城市横向对标，属于企业分析入口总览需要回答的全局问题，不属于风险识别。若继续只推进风险洞察，会导致企业总览对原需求覆盖不足；若把这些能力放入风险洞察，则会稀释风险洞察的供应链风险和痛难点诊断边界。长页面分区可以保持企业生态分析的连续性，顶部锚点支持快速定位各分析区。

Impact on plan:

`企业完整深化规格.md` 后续应优先补齐企业总览深度展示结构，至少包括 `企业类型与区域分布`、`重点企业领域覆盖`、`深圳企业产业链位置`、`城市横向对标` 四个分析区，并分别定义筛选条件、图表 / 列表形态、下钻动作、与企业查询 / 企业画像 / 企业评估的联动关系。风险洞察细化顺序后移，但已确认的风险洞察主链路和边界继续保留。

Status:
Confirmed

## Decision 102

Question:

企业 `风险洞察` 应如何与 `企业评估` 区分，并作为下一阶段产品 / UE 收敛方向展开？

User choice:

按推荐确认。`风险洞察` 不沿用企业评估的评分、排名、权重任务结构，而是按 `风险发现 -> 证据下钻 -> 成因解释 -> 处置线索` 组织。风险洞察不设置统一企业风险总分，采用分项风险等级、风险标签和证据支撑；首页默认采用 `总览 + 高风险企业清单`；首页统一呈现风险总览，详情页再拆分 `供应链风险` 和 `发展痛难点` 两个专题；处置线索提供初步建议，不生成完整一企一策方案，不直接进入政策匹配或服务派单。

Rationale:

企业评估回答企业能力水平、排名和支持价值，风险洞察回答企业哪里可能出问题、风险如何形成、需要关注哪些证据和处置方向。若风险洞察使用统一评分或完整评估任务结构，会与企业评估的综合竞争力评估混淆；若只做供应链图谱，又会弱化 `REQ-ENT-009 企业发展痛难点分析`。采用风险发现、证据下钻、成因解释、处置线索的链路，可以同时承接 `REQ-ENT-008 企业供应链关系分析` 和 `REQ-ENT-009 企业发展痛难点分析`，并与后续 `引育推荐` 保持边界。

Impact on plan:

`企业完整深化规格.md` 后续进入风险洞察细化时，应按总览、高风险企业清单、单企业风险画像、供应链风险专题、发展痛难点专题、风险诊断报告、追溯浮层和导出控制展开。后续 UE / frontend-agent 派单不得把风险洞察做成企业评估的另一个评分页，也不得把完整一企一策、政策匹配和服务派单提前放入风险洞察主流程。

Status:
Confirmed

## Decision 030

Question:

战略分析八个子域如何处理？

User choice:

需求边界保留八个子域，页面实现允许聚合，但必须能追溯到每个子域。

Rationale:

八个子域来自提取文档，是“智能查询与战略研判子系统”的完整研判对象边界。页面层可以为了交互效率和信息架构进行聚合，但不能丢失技术链、产业链、企业、科研机构、人才、政策、产业服务链、综合智能分析任一子域。

Impact on plan:

后续文档侧结构保留八个子域；实现对照时不要求一子域一页面，但要求每个子域有明确承载页面或功能入口。

Confirmed

## Decision 091

Question:

企业评估从带入企业对象到生成结果的任务流程、结果页结构和异常状态如何定？

User choice:

企业评估页默认不直接出结果，先进入评估任务配置。流程为：进入评估并携带企业对象、选择评估模式、确认企业对象、选择指标模板、调整指标权重、生成评估结果。结果页按任务摘要、核心结论、可视化分析、指标明细、差距 / 短板分析、报告输出组织。核心结论区不做左右结构，采用纵向分层：顶部一行紧凑 KPI 卡，最多 4 个；KPI 下方一条结论条，以标签和短句展示优势、短板、领先方或主要差距。企业数量不足、数据缺失、权重不等于 100%、临时调整指标等状态必须有明确处理；权重低于 100% 提示补齐，高于 100% 提示降低。企业评估不承担对象暂存，不嵌入对比篮，不输出招商 / 培育推荐结论，不输出风险洞察结论；风险相关指标只可作为评估因子引用。

Rationale:

企业评估需要承接企业查询、企业总览、对比篮和企业画像传入的对象，但它本身是评估任务工作台，不是对象篮或查询页。先配置任务再生成结果，可以把评估模式、企业数量、指标模板和权重校验统一处理，避免用户从不同入口进入时得到不一致的结果页。结果页分层组织，也能让评分结论、图表分析、指标追溯和报告导出各归其位。

Impact on plan:

`企业完整深化规格.md` 在企业评估规格中补充 `企业评估任务流程`、`企业评估结果页结构` 和 `企业评估状态规则`。后续 UE 派单应按任务配置页和结果页两个状态设计，不把对比篮嵌入企业评估，也不在企业评估中混入引育推荐或风险洞察结果。

## Decision 092

Question:

技术力模型、商业力模型和综合竞争力模型的指标选择、权重配置、默认模板和维护边界如何定？

User choice:

系统必须向用户提供默认模板。默认模板来自维护管理中的全局模板；普通用户进入评估时默认加载对应评估模式和行业 / 产业口径下的全局默认模板。用户可直接使用，也可临时调整或另存为个人模板，但不能修改全局模板。技术力和商业力都有独立指标库，用户可选指标、赋权；商业力默认模板受行业 / 产业领域影响。综合竞争力采用两层权重：综合维度权重 + 维度内部指标权重。所有权重合计必须等于 100%，低于或高于 100% 都不能生成结果。技术力 / 商业力配置可以实时计算得分预览，但正式结果生成仍要求至少 2 家企业。

Rationale:

原需求分别定义了 `技术力模型构建与参数自定义`、`商业力模型配置与指标选择` 和 `企业竞争力分析`。技术力模型要求从专利数量 / 引用、研发人员占比、核心技术覆盖度等指标库中灵活组合并赋权；商业力模型要求从年营收、利润率、客户集中度、品牌声量等商业指标中选择，并按行业特性调整；综合竞争力则是整合技术力、商业力等维度的综合评估框架。因此三类模型需要共用评估任务流程，但指标库、默认模板和权重层级不能混为一套。

Impact on plan:

`企业完整深化规格.md` 在企业评估规格中补充 `企业评估模型与权重规则`，并明确默认模板来自维护管理的全局模板。后续 UE / frontend-agent 需要在评估任务配置页支持默认模板加载、指标选择、权重校验、得分预览、临时调整和个人模板保存；维护管理负责全局模板的指标组合、默认权重、适用行业 / 产业、版本、生效状态和审批。

Question:

`商业竞争力对标分析` 与 `企业商业力评估对比分析` 是什么关系，企业评估结果页是否完整覆盖原需求中的技术力、商业力和综合竞争力输出？

## Decision 096

Question:

企业评估任务配置页中，指标选择与权重配置的交互如何定？

User choice:

指标配置区域采用 `模板选择 -> 指标分组表格 -> 已选指标与权重 -> 得分预览` 的顺序组织，不使用字段树。默认加载系统默认模板，可切换个人模板或临时自定义。指标库用分组表格展示，字段包括勾选、指标名称、指标分组、数据状态、当前权重、数据来源和指标说明入口。权重使用数字输入框，不使用滑杆；本期只支持整数权重，范围 0-100；总权重必须等于 100%，低于或高于 100% 都不能生成。支持 `一键均分`，不做自动归一化，也不在用户修改单个权重时自动改动其它指标。缺失指标可选，但必须提示会影响评分可信度。综合竞争力采用综合维度权重 + 维度内指标权重两层配置，维度内指标通过折叠面板展开。

Rationale:

原需求要求技术力模型支持灵活组合并赋权，商业力模型支持指标选择并按行业特性调整，综合竞争力支持多维度多指标自由选取并赋权。用分组表格比字段树更适合评估指标配置，可以直接展示数据状态、权重、来源和说明；数字输入框比滑杆更适合精确控制 100% 权重。`一键均分` 可降低配置成本，而不做自动归一化可以避免系统暗改用户权重。

Impact on plan:

`企业完整深化规格.md` 在企业评估规格中新增 `企业评估指标选择与权重配置交互`。后续 UE / frontend-agent 派单需要按表格配置、整数权重、总权重进度、缺失状态、得分预览、一键均分和综合竞争力折叠维度来设计；生成按钮必须同时校验企业数量、指标选择、权重等于 100% 和数据缺失规则。

## Decision 097

Question:

企业评估中数据缺失、低可信和评分可信度如何处理？

User choice:

缺失指标不记 0 分，不把“没有数据”误判为“表现差”。缺失指标不参与该企业该项得分计算，系统按剩余可用指标重算，同时降低评分可信度。指标数据状态分为正常、部分缺失、缺失、过期、低可信。评分可信度分为高 / 中 / 低 / 不可生成：可用指标权重覆盖率 >= 90% 且无关键指标缺失为高，70%-89% 或少量关键指标缺失为中，50%-69% 或多个关键指标缺失为低，低于 50% 或关键指标全部缺失则不可生成。多企业对比时每家企业独立计算可信度，排名表必须展示可信度，覆盖差异过大时提示可比性受限。差距分析只分析双方都有数据的指标，缺失项进入数据缺口说明。雷达图缺失点标记缺失，不用 0 填充。报告必须包含数据缺失清单、重算规则和可信度说明。

Rationale:

企业评估输出会被用于合作、并购、扶持、投资尽调或政策支持判断，缺失数据如果直接记 0 分，会造成错误负向判断。按剩余可用指标重算并展示可信度，可以在保留评估能力的同时显式提示数据质量风险。多企业对比需要额外提示可比性，否则不同企业的数据覆盖差异会被误读为能力差异。

Impact on plan:

`企业完整深化规格.md` 在企业评估规格中新增 `企业评估数据缺失与评分可信度规则`。后续 UE / frontend-agent 派单需要在配置表、结果核心结论、排名表、雷达图、指标明细、差距分析和报告输出中体现数据状态、可信度标签、数据缺口和可比性受限提示。

Confirmed

## Decision 098

Question:

结合原需求和既有导出口径，企业评估报告输出内容结构如何定？

User choice:

企业评估报告是企业评估结果页的结构化报告输出，不是报告编辑器，也不是跨模块综合大报告。报告入口只在企业评估结果页；配置页、企业总览和对比篮不导出企业评估报告。报告按评估模式命名：技术力评估输出技术力对比报告 / 技术力差距分析报告，商业力评估输出商业力对标报告，综合竞争力评估输出综合竞争力评估报告。报告通用目录包括报告封面、评估任务摘要、核心结论、可视化结果、指标明细、差距 / 短板分析、数据质量与追溯、导出审计。导出内容按当前评估任务和当前结果页状态生成，导出时不允许重新选择企业、指标或权重。默认导出 PDF，Word 作为后续增强；导出记录进入个人资产中心；导出必须带水印、审计和追溯编号。

## Decision 099

Question:

报告生成耗时较长、用户离开页面后再次生成、以及导出范围和敏感数据控制如何结合既有导出规则落地？

User choice:

在不推翻五类导出产物和 Decision 098 的前提下，补充报告生成与导出落地规则。报告生成是后台任务，不是前端假 loading；前端展示阶段式进度，包括任务提交、数据准备、评分计算、图表生成、报告装配、生成完成，并通过后台状态轮询对齐真实任务状态。用户离开页面后，可在个人资产中心查看生成状态和下载结果。报告生成以后台任务记录和评估任务指纹为准，不依赖前端本地缓存；同指纹任务正在生成时不重复生成，已生成且未过期时优先下载已有报告，失败时提供重试，过期或不存在时才创建新任务。导出权限不等于全量数据权限；导出受角色、字段分级、字段权限、导出模板、对象数量上限、敏感字段权限、审批 / 脱敏和审计规则共同控制。非敏感清单默认只导出部分字段，数量上限建议为 20-50 条并由模板或系统配置决定；敏感字段即使有权限也不默认全量导出；报告类导出以摘要和分析结论为主，不导出底层全量明细。

Rationale:

企业评估报告可能涉及大量企业对象、指标计算、可信度计算、图表渲染和 PDF 生成，耗时不可预测。如果只做前端 loading，用户离开页面或刷新后会丢失状态，也容易重复提交生成任务。以后台任务和评估任务指纹为准，可以避免重复生成，并让个人资产中心承接生成中、生成成功、失败、重试、过期等状态。企业数据存在敏感字段和大批量导出风险，因此有导出权限也不能等同于可全量导出。

Impact on plan:

`企业完整深化规格.md` 补充报告生成阶段进度、后台任务状态、评估任务指纹、同指纹任务再次生成规则、报告导出记录状态，以及导出范围与敏感数据控制。后续 UE / frontend-agent 派单需要实现报告生成任务条 / 进度面板、个人资产中心生成状态入口、下载已有报告 / 重新生成 / 重试生成等按钮状态，并在导出前提示数量裁剪、脱敏或审批。

Confirmed

## Decision 100

Question:

企业评估任务是否需要保存历史，如何与个人模板和报告导出记录区分？

User choice:

本期轻量保存企业评估任务历史。评估结果生成后自动形成任务记录，用于恢复最近任务、关联报告导出记录和避免重复生成报告；只配置但未生成结果的任务不进入正式历史。个人模板、评估任务历史、报告导出记录三者分开管理但互相关联：个人模板保存指标组合和权重，评估任务历史保存评估配置和结果快照，报告导出记录保存基于某个评估任务生成的文件状态。一个评估任务可以关联多个报告导出记录。企业评估页可提供 `最近评估任务`、`恢复上次评估`、`查看关联报告`；本期不做完整任务管理系统、团队共享评估任务、复杂版本比较和任务协作审批。

Rationale:

报告生成已经以后台任务和评估任务指纹为准，如果没有评估任务历史，个人资产中心只能看到报告文件，无法恢复评估配置和结果上下文，也难以判断同指纹报告是否重复生成。轻量保存评估任务历史可以支撑恢复、追溯和报告复用，同时避免把本期范围扩展成完整任务协作系统。

Impact on plan:

## Decision 101

Question:

企业评估的权限边界如何按角色、动作和字段控制？

企业总览的原始需求以“各未来产业”为展示范围。如果企业对象不标明所属未来产业，用户无法理解企业数量、趋势、重点企业和明星企业的产业口径。明星企业的原始语义是代表产业带动作用的龙头案例，固定推荐可以保证页面叙事与当前产业一致，避免退化为企业查询。

Impact on plan:

产品与 UE 文档增加 `所属未来产业` 的展示规则和明星企业固定推荐规则。后续只需细化预设推荐标准、候选池、更新频率、推荐依据字段和维护责任，不再讨论是否提供用户自行选企业。

Confirmed

## Decision 163

Question:

明星企业的推荐标准是否需要在页面中向用户说明？

User choice:

确认需要说明。明星企业页首屏展示简要 `推荐依据`、当前产业以及标准版本或数据时间；用户可通过 `查看推荐口径` 查看适用产业、候选范围、标准名称 / 版本、已确认维度和更新时间。推荐标准本身继续保留待讨论；未定稿时，原型明确标识“推荐口径待配置”。不公开具体权重、内部阈值、排名、敏感原始证据或运营人工备注。

Rationale:

明星企业由系统固定推荐，如果不解释推荐口径，用户无法判断其代表性是否与当前产业相关；若直接公开模型细节，又会把门户展示页变成模型配置或敏感信息页面。分层告知能同时提供可解释性和必要的边界控制。

Impact on plan:

产品与 UE 文档新增推荐标准三层透明规则。后续确定推荐标准时，需要同步补齐用户可见的推荐依据摘要和推荐口径详情，而不改变“固定推荐、不可自行换企业”的主规则。

Confirmed

## Decision 164

Question:

明星企业页面中的“推荐标准”和“为什么是这家企业”是否是同一件事？

User choice:

确认区分。同一产业、同一标准版本下，候选企业共用一套 `入选标准`；每家明星企业展示各自不同的 `入选理由`，说明它在共用标准下匹配的具体亮点和可展示证据。页面首屏展示企业入选理由，`查看入选标准` 展示产业共用标准的适用范围、候选范围、版本、已确认维度和更新时间。企业不得各自拥有一套不同标准。

Rationale:

共用、版本化标准才能保证同一产业中的明星企业选择可比较、可维护和可追溯；企业级理由保留个体差异，能解释为什么是这一家而不是只给出抽象规则。若每家企业各有独立标准，则属于人工案例挑选，不应再被表述为按标准推荐的明星企业。

Impact on plan:

产品与 UE 文档中“推荐依据 / 推荐口径”统一细分为“企业入选理由 / 产业共用入选标准”。后续只需补充共用标准和企业理由字段，不再将企业理由误写为独立推荐标准。

Status:
Confirmed

## Decision 165

Question:

原需求中的“各未来产业”应覆盖企业总览的哪些内容？“科研人数”采用什么指标口径？

User choice:

确认。原始“企业整体概况”中，`各未来产业`只作为企业总体数量和企业分布的统计分组口径，不推导为所有企业卡片、表格、节点或明星企业必须展示的实体类型标签；如后续新增跨产业企业对象列表，`所属未来产业`仅作为待确认的产品增强。科研人数确定展示为产业科研人数规模，不以企业从业者总人数替代。

Rationale:

原文在企业总体数量与企业分布中明确写有“各未来产业”，而科研人数仅描述产业中人数。严格按功能点归位，可避免把统计分组扩大为全部实体字段要求，也避免把科研人数误做成全体从业者规模。

深圳企业介绍中的“各未来产业”如何归位？

## Decision 167

Question:

完整实施方案中的科技专题服务，是否应将“各产业”理解为传统产业、战略性新兴产业与未来产业的全量范围？

Rationale:

完整方案在科技专题服务的专题全景中明确提出“对八大未来产业的综合情况进行全面介绍”，并规定可进入“某个产业”查看产业链、细分产业与关联企业。内容运营侧也将未来产业链图谱作为产业全景维护对象。相比之下，战略分析的目标产业表述属于另一层分析能力，不能用于改写门户范围。

Confirmed

## Decision 174

Question:

内部评审模式的目标、可见范围和默认状态是什么？页面内需求追溯应按页面还是按模块展示？

User choice:

内部评审模式用于让评审者切换视角、核对需求与实现、记录问题。所有内部用户默认开启；开关仅隐藏/显示评审相关信息，不改变业务权限。页面内追溯按小模块粒度展示，例如“未来产业企业数量排名”只展示该模块对应的原始要求、当前解释和验收口径，不展示整块 E-32 需求。

Rationale:

评审信息需要支撑逐项走查，但整块需求直接挂在卡片上会遮挡业务内容、降低定位效率，也无法表达组件级的需求与实现关系。权限与评审信息必须分层，避免评审模式成为越权开关。

Impact on plan:

后续评审模式采用“全局汇总 + 小模块内联”的两层信息架构：全局层汇总角色、页面状态、USM/TRACE、会签和问题；模块层只呈现局部需求片段、相关指标/Mock/开放项和验收点。远端演示链接默认进入评审信息可见状态，不需要额外分享参数来开启评审模式。

Confirmed

## Decision 175

## Decision 176

Question:

评审模式中，需求追溯编号与数据状态应如何分层，并由谁控制可见性？

保留现有需求、用户故事、指标、开放项和评审门禁等不同编号体系的语义边界；不把它们混作同一种“追溯号”。所有面向评审的状态标识（包括 `ⓘ` 需求/指标说明、`🧪` Mock 或待接入、`⚠️` 开放项或风险）统一由内部评审模式控制显示或隐藏，关闭评审模式后不在正式业务界面露出。

## Decision 177

Question:

内部评审模式应仅作为页面显示开关，还是作为有完整步骤的评审辅助流程？

内部评审模式作为独立的评审辅助产品流程梳理，不仅定义页面开关。它覆盖进入评审、选择视角、逐模块核对追溯与状态、记录问题、修订后复核和会签归档；业务页面仅作为承载面。

Impact on plan:

Confirmed

## Decision 179

Question:

Draft《需求追溯标号规范》中的自定义 `REQ-*` 编号规则如何处理？

删除该 Draft 文档及其自定义编号规则；保留其中“模块标题旁评审浮层、局部原文核对、演示—联调—上线处理”的交互定义，迁入《内部评审模式：产品流程与状态定义》。后续正式追溯只使用当前模块 TRACE 的验收叶子与 `md_ref`，不新增页面私有需求编号。

Rationale:

`REQ-*` 与验收目录叶子并存会形成两套需求编号真源。保留展示机制但收敛来源锚点，能避免后续文档和前端继续按历史 Draft 扩散编号。

Impact on plan:

历史文档中的 `REQ-*` 文本仅作历史梳理痕迹；后续 USM、TRACE、IA、Wireframe、派单和评审模式统一引用验收目录叶子、bid 原文位置与模块 TRACE。

## Decision 180

Question:

评审模式中的原型说明、交互规则说明与联动边界提示，是否属于正式业务交付内容？

User choice:

不属于。它们是评审辅助说明，可在必要时挂载到评审模式下，用于核对需求与实现；关闭评审模式后不显示。真实业务控件、业务数据结果、面向用户的即时反馈和空态仍须保留，不能因关闭评审模式而消失。

Rationale:

交互规则需要让评审者理解实现依据，但把这类解释当作业务文案会污染正式页面，也会把评审材料误认为交付功能。

Impact on plan:

后续按“评审辅助说明 / 业务交付内容 / 用户操作反馈”三类逐项审查 Demo；说明类内容通过 reviewMode 控制，业务行为和必要反馈不受该开关影响。

Confirmed

## Decision 181

## Decision 182

Question:

评审模式的内容显隐边界是否仅适用于 E-32 企业整体概况？

User choice:

不是。评审辅助说明、业务交付内容和用户操作反馈的三类划分，以及关闭评审模式后的处理方式，作为所有业务模块复用的通用契约。E-32 只记录首次应用时的具体文案和挂载位置。

Rationale:

如果由各模块自行决定什么是评审信息，正式页面会出现不一致的评审残留，后续实现和验收也无法统一。

Impact on plan:

后续模块只引用《内部评审模式：产品流程与状态定义》§4.3，并在各自 IA/Wireframe 补充具体内容清单；不得改写通用显隐边界或新增模块私有规则。

Status:
Confirmed
