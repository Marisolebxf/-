## Decision 001

Question:

本次需求梳理使用什么工作方法？

User choice:

使用 `Ask_Why` 进行项目需求梳理。

Rationale:

该任务属于产品需求整体梳理，存在目标产物、系统边界、模块重组方式和输出粒度等方向性选择。提前用 Ask_Why 记录计划、决策和开放问题，可以降低后续返工。

Impact on plan:

本轮先进行产品需求归位和决策收敛，不直接进入代码实现或 UI 改版。

Status:
Confirmed

## Decision 028

Question:

当前提取文档对应的产品边界应如何命名？

User choice:

科技专题服务系统 · 智能查询与战略研判子系统。

Rationale:

科技专题服务系统本身覆盖六大模块，是完整系统；当前提取文档和当前实现主要覆盖“科技专题数据查询 + 科技专题战略分析”，因此更适合定义为完整系统下的子系统，而不是完整科技专题服务系统本体。该命名既保留上级系统归属，又避免当前实现假装覆盖完整六大模块。

Impact on plan:

后续产品核对、派单和差距分析应使用“科技专题服务系统 · 智能查询与战略研判子系统”作为当前实现/当前梳理范围的产品边界；完整科技专题服务系统仍保留六大模块边界。

Status:
Confirmed

## Decision 029

Question:

数据查询应该如何定位？

User choice:

先作为独立能力定义，允许实现时分散嵌入各专题。

Rationale:

提取文档中“科技专题数据查询”是独立能力，包含综合智能查询、统一结构化结果展示、推荐图表、自定义图表和图表面板管理，不只是各专题页面里的搜索框。但在实现层面，查询入口可以分散嵌入企业、产业、政策等专题场景。

Impact on plan:

后续产品结构应保留“数据查询”作为子系统底座能力；实现对照时允许分散入口，但必须检查是否有统一查询规范和结果态闭环。

Status:
Confirmed

## Decision 030

Question:

战略分析八个子域如何处理？

User choice:

需求边界保留八个子域，页面实现允许聚合，但必须能追溯到每个子域。

Rationale:

八个子域来自提取文档，是“智能查询与战略研判子系统”的完整研判对象边界。页面层可以为了交互效率和信息架构进行聚合，但不能丢失技术链、产业链、企业、科研机构、人才、政策、产业服务链、综合智能分析任一子域。

Impact on plan:

后续文档侧结构保留八个子域；实现对照时不要求一子域一页面，但要求每个子域有明确承载页面或功能入口。

Status:
Confirmed

## Decision 051

Question:

对比篮一期怎么落地？

User choice:

按推荐项定：模块内入口常驻，全局篮轻量承接。全局篮一期只做统一入口和对象汇总，不急做复杂跨对象分析。

Rationale:

## Decision 083

Question:

企业普通查询初始态如何处理热门场景、示例查询、最近查询 / 查询方案，最近查询如何产生和保留？

## Decision 084

Question:

企业 schema 字段是否按 `必填 / 可选 / 预留` 分级？

User choice:

可以。企业 schema 按 `必填 / 可选 / 预留` 分级。必填字段支撑企业识别、查询、对比、评估、导出和追溯；可选字段用于增强详情和报告；预留字段用于后续产品化和外部系统对接。本期页面不追求展示全部字段，但必须保证必填字段链路完整、缺失可提示、来源可追溯。

Rationale:

Impact on plan:

## Decision 085

Question:

## Decision 086

## Decision 087

Question:

企业总览的五个分析模块应细化到什么交付粒度？

User choice:

确认企业总览按 `总体态势 / 企业类型分布 / 产业领域分布 / 当前区域企业现状 / 重点对象态势` 五个模块细化。每个模块明确展示结果、图表 / 列表形态、下钻动作、导出归口和追溯要求；企业总览作为企业分析入口页，不恢复旧 Tab，不做独立导出和独立后续动作入口。

Rationale:

企业总览不能只停留在模块名称或宏观指标看板层面。它需要承担企业分析入口页职责：先形成可被指标和对象集合支撑的判断，再把发现的企业、产业、链位、风险和引育线索转入后续二级菜单。经逐项确认后，企业总览采用全国视野 + 深圳主场景 + 本地培育对象的区域口径，按分层分析口径驱动全部模块，并通过上下文动作衔接企业查询、画像、对比、评估、风险、引育和分析导出。

Impact on plan:

`企业完整深化规格.md` 在 `企业总览分析结果定义` 下将 `企业总览模块明细` 升级为已确认规格。后续 UE / frontend-agent 可基于该规格拆解实现任务：口径区、总体态势、结构分布、当前区域企业现状、重点对象态势、上下文动作和下钻规则。

Confirmed

企业总览首屏 KPI 不超过 5 个，1440-1920 宽度下必须单行展示，不占两行。已确认默认 KPI 为：企业总数、重点企业数、创新型企业数、近三年新增、风险关注企业数。`综合竞争力均值` 不进入企业总览首屏 KPI，避免提前引入企业评估模型；产业覆盖和链位覆盖归入下方结构分析模块。

Confirmed export boundary:

Confirmed region scope:

企业模块不是只做深圳。原需求支持国家、省、市三级地理维度和从全国到城市逐级下钻；招引推荐从全国企业库筛选目标企业；培育推荐聚焦深圳市内企业。产品口径确认为：全国视野 + 深圳主场景 + 本地培育对象。企业总览中的 `深圳企业现状` 调整为动态模块 `当前区域企业现状`，默认深圳时显示为 `深圳企业现状`；切换北京、上海、苏州、全国等区域时，模块标题和统计对象随当前区域切换，深圳仅作为可选对标对象，不固定展示。

Confirmed page structure:

企业总览采用一页纵向结构，不恢复旧的 `态势概览 / 企业分布 / 重点对象` 强制 Tab。模块顺序确认为：`当前分析口径 -> 总体态势 -> 企业类型分布 / 产业领域分布 / 链位分布 -> 当前区域企业现状 -> 重点对象态势`。如内容较长，仅使用页内锚点导航，锚点只用于定位，不改变页面结构。

Confirmed analysis scope controls:

企业总览口径区采用分层口径，不把产业领域、产业链、链位环节混成一个字段。第一层主口径为 `区域 / 产业领域 / 时间`，常驻展示；第二层细化口径为 `产业链 / 链位环节`，在口径区可见，可收起 / 展开。产业链依赖产业领域，链位环节依赖产业链，默认 `全部产业链 / 全部链位`。产业链和链位环节会影响总览所有模块的统计、图表、对象列表和下钻条件，因此不放入高级筛选深处。时间只作为统计口径，默认最新数据批次 / 当前年度，可支持近一年、近三年、近五年或自定义范围，不作为复杂时序分析入口。

Confirmed action entry boundary:

企业总览不设置独立 `后续动作入口` 区块，不在页面底部重复放置企业查询、企业评估、风险洞察、引育推荐、分析导出等二级菜单入口。跨模块动作只以有上下文的方式出现在 KPI、图表、对象列表和画像抽屉中；全局导航由左侧二级菜单承担。
