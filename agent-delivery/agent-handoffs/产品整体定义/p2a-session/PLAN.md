# PLAN.md

## Current Version
v2.5

## Goal

基于《科技专题数据查询与科技专题战略分析-实施方案摘录.md》进行当前阶段产品需求核对，把“科技专题数据查询 + 科技专题战略分析”从完整实施方案中独立出来，并按本轮新边界重拆：本次只交付专业模式下的 `产业链`、`企业`、`政策`、`产业服务链`、`综合智能分析` 五个模块。

`技术链`、`科研机构`、`人才` 不属于本次工作范围，由其它厂商负责；在本轮文档中只保留为排除项和外部对接边界，不进入后续 UE / frontend-agent 派单。

完整《科技专题服务系统-实施方案摘录.md》仍作为上游来源和完整系统差距参照；当前核对、派单和下一步产品确认优先以提取文档为直接依据。

## Non-goals

- 不直接修改科技专题服务系统前端代码。
- 不先做 UI 视觉改版。
- 不把所有原文子功能机械拆成开发任务。
- 不在未确认边界前输出最终 PRD。
- 不把科技专题服务系统与科技信息展示系统混在一个需求口径里。
- 不在本轮直接展开科技信息展示系统需求梳理。
- 不在差距分析阶段修改当前前端实现。
- 不再把项目管理、信息发布、内容运营、系统支撑作为当前核对主范围；这些只保留为完整系统差距背景。
- 不把技术链、科研机构、人才纳入本次交付能力包。
- 不把由其它厂商负责的模块拆成 UE 或 frontend-agent 任务。

## Core Mechanism

采用 Ask_Why 的产品梳理流程：

1. 以提取文档作为当前直接需求基准。
2. 核对“数据查询 + 战略分析”是否足以解释 `demo-ui-topic` 当前前台实现。
3. 将完整实施方案中的其它模块保留为差距背景，不混入当前前台验收范围。
4. 输出 product-agent 后续确认边界。
7. 将确认事项记录到 `DECISIONS.md`，将未决问题记录到 `OPEN_QUESTIONS.md`。
8. 在 P0 和主要 P1 问题收敛后输出 `FINAL_PLAN.md`。

## Current Risks

- 若继续使用完整实施方案作为当前直接基准，会把项目管理、信息发布、内容运营、系统支撑重新混入当前实现核对，导致范围发散。
- 若继续使用旧八域追溯表，会把技术链、科研机构、人才重新带回本次范围，和用户明确边界冲突。
- 若继续用当前实现命名反推需求结构，会把“企业中心”“门户-产业服务”“门户-政策扶持”等实现 IA 当成需求源，造成产品边界偏差。
- “科技专题服务系统”与“科技信息展示系统”在业务语义和可视化能力上可能有交叉，必须避免混口径。
- 若不先确认目标读者，输出可能在 PRD、研发任务、汇报材料和 UE 说明之间摇摆。
- 若不确认粒度，可能过早进入页面级 UI 或组件级实现。
- 差距分析需要当前实现作为对照；当前实现由仓库结构定位，但仍需要防止把废弃 demo、旧路由或非当前实现误判为有效页面。
- 后续任务链第一阶段只输出 product-agent 派单，UE 和 frontend-agent 不应在产品边界未确认前提前执行。
- 当前实现更偏“专题分析/门户前台”，对源文档中的项目管理、信息发布、内容运营、系统支撑覆盖不足；需要先判断这些是否属于本轮前台差距，还是归入后台/后续域。
- 信息发布管理被归入前台业务闭环后，如果当前实现只有导出/分享等零散动作而没有编辑工具、推送配置页面，应作为关键差距进入 product-agent 确认。
