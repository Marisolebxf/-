> **状态**：🟢 已决议（2026-06-22 团队讨论，**选定方案 C —— 新增产品经理角色**）
> **落地**：已新建 `.cursor/rules/product.mdc`（产品经理人主导 + 可选 `product-agent`）；已同步 `team-collaboration-playbook.md §2`、`README.md` 角色清单
> **作者**：团队 AI agent（草拟）
> **创建**：2026-06-22
> **关联**：`.cursor/rules/product.mdc`（新增）· `team-collaboration-playbook.md §2` · `.cursor/rules/pm.mdc` · `客户决策清单跟踪表.md` · `scope-baseline.yaml`
> **结论先行**：原 12 角色体系中**没有"产品经理（Product Manager）"专属角色**，产品职责被拆散到 PM、UI/UE、架构师三方，存在"产品决策无单一负责人"的结构性缺口。团队评审后选择**方案 C**：新增产品经理角色，专责 PRD / 功能优先级 / 业务口径主动梳理，补齐缺口 #6。下文覆盖矩阵与风险分析保留作背景依据。

---

## 1. 问题陈述

`.cursor/rules/` 下现有 12 份角色规约：`architect / pm / coordinator / frontend / ui / ux / algorithm / data / api / qa / devops / doc`。

其中的 **PM 是"项目经理（Project Manager）"**（见 `pm.mdc`："你是项目经理（人）"），职责为进度 / 范围 / 商务 / 协调，**不是"产品经理（Product Manager）"**。

二者职责本质不同：

| 维度 | 项目经理（现有 PM） | 产品经理（缺失） |
|---|---|---|
| 核心问题 | "如何按时按预算交付？" | "该做什么、为什么做、做成什么样？" |
| 关注点 | 进度、范围守门、商务、风险 | 产品定位、需求规格、功能优先级、用户价值 |
| 关键产物 | `task-registry.yaml`、周报 | PRD、用户故事、功能优先级、产品路线图、验收口径 |
| 决策性质 | 资源/时间权衡 | 产品/业务权衡 |

---

## 2. 产品职责覆盖矩阵

把"产品经理通常负责的 10 项职责"映射到现有体系，看每项**有没有人真正负责**：

| # | 产品职责 | 当前承接方 | 覆盖度 | 缺口说明 |
|---|---|---|---|---|
| 1 | 需求采集 / 澄清 | PM + 甲方（`bid-reference/`） | 🟢 较全 | 招标型项目，需求真源是甲方文档，PM 直接消化 |
| 2 | 产品定位 / 目标用户 | — | 🔴 缺 | 无人专责；隐含在招标书内 |
| 3 | 需求规格（PRD） | UI/UE 的 IA/wireframe + SRS 文档 | 🟡 部分 | 有 wireframe 和 SRS，但非系统化 PRD，偏设计/技术视角 |
| 4 | 功能优先级排序 | 架构师（Epic 拆分）+ `task-registry` | 🟡 部分 | 按技术依赖排，而非产品价值排 |
| 5 | 范围基线管理 | PM + `scope-baseline.yaml`（58 项 ±10%） | 🟢 较全 | 守门机制完善 |
| 6 | **业务口径 / 语义定义拍板** | 甲方 + `客户决策清单跟踪表.md` | 🔴 **关键缺口** | 团队内**无人有权拍板**，全部外包给甲方 + 一张登记表 |
| 7 | 用户故事 / 验收标准 | PM（验收）+ QA（测试） | 🟡 部分 | 偏"测试通过"而非"用户价值达成" |
| 8 | 产品路线图 / 版本规划 | 里程碑（M1/Wave 0…）+ 架构师 | 🟡 部分 | 偏交付里程碑，非产品演进 |
| 9 | 竞品 / 市场分析 | — | 🔴 缺 | 招标型项目，优先级低 |
| 10 | 数据驱动迭代（埋点→改进） | observability + QA | 🔴 缺 | 有可观测性基建，但无"产品分析→需求"闭环 |

**统计**：🟢 较全 2 项 · 🟡 部分 4 项 · 🔴 缺失 4 项。

---

## 3. 最关键的缺口：业务口径拍板（职责 #6）

公约（`00-team-constitution.mdc §3.8`）明确：

> 业务口径决策只能甲方拍板……任何 agent / 角色（含 PM / 架构师 / 数据 Lead）都不能替甲方拍板……试点期间按"团队临时默认值"先跑（标 🟡）。

这条铁律本质上是在**绕开缺失的产品经理角色**：

- ✅ 好处：避免团队内部乱定义业务语义，强制对齐甲方，责任清晰。
- ⚠️ 隐患：
  1. **决策延迟**——每个业务歧义都要等甲方，甲方响应慢则全链路阻塞。
  2. **临时默认值无人统一**——"团队临时默认值"由谁定、是否一致，无单一负责人。
  3. **跟踪表是被动登记，不是主动产品决策**——`客户决策清单跟踪表.md` 记录"待确认项"，但没有角色负责"主动梳理产品语义、减少歧义产生"。

---

## 4. 为什么现状"可能是有意为之"

不急于补角色的合理理由：

1. **项目性质是招投标交付型**：需求真源 = 甲方招标文档（`bid-reference/`）+ 范围基线（58 项功能点），不是内部产品规划，"需求定义"环节天然弱。
2. **轻量团队**：当前阶段 3–5 人（`playbook 附录 A`），增设专职角色有编制成本。
3. **甲方即产品决策方**：业务语义最终归属甲方，团队内设产品经理也无最终拍板权。

---

## 5. 现状的代价（如果继续不补）

| 风险 | 触发场景 | 影响 |
|---|---|---|
| 产品决策真空 | 甲方未明确、又需立即推进 | 各 agent 各自臆测口径，返工 |
| 优先级失焦 | 资源紧张需取舍 | 按技术依赖而非用户价值排，做错重点 |
| 验收口径漂移 | 交付临近 | "做完了"与"甲方想要的"不一致 |
| 跨团队语义不一致 | 同一指标多团队实现 | 算法/数据/前端对同一业务词理解分歧 |

`data-lineage-policy.md` 的"指标 8 件套"和 `客户决策清单跟踪表.md` 是当前对冲手段，但属**事后补救**，非**事前产品定义**。

## 6. 候选方案（供讨论，不预设结论）

| 方案 | 做法 | 适合场景 | 成本 |
|---|---|---|---|
| **A. 维持现状 + 显式声明** | 在 playbook 补一段"本项目不设独立产品经理，产品职责由 PM+UE+架构师共担"，并明确各自分工边界 | 招标范围稳定、甲方响应及时 | 低 |
| **B. PM 角色扩容** | 把产品职责（尤其 #6 业务口径主动梳理）并入 `pm.mdc`，PM = 项目+产品双职 | 团队小、PM 有产品能力 | 中 |
| **C. 新增 `product.mdc` 角色** | 设产品经理（人）+ 可选 `product-agent`，专责 PRD/优先级/业务口径梳理 | 业务复杂、歧义多、甲方响应慢 | 高 |
| **D. UE 角色上移** | 由 UI/UE 团队 lead 兼任产品职责（已在做需求沟通+IA） | UE 偏业务型 | 中 |

> 个人倾向：当前阶段 **A 或 B**（轻量），把"业务口径主动梳理"明确指派给某个现有角色即可，暂不增编。但这是**人来拍板的决策**（涉及编制 / 分工），按公约 §3.1 不外包给 AI。

1. PM + 架构师 lead 评审本稿，确认"是否承认这是缺口"。
2. 若承认 → 从 §6 选方案（A/B/C/D），由 PM 拍板。
3. 落地动作（视选型）：
   - 选 A → 我补 `playbook §2` 一段声明 + 分工表。
   - 选 B → 我改 `pm.mdc` 增加产品职责段落。
   - 选 C → 我新建 `.cursor/rules/product.mdc`。
   - 选 D → 我改 `ux.mdc` / `ui.mdc` 上移职责。
4. 任一改动均需 PM（+ 架构师，如涉铁律）签字。
