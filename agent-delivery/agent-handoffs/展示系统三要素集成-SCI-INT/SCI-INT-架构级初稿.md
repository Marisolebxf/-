## 0. 结论先行

1. **对端依赖几乎全是 third_party**：93 条三要素指标里 84 条 `third_party`，全部 D1=draft、D4=mock。久新 51 行交付形态（SQL 3 / Python 6 / API 42）**一条未确认**，是整条集成的第一闸门。  
2. **有一块「无人认领」的算法缺口**：本范围页面上 A2 判为库 `missing` 的约 49 条（态势 43 + 人才 6），不在久新包里、我方也没有 owner。不先定 owner，页面只能空态。  
3. **契约未冻结**：态势 8 页 lumen 前端已有页面和 `defineApi` 双轨（`/situation/v1/{page}/**`），但 Java 契约 `BE-TS-CONTRACT-01` 仍是 claimed（lock 已于 10-15 过期）。人才 4 子页 lumen **还没有页面**，DS-13～16 也没有 METRIC-OPEN 叶。  
4. **最大技术风险是实体 ID 对齐**：久新模型若基于其自有数据计算，返回的人才 / 机构 / 技术点 ID 必须能对上我方主数据（甲方三方库 + TRSGraph），否则详情跳转、图谱联动、对账全部断。

## 2. 指标与算法层面的集成项

### 2.1 分层

| 层 | 组件 | 本范围职责 |
|---|---|---|
| L0 展示 | `lumen-ui-science-pc` | 数字 + ⓘ（MetricSpecCard）+ 就绪度角标；`defineApi` Mock / 真实双轨；对端失败显示空态 + 角标 |
| L1 Java 业务门面 | `gkxlumen-*`（态势现用 `/situation/v1/**`；人才模块待定） | 页面 DTO 聚合、分页、权限、导出、收藏订阅；**不做算法、不写 nGQL、只读 ADS**；Feign 调 Python |

### 2.2 按实现类型的集成思路

| 类型 / 久新交付形态 | 涉及指标 | 集成思路 | 我方责任层 | 关键约束 |
|---|---|---|---|---|
| **STAT**（6 条） | `M_TALENT_STRUCT_QUERY`、`M_TECH_HEAT_QUERY` / `INVEST_AMOUNT` / `OUTPUT_SCALE` / `PAPER_PATENT_CNT`、`M_ORG_PERF_QUERY` | ETL 从 ODS 预聚合进 ADS，Java 只读 ADS；不经过久新 | L5 ETL + L1 | 口径写进 8 件套；按地域 / 时间粒度预聚合 |

| **页面派生指标**（如 `ATTRACT_SCORE`、`SZ_STATUS`、`PATH_PRIORITY`） | registry 标 third_party，但实为 DEEP 结果的视图 | 挂到母叶 seq，不单独向久新要接口；Java 从快照取字段 | L1 / L5 | 每个派生指标写明母叶与字段 |
