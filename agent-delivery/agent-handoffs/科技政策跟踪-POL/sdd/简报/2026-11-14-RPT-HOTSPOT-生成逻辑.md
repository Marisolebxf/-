## 1. 现状

展示页「政策热点识别」在 `lumen-ui-science-pc` 动向页里。用户点「开始识别」或「重新识别」，才发 `POST /display/v1/policy/panorama/jobs`，体只有 `{kind:热点识别}`，不带领域、不带 `sub_type`。切筛选不会自动发。

`PolicyPanoramaService.syncTrendKind` 见到 `kind` 就只读表，不建任务。`kind` 与 `sub_type` 同时出现时，返回空列表。读面是 element `GET /trend/hotspot`：有领域则 `WHERE domain_name = ?`，没领域则读全表，按 `id` 排序。页面把每行画成序号、热点名称、领域名、一句说明。无行则空态「暂无热点识别数据（缺项表无行）」。读失败只提示「热点识别查询失败」，不清时序图和入库列表。

正式表 `gkxlumenx_gapfill.gapfill_policy_trend_hotspot` 现有 6 行，`fill_method=manual`。科创发展、人才引进、资金扶持各 2 条。说明都以「缺项演示」开头。科创发展是「研发机构布局」「成果转化通道」。列是 `domain_name`、`hotspot_name`、`brief`，外加 `metric_id`（空）、`gap_item`（`205 热点识别`）、`fill_method`、`gapfill_batch_id`、`generated_at`。没有热度分，没有 `is_mock` 列，不挂 `M_POLICY_FOCUS_INDEX`。

三个领域名是产品标签，不是库里的分类列。拿领域名当关键词去挑政策，标 🟡。

## 2. 生成逻辑

调用链：中台页面 → demo 侧 Java REST → Python `/internal/policy/jobs/execute`。Java 不写正文、不调模型。前端不直连 Python。不走展示页那条 `panorama/jobs`，避免和 `syncTrendKind` 的只读分支叠在一起。

一次请求的范围：不传领域，就是科创发展、人才引进、资金扶持三个范围，各写一批。传了领域，只处理那一个。领域只接受这三个名字，其它值直接失败，不写表。

每个范围按下面顺序做，范围之间互不删行：

1. 先读该范围现有行。命中则跳过（「重新生成」见第 5 节）。命中是指：该范围至少有一行，且每一行都是 `fill_method=llm`，并且 `brief` 不以「缺项演示」开头。没有行、仍有 `manual`、或仍有说明以「缺项演示」开头，都算未命中。
2. 未命中才取材。领域名当关键词，在政策标题、摘要、关键词里找，只要正文非空的，按发布日期从新到旧取 8 条。没有发布日期的不占这 8 条。一条都摘不到：不写新行，不删旧行。
3. 把这最多 8 条正文交给模型。模型返回若干条，每条只有热点名称和一句说明。不返回热度分、焦点指数、文件。
4. 合格条才准备入库：名称、说明都非空；名称不超过 128 字，说明不超过 512 字。`fill_method=llm`，`gap_item` 仍是 `205 热点识别`，`metric_id` 仍空，`is_mock` 的语义是 1（D4 保持 mock，本波不把就绪度改绿）。现表没有 `is_mock` 列，本波不加列。
5. 该范围合格条达到第 5 节确认的条数后，在同一个事务里先插入新行，插入全部成功再删除该范围旧行。事务失败则回滚，旧行仍在。不另写以「缺项演示」开头的句子。无密钥或模型失败与摘不到正文相同：该范围不动。
6. 只写 demo 库里的同名表 `gapfill_policy_trend_hotspot`。不写 `gkxlumenx_gapfill`，不写影响表、深度报告表、主题分布表。

## 3. 中台菜单看见什么

中台 `demo-ui-system-test` 单独一个菜单，名称就是「热点识别」。不和影响评估、深度分析报告放在同一个菜单里。

菜单上有领域选择：不限，或三个领域之一。主按钮是「生成」。点下去之后，每个被处理的领域各占一行状态：已命中跳过、生成中、成功并写出几条、失败及原因（摘不到正文、无密钥、模型失败、条数不够）。

成功后的列表只显示领域、热点名称、一句说明。不显示热度分。失败的领域旁边仍是该领域的旧行；demo 库里本来没有旧行时，该领域就是空列表加失败原因。三个领域一起跑时，成功的领域显示新行，失败的领域留旧行，两边同时看得见。

菜单不打开展示页，不做 PDF / Word。

## 4. 迁 lumen 时页面怎么保持

迁移只换正式表里的行。`lumen-ui-science-pc` 本叶不改：标题仍是「政策热点识别」，按钮仍是「开始识别 / 重新识别」，请求仍是 `{kind:热点识别}`，不带领域、不带 `sub_type`。`syncTrendKind` 仍只读 `gkxlumenx_gapfill`。

迁进去的规则与第 2 节第 5 步相同：某领域的新行在正式表插入成功之后，才删该领域旧行。没迁到的领域继续显示现在的句子。科创发展在被换掉之前，点识别仍看到「研发机构布局」「成果转化通道」，说明仍以「缺项演示」开头。

展示页上的「重新识别」仍是再读一次表，不在展示页重算。不点按钮不生成。时序、主题分布、影响评估弹窗、深度分析报告弹窗保持原样。

## 5. 待确认

第一项为推荐。

1. **一个领域怎样算命中**
   - 推荐：该领域每一行都已是 `fill_method=llm`，且说明都不以「缺项演示」开头，并且至少有一行。还混着演示行就整域重写，写成功后整域换掉。
   - 备选：只要已有一条合格的 `llm` 行就跳过。没换掉的演示行会继续出现在列表里。
2. **每个领域写几条**
   - 推荐：固定 2 条，与现种子每域 2 条一致。凑不满 2 条合格行，该领域不算写成功，旧行保留。
   - 备选：至少 1 条、最多 5 条，有几条合格写几条。
3. **一个领域失败时，同一次里其它领域怎么办**
   - 推荐：各写各的。失败的领域不删旧行；已经写成功的领域保留新行。
   - 备选：同一次里有一个领域失败，另外两个已经写下的新行也回滚。
4. **菜单要不要「重新生成」**
   - 推荐：要。「生成」遇到命中就跳过；「重新生成」无视命中重算，失败仍不删旧行，成功后才换该范围旧行。
   - 备选：只有「生成」。命中就停，重算留到以后的批量。
5. **demo 写到哪个库，`is_mock` 要不要成列**
   - 推荐：表名和列与正式表相同，不加 `is_mock` 列。`is_mock=1` 只表示这次正文是模型补齐、D4 仍是 mock。落在 demo 实例里当前账号写得进的库，开工时核对库名。不写 `gkxlumenx_gapfill`，也不把热点行写进 ADS。
   - 备选：坚持写 `demo_gkxlumenx_gapfill`，并给 demo 表加 `is_mock`。该库应用账号若仍无权限，本叶停下，不改写到别的库。
