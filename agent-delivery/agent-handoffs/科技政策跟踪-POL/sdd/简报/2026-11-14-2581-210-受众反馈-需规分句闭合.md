### 卡 1 · 210-2 「收集工具」口径

- 背景：需规写「提供政策受众反馈收集**工具**……**收集**……评价和建议」。现实现（已签收 ARCH）是「缺项表 + 只读展示」，无受众提交入口。缺陷即按此字面报出。
- **（推荐）选项 A · 维持已签收架构，缺陷按「口径澄清」处理**：不改代码。产出=给缺陷回复说明 210 按 D18 例外实现（2026-11-03 淮政玮签收），补一行说明书「收集=多渠道行聚合同位展示，无受众提交表单（有意不做）」+ 合规用例补「收集形态」期望句（面板即工具、无提交按钮为预期）。影响层：文档/用例。代价：最小。风险：若甲方验收坚持「可提交」，仍会 reopen。
- 选项 B · 补浏览器端收集表单（不入库或写 localStorage 演示）：FeedbackPanel 加「提交反馈」表单（渠道/评分/意见），提交只留在浏览器（参照 236-1「信息反馈与互动」先例：提交不回写接口）。影响层：FE 单文件。代价：小。风险：演示「可提交」但数据不落库，需 MockBadge/演示标注；且与 ARCH「不写死问卷或评价」精神需再确认。
- 选项 C · 全链路收集（FE 表单 + Java 写接口 + gapfill 表写通道）：真实收集落库。影响层：FE+Java+Python（灌数脚本要加写路径）。代价：中偏大，且 D18 例外语境下 gapfill 表语义是「灌入 mock」，混入真实提交行要重新定表语义。风险：超出 P1 缺陷合理范围，可能违反「最小安全变更」。
- 请选：**可行（按推荐 A）** / 改用 B / 改用 C / 先改计划 / 本次只归档
