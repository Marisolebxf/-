## 2. 标准应答 SOP

### 2.1 "这个数字哪来的？" — 标准 3 步答

> 站起来或指向屏幕，3 步操作 + 一段话：

**操作 1**：手指 UI 上数字旁的 ⓘ 图标，"我点开数据说明卡给您看"
**操作 2**：MetricSpecCard 展示 metric_id 8 件套
**操作 3**：底部按"查看完整加工链路" → DataLineageDrawer 展示 ODS→DWD→DWS→ADS 4 段血缘图

**配合话术**：

> "这个指标是 **{中文名}**，metric_id 是 `{M_xxx}`。数据来源是 **{source_systems}**，更新频率 **{update_freq}**，当前口径版本 **v{version}**。完整加工过程是从我们的源系统抽取后经过 4 段处理：贴源 ODS → 清洗 DWD → 主题宽表 DWS → 应用层 ADS。您可以在我们的 cfg_metric 注册表里查到完整定义。这套机制保证**每个数字都有身份证**，不会出现说不清来源的情况。"

**关键点**：
- ✅ 主动展示，不躲闪
- ✅ 用专业术语（ODS/DWD 等）但配合通俗解释
- ✅ 强调"机制"而非单点
- ❌ 不要说"应该是" / "大概是" / "我们后端那边"

---

### 2.2 "怎么算的？" — 加工过程

**操作**：MetricSpecCard 中点开 `formula` 字段，配合 mermaid 加工链路图。

**配合话术**（按指标类型分）：

#### 计数类
> "这个数字是 **{统计窗口}**内 **{对象范围}** 的数量，按 **{去重字段}** 去重。源码在 `innov-algo-demo/pipelines/{xxx}.py`，由数据治理委员会评审过的口径。"

#### 占比 / 率类
> "这个百分比 = **{分子定义}** ÷ **{分母定义}** × 100%。分母和分子的取数范围**严格一致**（同 quarter / 同行政区域 / 同审批状态），不会因为分子分母错位产生失真。"

#### 趋势类
> "这是 **{时间窗口}** 的时间序列：每个时间点统计 **{对象范围}**，按 **{聚合方式}** 计算。坐标轴均匀刻度，零基线，**不做断点处理**（避免视觉误导）。"

#### 排名 / TopN 类
> "这是按 **{排序字段}** 降序取的前 N 名。同分情况下按 **{第二排序字段}** 兜底，避免视觉跳动。底部的 TopN 阈值口径与历史报告**完全一致**。"

#### 评分 / 指数类（最容易被追问）
> "这是综合指数，由 **{N 个分项}** 加权得出：
> - 分项 A 权重 {x%}：{含义}
> - 分项 B 权重 {y%}：{含义}
> - ...
>
> 权重由 **{业务方 / 数据科学家 / 委员会}** 评审确定，记录在 cfg_metric.formula 中。当前是 v{version}，**口径版本变更全部进 changelog**，可审计。"

**关键点**：
- ✅ 每个公式都能溯源到具体业务规则或人/委员会决策
- ❌ **永远不说**"这是 AI 算的"（甲方会立即追问"AI 怎么算" → 答不上 → 信任崩盘）

### 2.3 "这个 X% 是什么意思？" — 口径定义

> 翻评审材料 §2 单指标完整说明卡中的 `definition` 字段，**逐字念**：

**话术**：

> "这个指标的官方口径定义是这段（指着评审材料念）：'**{definition 原文}**'。这段定义经过 **{数据 lead / 业务接口人}** 拍板，与 bid-reference 章节 §{bid_ref} 完全对应，不存在团队内部理解差异。"

**关键点**：
- ✅ 念原文，不即兴改述
- ✅ 强调"经过人拍板"
- ❌ 不要说"应该是..."

---

### 2.4 "你们是不是用的假数据？" — Mock 识别（Wave 0 评审最常见）

**操作**：手指数字旁的 🧪 MockBadge，"您看，这里有🧪标志，明确告诉您是 Mock 数据"。

**话术**：

> "您观察很准。本次评审处于项目 **Wave 0 设计验证阶段**，目的是先**对齐字段、信息架构、用户交互**这 3 件事是否符合您的需求。数据全部用 Mock，但有 3 件事我们已经做扎实了：
>
> 1. **每个指标都有身份证**（metric_id），已注册到 cfg_metric 表
> 2. **加工链路 4 段已设计完整**（ODS→DWD→DWS→ADS）
> 3. **Mock 与真实数据切换零代码改动**（只切换 cfg_degrade_switch）
>
> Wave 1 数据工厂接入真实三方源后，您看到的所有数字会**自动**变成真实值，🧪 标志自动消失，每个数字旁点 ⓘ 都能看到真实的 source_systems 和加工链路。"

**关键点**：
- ✅ 主动承认 Mock，不掩饰
- ✅ 转化为"专业准备"的体现（Mock 不是偷懒，是契约先行）
- ❌ 不要说"那个等以后再说"

### 2.5 "什么时候是真的？" — wave 路线时间表

**操作**：翻评审材料 §6 真实数据接入计划。

**话术**：

> "我们的 wave 路线（指评审材料表）：
> - **Wave 0（当前）**：契约先行 + Mock 验证；ADS 标准表 + 8 件套全部就绪
> - **Wave 1（约 X 月）**：数据工厂接入，三方源贴源 → DWD 清洗 → DWS/ADS 真实数据；预计 {YYYY-MM-DD} 完成 E7 政策要素首条垂向
> - **Wave 2（约 X 月）**：企业 / 产业链 / 技术链
> - **Wave 3+**：剩余要素 + 综合分析
>
> 每个 wave 完成时**与您单独评审**当 wave 涉及的指标，避免一次性给您太多信息。"

**关键点**：
- ✅ 给具体 wave 名字 + 大致月份
- ✅ 强调"分批评审"而非"全部完成才看"
- ❌ 不要给精确日期（除非有 100% 把握）

### 2.6 "这个指标和那个指标对不上" — 口径冲突

**操作**：打开评审材料对比两个指标的 `definition` 字段。

**话术**：

> "您观察很对。两个指标**口径不同**：
> - **{指标 A}**：定义是 '{def A}'，统计 **{窗口/范围}**
> - **{指标 B}**：定义是 '{def B}'，统计 **{窗口/范围}**
>
> 表面相似但本质是两个**独立指标**，对应不同的业务问题：
> - 指标 A 回答的是 **'{业务问题 A}'**
> - 指标 B 回答的是 **'{业务问题 B}'**
>
> 如果您觉得 UI 上让人混淆，我们可以加更明确的标题或 tooltip。这是 **UX 改进项**，记入今天评审反馈，本周内提供方案。"

**最坏情况：现场答不出来怎么办**

> "您这个问题非常重要。两个指标的差异**应该**有清晰口径，但我现场不敢即兴回答，避免给您不准确信息。我让数据团队 **24 小时内**单独给您一份详细对比说明，包含：①两个口径的精确定义 ②数据源差异 ③推荐如何选用。今天评审记录里这点单独列出。"

**关键点**：
- ✅ 接受"现场答不出"是合理的
- ❌ 不要硬答

---

### 2.7 "怎么保证更新及时？" — 更新频率

**话术**：

> "我们每个指标在 cfg_metric 中明确登记 update_freq 字段（daily / hourly / monthly 等），由数据工厂 ETL 调度保证按时跑批，调度日志 Grafana 可查。如果某次跑批失败，告警自动推送到运维群，**不允许界面静默使用过期数据**。所有界面会显示 **'数据最后同步时间'**，超过预期更新窗口会变橙色提示。"

---

### 2.8 "数据安全吗？" — 治理合规

**话术**：

> "我们在 cfg_metric 中给每个指标打了 governance_tags（公开 / 敏感 / 脱敏 / 内部）。敏感字段（如个人手机号、引进成本）走两层控制：① 网关层按用户角色脱敏 ② 应用层审计日志（任何查询写 Loki audit 日志）。展示层默认对所有角色脱敏，**点击'申请查看'触发 SSO 角色校验 + 审计**。所有数据传输 TLS 加密，存储符合等保三级。"

---

### 2.9 "我能要明细吗？" — 下钻

**话术**：

> "可以。UI 上每个统计数字都支持点击下钻 → 详情抽屉 → 明细列表 → 单条记录详情。明细可按权限导出 Excel / PDF / CSV。**导出行为自动记入审计日志**，便于合规追溯。"

**如果是 Wave 0 阶段还没实现明细**：

> "本期是字段层评审。明细下钻在 Wave 1 实现，wireframe 中已经预留了下钻入口（指 wireframe §1.1.1.1.4.6.1.3 成果详情）。Wave 1 完成后我们专门给您评审下钻体验。"

---

### 2.10 "我有个新指标要加" — 范围扩展

**话术**：

> "好。新指标我现场不答应纳入，避免影响已经对齐的 ±10% 范围基线。流程如下：
>
> 1. 评审会**记入新需求清单**（不是拒绝）
> 2. 会后 PM + 数据 lead + 架构师 **48 小时内**评估：
>    - 是否在合同范围内（落入 ±10%）
>    - 数据源是否就绪
>    - 实现复杂度 + 影响其他指标
> 3. 评估结果给您**书面反馈**：纳入 / 申请变更 / 暂缓
> 4. 任何变更走正式 change_log（记入 scope-baseline.yaml）
>
> 这是为了**保证我们承诺的事 100% 兑现**，新事项有序纳入。"

**关键点**：
- ✅ 不当场答应（避免范围爆炸）
- ✅ 也不直接拒绝（甲方有面子）
- ✅ 给具体流程 + 时间承诺

## 3. 极端情况话术

### 3.1 现场完全答不出来

> "您这个问题切中要害，但我现场不敢凭印象回答。我让 {负责人} 在 **48 小时内** 给您正式回复，包含 ① 完整答案 ② 是否需要修改我们的指标定义 ③ 修改的影响范围。今天评审记录单独列这一项。"

### 3.2 甲方质疑某个数字"明显不对"

> "您一线经验最熟，这个数字与您的预期差距大，说明 ① 我们的口径与您的理解可能有差异 ② 或者 Mock 数据偏离真实分布。请帮我们把您预期的值/范围告诉我们，我让数据团队对照口径定义和 Mock 生成器，**今天下班前**找到原因 —— 是口径调整还是 Mock 重新生成。"

### 3.3 甲方说"你们做的太复杂 / 太简单"

> "感谢反馈。我们今天主要看 ① 字段是否对齐您的需求 ② 信息架构是否符合您的工作流。视觉的繁简、交互的复杂度，我们在 Wave 1 工程化阶段会按您今天的反馈再调整。今天能否优先帮我们 review 字段和信息层？"

## 4. 评审中可以主动说的"加分话术"

> 用于显示团队专业度。在合适时机抛出。

### 4.1 关于数据治理

> "我们项目从设计期就建立了 **数据血缘规约 data-lineage-policy.md**：每个指标必须有 8 件套元数据（metric_id / 口径定义 / 公式 / 源表 / 源系统 / 更新频率 / 版本 / 负责人）。这套机制保证未来任何指标变化都可追溯、可审计、可回滚。"

### 4.2 关于人机分工

> "在我们的工程化交付模式里，**AI agent 出量，人做决策**。指标口径必须由数据 lead 拍板，AI 只负责把决策落到 cfg_metric 表和代码里，并维护一致性。这就避免了'AI 自由发挥导致口径不一致'的问题。"

### 4.3 关于可观测性

> "界面上每个数据请求都带 traceId，从前端到 Java 到 Python 到数据库**全链路可追踪**。Grafana Tempo 抽样可见每个数据点是如何被计算和传输的，便于您审计任何一次展示。"

### 4.4 关于评审材料

> "今天给您的评审材料是 **doc-agent 自动从 cfg_metric 注册中心汇编**的，不是人手编。意味着 ① 永远与代码一致 ② 不会出现文档过期 ③ 任何口径变更下次评审自动反映。"

## 5. 评审现场禁用话术（红线）

| ❌ 不能说 | 原因 | ✅ 替代说法 |
|---------|------|------------|
| "应该是..." | 不专业 | "口径定义是..."（念原文） |
| "我们后端那边..." | 甩锅 | "数据组 / 算法组 / 业务方负责，metric_id 注册了..." |
| "AI 算的" | 不可控 | "算法在 innov-algo-demo 仓的 xxx.py，由算法 lead 评审过" |
| "估计 / 大概" | 含糊 | "精确数字是 ... 来源是 ..." |
| "这个没想到" | 准备不足 | "现场不答，48 小时内书面回复" |
| "您随便看看" | 不自信 | "请重点关注 字段层 / 信息架构层 / 交互层" |
| "AI 出问题了" | 推责 | "口径或实现有偏差，原因正在排查，{时间} 给您反馈" |
| "我们尽量" | 不承诺 | "我们承诺 {具体时间} 之前 {具体动作}" |
| "甲方一直要" | 表明被动 | "您的需求很合理，我们的方案是..." |
