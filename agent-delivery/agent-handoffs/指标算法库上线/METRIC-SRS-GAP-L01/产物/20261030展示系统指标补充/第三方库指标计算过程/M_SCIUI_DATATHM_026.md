## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/应用视窗/KPI 概览（应用视窗 Tab 区顶栏）。UI 实际挂载：`ApplicationWindow.jsx:1264-1271` 主组件渲染的 `{applicationKPIs.map(...)}` → `<AppKPICard data={kpi} />`（`:42-58` KPI 卡组件：label/value+unit/trend 箭头+change 百分比）——第二卡 `{ label: '应用系统数', value: '147', unit: '个', trend: 'rise', change: 12.3 }`（`mockData.js:1667-1669` `applicationKPIs` 数组）。**mock 纯演示挂载披露（本件特有）**：KPI 卡的数值直接取自 mockData 常量（无任何组件内计算/聚合路径），与 024 的明细侧（数组求和路径）不同——mock 挂载件的读数连「派生逻辑」都不存在，147 是纯手写演示值（B10 不作数据证据）。第一卡「资产调用总量 285.6 万次」与本卡构成 KPI 双卡。

### 1.2 为什么需要本指标

KPI 卡是视窗的「一眼结论」层：用户进入应用视窗首先看到两个数——数据被用了多少次（调用总量）、被多少个系统在用（应用系统数）——后者是平台数据**流通广度**的 KPI 化表达。与明细侧（024 的业务应用 Tab）的关系是「总-分」结构：KPI 卡给总量锚，明细表给场景分布（每场景多少应用）。官方对应物同 024：省级调查表（R2）的挂接接口计数、上海平台（R3）的应用注册库——平台侧应用数是标配 KPI。本件的存在价值提示：同一指标在 UI 有多个读数位时，**必须同源计算**——mock 的失配（147 vs 162）正是反面教材。

## 二、计算过程

### 2.1 方法选择（文献依据）

与 024 共用登记面计数法（R3 注册制工程对偶），本件不重复展开。本件的特有方法是**读数位对账法**：同一指标的多个 UI 读数位必须同源——mock 侧用「KPI 卡值 vs 明细聚合值」互证（§2.2），真实数据侧的对应工程约束是「KPI 卡直读登记面计数，不得手填」。

### 2.2 KPI/明细双侧对账（本件核心证据）

四步对账全落产物：①KPI 侧读数 147（`mock_kpi_value`，`mockData.js:1668`）；②明细侧合计 162（`mock_detail_side.appcount_sum`——6 场景 appCount 45+32+28+23+19+15，024 件主证据）；③失配差 −15（`mock_kpi_vs_detail_diff`=147−162，分子 KPI 值/分母明细合计）；④失配幅度 9.26%（`mock_kpi_vs_detail_gap_pct`，分子 \|147−162\|=15、分母 162）。**KPI 双卡内对照**（`mock_kpi_pair`）：第一卡「资产调用总量 285.6 万次」=2,856,000，与 `cumulativeCallAnalysis.summary.totalSinceLaunch` 同值（mock 内部自洽）；第二卡「应用系统数 147」≠明细 162（未对账）——同一 KPI 行一卡对一卡错，证明 147 是独立手写值非聚合结果。

### 2.3 mock 挂载形态披露（本件特有）

本件是 mock 纯演示挂载件：KPI 卡数值直接取自 `applicationKPIs` 常量数组，组件内无任何计算/聚合路径（对比：024 明细侧至少有「数组求和」的派生形态；023 主体侧有 useMemo 聚合）——读数连演示性的派生逻辑都不存在。此类挂载的披露写法（B10）：值、单位、环比（147 个/+12.3%）全部标注「mock 演示值，不作数据证据」；正式版 KPI 卡必须绑定登记面计数查询，禁止手填。

### 2.4 口径敏感性

与 024 共用三层口径披露（去重键/状态过滤/场景归属不重复），本件追加 KPI 特有约束：跨场景共用的应用系统在「明细列合计」路径会被重复计入（场景行各计一次），KPI 直读路径不会——两路径天然可能不等，**必须以登记面去重计数为唯一真值源**，明细列改为「场景×应用」关系表的非重复归属计数。此约束是合并交付的工程规格之一。

## 四、数据缺失情况

### 4.1 与 024 同根：接入登记面零承载（结构级）

本件缺口与 024 完全同根（接入登记面「表不存在」），修复动作同一（六列新表或 OAuth 扩列）——不重复展开，详见 024 件 §4.1。本件追加的 KPI 工程规格：①KPI 卡绑定登记面计数查询（禁手填）；②明细列合计与 KPI 直读必须同值（唯一真值源=登记面去重计数）。

### 4.2 mock 纯演示挂载的展示风险（本件特有）

mock 挂载件无派生逻辑的读数位，正式版最容易残留手填值（前端「先随便写个数」的惯性）——风险登记为**高**：KPI 卡 147 若不被替换，用户会把演示值当真实运营数。缓解：上线前 KPI 卡数据绑定检查（无查询绑定的卡片一律「暂无数据」态）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 接入登记面（与 024 共用） | 数据工程 | 本件 + 024 + 023 联动 | 触发器①（族内最低门槛） |
| 024/026 合并交付 | 口径裁定（台账登记） | 本件 + 024 | 一处计算两处展示（§1.7） |
| KPI 卡绑定检查 | 前端工程 | 本件 UI | mock 147 → 登记面读数或「暂无数据」 |

档位后果：登记面 → **完全直接支持**（两件同步）；现状 → 部分支持（null）。推荐顺序：合并裁定先行（避免两处各建一套口径），登记面随族级工程。
