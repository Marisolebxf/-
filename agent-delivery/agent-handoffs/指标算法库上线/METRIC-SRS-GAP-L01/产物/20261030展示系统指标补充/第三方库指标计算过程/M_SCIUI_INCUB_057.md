## 一、需求定义概述

### 1.1 所属功能模块

科技信息展示系统 → 科技成果展示 → 大型科学仪器共享/**服务统计**。服务统计窗四宫格的「热门仪器利用率排行」卡片支持点击选中仪器（`:1442` 图 + `:1456` 点击联动），选中后统计详情区展示五项读数：利用率/预约量/服务次数/状态/所属机构（`:901-905` statisticRows）。「预约量」= `formatNumber(instrument.reservationCount)` + 「 单」。同字段另有两处消费：KPI 区「预约申请」合计（页面顶部汇总）、月度预约趋势的缩放基线（`buildScaledMonthlyReservations` 按 reservationCount 合计占比缩放）——三消费点共享同一 mock 字段族。

mock 值（128/156/89/42）为演示常量，不参与支持度结论。

### 1.2 为什么需要本指标

单台预约量回答「这台仪器抢不抢手」：创业者遴选仪器时与利用率并读（预约多=排队预期长）；管理侧识别高需求设备作扩容依据。SRS 上位功能（使用评价与频次统计）要求「自动收集仪器的使用频率」——预约量是需求侧频次读数。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「仪器预约量」指标名未出现；SRS 只有功能行为句，没有计数口径（累计 vs 年度、取消单剔除与否、单位单/次）。

### 1.4 类似指标权威方法可行性分析概要

预约量类指标在官方体系的对应物是科技部考核口径的「有效订单数」（SRS 附录 A 引深圳平台 2020 年末 1,336 个）与国家网络管理平台「对外服务成效」。方法族对照：

## 四、数据缺失情况

### 4.1 预约流水零承载（结构级，主因）

单台预约量的材料是订单流水（仪器×用户×时间），三源无镜像。四缺失情形归属：**表不存在**。修复动作是**订单系统对接**，库内无法构建。

### 4.2 派生列连带缺失

reservationCount 属流水派生列——即使台账接入也无此列，须由流水定时聚合物化。验收时流水表（根）与物化列（果）分开。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 接入预约订单系统 | 外部系统对接 | 本件 + INCUB_035 + SOFTSCI_010/015 + INCUB_007/008/019 | 流水原生存在 |
| 单台预约量物化列 | 数据工程 | 本件 + KPI 合计 + 趋势缩放 | 由流水定时聚合 |
| 单位口径裁定 | 产品裁定 | 本件 | 单 vs 次（§3.4） |

档位后果：流水接入 → 完全直接支持；仅机时日志 → 完全转换支持；无动作 → 维持完全不支持。推荐：与 INCUB_035 合并推订单系统一揽子对接（同根一源解一族）。
