## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/接入视窗/历史资源接入情况（1.1.1.1.4.4.2.3，挂靠 seq 362——组件注释自标「需规 seq 360/362/363，含 361 更新周期」，`AccessHistorySituation.jsx:169-171`）·动态历史趋势可视化卡。UI 实际挂载（派单 mount 行 97，实查确认）：`AccessHistorySituation.jsx:70-121` getTrendOption 三序列混合图——「历史接入量」bar（:97-101，yAxis 左轴）、「更新成功率%」line（:104-110，右轴）、「异常数」line（:111-118，右轴）；同卡汇总行「归档记录」Statistic（:286-289，`value={summary.archiveCount}` suffix="条"）。mock 语义源 `mockData.js:1422-1449` historyAccessDashboard：summary.archiveCount=12 + trend.accessVolume=[1860,2100,2350,2680,3010,3360]（labels 12月-5月）。mock 结构披露：archiveCount（台账行数语义）与 accessVolume（逐期量语义）是两个独立 mock 常量、内部未闭合（合计 15,360≠12）；演示值不作数据证据（B10）。

### 1.2 为什么需要本指标

历史接入情况的治理命题是「**接入家底与节奏**」：累计读数回答「总共接了多少」（家底），逐期序列回答「每期接了多少」（节奏）——两者合成「历史资源接入情况总览」（seq 362 的 L5 名）。与 DATAIN_002（归集数据量统计）的区别：DATAIN_002 是接入视窗总览位、本件是历史归档语境——「归档」暗示已登记入册的台账语义（archiveCount 条数=台账行数），这正是本件与 DATAIN_002 的口径差异点（台账条数 vs 数据量合计）。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「历史累计接入量」。**「历史接入量」是 UI 图例名（:97）；「归档记录」是 Statistic 题名（:288）。挂靠叶 seq 362 历史资源接入情况总览（SRS 接入视窗.md）功能行为在（长期趋势/归档记录/多维检索），「累计」的度量对象（记录条数/数据量/资源数）、「归档」的登记语义（什么算一条归档）均无定义。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「累计接入量」的权威方法锚与 DATAIN_002 同构三层：汇交台账口径（R1，GB/T 39912——动作量累计的制度化形态）、体量序列口径（R2，国家基础学科中心 4,325 项目/6.5PB——存量按主体统计）、库内代理（对象级行数+批次时间戳）。方法族对照：

|---|---|---|---|

## 四、数据缺失情况

### 4.1 接入/归档台账零承载（结构级，主因）

「归档记录」的登记面三源零承载（§3.3）——「什么算一条归档、何时登记、记什么」无任何承载结构。这是接入台账族（DATAOV_002/DATAIN_001/002/003/027 族+本件+043-045）共享的族级缺口。**四缺失情形归属「表不存在」**：修复动作是台账立项（一次建设多件受益），本件是该族内「归档条数」语义最直接的一件。

### 4.2 逐期序列与月维两点（数据级，次因）

即便只求「逐期接入量」（不求台账），月维代理也只有两点不成期（040/041 同证）——序列维与累计维的缺口同根（台账缺位的两个投影），台账建成后两个读数位（trend 序列+archive 累计）一次补齐。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 接入/归档台账立项（资源×量×时间） | 数据工程立项（族级） | 本件 + 043/044/045 + DATAIN 族 + DATAOV_002 | 触发器①（族级主线） |
| 存量代理口径裁定 | 口径裁定 | 本件零成本升档 | 触发器③（标签「库内存量」） |
| mock 两读数位对账 | 前端工程 | 本件 UI | 12 vs 15,360 失配回调 |

档位后果：台账 → **完全直接支持**；存量代理裁定 → **完全转换支持**；现状 → 部分支持。推荐：随族级主线（台账立项）并项，代理口径作即期内部参考。
