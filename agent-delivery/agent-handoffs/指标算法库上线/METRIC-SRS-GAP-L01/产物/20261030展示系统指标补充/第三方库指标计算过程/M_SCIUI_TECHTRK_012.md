## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技发展态势/**科技发展规划**/科创资源整合与推送（SRS seq 183）→ 订阅推送弹窗。UI 挂载点 `TechDevelopmentPlan.tsx:3549`：订阅设置弹窗的推送频率单选组（每日/每周/每月三选项），同弹窗 `:3523` 订阅条件（领域/载体），`:2916` 推送列表入口。用户在弹窗里选频率、提交订阅——UI 演示的是**配置交互**，没有展示任何频率统计读数。

**mock 全部为前端常量与交互占位，演示值，不参与支持度结论。**组件行为值得记录两点：其一，三选项是离散档位（每日/每周/每月）而非连续数值——真实接入时指标形态是「各档位订阅数分布」或「系统实际推送节奏达成率」，两种形态的数据需求完全不同；其二，弹窗提交动作在 mock 里无后端落点——这正对应数据侧的发现：**订阅配置表与推送流水表都属应用侧待建**，不是库内缺数而是系统缺表。

### 1.2 为什么需要本指标

推送频率是订阅服务的履约参数：用户选了「每日」，系统就要有每日的供给与推送执行能力。需求原文（seq 183）把「科创资源整合与推送」列为独立功能叶，主需求文档进一步写明「定期（每日/每周/每月）向用户推送」——频率是句子的主干参数。数据侧本件的调查重心是**把「频率」拆成两问**：①系统有多大的资讯供给能力（决定每日推送能推多少条、供给不足时频率承诺是空话）；②系统实际推送执行情况（履约统计）。第①问三源数据充足（本报告代理口径即答），第②问三源无承载——这个拆分就是判档的骨架。

与批内关系：011 件（成果数量）是库存视角、本件是分发视角，两件构成「库存-分发」对；本件的供给面读数（news_base/chain_news/org_news 三表）与 008-011 件共用的 gkx 探测面同源，批内复用密度高。

### 1.3 需求文档是否给出定义方法

**需求文档提及了指标语义但未给出计算方法。**本件是 Lane 2 五件中唯一 SRS 点名的：①SRS《全球创新监测.md》seq 80 订阅管理叶「用户可订阅关注的领域、创新载体，设置订阅条件和推送频率」——「推送频率」作为用户设置项出现；②主需求文档 L569 与 seq 80 同句（订阅设置推送原词），另 L1245 政策订阅服务节给出档位枚举「定期（每日/每周/每月）向用户推送」（政策推送语境，档位语义同源）；③UI 弹窗源头是《科技发展规划.md》seq 183 科创资源整合与推送叶（附录 A 摘录）。但**三处都是行为描述**：没有推送频率的统计口径（按推送动作计还是按推送内容计）、没有分档统计要求、没有达成率定义——计算方法完全留白，供给代理口径是本报告的推测填补。

### 1.4 类似指标权威方法可行性分析概要

推送频率的权威方法族：①**消息系统监控口径**（推送量 push volume / 触达率 delivery rate / 打开率 open rate，推送流水按日聚合，行业 SaaS 标配）；②**资讯供给侧口径**（内容入库频率 content ingestion rate，情报系统常用——回答「供给能否支撑承诺频率」）；③**SDI 通知统计口径**（R1，科技数据库联合协会年度统计的通知/推送服务量）。方法族对照：

| 方法族 | 频率定义 | 数据要求 | 与三源匹配 |
|---|---|---|---|
| 推送流水口径（监控） | 实际推送动作按日聚合 | push log 表（user/time/channel/content） | **无（三源探针全 0）** |
| 供给能力口径（供给侧） | 内容入库按日聚合 | 资讯主档发布时间列 | **有（gkx 三表 + dev 一表现成）** |
| SDI 通知口径（R1） | 年度通知服务量 | 服务统计报表 | 无（报表级，非库表） |

结论：履约口径（最贴近字面）无承载；供给口径四表现成可算——本件「部分支持」的依据即在供给侧充足、执行侧缺表。完整版见附录 C。

### 1.6 推测原意与推测定义

**推测定义（B10 代理口径明示，供给≠推送）**：

- 供给日频（主代理口径）：$f_{daily} = \frac{N_{news\_base,12m} + N_{chain\_news,12m}}{365} = \frac{4{,}657 + 65{,}661}{365} = \frac{70{,}318}{365} = 192.6521$ 条/日（derived `gkx_info_supply_daily_avg`；两表均 gkx 全表精确聚合、近12整月窗口，同库同源 B3）。

**降档/升档触发器（B10 模板）**：应用侧建推送流水表（user_id/push_time/channel/content_id 四列即够）→ 履约口径可算 → 升完全转换支持；若甲方接受供给口径作正式口径 → 本件读数即期回填；若要求分档订阅分布 → 需订阅配置表（同样应用侧待建）。org_news 166.8 万行表如需精确日频 → 20 万采样协议已走通（39,969/12 月桶），提频可复用。

## 二、计算过程

### 2.1 装载与规模校验

gkx 供给三表：`dwd_news_base` 20,000 行（fbsj 零 NULL、零非法日期——`gkx_news_base_fbsj_null=0`/`fbsj_invalid=0`，B9 日期陷阱前置排除）；`dwd_industry_chain_news_info` 108,052 行（近12整月 65,661 条，覆盖 60.8%）；`dwd_org_important_news_info` 1,668,414 行（20 万采样协议）。开发库 `enterprise_news` 近12整月 355,614 条（12 桶）。四表月分布各 12 个月份桶全非零（`distinct_months=12` ×4）——**供给连续性成立**，无断月。

### 2.2 主代理口径：供给日频

分子取 news_base + chain_news 近 12 整月（2025-05-01 至 2026-04-30）行数和 4,657 + 65,661 = 70,318（两表均 gkx 全表精确聚合，无采样混入）；分母 365 日。$70{,}318 / 365 = 192.6521$ 条/日（derived `gkx_info_supply_daily_avg`，numerator=70318/denominator=365 登记在产物）。**口径边界**：org_news（166.8 万行）与 dev enterprise_news（35.6 万条/年）**未混入**主口径——前者按采样协议单列旁证、后者属开发库不同装载面（与 gkx 同名面不同源不同量，notes 写死），混入会使日频读数失真到 1,500+ 条/日且口径漂移；单表参照月频 news_base 4,657/12 = **388.0833** 条/月（derived `gkx_news_base_monthly_avg`）。

### 2.3 旁证口径：org_news 采样分布

org_news 166.8 万行无发布时间索引，按批纪律走 20 万行采样子查询取月分布：近 12 整月 39,969 条（`gkx_org_news_recent12m_rows_200k_sample`）、12 桶全非零（月均 ~3,331 条，峰值 2025-12 4,245、谷值 2026-04 2,043）。**采样，非全表**——notes 明示「未混入日频精确口径」。作用：证明 166.8 万行大表的近月供给同样连续，供给能力结论对表选择不敏感。

### 2.4 履约侧：三源探针全记录

推送行为流水在三源的缺失证据链（absence_probe 8 条全录）：①gkx 280 表扫 `%push%/%subscr%/%notif%/%message%` 命中 0；②久新 SHOW TABLES `%push%`/`%news%`/`%subscr%` 三连空；③开发库五库（cms/app/mp/bi/report）扫加 `%alert%/%recommend%` 扩展模式命中 0；④dev `policy_latest_news`/`chain_news` 结构在但 0 行（与 gkx 同名供给面不同源不同量）。**四缺失情形归属：无承载表（主体）+ 表空置（dev 两表）**——推送流水属应用侧待建，不是库里缺数。

### 2.5 稳健性与口径敏感性

## 四、数据缺失情况

### 4.3 org_news 精确日频未取（协议级）

166.8 万行表按批纪律走 20 万采样（39,969/12 桶），采样值不做总体推断（红线）。若甲方要求 org_news 精确日频：该表发布时间列如无索引，走全表聚合需 DBA 评估窗口；或按月分区预聚合落中间表。影响面：仅旁证读数精度，不影响主口径。
