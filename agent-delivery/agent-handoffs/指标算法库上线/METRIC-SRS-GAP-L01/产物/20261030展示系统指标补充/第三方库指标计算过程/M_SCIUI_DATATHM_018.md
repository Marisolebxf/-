## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/接入视窗/资源接入情况总览/**多维度交互筛选·来源维度的「数据库同步」枚举值**（无独立需求叶；相邻叶 1.1.1.1.4.4.2.1.4 多维度交互筛选，SRS seq 350）。UI 实际容器是 `AccessWindow` 组件的「多维度交互筛选」Card（`AccessWindow.jsx:366-390`）：来源 Select（`ACCESS_CHANNEL_OPTIONS :44-51` 硬编码 6 项——全部来源/API 接口/文件传输/**数据库同步**（:48）/人工录入/物联网采集）、类型 Select、归集状态 Select、问题标签 Select、日期 RangePicker，五维联动过滤问题资源列表；查询动作（`handleMultiFilterSearch :292-298`）按渠道值过滤后 message 提示「已按来源『数据库同步』…查询，命中资源 N 条」。mock 语义源有两处：`mockData.js:91-95` 的 `accessChannelStats`（5 渠道统计行，数据库同步行 count 67/successRate 99.1/volume 15,600——本件读数语义锚）与 `problemResources` 列表的 channel 字段（筛选目标面）。前端把「数据库同步」同时用作筛选枚举与统计行维度，两处 mock 枚举一致（5 类）。

### 1.2 为什么需要本指标

多维度交互筛选（seq 350）要求「根据来源、类型、归集状态或问题标签快速定位目标资源」——来源维度是第一筛选轴，「数据库同步」是五种接入传输方式之一（程序化程度最高、体量通常最大的管道）。单渠道成功率读数的业务价值：数据库同步管道承载结构化批量数据（mock 演示 volume 15,600 为五渠道最大），其成功率直接决定结构化数据的时效性——若该渠道成功率跌破阈值，下游依赖同步数据的看板全部连锁变质。需求语境里它与 031 是点面关系：031 给全渠道矩阵（面），本件是运维最关心的单管道放大镜（点）；官方对应物是 R2/R3 SLA 的 per-service 口径——总 SLA 达标不代表单服务达标，单渠道读数是 SLA 树的叶节点。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「数据库同步成功率」指标名在三份需求真源 0 命中（附录 A.2）。「数据库同步」作为词仅出现在主需求的功能语境（如「整合多渠道资源接入信息」的渠道举例不在正文，正文以「科研院所、企业、开源平台」为来源举例——注意需求的「渠道」举例是**来源机构**口径，UI 硬编码的是**传输方式**口径，两套枚举不同物，本身就是一个待裁定的口径分叉）；成功率口径（分子分母、批次粒度、成功判定）无任何定义。UI 的 99.1 是 mock 常量，不构成口径证据。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：031 口径的单渠道特化：

$$\text{SR}_{db} = \frac{\text{「数据库同步」渠道成功同步记录数}}{\text{「数据库同步」渠道同步记录总数}} \times 100\%$$

其中渠道枚举取 UI 硬编码的传输方式口径（数据库同步=通过 DB 链路的批量同步管道）。**口径分叉披露**：需求正文的来源举例是机构口径（科研院所/企业/开源平台），UI 枚举是传输方式口径（API/文件/DB/人工/物联网）——两套 taxonomy 不同物，本件按 UI 口径（挂载点语义优先），机构口径的裁定登记为待定。**前提是渠道台账存在且渠道列可取值「数据库同步」，三源实测无**（§3.3）。

**降档/升档触发器（B10 模段）**：与 031 完全共用——①台账（带渠道列）+渠道字典 → 直查升**完全直接支持**；②xxl_job 投产+任务→渠道映射 → 转换升**完全转换支持**；③甲方裁定渠道口径=机构口径（非传输方式）→ 枚举重定义，本件语义随之迁移（挂载点语义与裁定对齐后重评）。维持现状 → 完全不支持。

## 四、数据缺失情况

### 4.1 渠道台账与枚举双零承载（结构级，与 031 同根）

单渠道成功率的两个前提——渠道台账（有「数据库同步」行）与渠道枚举（字典可取值）——三源双零（§3.3）。与 031 的缺口完全同根，本件不产生新缺口也不少缺口（单渠道切片不是「少一个维度就少缺一点」——切片键本身不存在时单渠道与全渠道同样无从建起）。**四缺失情形归属**：台账「表不存在」、枚举「字典值不存在」。修复动作与 031 并案（台账+渠道字典立项）。

### 4.2 渠道口径分叉（口径级，本件特有披露点）

本件调研发现一个**需求与 UI 的渠道 taxonomy 分叉**：需求正文（主需求 :2590 等）的来源举例是机构口径（科研院所/企业/开源平台），UI 硬编码（`ACCESS_CHANNEL_OPTIONS`）是传输方式口径（API 接口/文件传输/数据库同步/人工录入/物联网采集）——两套枚举不同物且都无需求定义背书。这个分叉影响整族渠道类指标（031/018/DATAIN_003）：若甲方裁定机构口径，UI 枚举需重定义、本件语义迁移；若裁定传输方式口径（挂载点语义优先），机构口径的渠道占比另立。**登记为族级待裁定项**（B10 不擅自定案）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 渠道 taxonomy 裁定（机构 vs 传输方式） | 口径裁定（族级） | 本件 + 031 + 014 + DATAIN_003 | §4.2 分叉，整族前置 |
| 渠道字典立项 | 字典表 | 同上 | 枚举值（含「数据库同步」）落库 |
| 归档台账（带渠道列） | 数据工程立项 | 同上 + 族内件 | 触发器①（族级共用） |

档位后果：taxonomy+字典+台账 → **完全直接支持**；调度器投产+映射 → **完全转换支持**；现状 → 完全不支持。推荐顺序：taxonomy 裁定最先（否则字典/台账建错口径返工），其余与 031 并案。
