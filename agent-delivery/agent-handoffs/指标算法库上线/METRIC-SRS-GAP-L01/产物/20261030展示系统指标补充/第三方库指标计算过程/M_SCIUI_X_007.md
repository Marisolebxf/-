## 摘要

「技术创新空间分布权重」是空间分布对的权重件：471 导出从页面提取了 17% 这一示例值，但现场实查发现它没有 UI 挂载点——`TechInnovationEvaluationPage.tsx` 的技术创新力权重组 `techWeights` 只有专利数量/专利质量/市场潜力三维（36/34/30，组和校验=100），空间分布维缺位；全 `src/` 检索「空间分布权重|spatialWeight」零命中。三源权重配置面同样无承载：开发库 `cfg.index_weight` 2 行（载体/城市两类指数的 AHP×熵权权重 JSON，逐行解析无空间维）、`ads.eval_weight` 0 行、gkx 0 表、久新 203 表 0 命中。本报告的交付重心因此从「复算一个数」转为「论证这个数应该由什么机制产生」：开发库在案的 AHP 先验×熵权客观综合归一框架完全可扩展承载空间分布维——先把主件（X_006）的区级/集群分布读数做成子指数，再入组定权。判**部分支持**：结构可承载（框架在）、数值无来源（17% 是待定参数非数据）。

- 需求判定：**UI 推导叶**（指标名三份说明书未出现；SRS seq 143「技术创新力综合评估」的「用户可自定义指标权重」是最接近的需求原文）。
- 复现状态：脚本跑通；三源权重面探针+UI 权重组登记+两基准比落产物。
- 档位结论：**部分支持**（框架可扩展+数值三源无承载）。
- 关键事实：UI techWeights 三维组和=100 且空间分布不在组内——17% 与现有组件口径直接冲突。
- 升档路径：甲方裁定空间分布维入组（扩 techWeights 或另立评估组）后，AHP×熵权框架即可产数。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技发展态势/科技创新评估/**技术创新力指标展示**（1.1.1.1.4.1.7.2；471 导出 row_01=112，l3「技术创新空间分布权重」）。本件无独立 UI 挂载点（mount 为空）——它是从主件 X_006 的评估语境推导出的权重位：科技创新评估页有完整的「评估参数配置」机制（`DEFAULT_EVALUATION_PARAMETER_CONFIG`，`:307-332`），四维度权重（科学创造力 30/技术创新力 25/产业发展潜力 25/政策与条件保障力 20）+ 各维度内部子权重组（techWeights/industryWeights/policyWeights），`:345-353` 的 `isWeightGroupValid` 强制每组权和=100，`:355-358` `weightedScore` 按权重加权合成。**空间分布在 `techWeights` 里没有条目**——这是「权重件无挂载」的组件层证据。

值得记录的推导链：471 导出的 17% 页面示例值（mean 字段）在当前组件源码中已不可复现——它可能来自更早版本页面的四维展示卡（X_003/005/008/009 等兄弟权重件同构，页面示例值 30%/20%/16% 等），当前版本把这类展示卡重构进了评估参数配置。因此本件的「UI 需求证据」是 471 导出的历史登记，不是现行组件行为。

### 1.2 为什么需要本指标

权重是综合评估的枢纽参数：同样一组子指标，权重不同结论不同。「技术创新空间分布」若进入技术创新力评估，它的权重决定了「创新的地域均衡性」在总分里的话语权——高权重会奖励集中（头部区优势放大），低权重会奖励均布。需求文档没有给出这个权重的值，甚至没有明说空间分布要进评估组；17% 这个数的存在（页面示例值）说明需求方预期它有朝一日会被配置。

数据侧本件的难点与主件不同：主件缺的是分布数据，本件缺的是「这个维度的相对重要性判定」。重要性判定无法从数据里直接算出——它要么来自专家先验（AHP 族），要么来自数据离散度（熵权族），要么来自两者综合。本报告的可行性论证因此围绕「框架在不在」展开。

### 1.3 需求文档是否给出定义方法

**需求文档没提及该指标与任何权重数值。** 三份指定说明书（科技全域态势/技术发展跟踪/全球创新监测）未出现「技术创新空间分布权重」指标名。语义最近的需求原文是《科技创新评估.md》seq 143（技术创新力综合评估）：「将技术创新力的各项指标进行综合展示，用户可自定义指标权重，系统根据权重计算综合得分」——「各项指标」的清单与权重值都留给用户/实现方，17% 无对应。

### 1.4 类似指标权威方法可行性分析概要

权重设定的权威方法族三支：Saaty **AHP**（专家两两比较→特征向量权重，主观先验的标准形）；**熵权法**（按指标数据离散度客观赋权，信息量越大权重越高）；以及两者乘性/线性综合的**组合赋权**（先验×客观修正）。开发库 `cfg.index_weight.method_desc` 在案的方法正是组合赋权（「AHP 先验 × 熵权客观权重 综合归一」）。方法族对照：

| 方法族 | 赋权轴 | 数据要求 | 与本库匹配 |
|---|---|---|---|
| AHP（Saaty） | 专家两两比较 | 判断矩阵调研 | 无调研（可立项） |
| 熵权 | 指标离散度 | 子指标数值面 | **依赖主件**（分布读数先落地） |
| 组合赋权（AHP×熵权） | 综合 | 两者兼具 | **框架现成**（cfg.index_weight 范式） |

结论：方法不需要发明——开发库已有同范式实现；缺的是空间分布子指数（主件口径裁定）与专家先验（AHP 调研）。完整版见附录 C。

## 二、计算过程

### 2.1 装载与规模校验

三源连接同批统一入口。权重面锚点：开发库 `cfg.index_weight` 2 行（2026-01-01 单版 effective）；`ads.eval_weight` 0 行；gkx 权重/配置类表 0；久新 203 表语义过滤 0（`jiuxin_weight_like_tables=[]`）。

### 2.2 开发库权重面深探：框架在、维度缺

`cfg.index_weight` 两行分别是 carrier（载体创新能力指数）与 city（城市创新能力指数）的权重配置：JSON 内含 `ahp`（专家先验）与 `final`（组合归一后）两套权重，载体四子维 output 0.35/quality 0.30/activity 0.20/performance 0.15，城市四子维 output 0.35/resource 0.25/environment 0.20/institution 0.20——方法论描述「AHP 先验 × 熵权客观权重 综合归一」。逐行 JSON 解析（脚本 `dev_cfg_index_weight_json_keys`）确认无 spatial/空间/region/district 任何键（`dev_cfg_index_weight_spatial_dim_hits=0`）。这组证据的含义两面：**消极面**——空间分布权重这一行不存在；**积极面**——同类「多源指标→子指数→加权合成」的工程范式已在库内落地过，扩展一个评估组的实现路径是清晰的。

### 2.3 UI 权重组现场：17% 无处安放

`techWeights` 三维实查（`:313-317`）：专利数量 36/专利质量 34/市场潜力 30，组和=100 过校验。空间分布若强行入组，现有三维必须让权（例如 30/28/22/20），17% 无论如何装不进一个「已经满 100」的组——这就是「UI 无承载」的算术本质。兄弟组 industryWeights 五维（22/20/20/19/19）与 policyWeights 五维同构，五维组的中性基准是每维 20%（`ui_fiveweights_mean_pct`），四维组是 25%——17% 若入组只能是非均匀配置，须由先验或数据说话。

### 2.4 gkx/久新权重面：结构性空白

gkx 280 表扫描 weight/config/coefficient 三关键词 0 命中（`gkx_weight_config_tables=0`）——三方要素库定位是底表供应，不做评估配置；久新 203 张 ads_* 表同样 0 命中（`jiuxin_weight_like_tables` 空数组）——分析层表自带 `metric_definition_version`/`score_version` 等版本字段但权重本体不外露为配置表。两源 absence 均为「表不存在」级（结构空白，非数据空白）。

### 2.5 基准读数（B3 同基）

两比给 UI 常量的结构基准（演示值语义，披露在 note）：techWeights 三维均值 33.33%（100/3）、五维组中性基准 20.00%（100/5）。17% 的隐含语义由此可读：低于五维中性基准 3 个百分点、接近四维组的弱维位置——若历史展示卡是四维（如技术创新力 30/空间分布 17/质量 28/市场 25 之类），17% 大约是「第四维偏弱」的配置。这只是构词学推测，产物 note 已注明不得作为数值来源。

### 2.6 稳健性与口径敏感性

权重件的敏感性在「参数非数据」这一本质：17% 无论取何值都不影响三源任何表的内容，只影响综合分的合成。因此本件的风险不在数字漂移而在**治理缺位**——没有配置所有者，这个数就会以 mock 形式固化进前端（与 techWeights 硬编码同理）。建议治理路径：`cfg.index_weight` 增行（index_type='tech_innovation'，weights JSON 含 spatial 键），AHP 调研存档 method_desc。

### 3.2 W1 框架维：本件唯一的正向证据

`cfg.index_weight` 的存在证明开发库具备「评估指数-权重配置-版本管理」的完整工程位：weight_version 可迭代、method_desc 记录方法学、effective_date 控生效。空间分布维入组的工程成本主要是「子指数接入+权重产数」两步，不是建机制。这决定了本件的修复路径是**配置动作**而非数据工程——与主件（要建匹配链）的修复成本结构完全不同。

### 3.3 W6 子指数输入：与主件的耦合关系

权重不能凭空产生：熵权轨需要子指数的数值面（主件口径 A 九区密度或口径 B 集群份额的 min-max 归一分），AHP 轨需要专家对「空间分布 vs 专利数量/质量/市场」的两两比较。主件已交付九区+集群两组可归一读数——熵权轨的输入即期就绪，AHP 轨需调研立项。这意味着「权重件升档」的前置一半在主件（已部分满足）、一半在流程（未启动）。

## 四、数据缺失情况

### 4.1 权重数值无来源（配置级，主因）

17% 在三源没有任何配置行、任何 JSON 键、任何 UI 常量对应——它是 471 导出从历史页面登记的「预期读数」，现行系统已无此位。四情形归属「表存在但行不存在」：`cfg.index_weight` 可加行（index_type 扩一类），`eval_weight` 可插行（model/dimension/weight 三字段即一配置）。修复是**一次配置动作 + 一次赋权流程**，不是数据回填。

### 4.2 赋权流程未启动（流程级，次因）

即便配置位就绪，权重值仍需 AHP 调研（专家先验）或熵权计算（数据客观轨）产生。熵权轨输入（主件子指数）已部分就绪；AHP 轨未立项。若跳过流程直接拍数（如沿用 17%），权重将无方法学背书——`cfg.index_weight.method_desc` 字段的存在意义就是防这类「裸数值」入库。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| techWeights 扩组评估（口径 B） | 产品决策 | 本件+X_006 | 四维重组，空间分布入组 |
| cfg.index_weight 加行 | 配置动作 | 本件 | index_type='tech_innovation'，AHP×熵权 |
| AHP 专家调研 | 流程立项 | 本件 | 两两比较矩阵→先验权重 |
| 熵权轨即期试算 | 数据动作 | 本件 | 主件九区/集群读数离散度赋权 |

档位后果：口径 B+任一赋权轨完成 → 升**完全转换支持**；维持展示件不入组 → 本件结论定格「不适用权重」。
