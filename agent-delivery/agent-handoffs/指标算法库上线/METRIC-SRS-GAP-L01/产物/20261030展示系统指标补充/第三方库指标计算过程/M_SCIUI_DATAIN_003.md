## 摘要

「渠道归集数据量统计」是需求明列叶（SRS seq 351：资源来源分析和详情五功能之首）——「自动统计并展示各渠道（如科研院所、企业、第三方平台等）归集的数据量，支持按时间、业务类型、来源类别进行细分」。UI 挂载实查是问题资源统计报表 Tab 的同名小卡（`AccessWindow.jsx:582`），渲染 mock `problemResourceStats.byChannel`（5 渠道问题资源计数）——是**复用位**非直挂位（seq 351 的直挂语义在资源来源分析和详情族，mount 勘误回执登记）。数据侧：渠道归集台账三源零承载；唯一现成渠道切片轴（gkx `table_data_source` 供应商标签）实测不可用（dwd_scholar 21,316 行单标签 'gkx_ods'、dwd_zh_paper 100,900 行全无效值、dwd_patent 采样 14,371 行全 null）；但内容量代理面三源双在（dev ods 75 表表级体量 Top10 + enterprise_base 269,511 行批次分布——与 DATAIN_001 同法同读数）。判**部分支持**：内容量代理可交付、渠道归集本体需台账+渠道字典立项（与 018 共享 taxonomy 分叉待裁定）。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**需求明列叶**（seq 351），功能在、度量单位（记录数/体量）与渠道 taxonomy 无定义。
- 复现状态：脚本已跑通；台账排除探针 + 标签轴实测 + 内容量代理读数全落产物。
- 档位结论：**部分支持**（渠道归集台账+切片轴零承载 + 内容量代理面三源双在）。
- 关键事实：gkx `table_data_source` 标签轴「有列无值」——dwd_zh_paper 100,900 行 100% 无效（'NULL' 字面+真空），渠道切片在库里连「错值的分布」都凑不出，这是比「无列」更明确的不可用证据。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/接入视窗/资源来源分析和详情/**渠道归集数据量统计**（1.1.1.1.4.4.2.2.1；SRS seq 351、excel_row 354）——**需求明列叶**（本组五件中唯一）。UI 实际挂载（派单 mount 行 582）实查是接入视窗「问题资源情况」卡的「问题资源可视化统计报表」TabPane 四小卡之第三：`AccessWindow.jsx:582` Card title="渠道归集数据量统计"，内渲染 `problemResourceStats.byChannel` 5 渠道条目（渠道名+Progress 占比条+计数，Progress 分母硬编码 23——mock 演示逻辑）；数据源 mock `mockData.js:546-552`。**mount 勘误**：该小卡是问题资源统计视图的渠道分布**复用位**（byChannel 是「问题资源×渠道」计数，非「归集数据量×渠道」）——seq 351 的直挂语义（各渠道归集的数据量）在资源来源分析和详情族（UI 侧由 `AccessSourceAnalysisDetail` 组件族承接，mock `accessSourceAnalysis.channels`：科研院所 12,580/企业 8,920/第三方平台 6,240/高等院校 4,120/政府部门 1,810 的 volume/count/share 三列——恰是 seq 351「各渠道归集的数据量」的机构口径演示形态）。本件按需求叶语义核（UI 两处复用位一并登记）。

### 1.2 为什么需要本指标

资源来源分析和详情（seq 351 所在 L4）的管理命题是「**谁在给平台供数、供了多少**」：渠道归集量是来源结构的定量基础——科研院所 vs 企业 vs 第三方平台的贡献度对比（mock channels 的 share 38.6%/28.3%/19.5% 演示形态）直接服务供数方运营（哪些来源要扩、哪些渠道要激励）；三个细分维（时间/业务类型/来源类别）分别回答「归集节奏、内容结构、来源层级」三问。官方对应物是 R1 汇交体系的分中心汇交量统计（国家基础学科中心项目汇交 4,325 个的分布口径）与 R2/R3 的体量序列（PB 级总量按中心统计）——渠道×量的登记与呈示是数据资源管理的元功能，本平台把它做成接入视窗的常驻读数。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**seq 351 主需求 :2607-2609 给出功能行为：「自动统计并展示各渠道（如科研院所、企业、第三方平台等）归集的数据量，支持按时间、业务类型、来源类别进行细分，帮助用户全面了解不同渠道的数据贡献度」——「数据量」的度量单位（记录数？存储体量？数据集个数？）无定义；渠道 taxonomy 的举例是机构口径（科研院所/企业/第三方平台），与 UI 筛选枚举的传输方式口径（API/文件/DB/人工/物联网）不同物（与 018 件共享的分叉）；三个细分维各自的聚合粒度无定义。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「渠道/来源×归集量」的权威方法锚分三层。其一，国家科学数据汇交统计（R1）：分中心汇交量（项目数/数据集数/体量）的登记制——归集量的制度化形态是**汇交台账**（谁、交了什么、多少）。其二，体量序列口径（R2/R3）：按中心统计数据总量（PB 级）——度量对象是存量体量，渠道切片=中心维度。其三，库内代理路径：无台账时以「库表层体量×来源标签」近似——标签轴是关键（本件实测 gkx 标签轴空载，§3.3）。方法族对照：

| 方法族 | 代表 | 度量对象 | 数据要求 | 与三源匹配 |
|---|---|---|---|---|
| 汇交台账口径 | R1（GB/T 39912） | 汇交动作量（数据集×体量） | 汇交台账 | **无台账** |
| 体量分布口径 | R2/R3（国家中心年报） | 存量体量×主体 | 体量登记 | **体量可数、主体维缺** |
| 库表体量代理 | 本件交付路径 | 表级行数×（可选标签） | information_schema | **三源双在**（语义降维） |
| 前端演示 | UI byChannel/channels | mock 计数/volume | mock 常量 | 结构披露（不作源） |

结论：台账口径零承载；体量口径的量可数（表级行数）但渠道主体维零承载（标签轴空载）。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

$$\text{Vol}_c = \sum_{r \in R_c} \text{quantity}(r),\quad R_c = \{r: \text{channel}(r) = c\}$$

即渠道 c 名下归集登记记录 r 的量（记录数/体量，单位待裁）加总——**前提是归集台账存在，三源实测无**（§3.3）。**口径 B（库表体量代理，即期可交付但语义降维）**：以库内贴源层的表级体量并列呈现（dev ods TopN），渠道切片待标签轴立项后叠加——语义=「库里有什么量」而非「渠道归集了多少」，补录/回溯灌库时两者脱钩（与 DATAOV_002 §2.5 同一敏感性）。

**降档/升档触发器（B10 模板）**：①建渠道归集台账（渠道×数据集×量×时间）+渠道字典 → 口径 A 直查升**完全直接支持**；②甲方裁渠道口径=库/表层（如 gkx 280 表按业务域分组当「来源」）→ 口径 B 升**完全转换支持**（分组约定+语义披露随行）；③甲方裁渠道口径=机构口径（需求举例）→ 需供数方登记面（机构→数据集映射），缺口更大维持部分支持。维持现状 → 部分支持（代理读数仅供内部参考）。

## 二、计算过程

### 2.1 方法选择（文献依据）

代理口径选**库表体量并列**（R2/R3 体量序列口径的表级落地）：dev ods 贴源层表级行数 TopN 并列展示，不合成单一「渠道归集量」总数——因为渠道切片轴零承载（§3.3），任何合成都要伪造渠道归属。选择理由：其一，表级体量三源可数且确定性（information_schema 直读）；其二，国家级实践（R2）的分中心并列体量与此形态同构（量可数、主体维待接）；其三，语义边界通过「并列+不归渠」天然传达（B10 不悬空）。口径 A 因台账不存在不做方法选型（F4）。

### 2.2 dev 代理读数：ods 贴源层表级体量

`gkxlumenx_ods` 75 表按 table_rows 降序 Top10（`dev_ods_top10_by_rows`，information_schema 估算值口径，B9 标注）：**dwd_org_important_news_info 1,572,131 / dwd_org_risk_zhixing 540,090 / dwd_org_annual_report_asset 516,532 / dwd_org_executive_info 429,913 / dwd_org_shareholder_info 394,487 / dwd_org_tech_tag 201,244 / dwd_org_income_statement 193,968 / dwd_org_base_info 179,920 / dwd_org_subsidiary_info 175,951 / dwd_industry_chain_news_info 91,190**——企业情报域（org_* 前缀 9/10）主导的体量结构。读数解读：贴源层的体量分布呈现「采集域结构」（企业情报/产业链新闻），这是「库表即渠道载体」口径下的量级面；但表级体量≠渠道归集量（一张表可能多渠道混灌、一个渠道可能灌多表），代理语义降维披露。

**dev**：access_history/collect_log/ingest/sync+channel 词族命中 0 张台账面（sync 唯一命中 es_sync_watermark 快照面、channel 唯一命中 pay_channel 支付域——语义排除，§3.3）。**gkx**：280 表归集/渠道词族 0 命中；唯一「来源标签」轴 `table_data_source` 实测不可用——dwd_scholar 21,316 行**单标签** 'gkx_ods'（100% 同值无区分度）、dwd_zh_paper 100,900 行全无效（'NULL' 字面 63,656 + 真空 37,244）、dwd_patent 采样框 14,371 行全 null（dwd_id≤200000 采样，非全表）——标签轴「有列无值」，渠道切片连错值的分布都凑不出。**久新**：210 张词族 0 命中；快照管理形态（metrics_as_of_date 实测 None 255,806 / 2026-09-18 1,022,242 两值）——单日一期快照无归集动作量、无渠道维。三源结论：台账 0、切片轴 0（语义级）。

### 2.5 稳健性与口径敏感性

代理口径的三点敏感性：其一，**表级体量的估算口径**——information_schema.table_rows 是 InnoDB 估算值（B9），精确读数须 COUNT(*) 逐表复跑（75 表成本可控，交付版建议实数化）；其二，**补录脱钩**——表级体量含历史全量，一次回溯灌库会让某「渠道」体量暴增而归集动作只有一笔（与 DATAOV_002 §2.5 同敏感性）；其三，**taxonomy 分叉的切片风险**——若按机构口径切渠道，库内无机构→数据集映射（缺口更大）；若按传输方式切，无渠道列（031/018 同缺口）；若按库/表层切（触发器②），语义降为「数据域结构」非「来源渠道」——三种切法都改变读数含义，必须随裁定重标。

### 2.6 需求符合性预评

需求三分句分评：**各渠道归集的数据量**——不满足（渠道切片轴零承载，只能给表级/批次级代理）；**按时间细分**——部分满足（批次面有按日分布，但单实体族且无渠道联动）；**按业务类型/来源类别细分**——不满足（业务类型轴与来源轴均零承载）。整体：量的量级面可交付、「渠道×量」的本体读数缺位——预评与触发器对齐。

## 四、数据缺失情况

### 4.1 渠道归集台账零承载（结构级，主因）

「渠道×数据集×量×时间」的归集登记面三源零承载（§3.3）——与 DATAOV_002/DATAIN_001/DATAIN_002 的接入流水缺口同族同根。**四缺失情形归属「表不存在」**：修复动作是归集台账建设（族级并项：与资产目录、接入流水台账三表共建——目录记资产、流水记动作、台账记渠道归属，本件的渠道切片是台账的核心增量列）。本件是族内对台账需求最直接的一件（需求明列「渠道×量」），台账立项的收益锚。

### 4.2 渠道切片轴空载（数据级，次因）

gkx `table_data_source` 标签轴「有列无值」（§3.3 三表实测）——即便台账缓建，标签轴治理也能先行解锁口径 B 的渠道切片（按供应商/来源标签分组）：修复动作是标签回填（三张 dwd 大表的 table_data_source 治理）+ taxonomy 裁定（§4.3）。**四缺失情形归属「表存在但关键列空载」**——与 4.1 的「表不存在」是两种修复路径，分立登记。taxonomy 分叉（机构 vs 传输方式 vs 库/表层）与 018 件共享，族级裁定一次生效。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 渠道 taxonomy 裁定（机构/传输方式/库表层三选） | 口径裁定（族级） | 本件 + 018 + 031 + DATATHM_033 | 分叉共享，先行 |
| 标签轴治理（table_data_source 回填） | 数据治理 | 本件（口径 B 解锁） | 比台账轻，可先行 |
| 渠道归集台账建设 | 数据工程立项 | 本件 + DATAIN_002 + 族内件 | 触发器①（族级并项） |
| ods 体量实数化（COUNT 替代估算） | 展示规范 | 本件代理读数 | 交付版建议 |

档位后果：台账+字典 → **完全直接支持**；标签治理+库/表层口径裁定 → **完全转换支持**；现状 → 部分支持。推荐顺序：taxonomy 裁定 → 标签治理（轻路径先走）→ 台账（族级立项）。

| v2 | 渠道归集台账 → 渠道×量×时间直查 | 触发器①（族级并项） |

### C.4 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 表级体量被冒充「渠道归集量」 | **高** | 标签改「库表体量」；补录脱钩披露（§2.5） |
| org_* 域 9/10 的单一叙事误导 | 中 | §3.2 代表性限制披露 |
| 标签轴治理后仍按错 taxonomy 分组 | 中 | v1 裁定先行（§C.3） |
| table_rows 估算值当精确数 | 中 | B9 标注+交付版实数化 |

### C.5 总判

**部分支持**：渠道归集台账零承载（结构级）+ 切片轴「有列无值」（数据级）双缺；表级体量与批次面代理三源双在可交付（语义降维披露）。gkx 标签轴的三表值域实测是本件最有信息量的探针——「有列无值」比「无列」更可惜也更可修（治理回填即解锁轻路径），v1 分期以此为主线。
