## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/主题视窗/数据库详情展示/数据集关联关系可视化（1.1.1.1.4.4.3.2.3；SRS seq 374、excel_row 377）。UI 实际容器是主题视窗中部的力导向图谱：`ThemeWindow.jsx:146-187` `getDatasetRelationOption()`——categories 四分类（`ThemeWindow.jsx:147-152`：文献计量/科技情报/领域主题/科技要素各配色），节点 15 个（mock `datasetRelationData.nodes`，`mockData.js:1484`），连线 16 条带关系标签（文献引用/基因-蛋白关联/靶点发现等）。本件挂载行 `ThemeWindow.jsx:148` 是 categories 首类 `{ name: '文献计量', itemStyle: { color: '#165dff' } }`——「文献计量类数据资源量」即该类目下的资源规模读数：图谱里文献计量类节点数（mock 3 个）背后的真实资源体量。需求原文（seq 374）：「采用知识图谱及节点网络可视化技术，展示数据集间的引用、衔接、主题交叉等关联情况」——图谱是需求明列功能，「文献计量类」是图谱自带的分类框架。

### 1.2 为什么需要本指标

关联图谱的分类着色让管理者一眼看到资源中心的**结构构成**：文献计量类（论文/专利/引文）是科研数据的底座，科技情报类（临床/影像/能源统计）是业务情报面，领域主题类（基因/材料/农业）是专题数据面，科技要素类（AI 训练/环境监测/人才）是要素支撑面。「文献计量类数据资源量」回答底座有多厚——它是资源建设投入产出比的核心分母（文献计量类采购/加工了多少数据）也是图谱叙事的可信度锚（底座类节点如果只有零星几个，「数据资源中心」就是空架子）。主需求 :2477 把「文献计量数据库」列在总体视窗资源结构首位（「涵盖文献计量数据库、科技情报数据库、领域主题数据库等」），人才域三处（:1463/:1701/:1707）把它作为数据融合底座点名——分区名的需求地位是明确的，缺的只是量指标。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**指标名「文献计量类数据资源量」三份真源 0 命中。「文献计量数据库」分区名的在案用法均为数据基础描述（:2477 总体视窗资源结构、:1463/:1701/:1707 人才域数据源枚举），无资源量统计口径（按库数？按表数？按记录数？论文+专利算不算同域？）。UI 图谱的类目框架（四分类）与 mock 分区字段（partition）是前端演示结构，不构成口径证据。本件按「文献计量=论文/专利及其文献学属性数据」的学科常识口径（R1/R2 权威方法佐证）做词族盘点，类边界双口径并列（§1.6）。

### 1.4 类似指标权威方法可行性分析概要

「文献计量数据资源」的权威界定分两支。其一，文献计量学（bibliometrics）学科口径：以科学引文索引（SCI/SSCI）、专利数据库（Derwent/Inpadoc）为标准数据源——Web of Science 核心合集、Scopus 全库、Lens.org（2.5 亿学术记录+3 亿专利）都是「文献计量类数据资源」的商业实践，资源量的通行计量是**记录数**（records）；其二，国家科学数据中心实践（R2/R3）：国家基础学科公共科学数据中心「数据记录超过 10 亿条」（R3）——记录数是官方量级口径。方法族对照：

| 方法族 | 类边界 | 计量单位 | 与三源匹配 |
|---|---|---|---|
| 学科口径（bibliometrics） | 论文+专利+引文 | 记录数 | **可映射**（词族盘点） |
| 商业库实践（Lens/Scopus） | 学术记录全集 | 记录数 | 可映射（主档行数） |
| 国家中心（R2/R3） | 中心全库 | 记录数/PB | 形态参考（量级锚） |
| 资源分区登记（需求语义） | 四分区类目 | 库/表/记录 | **无登记面**（待立项） |

结论：学科口径的词族映射三源即期可算（记录数量级充足），需求语义的四分区类目登记面缺位——本件按学科口径交付双口径读数。完整版见附录 C。

### 2.1 方法选择（文献依据）

方法选**词族盘点**（bibliometrics 学科口径的工程落地，R1 学科边界 + R3 记录数量级形态）：以表名词族（paper/patent/litera/biblio/thesis/citation/cited/reference）圈定资源边界，主档精确 COUNT + 结果面快照行数合计。选择理由：其一，词族面三源结构+数据双在（§2.2-2.4）；其二，主档记录数是商业库与国家中心的通行量级口径（Lens/Scopus/基础数据中心均以记录数报量）；其三，类边界不确定用双口径并列（B10），不擅自定案。dev 侧论文族 0 表是 S3-01 在案事实（gkxlumenx_dwd 无论文表），不重复深探。

### 2.2 gkx 词族盘点（主档精确 COUNT，核心承载）

gkx 280 表中词族命中 38 表（`gkx_family_table_count`，`gkx_family_tables_sorted` 全清单）：论文族 22 表——中文主档 `dwd_zh_paper`（100,900 行，s3_01 快照精确 COUNT）+ 英文主档 `dwd_en_paper`（1,387 行，本件实测）+ 文摘/引文/分类/基金/关联/题名等属性表（`dwd_zh_paper_abstract/citation/reference/title` 等）+ 学者论文关联（`dwd_scholar_paper_relation/dwd_scholar_papers`）+ 物质关联（`dwd_substance_paper`）；专利族 13 表——主档 `dwd_patent`（2,939,895 行，s3_01 快照）+ 文摘/申请人/受让人/引文/权利要求/说明书/同族/发明人/法律/优先权/题名/转让（`dwd_patent_*` 12 张属性表）。主档三表合计 3,042,182 条（论文中英 102,287 + 专利 2,939,895）——gkx 侧文献计量底座的记录数读数。

### 2.5 稳健性与口径敏感性

双口径的三点敏感性：其一，**跨域关联表的归属歧义**——`ads_institution_paper`（机构×论文）既是文献计量资源（论文属性面）又是机构域资源（机构画像面），核心口径剔除、宽口径计入，两口径差 2,001,999 条（`broad_minus_core_rows`，宽 39,265,801 - 核心 37,263,802）；其二，**备份/废表处理**——gkx 词族含 `dwd_patent_bak_20260912`/`dwd_scholar_papers_bak_20260923`/`dwd_scholar_papers_v3bad` 三张备份/坏表，本件主档口径只计 zh/en 主档与专利主档（属性表行数未逐一 COUNT——gkx 侧只交付主档读数，避免 38 表逐一 COUNT 的打库成本；宽口径的 gkx 部分同主档数，词族表清单留证）；其三，**mock 3 节点与真实体量的量级差**——mock 图谱文献计量 3 节点 vs 真实词族 gkx+久新 76 表（核心口径 `core_wan_unit`=3,726 万条），图谱节点的 size 值（78/73/80）是演示美学参数非量级映射，正式版节点大小可按本件词族行数重映射。

### 4.2 dev 论文主档未接入（数据级，次因）

dev `gkxlumenx_*` 无论文表（S3-01 在案）——开发库侧文献计量域只有专利族样例（29 万条）。这不影响本件核心口径（gkx+久新已充足），但影响「资源中心自有文献底座」的完整性：如果资源中心的正式叙事要求 dev 侧自有论文库，需接入工程（gkx dwd_zh_paper/dwd_en_paper 结构可复用）。此缺口与 DATAOV_001 §4.2 的接入台账缺口共用修复路径。
