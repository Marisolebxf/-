### 1.2 为什么需要本指标

累计调用与趋势分析的管理问题是「资源被用得多了还是少了」：累计量看存量消耗、同比增速看年度动能——「判断资源应用热度和生命周期，优化资源运维策略」（:2571 原文）。同比（较上年）是增长速度的基础口径（R1）：与环比相比，同比克服季节性波动、反映长期趋势——调用行为有明显周期性（工作日/月末/项目周期），年度同比是调用量趋势的最稳刻度。本库场景下，该读数要求调用动作被记录（接口×时间戳×次数的日志）——没有调用日志，任何内容面数据都与「被用了多少次」无关。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「调用量同比增速」指标名。**语义锚两处：主需求 :2563（资源接口状态跟踪）「通过API日志采集与接口调用分析，动态跟踪每个资源接口的连接活跃度、调用频率和失败率」；:2571（1.1.1.1.4.4.1.4.4 累计调用与趋势分析）「采用大数据统计技术，自动归集各类数据资源自上线以来的累计调用量，并按时间区段进行趋势分析」——功能在、且**需求自点名工程前提**（API 日志采集/归集累计调用量）；「同比增速」口径、调用量计数单位（次/批次？按接口还是按资源？）均无定义。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「调用量及其同比」的权威方法锚分三层。其一，国家统计局同比口径（R1）：同比增长速度=本期对上年同期，克服季节波动、反映长期趋势——本件「较上年」的标准定义。其二，政府数据开放平台的调用量统计实践（R2 深圳平台）：接口调用量累计 373,575,274 次公开统计、近七日/总量 TOP10 逐接口计数、扬州案例「累计被调用 4.78 亿次，同比增长 63%」——**调用日志聚合+同比披露**的官方形态，证明该读数的标准原料是平台侧调用日志。其三，国家数据资源调查的增速口径（R3）：「全国公共数据开放数据量同比增长 31.71%」——数据资源侧的年度增速官方叙事（度量对象是数据量非调用量，作叙事形态参照）。方法族对照：

| 方法族 | 代表 | 原料 | 度量对象 | 与三源匹配 |
|---|---|---|---|---|
| 统计同比 | R1（统计局） | 两期面 | 任意统计量 | **无两期调用面** |
| 开放平台调用统计 | R2（深圳/扬州） | 调用日志 | 接口调用次数 | **无调用日志** |
| 数据资源调查增速 | R3（国家数据局） | 年度调查 | 数据量 | 数据量面可代理但语义≠调用量 |
| 前端演示 | UI yoy 列 | mock 常量 | — | 结构披露（不作源） |

结论：权威口径的原料（调用日志两期面）三源零承载；R3 的数据量增速与调用量是两个度量对象，不可混同（015 已按数据量口径单独成件）。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：按 R1/R2 口径推测

$$\text{CallYoY}_y = \frac{\text{Calls}_y - \text{Calls}_{y-1}}{\text{Calls}_{y-1}} \times 100\%,\quad \text{Calls}_y = \sum_{\text{接口}} \text{调用次数}(y)$$

### 3.2 D2 最近邻证据与 D3 代理排除论证

**D2 量级证据**：dev `sys_log` 按月分布（`dev_sys_log_month_dist`）：2026-07:99 / 08:36 / 09:8 / 10:917，合计 1,060 条——管理操作级（月均数十至千条，且 10 月暴增是管理端密集操作），与 UI mock 语境的 totalCalls 2,856,000（日均近万次调用）**差三个数量级以上**；端点性质 020 已证（OAuth2 认证主导）。双重不符，整源排除。

**D3 代理排除论证**：本批 015 用内容年份面代理「数据量变化率」（判部分支持），本件为何不能同法代理「调用量同比」？因为两个指标的度量对象分属两侧：**数据量**是数据资产的规模属性（库内内容的年份分布是其边际变化的合理代理）；**调用量**是外部系统取用数据的服务动作计数——它发生在库外（网关/服务层），库内任何内容面（论文发表年/专利申请年/企业注册年/人才产出年）都不记录「谁在什么时候取用了多少次」。内容年份面的年份是**产出时间**，调用日志的时间是**使用时间**——两者在补录场景下彻底脱钩（一次回溯灌库让内容面出现历史峰值，而调用流水只有当期一笔）。故代理路径不存在，本件判完全不支持而非部分支持（与 015 的分界裁定，B10 写死）。

### 3.3 D1 的 absence_probe 全记录

否定性证据三件套：**查了什么**——①dev 542 表 call_log/invoke_log/api_log/access_log/request_log/usage_log/call_stat 词族（本件独立复跑，命中 []——0 张调用日志表；最近邻 sys_log 见 §3.2 排除）；②gkx 280 表 call/invoke/api/request/latency/response/duration/monitor/usage 词族（0 命中，族级探针 `gkx_call_like_tables=[]`——要素明细库无调用统计面）；③久新 210 表 call_log/invoke/api_log/access_log/request_log/usage_log/call_stat 词族（live 直连复核 0 命中——ADS 结果面库按快照管理无调用日志）；④三份需求真源（:2563/:2571 功能分句在、「调用量同比增速」名与算式无；:2571 自点名「归集累计调用量」前提）。**条件**——表级存在性+语义核对。**命中**——0。四缺失情形归属：D1 属「**表不存在**」（调用日志面三源均无——修复动作是 API 网关/调用日志接入，与 020/022 共用工程）。

## 四、数据缺失情况

### 4.1 调用日志面零承载（结构级，判定性缺口）

同比增速的两期原料（本年/上年调用次数）要求调用动作被记录。三源实测零承载（§3.3）——**服务侧从未留痕**：数据资源的「被使用」发生在 API 网关/服务层，该层日志未落库。需求 :2571 把「自动归集累计调用量」写进功能（前提自宣），工程未建。**四缺失情形归属「表不存在」**：修复动作是调用日志接入（网关日志/APM/访问计数），与 020（耗时维）/022（序列维）共用——一次接入，调用监控三件套全升档，且 seq 343-344 的服务可用性/接口响应/异常告警/调用分析族同时受益。

### 4.2 代理路径不存在（方法级，与 015 的分界）

内容年份面代理在本件不成立（§3.2 论证：产出时间≠使用时间）——这决定了本件判完全不支持而非部分支持。若强行用内容面年分布充当「调用量趋势」，会把「库内产出增长」冒充「服务使用增长」，语义完全失真——B10 禁止。唯一合法路径是触发器②（甲方裁定代理口径+先立项相应日志采集），库内无即期方案。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| API 网关/调用日志接入 | 监控工程立项 | 本件 + 020 + 022 + seq 343-344 族 | 触发器①（族级共用） |
| 导出列置空规范 | 展示规范 | 本件即期 | mock yoy 建议替换「暂无数据」 |
| 口径预定义 | 口径裁定 | 日志接入时同步 | 计数单位（次/批次）、聚合粒度（接口/资源） |

档位后果：日志接入 → **完全直接支持**；现状 → 完全不支持（无中间档——代理路径不存在）。推荐：随族级监控工程立项，本件不单独处置。
