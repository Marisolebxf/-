## 摘要

「应用主体总数」是总体视窗「资源应用主体详细列表」组件的汇总 Statistic（`ResourceAppSubjectList.jsx:126`），mock 给 10 个主体（科研机构 4/企业 3/项目团队 3，重点用户 4）——summary.total 就是 mock 数组长度。需求语义锚 SRS 总体视窗 seq 345/主需求 :2565「支持统计和展示所有资源实际应用主体，包括科研机构、企业、项目团队」——主体类型枚举在、计数口径无。数据侧判定分两层：严格口径的应用关系面（谁用过平台资源）三源零承载（subject 词族 0 命中；dev 主题工程库 21 表亦无实体登记表；mock 的调用资源类型/次数字段无数据侧对应）；但注册/要素域底册双在——dev `enterprise_base` 269,511 行（去重 268,647，活表增长中）、gkx 机构底册 189,116 + 海外高校 20,000 + 院所 2,074——上界口径计数即期可交付。核心语义排障：「数据里的主体」≠「用数据的主体」。判**部分支持**（双口径并列：严格 null、上界量级参考）。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**seq 345 语义派生**（「应用主体总数」指标名 0 命中；主体类型枚举与「统计和展示」功能在）。
- 复现状态：脚本已跑通；三源词族排除 + dev/gkx 底册实测计数 + 主题工程库实体词族扫描全落产物。
- 档位结论：**部分支持**（应用关系面零承载 + 注册域底册双在可代理）。
- 关键事实：dev `enterprise_base` 从历史快照 189,115 增至 269,511（活表增长 +42%）——上界口径读数是时点值，正式发布需注明快照日。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/总体视窗/资源应用状态/资源应用主体详细列表（1.1.1.1.4.4.1.4.3；SRS 总体视窗 seq 345）。UI 实际挂载是 `ResourceAppSubjectList` 组件（总体视窗「资源应用状态」区的主体明细卡）的汇总行第一格：`ResourceAppSubjectList.jsx:124-127` `<Statistic title="应用主体总数" value={summary.total} suffix="个" />`——`summary` 由 `mockData.js` 的 `resourceAppSubjects`（`:849-861`，10 条）在 `useMemo` 内聚合：`total = resourceAppSubjects.length`（`:46`），并列「累计调用（主体侧）」「重点用户」「主体构成」三格（`summary.byType` 按科研机构/企业/项目团队分桶）。表格列：应用主体（重点用户金星标）/主体类型/调用资源类型/调用次数/价值占比/用途——即 UI 对「应用主体」的完整画像=主体×类型×资源×调用次数×价值。mock 结构披露：10 是数组长度演示值，不作数据证据（B10）。

### 1.2 为什么需要本指标

主体总数回答「平台的数据被谁在用」的覆盖面：与累计调用量（用的强度）、重点用户数（用的深度）构成应用状态三读数。seq 345 的管理意图是「识别资源价值分布及重点用户」——总数是分布图的分母。官方对应物：国家数据局监测评估指南（R1）的「数源部门目录建设」（纳入授权运营范围的数源部门总数及占全部数源部门比例——供给侧主体计数）；省级公共数据资源调查表（R2）的「政务信息系统企业用户数量/个人用户数量」（需求侧主体计数）——官方两侧都以**登记关系**为计数基础（部门目录/系统用户册），不是从底册全量推。本库场景同理：应用主体总数的正确原料是「主体×资源应用关系」登记面，企业/机构底册只是候选池上界。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「应用主体总数」指标名。**语义锚：SRS 总体视窗 seq 345（主需求 :2565 同文）「支持统计和展示所有资源实际应用主体，包括科研机构、企业、项目团队等，详细列出各主体调用资源的类型、次数和用途，助力管理者识别资源价值分布及重点用户」——「所有资源实际应用主体」的「实际」二字把口径锚定在**发生过应用关系**的主体（非全量底册），主体类型三枚举在；但计数口径（按主体去重的键是什么/历史主体是否计入/项目团队如何登记）无定义。UI 的 10 是 mock 演示值，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

主体计数的权威锚分三层。其一，国家数据局监测评估（R1）：供给侧「数源部门总数」（建数源部门清单——登记制计数）+ 汇聚范围占比（清单内 ÷ 全部）——官方主体计数的分母是**清单**不是全量机构库。其二，省级调查表（R2）：「政务信息系统企业用户数量（个）/个人用户数量（个）」——按系统用户册填报，年度值+累计值双列。其三，平台运营实践（R3 上海平台）：应用注册制下的典型应用库与开发者账号体系——平台侧主体=注册开发者（账号制），可数、可审计。方法族对照：

| 方法族 | 代表 | 原料 | 口径 | 与三源匹配 |
|---|---|---|---|---|
| 数源部门清单 | R1（NDA 指南） | 部门目录 | 清登记制 | 无清单面 |
| 系统用户册 | R2（省级调查表） | 用户登记 | 年度/累计 | 无用户面 |
| 平台注册制 | R3（上海平台） | 开发者账号 | 账号计数 | 无注册面 |
| 底册代理上界 | 库内可行替代 | 企业/机构底册 | 去重计数 | **dev+gkx 双在**（量级参考） |
| 前端演示 | UI 10 | mock 常量 | — | 结构披露（不作源） |

结论：三条官方路径都要登记面（清单/用户册/账号），三源均无；库内可走的只有底册代理上界（口径必须披露）。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

方法选**登记面计数**（R1 数源部门清单制的工程对偶）：在「主体×资源应用关系」表上按主体键去重计数。选择理由：官方两侧先例（R1 清单制/R2 用户册制）都以登记关系为计数基础——「实际应用主体」的「实际」只能由关系记录证明，底册全量推会虚增（大量从未接触平台的主体）。**关系面缺位下**，本件交付降级为代理上界口径：dev `enterprise_base` 去重企业名计数 + gkx `dwd_org_base_info` 行数并列（不整合——跨源同名机构无映射表，叠加仅作量级参考，B3 note 写死）。

### 2.2 dev 注册域底册实测

dev `gkxlumenx_dwd.enterprise_base`（企业底册，活表）：总行数 **269,511**（`dev_enterprise_base_rows`，2026-11-02 实测），去重企业名 **268,647**（`dev_enterprise_base_distinct_names`——COUNT(DISTINCT enterprise_name)，重名 864 对）。注意：该表为活表，历史快照（S3-03 期）读数 189,115——本轮增长 +42%（企业底册在持续灌数），正式引用须注明快照日。主体类型分桶：底册仅企业一类（列结构无科研机构/项目团队标注），三分桶口径在 dev 侧不可分。

### 2.3 gkx 要素域机构底册实测

gkx 侧四张主体结构面（`gkx_counts_cache` B11 锚 + 本件复核）：机构主档 `dwd_org_base_info` **189,116** 行（`gkx_dwd_org_base_info_rows`）、海外高校 `dwd_forg_university_org_info` **20,000**（`gkx_dwd_forg_university_rows`）、科研院所 `dwd_research_institute_base_info` **2,074**（`gkx_dwd_research_institute_rows`）、学者 `dwd_scholar` **21,316**（`gkx_dwd_scholar_rows`，自然人主体参考）。与 dev 底册的关系：gkx org 底册与 dev enterprise_base 非镜像（189,116 vs 269,511——dev 侧含更多国内企业），跨源同名机构无映射表——两源计数**只可并列不可相加为正式值**（派生键 `registered_org_upperbound_dev_gkx_sum`=457,763 是未去重叠加的量级上界，note 写死）。

### 2.4 语义排障：「数据里的主体」≠「用数据的主体」

三源最接近「主体」的面全部是**数据域主体**（数据里描述的机构/企业——gkx org 底册、久新 institution 分析面 8 张 `ads_institution_*`、dev enterprise_base 企业档案），没有任何一张记录「该主体与平台发生过资源应用关系」。mock 侧的应用关系字段（调用资源类型/调用次数/价值占比）在数据侧无对应列——即便拿底册数出 45 万级，也回答不了 seq 345 的「实际应用」语义。四缺失情形归属：应用关系面属「**表不存在**」（三源均无——修复动作是建主体×应用关系表，可由调用日志/接入台账派生）。

### 2.5 口径敏感性与 mock 对账

## 四、数据缺失情况

### 4.1 应用关系面与类型标注双缺（结构级，主降档因）

严格口径的两个依赖（D1 关系面 + D2 类型标注）三源均为「表不存在」。修复动作：建「主体×资源应用关系」表（字段建议：主体标识/主体类型/资源标识/首次应用时间/累计调用次数——可由调用日志或接入台账自动派生），类型列按 seq 345 三枚举（科研机构/企业/项目团队）。该表与 013（供应方归属）、016（用户行为）、024/026（应用系统接入）共享同一登记面工程——一次建设五件受益。

### 4.2 上界口径的三重局限（口径级，交付披露）

其一，**语义局限**——底册主体未发生过平台应用关系（上界高估）；其二，**跨源未去重**——457,763 含跨源同名机构重复（无映射表不能去重）；其三，**分桶缺失**——底册仅企业一类，三分桶不可算。三重局限下上界只可作「主体候选池体量」参考，不得对外发布为「应用主体总数」（B10 写死）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 主体×应用关系登记面 | 数据工程 | 本件 + 013/016/024/026 族 | 触发器①（族级共用，五件一次升档） |
| 甲方裁定代理口径 | 口径裁定 | 本件 | 触发器②（enterprise_base 计数+口径披露） |
| 主体类型标注列 | 建表规格 | 本件分桶读数 | 随登记面建（三枚举） |
