## 一、需求定义概述

### 1.1 所属功能模块

科技信息展示系统 → 科技服务全景 → 科技传播 → 内容卡瀑布流 + `InsightDetailDrawer` 详情抽屉（`TechCommunication.jsx:81` meta 行 `<LikeOutlined /> {content.likes}`；`:126` 基本信息 items `{ label: '点赞数', value: detailTarget.data.likes }`）。数据源 `mockData.js:311-319` communicationContents 8 条（likes 260/310/380/420/540/650/890/1230）。

### 1.2 为什么需要本指标

点赞数是单条内容的**用户主动反馈读数**：与浏览量（THINK_011，被动触达）构成转化关系（浏览-点赞比），与月浏览量（THINK_010）构成质量互补。管理者用它识别高共鸣内容、排热门；用户把它作点击决策的社会证明。

### 1.3 需求文档是否给出定义方法

三份说明书未出现该指标名（检索记录见附录 A）。**固定句式：三份说明书未给出该指标的计算方法。**（挂载点为清单实查定位。）

### 1.4 类似指标权威方法可行性分析概要

权威侧无国标点赞口径（GB/T 31524 只管 PV/UV）；内容平台通用实践：点赞事件表（用户 ID+内容 ID+时间戳，幂等键防重复点赞）+ 主档 likes 快照列异步回写。方法族：①事件流水累计（可审计，可算去重）；②快照列直读（工程通用，依赖回写）；③第三方社交指标（阅读量/在看等，平台自设）。点赞属平台自设运营指标。

## 四、数据缺失情况

### 4.1 缺口清单

①点赞事件流水无表（三源）；②内容主档点赞快照列无预置（宿主表无列）；③十类传播内容主档本身未建全（12 行通用新闻≠十类）；④点赞去重口径未定（同用户重复点赞是否幂等，业界无强制标准）。

### 4.2 修复建议与影响面

短期：内容主档立项时同步落 likes 快照列 + 前端埋点回写 → 本件完全转换支持。中期：平台互动事件表入湖（用户 ID+内容 ID+行为类型+时间戳，幂等键）→ 评论/点赞/分享整族激活（P10_004/THINK_012 联动）。远期：社交平台 API 直连（公众号在看/点赞）→ 多端互动合并口径（须披露平台差）。同抽屉「浏览量」（THINK_011，部分支持）升档门槛更低（快照列结构已在），本件点赞列须从零预置。

### 4.3 影响面

科技传播页内容卡与详情抽屉的点赞数为 mock 演示态；整页互动反馈面无任何后端接口调用。
