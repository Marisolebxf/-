## 摘要

「存在质量问题的资源数」是接入视窗 P1-11 问题资源能力族的计数总闸：KPI 卡「问题资源数 23 个」（`AccessWindow.jsx:355-359`，accessKPIs）之下挂着整套稽核运营面——问题资源可视化统计报表（byType 六类/byLevel 三级/byChannel 五渠道/monthlyTrend 五月双线「问题总数/已解决」，`:514-566` 可导出）与自动识别列表（problemResources 8 行明细含状态流转 待处理/处理中/已解决，`:613-620`）。数据侧判定核心是**质量稽核违例登记台账**存在与否：三源词族逐一排除（dev 542 表 problem/issue/alarm/error 0 命中+quality 唯一命中运维开关语义排除 / gkx 280 表 0 命中 / 久新 212 表 0 命中+仿真面语义排除）。**台账缺位 → COUNT(DISTINCT) 无从执行**。判**完全不支持**。本件独立发现：**月度口径陷阱**（KPI 23 与 trend 5 月 total 同值但 5 月合计 108——当月新增 vs 存量未解决未定义）+ **三套数字互不对账**（KPI/byType/byLevel 均 23 对上，但明细仅 8 行）——演示数据自证稽核流水不存在。脚本已跑通（三源排除证据+三套数字实算对账落产物）。

- 需求判定：**需求能力项派生读数**（seq 367「问题资源自动识别与可视化统计」——识别+统计双能力；seq 343「异常告警」——流水前提；计数口径无定义）。
- 复现状态：脚本已跑通；三源词族排除 + 两处语义排除 + 三套数字实算对账全落产物。
- 档位结论：**完全不支持**（违例登记台账三源零承载——质量组最深缺口：台账是稽核最小产出物）。

### 1.2 为什么需要本指标

问题资源数回答「当前有多少资源的数据不可信」：它是质量运营的**总闸读数**——KPI 卡一眼看规模、趋势线看收敛（问题总数 vs 已解决双线）、四维分布定位重灾区（哪类问题/哪个渠道/多严重）、列表逐条处置（状态流转）。需求把它立在 seq 367「问题资源自动识别与可视化统计」——**识别（登记）+ 统计（聚合）** 双能力，与 seq 343「异常告警」构成稽核运营闭环。权威对应物是 R3（GB/T 39912-2021）汇交审核：管理方对汇交数据质量审核、不通过项登记台账——问题登记的制度形态；R1（GB/T 36344-2018）六维校验的违例即问题——问题类型枚举的维度源（mock byType 六类与之同构：完整性/准确性/时效性/规范性+两类工程异常）。本库场景下，该读数要求违例登记台账存在——没有台账，识别无从登记、统计无从聚合。

### 1.3 需求文档是否给出定义方法

**需求文档未给出计数口径。**SRS 接入视窗 seq 367「问题资源自动识别与可视化统计」（能力描述——识别与统计双要求，但未定义：问题判据（什么算「存在问题」——校验失败？人工标记？）、计数口径（**存量未解决 vs 当月新增**、去重否——一资源多问题算几个）、状态流转（待处理/处理中/已解决的闭环规则））；seq 343「异常告警」（告警流水前提，未定义告警与问题的换算）。**「问题资源数」KPI 字面**三份说明书 0 命中（仅见 UI accessKPIs）。**月度口径陷阱实证**（§3.2）：mock KPI 23 与 monthlyTrend 5 月 total 同值，但 1-5 月合计 108、resolved 合计 86——若 23 是当月新增则未解决存量应为 108-86=22（≈23 微差不齐）；若是存量则与 trend 语义脱钩——mock 自身未定义，两读皆不通。

### 1.4 类似指标权威方法可行性分析概要

问题资源计数的权威方法分三层。其一，汇交审核制度（R3 GB/T 39912-2021）：管理方对汇交数据做质量审核（真实可靠原则），**不通过项登记台账**——问题登记+处置闭环的制度形态；其二，数据治理平台工程口径（R2 Dataphin）：质量规则校验产生**校验流水**（通过/不通过），问题表=存在不通过规则的表——违例流水的工程范式；其三，国标评价框架（R1 GB/T 36344-2018）：六维指标校验（规范性/完整性/准确性/一致性/时效性/可访问性）——**问题类型的枚举源**。方法族对照：

| 方法族 | 原料 | 问题发现机制 | 与三源匹配 |
|---|---|---|---|
| 汇交审核台账（R3） | 审核记录 | 人工审核登记 | **无审核台账** |
| 规则校验流水（R2） | 规则库+跑批 | 自动校验不通过 | **无规则库/流水** |
| 六维校验（R1） | 评价表 | 维度指标违例 | **无评价表** |
| 前端演示 | mock 三套 | 手写常量 | 结构披露（不作源） |

结论：三条权威路径的原料（审核台账/规则流水/评价表）三源均无承载——本件是质量组**最深缺口**：评分（058/061）与分布（059/060）都是稽核的衍生读数，违例台账才是稽核的**最小产出物**（「有问题吗」先于「多少分」）。与 DATATHM_017（问题总数——同缺稽核流水，本件的计数孪生）同根。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：按 R3→R2→R1 路径推测，问题资源数是违例台账的去重计数——

$$N_{\text{problem}} = \bigl|\{\, r : \exists\, v \in T(r),\ v.\text{status} \neq \text{resolved} \,\}\bigr| = \text{COUNT}(\text{DISTINCT resource\_id})\; \text{WHERE status} \neq \text{resolved}$$

其中 $T(r)$ 为资源 r 的违例登记集（R1 六维校验产出，R2 流水形态，R3 台账制度），口径取**存量未解决**（KPI 语义）——若取当月新增须加 `AND found_month = current`。月度趋势：$N_{\text{total}}(m)$（当月发现）与 $N_{\text{resolved}}(m)$（当月解决）双线。**口径三未裁**：问题判据（校验失败阈值）、存量 vs 当月、去重规则（一资源多问题算一）。**前提是违例登记台账存在，三源实测无（§3.3）**——公式列示仅作口径锚（F4：本件 §二 从缺）。

**降档/升档触发器（B10 模板）**：①质量稽核违例台账立项（识别规则 R1 六维底稿+自动登记+状态流转）→ COUNT(DISTINCT) 直查（KPI/四维分布/趋势全套通吃）→ 升**完全直接支持**；②乙方自建核查脚本+问题登记（月度跑批）→ 升**完全转换支持**（判据/口径/状态机须登记）；③维持现状 → 完全不支持（UI KPI 卡与双 Tab 建议「暂无数据」）。

## 四、数据缺失情况

### 4.1 质量稽核违例登记台账零承载（结构级，判定性缺口——质量组最深）

违例登记台账三源零承载（§3.3）——本件是质量组的**最深缺口层**：058/061（评分）/059/060（聚合）都是稽核的衍生读数，违例台账才是稽核的**最小产出物**（「有问题吗」先于「多少分」）。SRS seq 367 把「问题资源自动识别与可视化统计」写进需求（识别+统计双能力），但三源无识别规则、无登记台账、无状态流转——问题资源从未被系统化发现过。**四缺失情形归属「表不存在」**：修复动作是违例台账立项（识别规则 R1 六维底稿+自动登记+状态机 待处理/处理中/已解决）；台账建成后 KPI/四维分布/趋势/列表**全套通吃**（一表六读）。本缺口与 017（问题总数——计数孪生）直接共享，且是 058/059/060/061 的**前置基建**（台账先于评分面）。

### 4.2 计数口径三未裁（口径级，即便建成也须先裁）

计数口径三无定义（§1.3/§3.2）：**问题判据**（什么算「存在问题」——R1 六维校验失败？人工标记？告警换算？）、**存量 vs 当月**（KPI 语义倾向存量未解决——月度口径陷阱实证）、**去重规则**（一资源多问题算一——本件定义即去重计数）。另有**状态机**（待处理/处理中/已解决的流转与回退规则）。正式版须一纸裁定——此裁定与台账立项解耦，可先行。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 质量稽核违例台账（识别规则+登记+状态机） | 数据工程立项 | 本件 + 017 + 058/059/060/061 | 触发器①（**族内第一优先级**：台账先于评分面，一表六读） |
| 计数口径裁定（判据/存量当月/去重/状态机） | 口径裁定 | 本件 + 017 | 月度口径陷阱实证在前，可先行 |
| UI 暂无数据态 | 展示规范 | 本件 UI 四处 | KPI 卡+双 Tab 建议空态提示 |

档位后果：台账 → **完全直接支持**（一表六读）；自建核查+登记 → **完全转换支持**；现状 → 完全不支持。推荐顺序：口径裁定先行（即期一纸）→ **台账立项（族内最优先**，017/069 直接受益、058/059/060/061 前置）。
