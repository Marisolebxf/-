## 摘要

「季度区段调用量」是总体视窗·累计调用与趋势分析卡（seq 346）左侧双轴图的「按季度」档：区段调用量柱状 + 上线以来累计折线（`CumulativeCallTrendAnalysis.jsx:26-77`，三档 Segmented 切换 :169-174）。指标名三份需求说明书 0 命中，语义锚在 seq 346「按时间区段进行趋势分析」——「时间区段」粒度（周/月/季）无定义，UI 三档是前端演示约定。数据侧判定核心是调用×时间戳明细面存在与否：三源词族逐一排除（dev 5 张命中全 0 行且语义排除；gkx 0 命中，要素表年份列是内容年份非调用时间；久新 14 张命中全为科研问题/技术热度快照面，`metrics_as_of_date` 单日一期无逐期调用记录）。时间序列最近邻 enterprise_base 月维仅 2 点且语义不符，不作代理。判**完全不支持**。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**需求功能分句派生**（seq 346 功能在；「季度区段调用量」名与聚合口径无）。
- 复现状态：脚本已跑通；三源词族排除 + 月维时间轴披露全落产物。
- 档位结论：**完全不支持**（调用台账零承载 + 库内无可用季度时间轴）。
- 关键事实：库内唯一真实时间序列面（enterprise_base.update_time）只有 2026-08/2026-09 两个有效月维点（269,163/348）——三大批次日集中 8 月的批次式灌库，而 mock 演示的是 2025Q2-2026Q2 五个季度的平滑爬升——库内既无调用事件，也无同构季度节奏。

### 1.2 为什么需要本指标

区段序列是「热度与生命周期研判」（seq 346 结尾语）的**时间维原料**：只看累计总量无法区分「持续高热」与「一次性冲量」——区段序列回答「每个季度用了多少、趋势是升是降」。权威对应物是公共数据开放平台的调用趋势公示（R2 江苏「接口调用趋势：近一年/近三个月/近一个月」；R4 安沐开放平台「>90 天查询支持月度粒度」）——区段聚合粒度由平台运营方定义，前提都是接口级调用日志。本库场景下，该序列要求调用事件带时间戳的明细面存在——没有台账，任何区段聚合都无从谈起。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「季度区段调用量」指标名。**语义锚一处：SRS 总体视窗.md seq 346（:241-252）「自动归集各类数据资源自上线以来的累计调用量，并按时间区段进行趋势分析，帮助用户判断资源应用热度和生命周期」——「时间区段」的粒度清单（周/月/季？）、聚合口径（按资源？全平台？）、起算点（上线日？财年？）均无定义。核增需求与算法库 0 命中（附录 A.2）。UI 的三档切换与五点季度序列是前端演示约定，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

「区段调用量序列」的权威方法锚分三层。其一，国家数据资源统计面（R1 国家数据局 2025 调查报告）：政务共享枢纽调用次数按「新增值/累计值」双列公示——区段（年度新增）与累计并行的官方口径形态，前提是调用日志逐笔落账。其二，地方开放平台趋势实践（R2 江苏 / R3 深圳）：接口调用趋势按近一年/近三月/近月三窗（江苏）、近七日/累计双窗（深圳）——粒度由运营方定义，原料同为接口日志。其三，库内时间序列面：enterprise_base.update_time 月维（批次式 2 点）与久新 `metrics_as_of_date`（快照单日一期）——形态上都不是逐期调用记录。方法族对照：

| 方法族 | 代表 | 粒度 | 原料 | 与三源匹配 |
|---|---|---|---|---|
| 官方新增/累计双列 | R1（国家数据局） | 年度新增+累计 | 逐笔调用落账 | **无台账** |
| 开放平台趋势窗 | R2 江苏 / R3 深圳 | 月/周/日 | 接口级调用日志 | **无日志** |

| 前端演示 | UI quarter 五点 | 季度 | mock 常量 | 结构披露（不作源） |

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：按 UI 结构反推，季度区段调用量=调用台账按自然季度聚合的区段和与累计和

$$\text{Calls}_{q} = \sum_{t \in q} n_t,\qquad \text{Cum}_{q} = \sum_{q' \le q} \text{Calls}_{q'}$$

即季度 $q$ 内调用次数之和（区段 bar）与截至 $q$ 的累计和（累计 line）。**前提是调用台账存在（调用事件×时间戳），三源实测无（§3.3）**——公式列示仅作口径锚，不构成可执行计算（F4：本件 §二 从缺，无伪计算过程）。

## 四、数据缺失情况

### 4.1 资源调用台账零承载（结构级，判定性缺口）

季度区段序列的唯一原料是调用事件×时间戳的逐笔明细。三源实测零承载（§3.3）——这不是数据量问题而是**调用监控工程缺位**：调用从未被逐笔记录，任何粒度（周/月/季）的聚合都无原料。需求 seq 346 把「自动归集……累计调用量，并按时间区段进行趋势分析」写进功能描述（工程前提自宣），三源无对应承载。**四缺失情形归属「表不存在」**：修复动作是 API 网关日志/调用台账接入——调用台账族（020/021/022/025/034/035 + 本件）共享此工程，一次接入全族升档。

### 4.2 库内时间轴不可代理（方法级披露）

两条潜在代理路径均被排除：其一，dev `enterprise_base.update_time`——语义是企业底册批次灌库时间戳（非调用），且月维仅 2 点（批次式非逐月）；其二，久新 `metrics_as_of_date`——快照管理字段（单日一期），非逐期事件记录。两条路径「有日期列」≠「有调用时间轴」，与 020 件 sys_log 耗时列的排障逻辑同构（本族最重要的语义排障模式）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| API 网关/调用台账接入 | 监控工程立项（族级） | 本件 + 020/021/022/025/034/035 + seq 343-346 族 | 触发器①（一次建设族内升档） |
| 区段粒度口径裁定 | 口径裁定 | 本件 | 周/月/季三档清单与起算点须甲方定 |
| UI 暂无数据态 | 展示规范 | 本件 | mock 五点建议替换为「暂无数据」 |

档位后果：台账建成 → **完全直接支持**；拨测/第三方监测 → **完全转换支持**（口径披露）；现状 → 完全不支持。推荐顺序：台账立项为主线（族级共用），粒度裁定并行（零成本）。
