### 1.2 为什么需要本指标

seq 378 的管理命题是「**平台的数据资产用在哪些业务上**」：六字段画像把每项资产的应用足迹（谁在用/用在哪/用多久）拉平成一张清单，seq 379 的多维筛选支撑业务分析与汇报下钻。「数据资产数量」是这张清单的**规模基线**：没有总量，筛选命中数（N/7）没有分母参照；有了它，业务类型覆盖度（几类业务有资产支撑）、单位渗透率（几家单位在用）才有计算基准——与 036（表总数，供给侧规模）互补构成资产侧的「存量×应用」双读数。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「数据资产数量」「资产数量」字面三份真源 0 命中（附录 A.2）。需求明列的是功能（SRS 应用视窗.md seq 378）：「为每项被应用的数据资产整理基础信息，如所属数据类型、应用主体、部署位置、使用周期、涉及的业务模块，便于业务部门整体评估资产应用效能」——**资产是列举对象不是计数指标**；「被应用的」限定词把口径锚定在应用关系上（非全量存量），但应用关系怎么登记无定义。三个口径黑洞：①资产单元是什么（物理表/数据集/主题库——mock 7 行是主题库级粒度）；②「被应用」怎么判（有调用流水？有挂接业务模块登记？）；③边界剔什么（配置 schema/备份表同 036 未裁）。mock 的 7 行是叙事截断演示（覆盖六业务类型），不构成口径证据。核增需求与算法库 0 命中。

## 四、数据缺失情况

### 4.1 逻辑资产目录零承载（结构级，升档关键缺口）

「资产×类型×应用关系」的数据资产目录三源零承载（§3.3）——与 036（白名单登记面）/006（价值分级面）三件同根：**资产管理制度缺位**。本件的特异性：seq 378 的六字段画像（数据类型/应用主体/部署位置/使用周期/业务模块/使用单位）就是目录的字段需求清单——需求其实已经把目录 schema 画出来了，缺的只是登记动作与流水挂接。**四缺失情形归属「表不存在」**：修复动作是目录立项（mock 六字段直作底稿）；物理口径（926/1,032）作为过渡期读数交付，边界裁定随目录落位自动闭合。

### 4.2 asset 词族语义陷阱披露（方法级，防误用）

「asset」是本域最大的字面陷阱（§3.3）：dev/gkx 命中的 6 张表没有一张是「数据资产」——3 张 BI 拖拽报表配置（onl_drag_dataset 族）、3 张企业年报财务资产（dwd_org_annual_report_asset 族，注册资本科目转换 bak 可证）。若按词族直接计数会把**财务资产**（企业注册资本口径）混入数据资产读数。本件在 §3.3 留语义核对证据并在 notes 写死排除理由，后续族内件引用 asset 词族时以本件为先例（与 017 件 problem 词族排除先例同型）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 数据资产目录立项（六字段底稿直用） | 数据工程立项 | 本件 + 006（分级属性）+036（白名单） | 触发器①（族级最大公约数） |
| 物理口径剔除规则裁定 | 口径裁定 | 本件 + 036/037 | 触发器②（一纸三件受益） |
| 「被应用」判定口径（流水挂接规则） | 口径裁定 | 本件（seq 378 语境） | 随目录立项落位 |
| 过渡期物理读数交付 | 交付策略 | 本件 | 926/1,032 多口径并列（B10） |

档位后果：目录立项 → **完全直接支持**；物理口径裁定 → **完全转换支持**；现状 → 部分支持（多口径并列）。推荐顺序：口径裁定（即期一纸，与 036 共用）→ 目录立项（族级主线，mock 字段底稿降本）→ 应用流水挂接（seq 378 语境闭合）。
