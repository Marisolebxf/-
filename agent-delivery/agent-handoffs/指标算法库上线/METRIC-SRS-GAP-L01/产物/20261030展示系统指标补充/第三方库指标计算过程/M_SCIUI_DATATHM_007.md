**语义裁定（派单预警处置）**：本组件族是**数据源可靠性评估面**而非 mock 纯演示——判定依据有三：其一，组件注释自标需规 seq 331；其二，五段结构与 seq 331 功能句逐分句对位（「智能分类和标签技术」→智能分类横幅+标签表、「来源的结构组成及变化」→结构占比+趋势+环比、「数据质量和来源可靠性」→质量与可靠性评估卡）；其三，筛选器（来源类型/可靠性/关键词）与详情 Drawer 是可交互评估界面形态。但**数据层是 mock**——五来源类型清单、reliability 评分（93/96/95/82/78）、环比 delta 全部硬编码于 mockData.js，无任何 API 调用。结论：需求真源在（seq 331）、UI 骨架在、数据面缺——本件按「评估面承载缺失」而非「演示页无需求」处理。

### 1.2 为什么需要本指标

seq 331 的管理命题是「**数据能不能信**」：来源结构占比回答数据从哪来，可靠性评估回答这些来源可不可靠，环比对比回答可靠性结构在变好还是变坏。「上期占比」是环比的基期锚——没有基期，本期读数只是横截面快照，无法回答「趋势」；mock 作者把五来源的 previous/current/delta 三元组并列，正是「结构变化」分句（seq 331「详细分析资源来源的结构组成**及变化**」）的直接实现。从数据治理视角，这类读数是数据源治理例会的基础物料：哪类来源可靠性占比掉了 2pp，下一季度的稽核资源就投向哪里。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「可靠性上期占比」指标名三份真源 0 命中。语义锚 seq 331（SRS 总体视窗.md:29 / 主需求 :2493）：「通过智能分类和标签技术，自动归纳各项科技数据的具体来源，包括国内外数据库、科研院所、企业和开源平台等，详细分析资源来源的结构组成及变化，辅助判断数据质量和来源可靠性」——「来源可靠性」是辅助判断的目标，判定标准（哪些维度算可靠？阈值多少？）、评估范围（全部资源还是抽检？）、期次（月/季/年？基期怎么定？）全部无定义。主需求 :717「用户可以查看数据来源的可靠性和时效性」是科技发展态势域的另一处功能复述（数据来源说明卡），同样无算式。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「来源可靠性占比」的权威方法锚分三层。其一，国标数据质量评价框架（R1 GB/T 36344-2018）：规范性/完整性/准确性/一致性/时效性/可访问性六维，每维按「满足要求元素数 ÷ 被评价元素数」计——达标占比的结构是国标原生形态，但六维稽核规则与阈值须先登记。其二，数据治理规范（R2 GB/T 34960.5-2018）：数据治理域含质量监控与评价过程——评估落地为「规则库+稽核流水+逐期评估报告」三件套，基期读数来自评估报告的期次序列。其三，汇交质量审核（R3 GB/T 39912-2021）：科学数据管理方承担汇交数据的质量审核（4.2 真实可靠原则）——来源侧可靠性的制度化形态是**汇交审核台账**（提交方×数据集×审核结论）。方法族对照：

| 方法族 | 判定轴 | 数据要求 | 与三源匹配 |
|---|---|---|---|
| 六维达标占比（R1） | 稽核规则×阈值 | 规则库+稽核流水 | **无（规则库未建）** |
| 治理评估报告（R2） | 评估期次序列 | 逐期评估面 | **无（单期皆无）** |
| 汇交审核台账（R3） | 提交方×审核结论 | 审核流水 | **无（无台账）** |
| 前端演示 | mock 常量 | mockData.js | 结构披露（不作源） |

结论：三条权威路径的原料（规则库/期次评估面/审核台账）三源均无承载。完整版见附录 C。

## 四、数据缺失情况

### 4.1 来源可靠性评估面零承载（结构级，判定性缺口）

「来源×评分×期次」的评估登记面三源零承载（§3.3）——这不是数据量问题而是**评估工程缺位**：来源可靠性从未被系统性评过（无规则库、无稽核流水、无评估报告）。需求 seq 331 把「辅助判断数据质量和来源可靠性」写进功能描述，UI 也按评估体系已建的形态做了五段组件，但数据侧的评估三件套（规则/流水/报告）一件都没有。**四缺失情形归属「表不存在」**：修复动作是来源可靠性评估面立项——R1 六维规则库是制度抓手，稽核流水是数据抓手，两者齐备后逐期评估面自然落地。本缺口与 DATATHM_008 完全同根（族级并项，一次立项双件受益）。

### 4.2 期维缺口（本件特有加深）

即便评估面建成，环比还需**至少两期**评估序列：基期读数 = 期次序列的倒数第二期。三源现状是「单期皆无」——久新的 metrics_as_of_date 是全库统一快照日（单日一期），不是逐期评估；dev/gkx 无任何分期语义。这意味着本件是族内升档最慢的一件：评估面立项后须先积累两期，环比对比才有数据。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 来源可靠性评估面（规则库+稽核流水+逐期评估） | 数据工程立项（族级） | 本件 + 008 | 触发器①（一次建设双件受益） |
| 来源结构登记（五来源类型×资源清单） | 数据工程 | 本件 + 008 + DATAIN_002/003 来源轴 | 分母侧共用 |
| R1 六维规则登记 | 口径裁定 | 本件族 | 阈值 θ 与评估范围 R 一纸裁定 |
| UI 暂无数据态 | 展示规范 | 本件 UI | mock 20.1-28.5 基期值建议替换为「暂无数据」 |

档位后果：评估面+两期积累 → **完全直接支持**；人工评估登记（不建流水）→ **完全转换支持**；现状 → 完全不支持。推荐顺序：规则登记（即期一纸）→ 评估面立项（族级主线）→ 期次积累（环比前置）。
