## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技政策跟踪/**多维政策对比**（export 挂靠口径）·利益攸关方参与评估。UI 实际容器是政策效果推演（效果预估）工作台的「利益攸关方参与评估」Tab 子面板（`EstimateWorkbench.jsx:672` 起）：三段结构——①`AlertBanner` 复述 SRS 需规（「在线问卷 / 意见征集 / 专家评审 → 汇总意见并纳入效果评估模型」）；②「评估活动识别」四卡（`STAKEHOLDER_AUDIT` 页内 mock 常量 `:75-81`：目标是否合理→合理/组织是否协调→基本协调/程序是否公正规范→规范/方法是否科学可行→可行）；③「信息反馈与互动」表单（`:672` 起的 Form：反馈渠道三选「在线问卷/意见征集/专家评审」、身份五选「决策者/评估者/企业/专家/公众」、单位选填、综合评分 `Rate` 1-5 星、意见文本、「纳入评估模型」开关）。提交动作 `setFeedback((prev) => [item, ...prev])`——**数据只进前端 React state，无任何 API 调用**，`message.success('已提交至站内意见列表（🧪 Mock，未外发）')` 自证演示态。

### 1.2 为什么需要本指标

政策效果评估的方法论痛点是「内部评估自说自话」——评估结论若不受利益攸关方（决策者/评估者/企业/专家/公众）检验，则目标合理性、组织协调性、程序公正性、方法可行性四项质量属性无从验证。需求原文的设计是让评估过程开放参与：三渠道（问卷/征集/评审）收集意见 → 系统汇总 → 纳入效果评估模型——参与度评分正是这个开放过程的量化读数，回答「评估活动的参与广度与质量够不够」。在多维政策对比语境下，它充当对比结论的公信力权重：两政策效果评估得分接近时，参与度高的评估结论更可信。它的政务对应物是重大决策社会稳定风险评估的公众参与程序（R1/R2：听证/公示/问卷征意的制度化要求）。

### 1.3 需求文档是否给出定义方法

**需求文档给出流程定义但未给出评分算法。**主需求 :1421-1423（1.1.1.1.4.2.3.1.5 利益攸关方参与评估）原文：

> 提供信息反馈与互动模块，支持决策者、评估者和利益攸关方等各方参与政策评估全过程，用户可通过在线问卷、意见征集、专家评审等方式提供反馈，系统汇总各方意见并纳入效果评估模型，确保评估活动目标合理、组织协调、程序公正规范、方法科学可行。

四项「确保」是评估活动的质量属性识别（UI 四卡正对应），不是参与度算式。export 行原文自认：「按评价模型算出的分数（科技政策库场景）——**评分维度和算法需要立项调研后才能确定**」。SRS 政策效果推演对应叶同文转述主需求。核增需求（2026-04 政策对比功能升级）17 叶逐一核对**无**利益攸关方条目——本叶属原方案效果预估，核增升级的是对比功能，两者不冲突。

### 1.4 类似指标权威方法可行性分析概要

「参与度评估」的权威方法锚是公众参与/社会稳定风险评估体系：

| 方法族 | 代表 | 评分结构 | 数据要求 | 与本库匹配 |
|---|---|---|---|---|
| 公众参与度指数 | R1 重大行政决策程序（听证/公示/征意） | 参与率+意见采纳率合成 | 参与事件流水（谁/何时/渠道/意见/采纳状态） | **事件无承载** |
| 社会稳定风险评估 | R2 稳评框架（风险识别→听证→量化） | 风险清单×参与广度×程序合规 | 听证记录/问卷台账 | **事件无承载** |

方法链条的共同前置是**参与事件台账**——无论选哪种评分口径，第一步都要有「事件记录表」。本库三源均无此面。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（三层均未闭合）**：

$$S_{participation} = g(E),\quad E = \{e_i\} = \{(user_i, role_i, channel_i, policy_i, t_i, score_i, comment_i, adopted_i)\}$$

即评分是参与事件集 $E$ 的函数。候选口径至少三种：**A 参与率**（参与人数/目标人数——需目标人群分母）；**B 参与量**（意见条数/评审场次——需事件计数）；**C 参与质量加权分**（$\sum w_{role} \cdot w_{channel} \cdot score_i$——需身份×渠道×评分×采纳状态）。UI 表单结构（身份五选/渠道三选/Rate 1-5/纳入开关）暗示 C 口径，但表单无后端落库。**当前三口径的分子数据均无源**，评分函数 $g$ 亦未立项——双缺。

**降档/升档触发器**：①应用侧（`gkxlumenx_mp`/`cms` 运行时库）问卷/意见征集功能上线并回流数据仓（事件台账闭合）+ 评分模型立项选型 → 升**完全转换支持**（评分随事件结构一并设计，dev `policy_public_opinion` 19 列结构可直接承载）；②若甲方接受政务侧稳评听证/问卷数据（R1/R2 口径）→ 需外部对接单独立项（不在三源范围）。降档无空间（已到底档）。

## 二、计算过程

### 2.1 方法选择（文献依据）

若事件面闭合，评分方法选参与质量加权分（口径 C）：以 R1 公众参与程序（参与广度+意见采纳的程序合规要求）为制度锚、R3 利益相关者分析（身份×影响力矩阵）为权重设计锚——身份五类（决策者/评估者/企业/专家/公众）×渠道三类（问卷/征集/评审）的二维权重表 + 1-5 星评分加权求和，采纳状态（adopted）作后期校正项。选择理由：UI 表单结构已暗示该口径（字段一一对应），且与 SRS「汇总各方意见并纳入效果评估模型」的语义一致（评分要能反馈进模型，必须是可比数值而非事件计数）。但该方法当前**不可执行**——事件集 $E$ 为空，权重表无数据可作用。

### 2.2 事件层三源盘点

## 四、数据缺失情况

### 4.1 参与事件零承载（数据级，主因一）

参与事件是运行时交互数据：问卷提交/意见征集/评审记录产生于终端用户操作，须经应用层（`gkxlumenx_mp`/`cms` 运行时库）落库后回流数据仓。当前链路断在源头——反馈功能未上线（UI 是 mock、dev 落位表 0 行）。三源（gkx 要素库/dev 数据仓/久新分析仓）都不是交互数据的产生地，也不存在外部交互数据接入。修复路径唯一且清晰：应用侧功能上线 → 事件写入 `policy_public_opinion`（结构已备）→ 数据仓可查。这一缺口与 POLCMP_001（兑现事件）/POLCMP_002（惠及事件）同构——**「事件在别处」**是政策族负结论件的标准形态。

### 4.2 评分口径未立项（方法级，主因二）

「参与度」的三种口径（A 参与率/B 参与量/C 质量加权分）分母分子各不相同：A 需目标人群（三源无）；B 只需事件计数（结构可满足但语义最弱——凑数提交会灌水）；C 需身份×渠道权重表 + 采纳状态（立项工作量最大、语义最强）。SRS 四项「确保」（目标合理/组织协调/程序公正/方法可行）是评估活动质量的定性识别，不是参与度量化结构——UI 四卡的定性 Tag（合理/基本协调/规范/可行）忠实还原了这一定性语义，恰恰反证「得分」是另一层未定义的量化。修复路径：立项选型（推荐 C 口径起步——表单结构已暗示；A 口径的目标人群分母可用政策适用范围结构化产物近似，随核增 PC-04「适用范围」维供给）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 应用侧反馈功能上线+回流 | 应用工程 | 本件（主） | dev `policy_public_opinion` 19 列直接承载 |
| 评分模型立项（C 口径起步） | 建模立项 | 本件 + POLCMP_022（评估体系） | 身份×渠道权重表 + 采纳校正 |
| 目标人群分母近似 | 依赖 PC-04 产物 | 本件（A 口径可选） | 政策适用范围结构化 |
| 稳评外部数据对接（可选） | 外部立项 | 本件 | R1/R2 口径，不在三源范围 |

档位后果：事件回流 + 口径立项 → **完全转换支持**（结构与算式双闭合，`policy_public_opinion` 直查直算）；仅事件回流（口径不立项）→ 部分支持（有事件可算参与量 B 口径，但「评估得分」语义仍缺）；仅口径立项（无事件）→ 仍完全不支持（算式无数据可作用）。推荐顺序：功能上线先行（周期长），口径立项并行。
