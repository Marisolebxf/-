## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/接入视窗/历史资源接入情况/**历史更新周期统计与分析·渠道平均周期列**（锚叶 1.1.1.1.4.4.2.4.2，SRS seq 361、excel_row 364）。UI 实际容器是 `AccessHistorySituation` 组件第二卡「历史更新周期统计与分析」TabPane（`:405-443`）：Table dataSource=updateCycleStats 三列——渠道（:410）/ **平均周期（:415，avgCycle 直读文本）** / 成功率（:417，031 件）；行展开渲染「近6月成功率趋势」（014/031 的时间维形态）。数据源是 mock `mockData.js:1451-1456` 的 `updateCycleStats.avgCycle`：5 渠道文本枚举。mock 注释自标「历史更新周期统计（需规 seq 361：更新频率/更新时间点/周期变化趋势）」——本表格整卡挂在 seq 361 叶下，avgCycle 列是「更新频率」的直接演绎，但 mock 用文本枚举而非数值，指标名（小时/天）提出了更强的数值化要求。另有同组件第一卡的历史归集记录表（seq 360 语境内 `updateCycle: '每周'`/`updateTime: '周五 22:00'` 字段——mock `historyAccessRecords`）与 mock `accessChannelStats` 无周期字段——周期语义的 UI 承载集中在 seq 361 这张表。

### 1.2 为什么需要本指标

更新周期回答「数据有多新鲜」：Seq 361 的功能定位是「帮助管理者把握资源维护的规律和实时性」——平均周期是新鲜度的直接读数（物联网采集实时=分钟级、人工录入每月=天级，五渠道的时效性分层一目了然）。数据消费侧的用途：下游报表/看板若依赖某渠道数据，其平均周期决定了「最多可能有多旧」的预期管理；SLA 视角下周期是 freshness 的承诺口径（R2：SLA 与检查频率挂钩——1 小时 SLA 配 30 分钟检查）。官方对应物：R1 汇交体系的「按时汇交」（汇交周期是计划口径）、R2/R3 数据工程 freshness SLA（staleness 阈值=周期的倍数）——两者都要求**周期先被度量**才能被承诺，本指标是度量的最小形态（平均值），seq 361 点名的「周期变化趋势」是其时间序列扩展（014 件的 trend Tag 形态）。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「渠道平均同步周期」指标名在三份需求真源 0 命中（附录 A.2）。最接近的 seq 361 主需求 :2660 述「通过时间序列分析技术，能够精准统计并展示各渠道、数据表的历史更新周期，包括更新频率、更新时间点及周期变化趋势」——「更新频率」「周期变化趋势」的概念在，但**数值口径无**：周期的量纲（小时？天？还是频率枚举？）、间隔的定义（相邻同步动作的间隔？数据内容更新的间隔？调度周期的标称值？）、「精准统计」的方法（实测间隔均值 vs 调度配置读取）均无定义。UI 的文本枚举（每日/实时）是「调度周期标称值」口径的演示，与指标名的「小时/天」实测口径不同物。

### 1.4 类似指标权威方法可行性分析概要

「同步/更新周期」的权威方法锚分三层。其一，数据工程 freshness 口径（R2/R3）：dbt source freshness 以「表最近一次加载时间 vs 阈值」度量新鲜度，检查频率≥2 倍最低 SLA（1 小时 SLA→30 分钟检查）；Bruin/Avo 的 staleness 模式同构——**周期的度量依托同步时刻序列**（max(event_time)/watermark）。其二，国家科学数据汇交（R1）：汇交计划规定「按时」的周期承诺（项目执行期内持续递交）——周期是**计划口径**（配置态）非实测口径。其三，UI 演示框架（5 渠道文本枚举——计划口径的展示形态）。方法族对照：

| 方法族 | 代表 | 周期定义 | 数据要求 | 与三源匹配 |
|---|---|---|---|---|
| freshness 实测口径 | R2/R3（dbt/Bruin/Avo） | 相邻同步间隔（实测） | 同步时刻序列 | **序列零承载** |
| 汇交计划口径 | R1（GB/T 39912） | 承诺周期（配置态） | 汇交计划台账 | **无计划面** |
| 耗时代理（错位） | dev es_sync cost_s | 单次同步耗时 | 水位表 | **量纲错位**（秒 vs 天） |
| 前端演示 | UI 每日/实时 | 文本枚举 | mock 常量 | 结构披露（不作源） |

结论：实测口径的序列零承载、计划口径的计划面零承载、耗时列量纲错位——三路皆断。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：两口径并列。**口径 A（实测间隔，指标名量纲）**：

$$\bar{T}_c = \frac{1}{N_c - 1}\sum_{i=2}^{N_c}\left(t_i^{(c)} - t_{i-1}^{(c)}\right),\quad t_1^{(c)} < \cdots < t_{N_c}^{(c)}$$

即渠道 c 的相邻同步时刻序列差分的均值（小时/天量纲）。**前提是同步时刻序列存在（N_c≥2），三源实测无**（§3.3）。**口径 B（调度标称，mock 量纲）**：渠道调度配置的周期枚举（每日/每周/实时）——计划口径，需调度配置面（xxl_job_info 的 cron_expression），实测 0 行空载。**量纲分叉披露**：指标名要 A（数值）、mock 给 B（文本），两口径不同物且都不可交付。

**降档/升档触发器（B10 模板）**：①xxl_job 投产+任务注册（trigger_time 序列 + cron_expression 配置双得）→ 口径 A 由 trigger_time 差分直算、口径 B 由 cron 直读，升**完全转换支持**；②渠道台账带逐次同步时刻 → 口径 A 直查升**完全直接支持**；③甲方裁定周期口径=内容更新间隔（非同步动作间隔）→ 转内容年份/更新时间面代理（DATAIN_001 的 update_time 批次分布形态），另评。维持现状 → 完全不支持。

`es_sync_watermark` 三组时间相关列逐一实测（14 模块，排除 1 行键名含 demo）：**begin_time/end_time 间隔**——14 模块全部 1-2 秒（`dev_es_sync_begin_end_span`，如 bid 1 秒/executive 2 秒/finance 2 秒），这是单次同步作业的起止差=**耗时**；**last_sync_cost_s**——1.02（min）至 1005.84（max）秒（`dev_es_sync_cost_s_min/max`），同为耗时（max 1005.84 秒≈16.8 分钟，是单次全量刷库的作业时长）；**last_sync_time**——范围 2026-08-11 15:41:39 至 2026-10-30 18:28:16（`dev_es_sync_last_sync_time_range`），但这是 15 模块**各一笔**的横截面（每模块一个最后同步时刻），不是同一模块的纵向序列——横截面的 min/max 差（80 天）是「不同模块的最后同步时点跨度」，与「同一渠道的同步间隔」无任何关系。三组列都与周期的「小时/天」量纲差 2-5 个数量级或语义不同物。**库内有「同步耗时」无「同步间隔」**——耗时是作业内部的钟表读数，间隔是两次作业之间的等待时长，前者在库后者不在。

## 四、数据缺失情况

### 4.1 同步时刻序列零承载（结构级，主因）

间隔计算的源面——同一渠道的同步时刻序列（≥2 个时间点）——三源零承载（§3.3）：es_sync 是单笔水位（结构上就不存序列）、xxl_job_log 空载（结构上支持序列但无数据）、台账不存在。**四缺失情形归属「表不存在 + 表存在但 0 行」复合**：修复动作分两路——台账立项（带逐次时刻列）或 xxl_job 投产（trigger_time 天然是逐次时刻序列）。后者成本远低：调度器投产+数据同步任务注册后，trigger_time 差分即间隔，无需新建台账。

### 4.2 周期口径与量纲未定义（口径级）

三重口径分叉叠加：其一，**实测间隔 vs 调度标称**（指标名暗示实测，mock 演示标称）；其二，**数值 vs 枚举**（小时/天 vs 每日/实时）；其三，**同步动作间隔 vs 内容更新间隔**（同步成功但 0 新记录时，动作间隔与内容间隔脱钩——R2 的「Measuring the wrong thing」陷阱：监控表修改时间会漏掉「跑了但没新数据」的情形）。三重分叉都需甲方裁定，本件按指标名口径（实测/数值/动作间隔）作为主口径评估，其余登记为触发器③的口径迁移选项。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| xxl_job 投产+任务注册 | 运维动作（性价比最高） | 本件 + 014 + 031 + 018 | 触发器①：trigger_time 差分→周期、handle_code→成功率，一次投产四件闭合 |
| 渠道台账（带逐次时刻+渠道列） | 数据工程立项 | 同上 + DATAOV_002 + DATAIN_001/003 | 触发器②（族级并项） |
| 周期口径裁定（三重分叉） | 口径裁定 | 本件 | §4.2，随修复先行 |

档位后果：调度器投产 → **完全转换支持**（trigger_time 直算）；台账建成 → **完全直接支持**；现状 → 完全不支持。推荐顺序：口径裁定 → xxl_job 投产（性价比主线）→ 台账随族级立项。
