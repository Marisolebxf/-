## 一、需求定义概述

### 1.1 所属功能模块

### 1.2 为什么需要本指标

累计调用次数是**数据资产活跃度的核心计价面**：哪些供应方的数据被用得最多、哪些数据产品是热点、哪个业务类型消费最旺——这三个维度共同回答「平台的数据资产在为谁服务」。与主题 Tab 的 DATAAPP_001/002（主题被调用）相比，供应方 Tab 把视角从「数据主题」切到「数据来源」：主题是消费视角的切面，供应方是供给视角的切面——同一份调用日志的两种投影。需求把本卡放在供应方 Tab 的量化核心位（第三卡多维可视化是它的图形化，本卡是可筛选可下钻的数值版），说明甲方要的是**经营分析台**而非单纯报表：筛选联动+命中计数+条表双呈现是自助式 BI 的典型交互。数据侧因此要求最高：不只日志，还要供应方维的登记与归集。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**seq 389 只给了一句功能描述（「基于实时调用日志和历史行为数据，自动统计每个供应方的数据累计被调用次数，支持按时间区段、业务类型、数据产品等多维度切换」），三类口径全缺：其一，「累计」的窗口语义（开窗至今滚动累计？还是可切时间区段的段内累计？UI 筛选器暗示后者但需求未言明）；其二，「业务类型」的归属口径（调用发生时带业务类型标签？还是按数据产品静态归类？mock 里每行都有 businessType 静态值）；其三，「数据产品」与主题/数据集的对应关系（供应方 Tab 的数据产品与主题 Tab 的主题是否同物异名？）。核增需求与算法库 0 命中（附录 A.2）。UI 28 行 mock 是前端演示约定，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

## 四、数据缺失情况

### 4.1 日志+登记+聚合三缺（结构级，判定性缺口）

累计统计的依赖链是「行级日志 → 供应方归集 → 月粒度聚合」三层，三源在第一层就断了（调用词族 0 命中），但即便第一层补齐，第二、三层也缺：供应方×数据产品登记面（维度骨架）与月粒度聚合任务（时间区段切换的载体）在三源均无现成承载。与主题 Tab（001/002）相比，本件把缺口从「日志单缺」细化为「日志+登记+聚合」复合链——这也是供应方 Tab 的经营分析定位决定的：筛选联动要求维度骨架先行，命中计数要求明细可数。**四缺失情形归属「表不存在」**：修复动作是调用日志工程（族级共用）+ 供应方×数据产品登记面 + 月聚合任务。

### 4.2 累计窗口口径未裁（口径级）

「累计」存在双解：滚动累计（开窗至今总数，随时间只增不减）或段内累计（随时间区段筛选重算——UI 的 Segmented 月标签筛选器暗示此解，但 mock 的 supplierCallPeriods 只有 5 个月标签，「all」选项才是全期）。正式版须先裁口径——若选段内累计，聚合表需按月分桶预聚合；若选滚动累计，另需「截至某月」的累计快照列。此口径缺口在日志建成后仍存在，建议随登记面一并裁定。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 调用日志接入（含供应方/业务类型/产品标识） | 监控工程立项（族级） | 本件 + DATAAPP 族全部 + seq 390/393/397 | 触发器① |
| 供应方×数据产品登记面 | 数据工程（轻量先行） | 本件 + seq 386/388（归集叶） | 静态字典表可先行锁值域 |
| 月粒度聚合任务 | 数据工程 | 本件 + seq 390（趋势叶） | 预聚合月桶 |
| 累计窗口口径裁定（滚动 or 段内） | 口径裁定 | 本件 | 随登记面一并裁 |
| UI 暂无数据态 | 展示规范 | 本件 | mock 28 行建议替换 |

档位后果：三件齐备 → **完全直接支持**；登记先行+日志后补 → 分步升档；现状 → 完全不支持。推荐顺序：登记面轻量先行 → 调用日志族级并项 → 聚合任务随建。
