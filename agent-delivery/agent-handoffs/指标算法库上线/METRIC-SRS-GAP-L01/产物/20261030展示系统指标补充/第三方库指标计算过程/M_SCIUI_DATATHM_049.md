## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/应用视窗·需求方调用数据详情（SRS L5 段，seq 392-395：名称归集/累计调用/行为分布/多维检索）。UI 实际挂载（派单 mount 行 233，实查确认）：`ApplicationWindow.jsx:233` demanderColumns `{ title: '活跃天数', dataIndex: 'activeDays', key: 'activeDays', align: 'center' }`——纯数值列（无边框 Tag，与活跃度 Progress 列 :235 相邻）。mock 语义源 `mockData.js:978-985` demanderUsageStats 八行：`{ name, calls, activeDays, avgDaily, department, businessType, projectTeam }`。mock 结构披露：activeDays（天）与 avgDaily（次/日，=calls/activeDays 的近似——9143≈256000/28）双量纲并列（B9）；紧邻 :235 的活跃度列按 `Math.round(r.activeDays / 30 * 100)` 折算——前端以 30 天为月基（050 件分析对象）。

### 1.2 为什么需要本指标

活跃天数是需求方黏性的**去噪频度读数**：与累计调用次数（seq 393）相比，活跃天数剔除单日爆量（一天调 10 万次与调 1 次同为 1 天）——刻画「多少天在用」而非「用了多少」，是黏性/依赖度的标准代理。典型用途：重点用户识别（月活≥20 天的部门纳入重点保障）、僵尸账户清理（连续 3 个月 0 天）。权威对应物：DAU/MAU 用户活跃分析（站点分析标准框架——月活跃天数=MAU 的用户侧细分）；API 网关的 per-consumer 日活统计（Kong/APISIX consumer 统计）；行为分析的 session 去重天数。

### 1.3 需求文档是否给出定义方法

**指标名级三份真源 0 命中。**「活跃天数」仅为 mock 表列题名。最近功能叶：seq 393「通过调用日志分析技术，全面统计每个需求方的数据资源累计调用次数」（累计口径——本件是活跃天数口径，不同量）与 seq 394「直观展示各需求方在不同时间段的数据调用分布状况」（分布语义近邻——活跃天数可视为日粒度分布的非零天数）。月窗定义（自然月？滚动 30 天？）无——UI 的 /30 折算暗示 30 天基但非定义。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「主体活跃天数」的权威方法锚分三层。其一，站点分析（R2，GA4/友盟）：月活跃天数=user×月窗内 DISTINCT session 日期数——DAU/MAU 框架的用户黏性细分，方法最成熟；其二，API 网关（R1，Kong/APISIX）：per-consumer 请求日志按日去重——网关 consumer 即需求方，与「数据资源调用」语境最贴合；其三，数据库审计（R3，MySQL audit log/MariaDB Audit Plugin）：user×connection×timestamp——DB 侧审计形态（sys_log 即此类）。方法族对照：

| 方法族 | 代表 | 原料 | 与三源匹配 |
|---|---|---|---|
| 站点分析 | R2（GA4） | session 日志 | 无 session 面 |
| API 网关 per-consumer | R1（Kong） | 请求日志（consumer 维度） | **无业务请求日志**（sys_log=管理 OAuth） |
| DB 审计 | R3（audit log） | user×connection | sys_log 结构近似但语义排除 |
| 前端演示 | UI mock | 八需求方常量 | 20-28 天（不作源） |

结论：三层方法原料（业务请求/session/审计日志）中，前两层零承载、第三层（sys_log）结构在但语义双排除。完整版见附录 C。

## 四、数据缺失情况

### 4.1 业务调用日志零承载（结构级，调用族五件同根）

正式口径原料（需求方×时间戳×资源）三源全无（041 复用排除）；sys_log 语义双排除（§3.2）。**四缺失情形归属「表不存在」**：修复动作是网关侧调用日志落地（表结构可径直参考 sys_log：主体标识+时间戳+资源 URI+方法）——与 041/050/052/053 共用触发器（调用族五件一次全升，本批第二大同根家族）。

### 4.2 月窗与「活跃」判据缺位（口径级）

月窗（自然月 vs 滚动 30 天）与活跃判据（≥1 次调用即活跃？≥1 次成功调用？token 刷新算不算？——sys_log 教训直指此点）双重缺位。建议裁定：自然月闭窗+「≥1 次成功业务调用」（HTTP 2xx 且资源 URI 前缀）+token/健康检查路径白名单排除——否则网关落地后仍会把呼吸流量计成活跃。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 网关调用日志落地（含需求方主体） | 数据工程 | 本件 + 041/050/052/053 | 触发器①（调用族五件共用） |
| 活跃判据+月窗裁定（成功调用+呼吸排除） | 口径裁定 | 本件 + 050 | 一纸文件（sys_log 教训入条款） |
| 列暂无数据态 | 展示规范 | 本件 | mock 20-28 替换；admin 9 天参考位标签 |

档位后果：网关日志+裁定 → **完全直接支持**；应用侧埋点 → **完全转换支持**；现状 → 完全不支持。推荐：裁定即期（含呼吸排除条款），网关日志随调用族主线。
