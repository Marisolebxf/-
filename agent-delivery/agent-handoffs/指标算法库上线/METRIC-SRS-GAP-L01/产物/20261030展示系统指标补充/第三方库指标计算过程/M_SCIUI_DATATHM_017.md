## 摘要

「问题总数」是接入视窗·问题资源情况（需求明列功能族 seq 364-367）「动态历史趋势可视化」卡的总量序列——UI mock 给 5 个月逐月值（1 月 18 / 2 月 22 / 3 月 25 / 4 月 20 / 5 月 23）与「已解决」对照线；同区列表态另有 8 条问题明细（完整性异常/时效性延迟/格式不兼容等，含 pending/processing/resolved 状态流转）。**语境核确认这是数据质量问题面**（派单预警处置）：趋势卡统计的是接入过程的数据质量异常总量。数据侧核心是问题登记面（资源×异常×时间）存在与否：dev 唯一词族命中是深圳产业链诊断面（0 行，语义排除）、gkx 零命中、久新 53 张 problem 表全是「基础研究问题清单」域（研究命题≠数据质量问题，抽样核对列结构后语义排除）——需求 :2673 自点名的「数据质量监测+错误日志采集」前提三源未建。判**完全不支持**。另披露 mock 自身不自洽（列表 8 条 vs 趋势月 18-25 条，两处 mock 未对齐）。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**需求功能族派生读数**（seq 364-367 明列功能；「问题总数」字面仅见于 UI legend）。
- 复现状态：脚本已跑通；三源词族排除 + 两处语义排除核对 + mock 不自洽披露全落产物。
- 档位结论：**完全不支持**（数据质量问题登记面三源零承载，工程前提 :2673 自宣未建）。
- 关键事实：久新 53 张 `ads_research_problem_*` 是本件最大的语义陷阱——「problem」字面高度相似，但域义是「基础研究问题清单」（科研命题管理），与「数据接入质量异常」不同源不同义；不核对列结构直接按表名取数会得出「问题总数 342+」的错误读数。
- 升档路径：数据质量稽核流水面立项（检测规则×资源×异常事件，R1 六维规则库）→ 完全直接支持。

### 1.2 为什么需要本指标

问题资源情况（seq 364-367）的管理命题是「**接入的数据干不干净**」：问题总数（含月度趋势）回答异常量的规模与走向，已解决对照线回答治理消化速度，分级饼回答处置优先级，列表态支撑复现与整改——四件套合起来是数据质量运营的例会看板。需求 :2673 把问题资源的价值定位为「为资源归集质量保障和数据接入流程优化提供强有力技术支撑」——问题总数是这张质量看板的**总量基线**：没有总量，解决率（已解决/总数）无从计算，分级占比也无分母。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「问题总数」字面三份真源 0 命中（仅见于 UI legend，附录 A.2）。需求明列的是功能族（SRS 接入视窗.md seq 364-367 / 主需求 :2675-2691）：seq 364「通过智能异常检测与质量监控算法，自动识别所有数据接入过程中出现的问题资源，并以列表的形式集中展示，支持按时间、类型或渠道进行过滤和排序」；:2673（L5 总述）「通过数据质量监测和错误日志采集，自动识别并汇总问题资源列表，包括数据缺失、格式错误、内容冲突等各类异常数据」——**需求自己点名了工程前提（数据质量监测+错误日志采集）**。计数口径无定义：全量登记条数还是未解决存量？月度序列按发现时间还是修复时间？mock 的双线设计暗示「总数/已解决」平行口径但无算式。核增需求与算法库 0 命中。

### 1.4 类似指标权威方法可行性分析概要

「问题总数」的权威方法锚分三层。其一，国标数据质量评价（R1 GB/T 36344-2018）：规范性/完整性/准确性/一致性/时效性/可访问性六维稽核——「问题」的制度化定义是**六维规则的违例事件**（如完整性维度的数据记录完整性不满足、准确性维度的脏数据出现率超标），问题总数=违例事件计数，按维度分类即问题类型。其二，数据治理规范（R2 GB/T 34960.5-2018）：数据治理过程含监控与评价——问题管理闭环是「检测→登记→分级→处置→复核」，登记面（问题库）是闭环的数据载体。其三，汇交质量审核（R3 GB/T 39912-2021）：科学数据管理方的汇交审核（4.2 真实可靠）——审核不通过项的登记台账是问题总数的另一制度形态（按提交方×数据集）。方法族对照：

| 方法族 | 「问题」定义 | 数据要求 | 与三源匹配 |
|---|---|---|---|
| 六维违例事件（R1） | 稽核规则违例 | 规则库+稽核流水 | **无（规则库未建）** |
| 治理问题库（R2） | 检测-处置闭环登记 | 问题登记面 | **无** |
| 汇交审核台账（R3） | 审核不通过项 | 审核流水 | **无** |
| 前端演示 | mock 常量 | mockData.js | 结构披露（不作源） |

结论：三条权威路径的原料（规则库/问题登记面/审核台账）三源均无承载——与 DATATHM_020 同属「工程前提自宣未建」型缺口。完整版见附录 C。

## 四、数据缺失情况

### 4.1 数据质量问题登记面零承载（结构级，判定性缺口）

「资源×异常类型×发现时间×级别×状态」的问题登记面三源零承载（§3.3）——与 DATATHM_020（API 耗时日志）同型：**监控工程缺位**而非数据量不足。需求 :2673 把「数据质量监测和错误日志采集」写进功能描述（工程前提自宣），但三源无对应承载表——接入过程的数据异常从未被规则化检测与登记过。**四缺失情形归属「表不存在」**：修复动作是质量稽核流水面立项（规则库+跑批+事件登记三件套）；mock 的六类问题类型可直接以 R1 六维为底稿映射，降低规则库启动成本。本缺口与可靠性族（007/008）共享规则库基建：一次登记 R1 六维规则，违例计数（本件）与达标占比（007/008）同源产出。

### 4.2 久新语义陷阱披露（方法级，防误用）

久新 53 张 `ads_research_problem_*` 是本族最大的语义陷阱：「problem」字面与「数据质量问题」高度相似，但域义是「基础研究问题清单」（科研命题管理——问题识别/分类/演化/预测，对应智库系统功能族）。若按表名取数（如 SUM 各表行数当「问题总数」）会得出带研究语义的错误读数（仅 `ads_research_outcome_problem` 一张即 342 行）。本件在 §3.3 留列结构核对证据并在 notes 写死排除理由，后续族内件引用久新 problem 词族时以本件为先例。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 质量稽核流水面（规则库+跑批+事件登记） | 数据工程立项 | 本件 + 007/008（规则库共用） | 触发器①（三件共享） |
| R1 六维规则登记 | 口径裁定 | 本件族 | mock 六类型→国标六维映射底稿 |
| 计数口径裁定（全量 vs 未解决存量） | 口径裁定 | 本件 | mock 双线暗示平行口径，须一纸裁定 |
| UI 暂无数据态 | 展示规范 | 本件 UI | mock 18-25 月序列建议替换为「暂无数据」 |

档位后果：稽核流水面 → **完全直接支持**；自建规则跑批 → **完全转换支持**；现状 → 完全不支持。推荐顺序：规则登记（即期一纸，mock 类型映射降本）→ 跑批流水立项（族级主线，三件受益）。
