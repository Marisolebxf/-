## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/接入视窗/资源来源分析和详情（1.1.1.1.4.4.2.2；SRS seq 351-355）——本件是**UI 派生读数**（指标名「平台归集数据量」三份真源 0 命中），挂靠该组件的总量位。UI 实际挂载：`AccessSourceAnalysisDetail.jsx` 渠道归集数据量统计卡（:339-405）内三处读数——渠道表格「归集数据量」列（:230，`dataIndex: 'volume'`，降序可排、右对齐整数呈现）、概览 Statistic「归集总量」（:367，`channels.reduce((s,c)=>s+c.volume,0)`）/「资源总数」（:373，count 求和）、导出字段「归集数据量」（:492）；mock 源 `mockData.js:100-106` `accessSourceAnalysis.channels`（科研院所 12,580/企业 8,920/第三方平台 6,240/高等院校 4,120/政府部门 1,810 的 volume/count/share 三列）。mock 结构披露：表格列与 Statistic 同源求和（合计 33,670/1,256，脚本算出），演示值不作数据证据（B10）。

### 1.2 为什么需要本指标

本件是「谁在给平台供数」叙事的**总量锚**：seq 351 要求「全面了解不同渠道的数据贡献度」——贡献度的分母就是平台归集总量（「平台攒了多少数据」）；表格 volume 列给出分渠道的量、Statistic 给出全平台合计，构成「总-分」结构的总层。官方对应物是国家科学数据中心的分中心汇交量序列（R1/R2：项目汇交 4,325 个/6.5PB——总量+分主体双口径并列）——「总量（记录条数）+渠道分列」正是汇交统计的标准形态，本件是该形态在接入视窗的落地读数。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「平台归集数据量」指标名三份真源 0 命中（附录 A.2）。直挂语义叶 seq 351 功能句：「自动统计并展示各渠道（如科研院所、企业、第三方平台）归集的数据量，支持按时间、业务类型、来源类别进行细分」——「数据量」的度量单位（记录数？体量？资源数？）无定义（组清单 screen 语「按记录条数计」是拆件侧口径，非需求原文）；渠道 taxonomy 的举例（科研院所/企业/第三方平台）与 mock channels 五分类（+高等院校/政府部门）一致，但库内轴（data_source 血缘）与之完全不同构。核增需求与算法库 0 命中。

### 1.4 类似指标权威方法可行性分析概要

「平台归集总量+渠道分列」的权威方法锚分三层。其一，汇交统计制（R1，GB/T 39912-2021）：分主体汇交量（数据集×体量）登记——总量的制度化形态是台账汇总。其二，分中心体量序列（R2，国家基础学科中心）：总量（6.5PB）+主体分列（项目 4,325 个）双口径并列呈现。其三，库内代理路径：无台账时以「存量行数+来源列分组」近似——存量可数、分组轴有值但语义待裁。方法族对照：

| 方法族 | 代表 | 度量对象 | 数据要求 | 与三源匹配 |
|---|---|---|---|---|
| 汇交台账口径 | R1（GB/T 39912） | 归集动作量×主体 | 汇交台账 | **无台账** |
| 总量+主体分列 | R2（国家中心序列） | 存量体量×主体 | 体量+主体标签 | 体量可数、主体轴语义分叉 |
| 存量+血缘分组 | 本件交付路径 | 行数+data_source | 行数面+来源列 | **三源双在**（taxonomy 待裁） |
| 前端演示 | UI channels/Statistic | mock 计数 | mock 常量 | 结构披露（不作源） |

结论：台账口径零承载；存量+dev 血缘分组即期可交付（语义披露随行）。完整版见附录 C。

## 四、数据缺失情况

### 4.1 归集台账零承载（结构级，主因）

「渠道×资源×量×时间」登记面三源零承载（§3.3）——本组件三件套（027/028/033）+ 需求叶件 003 + 总量族 002/039/030 共享的族级缺口。**四缺失情形归属「表不存在」**：修复动作是归集台账立项（与 DATAOV_002/DATAIN_001/002/003 族触发器共用）——台账建成后 027 的总量、028 的合计、033 的明细、003 的渠道分布同时直查，一次建设七件受益（含 DATAOV_002）。

### 4.2 渠道 taxonomy 分叉与跨库治理分裂（口径级，次因）

两个口径缺口：其一，**taxonomy 分叉**——dev data_source 血缘值 vs 需求「数据源单位（政务部门/事业单位）」vs mock 五分类（科研院所/企业/第三方平台/高等院校/政府部门）三套不同构（与 003/018/031 共享分叉，族级裁定一次生效）；其二，**跨库治理分裂**——dev 轴有值、gkx 轴空载、久新无轴：渠道字典须三源同权立项，单库治理会造成口径不齐。**四缺失情形归属「口径未裁定+列值治理」（分立登记）**：taxonomy 裁定是一纸文件（快），gkx 标签回填是数据治理（中），dev 血缘值重标为正式渠道轴是映射工程（慢）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 归集台账立项（渠道×资源×量×时间） | 数据工程立项（族级） | 本件 + 028/033/003/002/039/030 | 触发器①（一次建设多件受益） |
| 渠道 taxonomy 裁定（三套口径选一或映射） | 口径裁定（族级） | 本件 + 003/018/031/033 | 与 003 共享分叉，先行 |
| data_source 血缘轴升格/重标 | 数据治理 | 本件分组维 | dev 侧工程面已在（152 列） |
| gkx table_data_source 回填 | 数据治理 | 本件 + 003 | 跨库对齐（轻路径，003 触发器共用） |
| mock 形态披露 | 前端工程 | 本件 UI | 演示五分类与库内轴不同构披露 |

档位后果：台账+字典 → **完全直接支持**；taxonomy 裁定+存量口径确认 → **完全转换支持**；现状 → 部分支持。推荐顺序：taxonomy 裁定先行（一纸文件）→ gkx 回填（轻治理）→ 台账（族级主线）。
