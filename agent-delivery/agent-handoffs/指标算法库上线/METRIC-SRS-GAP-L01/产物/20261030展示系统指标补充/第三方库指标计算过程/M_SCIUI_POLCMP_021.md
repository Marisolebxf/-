## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技政策跟踪/**政策分析评价·企业画像呈现**（主需求 1.1.1.1.4.2.2「呈现政策、企业、人才的具体画像」）。UI 实际容器是政策分析页（`PolicyAnalysis.jsx`）的三画像卡区（`analysis/PortraitTrio.jsx:38` 起）：三张并排卡片分别画政策/企业/人才，数据来自 `policyData.js:2160-2212` `policyPortraitSummaries` 常量。本件挂载企业卡（id=enterprise，`kpi: 匹配满意度 82 分`）detail.metrics[3]：`{ label: '复购/续享率', value: '54%' }`（`:2205-2209`）。卡片其余三个 metric（惠及企业数 1.28 万家/申报通过率 63%/平均到账周期 46 天）与本件同池，全部为页内 mock 演示值——整条链路无 API 调用。

### 1.2 为什么需要本指标

企业画像的业务问题是「政策扶持的粘性」：惠及企业数（POLCMP_002 语义）量的是首次触达面，复购续享率量的是**再次享受**——一个企业享受过研发资助后，会不会再申报加计扣除、再续享稳岗补贴？高复购说明政策体系形成了持续服务闭环（企业知道来、来了能办、办完还来），低复购说明政策是一次性脉冲（发完钱关系就断）。这个读数在多维政策对比语境下是政策质量的差异化维度：两政策惠及面相近时，续享率高的政策粘性强。它的电商对应物是复购率（再次购买客户占比，R1/R2/R3 通用口径），政务对应物是免申即享的「多次免申即享」与政策到期续办的通过记录。UI 把它放进企业画像（而非政策 KPI 位），说明前端作者把它理解为企业维度的行为特征。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义**：

$$R_{repeat} = \frac{|\{e : e \in E, c_e \ge 2\}|}{|\{e : e \in E\}|},\quad E = \{(企业_i, 政策_j, 享受期次_k, 时间_t)\}$$

即客户口径复购率迁移：分子=统计期内享受期次 ≥2 的企业数，分母=同期享受过（≥1 次）的企业数（R1 口径的政务版）。两个口径分歧点待裁定：**A 统计期**——年内/跨年滚动 24 个月/政策周期（电商快消用月、耐用品用年，政务兑现频率低、建议按年或政策周期）；**B 「再次」的粒度**——同一政策再享受（如稳岗补贴连年续享）还是任一政策再享受（跨政策复用）——前者量单政策粘性、后者量政策体系粘性，UI 文案「复购/续享」两词并置暗示后者。两口径的分子分母数据同源（兑现台账含期次字段），当前三源零承载。

**降档/升档触发器**：接入政务兑现台账（免申即享兑付记录/财政拨付流水/企事速办工单，建 `policy_enterprise_enjoy` 关系表含享受期次字段）→ 分子分母直查可算，升**完全转换支持**（口径 A/B 由甲方裁定后一条 SQL 出数）；与 POLCMP_001/002 共用同一接入工程。降档无空间（已到底档）。

### 2.1 方法选择（文献依据）

若台账面闭合，方法选**客户口径复购率（R1 政务迁移版）**：分子=期内享受期次 ≥2 企业数，分母=期内享受过企业数。选择理由：其一，客户口径比交易口径（R3/R4 变体）语义更强——回答「多少企业回来了」而非「多少笔是重复的」，与企业画像的主体视角一致；其二，R2 的 BI 实现范式（COUNTD 客户×HAVING 次数≥2）可直接落 SQL：`COUNT(DISTINCT enterprise_id HAVING COUNT(enjoy_period) >= 2) / COUNT(DISTINCT enterprise_id)`；其三，政务侧免申即享的多次兑付记录天然携带期次字段（R5 免申即享口径），迁移无障碍。但该方法当前**不可执行**——台账无源。

### 2.2 gkx 台账面排除（表级+列级双扫）

gkx 280 表扫 enjoy/repeat/renew/repurchase/again/benefit 六词族——0 命中（`gkx_enjoy_repeat_like_tables=[]`）。列级复核：`dwd_policy_base` SHOW COLUMNS 全 33 列（`gkx_policy_col_count=33`）逐一核对，无 enjoy/enterprise/org/company/repeat/renew/benefit 类列（`gkx_policy_enjoy_like_cols=[]`）——政策底表是政策文件库（标题/正文/发文字号/主题词），不是兑现台账。这一层排除很重要：它证明 gkx 连「政策×企业」的关系维都不承载，更无「企业×享受期次」的事件维。

## 四、数据缺失情况

### 4.1 兑现台账零承载（结构级，主因）

分子分母同源于『企业×政策×享受期』兑现台账。兑现事件的产生地是政务兑现系统（免申即享平台兑付记录/财政拨付流水/企事速办工单），须经回流入库后才能计数。当前链路断在源头——兑现系统数据未接入数据仓（dev 连图谱表都是 0 行，更无事件流水）。修复路径唯一且清晰：兑现台账接入 + `policy_enterprise_enjoy` 关系表建模（企业×政策×享受期次×金额×时间五元组）。**族级共用**：这一缺口与 POLCMP_001（兑现/应享分子分母）、POLCMP_002（惠及企业增长）完全同源——三件是同一块台账的三个读数，一个接入工程同时闭合三件，本件只额外要求台账携带**期次**字段（001 要求状态、002 要求首末期）。

### 4.2 口径分歧未裁（次因，随主因解）

口径 A（统计期：年内/政策周期/滚动 24 月）与口径 B（「再次」粒度：同政策再享/跨政策复用）两个分歧点在台账闭合前无法实算、闭合后一条 SQL 即可切换——口径成本为零，全部押在数据接入上。这与其他「口径缺+数据缺」双缺件（如 POLCMP_008 参与度评分）不同：本件的口径是低悬果实，不构成独立降档因——判档主因纯粹是数据面（B10 保守交付：两口径并列写死，待甲方裁定）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 兑现台账接入工程 | 数据接入 | **本件 + 001 + 002（三件同族）** | 免申即享兑付/拨付流水/速办工单三源择一或并接 |
| `policy_enterprise_enjoy` 建表 | 建模立项 | 同上 | 五元组结构（企业×政策×期次×金额×时间） |
| 口径 A/B 裁定 | 甲方裁定 | 本件 | 统计期与「再次」粒度（闭合后零成本切换） |

档位后果：台账接入 + 建表 → **完全转换支持**（客户口径复购率直查）；仅接入无期次字段（只有首次享受记录）→ 分子恒 0，退化为 POLCMP_002 语义（仍不可算本件）——接入时必须确认期次字段。推荐顺序：与 001/002 合并立项（同一工程摊薄成本），期次字段写入接入规范。
