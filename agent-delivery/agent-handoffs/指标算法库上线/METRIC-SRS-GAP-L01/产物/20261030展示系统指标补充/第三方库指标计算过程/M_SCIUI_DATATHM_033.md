### 1.2 为什么需要本指标

seq 351 的细分要求「支持按时间、业务类型、来源类别进行细分」——业务类型维回答「**归的数据是干什么用的**」：基础研究 vs 产业应用 vs 开源汇聚 vs 政务统计的归集量结构，直接服务资源配置叙事（研究型数据与产业型数据的占比）；与渠道维交叉（堆叠）后进一步回答「哪类渠道供哪类数据」（mock 形态：科研院所主导基础研究 5,200、企业主导产业应用 4,200、第三方平台主导开源汇聚 2,800）。官方对应物是 R2 分主体×分类型的汇交量统计（项目/数据集/体量按主体与类型双列）——交叉细分是资源统计的标准深化形态。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「分组归集数据量」指标名三份真源 0 命中（附录 A.2）。细分维语义叶 seq 351：「支持按时间、业务类型、来源类别进行细分」——「业务类型」是举例式细分维：分几型、型名（mock 四型是演示约定）、量纲（归集量按记录数还是资源数）均无定义；「按质量等级」分组维同样举例式（seq 354「根据来源渠道、数据种类、时间、质量等多种维度」）。核增需求与算法库 0 命中。

### 1.4 类似指标权威方法可行性分析概要

「交叉细分×归集量」的权威方法锚分三层。其一，汇交统计的双维分列（R1，GB/T 39912）：汇交量按主体×数据类型双维登记——交叉的前提是**明细行带双维标签**。其二，分主体类型统计（R2，国家中心序列）：体量按主体与资源类型双列——编目在册方可交叉。其三，库内代理路径：无编目时交叉不可算，单维（血缘）分组可近似。方法族对照：

| 方法族 | 代表 | 交叉条件 | 数据要求 | 与三源匹配 |

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

$$V_{b,c} = \sum_{r \in R,\, \text{biz}(r)=b,\, \text{ch}(r)=c} \text{volume}(r),\quad b \in \text{业务类型},\ c \in \text{渠道}$$

## 二、计算过程

### 2.1 方法选择（文献依据）

### 2.2 mock 交叉矩阵复算（行列恒等+内部对账披露）

## 四、数据缺失情况

### 4.1 交叉两轴零承载（结构级，主因）

业务类型轴（独立扫 0 命中）+质量等级轴（3 处全偏移）+正式渠道轴（taxonomy 分叉）——交叉明细的三条轴无一可直接用（§3.3）。**四缺失情形归属「表不存在」**：修复动作是双字典立项（业务类型字典+质量档位表，与渠道字典并项）——字典建成后挂在明细登记面（028 第一性缺口）上，交叉格元即可直查。这是三件套中依赖最深的修复链：明细面（028 共同根）→ 三字典（027/003 共享渠道字典+本件特有业务类型字典）→ 交叉视图。

### 4.2 演示值内部不对账（演示层，披露项）

mock 的 channels 表与 byBizType 矩阵两套演示数对不上（21,100 vs 27,740，差 6,640）且柱图渠道覆盖不全（3/5）——演示面之间无单一真源。此缺口不影响库内判定（演示值不作数据证据），但影响 UI 正式化的验收基线：前端若按 mock 形态验收，会要求「卡片视图与交叉视图数值一致」——正式版以台账单一真源自动满足；缓建台账时两视图须声明口径差异（避免验收争议）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 业务类型字典+质量档位表立项 | 数据治理 | 本件特异性 | 交叉第一轴（四型或按裁定的型谱） |
| 明细登记面+渠道字典 | 数据工程（族级） | 本件 + 027/028/003 | 三件共同根（028 触发器①并项） |
| 血缘单维裁定（退化交付） | 口径裁定 | 本件即期 | 触发器②（标签「库内血缘分组」） |
| mock 两视图口径差异声明 | 前端工程 | 本件 UI | 21,100 vs 27,740 差异披露（台账建成前） |

档位后果：明细面+三字典 → **完全直接支持**；血缘单维裁定 → **完全转换支持**；现状 → 部分支持。推荐顺序：血缘单维裁定即期（零成本）→ 渠道字典（027/003 共享先行）→ 业务类型字典+明细面（本件特异性主线）。
