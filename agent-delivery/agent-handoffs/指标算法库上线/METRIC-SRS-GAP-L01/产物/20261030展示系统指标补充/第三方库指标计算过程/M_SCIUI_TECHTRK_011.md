### 1.2 为什么需要本指标

成果数量是七库体系的「产出存量」读数：规划汇报里「家底有多少」的第一问。它与 010 件（转化效率）构成存量-流量对，与 012 件（推送频率）构成库存-分发对——多维度指标体系卡的叙事完整性依赖这个数作为基座。需求原文（seq 179）把成果库列在七库之中，意味着它是顶层大屏的常驻读数，不是下钻页的细节指标。

数据侧本件的调查重心不是「能不能算」（四套底数都能），而是「算哪个」：官方统计语境的「科技成果」有明确分类（基础理论/应用技术/软科学三类，R2 登记制度），而库内四套底数各对应不同语义——项目产出（科研经费视角的结题产出）、论文/专利（文献计量视角）、技术节点归集（久新簇视角）。四口径数值差三个数量级（6.5 万 vs 294 万），并置展示必须先裁定主口径。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「成果数量」指标名三份说明书未出现。最接近的需求原文是 SRS《科技发展规划.md》seq 179 多维度指标体系展示叶：「在大屏上展示技术发展、产业数据库、机构库、课题库、成果库、统计库、人才库等指标体系，用户可自定义展示内容和布局，支持指标间的联动分析。」——「成果库」是库名不是指标定义，成果统计什么、怎么算，一个字没有。主需求文档同段复述。

### 1.4 类似指标权威方法可行性分析概要

「科技成果」的官方统计口径：国家科技成果登记统计调查制度（国家统计局批准，R2）按成果类别分基础理论/应用技术/软科学三类，以**登记**为口径（应用技术成果需鉴定/验收/行业准入/评估或获知识产权；基础理论需验收/评审/结题评价），年报制；《科技成果登记办法》（R3）规定登记材料（专利证书/论文/专著/评价证明）。方法族对照：

## 二、计算过程

### 2.1 装载与规模校验

gkx 侧（经 `_gkxdb.py`）：`dwd_zh_project_output` 20,133 行（facts.gkx_zh_project_output_rows）对应 `dwd_zh_project` 58,453 个中文项目（facts.gkx_zh_project_rows）——产出表覆盖 34.5% 的项目（其余项目无结题产出记录，是常态）；`dwd_en_project_output` 20,000 行对 `dwd_en_project` 20,000 个英文项目，覆盖率 100%（但英文表本身是 2 万行截断装载，见 §2.4）。久新侧：`ads_technology_profile` 19,430 节点（facts.jiuxin_tech_profile_nodes），与 009 件节点数同值（B11 跨件对账）。

### 2.2 口径 ①：项目产出合计

中文表分项合计（facts.gkx_zh_output_*）：total_outputs **80,944**，其中期刊论文 61,840 / 会议论文 7,985 / 专利 10,344 / 专著 775——四分项和 80,944 与 total_outputs 合计严格相等（内部一致性通过）。英文表（facts.gkx_en_output_*）：total_outputs **64,977**，其中仅 journal_articles 64,977 有值，patents/clinical_trials/reports/other 全空。两表相加 **145,921**（derived.gkx_zh_en_output_grand_total 和值；分子分母键登记为两表各自合计供对账）。**口径弱点**：英文表 coverage 截断（§2.4），145,921 是下界读数。

### 2.3 口径 ②③④：直查读数

论文 100,900 / 专利 2,939,895 直接复用共享快照（B11 不重复打库，快照键登记于 notes）；久新 profile 四指标列 SUM（facts.jiuxin_profile_paper_sum=108,479 / patent_sum=1,071,763 / institution_sum=2,528,802 / company_sum=99,821）——注意节点归集口径的论文数（108,479）小于 gkx 全量（100,900×N 倍），因为前者是「入选簇的种子论文去重计数」语义，两者**不可相加也不可直接比较**，产物 notes 已写死。

### 2.4 覆盖与质量核查

三个覆盖事实：其一，英文项目表 20,000 行整——疑似装载上限截断（与 dwd_news_base/dwd_policy_base 等同为 2 万行装载的表族特征一致），total_outputs=journal_articles 恒等说明英文产出仅回填了论文分项；其二，中文表获奖/报告列全空（awards_count 与 reports_count 非零行均 0，facts.gkx_zh_output_awards_nonzero_rows/reports_nonzero_rows）——UI 的「获奖成果 216」分项无承载；其三，`dwd_zh_journal` 有 award 列（列扫描命中）但属期刊获奖非成果获奖，语义排除。三个事实都指向同一条：**总量口径稳、细分口径缺**。

### 2.5 派生读数：产出密度

$\text{density} = 80{,}944 / 20{,}133 = 4.0205$ 项/项目（derived.gkx_zh_output_per_project）——同表分子分母（B3 同基），含义是「有产出记录的项目平均结题产出 4 项」。该读数可作 010 件效率叙事的辅助轴（产出密度×转化率=单位项目转化产出），也可作成果库卡的趋势分位参照。

### 2.6 稳健性与口径敏感性

## 四、数据缺失情况

### 4.1 获奖与标准分项缺失（细分级）

UI 成果库卡的「标准成果 438 / 获奖成果 216」两个分项位无数据承载（§3.3）。修复建议：获奖分项可走外部源（科技奖励名录/登记系统 R2 体系）；标准分项需标准数据库接入（三源无任何标准类表）。影响面：本件两个分项位 + 科技成果展示模块的获奖展示功能。

### 4.2 年度成果结构空置（时序级）

dev `org_achievement_year` 若灌数可直供「分年成果数」（与 010 件共依赖）；当前 0 行。替代路径：gkx 论文/专利主档的分年聚合（20 万采样协议）可即期补分年趋势，但口径是文献计量而非结题产出。影响面：本件分年路径 + 010 件时序面。

### 4.3 英文产出覆盖截断（覆盖级）

英文表 2 万行装载上限 + 仅期刊分项回填，口径 ① 的英文分量是下界。修复：确认上游是否有全量装载计划；若无，英文分量按披露下界使用。影响面：口径 ① 总量读数。
