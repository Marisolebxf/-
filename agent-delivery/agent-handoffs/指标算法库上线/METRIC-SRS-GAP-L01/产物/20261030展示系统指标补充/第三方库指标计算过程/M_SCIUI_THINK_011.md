## 摘要

「内容累计浏览量」在科技传播页有**双挂载点**：内容卡 meta 行的 `views` 直显（`TechCommunication.jsx:80`，EyeOutlined 图标）与内容详情抽屉基本信息段的「浏览量」行（`:125`，取 `detailTarget.data.views`）。mock 的 `communicationContents` 8 条内容各带 views 演示值（3,450-15,680）。需求侧 SRS 未列同名指标，上位叶是序号 600「内容数据接口服务」（详情数据接口支撑前端完整呈现）。三源探针（表名+列名词族双扫：dev 542 表 / gkx 280 表 / jiuxin 218 表现场实数）证实：浏览快照列结构存在（dev 3 处 + gkx 1 处）但承载行全 0/全 NULL；事件流水零承载；唯一有数的 `jimu_report.view_count`（66 行 SUM=749,666）为 BI 报表浏览语义错位。判**部分支持**：与 THINK_010 同族同判，但本件对数据形态要求更宽松（单批灌数即可出累计值）。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**UI 挂载件**（SRS 无同名；上位功能序号 600 覆盖）。
- 复现状态：薄壳已跑通；读数落 4 份共享快照 + 本件产物。
- 档位结论：**部分支持**（快照列结构在、承载 0 行；事件流水三源无）。
- 关键事实：dev 快照列 3 表全 0 行；gkx click_number 32 行全 NULL；jimu_report 66 行 749,666 语义错位。
- 升档路径：内容主档+浏览快照列灌数 → 完全转换支持；PV 事件流接入 → 完全直接支持。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技服务全景/科技传播/**内容卡瀑布流 + 详情抽屉**（SRS 1.1.1.1.4.7 域内交互面）。科技传播页中部是九宫分类导航 + 内容卡瀑布流（`filteredContents` 过滤渲染），每张内容卡 meta 行带发布日期/浏览量/点赞数三读数（`TechCommunication.jsx:79-81`：CalendarOutlined/EyeOutlined/LikeOutlined 三图标）；点击卡片弹出 `InsightDetailDrawer` 详情抽屉，基本信息段含「发布时间/浏览量/点赞数」+ 按类型扩展行（展览地点/主讲人/作者，`:118-131`）。累计浏览量在这里是**单条内容级的受欢读数**，与点赞数（THINK_012）构成内容质量的两个用户反馈面。

mock 数据源 `mockData.js:311-319` 的 `communicationContents` 8 条（展览/讲座/期刊/图书/视频/人物/讲座/文章）各带 `views`/`likes`。

### 1.2 为什么需要本指标

累计浏览量回答「这条内容总共被看了多少次」：它是单条内容触达的**存量读数**，与月浏览量（THINK_010，流量切片）构成时间维度互补，与点赞数构成质量维度互补（浏览-点赞比可看转化）。对管理者：排序热门内容、评估十类形态哪类更受欢迎；对用户：内容卡上的浏览数是点击决策的社会证明。它比月浏览量对数据形态的要求更低——只需要内容主档冗余一个累计列，不需要按月切分的事件。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「内容累计浏览量」指标名在三份需求说明书中未出现（检索记录见附录 A.2）；SRS《科技传播.md》序号 600「内容数据接口服务」要求详情数据接口「包括文本、图片、元数据」，浏览量是否属元数据、累计口径（是否去重、是否含多端）均未定义。

### 1.4 类似指标权威方法可行性分析概要

累计浏览量的权威口径即 GB/T 31524 的 **PV 累计**（R1）：累计浏览量 = 自内容发布起 PV 事件全量求和（不去重；若需 UV 累计须访客标识）。内容平台通用实践是**主档快照列**（CMS 冗余 views 列，由埋点系统异步回写）。方法族对照：

| 方法族 | 计数轴 | 数据要求 | 与本库匹配 |
|---|---|---|---|
| PV 事件累计求和 | 用户×内容×时间戳全量 | 浏览事件日志表 | **无（三源零承载）** |
| 主档快照列直读 | 内容主档 views 冗余列 | 内容表带浏览列 | **结构有**（dev 3 处 + gkx 1 处）**数据 0 行/NULL** |
| BI 报表浏览代理 | jimu_report.view_count | — | 有（66 行）但语义错位 |

结论：快照列形态在本库已预置，缺的是挂数的内容主档与回写机制。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

累计浏览量是简单直读/求和（无建模），方法选择落在**读数来源的裁定**：正式口径采用 GB/T 31524 的 PV 累计（R1），工程形态采用主档快照列直读（内容平台通用）。本库实测因事件流缺失，验证两条链：①「快照列存在性」——dev 3 处 + gkx 1 处列名逐一断言（`chain_news_columns` 含 `views`、`policy_latest_news_columns` 含 `view_count`、`app_article_columns` 含 `visit`）；②「累计求和计算链」——`jimu_report.view_count` 全表求和 749,666（66 行）证明求和链可跑通。结构与链路均验证通过，原料未灌。

## 四、数据缺失情况

### 4.1 浏览快照数据缺失（数据级，主因）

### 4.2 宿主主档缺口（随动缺口）

### 4.3 修复建议与影响面
