- 需求判定：**需求明列叶**（seq 376）本体端拆件——列表字段集与各字段口径无定义。
- 复现状态：脚本已跑通；三源词族排除 + 用户维独立缺位证据全落产物。
- 档位结论：**完全不支持**（主维台账零承载 + 扩展维用户/环比/登记轴全链缺位）。

### 1.2 为什么需要本指标

排行榜本体回答「**每项资产的应用全貌**」：位次（034）只给序，本体给排名依据（调用量）与画像字段（谁在用/增长如何/部署在哪/用了多久）——管理者从榜单一眼完成「价值排序 + 现状核对」。需求 seq 376 的三个排序维度（时间/应用主体/业务领域）与 seq 378 的基础信息整理（所属数据类型/应用主体/部署位置/使用周期/业务模块）在本卡合流。权威对应物是开放平台的 TOP 榜+接口详情页组合（R2 深圳：TOP10 榜点进接口详情有调用量/更新时间；R3 北京：最热接口列表带提供单位）——榜单与详情字段一体是平台运营标配。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**seq 376 功能句（与 034 同源）：「自动统计并展示各数据资源被调用和使用的排行情况，支持按时间、应用主体或业务领域进行排序，帮助用户直观了解哪些数据资产在实际业务中最具活跃度和价值」——榜单字段集（除调用量外还有哪些列？）、users/growth 等扩展字段口径（distinct 用户？注册用户？环比窗口？）均无定义。seq 378「应用基本情况汇总」补充「为每项被应用的数据资产整理基础信息，如所属数据类型、应用主体、部署位置、使用周期、涉及的业务模块」——信息项枚举在、取数口径无。核增需求与算法库 0 命中（附录 A.2）。UI 的 13 字段是前端演示约定，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

「榜单本体（多字段排行列表）」的权威方法锚分三层。其一，开放平台榜单实践（R2 深圳 / R3 北京）：榜单主维=调用量（双时间窗），扩展字段=提供单位/最近调用时间——字段集克制（不列用户数/环比），因用户粒度数据涉及合规边界。其二，官方统计面（R1 国家数据局）：数据产品/服务数量、交易额按主体汇总——「应用主体」维的官方口径参照，前提是逐笔流通记录。其三，库内承载：主维台账零承载（034 已证同根）；用户维最近邻 dev `sys_user` 3 行管理账号；时间维零承载（032 已证）。方法族对照：

## 四、数据缺失情况

### 4.1 主维台账零承载（结构级，判定性缺口）

榜单主维（资产×调用量）三源零承载（§3.3）——与 034 同根（调用台账族共用缺口），修复动作同族并项：API 网关日志/调用台账接入。

### 4.2 扩展维独立缺位（用户体系与时间明细）

本件超出 034 的缺口面在扩展维：**用户数**（users）要求调用用户注册/行为面——dev sys_user 3 行管理账号语义量级双排除，mock 千级用户量的基础三源皆无（与 DATATHM_016 平台月活跃件同根，用户体系未建是独立工程）；**环比**（growth）要求上期调用量——时间明细缺位（032 同根）。**四缺失情形归属「表不存在」**：扩展维修复须与主维台账同步设计（台账含 user_id 与时间戳列则三维一次落位）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 调用台账（含 user_id/时间戳列） | 监控工程立项（族级） | 本件 + 034/032/025/020-022 + DATATHM_016 | 主维+扩展维一次落位 |
| 资产登记面立项 | 数据工程立项 | 本件 D4 + 034 + DATAOV_001 族 | 对象轴 |
| 用户体系（注册/开发者账号） | 平台工程立项 | 本件 D2 + DATATHM_016 | users 字段独立前提 |
| 扩展维降维交付规则 | 口径裁定 | 本件 | 无用户体系时 users/growth 置空不填伪值 |

档位后果：三件套并项 → **完全直接支持**；第三方监测+白名单+降维规则 → **完全转换支持**；现状 → 完全不支持。推荐顺序：台账设计时即带 user_id/时间戳（一次到位），用户体系与登记面并行立项。
