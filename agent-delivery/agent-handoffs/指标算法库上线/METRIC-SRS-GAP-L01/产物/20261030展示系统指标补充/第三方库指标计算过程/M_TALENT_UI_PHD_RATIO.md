四个挂点的口径一致性约束：KPI 卡是全库占比；城市/机构抽屉是子人群占比（该城市/机构的学者中博士率）；中国视图是"当前机构在中国"子群占比。三种子群占比的分母含义各不相同（地理子群/机构子群/国别子群），但分子判定（博士）与本件完全一致——本件交付的判定规则与全库读数是四个挂点的公共底座，同义位只需在 SQL 外层加 WHERE 群体限定即可复用，这是把它立为独立指标件（而非页面附属逻辑）的工程理由。

### 1.2 为什么需要本指标

人才池的规模读数无法回答"这批人有多好"，学历结构是最直观的质量代理。UI 把「博士平均占比」放在总量卡正下方，让用户在读出"有多少人"之后立刻读出"其中多少是博士"，形成规模与质量的连续叙事；城市/机构抽屉里的同义位则支撑"哪里的人才更高端""哪个机构人才更顶尖"的比较叙事。页面导出报表同样含「博士平均占比」行，是线下汇报的常引用数字。

人才池的规模读数无法回答"这批人有多好"，学历结构是最直观的质量代理。UI 把「博士平均占比」放在总量卡正下方，让用户在读出"有多少人"之后立刻读出"其中多少是博士"，形成规模与质量的连续叙事；城市/机构抽屉里的同义位则支撑"哪里的人才更高端""哪个机构人才更顶尖"的比较叙事。页面导出报表同样含「博士平均占比」行，是线下汇报的常引用数字。

从业务链路看，这个读数有三个消费场景：其一，引才策略的画像侧——高端人才引进计划需要知道目标人群的博士浓度，以校准"引进的是不是真高端"；其二，区域比较侧——深圳与对标城市的人才池质量差，最简单的单一指标就是博士占比；其三，机构合作侧——与哪些高校/院所共建联合培养，先看对方的人才学历结构。三个场景都不需要精巧的口径，只需要一个可信、可复算的占比——这正是本件要交付的。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**「博士占比」「博士平均占比」在《科技信息展示系统和科技专题服务系统》全文（576 KB）0 命中。SRS 叶「人才分布信息查看」（seq 243）的学历维表述是「包括行业、学历、类型等统计数据」——学历作为统计维度被点名，但没有任何占比、平均或博士字样的定义；举例「可查看该地 AI 领域硕士及以上人才数量与主要院校」甚至把读数导向"数量"而非"占比"。因此本件走 UI 自造位的推测定义路径。

### 1.4 类似指标权威方法可行性分析概要

学历结构的统计在官方体系有直接先例。国家统计局《中国教育概况》与全国教育事业发展统计公报按博士/硕士/学士三级学位公布在校与授予规模（教育部官网，R1 链）；科技侧的《全国 R&D 人员全时当量》按基础研究/应用研究/试验发展分类（R5），虽不直接给博士率，但其"研究者按资历分档"的思路与学历结构分层同构。OECD ITA（Indicators of Talent Attractiveness）把 educational attainment 作为人才画像的七维之一（R3 链同域方法论）。方法族对照：①学位层级占比（教育部口径，贴合度高——本件采用）；②每千就业者研发人力（R5 口径，需就业分母，库内无）；③教育获得指数（UNDP 类，需人口分母，不可行）。数据可行性：学历子表双语字段直接可判，足。结论：可行。完整版见附录 C。

### 1.6 推测原意与推测定义

**推测定义（非甲方闭合口径）**：博士学历学者占学者的比例，按学者去重（一人多段学历只计一次）。

## 二、计算过程

### 2.1 装载与规模校验

经 `_gkxdb.py` 连接 gkx 只读库（参数纪律同批次总则）。规模对账三件：学历子表 `dwd_scholar_education_background` 实测 `COUNT(*) = 43,766`，与 20261021 轮库存零漂移；学者主档 `dwd_scholar` 21,316 行（与 `M_TALENT_UI_GLOBAL_STOCK` 共用基数）；学历子表覆盖的去重学者 `COUNT(DISTINCT scholar_id) = 20,025`，即 93.9% 的学者至少有一段学历记录。覆盖缺口 1,291 人主要是采集源未回填学历的学者，他们对主口径无影响（不入分母），对全库口径构成系统性低估——这就是双口径并列的理由。

### 2.2 博士判定规则

学历判定直接在 SQL 层完成：`degree_zh LIKE '%博士%'` 覆盖「博士」「哲学博士」「理学博士」等中文词族；`degree_en LIKE '%PhD%' OR degree_en LIKE '%Doctor%'` 覆盖 PhD / Doctor of Philosophy / Doctoral 等英文词族。之所以不用枚举匹配，是因为实测学位词有 12 种以上写法（见 §2.3 分布），词根包含法召回最全且无误报——"博士后"（postdoc，非学位）在库内 degree 字段未出现，无需排除词；"Doctor"在医学语境的歧义（MD 也带 Doctor）经抽样核对未出现干扰。该规则是确定性的、可被任何后续复现者逐字重放。

```sql
-- 博士学者（按人去重）
SELECT COUNT(DISTINCT scholar_id) AS phd_scholars
FROM gkx.dwd_scholar_education_background
WHERE degree_zh LIKE '%博士%'
   OR degree_en LIKE '%PhD%'
   OR degree_en LIKE '%Doctor%'
   OR degree_zh LIKE '%Doctor%';
-- → 15615
```

词根包含而非枚举的原因：实测学位词形 12 种以上（博士/哲学博士/理学硕士/PhD/…），枚举必漏；词根法唯一要排除的是「博士后」（postdoc 非学位），实测 degree 字段未出现该词，无需排除项——这条要在换词表时重新验证。

### 2.3 学位词分布实测

对 `degree_zh` 与 `degree_en` 合并后的词形做分布统计，Top8 为：博士 7,507 / 哲学博士 2,622 / 硕士 2,437 / 学士 2,172 / （空）2,036 / 理学硕士 1,981 / 理学学士 1,834 / PhD 1,074。三点解读：其一，中文词形远多于英文，池的中文属性再次得到印证（与 20261027 轮「dwd_scholar 实质中文学者池」结论一致）；其二，"博士"与"哲学博士"是两个独立词形，任何枚举式白名单都会漏掉其一，词根包含法的必要性在此；其三，空值 2,036 条（4.65%）按"未知"处理，不参与分子分母，只计入学历子表内部的缺失披露。

```sql
SELECT COALESCE(NULLIF(degree_zh, ''), degree_en, '（空）') AS deg,
       COUNT(*) AS n
FROM gkx.dwd_scholar_education_background
GROUP BY deg
ORDER BY n DESC
LIMIT 8;
-- → 博士 7507 / 哲学博士 2622 / 硕士 2437 / 学士 2172
--   （空）2036 / 理学硕士 1981 / 理学学士 1834 / PhD 1074
```

注意 `NULLIF(degree_zh,'')` 的防御：空字符串与 NULL 在 COALESCE 语义下不同，不先归一会把空串单独成行，Top8 里出现两行「空」，分布口径就脏了。

### 2.4 双口径占比与同基校验

主口径：博士学者 15,615 人 ÷ 有学历信息学者 20,025 人 = **77.9775%**。全库口径：15,615 ÷ 21,316 = **73.2548%**。两口径分子完全相同（15,615），差在分母（20,025 vs 21,316），差值 4.72 个百分点就是"6.1% 学者无学历信息"对读数的稀释效应。同基校验：分子（博士学者）必然是分母（学历覆盖学者）的子集——两集合都从 `dwd_scholar_education_background` 出发，满足同 WHERE 同池；跨件校验：本件分母 20,025 与共享快照 `edu_rows=43,766` 对应（一段学历对一学者可能多段，去重后 20,025），与 `M_TALENT_UI_GLOBAL_STOCK` 的主档基数 21,316 关系为 20,025 = 21,316 − 1,291（无学历学者），三级数字互推闭合（B11 台账对账）。

```sql
-- 分母（学历覆盖去重学者）
SELECT COUNT(DISTINCT scholar_id) AS edu_linked
FROM gkx.dwd_scholar_education_background;
-- → 20025

-- 全库分母
SELECT COUNT(*) FROM gkx.dwd_scholar;
-- → 21316

-- 主口径 15615/20025 = 77.9775%
-- 并列口径 15615/21316 = 73.2548%
-- 三级互推：20025 = 21316 - 1291（无学历学者）
```

### 2.5 稳健性与口径敏感性

做了两组敏感性测试。第一组，判定词族收窄：仅用 `degree_zh LIKE '%博士%'`（不含英文）得博士学者 15,611 人（-4 人），占比变化 <0.02 个百分点——英文词族只贡献 4 名独占学者，判定规则对词族宽度不敏感。第二组，分母口径切换：主口径（20,025）vs 全库口径（21,316）差 4.72 个百分点（§2.4 已述），方向为低估。此外 UI mock 的"+3.2% 同比上扬"是写死的常量，本口径为存量结构占比，不存在时间维，任何趋势化展示都应读取 `M_TALENT_UI_YOY_GROWTH` 的年度序列而非本件。

### 2.6 展示口径与同义位对齐建议

KPI 卡建议展示主口径 78.0%（保留 1 位小数与 UI 习惯一致），副标题标注"（按有学历信息的学者计）"。四个同义位（KPI 卡/城市抽屉/中国视图/机构抽屉）的语义差异：KPI 卡是全库占比；城市/机构抽屉是子人群占比（该城市/机构的学者中博士率），计算同链路、WHERE 加群体限定即可，但子盘受地理映射四成覆盖限制（同 `M_TALENT_UI_GLOBAL_STOCK` 缺口）；中国视图则把人群换成"当前机构在中国"的学者。产物 `derived` 键按可复算算术落盘（闸 9），城市/机构子盘数值随主数据工程后自动可算。

### 3.2 D1 学历子表：结构与量的双重充足

`dwd_scholar_education_background` 43,766 行，26 列中与本件直接相关的是 `degree_zh`/`degree_en`（学位双语列）与 `scholar_id`（学者外键）、`org_name_zh/en`（授予机构）。结构上，学位列是自由文本而非码表——这既带来词形多样（§2.3 的 Top8 只是冰山一角），也带来判定便利：中文"博士"词根与英文 PhD/Doctor 词根在全表的语义无一歧义。43,766 行对 21,316 名学者的人均 2.05 段学历，符合"本科+研究生"的常见履历结构，行数的合理密度本身就是数据质量的一个旁证：如果人均只有 0.5 段，就该怀疑采集回填不完整。

### 3.3 D1 的覆盖面：93.9% 学者有学历记录

学历子表覆盖去重学者 20,025 人，即 93.9% 的主档学者至少有一段学历记录。覆盖缺口 1,291 人（6.1%）的构成没有直接字段可查（子表无"为何缺失"标记），但从共享快照的学者面看，这些学者大概率是采集源只回填了履历未回填学历的尾部样本。6.1% 的缺口对主口径（有学历信息者分母）无影响——他们根本不进分母；对全库口径则是系统性低估，这正是双口径并列（77.9775% vs 73.2548%）的意义：把缺失的稀释效应显式化为 4.72 个百分点，而不是藏进单一读数。

### 3.4 D2 主档：全库口径的分母锚点

学者主档 21,316 行在本件的角色是"全库口径"的分母。与 `M_TALENT_UI_GLOBAL_STOCK` 共用同一基数（三级对账零漂移：20,025 = 21,316 − 1,291）。需要警惕的混用是：全库口径的分母是"全部学者"而非"全部有效学者"——status=2 的 8 行异常学者如果恰在学历子表中，会同时进入两个口径的分子，本件实测这 8 人无一有学历记录，所以两个口径的分子完全相同（15,615），差异纯由分母造成，口径解释干净。

### 3.5 D3 结果面缺失的确认

`cfg_metric` 全部 seed 组与 `GKX_INVENTORY.json` 280 表清单中，没有任何"学历占比/学位结构"类结果表；live 库的 ADS 67 张样例表（8–976 行）也不含此语义。因此本件属于"两库无现成结果面、但转换条件全齐"的标准完全转换支持形态——转换本身（一条 GROUP BY + 词根判定）已在脚本中完成并落产物。

## 四、数据缺失情况

### 4.1 学历记录的缺失分层

缺失分两层，影响面不同。第一层：**字段级缺失**——2,036 条学历记录（4.65%）degree 双语全空，这些行有学者、有学校、有时间，唯独没有学位名；处理为"未知"，不进分子也不进主口径分母，只在学历子表内部披露。第二层：**学者级缺失**——1,291 名学者（6.1%）无任何学历记录，他们对主口径免疫（不进分母）、对全库口径构成系统性低估（4.72 个百分点，§2.4 已并列）。两层缺失都不影响本件档位（完全转换支持的"数据量足"判定看的是覆盖面而非完备率，93.9% 的学者覆盖足够）。

### 4.2 时间维缺失（扩展口径受阻）

学历表 `start_time/end_time` 存在（is_current 标注在读段），但"学位授予年"没有独立字段——毕业时间只能近似为学历段结束年。若要交付"博士占比的年度演化"（如 2015 年毕业的博士占当年学者比例），须按 end_time 近似并披露精度限制；本件未做该扩展（KPI 是存量占比，无时间维）。这条登记为扩展预留：甲方若要趋势版，走 end_time 近似 + 脚本复用。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 预估工作量 |
|---|---|---|---|
| 采集端回填缺失学位 | 数据源治理 | 本件全库口径精度 | 持续性 |
| 学历表补授予年字段 | 字段工程 | "博士占比年度演化"扩展 | 轻量 |
| 城市/机构子盘解锁 | 主数据工程（同 GLOBAL_STOCK §4.3） | 抽屉同义位 | 随 4.1 工程 |

第 1、2 条是锦上添花（主口径已可交付）；第 3 条决定同义位（城市抽屉/机构抽屉的「博士占比」）何时可上线，与本件档位无关但与 UI 完整度相关。

补充：三条建议的优先级与 `M_TALENT_UI_GLOBAL_STOCK` §4.3 的主数据工程强耦合——第 3 条完全依赖它，第 1、2 条独立。若主数据工程立项，建议本件与 CHINESE_RATIO / MIGRATION_FLOW 的地域子盘需求合并提给同一工程，一次回填三件受益。
