## 摘要

「数据库含表数量」挂载在主题视窗库详情六元组的「数据表数」字段（`ThemeWindow.jsx:373`，mock 7 库各 156-234 张）——用户点选数据库卡片后看到的第一个结构规模读数。指标名三份真源 0 命中（:2729 元属性枚举无表数项）。数据侧按粒度双层交付：**schema 粒度**（工程口径）三源读数完整——dev 16 schema 表数分布 5-144 张（含非空分层：`gkxlumenx_dim` 18 表全非空 vs `gkxlumenx_ads` 96 表仅 5 非空——结构在数据未灌的分层事实）、gkx 单库 280 表（剔备份正表 181）、久新单库 210 表；**主题库粒度**（需求语义）三源无登记面——「基础研究主题库」的业务边界无登记，库均表数只能按 schema 近似（非空口径 14.4 张/schema）。mock 侧失配披露：详情字段合计 1,062 vs 同窗 StatCard 硬编码 1,248。判**部分支持**：schema 读数可交付、主题库语义需登记面。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**UI 派生读数**（指标名 0 命中；seq 372 元属性/seq 373 结构浏览为挂靠功能叶）。
- 复现状态：脚本已跑通；dev 16 schema 三元组 + 非空分层 + 三源单库读数全落产物。
- 档位结论：**部分支持**（schema 粒度双在 + 主题库粒度登记面缺位）。
- 关键事实：`gkxlumenx_ads` 96 表仅 5 张非空（5.2%）——「结构在数据未灌」的分层事实对「库含表数量」的语义选择（结构资产 vs 数据资产）有直接影响。
- 升档路径：主题库登记面（库边界+表清单）→ 完全直接支持；schema 近似口径认定 → 完全转换支持。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/主题视窗/数据库详情展示/数据集元属性详尽呈现（1.1.1.1.4.4.3.2.1；SRS seq 372、excel_row 375）。UI 实际容器是主题视窗右侧库详情 Descriptions 面板：`ThemeWindow.jsx:354-381` `detailItems` 十八项元数据（数据库名称/标签/采集时间/来源/数据类型/更新频率/所属主题/发布时间/数据结构/相关项目/**数据表数**/记录数量/存储大小/所在区域/负责人/分区/更新时间），其中 `ThemeWindow.jsx:373` `{ label: '数据表数', value: `${selectedDatabase.tables} 张` }`——消费 mock `themeDatabases` 每库的 `tables` 字段（156/234/189/128/112/145/98）。选中库由左侧卡片列表联动（`onDatabaseSelect`，`ThemeWindow.jsx:336`）——本字段是单库粒度读数，随用户点选切换。需求原文（seq 372）：「每个数据集显示其元数据，包括名称、所属主题库、数据类型、数据量、来源单位、采集时间、更新时间及维护责任人等信息」——「等信息」的开放枚举涵盖了 UI 实现的表数字段，但需求枚举本身无「表数」项。

### 1.2 为什么需要本指标

库详情的「数据表数」是用户下钻路径上的**第一结构读数**：从主题树（分类）→数据库卡片（库级）→详情面板（结构级），表数告诉用户「这个库里面有多少张表等我探索」——它是「数据表结构与字段详情查看」（seq 373，下一步下钻）的入口规模预期。管理侧价值：库均表数是资源建设密度的结构指标（一个主题库是 3 张表的空壳还是 150 张表的实库），直接服务资源建设质量评估。与同面板「记录数量」（DATATHM_030 单库粒度）构成库级双规模：表数管结构宽度、记录数管数据深度。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**指标名「数据库含表数量/数据表数」三份真源 0 命中。主需求 :2729（SRS seq 372）元属性枚举为「名称、所属主题库、数据类型、数据量、来源单位、采集时间、更新时间及维护责任人等信息」——「数据量」在列但通常指记录量，「表数」未明确枚举（UI 以「等信息」的开放性自行补充）；:2733（seq 373）「支持浏览每个数据集下的数据表结构」是结构浏览功能。表数的统计口径（物理表还是有效表？含不含备份/空表？）无定义。

### 1.4 类似指标权威方法可行性分析概略

「库含表数」的权威对应是数据资产目录的**库级结构登记**。其一，国家科学数据中心体系（R2）：数据集为登记单元（155,721 个），每个数据中心的数据集数即「中心含数据集数」——逻辑资产粒度；其二，数仓工程口径：schema×表数是物理结构的标准盘点（ODS/DWD/ADS 分层各含表数），如本件 dev 16 schema 分布；其三，DCMM 数据管理能力成熟度：资产目录要求库-表-字段三级登记，「库含表数」是目录的中间层读数。方法族对照：

| 方法族 | 登记单元 | 本库承载 | 贴合度 |
|---|---|---|---|
| 中心×数据集（R2） | 逻辑数据集 | 无目录（待立项） | 目标态 |
| schema×物理表（工程） | 物理表 | **三源双在** | **最高（即期）** |
| DCMM 三级目录 | 库-表-字段 | 无目录 | 目标态（触发器①） |
| mock 库粒度（演示框架） | 业务主题库 | 无登记（词族 0 命中） | 语义参考 |

结论：schema 粒度三源即期可算，业务主题库粒度需目录立项。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

方法选**schema 粒度结构盘点**（工程口径，DCMM 库-表-字段三级登记的中间层最小落地）：information_schema 聚合 schema×表数×行数三元组，附非空/空表分层。选择理由：其一，schema 是数据库引擎的权威「库」承载（与 004 §2.1 同理）；其二，三元组+分层能同时回答「结构宽度」（表数）与「数据深度」（行数/非空率）——本件字段语义（表数）与数据质量语义（空表）分离披露；其三，主题库粒度登记面缺位已留证（§3.3），不悬空。

### 2.2 dev 16 schema 三元组读数（核心承载）

dev `gkxlumenx_*` 16 schema 表数×行数三元组（`dev_schema_table_rows_sorted`）：`gkxlumenx_dwd` 144 表/420.9 万行（最大数仓层）、`gkxlumenx_ods` 75 表/562.5 万行（接入层）、`gkxlumenx_ads` 96 表/79 行（结果层——**结构在数据未灌**）、`gkxlumenx` 28 表/1,839 行（业务主库）、`gkxlumenx_bi` 41 表/3,105 行（报表）、`gkxlumenx_topic_enterprise` 21 表/7,190 行（企业专题）、`gkxlumenx_job` 21 表/0 行（调度配置）等。**非空分层**（`dev_schema_nonzero_tables_sorted`）：`gkxlumenx_dim` 18 表全非空（维度表全灌）、`gkxlumenx_ods` 75 表 63 非空（84.0%，`dev_ods_nonzero_share_pct`）、`gkxlumenx_bi` 41 表 35 非空、`gkxlumenx_ads` 96 表仅 5 非空（5.2%，`dev_ads_nonzero_share_pct`——空壳率最高的 schema）、`gkxlumenx_flow/job/mp/pay` 四 schema 全空（纯配置结构）。

### 2.3 gkx 单库读数（复用族内产物）

gkx 单 schema 一体库：280 表（`gkx_table_count`），其中备份表 99 张（`gkx_backup_like_table_count`，bak 三轮+v3bad，DATATHM_036 实测清单）——**正表 181 张**（`gkx_regular_table_count`）。「库含表数」在 gkx 口径双值并列：280（全）/181（剔备份）。

### 2.4 久新单库读数（快照锚）

久新单库 ads_*：210 表（`jiuxin_table_count`，2026-11-01 探测日快照），非空 206（`jiuxin_nonzero_table_count`）——活库装载率 98.1%，无备份污染（命名规范统一，bak 词族 0 命中）。

### 2.5 稳健性与口径敏感性

三点敏感性：其一，**schema↔主题库映射不唯一**（与 004 §2.5 同根）——16 schema 是工程分层（ods/dwd/ads 是数据流转层不是业务库），按业务语义「一个主题库」可能横跨多 schema（基础研究主题库的表可能散在 ods+dwd+ads 三层）——schema 粒度读数是结构事实但非业务语义；其二，**结构资产 vs 数据资产**——`gkxlumenx_ads` 96 表仅 5 张非空（非空率 5.2%，`dev_ads_nonzero_share_pct`）：按结构口径「ads 库含 96 表」、按数据口径「ads 库含 5 张有数据的表」——两个读数差 19 倍，语义选择影响巨大（mock 的 156-234 显然是数据资产叙事）；其三，**库均读数的分母选择**——三口径并列（派生键族）：全集均值 `dev_tables_per_schema_mean_all`=33.9（542/16）vs 非空表均值 `dev_tables_per_schema_mean_nonzero`=14.4（231/16）vs 剔配置均值 `dev_tables_per_schema_mean_data_schemas`=44.4（444/10）——本件主交付非空口径均值（14.4，分子分母同 16 schema 集，B3 note 写死），另两口并列在产物。

### 2.6 需求符合性预评

需求挂靠叶 seq 372「数据集元属性」——本字段是元属性面板的结构规模项。**结构规模预期**——部分满足（schema 粒度读数可交付，业务库粒度无登记）；**下钻入口预期**——满足（表数+记录数双规模字段的结构齐全，seq 373 结构浏览的入口数据在）；**元数据完整性**——部分满足（十八项中表数/记录/存储三项是规模项，mock 全有、库内只有 schema 近似）。此预评与升档触发器对齐：登记面立项后本字段直接回填业务库读数。

## 四、数据缺失情况

### 4.1 主题库粒度登记面缺位（结构级，主因）

「哪个库含哪些表」的业务登记（库边界+表清单映射）三源缺位——与 DATATHM_004 完全同根（004 数库、本件数每库表，同一张登记面解决两件）。修复动作：资产目录立项时把「库×表」映射作为目录核心实体（mock 的 tableSchemas 结构——每库 3 张示例表 schema——是登记面的正确形态参照，正式版扩为全量表清单）。本件 §2.2 的 schema 三元组即目录中间层的初始底稿。

### 4.2 空壳 schema 的语义裁定缺口（口径级，次因）

`gkxlumenx_ads` 96 表仅 5 张非空——结构资产口径（96）与数据资产口径（5）差 19 倍。这不是数据缺失（结构在）而是**灌数工程未完成**（ads 层是结果面层，上游加工业务未跑）。修复动作有二：灌数工程（ads 层加工任务上线，结构→数据补齐）或口径裁定（正式版字段选结构口径并披露空表率）。前者是数据工程、后者是一纸裁定——按 B10 不擅自定案。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 资产目录（库×表映射）立项 | 数据工程 | 本件 + 004/036/030 | 触发器①（族级共用，一次解四件） |
| schema 近似口径认定 | 口径裁定 | 本件 | 触发器②（语义损失披露） |
| ads 层灌数评估 | 数据工程 | 本件 ads 读数 | 空壳率 94.8% 的补齐 |
| mock 演示值对账 | 前端工程 | 本件 + 同窗卡 | 1,062/1,248/151.7 三失配修正 |

档位后果：登记面 → **完全直接支持**；schema 近似认定 → **完全转换支持**；现状 → 部分支持（双粒度并列）。推荐顺序：与 004 合并推登记面（共享修复项），mock 对账随正式版替换。
