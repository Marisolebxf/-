## 摘要

- 需求判定：**UI 派生读数**（三份说明书 0 命中；mock「亿」级文本量级值不作口径证据）。
- 复现状态：脚本已跑通；三源对象级行数 + 登记面排除探针全落产物。
- 档位结论：**部分支持**（资源登记面零承载 + 对象级读数三源精确双在）。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/总体视窗/科技数据资源统计/大数据资源中心详情·**记录数**（UI 派生读数，无需求编号）。UI 实际挂载有两处：其一，`BigDataCenterDetail.jsx:276-334` 主题库分类展示卡，每张分类卡底部三统计项「数据库数/数据表数/记录数」，记录数读 `cat.records`（mock 三分类：科技要素库 3.5 亿/领域主题库 2.9 亿/战略情报库 3.8 亿）；其二，`:535` 深度浏览抽屉 Descriptions 的「记录数」字段，读 `item.recordCount`（mock 文本量级值 '1.28亿'/'5800万条' 等）。派单 mount 行 `OverviewWindow.jsx:549` 实查是该组件抽屉内「关联主题库」渲染块（relatedIds 映射行）——非读数位，本件按真实读数位核（mount 勘误回执登记）。mock 总览另有 `bigDataCenterStats.overview`：totalDatabases 28/totalTables 1,248/totalRecords '10.2亿'——「数据资源数据量（条）」的全局锚定值。mock 结构披露：记录数以「亿/万」文本量级呈现（非逐条整数），数值不作数据证据（B10）。

### 1.2 为什么需要本指标

大数据资源中心详情的管理命题是「库里有什么、有多厚」：主题库分类卡用记录数回答每个分库的体量，深度浏览抽屉用记录数回答单条资源的体量——两者构成「总-分」体量叙事的「分」层。需求语境（主需求 :2729 数据集元数据列举「名称、所属主题库、数据类型、数据量、来源单位、采集时间、更新时间及维护责任人」）把「数据量」列为数据集元数据的标准字段——本读数就是该字段的可视化呈现。与 DATATHM_030（数据资源总记录数，主题视窗族）的区别：030 是主题库分级的记录数（ThemeWindow 表格列），本件是资源中心分级的记录数（BigDataCenterDetail 抽屉/分类卡）——语义同根（对象×记录数）、挂载窗不同（总体视窗 vs 主题视窗），两件互引对齐（§1.7）。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现该指标名。**主需求最近语境 :2729（1.1.1.1.4.4.3.1.2 数据集元数据展示）：「每个数据集显示其元数据，包括名称、所属主题库、数据类型、数据量、来源单位、采集时间、更新时间及维护责任人等信息」——「数据量」是元数据字段列举，无记录数/存储体量的口径定义、无计量单位约定。核增需求与算法库 0 命中（附录 A.2）。UI 的 recordCount 文本量级值（'1.28亿'）是前端演示约定，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

「资源×记录数」的权威方法锚分三层。其一，国家科学数据中心汇交体系（R1，GB/T 39912-2021）：数据集汇交的元数据含记录数/文件数/体量——记录数是汇交著录项的制度化形态，登记在册方可统计。其二，国家科技资源共享服务平台体量序列（R2）：数据中心总量按「库-表-条」三级统计（如 PB 级总量按中心公布）——对象级计数的官方口径。其三，数据资产盘点实践（R3，DAMA/国家标准 GB/T 36073）：数据资产目录的核心属性即「数据量」——目录化登记是计量的前提。方法族对照：

| 方法族 | 代表 | 度量对象 | 数据要求 | 与三源匹配 |
|---|---|---|---|---|
| 汇交著录口径 | R1（GB/T 39912） | 数据集记录数 | 汇交元数据登记 | **无登记面** |
| 三级体量口径 | R2（国家中心序列） | 库-表-条 | 目录+行数 | **表级行数可数、目录缺** |
| 资产目录口径 | R3（DAMA/GB/T 36073） | 资产×数据量 | 资产目录 | **无目录**（DATAOV_001 同根） |
| 对象级等价口径 | 本件交付路径 | 物理表=资源 | COUNT(*) | **三源精确双在**（等价口径） |
| 前端演示 | UI recordCount | mock 文本量级 | mock 常量 | 结构披露（不作源） |

结论：权威口径的登记面/目录层三源零承载；对象级等价口径（物理表行数）三源精确可数但语义须经裁定。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：按语义拆两口径。**口径 A（资源登记口径，UI 本意推测，不可交付）**：

$$\text{Records}(r) = \text{count}(T_r),\quad r \in \text{资源登记清单}$$

即登记清单内每条资源 r 映射到物理表（或表集合）$T_r$ 的行数——前提是「资源→库表」映射存在，三源实测无（§3.3）。**口径 B（对象级等价口径，即期可交付）**：库内物理表=一条数据资源，逐表精确 `COUNT(*)` 即记录数（dev 9 表/gkx 11 表/久新 5 表主量面 + 全库合计）——语义=「库内数据资产的记录数」，与口径 A 的差异（编目边界、聚合粒度）披露。

**降档/升档触发器（B10 模板）**：①建数据资源登记面（资源→库表映射×记录数快照，与 DATAOV_001 资产目录并项）→ 口径 A 直查升**完全直接支持**；②甲方裁资源口径=库内物理表（等价口径裁定）→ 口径 B 升**完全转换支持**（本件交付形态即该口径，零额外工程）；③维持现状 → 部分支持（对象级读数仅供内部参考，不对外标「平台资源数据量」）。

## 二、计算过程

### 2.1 方法选择（文献依据）

口径 B（对象级等价）的方法选**物理表精确计数并列 + 全库合计双口径**（R2 三级体量口径的表级落地 + R3 资产盘点的方法论）：对三源主量面逐表精确 `COUNT(*)`（dev/gkx 直连精确、久新 live 探针快照），全库合计 dev 用 information_schema 估算（B9 标注）、久新用共享快照 210 表逐表求和——两种合计口径并列不混用。选择理由：其一，对象级行数三源精确可数（确定性、可复算）；其二，R2 的官方实践就是「库-表-条」三级统计，表级是资源级的最近邻等价物；其三，合计的双口径并列（估算 vs 快照求和）让量级判断有交叉验证（B10 不悬空）。口径 A（登记面）因零承载不做方法选型（F4 禁伪公式）。

### 2.2 dev 对象级读数（9 表主量面 + 全 schema 估算合计）

### 2.5 稳健性与口径敏感性

对象级口径的三点敏感性：其一，**等价边界的模糊性**——物理表≠平台登记资源（一张表可能被多个「资源」引用、一个「资源」可能跨多表聚合），mock 的 28 库/1,248 表是编目级聚合（表均 44 条/库），物理表口径没有这层聚合——两口径的「资源个数」完全不同构；其二，**镜像表重复计数风险**——dev 的 enterprise_news 与 ods.dwd_org_important_news_info 是同源镜像（各 1,668,414 行），全库合计把它们计了两次（估算口径的固有粗糙，精确口径应按语义表清单去重——B9 双口径并列的意义）；其三，**活库快照漂移**——久新按 metrics_as_of_date 快照管理且当日探测 211 张（快照日 210 张），合计值随上游版本变动（2026-11-01 快照日口径标注，重跑须当日重数）。

### 2.6 需求符合性预评

UI 需要「每条资源一个记录数」（分类卡 3.5 亿级 + 抽屉 '1.28亿' 文本）。口径 B 交付的是三源主量面 25 张物理表的精确行数 + 全库合计双口径：**部分满足**——对象级读数即期可出（表级精确），但「资源」的编目边界（28 库/1,248 表的聚合层级）无同构面、记录数的呈现单位（mock 用亿/万文本）与逐条整数口径待统一。预评结论与触发器对齐：等价口径裁定（②）零成本即期闭合，登记面（①）是编目口径的根治路径。

## 四、数据缺失情况

### 4.1 资源登记面零承载（结构级，主因）

「每条资源多少条记录」的登记前提是「资源清单+资源→库表映射」存在。三源实测零承载（§3.3）——与 DATAOV_001 的资产目录缺口同根、与 DATAIN_002 的归集台账缺口相邻：目录（是什么资源）、台账（怎么来的）、映射（资源在哪张表）三者构成数据资源管理的元数据铁三角，本族五件+030 全部卡在同一个三角缺位上。**四缺失情形归属「表不存在」**：修复动作是资源登记面立项（资源清单×库表映射×记录数快照），一次建设六件受益（002/027/028/033/039/030）。

### 4.2 编目边界与计量单位口径缺位（口径级，次因）

即便走对象级等价口径，两个口径问题仍须甲方裁定：其一，**编目边界**——mock 的 28 库/1,248 表聚合层级（均 44 表/库）在库内无同构（三源物理表是平的，没有「库」级分组登记）；其二，**计量单位**——mock 用「亿/万」文本量级（'1.28亿'），UI 名称却写「（条）」，逐条整数 vs 量级文本是两种呈现口径（后者无法对账）。两者都是展示约定问题而非数据问题，但不确定则读数无法落地。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 资源登记面立项（清单×映射×快照） | 数据工程立项 | 本件 + 002/027/028/033/030 + DATAOV_001 | 触发器①（族级并项，一次建设） |
| 甲方裁资源口径=物理表 | 口径裁定 | 本件零成本升档 | 触发器②（本件交付形态即该口径） |
| 计量单位规范（逐条整数） | 展示规范 | 本件 + 030 | mock 文本量级值替换为整数读数 |

档位后果：登记面建成 → **完全直接支持**；等价口径裁定 → **完全转换支持**；现状 → 部分支持。推荐顺序：等价口径裁定即期（零成本）、登记面立项为主线（族级并项）、单位规范随 UI 改版。
