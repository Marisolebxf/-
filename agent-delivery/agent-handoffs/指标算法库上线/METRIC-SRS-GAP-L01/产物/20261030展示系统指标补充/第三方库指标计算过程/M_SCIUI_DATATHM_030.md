## 摘要

「数据资源总记录数」是主题视窗统计概览第三卡（`ThemeWindow.jsx:389`，mock 10.2 亿条），与主题库总数（28 个）/数据表总数（1,248 张）构成规模三卡的量级顶点。指标名三份真源 0 命中（UI 派生读数；主需求 :2729「数据量」是数据集元数据属性项）。数据侧三源全表行数面双在：本件对 gkx 280 表逐一精确 COUNT（65,814,945 条，零错误——单表最大 `dwd_zh_patent` 族外另有 7.98M 招聘表等均实测）+ dev 16 schema 估算合计（9,855,673）+ 久新 210 表快照合计（182,707,016），三源合计 **258,377,634 条（2.58 亿）**。降档根因是口径三重未裁：资源中心边界（配置库是否计入）、跨源去重（dev ods 与 gkx 同构表重复）、单位口径（mock 10.2 亿 vs 实测 2.58 亿的量级差）。判**部分支持**：量级读数可交付、正式口径需裁定。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**UI 派生读数**（指标名 0 命中；:2729「数据量」为属性项非平台指标）。
- 复现状态：脚本已跑通；gkx 280 表逐一精确 COUNT（零错误）+ 三源合计全落产物。
- 档位结论：**部分支持**（行数面三源双在 + 汇总口径三重未裁）。
- 关键事实：三源合计 2.58 亿 vs mock 10.2 亿——演示值是实测的 3.9 倍，量级失配必须披露。
- 升档路径：资源登记面（边界裁定）→ 完全直接支持；口径裁定（含/去重规则）→ 完全转换支持。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/主题视窗/数据资源展示（1.1.1.1.4.4.3；SRS seq 368-372）。UI 实际容器是主题视窗统计概览行第三张卡：`ThemeWindow.jsx:389` `<StatCard title="总记录数" value="10.2" unit="亿条" trend={{ type: 'rise', value: 15.2 }} />`——四卡依次主题库总数 28 个/数据表总数 1,248 张/总记录数 10.2 亿条/存储总量 18.6 TB（全部硬编码演示值）。三卡构成「库→表→记录」的规模漏斗：库数（28）→表数（1,248，平均每库 44.6 表）→记录数（10.2 亿，平均每表 81.7 万条），记录数是漏斗底部的量级顶点。主内容区的数据库详情面板（`ThemeWindow.jsx:378`）有对应的记录数量字段（`selectedDatabase.records`，mock 字符串如「2.3 亿」）——本件 StatCard 是详情字段的全库聚合形态。

### 1.2 为什么需要本指标

「总记录数」是数据资源中心最直接的**体量证明**：管理者汇报资源建设成果（「我们汇聚了 10 亿条数据」）、用户评估数据密度（平均每张表多少条记录）、采购方核验投入产出（每条记录的成本）都以它为锚。国家实践对应物是国家科学数据中心的 270PB/基础数据中心的「10 亿条记录」（R1/R3）——记录数与存储量并列是科学数据基础设施的双量级口径。本件的隐含难点：跨源汇聚场景下「总」的语义比单库复杂得多（三源独立计数是否去重？配置元数据算不算资源记录？），这是它与单库记录数的本质差异，也是本件调研重心。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**指标名「总记录数/数据资源总记录数」三份真源 0 命中。主需求 :2729「每个数据集显示其元数据，包括名称、所属主题库、数据类型、数据量、来源单位……」——「数据量」是数据集级元数据属性项（单库粒度），不是平台级总记录指标；平台级聚合口径（哪些库表计入、跨源怎么算、单位是条还是亿条）无任何定义。UI 的 10.2 亿是前端演示值，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

「总记录数」的权威口径分两层。其一，国家科学数据中心体系（R1）：20 个中心数据总量 270PB——**按中心上报汇总**，各中心内部口径自治（记录数/文件数/字节数三轨并行），总量是行政汇总不是技术去重；其二，国家基础数据中心（R3）：「数据记录超过 10 亿条」——单中心记录数口径，数据集为登记单元；其三，中科院体系页（R2）：184.42PB/155,721 个数据集——存储量与数据集数并列的看板口径，不报记录总数（记录数在文件型数据场景不可加）。方法族对照：

| 方法族 | 计量口径 | 汇总机制 | 与三源匹配 |
|---|---|---|---|
| 国家中心上报（R1） | PB+记录数 | 行政汇总（不去重） | 形态参考（本件三源合计同构） |
| 单中心记录数（R3） | 记录条数 | 中心内直查 | gkx/久新单库可映射 |
| 体系看板（R2） | PB+数据集数 | 体系登记 | 数据集级可映射 |
| 资源中心合计（需求语义） | 记录条数 | 边界+去重规则 | **无登记面**（待裁定） |

结论：三源各自的行数面完整（本件已实测），缺的是资源中心级的边界与去重规则——行政汇总口径（不去重、三源直加）本件即可交付，技术去重口径需登记面。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

方法选**全表行数聚合**（R1 行政汇总口径的工程落地）：三源各自全表行数合计后直加，不去重不剔表。选择理由：其一，行数面三源结构+数据双在（§2.2-2.4），本件已完整实测；其二，行政汇总是国家级实践口径（各中心自治口径直加，R1 的 270PB 即此机制），工程上零歧义可即期交付；其三，技术去重口径（口径 B）依赖跨源映射登记（哪张 dev 表与哪张 gkx 表同构），登记面缺位下强算会引入主观判断（B10 不擅自定案）。dev 用 information_schema 估算口径（B9：0 值可信非 0 为量级），gkx 逐一精确 COUNT，久新快照——三源口径异构随行披露。

### 2.2 dev 全库行数合计（估算口径）

dev `gkxlumenx_*` 16 schema 行数合计 **9,855,673**（`dev_rows_sum_estimated`，information_schema.table_rows 聚合）：主体在 `gkxlumenx_ods` 5,625,204 + `gkxlumenx_dwd` 4,209,027（两 schema 合计 99.99%）；配置面 `gkxlumenx_bi` 3,105/`gkxlumenx_dim` 6,063/`gkxlumenx_cfg` 2,236 等（`dev_rows_sum_by_schema_sorted` 16 项全分布）。注意口径：估算值（B9 note 写死），且 dev ods 75 表与 gkx 280 表存在同构（`dwd_patent` 族 dev 侧 913 行样例 vs gkx 侧 2,939,895 全量）——两源不是重复的全量镜像（dev 是采样残留），行政汇总直加的重复计数风险在 ods/dwd 两 schema 主要表上实际量级有限（详见 §2.5）。

### 2.3 gkx 全库行数合计（逐一精确 COUNT，核心实测）

gkx 280 表逐一 `SELECT COUNT(*)` 精确计数，合计 **65,814,945** 条（`gkx_rows_sum_exact`，零错误——`gkx_count_error_tables` 空）。行数 Top 构成（`gkx_rows_by_table_sorted` 280 项全清单在产物）：招聘表 `dwd_org_recruit_info` 7,981,643（单表最大）、股票行情族 `dwd_ls_stock_daily_quotation` 4,420,724（含 bak 备份同量）、司法/变更/标签等机构属性族（339 万/325 万/228 万级）、专利族合计 619 万（`dwd_patent` 2,939,895 主档 + 属性表族，`gkx_patent_family_rows_wan_unit`=619.06）。空表 10 张（`gkx_zero_tables`）：`dwd_fund_*` 基金族 8 张（含 bak_20260911 备份 3 张）+ `dwd_rd` 研发族 2 张（含 bak）——基金/研发域结构在、数据未灌（样例级以下）。大表 `dwd_zh_paper` 100,900/`dwd_patent` 2,939,895 走 s3_01 快照精确值（B11 锚，避免重复打库），其余 278 表本件实测。

### 2.4 久新全库行数合计（快照锚）

久新 ads_* 210 表 rowcounts 合计 **182,707,016**（`jiuxin_rows_sum`，lane7 快照 B11 锚；活库连接失败 2 次已由 L1 组登记，读数走快照）。非空 206 张，空 4 张（`jiuxin_zero_table_count`）。Top5（`jiuxin_top10_rows_sorted`）：`ads_institution_collaboration_subfield_yearly` 23,363,790/`ads_project_institution` 22,571,355/`ads_institution_collaboration_yearly` 14,380,246/`ads_patent_analysis_topic_patent` 12,406,725/`ads_project_topic` 11,374,389——前五均千万级，久新是三源中记录量最大的（占总合计 70.7%）。

### 2.5 稳健性与口径敏感性

三重口径敏感性：其一，**跨源重复计数**——dev ods 的 dwd_* 表与 gkx 同名表（dwd_patent 族 17 表）是「同名不同量」（dev 万级样例 vs gkx 百万级全量），行政直加在专利族上重复上界 289,929 条（`dev_gkx_overlap_rows_upperbound`，dev 侧专利族合计——即直加口径最大重复量），占三源合计 0.11%（派生键 `dev_gkx_overlap_share_pct_upperbound`=0.11，分子 289,929/分母 258,377,634）——重复风险实际可控但机制上不合规（正式口径必须裁定）；其二，**配置面污染**——dev 16 schema 中 job/pay/flow/mp 四 schema 行数为 0（无污染），bi/cfg/cms/config 四 schema 合计 6,187 条（`dev_config_schema_rows_sum`，占 0.06%）——配置面占比极小但语义上不是「数据资源」；其三，**估算口径漂移**——dev 的 information_schema 行数是 InnoDB 统计信息估算（B9），与精确 COUNT 可能有个位数百分比漂移；本件 dev 合计 985 万以「量级参考」交付（正式读数需逐表 COUNT）。三源合计 258,377,634 条（2.58 亿）vs mock 10.2 亿——演示值是实测的 4.0 倍（派生键 `mock_vs_measured_ratio`=4.0，分子 10.2 亿/分母 2.58 亿），量级失配披露（mock 作者的「亿级」叙事框架与三源现状不匹配，正式版读数会显著小于演示值）。

### 2.6 需求符合性预评

## 四、数据缺失情况

### 4.1 汇总口径三重未裁（口径级，主因）

「总记录数」正式口径需要三个裁定（§2.5）：**边界**（16+280+210 表全算还是仅数据类表白名单）、**去重**（dev ods 与 gkx 同名表的重复计数规则）、**单位**（条数直报 vs 亿条换算）。三者都无登记面/需求定义——本件行政汇总口径（直加不去重）是零歧义的最小交付，但对外发布前必须经业务裁定（尤其 mock 10.2 亿 vs 实测 2.58 亿的量级回调需要管理侧知情）。修复动作：口径裁定一纸文件（触发器②）+ 资源白名单登记面（触发器①，族级共用）。

### 4.2 dev 估算口径精度（数据级，次因）

dev 行数走 information_schema 估算（B9）——与精确值可能有个位数百分比漂移。正式读数若需精确，须对 542 表逐一 COUNT（成本可控：dev 无千万级大表，最大单表约百万行）。此缺口不影响本件量级结论（估算漂移 <5%，2.58 亿的量级判断稳健），列为正式化工程项。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 口径裁定（边界/去重/单位） | 口径裁定 | 本件 | 触发器②（一纸文件，即期） |
