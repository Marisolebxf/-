## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/应用视窗/资产应用总览（SRS 应用视窗 seq 376-379 四叶之首；UI 读数挂「资产应用总览」Tab 首屏）。UI 实际挂载是「调用趋势总览」卡（`ApplicationWindow.jsx:1287` Card title）的双轴折线图 `getCallTrendOption()`：legend 双系列（`:66`「调用次数」「活跃用户数」），users 系列挂右轴（`:76`，`yAxisIndex: 1`，青色虚线）——活跃用户数作为调用量趋势的伴随维度，用于判断「调用增长是用户变多还是单用户用得更频」。mock 数据源 `mockData.js:840-845` `usageCallTrend`：`{dates: ['05-16'…'05-22'], calls: [78200…85600], users: [3200, 3350, 3280, 3420, 3510, 3480, 3456]}`。mock 结构披露：users 是**日粒度**序列（7 个自然日）且未标注去重口径——MAU 形态（月窗去重）在 mock 中根本不存在，演示值不作数据证据（B10）。

### 1.2 为什么需要本指标

活跃用户数是平台运营的「体感温度计」：调用次数涨而活跃用户平 → 头部用户用得更深（粘性高但增长停滞）；两者同涨 → 用户与用量双增长。MAU 的权威地位：国家统计局《互联网经济统计报表制度》把「月度活跃用户数」列为主题互联网出行/医疗平台基本情况表的法定季报指标（与期末注册用户数并列，U202 表代码 16/U203 表代码 07）——国家统计层面 MAU 是平台经济的标准观测项。本库场景下，该读数要求「用户标识 × 行为时间戳」的行为日志存在且可按月窗去重——科技数据资源平台若无终端用户体系（纯管理后台）或无埋点，MAU 无从谈起。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「平台月活跃用户数」指标名。**语义锚两处：SRS seq 387（多维可视化排行与对比）「通过趋势图、排行榜等可视化组件，展示主题数据被调用次数、活跃用户、业务系统分布等多项指标，支持对比分析不同主题数据的调用表现」——「活跃用户」是图表伴随维度枚举项；主需求 :2813 同文。「月」「去重」「活跃行为定义」三个口径要素均无。核增需求与算法库 0 命中（附录 A.2）。UI 的 users 序列是 mock 演示值，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

MAU 口径分三层。其一，国家统计报表（R1）：重点互联网平台按季填报「月度活跃用户数」（计量单位：个）——法定指标但制度文本未公开去重细则，实际以平台自报口径为准。其二，业界标准定义（R2 AppsFlyer/R3 腾讯云）：MAU=统计月（或滚动 30 天）内与平台发生互动的唯一用户数——同用户多次使用只计 1 次；唯一性标识用设备 ID（GUID）或账号 ID；「活跃行为」（启动/登录/关键行为）由平台自定义且必须披露，不同平台口径不可直接比较。其三，移动统计工程口径（R4 百度移动统计）：月活跃用户=过去 30 天（含当日）启动过应用的用户（已去重），以独立设备为判断标准。方法族对照：

| 方法族 | 代表 | 原料 | 口径 | 与三源匹配 |
|---|---|---|---|---|
| 国家报表季报 | R1（统计局 U202/U203） | 平台自报 | 月度活跃用户数（个） | 无行为面可自报依据 |
| 术语标准 | R2（AppsFlyer） | 行为日志 | 月窗去重唯一用户 | **无日志** |
| 云厂商统计 | R3（腾讯云）/R4（百度） | SDK 埋点 | 设备 GUID 去重 | **无埋点** |
| 前端演示 | UI users 3,456 | mock 常量 | 日序列（DAU 形态） | 结构披露（不作源） |

结论：三条权威路径的原料（行为日志/SDK 埋点/用户体系）三源均无承载。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（须披露口径不闭合）**：按 R2/R3 业界共识推测

$$\text{MAU}_m = \left| \{ u : \exists\, a \in A_m,\ \text{user}(a)=u \} \right|,\quad A_m = \text{月 } m \text{ 内的活跃行为集（登录/访问/调用）}$$

即统计月内发生至少一次活跃行为的去重用户数（唯一性标识建议账号 ID；活跃行为三选一须裁定并披露）。**前提是行为日志面存在（用户标识 × 行为时间戳 × 行为类型），三源实测无（§3.3）**——公式列示仅作口径锚，不构成可执行计算（F4：本件 §二 从缺）。

## 四、数据缺失情况

### 4.1 终端用户行为面与注册面双缺（结构级，判定性）

MAU 的两层前提——**用户体系**（谁是我平台的用户）与**行为日志**（谁在何时干了什么）——三源均无：dev 是纯管理后台（3 个运维账号），无 C 端注册面；gkx/久新是数据与分析库，无用户表；行为埋点/访问日志任何源都未立项。这不是数据量问题而是**平台形态问题**：科技数据资源平台当前是「数据管理+展示」形态，尚无「终端用户运营」形态——MAU 的观测对象（活跃用户）本身不存在。**四缺失情形归属「表不存在」**：修复动作是用户体系建设（触发器②）+ 埋点接入（触发器①）两步走，与 013/020/021/022 调用族共用网关/埋点工程。

### 4.2 语义排障披露（本件方法论价值）

本件两个「看起来能用」的证据均被语义排除，排除依据落产物可复验：其一，dev sys_log 有 create_time/create_by 可按月去重——但操作人全为 admin 级（月去重 ≤4 人），是运维登录日志非用户活跃；其二，久新 community_member 名字带 "member"——列级 DESC 一步定性为图社群节点归属表。「词族命中 ≠ 语义命中」的双关核查（表名关 + 列名关）是本批负结论件的标配动作。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 埋点/访问日志接入（用户标识×时间戳） | 前端+网关工程 | 本件 + 013/020/021/022 族 | 触发器①（族级共用） |
| 终端用户注册面 | 用户体系工程 | 本件分母侧 + 023 主体族 | 触发器②（注册数可算、活跃仍缺） |
| UI 暂无数据态 | 展示规范 | 本件 | mock 3,456 建议替换为「暂无数据」 |

档位后果：埋点接入 → **完全直接支持**；仅注册面 → **部分支持**（只能报注册用户数，口径披露「非月活」）；现状 → 完全不支持。推荐顺序：埋点先行（注册面未建期间可用匿名设备 ID 口径先行统计），用户体系随平台运营化推进。
