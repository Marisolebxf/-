## 摘要

「主题库总数」是主题视窗统计概览四卡之首（`ThemeWindow.jsx:387`，mock 28 个），为管理者回答「资源中心建了多少个主题库」。三份需求真源（主需求/核增/算法库及 SRS 数据资源分册）命名检索 0 命中——它不是需求明列叶，是主题视窗「主题库分类展示」（seq 368）功能的 UI 派生概览读数。数据侧：库数盘点三源结构+数据双在（dev 16 schema 542 表、gkx 单 schema 280 表、久新单库 ads_*），但「主题库」语义的登记面（库×主题×来源的资产目录）三源缺位——theme/subject 词族 0 命中，唯一 domain 类命中 `gkxlumenx_dim.tech_domain` 实测 10 行技术领域维表（语义排除），库级登记面合计 8 条样例级。mock 侧另有硬伤披露：UI StatCard 硬编码 28 与 mockData `themeDatabases` 实际 7 个库对象不一致（演示框架自身失配）。判**部分支持**：库数读数可交付、主题语义需资产目录立项。脚本已跑通，产物与正文数字逐一对应。

- 需求判定：**UI 派生读数**（三份真源 0 命中；seq 368「主题库分类展示」是功能行为非计数指标）。
- 复现状态：脚本已跑通；三源库级盘点读数 + 词族排除探针 + mock 失配披露全落产物。
- 档位结论：**部分支持**（库数可数 + 主题语义登记面缺位）。
- 关键事实：UI 硬编码 28 vs mock 实际 7 库——演示框架自身失配，正式版数值空缺待登记面回填。
- 升档路径：建主题库资源登记面（触发器①）→ 完全直接支持；接受 schema 级近似口径（触发器②）→ 完全转换支持。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/主题视窗/数据资源展示/主题库分类浏览（1.1.1.1.4.4.3.1.1；SRS seq 368-372 五叶；主需求 :2701-2733）。UI 实际容器是主题视窗页首的统计概览行第一张卡：`ThemeWindow.jsx:387` `<StatCard title="主题库总数" value="28" unit="个" trend={{ type: 'rise', value: 8.3 }} />`——四卡 siblings 依次为主题库总数 28 个/数据表总数 1,248 张/总记录数 10.2 亿条/存储总量 18.6 TB（全部硬编码演示值）。卡下方的主内容区才是需求明列的功能面：左侧主题树（科技要素/领域主题/文献计量/科技情报四分区分类浏览）、中部数据库卡片列表（消费 mock `themeDatabases` 7 库）、右侧库详情（六元组元数据 + 数据表数/记录数量）。本件 StatCard 是浏览功能的概览入口读数：用户在进主题树之前先看到「资源中心规模」的第一印象数字。

### 1.2 为什么需要本指标

主题视窗的核心任务是「按主题组织数据资源」（分类浏览→多维筛选→资源分布→详情下钻），「主题库总数」是这个组织体系的规模锚：它是资源建设的成果指标（建了多少库）、也是检索的期望管理指标（用户知道有 28 个库，浏览和筛选才有边界感）。与同窗的「数据表总数」「总记录数」构成规模三卡（数量级从库到表到记录），管理者的资源建设汇报、用户的资源发现导航都以它为起点。国家实践对应物是国家科学数据中心体系的数据中心/数据集计数（R1/R2）：20 个国家科学数据中心、中科院体系 155,721 个数据集——「建了多少库」是科学数据基础设施的第一规模读数。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**更严格地说，三份需求真源连指标名都未出现：主需求《科技信息展示系统和科技专题服务系统.md》检索「主题库总数」0 命中（相邻的 :2513「主题库分类展示」/:2705「主题库分类浏览」均为功能行为描述——「支持大数据中心各主题库的数据资源、数据库详情展示」，非库计数指标）；SRS 数据资源分册（总体/接入/主题/应用四视窗）命名检索 0 命中；核增需求与算法库 0 命中。「主题库」的口径（哪些库算主题库？按学科分类？按数据类型？）与「总数」的统计边界（含在建？含下线？）均无定义。

### 1.4 类似指标权威方法可行性分析概要

「主题库/数据中心总数」的权威计数先例分三层。其一，国家科学数据中心体系（R1）：官方口径按**中心**计数（20 个国家科学数据中心）+ 数据总量口径（270PB，2025 年 9 月），中心的认定有正式批复程序——计数对象是制度实体不是库表集合；其二，中科院科学数据中心体系（R2）：体系页实时显示 1 个总中心 + 18 个学科中心 + 16 个所级中心、155,721 个数据集、184.42PB——「中心×数据集」两级计数，中心是组织实体、数据集是登记单元；其三，数据治理工程口径（库表盘点）：以元数据目录（information_schema/资产目录）为计数面，schema 即「库」的最小承载。方法族对照：

| 方法族 | 计数对象 | 认定机制 | 与三源匹配 |
|---|---|---|---|
| 国家中心体系（R1） | 中心（制度实体） | 批复认定 | 无（本库无中心建制） |
| 中科院体系页（R2） | 中心+数据集两级 | 体系登记 | 部分（数据集级可类比） |
| 库表盘点（工程口径） | schema/库 | 元数据目录 | **三源双在**（本件交付） |
| 主题库登记（需求语义） | 业务主题库 | 资产目录 | **无**（待立项） |

结论：需求语义（28 个业务主题库）需要资产目录承载，三源缺位；工程近似口径（schema 数）三源可数但语义有损。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

口径 B（工程近似盘点）的方法选**库表元数据盘点**（中科院体系页 R2 的数据集计数形态的最小工程落地）：以 information_schema 为计数面统计 schema 数与表数。选择理由：其一，盘点面三源结构+数据双在（§2.2-2.4），零工程即期可交付；其二，schema 是数据库引擎层面「库」的权威承载（MySQL schema 即 database），工程语义无歧义；其三，口径 A（登记面）缺位已由 absence_probe 留证（§3.3），不悬空。风险随行披露：schema 数与业务主题库数无一一映射关系，读数语义有损（§2.5）。

### 2.4 久新盘点读数（结果面单库）

久新 `gkx_technology_analysis_dev` 单库（`jiuxin_db_count`=1）ads_* 表清单（`jiuxin_table_count`，2026-11-01 探测日 210 张，活库上游持续加表不写死总数）。theme/subject 词族命中 `ads_emerging_topic_*` 等主题分析结果面（`jiuxin_theme_like_tables`）——是「主题内容分析」的产出表（新兴主题快照/年度指标），不是「主题库登记」语义，语义排除。

### 2.5 稳健性与口径敏感性

口径 B 的三点敏感性：其一，**schema↔主题库映射不唯一**——16 schema 里 gkxlumenx_pay（支付）/gkxlumenx_job（调度）明显不是主题库，若按「业务语义 schema」再筛（如仅 dwd/ods/ads/topic 四类）可得 4-5 个「数据类 schema」，但筛选规则本身无需求依据（B10 不擅自定口径）；其二，**三源库数不可加总**——dev 16 + gkx 1 + 久新 1 = 18 是「三源实例数」不是「主题库数」（同一批数据可能多源冗余存储，加总会重复计数）；其三，**mock 28 的口径无解**——mock `themeDatabases` 仅 7 库（156+234+189+128+112+145+98=1,062 表，`mock_tables_sum`），UI 硬编码 28 无任何数据面来源，两数失配说明前端演示值本身未经数据侧对账。三源读数并列登记不做加总（产物 `derived[0]` note 写死）。

### 2.6 需求符合性预评

## 四、数据缺失情况

### 4.1 主题库登记面缺位（结构级，主因）

「主题库总数」的语义锚（四分区×资源库的资产目录：库×主题分区×来源×表数×状态）在三源均无承载。这不是数据量问题而是**登记体系缺位**：库内有 542+280+210 张表的数据实体，无「哪些表构成一个主题库」的组织登记。国家实践（R1/R2）的计数对象都是**制度实体**（批复认定的中心/体系登记的中心），本项目的「主题库」尚无对应认定机制。修复动作：资产目录立项——建议以 mock 四分区为初始框架（科技要素/领域主题/文献计量/科技情报），从 information_schema 出发生成初始目录（库×表×语义分类），再由业务侧认定主题库边界。

### 4.2 库级登记面样例级（数据级，次因）

`gen_datasource_conf` 0 行 + `jimu_report_data_source` 8 行——与 542 表体量严重失配（族级缺口，与 DATAOV_001/DATAOV_002/DATAIN_001 同根）。这是数据资源族（本批 L2 组 5 件）的最大公约数缺口：**资源接入台账/资产目录从未系统建立**。回填路径与 DATAOV_001 §4.2 同法，不重复立项。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 主题库资产目录立项 | 数据工程 | 本件 + DATATHM_036/030 | 触发器①（库×主题×来源×表数） |
| schema 近似口径随行披露 | 口径裁定 | 本件 | 触发器②（16/1/1，语义损失披露） |
| mock 演示值对账 | 前端工程 | 本件 + 同窗三卡 | 28 vs 7 失配修正 |

档位后果：资产目录建成 → **完全直接支持**；schema 近似口径获认 → **完全转换支持**；现状 → 部分支持。推荐顺序：资产目录先行（族级共用），mock 对账随正式版替换同步。
