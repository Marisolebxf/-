## 摘要

- 需求判定：**UI 派生读数**（指标名 0 命中；seq 373/382 为浏览/筛选功能）。
- 复现状态：脚本已跑通；三源计数 + 备份表分层（gkx 99 张/dev 3 张）+ 双口径合计全落产物。
- 档位结论：**部分支持**（表清单面三源双在 + 资源边界无登记）。
- 关键事实：gkx 备份表占 35.4%（99/280）——任何以「gkx 280 表」为基数的读数都须先剔备份，此发现对族内全部件（004/029/030）的 gkx 侧口径有传导影响。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/应用视窗/数据资源使用情况和详情/使用详情可视化报表（1.1.1.1.4.4.4.2.3；SRS seq 383、excel_row 386）。UI 实际容器是应用视窗「使用详情」区块的统计行首卡：`ApplicationWindow.jsx:1083-1088` `<Statistic title="数据表总数" value={new Set(filtered.map((d) => d.tableName)).size} suffix="张" />`——与字段总数（filtered.length）/关联部门（Set(sourceDept).size）/累计调用（reduce usageCount）并列四卡。数据源是 mock `dataUsageDetails`（`mockData.js:1524`，12 行字段级使用明细）；**值随筛选联动**：`filtered` 是 dataUsageDetails 经多维筛选（表名/字段类型/应用频率/来源部门）后的子集——筛选全开时 6 张（12 行去重），筛选后更少。同窗对照：主题视窗 `ThemeWindow.jsx:388` StatCard「数据表总数 1,248 张」为硬编码演示值——同名指标两处挂载、两个口径（应用窗=使用中的表/主题窗=全库表）、两个值（6/1,248），本件以应用窗挂载为主、主题窗对照披露。

### 1.2 为什么需要本指标

使用详情报表的管理问题是「数据资源到底被用了多少张表」：数据表总数（在用表数）×字段总数（在用字段数）给出使用面的**广度**，累计调用给出**深度**，四卡合起来回答「资源中心的资产有多少在被消费」。需求 seq 383 原文「所有数据资源使用情况均以可视化方式展现」——表数是使用情况的空间维度基底。它与主题视窗的全库口径（1,248 张演示值）形成「存量 vs 流量」的对照：全库表数是资源建设存量，使用中的表数是消费流量——mock 作者把两个口径分开挂载是符合数据资产管理常识的设计（正式版应统一数据源）。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**指标名「数据表总数」三份真源 0 命中。主需求 :2733「支持浏览每个数据集下的数据表结构，详细列出表名、字段名、字段类型、字段含义及必填/可选信息」（SRS seq 373）是结构浏览功能；:2787「支持按数据表名称、字段类型、应用频率、来源部门等多维条件筛选」（seq 382）是筛选功能——两处「数据表」都是操作对象不是计数指标。计数口径（全库表数还是使用中表数？含不含配置/备份表？）无定义。

### 1.4 类似指标权威方法可行性分析概要

「数据表总数」的权威对应是数据资产盘点中的**物理表计数**。其一，国家科学数据中心体系（R2）：155,721 个数据集——**数据集**为登记单元（逻辑资产），不以物理表计数（物理结构是实现细节）；其二，数据治理框架（DAMA/DCMM）：资产盘点以**数据资产目录**为准（逻辑资产清单），物理表数是目录的技术底账——两者需映射；其三，数仓工程惯例：分层计数（ODS/DWD/ADS 各层表数）+ 剔除规则（临时表/备份表 `_bak`/`_tmp` 不入资产账）。方法族对照：

| 方法族 | 计数单元 | 剔除规则 | 与三源匹配 |
|---|---|---|---|
| 数据集登记（R2） | 逻辑数据集 | 目录裁定 | 无目录（待立项） |
| 资产目录盘点（DAMA） | 资产条目 | 目录裁定 | 无目录 |
| 数仓分层计数（工程） | 物理表 | 剔 tmp/bak | **三源可算**（本件交付） |
| 全物理表直计 | 物理表 | 无 | 三源可算（污染披露） |

结论：数仓工程口径（分层+剔备份）三源即期可算，逻辑资产口径（数据集/目录）无承载。完整版见附录 C。

## 二、计算过程

### 2.1 方法选择（文献依据）

方法选**数仓分层计数+备份剔除**（工程惯例口径，R2 数据集计数的物理底账形态）：三源表清单聚合，备份表（bak/v3bad/tmp/copy 词族）单列剔除口径。选择理由：其一，表清单面三源完整（快照+本件复核）；其二，备份表污染量级重大（gkx 35.4%）不剔除会严重虚增读数；其三，逻辑资产口径（数据集目录）无承载，物理口径是最小可交付。配置 schema 剔除（dev 6 个配置库 98 表）作为第三层口径选项保留（不擅自定案，B10）。

### 2.2 dev 表计数与分层（快照+复核）

dev `gkxlumenx_*` 16 schema 542 表（`dev_table_count_all`）：**数据类 schema 444 表**（`dev_data_schema_table_count`：gkxlumenx 主 28/ads 96/app 9/cms 36/dim 18/dwd 144/mp 6/ods 75/topic_enterprise 21）+ **配置类 schema 98 表**（`dev_config_schema_table_count`：bi 41/codegen 9/config 12/flow 10/job 21/pay 5——语义为报表/调度/支付配置面，非数据资源）。备份/临时表 3 张（`dev_backup_like_tables_sorted`）：`gkxlumenx_bi.tmp_report_data_1`/`tmp_report_data_income`/`gkxlumenx_flow.process_copy`。

### 2.3 gkx 表计数与备份表发现（关键实测）

gkx 280 表（`gkx_table_count`，本件 SHOW TABLES 复核与快照一致）。**备份/坏表词族（bak/v3bad/_tmp/copy）命中 99 张**（`gkx_backup_like_table_count`，全清单 `gkx_backup_like_tables_sorted`）：命名模式 `bak_YYYYMMDD` 三轮——bak_20260911（金融证券族为主：港股/美股/期权/基金）、bak_20260912（物质/化学/材料族）、bak_20260923（学者/机构/政策/医药族），另 v3bad 3 张（`dwd_en_report_v3bad`/`dwd_medical_company_v3bad`/`dwd_scholar_papers_v3bad`）。**gkx 正表 = 280 - 99 = 181 张**。空表 10 张（`gkx_zero_table_count`，复用 DATATHM_030 逐一 COUNT 产物：fund 族 8+rd 族 2，其中 3 张本身是 bak）。此发现的口径含义：族内此前以「gkx 280 表」为基数的读数（004/029/030）在资产语义下应收窄为 181 正表（各件敏感性披露已交叉引用本件）。

### 2.4 久新表计数（快照，探测日读数）

久新 ads_* 210 表（`jiuxin_table_count`，lane7 快照 B11 锚；活库连接失败 2 次已登记，读数走快照）：非空 206 张（`jiuxin_nonzero_table_count`）+ 空 4 张（`jiuxin_zero_table_count`：ads_geo_yearly_index/ads_talent_institution_cooperation/ads_technology_bottleneck_evidence/ads_technology_policy_evidence）。备份词族 0 命中（ads_* 命名规范统一，无 bak 污染）。

### 2.5 稳健性与口径敏感性

三层口径敏感性：其一，**备份表剔除的边界**——gkx 99 张 bak 是否全剔除？bak 与正表数据同构（备份时点快照），资产语义下应剔（避免同数据双计）；但若正表在备份后被更新/清理，bak 可能是唯一完整快照（fund 族正表 0 行而 bak 也是 0 行——本例不存在该问题）。其二，**配置 schema 的语义裁定**——dev 98 张配置表（bi/codegen/config/flow/job/pay）语义上不是「数据资源」，但 app/cms/mp 等业务库含真实业务数据（app_article_collect 等），一刀切剔除会误伤——本件数据类/配置类分层交付不擅自定裁（B10）。其三，**空表处理**——14 张空表（dev 311 张空表未单列因 dev 全口径含之；gkx 10/久新 4）结构存在但无数据，「表总数」是否计入取决于「结构资产还是数据资产」的语义选择。多口径并列：全口径 1,032 / 剔备份 930（另剔配置则 832，未单列因配置边界未裁）。

### 2.6 需求符合性预评

## 四、数据缺失情况

### 4.1 资源白名单缺位（结构级，主因）

「哪些表算数据资源」的白名单登记（资产语义标记）三源缺位——配置 schema（98 表）、空表（14+311 dev 估算空表）、备份表（102 表）的剔除规则无登记依据。族级缺口（与 DATATHM_004/029/030 共用），本件的特异性贡献是把**备份表污染**量化到表级（gkx 99 张清单在产物）——白名单立项时可直接以本件分层清单为底稿（数据类 444+181+206=831 张候选）。

### 4.2 使用明细无承载（应用窗口径缺口）

应用窗挂载的语义（被使用的表数）依赖消费流水（哪个系统调用了哪张表），三源无承载（S3-03 DATAOV_002 已结论：接入流水台账三源未立项）——mock 12 行是唯一「使用明细」形态。此缺口不阻断存量口径交付（主题窗语义），但阻断使用口径：应用窗卡在正式版要么改挂存量口径（值=930/831），要么等运营监控立项。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |

| 资源白名单登记面 | 数据工程 | 本件 + 004/029/030 族 | 触发器①（底稿=本件分层清单） |
