- 复现状态：脚本已跑通；列级新探针 + 019 全套复用落产物。
- 档位结论：**完全不支持**（数值周期三源零承载+枚举层无登记列）。
- 关键事实：46 列命中 0 张可用——「频率」一词在库内大量出现（stat_period 23 列）但全是「统计期间」业务语义；「资源多长时间更新一次」这件事在任何一张表里都没有登记，元数据治理缺位。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源·主题视窗（库详情六元组+导出）与接入视窗·资源接入明细查询（挂靠 seq 361 历史更新周期统计与分析）。UI 实际挂载（派单 mount 三行，实查确认）：①`ThemeWindow.jsx:368` detailItems「更新频率」`<Tag color="cyan">{selectedDatabase.updateFreq || '—'}</Tag>`（seq 371 六元组+seq 372 扩展属性项）；②`ThemeWindow.jsx:605` 导出 sheets「数据库基本信息」fields「更新频率」列（`dataIndex: 'updateFreq'`）；③`AccessResourceDetailQuery.jsx:124-129` 表列「更新频率」（cyan Tag + `updateFreqSortRank` 排序器，`:20-22` 常量 `UPDATE_FREQ_ORDER = { 实时: 0, 每日: 1, 每周: 2, 每两周: 3, 每月: 4 }`，未知值 99 兜底）。mock 语义源 `mockData.js` 26 处 updateFreq 赋值（资源卡 7 + 明细 rad-* 5 + 主题库 14 处）。mock 结构披露：全部为五档文本枚举（每日/每周/每月/实时/每两周），无一处数值周期。

### 1.2 为什么需要本指标

更新频率是资源供给方的**服务承诺读数**：管理者按频率档位判断资源新鲜度（实时期资源断流 1 天即告警、月更资源容忍 35 天）；seq 361 的三件套（更新频率/更新时间点/周期变化趋势）是「资源维护规律与实时性」管理的入口。权威对应物：数据目录的 updateFrequency 元数据字段（DCAT/GB/T 2403 目录规范——枚举档位形态）；调度系统的 cron 周期（Airflow schedule_interval——数值形态）；GB/T 36344 数据质量框架的时效性维度（R1）。

### 1.3 需求文档是否给出定义方法

**指标名级三份真源 0 命中。**seq 361 功能句：「通过时间序列分析技术，能够精准统计并展示各渠道、数据表的历史更新周期，包括更新频率、更新时间点及周期变化趋势」——「更新频率」功能词在，但：数值口径（周期=相邻更新间隔均值？P50？分布？）与枚举口径（五档分界：实时/每日/每周/每两周/每月的边界定义）、统计对象（渠道级/表级/资源级）均无定义。UI 的五档枚举只来自前端常量（`UPDATE_FREQ_ORDER`），不构成口径证据。核增需求与算法库 0 命中（附录 A.2）。

### 1.4 类似指标权威方法可行性分析概要

「更新频率」的权威方法锚分三层。其一，数据目录元数据（R3，W3C DCAT/GB/T 2403）：`dct:accrualPeriodicity`（更新周期）标准字段——枚举档位（连续/日/周/月/年…），目录登记即得，是 UI 枚举层的正对应物；其二，调度系统（R2，Airflow）：`schedule_interval`（cron 表达式）——任务级数值周期，从调度配置直读；其三，实测法（数据质量框架 R1）：相邻数据版本时间戳间隔序列的统计量（均值/P50/分布）——不依赖声明，从留痕反推。方法族对照：

| 方法族 | 代表 | 原料 | 与三源匹配 |
|---|---|---|---|
| 目录元数据登记 | R3（DCAT/GB 2403） | updateFrequency 字段 | **无登记列**（46 列排除） |

| 留痕实测 | R1（质量框架） | 版本时间戳序列 | **无序列**（es_sync 单笔） |
| 前端演示 | UI mock 枚举 | mock 26 条 | 文本常量（不作源） |

结论：三层方法（声明/配置/实测）的原料在三源全部缺席——这不是「有数据没算好」而是「这件事从未被登记」。完整版见附录 C。

### 1.6 推测原意与推测定义（含降档/升档触发器，B10 模板）

**推测定义（双口径并列，须披露未裁定）**：

枚举层（UI 对应形态）：

$$F_{\text{enum}}(r) = \text{档位}\left(\bar{\Delta}_r\right),\quad \text{档位} \in \{\text{实时}, \text{每日}, \text{每周}, \text{每两周}, \text{每月}\}$$

数值层（指标名对应形态）：

$$\bar{\Delta}_r = \frac{1}{n-1}\sum_{i=2}^{n}\left(t_i - t_{i-1}\right),\quad \{t_i\} = \text{资源 } r \text{ 的更新时刻序列}$$

**前提是更新时刻序列（≥2 点）或登记列存在，三源实测均无**（§3.3）——es_sync 单笔水位连一个间隔都算不出。公式列示仅作口径锚（F4：本件 §二 从缺）。

**降档/升档触发器（B10 模板）**：①资源元数据表加 update_freq 登记列（5 档枚举，随资源登记）→ 升**完全直接支持**（枚举层）；②es_sync/同步任务改逐次留痕（每模块≥2 时刻）→ 升**完全转换支持**（数值层，均值/分布双口径可算）；③维持现状 → 完全不支持（UI Tag 显示「—」；末笔月分布可作即期参考、标签「非周期读数」）。

## 四、数据缺失情况

### 4.1 资源元数据登记列缺位（结构级，判定性缺口）

枚举层的正对应物是目录元数据的 updateFrequency 字段（DCAT `dct:accrualPeriodicity`——R3 标准字段）。dev 46 列词族全业务语义、gkx/久新 0 命中——「资源多长时间更新一次」在三源任何一张表都没有登记。**四缺失情形归属「结构不存在」**：修复动作是资源元数据表加 update_freq 列（5 档枚举对齐 `UPDATE_FREQ_ORDER`），随资源登记流程落地——DCAT/GB 2403 目录规范的标准做法（一列登记，枚举层即完全直接支持）。

### 4.2 更新时刻序列缺位（序列级，数值层缺口）

数值层要求每资源≥2 个更新时刻（§1.6）。es_sync 单笔覆盖式设计（只留水位）+xxl 调度空载（0 行）——序列面不存在（019 同锚）。修复动作：同步任务逐次留痕（与 019/043/044 共用触发器）。备选轻量路径：登记列落地后由供给侧声明（不实测）——牺牲真实性换可行性。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 资源元数据表加 update_freq 登记列 | 元数据工程 | 本件（枚举层直达） | 触发器①（5 档对齐 UPDATE_FREQ_ORDER） |
| 同步逐次留痕 | 数据工程 | 本件 + 019 + 043 + 044 | 触发器②（数值层，运行日志族共用） |
| 枚举档位边界裁定（每两周=14±?天） | 口径裁定 | 本件枚举层 | 随登记列落地一并裁定 |
| UI Tag「—」暂无数据态 | 展示规范 | 本件 | mock 枚举替换需数据面 |

档位后果：登记列 → **完全直接支持**（枚举层）；留痕 → **完全转换支持**（数值层）；现状 → 完全不支持。推荐：登记列即期（一列成本，枚举层直达），留痕随运行日志族主线。
