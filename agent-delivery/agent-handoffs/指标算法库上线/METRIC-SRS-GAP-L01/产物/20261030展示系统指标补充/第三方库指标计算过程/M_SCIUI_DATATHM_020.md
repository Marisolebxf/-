## 摘要

「接口平均响应时长」是总体视窗应用系统状态监控卡的「平均响应」读数（三份需求说明书无此指标名，语义锚在 :2559/:2563 的「接口响应速度」功能分句），UI mock `resourceUsageStats.avgResponseTime` 给常量 245 ms。数据侧判定核心是 API 调用耗时日志面存在与否：三源词族逐一排除（dev 542 表 0 张/gkx 280 表 0 命中/久新 210 表 live 复核 0 命中）。最近邻证据 dev `sys_log` 虽有 time 耗时列（1,060 行全有效、均值 542.92 ms、Top 耗时簇 134-139 ms），但请求 URI 分布证明它是平台认证管理日志（`/oauth2/token` 1,052 行占 99.2%）——登录 token 刷新的耗时与「数据资源接口调用」耗时不同源，语义排除。需求 :2563 自己写明工程前提「通过API日志采集」——前提未建，指标及关键依赖三源均无法构建。判**完全不支持**。脚本已跑通（语义排除证据全落产物），产物与正文数字逐一对应。

- 需求判定：**需求功能分句派生**（:2559/:2563 功能在；「平均响应时长」指标名与算式无）。
- 复现状态：脚本已跑通；三源词族排除探针 + sys_log 语义排除证据全落产物。
- 档位结论：**完全不支持**（API 调用耗时日志面三源零承载，最近邻语义排除）。
- 关键事实：dev sys_log 耗时均值 542.92 ms 是本库唯一真实存在的「耗时读数」，但它是 OAuth2 认证端点耗时（`/oauth2/token` 占 99.2%）——「有耗时列」≠「有接口监控」，这是本件最重要的语义排障。
- 升档路径：API 网关/链路追踪（APM）日志接入 → 完全直接支持（触发器①）；自建探针拨测 → 完全转换支持（触发器②，非调用量加权）。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/总体视窗/资源应用情况·**应用系统状态监控·平均响应**（1.1.1.1.4.4.1.4.1 的「接口响应速度」分句；UI 读数挂 seq 343 语境）。UI 实际挂载是总体视窗侧栏「应用系统状态监控」卡（`OverviewWindow.jsx:713` Card title）内的状态项：`ApplicationStatusMonitor`（`:379` 定义）的 items 数组第一项 `{key:'latency', label:'平均响应', value: '${stats.avgResponseTime} ms'}`（`:385-390`，tone warning 橙色云图标）；同卡并列「异常告警」项与「接口成功率」进度条（`stats.successRate`）、「资源接口状态跟踪」质量条。数据源是 mock `mockData.js:833-839` 的 `resourceUsageStats`：`{totalCalls: 2,856,000, avgResponseTime: 245, successRate: 99.2, alarmCount: 12, alarmCritical: 2}`——mock 注释自标「需规 seq 343：服务可用性 / 接口响应速度 / 异常告警」。mock 结构披露：245 ms 是演示常量，不作数据证据（B10）。

### 1.2 为什么需要本指标

应用状态监控卡回答「资源供得稳不稳」：平均响应看时延、成功率看可用、告警看风险——三读数并排是 APM（应用性能监控）的标准卡面。需求把它放在资源应用情况首位（:2557-2559），定位是数据资源「稳定供给和高效流通」的保障性监控。权威对应物是 API 监控的指标族（R1 GB/T 33850 响应性评价 / R2 云智慧 API 监控 13 指标 / R3 数据接口元数据的「响应时长」字段）：平均响应时间=一段时间内请求响应时间的平均值（不可用请求不计）——工程上要求调用级日志（每次请求的端到端耗时）作原料。本库场景下，该读数要求「数据资源接口」的调用日志存在且含耗时毫秒列——没有日志面，任何耗时读数都无从谈起。

### 1.3 需求文档是否给出定义方法

**三份需求说明书未出现「接口平均响应时长」指标名。**语义锚两处：主需求 :2559（1.1.1.1.4.4.1.4.1 应用系统状态监控）「可实时监控各类数据资源在不同应用系统中的运行状态，包括服务可用性、接口响应速度及异常告警」——「接口响应速度」为功能分句，均值/分位/口径无定义；:2563（1.1.1.1.4.4.1.4.2 资源接口状态跟踪）「通过API日志采集与接口调用分析，动态跟踪每个资源接口的连接活跃度、调用频率和失败率」——**需求自己点名了工程前提（API 日志采集）**，但未建。核增需求与算法库 0 命中（附录 A.2）。UI 的 245 ms 是演示常量，不构成口径证据。

### 1.4 类似指标权威方法可行性分析概要

「平均响应时长」的权威方法锚分三层。其一，国标评价框架（R1 GB/T 33850-2017）：信息技术服务质量模型的「响应性」特性——运行维护服务评价指标含响应及时性类指标（第 8 章），平均口径与分位口径由测量方法规定。其二，API 监控工程口径（R2 云智慧）：平均响应时间=一段时间内某请求响应时间的平均值，**不可用、不正确的不计算**——均值前的可用性剔除是口径硬前提；响应时间=请求结果返回的时间，含 DNS 解析、建立连接、服务器计算、内容下载全链路。其三，数据要素登记元数据（R3）：数据接口描述信息含「响应时长 Response Time」必填字段（接口地址/参数/响应时长三元组）——登记口径（≤300ms 的静态声明）与实测口径（调用日志聚合）分离。方法族对照：

| 方法族 | 代表 | 原料 | 口径 | 与三源匹配 |
|---|---|---|---|---|
| 质量评价响应性 | R1（GB/T 33850） | 服务协议/监控 | 响应及时性 | **无监控面** |
| API 监控均值 | R2（云智慧） | 调用级日志 | 均值（剔除不可用） | **无日志** |
| 登记元数据声明 | R3（数据产权登记） | 接口文档 | 静态声明值 | **无登记面** |
| 前端演示 | UI 245 ms | mock 常量 | — | 结构披露（不作源） |

结论：三条权威路径的原料（监控面/调用日志/接口登记面）三源均无承载——本件是「工程前提未建」型缺口，非数据量不足。完整版见附录 C。

## 四、数据缺失情况

### 4.1 API 调用耗时日志面零承载（结构级，判定性缺口）

平均响应时长的唯一原料是调用级耗时日志（R2：响应时间=请求结果返回的时间，含 DNS/连接/计算/下载全链路）。三源实测零承载（§3.3）——这不是数据量问题而是**监控工程缺位**：数据资源接口的调用从未被网关/链路追踪层记录过。需求 :2563 把「API日志采集」写进功能描述（工程前提自宣），但 dev 库内无对应承载表。**四缺失情形归属「表不存在」**：修复动作是 API 网关日志/链路追踪（APM）接入——本批 021/022（调用量族）与需求 seq 343-344（服务可用性/接口响应/异常告警/调用分析）共用此工程，一次接入族内全升。

### 4.2 最近邻语义排除（方法级披露）

dev `sys_log` 是本库唯一真实存在的耗时读数源（1,060 行/均值 542.92 ms），但语义三层不符：其一，端点性质——OAuth2 认证管理端点非数据资源接口；其二，量级——日均数条管理操作 vs UI 语境的日均万级调用；其三，口径——无接口标识维（不能分接口算）、无可用性标记（不能按 R2 剔除不可用）。三层皆不符故整源排除（B10：542.92 仅作排除披露，不作分子不作对外值）。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| API 网关/APM 日志接入 | 监控工程立项 | 本件 + 021/022 + seq 343-344 族 | 触发器①（族级共用） |
| 自建拨测探针 | 轻量替代 | 本件即期 | 触发器②（主动测延迟，非调用量加权须披露） |
| UI 暂无数据态 | 展示规范 | 本件 | mock 245 建议替换为「暂无数据」 |

档位后果：APM 接入 → **完全直接支持**；拨测探针 → **完全转换支持**（口径披露）；现状 → 完全不支持。推荐顺序：APM 立项为主线（族级三件共用），拨测作即期过渡（标签「拨测延迟」非「平均响应」）。
