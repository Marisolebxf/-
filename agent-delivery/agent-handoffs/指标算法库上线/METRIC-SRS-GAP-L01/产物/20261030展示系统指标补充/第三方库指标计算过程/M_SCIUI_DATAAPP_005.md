## 摘要

- 需求判定：**需求明列叶**（seq 385），追踪粒度（行级 or 聚合）与「实时记录」的落地形态无定义。
- 复现状态：脚本已跑通；调用+三联目录+两库追踪词族排除探针全落产物。
- 档位结论：**完全不支持**（日志 + 用户面运营数据 + 应用登记三依赖均缺）。

## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技数据资源/应用视窗/主题数据被调用情况/调用用户与应用系统追踪（1.1.1.1.4.4.4.3.2；SRS seq 385、excel_row 388）。UI 实际挂载是主题 Tab 第五卡：`ApplicationWindow.jsx:311` Card title="调用用户与应用系统追踪"，Table 列定义 `userTrackColumns`（`:262-268`：用户 userName/部门 department Tag/应用系统 application/访问主题 theme Tag cyan/最近调用 lastCallTime/调用次数 callCount 六列）消费 mock `callUserTracking`（`mockData.js:1733-1741`，8 行，另有 userId/ipAddress 两列 UI 未显示——mock 作者预留了追踪主键与 IP 定位字段）。mock 结构披露：8 用户分属 8 部门、各挂一个应用系统与一个主题、lastCallTime 精确到分钟、callCount 三位数到四位数——这是「按用户聚合」形态（每用户一行，非每次调用一行）。

### 1.2 为什么需要本指标

用户追踪是调用分析的**主体归因层**：001/002 回答「主题被调了多少」，本件回答「被谁调的」——用户名、部门、应用系统三列把调用量归因到组织末梢。需求的用途句写得明确：资源分配与权限控制——谁用得多谁的配额该加，哪个部门在用哪个应用决定了权限包怎么发。与明细表（002）相比：002 是主题维投影（每主题一行），本件是用户维投影（每用户一行）；两者共享同一份调用日志，是「主题面/用户面」一对。IP 列（mock 预留）暗示追踪还有安全审计用途（异常调用源定位）——这在权限控制语义里是天然诉求。

### 1.3 需求文档是否给出定义方法

### 4.1 日志+用户面运营数据+应用登记三缺（结构级+数据级，判定性缺口）

追踪卡的依赖链比主题维投影（001/002）多一层**目录运营化**：调用日志（族级共缺）之上，还要运营用户目录（3 测试账号 disqualified）与应用登记面（oauth 语义排除）。本件的特殊性在于它是 DATAAPP 族里唯一**结构在但数据 disqualified** 的件——`sys_user`/`sys_dept` 表存在、字段齐（dept_id 关联在），但内容是框架预置而非运营数据。这意味着修复动作分两类：日志接入（建表工程）+ 目录运营化（启用/导入既有表）。四缺失情形归属：D1/D4 表不存在；D2 表存在数据不可用。

### 4.2 追踪粒度与部门归属口径未裁（口径级）

两个口径缺口：其一，追踪粒度——按用户一行（mock 形态）会丢失「用户跨应用/跨主题」的分布，按用户×应用×主题展开则行数膨胀（需分页+筛选策略），需求未裁；其二，部门归属——用户主部门（静态）or 调用时部门快照（动态）：人员调岗后历史追踪行的部门归属会随口径不同而漂移，权限控制场景（本件用途句）要求可追溯，倾向快照口径但需求未言明。两口径在日志建成后仍须裁定，建议随日志工程一并出口径单。

### 4.3 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 调用日志接入（含用户/应用/主题标识） | 监控工程立项（族级） | 本件 + DATAAPP 族全部 | 触发器① |
| 运营用户目录启用（sys_user 扩容+部门映射核准） | 运营数据工程 | 本件 | 结构在，数据待运营化 |
| 应用登记面（业务系统目录） | 数据工程（轻量） | 本件 + 002 | 002 同建议共用 |
| 追踪粒度+部门归属口径裁定 | 口径裁定 | 本件 | 随日志工程出口径单 |
| UI 暂无数据态 | 展示规范 | 本件 | mock 8 行建议替换 |

档位后果：三件齐备 → **完全直接支持**；网关用户日志先行 → 分步升档；现状 → 完全不支持。推荐顺序：网关用户日志先行（日志带用户/系统标识即可启算）→ 目录运营化并步 → 口径单随发。
