## 一、需求定义概述

### 1.1 所属功能模块

智能服务集群/科技信息展示系统/科技政策跟踪/**多维政策对比**·规划指标库·适用范围维。UI 实际容器是 PC 端政策对比页的**规划指标库**（`policyPcData.js:299` 四维注释）：`planningMetricLib` 数组第 5 位 `pm5`——`{ name: '示范场景开放数', dim: '适用范围', unit: '个', sample: '30', scope: '重点行业应用场景', validity: '2026 年度清单', applyCond: '场景主管部门联合认定' }`（`:343`）。消费方有两个：mock 政策 pol-ai-2026（AI 产业政策）的详情卡 metrics 引用（`:419`：`{ key: 'm3', libKey: 'pm5', name: '示范场景开放数', value: '30', unit: '个', dim: '适用范围', kind: '时间节点' }`）与同一政策的条款树（`:411`：`c3-1 第五条 首购首用与示范场景清单`——场景清单作为政策条款的组成部分）。pm5 是规划指标库 5 槽中唯一挂「适用范围」维的件——场景开放数度量的是政策惠及面的**供给规模**（开放多少个场景供企业参与），与扶持力度维（pm1/pm3/pm4 的资金强度）构成对比视角。

### 1.2 为什么需要本指标

场景开放是近年科技政策的核心供给工具：政府开放政务/行业应用场景（首购首用/揭榜攻关），让新技术有落地试验田——「给场景」被视为与「给资金」同级的政策供给。开放场景数直接度量场景供给规模：对比两条产业政策，「开放 50 个场景 vs 补贴 1 亿元」是供给工具类型的比选读数。放多维政策对比语境，本指标是**适用范围维的量化锚**：pm5 的 applyCond「场景主管部门联合认定」与 validity「2026 年度清单」说明 UI 作者理解其清单属性（年度发文、联合认定、条目制）。它的政务对应物是各地场景清单年度发文（R1-R4），清单本身是政策附件或独立发文形态。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。**三份需求真源检索记录：主需求与 SRS 政策族无「示范场景/场景开放」指标名；核增需求「场景」4 处逐一核对均为**使用场景语境**（「系统使用场景」「政策解析适用场景」——展示层定位与政策解析功能描述），非场景开放指标；PC-04 四维框架是维度语义源。export 行归类无线索——实义以 UI 槽位为准：pm5 的 unit '个' + validity '2026 年度清单' + applyCond '场景主管部门联合认定'——即「年度场景清单开放的示范场景条目数（个）」。

## 二、计算过程

### 2.1 方法选择（文献依据）

清单类指标的权威口径是**条目级台账计数**（南京 1000 个/年的清单台账形态，R2；科技部常态化机制，R3）——不是统计估算而是清单枚举。本件方法链分两段：**台账对接段**（正路——各地清单发文/平台 API 解析为条目级台账，计数平凡）与**文本抽取段**（弱代理——「开放N个场景」表述抽取，量窄且受收录窗限制）。两段式的选择理由：台账对接需外部数据源立项，文本抽取是库内即可启动的过渡路径，双路径并行披露供甲方选择。

### 2.2 gkx 文本面盘点（弱代理的边界）

全文本（title+theme+content+keywords+keypoints 五字段拼接）四层扫描：**泛词层**——「场景」命中 **311 行**（占全表 20,000 的 1.555%，派生键 `changjing_text_share_pct`）；**精确层**——「示范场景」**5 行**、「场景开放」**7 行**；**数量层**——「N个…场景」数字表述 **16 行**；**语境层**——「应用场景」**173 行**（应用层语境，多为技术落地叙述非政策开放承诺）。

具名样本（`gkx_text_shifanchangjing_sample` 5 行全量）：北京市氢能技术应用试点示范项目征集通知（2021）、天津车联网产业发展行动计划（2019）、制造业产业链供应链现代化实施意见（2021）、中关村海外人才创业园建设意见（2021）、河北省数字经济发展规划 2020-2025（2020）——5 行均为**试点示范项目/规划语境**（征集试点、产业发展规划中的示范工程建设），不是「开放 N 个场景」的清单发文形态——精确层命中里真正的场景清单发文为 0。

### 2.3 时间错期的形态证据

## 四、数据缺失情况

### 4.1 场景清单台账缺失（结构级，主因）

「政策/清单→开放场景数」的条目级台账在三源均不存在（gkx 无表无列、dev 无落位、久新案例面语义错位）。这是**供给侧清单**缺口——与 Lane 1 兑现事件族（政策×企业享受台账，需求侧兑现）不同物：清单是政策发文自带的附件（供给侧），兑现是政策执行产生的事件（需求侧）。修复动作：各地清单发文对接（R1-R4 官方源）+ 附件解析（清单表格抽取）→ dev 侧落地 `policy_scenario_list` 类台账表。

### 4.2 时间窗错期（源级）

库内政策收录窗截止 2022，而场景开放政策潮是 2023+（R1-R4 均为 2024+ 发文）——即使文本抽取完美，现行清单读数仍在库外。修复：清单对接路径天然绕开此限（直接对接现行发文）；文本代理路径则永久受限（只能覆盖 2022 前试点示范叙述）。

### 4.3 邻接案例面语义甄别（方法级）

久新 `ads_technology_application_case`（181,735 行）是本件最大的**误采风险**：表名 application case 与「应用场景开放」字面邻接，但语义是技术商业化案例（技术→案例关联）。若误采会得到 181,735 的「场景数」——与清单口径（年度几十个）量级即证错位。本件在 §2.4/§3.3 双处留证不采；后续若建台账，该表可作「技术落地案例」辅助面但不得作清单本体。

### 4.4 修复建议与影响面

| 建议 | 类型 | 影响指标 | 说明 |
|---|---|---|---|
| 场景清单发文对接 + 附件解析 | 外部数据源 | 本件 | R1-R4 官方源，条目级台账 |
| 场景发布平台 API 对接 | 外部数据源 | 本件 | 政府平台直达 |
| 文本弱代理读数（过渡） | 转换工程 | 本件 | 16 行数量表述抽取，随行披露局限 |

档位后果：清单对接落地 → **完全转换支持**（计数平凡）；仅文本代理 → 维持部分支持（读数语义弱+错期限定随行披露）。推荐：清单对接立项为主。
