## 摘要

「企业实体识别构建」在原设计里是一条 NER 管道：从新闻文本里识别企业名、归并别名、连成图。库内没有这条管道，也没有 `graph_node` 结果面，所以本件做的是**它的结构化底座**：用工商主档建节点，用投资与股东关系建边。

实测 189,116 个节点、117,001 条边（投资 46,967、股东 70,034）。图的形状很极端：3,605 个连通分量，最大一个 10,462 家，第二到第五名只有 20、20、19、17 家；孤立节点 169,341 个，占 89.54%。也就是说，这张图是「一个大核心 + 大量孤岛」，不是一个均匀网络。

属性覆盖上，名称/城市/企业类型/行业一级都是 100%，成立年 99.81%，专利 64.81%，而「有任意关系边」只有 10.46%。这个数字比孤立率更直白：近九成企业在图里没有任何连接。

结论是「部分支持」：结构化图能建、指标能算、结构可解释；文本 NER、实体链接、节点权重、标注集评估四样都没有。没有这四样，它就不是「实体识别」，只是「关系表转图」。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业服务 → 企业图谱 → 实体库**。页面形态是关联网络图 + 节点详情卡：点一家企业，展开它的投资与股东邻居。

它是图谱类指标的底座，不直接面向业务结论。上游的 centrality、关键节点、协同关系都依赖这张图，所以它的口径稳定性比单指标更重要。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业服务 → 企业图谱 → 实体库 |
| 页面载体 | 关联网络图 + 节点详情卡 |
| 输出形态 | 节点表 + 边表 + 图统计 |
| 更新频率 | 建议季度 |
| 粒度 | 企业（org_id） |

### 1.2 为什么需要这个指标

实体库是所有图谱分析的前提。没有统一的节点与边，中心度、社区发现、关键节点识别都无从谈起。它本身不是结论，但它决定了后面所有结论的可信度。

第二个用途是消歧。同一家企业在新闻里可能叫「华为」「华为技术」「HUAWEI」，在工商里只有一个 org_id。实体链接就是把这些写法收敛到一个节点。本件没做这一步，所以节点只来自主档。

第三个用途是发现隐性关联。投资与股东关系是显性的，但两家企业可能通过同一个有限合伙、同一个自然人连接。图建起来之后，这类「二跳关联」才能被查出来。

### 1.3 需求文档是否给出定义方法

**需求文档给了管道定义，但没给节点权重与验收标准。** calc-logic 写的是：

> 企业实体识别：从企业主档与新闻文本中抽取企业实体，构建企业关系图，节点带权重。

「从新闻文本抽取」这一半做不了：没有 NER 模型、没有别名词典、没有标注集。本件只做了「从主档抽取」这一半。节点权重也没有——`graph_node.weight` 不存在，本件用度替代，并在产物里把这一点写进 `proxy_deviation`。

### 1.4 类似指标权威机构构建方法可行性

实体识别与实体链接在图谱工程里有成熟的方法族：规则词典、统计 NER、深度学习 NER、以及基于嵌入的实体链接。它们的共同前提是有标注数据或大规模别名词典。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 规则/词典匹配 | 企业名库 + 后缀规则 | 按全称/简称匹配 | 本件采用（仅主档） | 中（无文本召回） |
| B 统计 NER（CRF） | 学术界/工业界 | 字符+词性特征序列标注 | 需标注集 | 中 |
| C 深度 NER（BERT） | Google/哈工大 | 预训练 + 微调 | 需标注集与算力 | 低（本批无） |
| D 实体链接（嵌入） | Facebook/阿里 | 向量相似 + 消歧 | 需别名词典 | 低（本批无） |

**A 族是本件采用的方法**，而且只用了主档全称：不做简称匹配、不做别名归并。这是「能建图」与「能识别」的分界线。

**B/C 族**需要标注集。没有标注集，NER 的准召无法评估，做出来也无法验收。本批没有标注资源，所以不做。

**D 族**需要别名词典或向量库。库内没有企业别名表，`dwd_org_base_info` 只有法定名称，所以链接也做不了。

### 1.5 引用来源

1. 项目内 calc-logic V2：`M_ENT_GRAPH_108_1.md`。

2. 国家标准：企业信用信息公示数据规范。https://www.samr.gov.cn/

## 二、计算过程

### 2.1 总体思路与数据流

主档出节点，关系表出边，属性表补字段，并查集算连通分量，度分布刻画形状。整条链没有模型，全是结构化操作。

这样做的原因是：结构化关系是确定的，不需要预测；文本抽取才需要模型。把确定的部分先做完，图的骨架就立住了，后面接 NER 只是往骨架上挂新边。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 节点 | 主档 | DISTINCT org_id | 189,116 |
| 边 | 投资 + 股东 | union | 117,001 |
| 属性 | 专利/行业/城市 | left join | 覆盖率 |
| 图统计 | 邻接表 | 并查集 + 度分布 | 分量/孤立率 |

### 2.2 口径定义与公式

`node = DISTINCT org_id`；`edge = (src_org_id, dst_org_id, type)`，type ∈ {invest, shareholder}；`degree = in + out`。

`isolated_share = COUNT(degree = 0) / COUNT(node)`；`drop_rate = 1 - both_ends_in_base / total_edges`。两个比率是本件最重要的形状指标，比节点数更能说明图的质量。

连通分量用并查集，不做弱连通/强连通区分——关系边是有向的，但本件把它当无向图处理，因为「有没有关联」比「谁控制谁」更基础。

| 量 | 公式 | 本件值 |
|---|---|---|
| 节点 | DISTINCT org_id | 189,116 |
| 边 | invest ∪ shareholder | 117,001 |
| 孤立率 | degree=0 / 节点 | 89.54% |
| 丢弃率 | 1 − 两端在内/总边 | 77.44% |

### 2.3 边的构建与库外主体

投资边 46,967 条、股东边 70,034 条，合计 117,001 条。但只有 26,394 条两端都在主档内，77.44% 的边有一端是库外主体（自然人、外省企业、有限合伙）。

这是一个必须说清的口径：如果只保留两端都在主档的边，图会小很多但每条边都可用；如果保留全部边，会出现大量「悬空端点」，图统计被拉偏。本件选择「建图时保留、统计时只算两端在内」，两个数都写进产物。

悬空端点的根因是主档只覆盖深圳都市圈，而投资关系天然跨区域。这不是数据错误，是覆盖边界。

| 边类型 | 条数 | 说明 |
|---|---|---|
| 投资 | 46,967 | 企业→企业/自然人 |
| 股东 | 70,034 | 股东→企业 |
| 两端在内 | 26,394 | 可用于图统计 |
| 一端在外 | 90,607 | 悬空端点 |

### 2.4 计算步骤（脚本逐步实现）

1）读主档建节点；2）读两张关系表建边；3）过滤自环与重复边；4）并查集算分量；5）算度分布与孤立率；6）算属性覆盖率；7）取 Top 度节点。

第 3 步的重复边处理很重要：同一对企业在投资与股东两张表里可能各出现一次，若不去重，度会被重复计数。本件按 (src, dst, type) 去重，保留类型差异。

| 步骤 | 实现 | 校验 |
|---|---|---|
| 建节点 | drop_duplicates(org_id) | 189,116 |
| 建边 | concat + dedup | 117,001 |
| 分量 | 并查集 | 3,605 |
| 度 | groupby 计数 | max 522 |

### 2.5 结果与图结构

|---|---|---|---|
| 企业主档 | 可用 | 189,116 行 | 无 |
| 投资关系 | 可用但跨域 | 46,967 条 | 库外端点 77.44% |
| 股东关系 | 可用但跨域 | 70,034 条 | 同上 |
| 新闻文本 | 不可用于 NER | 无模型、无标注 | 需 NER 管道 |
| 节点权重 | 不可用 | 字段不存在 | 用度替代 |
| 标注集 | 不可用 | 无 | 需人工标注 |

### 3.2 四判定落表

四判定里，结构与数据都只是「部分」：结构上主档与关系表齐，但缺 NER 所需的文本处理；数据上节点全、边有一端在外。

这个「部分」不是量的问题，是层次的问题：结构化的那一层完整，语义的那一层为零。

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 无 graph_node |
| 表数据直接支持（开发库+三方库） | 否 | 同上 |
| 依赖表结构支持（开发库/三方库） | 部分 | 缺 NER 与别名词典 |
| 依赖表数据支持（开发库/三方库） | 部分 | 77.44% 边一端在外 |
| 聚合结论 | 部分支持 | 有骨架、无语义层 |

### 3.3 数据量、覆盖与代表性

覆盖上，节点是全量的 189,116，但「有边」只有 19,775（10.46%），「有专利」122,571（64.81%）。三个比例说明：主档很全，关系很稀。

代表性上，这张图几乎只反映深圳都市圈的投资关系。跨省投资的一端落在库外，被丢弃 77.44%。所以任何「全国企业关联网络」的表述都不成立。

### 3.4 结构支持判定

结构侧够建图：节点、边、属性、图算法都有载体。

语义侧不够：没有别名表、没有 NER、没有标注集。这三样缺任何一样，「实体识别」这个词都用不了。本件因此在标题上保留原名，但在正文明确降级为「结构化关系图」。

### 3.5 与开发库 live 的差异

开发库无 graph_node，live 不产出。上线需把节点表与边表分别物化，并保留 `both_ends_in_base` 标记，否则下游无法区分「真邻居」与「悬空端点」。

建议同时物化 `pipeline_spec.not_built`，让使用方知道哪些能力还没有。

## 四、数据缺失情况

### 4.1 缺口清单

本件的缺口分两层：数据层的「边跨域」与能力层的「无 NER」。前者可以靠扩主档缓解，后者必须建管道。两层不能混为一谈。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 无文本 NER | 新闻里的企业提及无法入图 | 明示未建 | 建 NER 管道 + 标注集 |
| 无别名归并 | 同一企业多写法成多节点 | 不做归并 | 建别名词典 |
| 77.44% 边一端在外 | 图统计偏小 | 统计只算两端在内 | 扩主档覆盖 |
| 节点权重缺失 | 中心度只能用度 | 用度替代 | 定义权重口径 |
| 无标注集 | 准召不可评估 | 不做评估结论 | 人工标注 1,000 对 |

### 4.2 逐条影响

「无 NER」是本件最硬的缺口。它不是「数据少」，是「能力没有」。没有 NER，新闻里出现的 90% 企业提及都进不了图，图的召回率无法估计。

「无标注集」让缺口更严重：即使做了 NER，也无法证明它准。两者必须一起补，只补一个没有意义。

### 4.3 明确不做什么（禁止的替代）

- 不把主档全称匹配称为「实体识别」——它只做精确匹配，不做别名与错写归并。
- 不把度当权重写进 `weight` 字段——度是结构量，权重是业务量，两者语义不同。
- 不用悬空端点做度统计——会让投资平台的度虚高，图的形状被拉偏。
- 不声称图覆盖全国——主档只覆盖深圳都市圈，跨省边被丢弃 77.44%。
- 不在无标注集的情况下报告准召——没有评估就没有数字。

五条禁令的核心是一句话：不要把「建了图」说成「做了实体识别」。前者是结构化操作，后者需要模型与标注。混淆这两者，会让下游对图的召回率产生错误预期。

### 4.4 若甲方补齐后的口径升级路径

补齐路径分三步：先扩主档覆盖降丢弃率，再建 NER 管道，最后建标注集评估。三步的顺序不能反——没有标注集就做 NER，等于没有验收标准。

三步都完成后，档位可以从「部分支持」升到「完全转换支持」；只做第一步，仍然是部分支持，因为语义层还是空的。

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 扩主档覆盖 | 丢弃率下降 | 仍为部分支持 |
| 建 NER 管道 | 新闻实体可入图 | 仍为部分支持 |
| 建标注集 | 准召可评估 | 可升完全转换 |
| 定义节点权重 | 权重可算 | 可升完全转换 |

**基期声明**：`base_years_used` = []；`base_years_missing` = []。本件是图结构与属性覆盖的截面统计，不做年度序列，故无基期年份；主档与关系表都是当前快照，无历史版本，无法观察图结构的年度演化。

## 五、王惠方法对照

王惠原稿把实体识别定义为「从主档与新闻文本抽取实体、建图、节点带权重」。本件保留「主档抽取 + 建图」，去掉「新闻文本」与「权重」。

差异的实质是能力边界：原稿假定 NER 管道已存在，实测没有任何文本处理组件。把这一半去掉之后，剩下的部分仍然有价值——它是所有图谱分析的地基。

需要提醒的是：去掉文本抽取后，「实体识别」这个名字会让人高估召回。所以正文反复写「结构化关系图」，并在 `pipeline_spec.not_built` 里逐项列出未建能力。

**选用建议**：节点与边的定义沿用王惠（org_id 为节点、投资与股东为边）；文本 NER、别名归并、节点权重三项因能力缺失暂不实现，在产物与正文双重声明。待 NER 与标注集就位后按原口径补回，档位可升格。

## 六、运行、验收与变更

验收看五件事：节点数、边数、两端在内比例、孤立率、未建能力清单。前四个是数，最后一个是文字，但同样重要——它决定了使用方会不会高估这张图。

变更管理上，边的类型与去重规则属于冻结口径。新增边类型（如供应链、专利共现）必须重跑全部图统计，不能只增量加边。
