## 摘要

「城市企业密度」是把企业数除以城市土地面积，回答「这个城市每百平方公里有多少家企业」。它是区域透视里最有解释力的指标之一——企业数只说明规模，密度才说明集聚。

分子完全成立。gkx 主档 189,116 行，`city` 字段 66 个取值、189,115 行可绑定城市码，深圳 95,600 家（50.55%）、广州 49,605 家（26.23%）、东莞 33,590 家（17.76%）、惠州 9,979 家（5.28%），四城合计 188,774 行（99.82%）。

分母完全不存在。全库 `information_schema` 扫描「列名含 area / land / square / km2 且类型为数值」的列，命中 0 个；`area` 列共 5 个，全是 varchar 行政区名（区县名，不是面积）；区划字典 `dwd_dim_admin_area` 29 列里只有代码与名称，没有面积。唯一的面积相关宏观指标是「人口密度(每公里土地面积人数)」`a77361`，只有 30 行、14 个国家代码、年份 1962—2021，最新年只有 1 个国家有值。

因此本件**不出任何密度数值**。产物里 `density_per_100km2` 一律为 `null`，`density_result.computed = false`，`denominator.status = "absent"`。这不是偷懒，是不让空值被读成 0——密度 0 会被理解成「这个城市没有企业」，而事实是「这个城市的企业数有、面积没有」。

结论是**部分支持**：分子可交付、密度不可交付，缺的是整张城市面积表。若甲方补齐面积，本件当天就能出密度值，不需要改公式。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业分析 → 区域透视 → 城市密度**。页面形态是一张城市表，每行显示城市、企业数、土地面积、密度；另有一张密度热力图，颜色深浅表示每百平方公里企业数。

它是区域类的第二个指标：区域企业数量回答「有多少」，本件回答「有多密」。两个指标共享分子，差别只在分母——这也意味着分子一旦出错，两个指标一起错。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业分析 → 区域透视 → 城市密度 |
| 页面载体 | 城市表 + 密度热力图 |
| 输出形态 | 城市 → 企业数 / 面积 / 密度（家每百 km²） |
| 更新频率 | 年度（面积年际变化小） |
| 粒度 | 城市（地级市） |

### 1.2 为什么需要这个指标

第一，密度比总量更能说明集聚。深圳 95,600 家与广州 49,605 家，总量差近一倍；但深圳面积不到广州三分之一，密度差会放大到三倍以上。这个放大正是「集聚」的量化表达。

第二，密度是排名与政策的输入。多城市对标排名里密度维占 30% 权重，本件是那一维的分子与分母提供方。

第三，密度是土地产出效率的代理。单位面积企业数高的城市，通常地均产出也高——这不是因果，但相关性足以支撑「集约发展」这类政策叙事。

### 1.3 需求文档是否给出定义方法

**给了公式，没给面积口径。** calc-logic 写的是「城市企业数 ÷ 城市土地面积，单位家每百平方公里」。未给的是：面积取行政区划总面积还是建成区面积、填海与水域是否计入、面积年际变化如何处理。

本件的处置：面积口径取「行政区划土地面积」（与统计年鉴同源），不取建成区（建成区面积库内更没有）；填海与水域是否计入由甲方定，本件不预设；面积视为年度常量，不做年际更新。三条都写进 §2.2，不默认甲方已知。

### 1.4 类似指标权威机构构建方法可行性

企业密度在官方统计与学术研究里有两套主口径：行政区域密度（企业数 / 行政区面积）与建成区密度（企业数 / 建成区面积）。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 行政区域密度 | 统计年鉴·区域经济密度 | 单位行政面积上的经济活动量 | 高（本件拟采用） |
| B 建成区密度 | 城市统计年鉴·建成区指标 | 单位建成区面积上的活动量 | 中（建成区面积更缺） |
| C 就业密度 | 经济地理学·集聚经济 | 单位面积就业人数 | 中（就业数据另需） |

**A 族是本件拟采用的口径**，因为它的分母（行政区划面积）是公开、稳定、可对齐的。问题不在方法，在数据：gkx 没有这张面积表。

**B 族**的分母更贴近「实际开发强度」，但建成区面积在公开统计里只有年度汇总、没有城市全量，补齐难度高于 A 族。本件不采用。

**C 族**用就业人数替代企业数，是另一条路，需要就业数据，本批不做。

### 1.5 引用来源

1. 项目内 calc-logic：`gkx-orchestration/agent-delivery/metrics/calc-logic/ENT/M_ENT_CITY_DENSITY.md`。

2. 国家统计局·城市统计年鉴（行政区划面积与建成区面积）。https://www.stats.gov.cn/

3. 民政部·全国行政区划信息查询平台（行政区划边界与面积）。https://www.mca.gov.cn/

4. 自然资源部·国土调查成果（土地利用现状）。https://www.mnr.gov.cn/

四条来源里，第 2 条是面积的主要公开来源，第 3 条可用于校验行政区划边界，第 4 条是更精细的土地利用数据（本批不用）。

本报告推测的定义：**密度_c = 城市企业数_c ÷ 城市行政区划面积_c × 100**，单位家每百平方公里。

## 二、计算过程

### 2.1 总体思路与数据流

分子从主档按城市分组计数，分母从面积表按城市取值，两者相除。分母缺，所以流程在第三步停住：分子算出、面积取不到、密度不出。

停住这件事必须显式化。产物里 `density_result.computed = false`、`rows = 0`、`note` 写明「分母缺 A_c，密度值一律不出」，而不是给一个全是 null 的表让人自己猜。表格里 null 与「没算」是两件事，前者可能被读成缺失值，后者明确是「未计算」。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 分子 | `dwd_org_base_info` | `GROUP BY city` | 66 行 |
| 分母 | 面积表 | 按城市取值 | **0 行（表不存在）** |
| 相除 | 分子 / 分母 | 逐城 | 未执行 |
| 探针 | `information_schema` | 扫面积类列 | 0 命中 |

### 2.2 口径定义与公式

密度的定义是一行除法，单位换算系数 100 是为了把「家每 km²」放大成「家每百 km²」，让数值落在易读区间：

$$\rho_{c}=\frac{N_{c}}{A_{c}}\times 100,\qquad A_{c}>0$$

其中 $N_c$ 是城市 $c$ 的企业数，$A_c$ 是行政区划土地面积（km²）。分子与分母的取值范围必须匹配：如果 $A_c$ 取建成区面积，$N_c$ 也应只取建成区内企业，否则分子分母不同域，比值无意义。本件不涉及这个选择，因为两个面积口径都没有。

城市标识的处理需要说清。主档的城市字段是**行政区划名**（「深圳市」），不是代码；代码来自 `dwd_dim_admin_area` 的 12 位 `city_code`（`440300000000`），前 6 位 `440300` 即民政部 6 位码，`4403` 是深圳市的省级前缀段。本件严格区分两者：`city` 是名称、`city_code` 是代码，不用 `area_code`（那是区县级）冒充城市码。

| 量 | 取值 | 含义 |
|---|---|---|
| $N$ 全库 | 189,116 | 分母底册 |
| 城市数 | 66 | `city` 去重取值 |
| 四城合计 | 188,774 | 深圳 + 广州 + 东莞 + 惠州 |
| 四城占比 | 99.8192% | 四城 / 全库 |
| $A_c$ | 不可得 | 面积表不存在 |

### 2.3 累计口径与年度切分的区别

本件是截面指标：分子是当前主档的企业数，分母是当前行政区划面积。两者都不按年切。

面积不做年际更新的理由是数据可得性：面积表本身没有，谈不上年际。分子不做年际的理由与区域企业数量一致——主档没有区域变更流水，按年切会与迁址混淆。

| 口径 | 含义 | 本件是否采用 |
|---|---|---|
| 截面密度 | 当前企业数 / 当前面积 | 拟采用（分母缺） |
| 年度密度 | 每年企业数 / 当年面积 | 否（面积无年际） |
| 建成区密度 | 建成区内企业 / 建成区面积 | 否（两项都缺） |

### 2.4 计算步骤（脚本逐步实现）

1）读三级计数快照，按城市聚合；2）扫 `information_schema` 找面积类数值列；3）扫 `area` 列的类型；4）查宏观指标里的面积类指标；5）查区划字典的列清单；6）写分子、分母状态与探针结果。

第 2 至 5 步是「否定性证据」：它们不产出数字，只产出「为什么算不出」的可复核记录。没有这四步，判「分母缺」就只是一句散文；有了这四步，任何人都能拿同样的四条 SQL 复现「0 命中」。

| 步骤 | 实现 | 校验 |
|---|---|---|
| 分子聚合 | dict 累加 | 66 城 |
| 面积列扫描 | `information_schema` | 0 命中 |
| `area` 列类型 | 同上 | 5 列全 varchar |
| 宏观指标 | `index_code='a77361'` | 30 行 / 14 国 |
| 字典列清单 | 同上 | 29 列无面积 |

### 2.6 关键中间量与校验

四个中间量：全库 189,116、城市 66、四城 188,774、面积列命中 0。

校验一：四城之和 188,774 ≤ 全库 189,116，通过。校验二：66 个城市求和 = 189,116（含 1 行空城市名），与主档行数相等，通过。校验三：面积数值列命中 0，与「分母不存在」的结论一致，通过。校验四：`area` 5 列全为 varchar，确认它们不是面积而是区县名，通过。

| 量 | 取值 | 校验方式 |
|---|---|---|
| 全库 | 189,116 | 与主档行数相等 |
| 城市数 | 66 | 去重取值 |
| 四城合计 | 188,774 | 小于等于全库 |
| 面积列命中 | 0 | 与分母缺失一致 |
| `area` 列 | 5 列 varchar | 类型核验 |

### 2.8 与旧稿的差异

旧稿引用的是一张 `dim.code_region` 维表，声称该表有 `area` 列但 100% 为 NULL（3,349 行，旧稿原文所载，见 `20261020_指标整体开发进度调研/开发库指标计算过程/M_ENT_CITY_DENSITY.md`）。本稿在 gkx 里找不到这张表——`information_schema` 的 `%code_region%` 表名扫描 0 命中，说明它属于开发库口径，不在 gkx。

因此本稿改用「四条探针」证明分母缺失，而不是引用一张不存在的表。这是本件与旧稿最大的方法差异：旧稿的证据是「表在但列为空」，本稿的证据是「连表都没有，且全库没有任何面积数值列」。

| 项 | 旧稿 | 本稿 | 差异原因 |
|---|---|---|---|
| 面积来源 | `dim.code_region.area` | 全库扫描，0 命中 | 旧表在 gkx 不存在 |
| 证据形态 | 「列为空」 | 「列不存在 + 四条探针」 | 口径换轨 |
| 密度值 | 可能给 0 或空 | 一律 null + computed=false | 防误读 |
| 档位 | 部分支持 | 部分支持 | 结论未变 |

## 三、数据支撑情况

### 3.1 依赖表与可得性

分子一张表就够，分母一张表都没有。这是本件最简洁也最刺眼的结论。

分母的四条探针结果：① 面积类数值列（列名含 area/land/square/km2 且类型为数值）0 命中；② `area` 列 5 个、全是 varchar；③ 人口密度指标 30 行 / 14 国 / 止于 2021；④ 区划字典 29 列无面积列。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 城市企业数 | 可用 | 66 城 / 189,115 行 | 无 |
| 城市面积 | 不可用 | 数值列 0 命中 | 甲方提供面积表 |
| 城市代码 | 可用 | 绑定 99.9995% | 无 |
| 建成区面积 | 不可用 | 全库无 | 需城市统计年鉴 |
| 面积年度序列 | 不可用 | 无表 | 同上 |
| 城市边界 | 不可用 | 无空间数据 | 需 GIS 数据 |

### 3.2 四判定落表

四判定里，结构侧「分子有、分母无」，数据侧同构。这不是「部分行缺」的可修补缺口，是「整列不存在」的结构性缺口。

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 无密度结果面 |
| 表数据直接支持（开发库+三方库） | 否 | 同上 |
| 依赖表结构支持（开发库/三方库） | 分子是 / 分母否 | 面积列 0 命中 |
| 依赖表数据支持（开发库/三方库） | 分子是 / 分母否 | 面积表不存在 |
| 聚合结论 | 部分支持 | 分母恒缺 |

### 3.3 数据量、覆盖与代表性

分子的覆盖是完整的：66 个城市、189,115 行（99.9995%），没有抽样、没有截断。这个分子本身就是一个可交付的指标（区域企业数量），只是不能单独叫「密度」。

代表性上，四城占 99.82%，其余 62 城合计不到 0.2%。即使面积补齐，密度排名也只有前四名有意义——北京 163 家、上海 16 家的密度会被面积极大值除成一个接近 0 的数，排名没有解释力。

### 3.4 结构支持判定

结构侧的分母完全缺失。这不是「表在但列空」的软缺，是「列不存在」的硬缺：没有任何一张表有 km² 数值列，没有任何一张表有城市面积字段。

有人会问「能不能从经纬度算面积」——主档有 `addr_lng` / `addr_lat`，但那是企业地址点位，不是城市边界；用它算城市面积需要凸包或栅格化，得到的不是行政区划面积，是「企业分布范围」，语义完全不同。本件明确不做。

### 3.5 与开发库 live 的差异

开发库有一张区域维表（旧稿引用），gkx 没有。这意味着同一个指标在两个库里「缺什么」是不同的：开发库缺的是填充，gkx 缺的是整张表。

上线需先把城市面积表灌进 gkx（一张 `dim_city_area(city_code, city_name, area_km2, year)` 即可），再物化密度宽表。面积表是唯一的阻塞项。

## 四、数据缺失情况

### 4.1 缺口清单

六个缺口，第一个是根，后五个是枝。面积表不来，后面五个都无从谈起。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 城市面积表 | 密度不可算 | 密度一律 null | 甲方提供面积表 |
| 建成区面积 | 无法做建成区口径 | 不做 | 城市统计年鉴 |
| 面积年度序列 | 无法做密度趋势 | 不做 | 面积表面向年度 |
| 城市边界空间数据 | 无法自算面积 | 不做 | GIS 数据 |
| 62 城样本过小 | 排名无解释力 | 只讲前四城 | 扩样本 |
| 登记地 ≠ 经营地 | 分子归属偏差 | 正文声明 | 经营地字段 |

### 4.2 逐条影响

**城市面积表缺失**是根缺口。它让密度这个比值无法成立，也让「多城市对标排名」的密度维（权重 30%）整维失效——两个指标共用一个分母，分母缺则两个都缺。

**建成区面积缺失**影响的是口径选择。行政区域密度会把大片山地、水域算进分母，低估建成区的真实密度；建成区口径更准，但数据更难拿。本件连行政区域面积都没有，谈不上选口径。

**62 城样本过小**是分子侧的问题，即使面积补齐也存在。北京 163 家、上海 16 家，密度值会被极小的分子主导，排名只能在前四城里做。

### 4.3 明确不做什么（禁止的替代）

- 不用人口密度反解面积——`a77361` 只有 30 行、14 个国家代码、止于 2021，且反解需要同城市同年的常住人口，库内没有。
- 不用经纬度凸包算城市面积——那是企业分布范围，不是行政区划面积。
- 不把 `area` 列（区县名）当面积——它是 varchar 行政区名，不是 km²。
- 不把密度 0 当「没有企业」——0 与 null 语义不同，本件一律 null。
- 不用四城密度代表全国——62 城样本不足，外推无意义。

第一条禁令值得展开。理论上可以用「企业数 ÷ 人口 × 人口密度」反解面积，但需要三个条件同时成立：同城市、同年、两个指标都有值。`a77361` 只有 30 行、覆盖 14 个国家代码（`049`、`082` 这类世界银行国别码，不是中国城市码），最新年 2021 只有 1 个国家有值。三个条件一个都不成立，反解出来的面积会是错的，比没有更糟。

### 4.4 若甲方补齐后的口径升级路径

补齐只有一条主路径：提供城市面积表。面积表到位后，密度当天可算，不需要改公式、不需要重写脚本，只需在脚本里加一段 join。

面积表之外，建成区面积与年度序列是增强项，不影响主口径成立。62 城样本问题是分子侧问题，靠面积表解决不了。

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 提供城市面积表 | 密度可算 | 可升完全转换支持 |
| 提供建成区面积 | 可做双口径 | 另立指标 |
| 面积表面向年度 | 可做密度趋势 | 另立指标 |
| 扩城市样本 | 排名有解释力 | 仍受分子限制 |

**基期声明**：`base_years_used` = []；`base_years_missing` = []。本件是截面指标，分子为当前主档全量计数；分母缺，无年度序列可谈。面积若将来按年提供，应改用 `base_years_used` 记录年份。

## 五、王惠方法对照

王惠原稿把密度定义为「企业数 ÷ 城市土地面积 × 100」，与本件一致。差异在数据侧：原稿假定面积可由区域维表取到，本件实测 gkx 没有任何面积载体。

第二处差异是零值处置。原稿未规定分母缺失时怎么办，本件明确「一律 null + computed=false」，并把理由写进产物。

**选用建议**：公式、单位（家每百 km²）、行政区划面积口径三项沿用王惠；面积来源改为「甲方提供面积表」；缺失处置改为「null 而非 0」。若甲方坚持用人口密度反解，必须先补同城市同年的人口与人口密度两列，且反解误差需实测披露——本件不做这个尝试。
