## 摘要

「服务链完整度」是深圳对比页里唯一一个被项目明确挂起的指标。calc-logic 0.2.0 的口径定义写得很直接：状态「挂起」、公式「未签（Q-SVCCHAIN-04 / 唐绍祖）」、环节数据「机构×服务链环节服务记录不存在」、本批「不做真数」；计算公式一节干脆写「无。不写可执行 SQL」，并列出三条禁令——禁止写 ADS 本 ID、禁止用六站有机构占比或六类覆盖率冒充、禁止把 fixture 验收成 live。

本件按这四条做了否定性探针，结论与 calc-logic 一致。算法层：公式未签，分子分母的定义都没有落纸。结构层：gkx 280 张表里 `svc_*` 相关表 0 张；全库带 `stage` 的列只有 6 列，全部落在招投标表（`bidding_stage` / `bidding_stage_code`），与服务机构无关；机构×环节成员表在两张库里都不存在。数据层：开发库 13 张 `svc_*` 表全部 0 行。代理层：用经营范围词表派生的六站供给面，在城市级恒为 6/6，在 12 个产业上恒为 5/6（distinct = 1，零方差），不能当取值。

判档为 **完全不支持**：不是说「深圳没有服务链」，而是说「这个指标的分子无法从两库里数出来」。本件因此不产出完整度数值，只产出阻断证据与代理的失效证明，并把「代理为什么不能救」写成可复核的量化结论（6/6 与 5/6）。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的是产业服务链分析 → 服务链分析 → 深圳对比 → 完整度柱。展示形态本应是一个百分比柱 + 一句「深圳服务链覆盖了 X/Y 个关键环节」；当前现网的处理是「诚实排除」——不画柱，badge 挂排除声明。算法侧是服务机构基础指标模型的覆盖度件，与「城市对比指标值」「深圳梯队位置」共用同一批城市取值。

这个指标的特殊性在于它是「覆盖类」而不是「计数类」：它要回答的不是「有多少家机构」，而是「这些机构把服务链的哪些环节填上了」。覆盖类指标的分子是「有覆盖的环节数」，判定单位是环节而不是机构，因此必须有「机构 × 环节」的成员关系才能数。

### 1.2 为什么需要这个指标

服务机构数量回答「供给有多少」，完整度回答「供给全不全」。一个城市可能有上万家中介，但全部集中在金融与咨询，研发、中试、检测三环节一片空白——这种情况下数量很漂亮、链条却是断的。完整度的价值就是把「数量」与「完整性」分开，让决策者看到结构性的缺口。

对深圳而言这个指标尤其重要：深圳的服务机构池里综合咨询与金融服务占大头，研发创新服务只占 4% 左右，中试熟化环节在词表口径下只有 2 家。如果只看总量 25,597，会得出「供给充足」的结论；完整度本应揭示「中试与检测是短板」，但这个结论需要真实的环节成员数据支撑，而不是靠经营范围词表猜。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法；calc-logic 0.2.0 明确「公式未签、本件不做真数」。** 需规只写「深圳服务链现状分析」，没有给环节清单、没有给覆盖判定标准、没有给分母。calc-logic 正本（`gkx-orchestration/agent-delivery/metrics/calc-logic/SVC/M_SVC_SZ_CHAIN_COMPLETENESS.md`）在「计算公式」一节写「无。不写可执行 SQL」，并给出解挂条件：唐绍祖出完整度定义卡 +（若公式依赖覆盖）供方交付机构×六环节成员表。

项目内另有一版王惠式的四环节定义（研发创新/成果转化/企业孵化/产业加速），但 `REM_QUEUE_20261023.json` 中本件的 `wanghui` 字段为 `null`，说明这版四环节不是本指标的王惠正本，只能作参考。calc-logic 0.2.0 明确：若将来用覆盖占比，环节轴「只能是 CT-SVC-PT-01 服务链六环节，不是产业链」。

### 1.4 指标口径与维度拆解

按 calc-logic 的锁定值，本件的口径如下。注意「锁定值」里没有公式，只有禁令与解挂条件。

| 项 | 锁定值 |
|---|---|
| 状态 | 挂起（沿 2026-08-28 侯佳伟 1A） |
| 公式 | 未签（Q-SVCCHAIN-04 / 唐绍祖） |
| 环节轴 | CT-SVC-PT-01 服务链六环节（research / ip / transfer / pilot / testing / market） |
| 环节数据 | 机构×服务链环节服务记录不存在（SVC-P0-3） |
| 现网 | 对比页诚实排除，不画完整度柱 |

公式的形式（供参考，不作为本件取值）：完整度 = 已覆盖的关键环节数 ÷ 全部关键环节数 × 100%。当分母取 6 时为六站口径，取 4 时为四环节口径；两种分母本件都算不出真值。

### 1.5 与同域姊妹指标的分工

与 `M_SVC_SZ_TIER` 的分工：完整度是 TIER 的三维之一。TIER 引用本件的「值不可用」结论，不重复做探针；本件负责把阻断证据做全。

与 `M_SVC_PT_CHAIN_NODE_ORG` 的分工：后者是「服务链环节上有多少机构」的节点件，用同一套经营范围词表。两件的共同点是都只能给供给面代理，区别是本件要的是「覆盖比例」，而比例的分母（环节全集）与分子（已覆盖环节）都还需要定义。

与 `M_SVC_SZ_COMPARE_METRIC` 的分工：COMPARE 是三小项面板，完整度不在其内（calc-logic 明写「完整度另见本件，已挂起，不在本三小项内」）。

### 1.6 本件的边界与不做什么

本件不做五件事：不写完整度数值（公式未签）；不用六站有机构占比冒充完整度（calc-logic 禁令）；不用六类服务覆盖率冒充完整度（同禁令）；不用产业链 `industry_link_code` 冒充服务环节（同禁令）；不把 fixture 验收成 live（同禁令）。

## 二、为何本件没有计算过程

本件不设常规的「步骤 1—5 计算过程」，原因是计算所需的三要素同时缺失，任何步骤都无法落地。

第一，算法缺失。完整度的分子与分母定义没有签：分子是「有 ≥1 家机构的环节数」还是「有 ≥N 家机构的环节数」未定；分母是 6（六站）还是 4（四环节）未定；四环节与六站如何映射未定。定义未定就没有可执行公式，calc-logic 因此写「不写可执行 SQL」。

第二，结构缺失。要数「某个环节是否被覆盖」，最小结构是「机构 × 环节」的成员关系。gkx 280 张表中没有这样一张表，开发库 13 张 `svc_*` 表也没有；`chain_stage` 在两张库中都不存在。没有成员表，唯一能做的就是用经营范围文本猜，而猜出来的东西不满足「机构在某环节提供过服务」这一事实语义。

第三，数据缺失。即便结构补上，也需要至少一行环节事实才能算出非空值。开发库 13 张 `svc_*` 表逐表 COUNT 全部为 0；`svc_metric_fact`、`svc_metric_series` 同样 0 行。没有任何一行可以进入分子。

三缺其三是「结构与数据均不具备可算闭环」，按四档定义即完全不支持。本件因此把篇幅放在 §三 的四条否定性探针与 §四 的解挂条件上，而不是编一套跑不出真值的计算步骤。

## 三、数据支撑情况（否定性探针）

### 3.1 探针一：算法层是否已签

| 项 | 内容 |
|---|---|
| 问题 | 完整度的分子/分母定义是否已在项目内签定 |
| 方法 | 读 calc-logic 正本 0.2.0（2026-10-13 落 seed） |
| 结果 | 状态「挂起」；公式「未签（Q-SVCCHAIN-04 / 唐绍祖）」；「本件不做真数」；「计算公式：无。不写可执行 SQL」 |
| 结论 | 算法层不可构建 |

calc-logic 同时列出三条禁令：禁止本批写 ADS 本 ID；禁止用六站有机构占比 / 六类覆盖率冒充完整度；禁止把 fixture 验收成 live。这三条禁令本身就是「算法未定」的旁证——如果公式已定，就不需要用禁令去堵替代口径。

### 3.2 探针二：结构层是否存在

| 项 | 内容 |
|---|---|
| 问题 | gkx 是否存在机构×环节成员表或等价结构 |
| 方法 | 检索全库列字典 `code/_snapshots21/gkx_columns_20261023.json`（280 表 / 6,312 列）+ 表名模式匹配 |
| 结果 | `svc_*` 表 0 张；`%svc%` / `%service%` / `%stage%` / `%circle%` / `%card%` 五个模式命中 0 张服务链表 |
| 细查 | 带 `stage` 的列共 6 列，全部在 `dwd_bid_base_out` 及两张备份表的 `bidding_stage` / `bidding_stage_code`（招投标阶段），与服务机构无关 |
| 结论 | 结构层不可构建 |

这一条最容易被误判：表名里带 `stage` 的列确实存在，但它是「招标所处的阶段」（如资格预审、评标、中标），不是「服务机构在服务链上的环节」。把招投标阶段当服务链环节，会得到一张看起来像成员表、实际语义完全错位的表。

### 3.3 探针三：数据层是否有行

| 项 | 内容 |
|---|---|
| 问题 | 开发库 13 张 `svc_*` 表是否有行 |
| 方法 | `_work_gkx21/LIVE_INVENTORY.json` 逐表 COUNT |
| 结果 | 13 张全部 0 行；`svc_metric_fact` 0 行、`svc_metric_series` 0 行 |
| 结论 | 数据层不可构建 |

开发库的 `svc_*` 表是空壳：表建好了、列也齐，就是没有数据。这种「结构在、数据空」的状态比「表不存在」更容易骗过结构检查——只看 `information_schema` 会以为有源，实际 COUNT 为 0。本件因此把 COUNT 结果单列，而不是只报表名。

### 3.4 探针四：代理能否充当取值

| 项 | 内容 |
|---|---|
| 问题 | 经营范围词表派生的六站供给面能否作「部分可算」的取值 |
| 方法 | 按六站口径对深圳切片与 12 个产业分组，统计覆盖站数 |
| 结果 | 城市级 6/6（恒满）；产业级 12 个全部 5/6（distinct = 1，唯一缺项恒为中试熟化） |
| 结论 | 代理零方差，不构成可用取值 |

这一条是「为什么不能判部分支持」的关键。部分支持的前提是「部分维度可算」，而这里唯一的代理在两个层级上都是常数：城市级恒 100%，产业级恒 83.33%。常数不是取值，它无法区分城市、无法区分产业、也无法随时间变化——把它当完整度，等于把「所有城市一样好」写进结论。

### 3.5 六站供给面代理的实测（仅作缺口证据）

| 环节 | 深圳家数 | 占切片 | 说明 |
|---|---:|---:|---|
| 研发与科研合作 | 18,987 | 74.17% | 词表最宽，几乎人人命中 |
| 知识产权与标准 | 422 | 1.65% | 窄口径，纯 IP 服务机构 |
| 技术转移与孵化 | 6,834 | 26.70% | 「孵化」并入此站 |
| 中试熟化 | 2 | 0.01% | 全池仅 10 家，深圳 2 家 |
| 检验检测认证 | 2,360 | 9.22% | 重资产环节 |
| 市场与金融咨询 | 6,599 | 25.78% | 与金融类机构重叠 |

六站是多标签，逐站家数相加为 35,204，大于切片 25,597；有任一环节命中的机构 21,080 家（82.35%），其余 4,517 家六站全不命中。这两组数说明代理本身不是「每站互斥的划分」，而是「各自独立的关键词命中」，因此不能用「命中站数 ÷ 6」当完整度——那会把一家同时做研发与咨询的机构算成两站覆盖，而它的「覆盖」只是经营范围里出现了两个词。

### 3.6 四环节与六站的映射（为什么映射本身也是缺口）

| 四环节（参考口径） | 映射到六站 | 状态 |
|---|---|---|
| 研发创新 | research | 可映射 |
| 成果转化 | transfer + testing + pilot | 映射不唯一（横跨三站） |
| 企业孵化 | 无独立站 | 缺轴（「孵化」被并入 transfer 词表） |
| 产业加速 | market | 可映射，但无「产业基金/上市辅导」独立字段 |

四环节口径若要用，必须先定这张映射表。表里有两处未定项：成果转化横跨三站（算一站还是三站？），企业孵化没有独立轴（用 transfer 顶替还是另找名录？）。这两处未定意味着「分母取 4」这条路比「分母取 6」还要多一层假设，因此 calc-logic 选择只认六站轴。

### 3.7 中试熟化的 2 家说明了什么

中试熟化在深圳切片只命中 2 家（全池 10 家），词表为「中试/概念验证/熟化/试制/小试」。这个数不是「深圳只有 2 家能做中试」，而是「深圳只有 2 家把中试写进了经营范围」。真实的中试平台（概念验证中心、中试基地）多数由高校、科研院所或产业园区运营，其登记经营范围未必出现这四个词。

这条差异正是「经营范围代理」与「服务事实」之间差距的极端案例：如果按代理出值，深圳的中试覆盖率是 2/25,597 = 0.01%，结论会是「深圳几乎没有中试能力」；而现实是深圳有一批中试平台，只是它们不在这个池的词表里。用这个代理去写政策结论，会严重误导。

| `chain_stage` | 0 | 两库均无 |

八条证据分三层：表名层（有没有这张表）、列层（有没有这个字段）、数据层（有没有这一行）。三层全部为零，才足以支撑「完全不支持」这个判断；只看其中一层都会误判。

需要单独说明 `svc_metric_fact` 与 `svc_metric_series` 这两张表：它们在 2026-10-20 的造数批次里是演示数据产物，落到开发库后 0 行，既无造数值也无真实值，属空壳表，不可作真源、不可作证据。本件引用它们只是为了说明「连这两张最像结果面的表都是 0 行」，不是把它们当数据来源。

### 3.9 三种替代口径的否定

除了六站供给面代理，项目里还有三种常见的「替代完整度」写法，本件逐一验证并否定。

第一种是「六类服务覆盖率」。服务六类（IP / FINANCE / HR / MKT / CONSULT / INNOV）是机构类型的分类轴，不是服务链的环节轴。用六类覆盖率冒充完整度，等于把「深圳有多少种类型的机构」当成「深圳填满了几个环节」——一家综合咨询机构可以同时算进 CONSULT 与 MKT，但它对「中试熟化」环节没有任何贡献。两套轴不可互换，calc-logic 也因此把它写进禁令。

第二种是「产业链节点覆盖率」。产业链用的是 `industry_link_code`，节点是产业环节（上游材料、中游制造、下游应用），服务链环节是服务机构在创新过程中的功能（研发、IP、转移、中试、检测、市场）。深圳的产业链节点覆盖可以很高，同时服务链的中试环节完全空白——两者不矛盾，因为它们量的不是同一件事。

第三种是「fixture 完整度」。旧稿曾用一组预置的完整度值（fixture）撑起对比页的柱子，这些值不是从任何一张表算出来的，而是演示态的手填值。把它们验收成 live，等于把演示结论写进正式数据。calc-logic 明确禁止，本件在产物里也不保留任何 fixture 字段。

三种替代口径有一个共同点：它们都能给出一个 0—100 之间的数，且都看起来合理。这正是它们危险的地方——完整度是一个「看起来谁都能算」的指标，而真正能算的前提是成员表，恰恰是所有人都不愿补的那张表。

### 3.10 与同族已交付件的一致性

本件的结论必须与同族件对齐，否则会出现「一件说可算、另一件说不可算」的口径裂缝。

与 `M_SVC_PT_CHAIN_NODE_ORG` 的一致性：该件用同一套六站词表统计「环节上有多少机构」，判部分支持——它只需要存在性计数，不需要覆盖判定。两件不矛盾：节点件数的是「有几家」，本件要的是「覆盖了几个环节」，后者需要成员表。

与 `M_SVC_SZ_TIER` 的一致性：TIER 的完整度维直接引用本件的「值不可用」，两件的代理轴与零方差结论必须同数（城市 6/6、产业 5/6、distinct=1）。若两件出现不同的代理值，说明词表版本不一致，必须回查快照。

与 `M_SVC_SZ_COMPARE_METRIC` 的一致性：COMPARE 的面板明确不含完整度（calc-logic 原文「完整度另见本件，已挂起，不在本三小项内」），本件也不把自己的值塞进那个面板。

### 4.2 修复路径与优先级

短期（一周内）只有一件事能做：把本件的否定性证据固化成可复跑的探针（已落 `code/M_SVC_SZ_CHAIN_COMPLETENESS.py`），让下一次有人问「为什么没有完整度」时能直接给出两库证据，而不是重复调研。

### 4.3 降档论证（为什么不是更高一档）

不抬到部分支持的理由：部分支持要求「部分依赖维度可算」。本件唯一的代理在城市级恒 6/6、产业级恒 5/6，是常数而不是取值；常数无法进入任何排序或分档。同时 calc-logic 明令禁止用代理冒充完整度，工程上也不允许把被禁止的口径写成「部分支持」。

不抬到完全转换支持的理由更直接：结构与数据双缺，连一行环节事实都没有，不存在「转换」的输入。

### 4.4 缺口对下游的影响

第一层影响是「对比页缺一根柱」：深圳对比页本应有完整度柱，现在只能挂排除声明。第二层影响是「梯队三维缺一维」：`M_SVC_SZ_TIER` 的完整度维因此置空，连带整个梯队名次无法产出。第三层影响是「政策叙事缺口」：没有完整度，就无法用一张图说明「深圳服务链的短板在哪个环节」，只能退回机构数量与类型结构。

### 4.6 解挂条件（写死，便于交接）
本件解挂需要同时满足三个条件，缺一不可：其一，唐绍祖签署完整度定义卡（Q-SVCCHAIN-04），明确分子分母与判定阈值；其二，供方交付机构×六环节成员表（SVC-P0-3），含机构 id、环节 id、生效期；其三，明确四环节与六站的对应关系（若定义卡选择四环节口径）。

### 4.7 解挂的连带影响

本件解挂不是孤立事件，会连带三件事。其一，`M_SVC_SZ_TIER` 的完整度维可以恢复，但梯队仍缺城市集合，所以 TIER 不会立刻从部分支持升档。其二，`M_SVC_ORG_COVERAGE_DEPTH` 一类覆盖深度件需要重算，因为它们与本件共用六站词表；成员表到位后，深度件的「每环节平均家数」才有真值。其三，对比页的排除声明可以撤下，但必须同时上线「环节口径」的图注，否则用户会以为完整度是按机构数算的。

连带影响的清单要随解挂一起交付，不能只改本件。同族件的口径是同一套，任何一次变更都要整族重跑。

## 五、结论与发布建议

本件不发布完整度数值。发布形态应为「诚实排除」：对比页不画完整度柱，badge 挂一句排除声明，声明里写清三层缺失——公式未签、成员表不存在、两库 0 行。

## 附录 F　常见误读与纠正

**问：机构池里六站都有人，为什么说完整度算不出？** 「六站都有人」是供给面的存在性判定，不是「某机构在某环节提供过服务」的事实。完整度的分子需要后者，而后者需要成员表。

**问：能不能用「六站有机构的站数 ÷ 6」当一个临时完整度？** 不能。calc-logic 明令禁止；而且这个代理在城市级恒 6/6、产业级恒 5/6，是常数，没有区分度。

**问：中试只有 2 家，是不是深圳真的没有中试能力？** 不是。是「只有 2 家把中试写进经营范围」。真实的中试平台多在高校、院所、园区名下，登记范围未必出现这些词。

**问：开发库有 13 张 svc_ 表，为什么还说没有结构？** 表在、列在、行数为 0。空壳表不能承载成员关系，COUNT 为 0 就是没有数据。

**问：能不能先用产业链的 industry_link_code 顶一下？** 不能。服务链环节与产业链节点是两套轴，calc-logic 明确禁止用产业链冒充服务环节。

**问：这个指标什么时候能上线？** 需要三个条件同时满足：定义卡签、成员表交付、四环节映射明确。三个都到位才可能解挂。
