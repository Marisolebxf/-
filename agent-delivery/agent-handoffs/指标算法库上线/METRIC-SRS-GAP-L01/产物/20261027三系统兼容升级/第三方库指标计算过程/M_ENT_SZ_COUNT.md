## 摘要

「深圳企业数」是一个区域切片计数：在国内企业底册里，注册地落在深圳的企业有多少家。它的公式只有一行，难点全在「深圳」这个键怎么定义：是行政区划码 4403 前缀、是中文市名「深圳市」、还是工商登记地址里的「深圳」二字。三种键在边界上会给出不同的数。

本报告先按 gkx 现有结构复算。底册 `dwd_org_base_info` 有 189,116 行，`city` 列有 66 个市值、1 行为空；`city='深圳市'` 的有 95,600 家，占全国 50.55%、占广东 50.64%。同省的广州 49,605 家（26.23%）、东莞 33,590 家（17.76%）、惠州 9,979 家（5.28%），四市合计 188,774 家，占广东 100.00%，差额 2 家是佛山、中山各 1 家。这个闭合关系说明 `city` 列的取值是自洽的，不是随手填的。

选产业后，深圳链属 16,875 家，占 12 链严格链属 28,031 的 60.20%；宽口径深圳 19,909 家，占宽口径 35,046 的 56.81%。深圳在 12 条链上的链属占比从 36.61%（生物医药）到 75.81%（智能网联汽车），说明深圳的产业分布并不均匀：智能网联汽车、具身智能、智能终端三条链的深圳占比超过 67%，生物医药、合成生物、数字创意三条链低于 49%。

类型结构上，深圳 95,600 家里小微 84,375 家（88.26%）、高企 15,683 家（16.40%）、专精特新 8,802 家（9.21%）、外资 4,554 家（4.76%）、小巨人 1,271 家（1.33%）、上市 1,117 家（1.17%）。小微占比比全国高 21.91 个百分点，是深圳企业结构最显著的特征。

结论是 **部分支持**：数可算、可勾稽，但计算键不是 calc-logic 要求的 `region_id`。gkx 底册没有这个列，只有中文市名；中文名能覆盖「注册地在深圳」，不能覆盖「行政区划码 4403」与深汕边界。只要 `region_id` 未绑，95,600 就只能作代理值发布，不能作正本值。

## 一、需求定义概述

### 1.1 所属功能模块

本指标挂在企业分析 → 企业总览 → 深圳企业现状，页面形态是一个 KPI 数字，常与「企业总数」「重点企业数」「深圳产业链企业数」并排。它是深圳专题的规模底盘，也是深圳类型占比、深圳链属占比的分母。

| 项目 | 内容 |
|---|---|
| 一级模块 | 企业分析 |
| 二级模块 | 企业总览 / 深圳企业现状 |
| 三级模块 | 企业整体概况 |
| 需求出处 | 展示系统 §1.1.1.2.4.1；算法库「企业基础指标模型 → 企业总览」 |
| 输出形态 | 单个整数（可选产业范围） |
| 更新频率 | 日（calc-logic），实际随批次 |
| 粒度 | 企业集合，按 `org_id` 去重，区域限深圳 |

### 1.2 为什么需要这个指标

深圳专题的第一屏需要一个规模数。没有它，「深圳高企 15,683 家」只是一个绝对数，无法判断是多还是少；有了 95,600 这个分母，才能算出 16.40% 的高企占比，并与全国 14.77% 比较。规模数是所有结构分析的前提。

第二个用途是对外表述。「深圳有近十万家企业」「深圳占广东一半」这类表述需要一个可复算的数。95,600 与 50.55% 都能从底册直接复核，适合对外；但必须注明是「注册地」而不是「实际经营地」，否则会把集团总部与空壳公司都算进深圳。

第三个用途是产业链招商。选产业后，深圳链属 16,875 家、智能网联汽车链 420 家、低空经济链 64 家，这些数决定招商目标池的大小。它们与全市 95,600 是两个层级，不能互相替代。

### 1.3 需求文档是否给出定义方法

**需求给了「深圳」这个地名，没有给计算键。** 展示系统只写「深圳企业数」，算法库只写「注册地在深圳的企业去重数」，两处都没有说用行政区划码还是中文市名。

王惠 20260817 底稿写得很具体：`gkx.dwd_org_base_info（org_id, city="深圳市"）`，也就是用中文市名。calc-logic 2026-08-28 版把键收紧为 `region_id LIKE '4403%'`，并明确「禁止 `headquarters_city` / `city` 中文名当计算键」，理由是中文名有别名（深圳 / 深圳市）与边界问题（深汕）。

两版定义的语义一致（都是注册地），但键不同。gkx 底册没有 `region_id`，所以本件只能用王惠的中文市名键；这也是判「部分支持」而不是「完全转换支持」的直接原因。

## 二、计算过程

### 2.1 总体思路与数据流

先确认「深圳」用什么键。正本是 `region_id LIKE '4403%'`，但底册没有 `region_id`；退而用 `city='深圳市'`，并在产物里把「无 region_id」写成缺口，而不是假装键已对齐。

数据流分两层：第一层是全市计数，读底册快照，按 `city` 分组，取「深圳市」；第二层是产业切片，读链属快照，取 `city='深圳市'` 的子集，再按链与类型分组。两层都用 `org_id` 去重，都不涉及跨表 JOIN。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 1 | 底册快照 | 按 `city` 分组 | 66 市分布 |
| 2 | 同上 | 取「深圳市」 | 95,600 |
| 3 | 同上 | 省/市勾稽 | 广东 188,776、四市 188,774 |
| 4 | 链属快照 | 取深圳子集 | 16,875 |
| 5 | 同上 | 按链分组 | 12 链深圳数 |
| 6 | 同上 | 按类型分组 | 六类深圳数 |

### 2.2 口径定义与公式

全市计数是：

$$sz = \left| \{\, e \in S_{dom} : city(e) = \text{深圳市} \,\} \right|$$

其中 $S_{dom}$ 是国内底册。占全国比例是：

$$share_{nation} = \frac{sz}{189{,}116} \times 100\% = 50.55\%$$

占广东比例是：

$$share_{gd} = \frac{sz}{188{,}776} \times 100\% = 50.64\%$$

产业切片是：

$$sz(C) = \left| \{\, e : city(e) = \text{深圳市} \land chain(e) \in C \,\} \right|$$

其中 $C$ 是 12 条战略链。因为一家只挂一条链，$sz(C)$ 对多选产业可加：

$$\sum_{c} sz(\{c\}) = 16{,}875$$

### 2.3 为什么 `region_id` 不可得

calc-logic 把键钉成 `region_id LIKE '4403%'`，理由是中文名有别名与边界问题。按这个要求，底册必须有 `region_id` 或至少 adcode 列；实测 gkx `dwd_org_base_info` 的 44 列里，与地理相关的只有 `province`、`city`、`area`、`address`、`addr_lng`、`addr_lat`、`postal_code`，没有 `region_id`、没有 `adcode`、没有 `district_code`。

`area` 列是区县名，不是码；`address` 是自由文本，含「深圳市」但不保证与注册地一致；经纬度可以反查行政区，但需要外部地理库，且反查误差不可控。live 侧的底册同样是空壳，`region_id` 也没有绑上。也就是说，正本要求的键在两库都不存在，这不是「数据少」，而是「列没有」。

因此本件只能用中文市名代理。这个代理与王惠底稿完全一致（她写的就是 `city="深圳市"`），所以数本身不是新造的；但与 calc-logic 的正本键不一致，判档必须降级。若甲方未来绑上 `region_id`，95,600 这个数可能会变，因为中文名与行政区划码在深汕、飞地、地址异常上不完全等价。

### 2.4 计算步骤（脚本逐步实现）

第一步读族级快照的 `base` 块，取 `shenzhen_city`、`city_dist_top`、`city_null`、`distinct_city`、`prov_dist_top`；第二步读 `types` 块，取深圳六类计数与深圳分母；第三步读链属快照的 `shenzhen`、`shenzhen_types`、`per_chain`；第四步计算占全国、占广东、占链属三个比例；第五步把深穗莞惠四市相加，与广东总数勾稽；第六步把佛山、中山的 2 家单列为「四市外广东」；第七步输出 `checks`，校验深圳不大于广东、广东不大于全国、四市加余数等于广东、空 city 为 1。

脚本没有 SQL，所有数来自共享快照。`per_chain_shenzhen` 保留 12 条链的深圳数与链内占比，`chain_slice` 保留严格/宽两套口径，`gaps` 把注册地、深汕、空值、链覆盖四条写死。

### 2.6 关键中间量与校验

第一个中间量是省域勾稽。广东 188,776 家，深圳 95,600、广州 49,605、东莞 33,590、惠州 9,979，四市合计 188,774，差 2 家正好是佛山 1、中山 1。这个恒等式在 `checks.sz_plus_other_prd_plus_rest_eq_gd` 里为 `true`，说明 `city` 列没有漏值或重复。

第四个中间量是宽窄差。宽口径深圳 19,909 比严格 16,875 多 3,034 家，占严格口径 17.98%。这 3,034 家是「在产业表里、只挂顶层链、无细分链」的深圳企业；它们是否属于该链无法确认，所以不作发布值。

### 2.8 与旧稿的差异

第一个差异是键。王惠底稿用 `city="深圳市"`，calc-logic 用 `region_id LIKE '4403%'`；本件用前者，因为后者在 gkx 不存在。旧稿若声称已按 `region_id` 落地，需要重新核对。

第二个差异是数。calc-logic 记录的旧 live 探针是 `city='深圳市'` 17,562 行、结果表 mock 12,860；本件底册是 95,600。三个数不是同一批数据：17,562 是旧 ODS 样本，12,860 是 mock 结果表，95,600 是 gkx 底册全量。不能直接比较，也不能把 12,860 当历史值。

第三个差异是产业切片。旧稿只有全市数，没有链属切片；本件补了 16,875 与 12 链分布，并区分严格/宽口径。

第四个差异是类型。旧稿不拆类型；本件补了六类深圳计数，供 `M_ENT_TYPE_RATIO` 的深圳口径使用。

### 3.3 数据量、覆盖与代表性

95,600 家覆盖深圳全市（含深汕特别合作区，按 `city` 名归集），占底册一半。底册的 66 个市值里，前四市占 99.99%，其余 62 市合计 342 家；这不是「全国城市分布」，而是「广东四市 + 少量外省注册地」。因此 95,600 的「全国占比 50.55%」只在库内成立，不能外推为「深圳占全国企业的一半」。

产业切片 16,875 家覆盖 12 条链，链间从 5,488 到 64，前三链合计 69.30%。深圳在智能网联汽车、具身智能、智能终端三条链的占比超过 67%，在生物医药、合成生物、数字创意三条链低于 49%；这个差异与深圳的产业结构一致，但也受链属标签覆盖影响，不能单独作为「深圳产业强弱」的证据。

### 3.4 结构支持判定

结构侧部分可用。底册有 `province`、`city`、`area`，能支持省/市/区县三级中文名分组；有 `address` 与经纬度，能支持地址级核验；没有 `region_id`，不能支持行政区划码过滤。产业表有 `credit_code`、`industry_code`，能支持链属切片。

结构侧的缺口是「码」。calc-logic 要的是 4403 前缀，底册给的是中文名；两者在大多数企业上等价，在深汕、飞地、地址异常上不等价。没有码，就无法用「4403」这个稳定键做跨库对齐，也无法与统计局的区划口径逐条核对。

### 3.5 与开发库 live 的差异

live 侧底册是空壳，`region_id` 没有绑，`shenzhen_enterprise_summary` 只有 mock 的 12,860。也就是说，开发库侧既没有可算的底册，也没有可信的结果表；本件的 95,600 完全来自 gkx。

gkx 侧的底册有 189,116 行，`city` 列可用，但没有 `region_id`。这不是「数据量不足」，而是「列缺失」；补列需要上游把工商注册地址标准化成区划码，属于 ETL 工作，不是本件能补的。

### 3.6 深汕与边界问题

深汕特别合作区在行政区划上由深圳主导，但地理上位于汕尾。底册的 `city` 列如果把它归到「深圳市」，95,600 就含深汕；如果归到「汕尾市」，就不含。本库没有 `region_id`，无法判断这部分的归属，也没有单列深汕的标记。

同样的问题出现在「注册地在深圳、实际在东莞」的企业：底册按注册地归集，会把它们算进深圳；按实际经营地归集，会算进东莞。两种口径的差不是小数，但在本库无法量化，因为 `address` 是自由文本，且没有实际经营地字段。

### 3.7 与同族件的一致性

本件的 95,600、188,776、189,116 与 `M_ENT_TOTAL_COUNT` 的 `domestic_structure` 完全一致；50.55% 与 `M_ENT_TOTAL_COUNT` 的 `shenzhen_share_pct` 一致；16,875、28,031 与 `M_ENT_TYPE_MATCH_COUNT` 的 `sz_strict`、`universe` 一致；深圳六类 15,683/8,802/1,271/4,554/84,375/1,117 与 `M_ENT_TYPE_COUNT` 的 `shenzhen_counts` 一致。跨件引用时注意：本件的 95,600 是「注册地」口径，不是「实际经营地」。

## 四、数据缺失情况

### 4.1 缺口清单

| 代号 | 缺口 | 影响维度 | 严重度 | 现有代理 |
|---|---|---|---|---|
| G1 | 无 `region_id` / adcode | 计算键 | 高 | `city` 中文名 |
| G2 | 1 行 `city` 为空 | 市域合计 | 低 | 单列 |
| G3 | 深汕归属无码可判 | 边界 | 中 | 按市名 |
| G4 | 注册地 ≠ 实际经营地 | 语义 | 高 | 无 |
| G5 | 结果表只有 mock | 结果面 | 中 | 现算 |
| G6 | 产业切片只覆盖 12 链 | 产业维 | 中 | 严格/宽双口径 |
| G7 | `area` 区县未绑码 | 区县 | 中 | 无 |
| G8 | 无区县年序列 | 时间维 | 低 | 无 |

### 4.2 逐条影响

G1 是最根本的缺口。没有 `region_id`，就无法用 4403 前缀做稳定过滤，只能用中文名；中文名在深圳/深圳市、深汕、飞地上有歧义。这个缺口决定本件只能判部分支持。

G2 只影响 1 家，但会让「全国 = 各市之和」差 1；报告在附录 H 单列，避免被误读为算错。G3 影响深汕的归属，当前按市名归深圳，若甲方要求单列，需要补码。

G4 影响语义。底册的 `city` 是注册地，不是实际经营地；集团总部、空壳公司、异地经营都会让 95,600 与实际产业活动偏离。这个缺口无法用现有字段补，只能靠年报或实地登记。

G5 影响结果面。`shenzhen_enterprise_summary` 只有 mock 的 12,860，不可作真源；本件现算 95,600，不读结果表。G6 影响产业切片：12 链只覆盖战略链，不是全部产业；严格/宽口径差 3,034 家。

G7 与 G8 影响区县与时间维度。`area` 有区县名但没有码，无法与区划表对齐；底册没有年度快照，无法做「深圳企业数逐年变化」，只能做截面。

### 4.3 明确不做什么（禁止的替代）

第一，不读 `shenzhen_enterprise_summary` 的 mock 值 12,860。它是演示值，不是真源；本件现算 95,600。

第二，不用 `address` 文本里的「深圳」二字做二次筛选。地址含「深圳」的企业可能注册在惠州，也可能只是通讯地址；文本解析的误差大于中文市名。

第三，不用 `headquarters_city` 替代 `city`。底册没有这个列，且总部城市与注册地是两个概念，混用会改变口径。

第四，不把 95,600 当「深圳实际经营企业数」。它是注册地口径；实际经营地需要年报或实地登记，本库没有。

### 4.4 若甲方补齐后的口径升级路径

第一步给底册补 `region_id`（4403 前缀）或 adcode，把中文名键换成码键。第二步补深汕特别合作区的归属标记，让边界可判。第三步补实际经营地字段（年报地址或登记地址），把「注册地」升级为「经营地」。第四步补区县码与年度快照，支持区县与时间维度。

四步完成后，本件可从「中文市名代理」升级为「区划码正本」，判档可从部分支持升到完全转换支持。升级的关键是 G1 与 G4：没有码，键不稳定；没有经营地，语义不完整。

### 4.5 工程侧缺口

两库都没有可信的深圳结果表。每次查询要扫 189,116 行底册，当前数据量下可接受；如果做区县或年度切片，需要预聚合。建议按「市 × 区县 × 链」建汇总表，并在底册上给 `city` 建索引。

### 4.6 口径披露要求

报表页脚至少披露三件事：深圳按 `city='深圳市'` 中文名统计（非 `region_id`）、注册地口径（非实际经营地）、深汕按深圳归集。三项缺一项，95,600 就会被误读为「深圳实际经营企业数」。

## 五、王惠方法对照

### 5.1 王惠原方法还原

王惠 20260817 底稿的定义是「注册地在深圳市的选定未来产业有效企业去重数」，源表写 `gkx.dwd_org_base_info（org_id, city="深圳市"）`。她的口径有三个特征：只国内、按中文市名、可选未来产业过滤；没有 `region_id`，也没有区县码。

这个口径与本件的实现完全一致：本件也是 `city='深圳市'`，也支持产业过滤。差别只在产业维：王惠用未来产业正则，本件用 12 链 `industry_code`。

### 5.2 新方法概述

calc-logic 2026-08-28 版把键收紧为 `region_id LIKE '4403%'`，理由是中文名有别名与边界问题；同时明确「禁止 `headquarters_city` / `city` 中文名当计算键」。它的目标是让深圳键与统计局的区划码对齐，支持区县下钻与跨库核对。

这个目标是对的，但 gkx 底册没有 `region_id`，所以本件无法按正本实现。本件退回王惠的中文名键，并在产物里把「无 region_id」写成缺口；这不是偷懒，而是现有结构下唯一能算的路。

### 5.3 逐维对照表

| 维度 | 王惠 20260817 | calc-logic 2026-08-28 | 本件实测 | 差异处理 |
|---|---|---|---|---|
| 计算键 | `city="深圳市"` | `region_id LIKE '4403%'` | `city` 中文名 | 键缺，降级 |
| 区域范围 | 深圳市 | 4403 前缀（含各区） | 深圳市（含深汕） | 边界无码 |
| 产业过滤 | 未来产业正则 | `enterprise_industry_chain` | 12 链 `industry_code` | 代理 |
| 去重键 | `org_id` | `org_id` | `org_id` | 一致 |
| 只国内 | 是 | 是 | 是 | 一致 |
| 结果表 | 无 | `shenzhen_enterprise_summary` | 现算 | mock 不读 |

### 5.4 选用建议与理由

建议**发布 95,600，但标注为「中文市名代理值」**。理由有三：第一，它与王惠原口径完全一致，业务可解释；第二，它与广东 188,776、全国 189,116 勾稽闭合，数本身没有错；第三，calc-logic 的 `region_id` 键在两库都不存在，强行按正本实现会得到空值。

如果甲方要求「必须按 4403 码」，则应先补 `region_id`，再重算；在补列之前，任何声称「已按 4403 统计」的说法都是不成立的。页脚应写「深圳按 `city='深圳市'` 统计，`region_id` 待绑」。

## 附录 C 可行性完整版

### C.1 问题拆解

深圳企业数可拆成三个问题：区域键、注册地语义、产业过滤。区域键决定「哪些企业算深圳」，注册地语义决定「算的是不是实际经营」，产业过滤决定「是不是产业链口径」。三个问题里，区域键缺码是主因。

### C.2 方法族比较

区划码法最稳定，但本库无码；中文市名法可算，但有别名与边界问题；地址解析法最细，但误差大；实际经营地法最准，但本库无字段。四条路里，中文市名法是唯一能在现有结构上闭环的。

### C.3 风险

主要风险是「把注册地当经营地」「把深汕漏掉」「把中文名当码」。三个风险都在 §4.3 与 §4.6 明确披露。

### C.4 结论

数可算、键不完整，判部分支持。

## 附录 G 口径问答

**问：为什么不用 `region_id`？**

答：gkx 底册没有这个列，44 列里只有 `province`、`city`、`area`；live 侧也没有绑。用 `city='深圳市'` 是现有结构下唯一能算的键，与王惠原口径一致。

**问：95,600 是注册地还是经营地？**

答：注册地。底册的 `city` 来自工商登记，不是实际经营地；集团总部、空壳、异地经营都会让这个数偏离实际产业活动。

**问：深汕算深圳吗？**

答：按 `city` 名归集，算深圳；本库没有 `region_id`，无法单列深汕，也无法判断边界。

**问：为什么深圳链属只有 16,875，比全市 95,600 少那么多？**

答：16,875 是 12 条战略链的严格链属，只覆盖有细分链的企业；全市 95,600 含所有行业。两者不是同一个母体。
