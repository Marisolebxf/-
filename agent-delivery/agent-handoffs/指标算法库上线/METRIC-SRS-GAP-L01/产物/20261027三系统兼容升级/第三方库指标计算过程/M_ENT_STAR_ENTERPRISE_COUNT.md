## 〇、数据支持度与四判定口径

### 0.1 四档定义（本文件沿用）

| 档位 | 定义 | 本件是否落入 |
|---|---|---|
| 完全直接支持 | **开发库+三方库（gkx）**中直接就有该指标（或 100% 语义一致指标/结果面）可用，且数据量完全支持直查/直算 | 否 |
| 完全转换支持 | 两库均无现成结果面，但依赖侧的表结构与当前数据量均已足够，现在即可通过转换与加工生成该指标；数据量不足不得入本档 | 否 |
| 部分支持 | 无论如何构建，始终有部分依赖维度无法从**开发库+三方库（gkx）**得到足够数据 | **是** |
| 完全不支持 | 该指标及其关键依赖维度，在**开发库与三方库（gkx）**均无法构建（结构与数据均不具备可算闭环） | 否 |

> **数据源口径**：本件支持度按「开发库 + 三方库（gkx，183.240.141.251:3318 只读）」评估，仅排除 `demo_*`；本机开发库事实面为空壳（`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张），实际取数面为 gkx。

判「部分支持」而不是「完全不支持」，理由只有一条：本件有一条**可复算的代理闭环**。名单真源（门户 CMS 已发布名单）确实在两库都找不到，但 gkx 的专利申请人聚合足以按一个公开、可复核的规则构造一份代理名单，且这份名单已经被 STAR 簇四件已交付件共用（区域分布、研发强度、行业分布、基本信息）。代理名单的计数可以逐条复算到人，差额为 0，这一点在 §2.2 用集合运算证明。

判「部分支持」而不是「完全转换支持」，理由也只有一条：**名单这一维度不是「加工」出来的，而是「替换」出来的**。加工是把同一语义的数据换个算法；替换是把「CMS 已发布」换成「专利授权数≥50」。前者改口径不改语义，后者连语义一起改。calc-logic 甚至把「禁止拿专利≥50 当明星」写成了红线，本件因此不能声称自己交付的是需求里那个「共 N 家」。

### 0.2 四判定拆分

| 判定项 | 本件答案 | 证据位置 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否：两库均无 `star_roster_item` / `ent_star_roster_count`；gkx 280 张表里 `star` / `roster` / `cms` 命中 0 张 | §3.1 |
| 表数据直接支持（开发库+三方库） | 否：没有名单表就没有名单数据；live 开发库为空壳 | §3.1、§3.5 |
| 依赖表结构支持（开发库/三方库） | 部分：专利申请人聚合（`star_applicant_agg_gkx.json`）与企业底册（`base_20261021.json`）均在 gkx 侧 | §2.1 |
| 依赖表数据支持（开发库/三方库） | 是（量足）：169,226 个申请人的 `[件数, 授权数]` 与 189,116 行底册，足以构造代理名单 | §2.2 |
| 聚合结论 | 部分支持 | 名单维度无源，代理可算 |

四判定里最关键的是第一行。用户问「明星企业数是多少」，字面答案是 4,561；但需求问的是「CMS 已发布名单里有多少家」，这两个数不是同一个东西。把 4,561 当成后者交付，是最容易被下游当成事实、又最难在事后发现的一类错——因为它有产物、有脚本、有快照，链条完整，只差语义。

### 0.3 一句话结论

gkx 无 CMS 名单表，本件交付的是「专利授权数≥50」构造的代理名单计数 **4,561 家**（候选 4,724、剔除高校/科研/医院 163 家），占底册 189,116 家的 **2.4117%**；深圳 2,590 家（56.7858%）、广州 1,020 家（22.3635%）、东莞 775 家（16.9919%）、惠州 176 家（3.8588%）。阈值从 50 改到 30 立刻变成 9,813 家、改到 100 变成 1,630 家，说明这个「共 N 家」完全由阈值决定，不是名单事实。

## 摘要

「明星企业数」在产品上是一个很小的数字：门户明星企业栏目顶部写「共 N 家」。但它的口径最硬——calc-logic 写的是「对 CMS 已发布名单按 `enterprise_code` 去重计数」，并且用六条禁令把各种替代路径全部堵死：不许拿专利≥50 当明星、不许用 `enterprise_tag.tag_code='star_enterprise'`、不许用荣誉名含「明星」、不许用竞争力或推荐 TopN。也就是说，这不是一个可以靠「找张像的表」解决的指标。

本件在 gkx 侧逐表核过：280 张表里 `star` 命中 0 张、`roster` 命中 0 张、`cms` 命中 0 张，`key_enterprise` 与 `enterprise_tag` 同样 0 张；机构标签表 `dwd_org_tech_tag` 的 32,322 家里，「明星」命中 0 家。live 开发库侧是空壳，`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张。结论是名单真源**两库均无**，这一点没有含糊空间。

但本件仍然交付了一个可复算的数：4,561 家。它来自 STAR 簇共用的代理名单快照 `star_roster_gkx_20261021.json`，构造规则是「专利授权数≥50 且剔除高校/科研/医院等非企业主体」。候选 4,724 家，剔除 163 家（3.4505%），入册 4,561 家；与快照逐 org_id 对账，双向差集都是 0。这份名单同时被区域分布、研发强度、行业分布三件已交付件引用，跨件口径一致。

必须同时说清三条限制。第一，4,561 是阈值 50 的产物：阈值取 30 是 9,813 家、取 80 是 2,290 家、取 100 是 1,630 家、取 200 是 591 家、取 500 是 166 家，曲线单调但没有拐点，说明「明星」在这条曲线上没有自然断点。第二，名单 100% 在广东（深圳 56.7858%、广州 22.3635%、东莞 16.9919%、惠州 3.8588%），与底册 99.8202% 偏粤同源，不能拿来表述「全国明星企业分布」。第三，calc-logic 明禁以此当明星，所以本件判**部分支持**：数能算、能复算，但它回答的不是需求问的那个问题。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业分析 → 企业总览 → 明星企业介绍**，页面形态是栏目顶部的「共 N 家」计数，下面接名单列表与属地/产业筛选。它不是一个独立图表，而是名单类页面的分母：所有「明星企业占比」「明星企业区域分布」「明星企业研发强度」都以它为分母。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业分析 → 企业总览 → 明星企业介绍 |
| 页面载体 | 栏目计数 + 名单列表 + 属地/产业筛选 |
| 输出形态 | 单一整数（可带产业/集群筛选后的子集计数） |
| 更新频率 | 日（随 CMS 拉取） |
| 粒度 | 名单 × 产业/集群（筛选是 API，不进 8 件套） |
| 关联Q | Q048（名单）、Q041（CMS 字段/授权） |

同族的分工是：本件数「名单里有多少家」，`M_ENT_STAR_BY_REGION` 数「这些家落在哪」，`M_ENT_STAR_BY_INDUSTRY` 数「这些家做什么」，`M_ENT_STAR_RD_RATIO` 算「这些家研发投入多高」。四件共用同一份代理名单，因此名单口径一旦改动，四件必须同批重跑，不能只改一件。

### 1.2 为什么需要这个指标

第一个用途是对外表述的锚。门户写「共 4,561 家明星企业」，这个数字会被截图、被引用、被拿去做招商材料；它必须能被复算，否则每一次对外披露都是一次不可审计的承诺。

第二个用途是筛选器的基数。用户选「人工智能」产业后，页面要显示「共 N 家」，这个 N 是名单与产业标签的交集。若名单本身是代理的，产业筛选后的子集也只能是代理的——这一点必须在页面上或接口里标注，否则用户会以为选出来的是官方认定名单。

第三个用途是横向对账。区域分布、行业分布、研发强度三件都以本件为分母，如果本件换了名单而其它三件没换，四份文档的分母会互相矛盾。本件的产物因此把 `roster_count` 与 `reconcile` 两块单列，供下游逐件比对。

### 1.3 需求文档是否给出定义方法

需求文档只给了业务语义与页面位置，没有给公式。calc-logic 把口径写死为：

```
本条 = COUNT(DISTINCT enterprise_code)
FROM star_roster_item
WHERE 只收已发布
```

并明确「选产业 / 选集群是 API（按 `future_industry_code` / `cluster_id` 过滤后再 COUNT），不把当前所选产业写进 8 件套」。这句话很重要：它说明指标本体是「全量已发布名单」，产业筛选是查询参数，不是指标定义的一部分。本件因此只交付全量计数，不交付「某产业明星企业数」。

calc-logic 同时列出六条禁止项，其中三条直接封死了本库的替代路径：禁止 `M_ENT_KEY_TOTAL` / 专利≥50 当明星；禁止 `enterprise_tag.tag_code='star_enterprise'`；禁止把荣誉名含「明星」的记录当名单。三者恰好是 gkx 唯一可能「像名单」的三类数据，所以本件在定义层面就已经没有直接路径。

### 1.4 类似指标权威机构构建方法可行性

「明星企业/龙头企业」在官方与商业实践里有五条测法，差别在「谁认定」与「按什么认定」。

| 方法族 | 代表机构/实践 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 官方名单制 | 工信部单项冠军、专精特新「小巨人」名单 | 主管部门发布，名单即口径 | 高（但库内只有标签，无名单） |
| B 平台编辑名单 | 门户 CMS 已发布名单 | 运营侧认定，可人工调整 | **最高（本指标真源）** |
| C 规模阈值 | 营收/专利/员工数≥阈值 | 单指标切分，可复算 | 中（本件代理采用） |
| D 荣誉标签 | 独角兽、隐形冠军、单项冠军 | 第三方榜单标签化 | 低（calc-logic 明禁） |
| E 排序 TopN | 竞争力/推荐分排序取前 N | 分数驱动 | 低（calc-logic 明禁） |

A 族在库内的残影是 `dwd_org_tech_tag` 的 55 种标签（国家级制造业单项冠军企业 172 家、独角兽企业 167 家、隐形冠军企业 72 家），但标签是「曾经获得」的资格记录，不覆盖未申报企业，且与本指标的 CMS 名单没有映射关系。C 族是本件实际采用的路径，因为它是唯一能同时满足「可复算」「覆盖全底册」「不依赖外部名单」三条的规则。D、E 两族被 calc-logic 明文禁止，本件不采用。

### 1.6 推测原意与推测定义

推测原意是：**门户要展示一份由运营侧维护的「明星企业」名单，并在栏目顶部告诉用户这份名单有多大**。它要的是一个可对外披露的规模数，不是一次算法评选。

据此给出两个定义，必须并列，不能混：

$$ N_{cms} = \mathrm{COUNT}(DISTINCT\ enterprise\_code)\ \text{from CMS published roster} $$

$$ N_{proxy} = \mathrm{COUNT}(DISTINCT\ org\_id)\ \text{where } grant\_cnt \ge 50,\ \text{non-enterprise excluded} $$

本件交付 $N_{proxy}=4{,}561$；$N_{cms}$ 无法从两库取得。依赖维度如下表，前三项是主口径，后三项是筛选与解释维。

| 代号 | 依赖维度 | 类型 | 本件实测 |
|---|---|---|---|
| D1 | 已发布名单 | 核心 | **不可得**（两库均无名单表） |
| D2 | 名单主体去重键 | 核心 | 代理用 `org_id`，CMS 用 `enterprise_code` |
| D3 | 企业主档 | 核心 | 可得，189,116 行 |
| D4 | 专利授权数 | 代理规则输入 | 可得，169,226 个申请人 |
| D5 | 产业/集群标签 | 筛选 | 部分可得（行业分类有，`future_industry_code` 无） |
| D6 | 发布状态 | 筛选 | **不可得**（无草稿/归档状态字段） |

D5 与 D6 是产品侧「选产业后共 N 家」的必要条件。本件只能交付全量计数，产业筛选后的子集无法按 CMS 口径复现；这一点在 §四 的缺口清单里单列。

## 二、计算过程

### 2.1 总体思路与数据流

整条链路四步，全部离线：读代理名单快照、读企业底册、读申请人聚合、按阈值重算并做集合对账。没有数据库连接，没有 JOIN 大表，重跑一次不到两秒——这是本件能作为 STAR 簇公共分母的前提。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 取名单 | `star_roster_gkx_20261021.json` | 读 `rows`（4,561 条） | 名单主体 |
| 取底册 | `base_20261021.json` | 189,116 行，取 `org_id/name/province/city` | 主体与属地 |
| 取申请人聚合 | `star_applicant_agg_gkx.json` | `agg[name] = [件数, 授权数]` | 阈值输入 |
| 重算与对账 | 上述三份 | 按 `grant>=50` 重算集合，双向差集 | 4,561 / 差集 0 |
| 分布统计 | 名单 | 城市、行业、授权分位 | 表与分位 |
| 否定性探针 | `GKX_INVENTORY.json`、`tech_tags` | 表名扫描、标签扫描 | 名单表 0 张、明星标签 0 家 |

这张表里没有任何一步是「查询数据库」。原因是专利侧的全表聚合已在 `star_applicant_agg_gkx.json` 里做完了（83 块、扫满 2,939,895 行、件数合计与表行数逐位相等），本件再去查一遍既慢又会与兄弟件产生口径差。

### 2.2 步骤 1｜代理名单的构造与复算

构造规则三步：申请人聚合取 `grant_cnt`；与底册 `name_cn` 等值匹配；剔除高校/科研/医院等非企业主体后取 `grant_cnt >= 50`。结果分三层：

| 层 | 家数 | 说明 |
|---|---|---|
| 候选（授权≥50） | 4,724 | 含高校、科研院所、医院等 |
| 剔除非企业主体 | 163 | 名称含大学/学院/研究院/研究所/医院/学校/协会/基金会，或 `org_type` 属事业单位等 |
| 入册 | 4,561 | 代理名单最终规模 |

剔除比例 163/4,724 = 3.4505%。这个比例不高，但方向很重要：如果不剔除，名单第一屏会出现华南理工大学（授权 18,235 件）、广东工业大学（14,061 件）、中山大学（11,025 件），而需求要的是「企业」。剔除后榜首变成比亚迪（17,072 件）、华为（13,360 件）、维沃（11,145 件），与企业语义一致。

复算的硬证据是集合运算：以快照 `rows` 的 `org_id` 为集合 A，以底册 + 聚合按同一规则重算的 `org_id` 为集合 B，实测 $|A|=4{,}561$、$|B|=4{,}561$、$A-B=\varnothing$、$B-A=\varnothing$。四个数都在产物 `reconcile` 块里，任何人可以照规则重跑一遍。

### 2.3 步骤 2｜去重键与主体识别

去重键是 `org_id`，不是企业名。原因有两个：底册 189,116 行只有 189,069 个不同 `name_cn`，存在 47 个重名；专利侧聚合又是按 `first_applicant_name` 做的，同名多企会各匹配一次。用 `org_id` 去重可以把「同名不同企」拆开，代价是「同企不同名」（曾用名、简称、英文名）会被漏掉。

本件没有做名称归一。原因是归一规则一旦引入，就必须给出可复核的映射表，否则 4,561 这个数会变成「取决于规则版本」的数。这一步的代价可以量化：169,226 个申请人名里有 157,363 行能等值匹配到底册（92.9898%），剩下 11,863 个名字匹配不上，其中一部分就是名称写法差异。代理名单只取能匹配上的部分，所以 4,561 是**下界**——真实「专利授权≥50 的企业」只会更多，不会更少。

### 2.4 步骤 3｜阈值敏感性

「明星」没有自然断点，这是本件最重要的发现。把阈值从 20 一路拉到 500，得到一条单调下降但没有拐点的曲线：

| 授权阈值 | 家数 | 占底册 | 相对阈值 50 的倍数 |
|---:|---:|---:|---:|
| 20 | 17,904 | 9.4672% | 3.9255 |
| 30 | 9,813 | 5.1889% | 2.1515 |
| **50** | **4,561** | **2.4117%** | **1.0000** |
| 80 | 2,290 | 1.2109% | 0.5021 |
| 100 | 1,630 | 0.8619% | 0.3574 |
| 200 | 591 | 0.3125% | 0.1296 |
| 500 | 166 | 0.0878% | 0.0364 |

阈值 20 到 30 之间家数近乎腰斩（17,904 到 9,813），30 到 50 再腰斩一次（9,813 到 4,561），之后每翻一倍阈值大致减半。这是典型的重尾分布，不是「明星」与「非明星」的双峰。换句话说，**这条曲线上没有任何一个点可以被论证为「明星」的边界**；50 之所以是 50，只是因为 STAR 簇的历史口径用了 50。

这一节的存在不是为了给 4,561 找合理性，而是为了让读者知道：换一个阈值，门户上那个「共 N 家」就会变成另一个数，而两个数都能自称「明星企业数」。

### 2.5 步骤 4｜名单的属地与行业结构

名单 100% 在广东，四市构成深圳 2,590（56.7858%）、广州 1,020（22.3635%）、东莞 775（16.9919%）、惠州 176（3.8588%）。省外 0 家。这不是「广东明星企业多」，而是底册本身 188,776/189,116 = 99.8202% 在广东，省外合计仅 340 家。名单是底册的子集，子集不可能比母体更分散。

行业结构上，制造业 1,995 家（43.7404%）、批发和零售业 912 家（19.9956%）、科学研究和技术服务业 787 家（17.2550%）、信息传输/软件和信息技术服务业 446 家（9.7786%），前四类合计 90.7696%。二级行业 74 个，Top5 是计算机通信和其他电子设备制造业 744 家（16.3122%）、批发业 646 家（14.1636%）、软件和信息技术服务业 403 家（8.8358%）、科技推广和应用服务业 328 家（7.1914%）、零售业 266 家（5.8321%）。

「批发和零售业」占到近两成，是这份名单最反直觉的地方。原因不是明星企业都在做批发，而是专利授权≥50 的企业里有相当一批是品牌商与渠道商（例如维沃的注册行业被登记为批发业）。这说明用专利数当名单规则，会把「专利多」误读成「产业地位高」，两者相关但不重合。

区县字段缺失 775 家（16.9919%），与同族区域分布件报的 17.0% 一致。这不影响本件的计数，但会影响按区下钻的名单展示——页面上会出现「未填区」这一类，且它比任何一个真实区都大。

### 2.6 步骤 5｜与母体的占比

名单占底册 4,561/189,116 = 2.4117%，占全部专利申请人 4,561/169,226 = 2.6952%。两个分母的含义不同：前者是「所有企业里有多少家够得上明星」，后者是「所有有专利的申请人里有多少家够得上」。对外表述应使用前者，因为门户的语境是「企业」。

名单的专利量占全库 1,069,438/2,939,895 = 36.3767%，授权量占 699,284/2,140,420 = 32.6704%。也就是说，2.4117% 的企业贡献了 36.3767% 的专利记录。这个集中度是重尾分布的直接证据，也是「用专利阈值筛明星」在统计上并非随意的一个理由——但它仍然不等于 CMS 名单。

## 三、数据支撑情况

### 3.1 依赖表与可得性

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| CMS 已发布名单 | **两库均无** | gkx 280 表中 `star`/`roster`/`cms` 各 0 张；live 空壳 | 需 Q050 联调、开放 CMS 只读接口 |
| 名单去重键 `enterprise_code` | 无 | 无名单表即无此键 | 随名单接口提供 |
| 企业主档 | 可用 | 189,116 行，`org_id` 唯一 | 无 |
| 专利授权数 | 可用 | 169,226 个申请人，合计 2,939,895 行 | 无 |
| 产业/集群筛选键 | 部分 | 有 `industry_l1/l2_name`，无 `future_industry_code` / `cluster_id` | 需产业链树映射 |
| 发布状态 | 无 | 无草稿/归档字段 | 随 CMS 接口提供 |

前两行是本件判「部分支持」的直接原因，后四行决定代理值能用到什么程度。需要强调的是第四行：专利授权数不是「够用就好」的替代品，它只能支撑一个阈值规则的名单，不能支撑一个「认定」名单。

### 3.2 四判定落表

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 两库均无名单表，`star_roster_item` 在 gkx 0 张 |
| 表数据直接支持（开发库+三方库） | 否 | 无表即无数据；live 开发库非空表 0 张 |
| 依赖表结构支持（开发库/三方库） | 部分 | 专利聚合 + 底册均仅 gkx 侧有，需本地匹配 |
| 依赖表数据支持（开发库/三方库） | 是 | 169,226 申请人、189,116 企业，量足 |
| 聚合结论 | 部分支持 | 名单维度无源 |

### 3.3 数据量、覆盖与代表性

代理名单 4,561 家覆盖底册 2.4117%，覆盖专利申请人 2.6952%。这两个覆盖率都不高，但名单承载的专利量占全库 36.3767%，说明覆盖的是「专利头部」而不是「企业随机样本」。用于门户展示规模是够的；用于「明星企业占全部企业比例」这类推断则不够，因为分母里的 97.5883% 企业根本没有进入候选池。

代表性上还有一条硬限制：名单 100% 在广东。底册省外合计 340 家，其中北京 163 家、浙江 19 家、上海 16 家、四川 16 家。这些省外企业里没有一家专利授权≥50，不是因为它们专利率低，而是因为底册在省外采样极少。任何「全国明星企业 4,561 家」的表述都会把采集边界当成市场边界。

### 3.4 结构支持判定

结构侧不是「缺一张表」这么简单。CMS 名单至少有四个字段是本指标口径的一部分：`enterprise_code`（去重键）、`publish_status`（只收已发布）、`future_industry_code`（产业筛选）、`cluster_id`（集群筛选）。gkx 侧一个都没有；用 `org_id` 顶 `enterprise_code` 可以做集合运算，但顶不了「已发布」与「产业/集群」这两个筛选语义。

因此本件的结构判定是「部分」而不是「否」：主计数不需要 JOIN、不需要权重、不需要分母表，只要一份名单；名单缺席时，代理规则可以填上计数这一格，但填不上筛选与状态两格。

### 3.5 跨件口径一致性

STAR 簇四件共用 `star_roster_gkx_20261021.json`。本件报 4,561；`M_ENT_STAR_BY_REGION` 报 4,561 且城市分布为深圳 2,590、广州 1,020、东莞 775、惠州 176；`M_ENT_STAR_BY_INDUSTRY` 与 `M_ENT_STAR_RD_RATIO` 同样以 4,561 为分母。四件的名单规模、城市分布、区县缺失 775 家三项逐字一致。

一致性不是巧合，是同一份快照的必然结果。它的价值在于：任何一件要改名单口径，另外三件必须同批重跑，否则分母会分裂。本件在产物里把 `reconcile` 与 `city_dist` 落盘，就是为了让下游能一眼看出「这一版名单有没有变」。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| CMS 已发布名单表 | 指标真值不可得 | 代理名单 4,561 | Q050 联调，开放只读接口 |
| `enterprise_code` 去重键 | 无法与 CMS 对账 | 用 `org_id` 去重 | 随名单接口提供 |
| `publish_status` | 无法排除草稿/归档 | 不排除（代理名单无状态） | 随名单接口提供 |
| `future_industry_code` / `cluster_id` | 产业/集群筛选后的「共 N 家」不可算 | 只交付全量 | 建产业链—企业映射 |
| 名单认定规则 | 代理阈值无自然断点 | 固定 50 并交曲线 | 甲方给认定标准 |
| 省外样本 | 全国分布不可解释 | 限定为深圳都市圈 | 扩采省外企业 |

六条里前四条是数据源问题，第五条是口径问题，第六条是采集问题。责任方不同，不能混成一句「数据不够」。

### 4.2 逐条影响

「CMS 名单表缺失」是最根本的一条。它决定本件交的是代理值而不是真值，也决定档位停在「部分支持」。如果甲方把这份名单当成 CMS 名单使用，风险不在数字本身，而在后续所有以名单为前提的结论——比如「明星企业研发强度高于行业均值」，一旦名单换了，结论可能反向。

「`enterprise_code` 缺失」看起来只是换个键，实际影响对账能力。CMS 名单的 `enterprise_code` 可以与工商主档对齐，也可以不与；用 `org_id` 去重时，同名多企会被拆开，同企不同名会被合并，两个方向都可能产生 1—2 家的差。本件用集合运算把代理名单内部对齐到 0 差，但无法与 CMS 对齐，因为 CMS 那份名单不在库里。

「产业/集群筛选不可算」是产品侧最容易忽略的一条。页面上的筛选器是真的会调 API 的，用户选了产业就会看到一个新数字；如果后端拿代理名单按行业分类去筛，筛出来的不是「该产业的明星企业」，而是「专利≥50 且行业分类命中该产业的企业」。两者在语义上差一层认定。

### 4.3 明确不做什么（禁止的替代）

- 不把 `enterprise_tag.tag_code='star_enterprise'` 当名单——calc-logic 明禁，且 gkx 侧 `enterprise_tag` 表 0 张。
- 不把荣誉名含「明星」的记录当名单——`dwd_org_tech_tag` 32,322 家里「明星」命中 0 家，本身也无从替代。
- 不把独角兽（167 家）、隐形冠军（72 家）、单项冠军等标签当名单——标签是资格记录，覆盖面与认定主体都不同。
- 不把竞争力/推荐 TopN 当名单——calc-logic 明禁，且 TopN 的 N 是产品参数，不是认定结果。
- 不把 4,561 说成「CMS 已发布名单」——这是本件最重要的一条禁令。

五条禁令的共同点是：它们都能让本件「看起来有答案」，但答案回答的不是同一个问题。宁可交一个标注清楚的代理值，也不交一个没有标注的假真值。

### 4.4 若甲方补齐后的口径升级路径

补齐 CMS 只读接口后，本件可以从「部分支持」升到「完全直接支持」：`COUNT(DISTINCT enterprise_code)` 是一条直查，不给任何加工空间，也不依赖专利侧。升级时只需把 `roster_count` 的数据源从代理快照换成 CMS 结果表，其余结构（分布、分位、对账）可以保留，用于新旧名单的差异审计。

| 补齐条件 | 口径变化 | 档位变化 |
|---|---|---|
| CMS 名单只读接口 | 真值可直查 | 部分支持 → 完全直接支持 |
| `publish_status` 字段 | 可只收已发布 | 同上 |
| 产业/集群映射 | 筛选后子集可算 | 同上 |
| 省外企业扩采 | 全国分布可解释 | 不改变档位，只扩大解释范围 |

**基期声明**：`base_years_used` = []；`base_years_missing` = []。本件是截面件，口径是「当前名单有多少家」，不含年度序列；名单与底册都没有快照日期字段，若要比较跨期名单变化，必须先补 ETL 元数据（本件未做，避免把两个不同时点的名单当成同一口径）。

结论：可交付的是「代理名单的规模与结构」，不是「CMS 名单的规模」。这两句话必须在交付物里同时出现，缺一句就会误导。

## 附录 F 口径问答

**问：为什么不能直接用「专利≥50」当明星？**

答：calc-logic 明禁，理由是「明星」是 CMS 运营认定，不是算法评选。专利≥50 只能说明该企业专利多，不能说明它被认定为明星；两者相关但不重合，且阈值本身没有自然断点（§2.4）。

**问：为什么 4,561 比候选 4,724 少？**

答：剔除 163 家高校/科研/医院等非企业主体。不剔除的话名单第一屏是华南理工大学、广东工业大学、中山大学，而需求要的是企业。

**问：为什么不用独角兽标签？**

答：`dwd_org_tech_tag` 里独角兽相关标签覆盖 167 家，与 4,561 差一个量级，且标签是「曾获/入选」记录，覆盖面取决于企业是否申报，不是认定名单。

**问：4,561 能不能对外写「明星企业 4,561 家」？**

答：可以写，但必须同时标注「代理名单（专利授权≥50）」。不加标注就是把它当 CMS 名单，属于口径冒充。
