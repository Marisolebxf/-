## 摘要

本件按王惠五子项框架对 20,000 条政策做力度评估，结果是一次彻底的「字段清点」而不是一次打分。V1 实施日：`implementation_date` 在 MySQL 里 20,000 行全部非 NULL，`IS NOT NULL` 会读出 100% 完备；但 `COUNT(DISTINCT)` 只有 1，唯一取值是 `0000-00-00`，真值 0 条。V2 支持方式、V3 支持对象、V5 扶持行为：三者都读 `policy_support` 的 JSON 子键，而该列 20,000 行全是字符串 `'null'`，子键根本不存在。V4 区县落地：`district` 非占位符 1,165 条（5.83%），是五項里唯一有变异的。

合成的政策级指数因此退化为二值：P50 = 0、P90 = 0、均值 5.83、最小值 0、最大值 100，18,835 条 0 分、1,165 条 100 分。这个分布不能叫「力度」，只能叫「区县字段填没填」。更要紧的是 V4 的语义也可疑：北京 2,268 条里 887 条带区县（39.11%，15 个区名），上海 1,841 条里 205 条（11.14%，8 个区名），而深圳 879 条里只有 7 条（0.80%）。直辖市的高填充率说明这个字段抓到的多半是**发文机关所在的区**（如「海淀区人民政府」），不是政策适用的区；深圳的低填充率则是因为区级文件本来就少。把这个当成「区县落地力度」，等于把发文机关的命名习惯当政策强度。

作为空壳期的替代诊断，本件另算了一组 17 词工具密度：资金、补助、补贴、奖励、资助、贴息、税收减免、减税、免税、股权投资、基金、贷款、担保、经费、拨款、专项资金、支持资金。20,000 条政策里 8,839 条命中（44.20%），工具词总频次 139,653。这个数只能说明「文本里写了钱」，不能说明「给了多少钱」——`support_amount` 字段不存在。年度密度 2016 年 2.69 → 2019 年 3.60 → 2021 年 2.70（每千字），先升后降。

结论：政策级力度分**不发布**；发布的是五子项完备率表（说明缺什么）、区县标记的城市对照（说明这个字段实际在测什么）、工具词密度（说明文本层面的力度书写强度）。判**部分支持**，等 `policy_support` 与 `support_amount` 灌数后指数可恢复五子项满配。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

需求把政策力度评估定义为一个「判断政策给的支持有多强」的模型。它要回答的问题很具体：这份政策有没有明确的实施时间、给的是钱还是给的是地、补给谁、在哪个区落地、是补贴还是贴息。五个问题对应五个子项，合成一个 0—100 的力度分，用于横向比较不同政策、不同城市、不同年份的支持强度。

产品形态是一个政策力度卡片：总分 + 五个子项打勾 + 一句「主要支持方式」。它天然会被拿来做排名（哪个城市政策力度大），因此本件对「指数不可发布」这件事必须写得非常清楚，否则排名页会成为误读的放大器。

### 1.2 为什么需要这个指标

政策文本里最容易被夸大的就是力度。「最高给予 1 亿元支持」这类表述在申报通知里随处可见，但它往往附带一长串条件，实际兑现远低于字面。反过来，一份没有写金额的文件可能通过税收减免给出更大支持。要让机器判断力度，必须有结构化的支持方式、对象、金额，而不是靠形容词。

本件的现实价值因此在两个方向：一是把「力度可算的部分」算清楚（区县标记、工具词密度），二是把「不可算的部分」点名（金额、支持方式、扶持行为）。后者对甲方的价值可能更大——它直接给出了补数字段的清单，而不是给一个看起来合理的假分数。

### 1.3 需求文档是否给出定义方法

**给了维度，没给权重与阈值。** 需求原文列出「实施时间、支持方式、支持对象、落地范围、扶持行为」五个方面，并要求「综合评估政策力度强弱」。它没有说五项等权还是加权，没有说每项怎么归一，也没有定义「力度强」的门槛。

更重要的是，原文假定这些信息是结构化字段（`support_way`、`support_object`、`support_behavior`、`support_amount`），而库里它们只以 JSON 形式存在于 `policy_support` 一列，且该列为空。也就是说，需求描述的是一个**理想表结构**，本地拿到的是一个**空壳列**。这是本件所有问题的根源。

### 1.6 推测原意与推测定义

**推测原意**：给政策打一个可比较的力度分，支撑「哪个城市支持更强」「哪类政策给得更多」两类问题；同时让业务方一眼看到这份政策是给钱、给地、给税收还是只给荣誉。

**推测定义（本报告采用，王惠五子项）**：

$$V_k=\frac{\#\{i:\ \text{subitem}_k(i)\ \text{完备}\}}{N},\qquad k=1,\dots,5$$

$$\text{Intensity}_i=100\cdot\frac{1}{5}\sum_{k=1}^{5}\frac{V_k^{(i)}-\min V_k}{\max V_k-\min V_k}$$

其中 $V_k^{(i)}$ 为第 $i$ 条政策在第 $k$ 子项上的 0/1 标记。文本代理另算：

$$D=\frac{1000\cdot\sum_{w\in W}c_w}{L}$$

$W$ 为 17 个工具词，$c_w$ 为词频，$L$ 为去空白正文字符数。

**依赖维度两跳拆解**：

| 代号 | 子项 | 依赖字段 | 两跳 | 状态 |
|---|---|---|---|---|
| V1 | 实施日完备 | `implementation_date` | 零日期判定 | 0 条真值 |
| V2 | 支持方式 | `policy_support.support_way` | JSON 子键 | 不存在 |
| V3 | 支持对象 | `policy_support.support_object` | JSON 子键 | 不存在 |
| V4 | 区县落地 | `district` | 行政区名 | 1,165 条（5.83%） |
| V5 | 扶持行为 | `policy_support.support_behavior` | JSON 子键 | 不存在 |
| — | 金额 | `support_amount` | 未建字段 | 不存在 |

## 二、计算过程

### 2.1 方法选择：先做字段清点，再谈指数

正常的指标文档会直接从「怎么算」开始，但本件必须先做一步字段清点，因为五子项里有四项的可用性不是「覆盖率高低」而是「字段在不在」。如果跳过这一步直接写公式，会得到一个跑得通、有数、但完全没有解释力的指数——这正是本件要避免的结果。

清点的顺序是：先看列是否存在，再看列是否非空，最后看非空值是否有变异。三步缺一不可。`implementation_date` 就是典型：列存在（是），非空（20,000 行），有变异（**否，唯一取值 `0000-00-00`**）。只看前两步会得出「100% 完备」的错误结论，这正是本件在 §2.2 要专门处理的陷阱。

### 2.2 步骤 1｜V1 实施日：零日期空壳

MySQL 的 `date` 类型允许 `0000-00-00`（在非严格模式下），它是一个合法存储值，不是 NULL。因此 `SUM(implementation_date IS NOT NULL)` 返回 20,000，看起来完美；`COUNT(DISTINCT implementation_date)` 返回 1，暴露了真相。本件的判定规则是「值 > `1990-01-01` 才算真实实施日」，实测通过者为 0 条。

这条规则不是拍脑袋：政策实施日不可能早于 1990 年（本库最早政策为 1981 年，但那是发布年，实施日若早于 1990 年只可能是数据错误或零日期）。加上这个下界后，V1 完备率 = 0.00%。这个结果必须写进文档，而不是把 20,000 当作 100% 上报——后者会让整个指数看起来「有一项满分」，从而掩盖其余四项全空的事实。

### 2.3 步骤 2｜V2/V3/V5：JSON 子键不存在

`policy_support` 在设计上是一个 JSON 列，预期结构类似 `{"support_way":"资金补助","support_object":["企业"],"support_behavior":"一次性奖励","support_amount":100}`。实测该列 20,000 行全为字符串 `'null'`（非占位符计数 0），意味着连 JSON 解析都不需要做——没有任何一行包含子键。

因此 V2（支持方式完备率）、V3（支持对象种类数）、V5（扶持行为完备率）三项全部为 0。这里要注意一个逻辑区别：V2 是「有支持方式的政策占比」，V3 是「支持对象去重种类数」，两者量纲不同（比率 vs 计数），但在本库都恒为 0，所以区别暂时不重要。等字段灌数后，V3 需要单独归一，不能直接与比率型子项等权。

### 2.4 步骤 3｜V4 区县标记：唯一有变异的子项

`district` 非占位符 1,165 条（5.83%），去重后 4—15 个区名不等（按城市）。这条子项的定义是「政策是否标注了落地区县」，0/1 型。它是五项里唯一有变异的，也是指数唯一的信息来源。

但它的语义需要拆开看。按城市统计：北京 2,268 条里 887 条带区县（39.11%，15 个不同区名）、上海 1,841 条里 205 条（11.14%，8 个区名）、嘉兴 105 条里 48 条（45.71%，但只有 1 个区名）、深圳 879 条里 7 条（0.80%，4 个区名）。嘉兴 45.71% 却只有 1 个区名，说明该市所有带区县的文件都指向同一个区——这更像采集时的默认填充，而不是真实的落地分布。北京 15 个区名则更像「发文机关名里带区」（海淀区人民政府、朝阳区人民政府）。

深圳 0.80% 与北京 39.11% 的落差，不能解释为「深圳政策落地性差」，只能解释为「深圳的区级文件少、且市级文件不写区」。这条必须写进页面注释，否则用户会得出完全相反的结论。

### 2.5 步骤 4｜指数合成与退化

按王惠原式，五子项各自 min-max 后等权平均。由于 V1/V2/V3/V5 的取值在全库是常数 0（min = max = 0），min-max 的分母为 0。本脚本的处理是：常数维返回 0.5（中性），不参与区分——但即便如此，四项常数维各贡献 0.5 × 1/5 = 0.1，合计 0.4，再加上 V4 的 0/1 × 1/5，指数会被锁在 40—60 区间，看起来「所有政策力度都中等」。

这显然不可接受。本件改用「可用子项等权」：只对 `available=true` 的子项归一后平均。这样指数 = V4 的 0/1 × 100，即 0 或 100。结果是 P50 = 0、P90 = 0、均值 5.83、18,835 条 0 分、1,165 条 100 分。指数没有中间值，无法区分「给一点」与「给很多」，因此不可发布为力度分。

两种处理都不理想，但「可用子项等权」至少诚实：它明确显示只有一项在起作用。而「常数维按 0.5」会制造一个虚假的中间分布，让指数看起来正常——这是更危险的错误。

### 2.6 步骤 5｜文本工具词密度代理

既然结构化路径只剩一个 0/1 标记，本件另建一条文本代理：17 个工具词在正文中的每千字频次。词表分四组——资金类（资金、经费、拨款、专项资金、支持资金）、补助类（补助、补贴、资助、贴息、奖励）、税收类（税收减免、减税、免税）、金融类（股权投资、基金、贷款、担保）。约束词另设四个（应当、必须、不得、禁止），单独统计。

实测 20,000 条政策里 8,839 条命中工具词（44.20%），总频次 139,653。约束词命中率 32.55%。这两个数的含义要分清：工具词命中率高说明「多数政策会谈钱」，约束词命中率 32.55% 说明「约三分之一政策含强制性表述」。前者与力度相关但不等价，后者与执行力相关但也不等价。

城市密度排名：广州 6.90、佛山 6.87、石家庄 5.66、济南 5.09、深圳 5.07、长沙 4.92、聊城 4.59、天津 4.46、珠海 4.41、长春 4.35、南昌 4.20、苏州 3.98（每千字）。深圳 879 条、工具词 7,786 次、密度 5.07，处于中上位置。这个排名**不能**当政策力度榜：它只反映文本里写钱的密度，写得多的可能只是因为文件长、或者习惯把补贴标准逐条列出。

### 2.10 为什么约束词不进指数

约束词（应当、必须、不得、禁止）命中率 32.55%，看起来是一个有用的维度，本件没有把它并进力度指数，理由有两个。第一是语义相反：工具词测「给什么」，约束词测「不许什么」，两者混在一个分数里会互相抵消——一份既给补贴又设严格条件的政策，会同时得高分与低分，平均后变成中等，恰好丢掉最有信息量的部分。第二是共线性：约束词多的文件往往也是长文件、体例完整的文件，它与工具词密度正相关（都要正文够长才有词频），并入后等于给长文件加两次分。

约束词的正确用法是单独出一张「强制性表述」标签，与力度并列展示，让用户自己判断这份政策是「激励型」「约束型」还是「混合型」。这个标签不需要归一，只需 0/1。

### 3.3 逐项缺口与修复路径

V1 的修复是正则回填：从正文抽「自 20XX 年 X 月 X 日起施行」，可覆盖一部分政策；但大量文件不写实施日（默认发布即实施），回填后完备率也不会到 100%。这项修复的成本低、收益中等。

V2/V3/V5 的修复只有上游灌数一条路。`policy_support` 需要按 JSON 结构回填三个子键，且要有受控词表（支持方式枚举、对象枚举、行为枚举），否则即使灌了数，去重后仍是几百种自由文本，无法归一。这项工作的工作量在数据治理侧，不在算法侧。

金额维（`support_amount`）需要新建字段并从正文抽取「最高 X 万元」「按 X% 补贴」等表述，抽取出错率高（上限 vs 实际、比例 vs 定额），建议先做人工抽检再上线。区县标记的修复是补采区县政府公报，并明确「district 指发文机关所在区还是政策适用区」——这个语义不定义清楚，补采也解决不了误读。

### 3.5 区县字段的语义审计

| 城市 | 覆盖率 | 区县去重数 | 最可能来源 |
|---|---:|---:|---|
| 嘉兴市 | 45.71% | 1 | 单一区名默认填充（疑似） |
| 北京市 | 39.11% | 15 | 发文机关名含区（海淀区人民政府等） |
| 上海市 | 11.14% | 8 | 同上，但市级文件占比更高 |
| 深圳市 | 0.80% | 4 | 区级文件本来就少 |

这张表是对 V4 语义的审计。判定依据是「覆盖率 × 去重数」的组合：高覆盖 + 1 个区名 = 默认填充；高覆盖 + 多区名 = 机关名带区；低覆盖 = 区级文件少。三种来源都不是「政策适用区」，因此 V4 即便在 5.83% 的覆盖上，也不能直接叫「落地范围」。

真正的落地范围需要从正文抽「本政策适用于 XX 区」这类表述，或用政策—企业关联反推受惠企业注册地。两条路本件都没走：前者需要 NLP 抽取且覆盖率未知，后者缺少关联键（见 §4.1 第 5 项）。

## 四、数据缺失情况

### 4.1 缺口清单

| # | 缺口 | 影响子项 | 后果 | 修复路径 | 优先级 |
|---|---|---|---|---|---|
| 1 | `policy_support` 全占位符 | V2/V3/V5 | 三项恒 0 | 上游按受控词表灌 JSON | 高 |
| 2 | `implementation_date` 全零日期 | V1 | 完备率假 100% | 正文正则回填 | 中 |
| 3 | 无 `support_amount` | 金额维 | 力度无法量化 | 新建字段 + 抽取 | 高 |
| 4 | `district` 语义未定义 | V4 | 误读为落地范围 | 明确口径并补采 | 高 |
| 5 | 补助台账无表 | 受惠反推 | 无法验证兑现 | 接财政/科技部门台账 | 高 |

### 4.2 后果归因：哪些话不能说

第一，不能说「政策力度指数均值 5.83，说明政策支持很弱」。这个 5.83 只是区县字段的填充率，与力度无关。第二，不能说「北京政策力度是深圳的 49 倍」（39.11% / 0.80%）。这个比值量的是区县字段填充率，不是支持强度。第三，不能说「2019 年政策力度最强」。工具词密度 3.60 只说明那年的文件里写钱写得密。

第四，不能说「深圳政策不落地」。0.80% 的区县填充率是采集与发文层级问题。第五，不能把工具词密度当作财政投入。它连「承诺金额」都不是，只是词频。第六，不能把 V1 的 20,000 非 NULL 当成实施日完备——这是零日期陷阱，`IS NOT NULL` 在这里完全失效。

### 4.3 判档说明

判「部分支持」的依据是五子项里四项无真值、指数退化为二值。这不是覆盖不足，而是字段结构性缺失：`policy_support` 连一行有效 JSON 都没有，`implementation_date` 连一个真实日期都没有。任何「完全转换支持」的判断都会在这里被推翻。

有人会主张「有 V4 就能算，算部分支持偏保守」。但指标的定义是力度，而 V4 测的是区县标记，一个只有区县标记的力度分不叫力度分。降档是为了让页面不给这个分数挂「力度」的标签。

### 4.4 缺口对结果的量化影响

若 `policy_support` 按 90% 覆盖率灌入三个子键，五子项中四项恢复（V2/V3/V5 加上已有的 V4，V1 仍缺），指数从二值变成四维连续，分布会接近正态，均值可能落在 40—60。若 `support_amount` 同时到位，金额维可以做对数归一，力度分才第一次具备「给多给少」的区分力。

若 `district` 语义澄清为「政策适用区」并补采到 50% 覆盖率，V4 的分布会从 5.83% 升到 50% 左右，且城市间差异会大幅缩小——目前北京 39.11% 与深圳 0.80% 的落差，主要就是语义与采集造成的。

## 五、方法对照与选用建议

### 5.1 三种指数处理对照

| 处理 | 做法 | 结果 | 可否发布 |
|---|---|---|---|
| 原式（常数维 0.5） | 五子项全入，常数维取 0.5 | 锁在 40—60，看似正态 | **否**（虚假中间分布） |
| 可用子项等权 | 只算 V4 | 0/100 二值 | **否**（无区分力） |
| 子项披露 + 代理诊断 | 不合成总分，出完备率与密度 | 五张明细表 | **是** |

### 5.2 选用建议

**采纳第三种：本期不发布政策级力度总分。** 理由是本件的目的在于支撑政策比较，而一个二值分或一个被锁在 40—60 的假分布都无法支撑比较，反而会给下游推荐系统注入噪声。发布五子项完备率 + 城市区县对照 + 工具词密度三张表，可以让业务方看到「缺什么」，这比一个假分数有用。

若甲方坚持要一个总分用于排序，唯一可接受的替代是「文本工具词密度分位」：把 18,763 条按密度排百分位，输出 0—100。它至少有变异、可复算，且语义清楚（写得密不密）。但必须在页面上写明「文本书写强度，非财政投入」，且禁止用于对外宣传。

### 5.3 结论

本件是一次成功的「证伪」：它证明了在当前库结构下，王惠五子项力度模型无法产出有意义的力度分。这个结论本身有交付价值——它把补数字段的清单（`policy_support` 四个子键、`support_amount`、`district` 语义）明确列了出来，而不是给一个跑得通但没意义的指数。

### 5.4 发布建议

第一，政策详情页显示五子项打勾表，缺的项显示「字段未建」而不是「0 分」。第二，城市对照页只放区县填充率，标题写「区县字段覆盖」，不写「落地力度」。第三，工具词密度可做趋势图（2016—2021），注明「文本密度，非投入金额」。第四，任何榜单页禁用力度分排序。

SELECT city, COUNT(*) n,
       SUM(NULLIF(NULLIF(UPPER(TRIM(district)),'NULL'),'') IS NOT NULL) d
FROM gkx.dwd_policy_base
GROUP BY city HAVING n >= 50 ORDER BY d DESC LIMIT 12;
-- 嘉兴 105/48、北京 2268/887、上海 1841/205、深圳 879/7、天津 666/0 …

## 附录 C　构建方法可行性报告（完整版）

**一、为什么会出现「跑通但无意义」。** 五子项框架本身没错，错在把「字段存在」当成「字段有值」。`implementation_date` 与 `policy_support` 都属于「结构在、数据空」的类型，且前者被零日期伪装成 100% 完备。这类陷阱在数据治理里比整列 NULL 更危险，因为它能骗过常见的非空检查。

**二、指数退化的判定标准。** 一个指数若在全体样本上只取两个值，且两值由单一 0/1 变量决定，则它不构成「指数」，只是该变量的缩放。本件实测 0 分 18,835、100 分 1,165，中间无值，符合退化判定。

**三、替代方案的成本。** 文本工具词密度是零成本替代（只需正文），但它测的是书写强度；财政投入口径需要接预算与台账，成本最高但语义最准；企业受惠反推需要政策—企业关联键，本库没有。本件选零成本替代作诊断，把高成本方案写进修复路径。

**四、结论。** 本期发布子项完备率与文本密度，不发布力度总分；补齐 `policy_support` 与 `support_amount` 后可恢复五子项满配，届时需重跑全量并打版本号。
