## 摘要

「政策类型分布」在需求里写得含糊：「按政策类型（产业政策、人才政策、企业扶持政策等）分类统计」。这句话里「类型」指的是**政策主题**——这条政策是扶持产业的、招引人才的，还是帮企业的。但 `gkx.dwd_policy_base.type` 装的是**文种**：管理办法、申报通知、公示公告、规划纲要。文种与主题是两套正交的分类，一条「人才政策」的文种可能是「申报通知」，一条「申报通知」的主题可能是产业也可能是人才。

本件先按库里真实存在的 `type` 做了 14 种文种的完整分布，再把「需求要的三分法能不能得到」单独验了一遍：`theme` 字段全库只有 2 行有值（样本里出现「创业扶持/财政支持/融资服务/科技创新/乡村振兴」），`keywords` 与 `keypoints` 均为 0 行，`policy_support` 20,000 行全是小写 `'null'`。也就是说，主题分类的**结构在、数据不在**。

于是本件的交付分成两层：第一层是可直接上线的**文种分布**（14 种、合计 20,000）；第二层是**主题三分法的可行性否定证据**，明确告诉甲方「产业/人才/企业扶持」这三分法当前算不出来，不要用文种去冒充。判**部分支持**，否定的部分给证据，不给猜测。

文种分布本身还有一个必须披露的结构事实：20,000 条里 **10,596 条（52.98%）是事务通知类**（其他通知 5,782 + 公示公告 2,995 + 申报通知 1,819），真正的政策文件类只有 6,881 条（34.405%），规范性文件类 644 条（3.22%），政策解读 17 条。把「申报通知」当「政策」数，会把政策库规模虚高一半。

| 口径要点 | 本件取值 |
|---|---|
| 总条数 | 20,000 |
| 文种种类 | 14（13 类有效 + 未标注） |
| 最大文种 | 其他通知 5,782（28.91%） |
| 未标注 | 1,862（9.31%，字面 `'NULL'`） |
| 事务通知类 | 10,596（52.98%） |
| 政策文件类 | 6,881（34.405%） |
| 规范性文件类 | 644（3.22%） |
| 政策解读 | 17（0.085%） |
| 主题可用行 | 2（0.01%） |
| 判档 | 部分支持 |

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

政策类型分布挂在科技专题服务系统的「政策类型指标」页，形态是饼图加图例：每类政策一个扇区，点击扇区下钻到该类政策清单。科技信息展示系统的政策检索页复用同一套分类做筛选项。

页面设计上有一个隐含前提：用户理解的「类型」是**对我有什么用**——是给钱的政策、给人才的政策，还是给场地的政策。而库里的 `type` 回答的是**这份文件是什么文体**。两者错位，是本件所有口径问题的根源。

### 1.2 为什么需要这个指标

第一，它决定政策库的「有效政策」口径。10,596 条事务通知里，公示公告是结果披露、申报通知是流程入口，它们不是政策本体；如果把它们计入政策总量，会得到「政策很多」的错觉。

第二，它支撑检索体验。用户按「管理办法」找制度依据、按「申报通知」找申报窗口、按「规划纲要」看方向，这些是真实需求，文种筛选能直接满足。

第三，它是判断「主题分类能不能做」的前置检查。只有先把文种与主题拆开，才能说清「为什么不能按产业/人才/企业扶持分类」。

### 1.3 需求文档是否给出定义方法

**给了三个例子，没给映射规则。** 原文写「按政策类型（产业政策、人才政策、企业扶持政策等）分类统计」，这三个词都是主题，不是文种；而注册表写 `GROUP BY policy_type`，把问题指向了 `type` 列。两处对「类型」的理解不一致。

本件没有替甲方选一个解释硬做，而是两条都查：`type` 能做什么、`theme` 能不能补。结论是 `type` 能做文种分布，`theme` 补不了主题分布。这是「部分支持」判定的直接来源。

### 1.4 类似指标权威机构构建方法可行性分析概要

| 方法族 | 代表做法 | 口径要点 | 与本件的差 | 贴合度 |
|---|---|---|---|---|
| A 文种分类 | 政策文件管理规范 | 通知/办法/规划/公告/解读 | 本库 `type` 已细分到 14 种 | 高（可直算） |
| B 主题分类 | 政策主题词表 | 产业/人才/科技/民生 | 需 `theme` 或关键词，本库近乎空 | 低（数据不足） |
| C 政策工具分类 | 补贴/税收/金融/土地 | 需结构化工具字段 | `policy_support` 全 `'null'` | 不可行 |
| D 发文机关分类 | 按部门职能 | 需 `ministry` 完整 | 有字段但未在本件展开 | 中 |

**三句结论**：① A 族可立即上线，14 种文种已实测；② B 族是需求原意，但 `theme` 只有 2 行，**不能做**；③ C 族依赖的 `policy_support` 20,000 行全为 `'null'`，同样不可行。

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设第 $i$ 种文种的政策数为 $n_i$，则

$$p_i=\frac{n_i}{20{,}000}\times100,\qquad \sum_{i=1}^{14}n_i=20{,}000$$

大类聚合为四个可加集合：事务通知类 $T$、政策文件类 $F$、规范性文件类 $N$、政策解读 $I$，满足

$$|T|+|F|+|N|+|I|=20{,}000$$

**边界**：① 「类型」在本件指**文种**，不是政策主题；② 主题三分法明确判「当前不可得」，不用文种替代；③ `'NULL'` 字面量 1,862 行是「未标注文种」，不是 SQL NULL；④ 分母固定 20,000，与 `M_POLICY_TOTAL_COUNT` 同母体；⑤ 不按年份切分。

### 1.7 与旧稿的差异（摘要）

旧稿（20261019 版）判**完全直接支持**，依据是 live 侧 `ads.policy_type_dist` 的 5 行大类（汇总 600）；本件判**部分支持**，因为文种虽可算，需求原意的主题三分法（产业/人才/企业扶持）在 `theme` 上只有 2 行、`keywords` 为 0 行。旧稿没有区分「文种」与「主题」，这是本件最重要的修正。详细对照见 §5.3。

## 二、计算过程

### 2.1 第一步：确认 `type` 到底是什么

`type` 是单值字符串列，不是数组。实测 14 种取值，最大「其他通知」5,782，最小「政策文件-评定标准」1。取值命名有明显的前缀体系：`政策文件-*`（管理办法/指导意见/规划纲要/其他文件/政策指南/评定标准）、`规范性文件-*`（规范条例/部门规章/法律法规）、以及无前缀的「其他通知」「公示公告」「申报通知」「政策解读」。这套命名本身就说明 `type` 是**文种**，不是主题。

如果 `type` 是主题，取值应该是「产业/人才/科技/民生」这类；实际取值是「管理办法/公示公告」，任何一个做过政策库的人都能一眼看出这是文种。这一步不做，后面整篇都会跑偏。

### 2.2 第二步：直接分组，保留 `'NULL'` 作为独立一档

分组时最容易犯的错是把 `'NULL'` 当 SQL NULL 过滤掉。`type` 里的 1,862 行是**字面字符串 `'NULL'`**，`WHERE type IS NOT NULL` 会把它们全部保留，`WHERE type != 'NULL'` 才会剔除。本件不剔除：1,862 行是真实存在的政策，只是文种没标；剔除会让分母从 20,000 掉到 18,138，与总数指标对不上。

所以 14 行里有一行 `type='__NULL__'`、`n=1,862`、`is_null_placeholder=true`。产物用 `__NULL__` 这个显式占位符，避免下游把它当真实文种名。

### 2.3 第三步：大类聚合，把 14 种压成 4 类

14 种对饼图太碎，本件按命名前缀聚成 4 类：

- **事务通知类** 10,596 = 其他通知 5,782 + 公示公告 2,995 + 申报通知 1,819
- **政策文件类** 6,881 = 管理办法 3,708 + 指导意见 1,697 + 规划纲要 699 + 其他文件 683 + 政策指南 93 + 评定标准 1
- **规范性文件类** 644 = 规范条例 606 + 部门规章 34 + 法律法规 4
- **政策解读** 17（单列，不并入政策文件类）
- **未标注** 1,862

四类加未标注 = 20,000。这里有一个口径选择：政策解读要不要并入政策文件类？本件不并。理由是解读是对政策的解释，不是政策本体；并入会让「政策文件类」从 6,881 变成 6,898，差别虽小，但会在「有效政策」口径上制造 17 条噪声。产物 `document_purity` 同时给了并入后的 7,542（37.71%），供甲方选用。

### 2.4 第四步：验证主题三分法能不能做

需求要的是「产业政策、人才政策、企业扶持政策」。本件按三条证据逐条否定：

**证据一：`theme` 只有 2 行有值。** 全库 20,000 行，`theme` 非空 2 行（0.01%）。两行样本的标签是 `["创业扶持","财政支持","融资服务","科技创新"]` 与 `["财政支持","科技创新","乡村振兴"]`。这证明字段结构存在、标签体系也有，但**样本量不足以做分布**——2 行分不出 20,000 行的结构。

**证据二：`keywords` 与 `keypoints` 为 0 行。** 两个字段都是大写 `'NULL'` 字面量，没有任何一行有真实关键词。想靠关键词做主题归类也没有原料。

**证据三：`policy_support` 全为小写 `'null'`。** 这是 JSON 列，20,000 行全是字符串 `'null'`。陷阱在于 `JSON_LENGTH('null')` 返回 1，看起来「有一项」，实际是空值。想用它做「补贴/税收/金融」的工具分类，一行都用不上。

三条证据合起来：主题分类的**结构存在、数据不足**。这不是「再多写点 SQL 就能算」，是原料没有。

### 2.5 第五步：占比与四舍五入

14 种文种的占比逐项算出，保留三位小数（如 14.975、9.095、3.495、3.415）。为什么不用两位？因为两位小数下 14 项相加会出现 99.99 或 100.01，审计时会被问「差额去哪了」。三位小数能把误差压到 0.001 级别，且本件所有百分比都由整数除法直接得出，不经过中间舍入。

四类大类的占比同样保留三位：52.98、34.405、9.31、3.22、0.085，合计 100.00。

分母 20,000 是全库记录数，其中 9,706 行 `city` 是字面 `'NULL'`。本件不按城市切分，城市缺失不影响文种计数；但若下游要把文种分布与城市交叉，必须先剔除这 9,706 行，不能把它们当有效城市。

### 2.6 第六步：与总数、级别、城市三件对账

- 与 `M_POLICY_TOTAL_COUNT`：`type_total=20,000`，与 `COUNT(*)` 一致。
- 与 `M_POLICY_LEVEL_DIST`：本件不按级别切，但两件分母相同，国家级 2,174 条、广东 1,612 条、深圳 879 条都在这 20,000 条之内，文种只是给它们再贴一个标签，不改变任何总量。
- 与 `M_POLICY_SZ_DIST`：深圳 879 条同样分布在这 14 种文种里，不另立文种。

### 2.8 为什么不用 `table_rows` 做分母

`information_schema.table_rows` 对本表报 18,808，实测 `COUNT(*)` 是 20,000，差 1,192 行（约 6%）。InnoDB 的 `table_rows` 是采样估算，不是精确值。若用它做分母，14 种文种的占比会整体虚高约 6%，而且「未标注 9.31%」会变成「未标注 9.9%」，与总数指标对不上。本件一律用 `COUNT(*)`，并在产物 `known_estimate` 里记录估算值，仅作对照。

### 2.9 文种纯度：52.98% 不是政策

把 20,000 条按「是不是政策本体」重排，得到三块：政策文件类 6,881 + 规范性文件类 644 = **7,525 条（37.625%）**是政策本体；事务通知类 **10,596 条（52.98%）**是流程性文书；未标注 1,862 条（9.31%）；政策解读 17 条（0.085%）。若把解读也算进政策，政策本体 7,542 条（37.71%）。

这组数字对下游的直接影响是：任何声称「政策库有 20,000 条政策」的说法都不准确，应说「政策库有 20,000 条记录，其中政策本体 7,525 条」。这不是抠字眼，是口径问题——用 20,000 做「政策覆盖率」的分母，会把覆盖率压低近三分之二。

## 三、数据支撑情况

### 3.1 四判定落表

| 依赖维 | 类别 | 源表 / 快照 | 行数 / 覆盖 | 是否可得 | 结论 |
|---|---|---|---|---|---|
| D1 文种 `type` | A（分级） | `dwd_policy_base.type` | 20,000 行，14 种 | 是 | 全量 |
| D2 未标注识别 | A（清洗） | `type='NULL'` | 1,862 行 | 是 | 可识别 |
| D3 大类归并 | B（规则） | 命名前缀 | 4 类 | 是 | 需会签 |
| D4 主题 `theme` | B（分级） | `theme` JSON | 2 行 | 否 | 数据不足 |
| D5 关键词 | C（不可得） | `keywords`/`keypoints` | 0 行 | 否 | 全空 |
| D6 政策工具 | C（不可得） | `policy_support` | 0 行有效 | 否 | 全 `'null'` |

**四判定（§〇）**：直接结构/数据 = 否 / 否（无现成结果面）；依赖结构 = 有（`type` 单列）；依赖数据 = **部分**（文种足、主题不足）；综合 → **部分支持**。

### 3.2 字段级填充率

| 字段 | 有值行数 | 占 20,000 | 本件用途 |
|---|---:|---:|---|
| `type` 非 `'NULL'` | 18,138 | 90.69% | 13 种有效文种 |
| `type='NULL'` | 1,862 | 9.31% | 未标注档 |
| `theme` 非空 | 2 | 0.01% | 主题诊断（不足） |
| `keywords` 非空 | 0 | 0% | 不可用 |
| `keypoints` 非空 | 0 | 0% | 不可用 |
| `policy_support` 有效 | 0 | 0% | 不可用（全小写 `'null'`） |

### 3.3 缺口清单（逐条给补法）

| # | 缺口 | 影响 | 补法 | 补齐后能否算 |
|---|---|---|---|---|
| G1 | `theme` 仅 2 行 | 主题三分法不可算 | 回溯源库补主题标引 | 能 |
| G2 | `keywords` 0 行 | 无法用关键词归类 | 同上 | 能 |
| G3 | `policy_support` 全 `'null'` | 工具分类不可算 | 重新解析原始 JSON | 能，需源侧修 |
| G4 | `type` 未标注 1,862 | 9.31% 文种未知 | 按标题规则回补 | 能，需抽检 |
| G5 | 大类归并靠前缀 | 口径可争议 | 甲方会签 | 能 |
| G6 | 无多标签文种 | 一条政策只能一个文种 | 补多标签 | 能 |
| G7 | 无「政策/非政策」标记 | 纯度靠文种推断 | 补 `is_policy` 布尔 | 能 |

G1—G3 是主题维度的三条硬缺口，也是本件判「部分支持」的全部理由。G4—G7 属文种维度的质量问题，不影响可算性。

### 3.4 结构支持判定

文种维度的结构是干净的：单列、单值、14 种取值、命名稳定。这种结构下 `GROUP BY` 是唯一正确解法，不需要 JSON 解析、不需要 join。风险只在清洗：`'NULL'` 是字面量、前缀归并是人为规则。把这两点写进产物后，文种分布可以视为**完全可复现**。

主题维度的结构也在（`theme` 是 JSON 数组，标签体系可见），但数据只有 2 行。按四档定义，「结构在、数据不足」落在「部分支持」，不落「完全不支持」——后者要求结构也没有。

### 3.5 与已交付政策件的口径差

`M_CHAIN_POLICY_MATCH_SCORE` 把 620 条招标类记录排除在「有效政策」之外，本件的「事务通知类 10,596 条」与它的排除逻辑方向一致但不完全重合：招标类是文种之外的另一条线索。两件不能直接相减，否则会把「申报通知」误当「招标」。

`M_CHAIN_SZ_POLICY` 用的文种分布与本件同源（共用快照），深圳 879 条在各文种上的分布可直接从本件 `type_dist` 按城市过滤复算，不需要另建口径。

## 四、数据缺失情况与结论边界

### 4.1 缺口的后果归因

**主题三分法不可算 → 需求原意无法满足。** 这是本件最重的结论。甲方要的是「产业/人才/企业扶持」，本件只能给「管理办法/申报通知/公示公告」。两者不是粒度差异，是分类轴不同。任何把文种当主题的映射（例如「申报通知=企业扶持」）都会错得离谱：一条人才申报通知和一条产业申报通知在文种上完全相同。

**`type` 未标注 1,862 行 → 文种分布有 9.31% 的灰区。** 这 1,862 行不能摊进任何文种，也不该被静默剔除。页面应保留「未标注」扇区，否则 14 项占比之和不足 100%。

**`policy_support` 全 `'null'` → 政策工具维度为零。** 这条影响的不只是本件，任何想做「补贴力度/税收优惠/金融支持」分布的指标都缺原料。

**文种纯度 37.625% → 「政策库规模」不能直接用 20,000。** 这是口径问题而非数据问题，但后果很实际：用 20,000 做分母算政策覆盖率，会系统性低估。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

- **`'NULL'` 是字面量**：`type` 1,862 行、`theme`/`keywords`/`keypoints` 用大写 `'NULL'`，`IS NULL` 查不到。
- **`policy_support` 是小写 `'null'`**：`JSON_LENGTH` 返回 1，看似有值，实为空。
- **`table_rows=18,808` 不准**：实测 20,000，差 1,192 行。
- **文种不是主题**：14 种取值全是文体名，没有一个主题标签。
- **`theme` 的 2 行是样本不是分布**：不能拿 5 个标签反推全库主题结构。

### 4.3 可构建但存在缺口（不是「无法构建」）

1. **主题三分法**：补标引后可算，当前不可算。
2. **政策工具分布**：修 `policy_support` 后可算。
3. **文种×级别交叉**：`type` 与 `rank` 同表，可直接交叉。
4. **文种×城市交叉**：与深圳件共用快照，可直接过滤。
5. **政策/非政策二分**：用 `type` 前缀可近似，但需人工抽检 1,862 行未标注。

### 4.4 结论与发布建议

**建议上线文种分布，不上线主题分布。** 页面饼图用 14 种文种（或 4 大类），图例注明「未标注 9.31%」；同时在页面配置里**不要**出现「产业政策/人才政策/企业扶持政策」这三个筛选项，因为点进去没有数据。

若产品坚持要三分法，正确路径是回源补 `theme` 标引，而不是让开发在 `type` 上做映射。本件已在 `requested_taxonomy` 里写明 `derivable_from_type=false`、`derivable_from_theme=false`，作为否定性证据留档。

**待甲方裁决点**：① 大类归并是否按前缀；② 政策解读是否并入政策文件类；③ 1,862 行未标注是否回补；④ 是否启动主题标引。

### 4.5 发布口径建议（可直接抄进页面配置）

| 页面元素 | 建议文案 | 依据 |
|---|---|---|
| 饼图主分类 | 其他通知 28.91% / 管理办法 18.54% / 公示公告 14.975% | `type_dist` |
| 灰色扇区 | 未标注 9.31%（1,862 条） | `type_dist` |
| 大类切换 | 事务通知 52.98% / 政策文件 34.405% / 规范性文件 3.22% / 解读 0.085% | `type_class_dist` |
| 政策本体口径 | 7,525 条（37.625%），非 20,000 | `document_purity` |
| 主题筛选 | 暂不上线 | `topic_dimension` |

### 4.6 对下游复用的三条提醒

1. **不要把 `type` 当主题**：它回答「这是什么文件」，不回答「这政策扶持谁」。
2. **不要把 `'NULL'` 当缺失丢掉**：丢掉会让分母变成 18,138，与总数件冲突。
3. **不要用 20,000 当政策数**：政策本体 7,525 条，其余是通知与解读。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答三问：① 文种分布能不能现在出；② 需求要的主题三分法能不能出；③ 未标注 1,862 行怎么处理。范围限定 `type` 一列及三个主题候选字段。
