## 摘要

供应链结构指标不是一张表，而是一组定义在「供应子图」上的图指标：供应商数量是入度，供应商间距离是子图最短路径，稳定性是同一条边跨年存续比例，密度是边数除以节点对数，关系紧密度是边权的均值或分位。五者共用同一个前提：存在一张「供应商 → 采购方」的有向边表，且边上有时间与强度。

这个前提在两库里都不成立。gkx 侧 280 张表、6,312 列逐列扫描，表名命中 `supply` 的 0 张，列名命中 `supplier` 的 0 列，唯一带「采购」字样的列是 `dwd_bid_base_out.estimated_purchasing_time`（招标预计采购时间），语义不是供应关系。live 侧有同名表 `enterprise_supply_chain`，但 0 行；`enterprise_industry_chain` 也是 0 行。唯一能摸到边的是 `graph_edge`：589 条边里 152 条 `relation_type='supply'`，涉及 80 个起点、79 个终点、145 个节点。

这 152 条边不够，也不对。不够，是因为 145 个节点只占底册 189,116 家的 0.077%，平均度 1.05，连度分布的形状都画不出来；不对，是因为同一 `relation_type='supply'` 下 `props` 既写 `type=supplier` 又写 `type=customer`，方向语义自相矛盾，而且没有交易额、没有起止日期，五个子指标里有三个连输入字段都凑不齐。

替代路径也逐一否掉：投资边 46,967 条、股权边 400,286 条，是所有权不是供货；中标共现 39,520 条、29,429 个项目，98.8855% 的项目只有 1 家中标，可配对项目仅 328 个，共现还是无向的。20261020 旧稿判「部分支持」，依据是演示库 `enterprise_supply_chain` 85,791 行、123,294 节点；20261021 口径排除演示面后，这份依据不再有效，判档随之降为 **完全不支持**。

## 一、需求定义概述

### 1.1 所属功能模块

本指标服务企业结构分析中的「供应链结构」，用于描述一家企业在上游供应网络中的位置与关系质量。它不是页面上的单值卡片，而是由五个子指标组成的图分析族。

| 项目 | 内容 |
|---|---|
| 一级模块 | 企业分析 |
| 二级模块 | 企业结构 |
| 三级模块 | 供应链结构 |
| 需求出处 | 科技专题算法库需求·企业结构分析（页面引用，seed 未登记） |
| 输出形态 | 五子指标：供应商数量 / 距离 / 稳定性 / 密度 / 紧密度 |
| 更新频率 | 年（稳定性需年面板） |
| 粒度 | 企业（节点）与供应边（有向） |

### 1.2 为什么需要这个指标

单看一家企业的专利、营收、员工数，回答不了「它在产业链里卡在什么位置」。供应链结构补的是关系面：一家企业有多少直接供应商（入度），供应商之间是否互相认识（距离），这些供应关系是长期还是临时（稳定性），整个供应子图是稠密还是稀疏（密度），关系是强是弱（紧密度）。

这五个问题在招商与稳链场景里对应五种动作。入度低的重点企业是「单点依赖」，需要补链；供应商间距离短说明圈子封闭，可以整群招引；稳定性差说明供应关系在流失，需要预警；密度低说明本地配套不足；紧密度低说明合作停留在浅层交易。

也正因为它们都是图指标，对数据的要求比普通计数指标高一个量级：不仅要边，还要方向、时间和权重。缺任何一项，五子指标里就有一组算不出来。

### 1.3 需求文档是否给出定义方法

**calc-logic 没有正本，需求文档也没有给出公式。** `REM_QUEUE_20261023.json` 里本件的 `calc_logic` 与 `wanghui` 都是 `null`，只给了 4 张候选表与 1 个 blocking 表 `enterprise_supply_chain`。20261019 版文档明确写「王惠与 calc-logic 均未定义；沿用 20261016 调研 AI 依 seed/需求文档拟的口径」。

因此本件的口径是「AI 拟定 + 需求语义约束」，不是甲方确认的公式。这一点必须在交付时讲清楚：五子指标的定义可以讨论，但无论怎么定义，都需要一张带方向、时间、强度的供应边表；这张表不存在，定义再改也算不出。

需求文档《科技专题算法库需求》对「供应链结构」只有一句功能级描述，没有字段级要求。它要求「对接企业数据库，采集并清洗供应链关系」，但没有说明供应关系从哪个系统来、以什么粒度记录、是否含交易额。

## 三、数据支撑情况

### 3.1 目标口径的五个子指标

五个子指标共用一张供应边表 $E$，节点集 $V$ 为企业，边 $(u,v) \in E$ 表示「$u$ 向 $v$ 供货」。定义如下：

| 子指标 | 图定义 | 需要的字段 |
|---|---|---|
| 供应商数量 | 以目标企业为终点的不同上游节点数 | `supplier_org_id`、`buyer_org_id` |
| 供应商间距离 | 供应子图上供应商两两最短路径 | 同上 + 连通性 |
| 供应商稳定性 | 同一供应边在相邻年度的存续比例 | 同上 + `start_date`、`end_date` |
| 供应链密度 | $E / (N(N-1))$ | 边数、节点数 |
| 关系紧密度 | 边权均值或分位 | `trade_amount` 或关系强度字段 |

五者不是同一条 SQL 的五个聚合，而是五个图算法。供应商数量可以一条 `GROUP BY` 出；距离要跑 BFS；稳定性要年面板；密度要全局边数与节点数；紧密度要边权分布。这意味着即使只有「边表但无时间无权重」，也只能算前两个和第四个，且第四个的分母 $N(N-1)$ 需要确定节点域（全底册还是子图），口径必须先定。

本件的判定不是「五缺一」的降档，而是五个全缺：边表本身不存在，五个子指标的输入都不成立。

### 3.2 gkx 侧否定探针

对 `code/_snapshots21/gkx_columns_20261023.json` 做全库列扫描，结果如下。这张字典覆盖 gkx 280 张表、6,312 列，是本件否定证据的主面。

| 探针 | 匹配规则 | 命中 |
|---|---|---|
| 表名含 supply | `table LIKE '%supply%'` | **0** |
| 表名含 supplier | `table LIKE '%supplier%'` | **0** |
| 表名含 purchase/procure | `table LIKE '%purchase%'` | 0（仅列名有 purchasing） |
| 列名含 supplier | `column LIKE '%supplier%'` | **0** |
| 列名含 supply | `column LIKE '%supply%'` | **0** |
| 列名含 buyer/customer | `column LIKE '%buyer%'` / `%customer%` | 0 |
| 列名含 trade_amount | 精确/模糊 | 0（`dwd_org_invest_info.investment_amount` 是投资额） |
| 列名含 purchasing | 模糊 | 1：`dwd_bid_base_out.estimated_purchasing_time` |

唯一命中的 `estimated_purchasing_time` 是招标公告里的「预计采购时间」，描述的是采购方什么时候买东西，不是「谁卖给谁」。把它当供应边会造成两个错误：一是把招标计划当成已发生的交易，二是同一项目的中标人与采购人之间是合同关系，不是供应网络中的上下游。

因此 gkx 侧的结论是**结构级不存在**：不是数据稀疏、不是覆盖不足，而是整个库里没有供应关系的表或列。这一条足以支撑「完全不支持」，后面的 live 探针是补充证据。

145 个节点、152 条边意味着平均每个节点只有 1.05 条边。这个规模连「度分布」都画不出来：绝大多数节点度数为 1，少数枢纽节点撑起整张图，任何中心性、距离、密度的估计都会被子图边界主导。用这 152 条边算「供应商间距离」，得到的不是供应链结构，而是这 145 个节点被抽样时的连接方式。

### 3.4 替代边逐条否证

| 替代候选 | 行数 | 为什么不能当供应边 |
|---|---:|---|
| `gkx.dwd_org_invest_info` | 46,967 | 对外投资是所有权关系，方向是「投资方 → 被投方」，不是「供货方 → 采购方」 |
| `gkx.dwd_org_shareholder_info` | 400,286 | 股东关系，同上；且同一对企业可互为股东，方向不唯一 |
| `gkx.dwd_bid_win_candidate_out` | 39,520 | 中标记录，采购人与中标人是合同关系；共现无向 |
| `graph_edge` `parent_sub` | 22 | 母子关系，是股权不是供货 |
| `graph_edge` `cooperate` | 74 | 合作关系，无方向、无金额 |

**投资边**：46,967 条看起来量还可以，但语义是「A 投资了 B」。用投资边算「供应商数量」，得到的是「被投企业数量」，两者在集团内部可能重合，在集团外部完全不重合。更关键的是方向：投资边的方向是资金流向，供应边的方向是货物流向，两者可以相反（供应商投资客户、客户投资供应商都常见）。

**股权边**：400,286 条是两库中最大的关系边集，但它是股东名册，同一对企业可能互为股东（交叉持股），也可能一股多投。用它建图会得到有环的所有权网络，不是供应链。

**中标共现**：39,520 条记录、29,429 个项目、12,528 家企业。项目规模分布极度偏斜：单中标人项目 29,101 个（98.8855%），2 家 289 个、3 家 31 个、4 家 6 个、5 家 1 个、最大项目 2,302 条。可配对项目只有 328 个（1.11%），且共现是「同一项目的中标人」，不是「上下游」。最大项目 2,302 条会把共现图拉成一个星形，任何密度指标都会被这个项目主导。

四种替代都不成立。这不是「替代后精度下降」的问题，而是「替代后指标含义变了」：投资网络密度、股权网络密度、中标共现网络密度，都不是供应链密度。

### 3.5 旧稿对比与降档理由

20261020 版判「部分支持」，依据是演示库 `enterprise_supply_chain` 85,791 行、123,294 节点。20261019 版更判「完全转换支持」，理由是「demo 库源表齐备可直查出数」。两版的共同前提是演示面可用。

20261021 口径只允许「开发库 + 三方库（gkx）」，仅排除 `demo_*`。演示库的 85,791 行边不在允许面内；gkx 无替代表；live 同名表 0 行。因此判档从「可算不可信」降为「不可算」。

| 维度 | 20261020 旧稿 | 20261021 本件 | 差异原因 |
|---|---|---|---|
| 判档 | 部分支持 | 完全不支持 | 演示面被排除 |
| 边表行数 | 85,791（演示） | 0（live） | 演示面不可用 |
| 节点数 | 123,294（演示） | 145（graph_edge） | 同上 |
| 五子指标 | 部分可算 | 全部不可算 | 同上 |
| 判定类型 | 数据缺口 | negative_evidence | 结构级不存在 |

这里要说清一个区别：20261020 的「部分支持」不是错在算法，而是错在证据面。它把演示库的边当成了可用的边，同时用「演示值不可信」作为降档理由。20261021 的口径更硬：演示数据连证据资格都没有，所以不再是「算出来不可信」，而是「根本算不出来」。

### 3.6 样本量门槛

即使甲方明天补一张供应边表，也不是有行数就能算。五个子指标各有最低样本要求：

| 子指标 | 最低要求 | 理由 |
|---|---|---|
| 供应商数量 | 覆盖底册 ≥10% 企业，每家 ≥2 条边 | 只有 1 条边的企业入度恒为 1，无分布 |
| 供应商间距离 | 子图连通分量 ≥3 个节点 | 两点之间的最短路恒为 1 |
| 供应商稳定性 | 连续 ≥3 年同一边表 | 两年只能算一次存续，不能算比例 |
| 供应链密度 | 节点域明确 + 边数 ≥10 万 | 152 条边的密度在 $10^{-9}$ 量级，无意义 |
| 关系紧密度 | 边权为真实交易额或披露强度 | 0—1 的归一权重无法还原金额 |

按这个门槛，152 条边距离「能算」还差三个数量级。本件在产物里写了 `recompute_recipe_if_data_arrives`，列出所需字段与最小行数，供甲方补数时对照。

### 3.7 结构支持判定

结构侧同样不成立。目标口径需要 7 个字段：供应商 id、采购方 id、关系类型、交易额、起始日、终止日、来源。gkx 侧 0 个，live `graph_edge` 侧只有 2 个（两个 id 与关系类型），缺 4 个（金额、起止、来源、稳定方向）。`enterprise_supply_chain` 表若有数据，结构可能够，但它是 0 行，无法验证字段。

所以「结构支持」这一行也判否，而不是「结构有、数据缺」。这一点决定了本件不能落在「部分支持」：部分支持的前提是结构在、只是某个维度缺数据；本件是结构级缺失。

## 四、数据缺失情况

### 4.1 缺口清单

| 编号 | 缺口 | 影响 | 严重度 | 可否代理 |
|---|---|---|---|---|
| G1 | 供应边表（gkx） | 五子指标全部 | 致命 | 否 |
| G2 | live 同名表 0 行 | 五子指标全部 | 致命 | 否 |
| G3 | 边方向语义 | 入度/出度不可分 | 高 | 否 |
| G4 | 交易额/强度 | 关系紧密度 | 高 | 否 |
| G5 | 边起止时间 | 稳定性 | 高 | 否 |
| G6 | 节点覆盖 | 距离/密度 | 高 | 否（0.077%） |
| G7 | 来源与披露 | 可信度 | 中 | 否 |

### 4.2 逐条影响

G1 与 G2 是同一个缺口的两个面：结构面在 gkx 完全没有，数据面在 live 是空表。两者合起来意味着「两库都没有可用的供应边」，这是判「完全不支持」的直接依据。

G3 决定入度能不能算。供应边必须是有向的「供应商 → 采购方」；如果方向靠 `props.type` 逐条标注，且同一 `relation_type` 下混着 supplier 与 customer，那么同一张表既可能被读成入度也可能被读成出度。方向不确定，供应商数量就不是一个良定义的量。

G4 决定紧密度能不能算。`weight` 是 0—1 的归一值，没有单位、没有金额字段，也没有说明它是交易额归一还是合作频次归一。用它算均值可以得到一个数，但这个数不能解释成「平均交易额」，也不能跨企业比较。

G5 决定稳定性能不能算。稳定性要「同一条边在相邻年度是否存续」，需要边的业务起止时间或逐年快照。`graph_edge` 只有 `create_time`（入库时间），没有业务起始日，也没有终止日；单期快照无法构造面板。

G6 决定距离与密度能不能算。145 个节点、152 条边，平均度 1.05，子图大量是一棵棵孤立的树甚至孤立边。在这种图上跑最短路，绝大多数点对不可达；算密度，分母用全底册还是用 145 个节点会差六个数量级。

G7 决定这份数据能不能被引用。供应关系是商业敏感数据，正规数据源会带披露来源（年报、公告、海关、供应链平台）。`graph_edge` 没有 `source` 字段，无法判断一条边是来自公开披露还是推断。

### 4.3 明确不做什么（禁止的替代）

1. 不用投资边冒充供应边。所有权与货物流是两种关系，方向、语义、时间粒度都不同。
2. 不用股权边冒充供应边。股东名册不是供应商名册。
3. 不用中标共现冒充供应边。共现无向，且 98.89% 的项目只有 1 家中标。
4. 不用 `graph_edge` 的 152 条边出「供应链密度」。样本 0.077%，出的数是抽样噪声。
5. 不用 `weight` 冒充交易额。它是无量纲归一值。
6. 不用演示库 `enterprise_supply_chain` 的 85,791 行做证据。演示面已排除。
7. 不用「行业投入产出系数」替代企业级供应关系。粒度不同，不能下钻到企业。
8. 不把「不可算」写成「算出来是 0」。0 是一个结果，不可算是没有结果。

### 4.4 若甲方补齐后的口径升级路径

第一步补一张企业级供应边表，最小字段集是 `supplier_org_id / buyer_org_id / relation_type / trade_amount / start_date / end_date / source`。第二步把它接入节点域（底册 189,116 家），确保供应商与采购方都能绑到 `org_id`。第三步补至少 3 年快照，才能算稳定性。第四步定义密度的节点域（全底册 / 某产业链 / 某区域子图），否则密度不可比。

四步完成后，五子指标可从「全部不可算」升到「可算」；判档能否到完全转换支持，取决于边表覆盖率。按 §3.6 的门槛，覆盖底册 ≥10%、每家 ≥2 条边是底线。

如果只能补一项，优先补「边表 + 方向」。没有边，其余都是空谈；有了边但方向不清，供应商数量这一最基础的子指标仍然是错的。

## 五、方法对照与选用建议

### 5.1 四种可选口径

| 口径 | 数据要求 | 现在可算 | 能回答什么 |
|---|---|---|---|
| A 企业级供应边图 | 有向边 + 金额 + 时间 | 否 | 五子指标全部 |
| B 行业投入产出 | 行业 × 行业流量 | 否（无 IO 表） | 行业间依赖 |
| C 中标共现 | 项目-中标人 | 是（但无向） | 本地投标圈 |
| D 股权/投资网络 | 投资/股东边 | 是 | 集团归属 |

### 5.2 选用建议

不建议用 C 或 D 顶替 A。C 能回答「哪些企业常在同一项目里出现」，这是一个有价值的本地化指标，但它是「投标共现结构」，不是「供应链结构」；如果要交付，应另立指标名，不要挂在 `M_ENT_SUPPLY_STRUCT_TOPIC` 下。D 同理，它是集团网络，不是供应网络。

如果甲方短期只要一个「能上图」的供应链示意，可以用 `graph_edge` 的 152 条边做一张「样本图」，但必须标注「样本 145 节点、非全量、不可用于度分布与密度结论」。这属于演示，不属于指标交付。

### 5.3 与同族件的口径对齐

本件的「不可算」结论与 `M_ENT_INDUSTRY_CHAIN_*` 系列不冲突：后者算的是企业挂链（`dwd_org_industry_tags` 可支撑），本件算的是企业之间的供货边。挂链是「企业属于哪条链」，供应是「企业向谁供货」；前者是属性，后者是关系。不能因为挂链可算，就推断供应链可算。

与本件最接近的是 `M_CHAIN_*` 系列的链属企业计数：那些件用 `chain_firm_index_20261023.json` 的 1,714,457 家链属企业做分母，回答「链上有多少家」，不回答「链内谁供谁」。跨件引用时要区分「链属」与「供应」。

## 附录 G 口径问答

**问：为什么不能像链属指标那样用挂链表替代？**
答：挂链表回答「企业属于哪条产业链」，是节点属性；供应链回答「企业向谁供货」，是节点之间的关系。属性可以替代属性，不能替代关系。

**问：152 条边为什么不能算密度？**
答：密度是边数除以节点对数。145 个节点的完全图有 10,440 条可能边，152 条对应的密度是 0.0146；但这个 145 是抽样出来的，不是真实节点域，换一个节点域密度就变。分母不确定，密度不可比。

**问：中标共现有 29,429 个项目，为什么还说样本不够？**
答：98.8855% 的项目只有 1 家中标，没有共现对；可配对项目只有 328 个。共现还只是无向关联，不是供应方向。

**问：旧稿说演示库有 85,791 条边，为什么不能用？**
答：20261021 口径只允许开发库 + gkx，仅排除演示面。演示库的边不在允许面内，连证据资格都没有。

**问：本件判完全不支持，是不是说明这个指标不重要？**
答：不是。它说明数据侧还没有具备可算条件。指标定义可以保留，等甲方补边表后按 §4.4 升级。
