## 摘要

`M_INNOV_DS_FACTORS_019` 在指标注册表里是一个 **OPEN draft 身份的镜像条目**：它的 definition、formula、source_tables 三个字段的值都是同一句话——「同 M_INNOV_FACTOR_ANOMALY-监测异常点识别」。这意味着它不引入新口径，只承担一个验收单元（DS-FACTORS-019）的登记职责。

镜像条目最容易出的问题，是「两份实现慢慢漂移」：今天改了母条目的低基数门槛，明天忘了改镜像，两边出的命中期次就不一样，而文档还都写着「同」。本批的处置是让镜像脚本**直接 import 母条目模块**，复用同一份 `build_series()` 与 `run_all()`，再把结果与母条目落盘的缓存逐序列、逐口径比对。实测 20 个比对单元全部 `identical`，`mirror_all_identical=true`——这不是「结果看起来差不多」，是「同一个函数跑两遍，逐位相等」。

第二个要交代的是 DS 侧声明的输入清单。DS 条目声明的数据是六类：专利、中文论文、机构、学者、英文论文、项目；实际落地的只有三类（中文论文、机构新设、项目立项），另三类各有硬原因：专利序列只有 2021—2026 共 6 期、学者是截面表没有按年存量、英文论文只有 1,387 行且 88% 堆在 2026。这个 3/6 必须写在文档正文，否则甲方按 DS 口径核对时会以为六类都算了。

结论：镜像关系成立、实现可复现、判档与母条目一致，判**部分支持**。§六 的具体建议是：**不要在注册表里长期保留两条同口径条目**，DS-FACTORS-019 应在母条目验收后标为 `merged`，只留作验收单元编号。

功能位置与母条目完全相同：**科技信息展示系统 → 科技发展态势 → 科技全域态势 → 异常监测**。需求原文仍是一句「提供异常监测功能，自动识别和标记数据异常点和突变点」。

### 1.2 为什么需要这个「镜像」条目

因为登记与实现是两条线。登记线按 DS 编号逐个清账（DS-FACTORS-001…019…），实现线按口径去重（同一个「监测异常点识别」只该有一套算法）。如果强行让 019 拥有独立实现，就会出现两份几乎相同的代码，维护成本翻倍且必然漂移；如果直接删掉 019，登记线就少一个编号，`GAP-ALGO-TYPE-UNSIGNED` 这条缺口在台账上关不掉。

镜像条目就是这两条线的交点：**编号保留、实现复用、一致性可证**。它在产品上不产生任何新界面元素，在数据上不产生任何新表，只在验收时提供一个可核对的等价性证明。

## 二、计算过程

> 以下读数全部由 `code/M_INNOV_DS_FACTORS_019.py` 实测产出，结果见 `M_INNOV_DS_FACTORS_019_out.json`（与母条目 `M_INNOV_FACTOR_ANOMALY_out.json` 逐位一致）。

### 2.1 方法定位：镜像不是第二套算法

如果 019 自己实现一遍 MAD，就有两个隐患：① 常数抄错（3.5 抄成 3.0）；② 边界处理不一致（`MAD=0` 时一边用平均绝对偏差、一边直接跳过）。这两种偏差都不会报错，只会让两次运行给出不同期次，而文档两边都写着「同」。

因此本批的实现方式是**模块级复用**：`M_INNOV_DS_FACTORS_019.py` 用 `importlib.import_module("M_INNOV_FACTOR_ANOMALY")` 拿到母模块，直接调用 `build_series()` 与 `run_all()`。这样 019 里不存在任何自己的阈值常数，也不存在自己的序列拼装逻辑——**两份结果的差异只可能来自母条目自身的不确定性，而母条目读的是同一份缓存，所以差异为零**。

代价是 019 不能独立演进。如果将来母条目改口径，019 会自动跟着改，一致性天然保持，但 019 也无法保留旧版口径。对本条目这是可接受的：它的职责就是「等价」，不是「另一个版本」。

五条序列的读数由母条目 `build_series()` 从 `a16_raw_series.json` 读入，019 不重复拉库：

| 序列 | 期数 | 起止 | 合计 | 是否合格 |
|---|---:|---|---:|---|
| 专利年度件数 | 6 | 2021—2026 | 2,939,895 | 不合格（6 < 8） |
| 中文论文年度 | 46 | 1980—2025 | 97,911 | 合格 |
| 学者-论文关系年度 | 38 | 1988—2025 | 1,042,886 | 合格 |
| 机构新设年度 | 46 | 1980—2025 | 188,580 | 合格 |
| 项目立项年度 | 38 | 1986—2023 | 58,453 | 合格 |

专利序列的六期读数 604,512 / 601,893 / 611,811 / 606,468 / 440,401 / 74,810 全部来自面板缓存，**一条专利 SQL 都没发**。这条纪律在本条目尤其重要：019 与母条目如果各自去查一次 294 万行的 `dwd_patent`，就是双倍压力，而它们本来只需要同一份缓存。

### 2.3 步骤 2｜四套口径并行 + 逐位镜像核对

四套口径与母条目完全相同：`levels`（全序列中枢，口径原式）、`rolling`（前 5 期滚动中枢）、`yoy`（同比中枢）、`yoy_floor`（同比 + 1% 峰值低基数门槛，推荐）。阈值固定 3.5，突变阈值 MAD×3，长度门槛 8 期。

核对方式：对每条序列的每个口径，比对三项——异常数 `n_anomalies`、突变数 `n_mutations`、异常年份列表。实测结果：

| 序列 | levels | rolling | yoy | yoy_floor | identical |
|---|---|---|---|---|---|
| patent_year | true | true | true | true | **是** |
| zh_paper_year | true | true | true | true | **是** |
| scholar_rel_year | true | true | true | true | **是** |
| org_reg_year | true | true | true | true | **是** |
| project_year | true | true | true | true | **是** |

20 个比对单元全部相等，`mirror_all_identical=true`。命中数汇总：levels 42、rolling 25、yoy 17、yoy_floor 13。

这里要说明一点：**levels 的 42 期不是「42 个异常」**，其中 19 期来自中文论文序列（占该序列 41.3%），是增长趋势被误判。镜像核对只保证「两边一样」，不保证「结果合理」——合理性由母条目 §2.3 判定为退化，本文沿用该判定。

### 2.4 步骤 3｜DS 声明输入落地映射（3/6）

这是 019 相对母条目**唯一新增的实质内容**。DS 侧声明了六类输入，脚本逐项标注落地状态：

| # | 声明输入 | 实际序列 | landed | 落地说明 |
|---|---|---|---|---|
| 1 | 专利 apdt_year 按年聚合（IPC 领域切片） | patent_year | **false** | 6 期 < 8，按口径不进入检测；IPC 切片未实施（切片后每格更薄） |
| 2 | 中文论文 cover_year_start 按年聚合 | zh_paper_year | true | 1980—2025 共 46 期 |
| 3 | 机构按年存量（底册入集） | org_reg_year | true | 无存量快照年，用 incorporation_year 作新设年序列，**存量口径不可得** |
| 4 | 学者存量（paper_nums/h_index） | scholar_rel_year | **false** | 截面表无按年存量，落地为学者-论文关系条数，**语义已变** |
| 5 | 英文论文 cover_year_start | —— | **false** | 1,387 行、18 个年份档，2026 年 1,222 篇（88%）为残年堆积 |
| 6 | 项目立项年（定义未列，本批补充） | project_year | true | 1986—2023 共 38 期，作对照序列 |

`n_declared_inputs=6`、`n_inputs_landed=3`。三个 false 的性质不同：第 1 项是**长度结构性不足**（补数据才能救），第 4 项是**语义替换**（口径必须改写），第 5 项是**量不足**（扩容才能救）。把三者混成一句「部分支持」会掩盖差异，所以这里分开写。

第 3 项虽然是 true，但它是**降级落地**——底册没有「某年有多少家机构存续」这种快照，只有「某年新注册多少家」。新设年序列测的是「注册节奏」，不是「存量变化」。这一点在母条目里也写了，此处再标一次，因为 DS 侧声明的原文是「机构按年存量」。

### 2.5 步骤 4｜推荐口径的命中结果

### 2.6 步骤 5｜镜像口径下的不变量与敏感性

因为是同一份算法，"敏感性"在 019 里的意义不是「换参数看结果变不变」，而是「换阈值时两个条目的命中集合是否同步变化」。实测四套口径在 2.5 / 3.5 / 5.0 三个阈值下的命中集合完全同步（因为同一个函数、同一份缓存），因此不存在「镜像漂移」这一风险类别。

## 附录 C　镜像类条目的权威实践与可行性（完整版）

### C.1 问题：同一口径为什么要挂两个 ID

指标登记与指标实现是两套账。登记账按验收单元编号清点（DS-FACTORS-001 … 019），实现账按口径去重（同一逻辑只该有一套代码）。两套账不同步时只有三种解法：① 每个编号都独立实现——代码冗余、必然漂移；② 只保留实现账——登记缺口关不掉；③ 编号保留、实现复用、一致性可证——本条目选第三种。

### C.2 权威实践中的对应做法

OECD Frascati Manual 在指标定义表里允许同一概念有多个 code（如「R&D 人员」在不同统计口径下的多个 code），但要求它们指向同一条 definition。Eurostat 的 SDMX 概念表同理：concept 可以有多个 representation，definition 唯一。DAMA-DMBOK 的「单一事实来源」原则则从实现侧给出要求：一份数据只有一个权威来源，多入口只做只读分发。

这三条合起来构成本条目的设计依据：definition 唯一（指向母条目）、实现唯一（import 母模块）、入口可以有多个（DS-FACTORS-019 是一个入口编号）。

### C.3 一致性证明的三种强度

| 强度 | 做法 | 能否发现漂移 |
|---|---|---|
| 弱 | 文档写「同母条目」 | 不能 |
| 中 | 结果表人工比对数个期次 | 能发现大偏差，漏小偏差 |
| 强 | 逐序列逐口径比对异常数、突变数、年份列表 | 能发现任何差异 |

本批采用强证明：20 个比对单元（5 序列 × 4 口径），每个单元比三项。这也是 `gate_check.py` 之外的第二道保险——结构门禁查不出「两份实现悄悄不同步」。

### C.4 数据可行性（与母条目一致）

四条合格序列 38—46 期；专利 6 期；英文论文 1,387 行；学者截面。落地 3/6。镜像不改变任何数据事实，因此可行性结论与母条目相同：部分支持。

### C.5 风险清单

- **重复计数**：同一指标在报表里被数两次，除非按 `mirror_of` 去重。
- **文档双份漂移**：两份文档各自维护，半年后必然不一致；建议母条目验收后把 019 标 `merged`。
- **自动跟随风险**：019 import 母模块，母条目改口径时 019 无预警跟随；需在母条目变更流程里加「同步通知 019」一步。
- **验收口径混淆**：`acceptance_unit_id` 与 `metric_id` 是两套编号，报告里不能混用。

### C.6 可行性总判

实现可行（已跑通、已证等价）、数据部分可行（3/6）、治理需补（去重规则、合并时点）。判**部分支持**，与母条目一致。
