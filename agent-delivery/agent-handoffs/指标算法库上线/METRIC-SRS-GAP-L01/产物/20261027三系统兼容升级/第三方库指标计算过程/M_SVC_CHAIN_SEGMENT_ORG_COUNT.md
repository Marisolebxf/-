## 〇、数据支持度与四判定口径

### 0.1 数据支持度四档

| 档位 | 定义 |
|---|---|
| **完全直接支持** | **开发库+三方库（gkx）**中直接就有该指标（或 100% 语义一致指标/结果面）可用，且数据量完全支持直查/直算 |
| **完全转换支持** | 两库均无现成结果面，但依赖侧的表结构与当前数据量均已足够，现在即可通过转换与加工生成该指标；数据量不足不得入本档 |
| **部分支持** | 无论如何构建，始终有部分依赖维度无法从**开发库+三方库（gkx）**得到足够数据 |
| **完全不支持** | 该指标及其关键依赖维度，在**开发库与三方库（gkx）**均无法构建（结构与数据均不具备可算闭环） |

> **数据源口径**：本件支持度按「开发库 + 三方库（gkx，183.240.141.251:3318 只读）」评估，仅排除 `demo_*`；本机开发库事实面为空壳（`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张），实际取数面为 gkx。

### 0.2 四判定拆分

| 判定项 | 本件结论 |
|---|---|
| 表结构直接支持（开发库+三方库） | 否——gkx 无「机构×环节」成员事实表（SVC-P0-3 待建） |
| 表数据直接支持（开发库+三方库） | 否——同上 |
| 依赖表结构支持（开发库/三方库） | 是——经营范围文本可作为环节命中的代理载体 |
| 依赖表数据支持（开发库/三方库） | 是——45,011 行、文本中位 213 字，足够做词表代理 |

### 0.3 本指标套用（一句话）

六环节计数的「正式口径」依赖一张机构×环节成员表（SVC-P0-3），gkx 与 live 都没有这张表。可执行的替代是「经营范围词表命中」：机构在经营范围里写了某环节的关键词，就认为它在该环节有供给。这是代理，不是事实表——一家机构可能写了但没做，也可能做了但没写。

代理口径下六环节计数为：研发 30,776、IP 776、技术转移 13,878、中试 8、检测 4,533、市场 10,702，去重后 34,578 家参与至少一个环节（池 44,153 家）。因缺正式成员表，判 **部分支持**。

综合上述，本件落 **部分支持**。理由：六环节家数可词表代理现转（pool 44,153 家，六环节去重 34,578 家）；正式「机构×环节」成员事实表在 gkx 与 live 均不存在（SVC-P0-3 待供方），正式口径不可执行

## 摘要

「环节服务机构数」是产业服务链分析最基础的计数：每个环节有多少家机构在供给，直接决定链路图上每个节点的粗细。旧稿在演示库口径下得到 0/151/3/2/412/8 这一组数，其中研发环节为 0，被解读为「研发服务空白」。

本件换到 gkx 后发现该结论不成立：旧稿用的四个窄词（委托研发、联合攻关等）在 45,011 条经营范围里命中 0，但「研发」命中 17,736 家、「技术开发」命中 22,563 家。研发环节不是空白，而是旧词表太窄。换用分层词表后，六环节计数变为 30,776 / 776 / 13,878 / 8 / 4,533 / 10,702，去重 34,578 家。

档位为 **部分支持**：计数可算、可复核，但「机构是否真在该环节供给」没有事实表支撑，且词表宽度会显著改变结论（研发环节从 0 到 30,776 就是词表造成的）。词表敏感性写进 §3.3，并保留单词命中量供甲方调参。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的是产业服务链分析的全链路可视化：链路图有六个环节节点，节点大小由该环节的机构数决定。这个计数同时是瓶颈判定、平均深度、短板分析的输入——分母错了，后面三个指标的结论都会跟着错。

### 1.2 为什么需要这个指标

链路图的说服力全在分母上。若「研发服务」节点显示 0，管理者会得出「本地没有研发服务能力、必须外引」的结论；而真实情况可能是本地有上万家机构在做技术开发，只是没人把它们登记成「委托研发」。一个词表的选择，能改变一个城市的补链政策方向，所以这个指标必须把口径与敏感性一起交付。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。** 需规只要求「统计各环节服务机构数量」，没有给环节的判定规则、也没有给机构与环节的归属依据。旧稿用王惠的词表口径，但词表本身是经验产物，不是需求给定。

### 1.4 指标口径与维度拆解

六环节：研发与科研合作、知识产权与标准、技术转移与孵化、中试熟化、检测认证、市场化服务。每个环节有一组词（宽词 + 窄词），机构命中任一宽词即计入该环节；一家机构可同时属于多个环节（多命中）。

产物同时给 `org_count`（多命中口径）、`share_of_pool`（占池比）与 `count_source=keyword_proxy`（标记为代理），下游若要做「唯一归属」的环节分布，需要另定归属规则（本件不做）。

| 维度/口径 | gkx 字段 | 缺失时的处理 |
|---|---|---|
| 池/机构域 | `dwd_org_org_product_info.org_id` | 按 org_id 去重，不做行数计数 |
| 行业/类型 | `main_activities` 词表 | 未命中归 UNCLASSIFIED，不丢弃 |
| 财务截面 | `dwd_org_annual_financial_info` 最近有值年 | 缺年不补 0，取最近有值年 |
| 风险事件 | `dwd_org_risk_shixin` / `dwd_org_company_punish` | 无记录记 0 件（事件型字段，0 是真实语义） |
| 资讯量 | `dwd_org_important_news_info` 标题条数 | 无资讯记 0，仅作代理 |
| 资本关系 | `dwd_org_invest_info` / `dwd_org_shareholder_info` | 对端解析不了的行丢弃并计数 |

### 1.5 与同域姊妹指标的分工

与 `M_SVC_CHAIN_BOTTLENECK` 的分工：本件只回答「多少家」，BOTTLENECK 回答「这个数量算不算瓶颈」。两者共用同一份环节计数，BOTTLENECK 直接引用本件的 `stage_rows`，不重算。

与 `M_SVC_CHAIN_SEGMENT_AVG_DEPTH` 的分工：本件是分母，AVG_DEPTH 是分子缺失时的空值展示；两者合起来才构成「环节供给的广度与深度」。

### 1.6 本件的边界与不做什么

本件不做三件事：不做唯一归属（多命中就是多命中）、不做年度序列（经营范围是当前状态，没有历史版本）、不用企业规模给计数加权（加权需要可信的规模口径，见 101 的规模缺口）。

## 二、计算过程

### 2.1 数据源与池

池来自 `dwd_org_org_product_info`：45,011 行、去重 44,153 家、`main_activities` 非空。环节命中在该文本上做子串匹配，词表与命中量落在 `svc21_kw_20261022.json`。

### 2.2 词表设计（宽词 / 窄词）

每个环节配一组宽词与一组窄词。宽词保召回（如研发环节的「研发」「技术开发」「研究开发」），窄词保精度（如「委托研发」「联合攻关」）。本件计数用宽词，窄词只用于敏感性对照。

| 环节 | 计数用宽词 | 窄词（仅对照） | 宽词命中 | 窄词命中 |
|---|---|---|---:|---:|
| 研发 | 研发 / 技术开发 / 研究开发 | 委托研发 / 联合攻关 | 30,776 | 0 |
| IP | 专利 / 商标 / 知识产权 / 标准 | 专利代理 / 商标代理 | 776 | — |
| 技术转移 | 技术转让 / 技术转移 / 孵化 | 概念验证 | 13,878 | 0 |
| 中试 | 中试 / 熟化 / 小试 | 熟化 | 8 | 0 |
| 检测 | 检测 / 检验 / 认证 | 检验检测 | 4,533 | — |
| 市场 | 市场 / 营销 / 推广 / 品牌 | 渠道推广 | 10,702 | — |

窄词全 0 是旧稿「研发空白」的直接来源。这不是数据缺失，而是词表与真实表述不匹配：经营范围里几乎不会写「委托研发」，只会写「研发」。

### 2.3 计数口径与去重

环节计数 = 命中该环节任一宽词的机构数（多命中不去重）；跨环节合计 60,673（含重复），去重 34,578 家。两个数都要报：前者用于链路图节点大小，后者用于「有多少机构参与服务链」这类口径。

| 环节 | 机构数 | 占池 |
|---|---:|---:|
| 研发与科研合作 | 30,776 | 69.70% |
| 知识产权与标准 | 776 | 1.76% |
| 技术转移与孵化 | 13,878 | 31.43% |
| 中试熟化 | 8 | 0.02% |
| 检测认证 | 4,533 | 10.27% |
| 市场化服务 | 10,702 | 24.24% |

### 2.4 中试环节的 8 家怎么读

中试熟化只有 8 家，是六环节里最稀疏的一环。这个数不能简单读成「中试服务极缺」：中试是重资产环节，机构数量本来就少；同时「中试」「熟化」这两个词在企业经营范围里出现率极低，很多做中试的企业不会这么写。

本件保留 8 这个数并标注 `keyword_proxy`，同时在 §四 给出「用设备原值/试验平台资质替代词表」的修复路径。在没有平台清单之前，任何「中试空白」的政策结论都应当加限定语。

### 2.5 词表敏感性与旧稿对照

单词命中量（全表口径）：检测 4,533、研发 17,736、技术开发 22,563、技术转让 6,412、技术转移 5,203。同一环节换一个词，计数可以差一个数量级。

| 口径 | 研发 | IP | 转移 | 中试 | 检测 | 市场 |
|---|---:|---:|---:|---:|---:|---:|
| 旧稿（窄词，演示库口径，不再引用） | 0 | 151 | 3 | 2 | 412 | 8 |
| 本件（宽词，gkx） | 30,776 | 776 | 13,878 | 8 | 4,533 | 10,702 |

两版差异不是「换库导致」，而是「换词表导致」。为让甲方能自己验证这一点，产物里保留了每个词的独立命中量，任何一版词表都可以在 5 分钟内重算。

### 2.6 复现代码与结果展示

`cd code && python3 M_SVC_CHAIN_SEGMENT_ORG_COUNT.py`，纯读快照，输出六环节计数与去重数，覆盖写 `_out.json`。

| 产物键 | 取值 |
|---|---|
| `population.distinct_org_id` | 44,153 |
| `stage_union_orgs` | 34,578 |
| `stage_total_with_multiplicity` | 60,673 |
| `stage_rows[*].count_source` | keyword_proxy |

### 2.7 结果解读

从供给广度看，服务链的两端最厚：研发 69.7%、技术转移 31.4%、市场 24.2%；中间三段最薄：IP 1.8%、检测 10.3%、中试 0.02%。这与「服务链中段塌陷」的直觉一致，但必须记住这是词表口径下的形状，不是事实表口径。

对下游：链路图可以按这个形状画，但要在图注写「代理口径、多命中、词表敏感」；瓶颈判定不能只看这个计数（见 BOTTLENECK 的相对短板档）。

### 2.8 与旧稿的差异

旧稿的六个数与结论（研发空白）在 gkx 上不可复现；本件撤回「研发空白」，改为「研发供给最厚、中段最薄」。撤回的理由是词表敏感性实测，不是口径偏好。

### 2.9 参数与常量清单

| 参数 | 取值 | 来源/说明 |
|---|---|---|
| 池规则 | org_id 去重 + 经营范围非空 | 避免 45,011 行 / 44,153 家的重复计数 |
| 标准化 | 截面 min-max 到 [0,1] | 同值给 0.5，不制造极值 |
| 缺维处理 | 空维不进平均、不补 0 | 缺维时按非空维等权，权重分母同步缩小 |
| 最少维度 | ≥2 维非空才出综合值 | 单维噪声不得冒充综合分 |
| 阈值 | 见各件 §2 合成小节 | 需规未给数值，本件按分位或经验值并标注 |
| 年份 | 见产物 `base_years_used/_missing/_note` | 缺失年不摊 0，残年单独标注 |

计算链在本目录闭合：脚本只读 `code/_snapshots21/` 下的四份快照（机构池、底册、词表命中、专利代理样本），不连任何数据库，也不 import 本目录之外的模块。快照自身带 `source` 字段（库名 gkx、主机、拉取时间），因此「文档 → 产物 → 脚本 → 快照 → 源表」这条链上每一跳都能单独打开核对，不存在只在某台机器上偶发能跑通的环节。

对可复现性的一个硬约束是「不许把时间当自变量」：本件所有取值都是截面，不按采集时点做插值或外推；产物里的 `generated_at` 只用于版本标识，不参与任何计算。这样同一份快照在任何一天重跑，除时间戳外结果完全一致，甲方复核时不会遇到「昨天 52 今天 57」这种无法解释的漂移。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺口 | 缺什么 | 影响 | 修复路径 |
|---|---|---|---|
| 机构×环节成员表 | SVC-P0-3 事实表 | 计数只能是代理，无法判定「真实供给」 | 由供方提供成员表，或按服务合同/中标记录反推 |
| 环节唯一归属 | 归属规则 | 多命中导致环节份额不可加总 | 定义主环节优先级（如按营收占比） |
| 中试环节 | 试验平台/设备清单 | 8 家可能严重低估 | 接入大型仪器共享平台与中试基地名录 |
| 年度序列 | 经营范围历史版本 | 只能给截面，不能给趋势 | 接入工商变更历史 |

### 4.2 修复路径与优先级

优先级按「补齐成本 ÷ 解锁维度数」排：成本最低、能一次解锁多个维度缺口的排前面。本批十件的共同短板是「服务过程类数据」（合同、验收、评价、投诉）在 gkx 完全没有承载表，这类缺口不是换字段能解决的，必须等甲方开放业务系统或采购第三方评分。

短期（可在一周内做）优先补「已有表但没接」的部分：把 dwd_org_recruit_info 的 hiring_number、dwd_org_annual_financial_info 的更多科目、dwd_org_org_product_info 的结构化产品字段接进快照。中期（需要建表）补 svc_quality_score / svc_csat_score / svc_success_case_count / svc_coop_edge 四张结果面。长期（需要外部数据）补牌照清单、服务合同、客户评价。

### 4.3 降档论证（为什么不是更高一档）

不抬档的第一条理由：抬档的门槛是「所有必需维度现在都能算出足够数据」，而本件至少有一维是结构性无源——不是「样本少」，而是「库里没有这张表、也没有可替代的字段」。这类缺口换写法、加 SQL 都补不出来。

不抬档的第二条理由：本件的代理关系是「语义降级」而非「同义转换」。例如用资讯条数代理服务质量，代理量测的是曝光度，方向可能相反（负面新闻也会推高条数）。只要存在这种方向性风险，就不能称「完全转换支持」。

不降档的理由：主体维度确有量、能算、能复核，且排序结果与行业常识不冲突（见 §2.8 的极值回查），不属于「完全不支持」。故最终判 **部分支持**。

### 4.4 缺口对下游的影响

缺口的第一层影响是「指标语义不完整」：缺一维时综合值仍能算，但它回答的问题已经变了。例如技术力指数若缺「融资成本」，高分机构可能只是「资本多、风险低」，而不是「融资便宜」。

第二层影响是「跨指标不可比」：两件指标若缺的维度不同，排序差异无法归因到机构本身，只能归因到口径差异。本批十件因此统一了池规则、标准化与缺维处理三条，尽量把差异压到维度选择上。

第三层影响是「展示必须带限定语」：凡缺维的指标，前端角标要写明「本指标不含 X 维」，否则用户会默认它是全维度评价。这一点写进 §附录 C 的交付清单。

## 五、王惠方法对照与选用建议

王惠调研稿（20260829 批次规范化迁移）给出的口径，是本批十件里唯一有「维度名 + 可执行代理规则」的版本：它把需求原文的定性描述翻译成「哪张表、哪个字段、缺了用什么代理、缺维怎么处理」，并显式登记了待建项。本件沿用其维度划分与合成骨架，只把数据来源从旧库口径整体换到 gkx，并把代理规则逐条落进脚本。

与官方口径对照：需求原文本身不给公式（见 §1.3），故不存在「官方公式 vs 王惠公式」的正面冲突；可比的只有维度语义。国家统计局《国家科技服务业统计分类（2018）》提供的是行业边界而非评分方法，OECD/JRC 复合指标手册提供的是「标准化—赋权—聚合—敏感性」的通用流程，二者与王惠口径不矛盾。

与替代路径对照：一条常见替代是「用专利/研发等硬指标直接排序」，优点是客观，缺点是把服务能力窄化为创新能力，对咨询、营销、人力类机构几乎失效；另一条是「纯专家打分」，可解释但不能复算。王惠口径走的是「可复算的代理 + 显式披露缺口」中间路线，与本项目「数字必须能指到落盘文件」的交付要求一致。

### 5.4 替代路径对比

| 路径 | 优点 | 缺点 | 本件取舍 |
|---|---|---|---|
| 纯硬指标排序（专利/研发） | 客观、可复算 | 把服务能力窄化为创新能力，咨询/营销/人力类失效 | 不采用，仅作旁证 |
| 纯专家打分 | 可解释、贴合行业 | 不可复算，无法审计 | 不采用 |
| 本件：代理 + 显式缺口 | 可复算、缺口可追责 | 代理存在语义降级 | 采用 |

**选用建议**：采纳王惠的六环节划分；词表由窄改宽并附敏感性对照，撤回旧稿「研发空白」结论。

## 附录 G 常见误读与纠正

**问：为什么分母是 44,153 而不是底册 189,116？**

底册是全量法人库（189,116 行），其中绝大多数不是服务机构。本批统一以「经营范围里出现服务类表述」作为服务机构的可操作定义，故分母是 44,153。若甲方有正式的服务机构认定名单，应替换分母并重跑全部十件。

**问：为什么同一家机构会出现在多个环节/类型里？**

因为代理口径是「经营范围命中」，不是「唯一归属」。经营范围是一段自由文本，一家机构可以同时写研发、检测、销售。产物同时给多命中与主类两列，就是为了让下游按需选择，而不是让本件替甲方决定归属。

**问：数字能不能直接和旧稿比？**

不能比绝对数，只能比结构与排序。旧稿的分母是人工圈选名单（43,296），本件是经营范围实体（44,153），两者不是同一个总体；此外旧稿的分类器列与词表口径也不同。

**问：缺维为什么不补 0？**

补 0 等于断言「该机构在这一维得分为 0」，而事实是「我们不知道」。这会把「无数据」伪装成「表现最差」，系统性压低数据稀疏机构的排名。本件的做法是缺维不进平均，并同步缩小权重分母。

**问：为什么阈值不直接用行业均值？**

gkx 没有行业均值口径（无行业代码主表与行业统计口径对齐）。用本池分位数是退而求其次，但它至少可复算；写一个来源不明的「行业均值」会让整条链无法审计。

**问：代理指标会不会方向相反？**

会。典型是「资讯条数代理服务质量」：负面新闻也计入条数。凡是存在方向性风险的代理，本件都在 §四 标注，并限制其只作排序参考、不作结论依据。

**问：重跑后数字变了怎么办？**

先看是不是快照变了（`generated_at` 与 `built_at`），再看是不是上游表补数。文档与产物必须同步更新：本批要求 MD 的 mtime 晚于 `_out.json`，且改脚本后必须重跑渲染器，避免正文停在旧数字。

**问：这套口径能不能直接上生产？**

能上「有供给/相对排序」这类展示，不能上「绝对水平/政策结论」这类判断。上生产前至少要补：正式机构名单、机构×环节成员表、服务质量与满意度结果面三件。
