## 摘要

候选机构数原本登记为 STAT 类指标，设想是「招引池/培育池里一共有多少家候选机构」。2026-10-13 的判定推翻了这个设想：页面上的「共 N 家候选」是前端在当前筛选条件下对推荐结果集取 `length`，不请求任何指标服务，也不落 ADS。它随产业方向、机构类型、服务环节、规模等条件实时变化，本质是查询结果集大小，不是可预聚合、可跨期比较的统计指标。注册表因此把 `lifecycle_stage` 置为 `retired`，`formula` 留空，calc-logic 正本写「无。不计算。」

本件按「完全不支持」交付，并用四组否定性证据闭环。第一，表结构：gkx 280 张表里 0 张名字含 `svc` / `service` / `recommend` / `circle` / `card` 的表，0 张 `svc_metric_fact` / `svc_metric_series`；唯一带 `candidate` 的两张是 `dwd_bid_win_candidate_out`（中标候选人），与服务机构的候选无关。第二，列结构：全库 1,285 个不同列名里 0 个 `svc_type` / `service_type`，连「候选池用哪个字段分组」都无法回答。第三，语义：同一句「候选机构」在 9 种筛选条件下得到 9 个 N，最小 531、最大 25,597、跨度 25,066，没有任何一个可以被称为「候选机构数」。第四，制度：注册表已判 retired，复活本 ID 会与 `M_SVC_ORG_SELECTED_COUNT` 一样，把页面集合大小伪装成指标。

判档 **完全不支持**。这不等于「数据质量差」，而是「对象不存在」：没有一个叫「候选集合」的表，也没有一个稳定的筛选组合可以固化成指标。若甲方确需「候选规模」这个读数，正确做法是另立查询态口径卡（参照 `M_SVC_TYPE_DIST_QUERY` 的六要素），不要复活本编号。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

原需求挂在产业服务链分析 → 服务机构推荐 → 招引/培育名单页，展示形态是列表标题旁的一句「共 N 家候选」。按最初的指标卡设想，N 应由指标工厂预聚合，页面直接读一个数；实际实现是页面拿到推荐结果数组后取长度。这两种实现看起来只差一个数据来源，实际差一个本体：前者需要一个「候选集合」的持久化定义，后者只需要一个数组。

### 1.2 为什么需要这个指标

从产品角度，「共 N 家」是有用的：它告诉运营这次筛选命中了多少家，是否需要在条件上收窄。但它有用的前提是「随筛选实时变」，而不是「跨页面稳定」。一旦把它登记成指标，就会被要求「上月多少、这月多少、同比多少」，而这些比较在语义上不成立——两个月的筛选条件可能完全不同，N 的变化反映的是条件变化，不是池子变化。

### 1.3 需求文档是否给出定义方法

**需求文档没有给出「候选」的集合定义，只给了页面文案；项目内 calc-logic 正本明确写「无。不计算。」** 正本列了五条判定依据：页面数字等于结果集 `length`；N 随产业方向、机构类型、服务环节变化；招引池是外部候选、培育池是本土在库；与已废止的 `M_SVC_ORG_SELECTED_COUNT` 同类；2026-08-28 侯佳伟 1B 的「仍挂 STAT、查询时 COUNT」口径被 2026-10-13 徐滕强一并拿掉。

定义方法缺失的关键不是「公式没写」，而是「集合没定义」。要做统计，至少要说清：候选的纳入条件是什么、排除条件是什么、去重键是什么、时间窗是什么、四个筛选维度如何组合。这五件事在正本里一件都没有，因为产品侧从未把「候选」当成一个集合，只当成一次查询的结果。

### 1.4 指标口径与维度拆解

| 要素 | 原设想 | 实际实现 | 后果 |
|---|---|---|---|
| 对象 | 招引池/培育池的候选机构 | 当前查询命中的结果数组 | 对象随查询变 |
| 分组 | 招引 / 培育 | 页面两个 tab | 两组条件不同 |
| 度量 | `COUNT(DISTINCT org_id)` | `results.length` | 未去重、未落库 |
| 时机 | 预聚合 / 定时 | 查询链路实时 | 无法跨期比较 |
| 空态 | 0 | 0 或空列表 | 无统计意义 |
| 边界 | 不消费门户类型码 | 无定义 | 无法对账 |

四个筛选维度是产业方向、机构类型、服务环节、规模。它们的组合数不是 4 个，而是四个集合的笛卡尔积；正本没有给每个维度的取值域，因此连「一共有多少种候选口径」都数不清。这是本件判「完全不支持」的结构性理由：不是数据缺，是口径的对象缺。

### 1.5 与同域姊妹指标的分工

与 `M_SVC_TYPE_DIST_QUERY` 的分工：后者也是查询态，但它有六要素口径（对象/分组/度量/时机/空态/禁联），保留指标身份作查询页图表的口径真源；本件连六要素都没有，已被撤销身份。两者的差别不是「一个能算一个不能算」，而是「一个有口径卡一个没有」。

与 `M_SVC_REC_ATTRACT_SCORE` / `M_SVC_REC_CULTIVATE_SCORE` 的分工：两件评分是对结果集里每家机构打分，不产出「共有多少家」。本件的 `target_population` 若被误写成候选数，会让评分件的分母看起来像候选数，这是必须避免的串口径。

与已废止的 `M_SVC_ORG_SELECTED_COUNT` 的分工：后者是「已选 N 家」，本件是「候选 N 家」，两者都是页面集合大小，同批废止，保留 ID 防冲突。

### 1.6 本件的边界与不做什么

本件不做五件事：不计算任何 N（包括「深圳 25,597」「外部 18,535」这类切片总量，它们不是候选数）；不建 `svc_metric_fact` 表；不往任何 ADS 灌本编号；不把历史演示值当候选数；不复活 STAT 身份。页面可以继续显示「共 N 家」，但必须去掉 ⓘ 与 MetricSpecCard。

## 三、数据支撑情况

### 3.1 表结构探测：280 张表逐名扫描

gkx 当前 280 张表，表名逐个小写化后按五个模式匹配：`svc`、`service`、`recommend`、`circle`、`card`。命中 0 张。这意味着 calc-logic 里提到的 `svc_metric_fact`、`svc_metric_series`、`svc_org_card`、`svc_org_circle` 四张表在 gkx 一张都不存在；开发库侧同样为空壳（`gkxlumenx_*` 逐表非空 0 张）。两侧都核过，结论是「两库均无」。

| 探测模式 | 命中表数 | 说明 |
|---|---:|---|
| `%svc%` | 0 | 无任何 `svc_*` 表 |
| `%service%` | 0 | 无服务类型结果面 |
| `%recommend%` | 0 | 无推荐结果面 |
| `%circle%` | 0 | 无机构圈层表 |
| `%card%` | 0 | 无机构卡片表 |

### 3.2 列结构探测：1,285 个列名无 svc_type

对 `information_schema.columns` 落盘的 6,312 列做列名去重，得到 1,285 个不同列名；其中含 `svc_type` 或 `service_type` 的 0 个。这个结果比「表不存在」更硬：即使有人想用某张宽表临时拼一个分桶，也找不到「服务类型」这个字段。gkx 侧的服务类型只能由 `dwd_org_org_product_info.main_activities` 的经营范围词表重建，而重建结果是「本件口径」，不是甲方主数据。

### 3.3 同名表探测：唯一的两张 candidate 是中标候选人

全库表名含 `candidat` 的只有两张：`dwd_bid_win_candidate_out` 与它的备份表 `dwd_bid_win_candidate_out_bak_20260911`。前者是招投标「中标候选人」明细，字段围绕标段、投标人、报价，与服务机构候选没有任何关系。这是典型的「名字像、语义不像」：如果只看表名做关键词检索，会误以为找到了候选表；打开字段就会发现它是另一条业务线。

### 3.4 筛选条件阶梯：9 个 N 证明它是结果集长度

在同一份池快照上，按「候选」可能的口径逐层加条件，得到 9 个不同的 N：

| # | 筛选条件 | N |

| 1 | 外部三市·全部 | 18,535 |
| 2 | 外部三市·命中产业标签 | 7,139 |
| 3 | 外部三市·有专利记录 | 9,995 |
| 4 | 外部三市·有营收年报 | 531 |
| 5 | 外部三市·命中产业标签且有专利 | 4,583 |
| 6 | 深圳·全部 | 25,597 |
| 7 | 深圳·INNOV 主型 | 19,879 |
| 8 | 深圳·人工智能标签 | 2,071 |
| 9 | 深圳·大型 | 1,045 |

最小 531、最大 25,597、跨度 25,066。这 9 个 N 都可以被页面读成「共 N 家候选」，但它们互相矛盾；没有任何统计口径能同时容纳它们。若把某一个固化成指标，另外八个就会变成「口径错误」，而实际上它们只是不同筛选条件。

### 3.6 与页面实现的对账

正本记录页面实现为「共 {results.length} 家」，不请求 Java/Python 出指标值。这与 3.4 的 9 个 N 完全吻合：`results.length` 就是某个筛选组合下的数组长度，天然随条件变。页面没有错，错的是把它登记成指标；撤销身份后，页面继续显示 N 是合法的，只是不能再挂指标卡。

### 3.7 为什么不能用切片总量替代

有人会提议「那就固定一个口径，比如深圳全部 25,597」。这个提议看似解决了稳定性，实际制造了新的错误：25,597 是服务机构池的切片总量，不是候选数；它不随产业方向变，也就失去了「候选」的产品含义。更重要的是，一旦把它写成候选数，招引页会显示「深圳 25,597 家候选」，而招引对象本来应该是外部机构，语义直接冲突。

### 3.8 否定性证据的完整性

四条证据分别覆盖「表」「列」「同名表」「语义」四个层面：表层 0 张，列层 0 个，同名表层 2 张但语义无关，语义层 9 个 N 互相矛盾。再加上注册表的 retired 判定，构成一个闭环：即使有人绕过注册表，也无法在库里找到可复算的候选集合。这是本件判「完全不支持」的证据基础。

### 3.9 与 S1 批服务机构九件的池一致性

本件用的池与 S1 批九件完全同源：`dwd_org_org_product_info` 45,011 行重建 44,153 家，深圳 25,597、广州 12,641、东莞 4,300、惠州 1,594、未回联 21。这个一致性有两个用途：其一，证明 3.4 的 9 个 N 不是另一套池算出来的，而是同一批机构在不同条件下的切片；其二，防止把「池总量」误当「候选数」——池是固定的，候选是条件化的，两者不在一个层面。

| 切片 | 家数 | 在本件中的角色 |
|---|---:|---|
| 全池 | 44,153 | 不作为任何 N |
| 深圳 | 25,597 | 阶梯第 6 组，仅作反例 |
| 广州 | 12,641 | 外部三市之一 |
| 东莞 | 4,300 | 外部三市之一 |
| 惠州 | 1,594 | 外部三市之一 |
| 未回联 | 21 | 不入任何候选口径 |

这张表的六行来自同一个 `city` 字段的切片，不是六次独立查询；因此它们之间的加减是闭合的（25,597 + 12,641 + 4,300 + 1,594 + 21 = 44,153）。任何候选口径如果要跨切片组合，必须先说明是按 `city` 还是按其他维度，否则 N 的加减会对不上。这也是「候选」不能只给一个数的原因：它缺的不是数值，是切片定义。

产物因此在 `population_context.city_rows` 与 `filter_ladder` 两处分别保存切片与阶梯，读者可以自行验证两者不是同一套数。

### 3.10 为什么 `results.length` 不能跨期比较

跨期比较要求「同一对象、同一口径、不同时间」。`results.length` 三个条件一个都不满足：对象是当前数组，口径是当前筛选组合，时间只是查询瞬间。即使两次查询用同一组条件，结果也可能因为底层数据更新而变化；反过来，条件变了而 N 恰好相同，也不能读成「候选规模没变」。统计上，这叫作「分母随观测而变」，任何同比、环比、占比都会失去意义。

页面运营需要的其实是「本次筛选命中多少」，这是一个即时读数，不是一个时间序列。把它做成时间序列，会逼着产品去固定筛选条件，而固定条件又会让页面失去筛选能力——这是本件废止的深层原因，不是单纯的「数据不够」。

### 3.11 与「服务机构总量」的语义边界

服务机构总量回答「池里有多少家」，候选数回答「这次筛出多少家」。前者是供给侧存量，后者是需求侧查询结果。两者混用会产生三种错误：把 25,597 写成「深圳候选 25,597 家」；把 18,535 写成「外部候选 18,535 家」；把评分件的 `target_population` 写成候选分母。本件在产物里把这三个数都标为「切片总量」，并在正文逐条否认它们是候选数。

### 3.12 否定性探针的可复现性

探针脚本 `code/M_SVC_REC_CANDIDATE_CNT.py` 只读两个落盘快照：`gkx_columns_20261023.json`（表/列字典）与 `svc21_rec_20261023.json`（池与 9 组阶梯）。它不连库、不重扫表，运行时间约 1 秒。任何人拿到仓库都可以用 `cd code && python3 M_SVC_REC_CANDIDATE_CNT.py` 复现 3.1—3.4 的全部数字；这也是「完全不支持」档仍然要求 py + out.json 的意义——负结论不能只靠散文。

### 3.13 表名关键词检索的误判风险

`candidat` 命中两张中标候选人表，是一个很好的反例：如果只按表名做关键词检索、不打开字段，就会把 `dwd_bid_win_candidate_out` 当成候选池，进而写出「候选机构表已存在」的错误结论。本件在 3.3 逐字段核对了它围绕标段、投标人、报价，与服务机构的 `org_id`、服务类型、产业方向没有任何交集，才把它排除。

同类误判还有三种形态：表名含 `service` 但实际是「服务外包」业务线；表名含 `card` 但实际是「银行卡」；表名含 `circle` 但实际是「朋友圈」社交数据。gkx 280 张表里这五种模式命中 0 张，说明连误判的机会都没有；但这不改变方法：**否定性结论必须打开字段核，不能只凭表名。**

### 3.14 与「统计指标」四要素的对照

一个可发布的统计指标至少要具备四要素：稳定的对象集合、稳定的分组维度、可复算的度量、明确的时间语义。本件逐项对照的结果是四项全缺：

| 要素 | 本件状态 | 缺在哪 |
|---|---|---|
| 对象集合 | 无 | 候选集合未定义 |
| 分组维度 | 无 | 四维筛选的取值域未枚举 |
| 度量 | 只有 `results.length` | 未去重、未落库 |
| 时间语义 | 无 | 查询瞬间，不是统计期 |

四要素全缺，已经足以判「完全不支持」；9 个 N 只是把这个判断可视化。把这张表与 3.1—3.3 的结构证据放在一起，结论不依赖任何单个数字。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺口 | 缺什么 | 影响 | 修复路径 |
|---|---|---|---|
| 候选集合定义 | 纳入/排除/去重/时间窗 | 无对象可统计 | 甲方先定义集合，再谈指标 |
| 候选成员表 | `svc_org_circle` / `svc_org_card` | 无法物化集合 | 不建；改为查询态口径卡 |
| 服务类型主数据 | `svc_type` 列 | 无法分桶 | Q106 甲方签主数据 |
| 筛选维度取值域 | 四个维度的枚举 | 组合数不可数 | 产品侧补枚举 |
| 指标身份 | 注册表 retired | 不得灌数、不得挂卡 | 维持 retired |

### 4.2 修复路径与优先级

短期不应修复本件，而应把它维持为 retired。若产品确实需要「候选规模」这个读数，正确路径是另立一张查询态口径卡：对象 = 当前查询命中的 org_id 去重集合，度量 = `COUNT(DISTINCT org_id)`，时机 = 查询链路实时，空态 = 0 命中空图，禁联 = 不复用门户类型分布。这张卡可以复用 `M_SVC_TYPE_DIST_QUERY` 的六要素模板，但必须使用新 ID，不能复活本编号。

中期需要补的是筛选维度枚举与服务类型主数据。前者是产品定义工作，后者是 Q106 的甲方签字事项；两者都不是数据采集问题，不能靠跑批解决。

### 4.3 降档论证（为什么不是更高/更低一档）

本件已经是四档中最低档，不存在「更低」。要说明的是为什么不抬到「部分支持」：部分支持的前提是「有部分依赖维度可算」，而本件连对象都不存在——没有一个叫候选集合的表，也没有一个稳定的筛选组合。9 个 N 不是「部分可算」，而是「每个都可算但互不等价」，这属于对象缺失，不是覆盖不足。

也不应抬到「完全转换支持」：转换支持要求「结构与数据足够，现在就能加工出来」。本件没有结构（0 张表、0 个列），加工对象不存在，谈不上转换。

### 4.4 缺口对下游的影响

第一层影响是「页面文案与指标卡解耦」：页面可以继续显示 N，但不能挂 ⓘ；前端若已挂卡，必须下线。第二层影响是「评分件分母」：`M_SVC_REC_ATTRACT_SCORE` 的对象池 18,535 是切片总量，不得写成候选数。第三层影响是「注册表一致性」：任何批量脚本不得给本 ID 生成 `_out.json` 之外的指标值，也不得往 `svc_metric_*` 灌行。

### 4.5 字段级缺口表

| 期望字段 | gkx 是否有等价列 | 处置 |
|---|---|---|
| 候选机构 org_id | 无候选表 | 不建 |
| 候选分组 | 无 | 不建 |
| 候选时间戳 | 无 | 不建 |
| 服务类型 | 无 `svc_type` | 查询态另立 |
| 筛选条件快照 | 无 | 前端会话持有 |

### 4.6 口径变更的影响矩阵

| 若口径定为 | 本件状态 | 下游需要重算的件 |
|---|---|---|
| 维持 retired | 不变 | 无 |
| 另立查询态口径卡 | 新 ID | TYPE_DIST_QUERY 模板复用 |
| 固定深圳全部 25,597 | 仍错（切片总量≠候选） | ATTRACT / CULTIVATE 分母需澄清 |
| 固定外部 18,535 | 仍错（同上） | ATTRACT 对象池需澄清 |

### 4.7 与查询态口径卡的字段对照

若另立查询态口径卡，最小字段集如下。它不是本件的产物，只是给下一张卡的输入清单，避免「废止了却没告诉别人怎么接」。

| 要素 | 本件是否有 | 查询态卡需要什么 |
|---|---|---|
| 对象 | 无集合表 | 当前查询命中的 org_id 去重集合 |
| 分组 | 无 | 六类服务类型 + 未分类 |
| 度量 | 无 | `COUNT(DISTINCT org_id)` |
| 时机 | 无 | 查询链路实时，不落 ADS |
| 空态 | 无 | 0 命中空图，禁止回退全库 |
| 禁联 | 无 | 不复用门户类型分布 |

这张对照表也解释了为什么不能「顺手」把本件改成查询态：本件连对象都没有，改造成本不是改公式，而是重建一个口径卡。重建就要新 ID，这是注册表纪律，不是命名偏好。

## 五、结论与发布建议

本件结论是「不发布、不计算、不复活」。页面上的「共 N 家」可以保留，但必须去掉指标卡与 ⓘ；N 只是当前筛选的结果集长度，不进入任何报表、不参与同比、不作为评分件分母。注册表的 retired 状态应维持，保留 ID 只为防冲突。

若甲方确实需要「候选规模」的分析能力，建议另立一张查询态口径卡，明确对象、分组、度量、时机、空态、禁联六要素；这张卡可以做「当前查询命中多少家、按类型怎么分」的实时图表，但不能做跨期比较，也不能落 ADS。把这件事与「候选机构数」分开，是对产品与数据都更诚实的处理。

## 附录 E　常见误读与纠正

**问：页面明明显示「共 N 家」，怎么会没有这个指标？** 页面显示的是数组长度，不是指标值；数组长度可以显示，但不能做同比、不能落 ADS、不能挂指标卡。

**问：固定一个筛选条件不就有指标了吗？** 固定条件得到的是「某个条件下的结果集大小」，不是「候选机构数」；换一个条件就换一个数，跨期不可比。

**问：深圳 25,597 家能不能当候选数？** 不能。它是服务机构池的深圳切片总量，包含大量非候选机构；而且招引对象应是外部机构，语义冲突。

**问：为什么不建一张候选表？** 建表先要定义候选的纳入/排除/去重/时间窗，这四件事产品侧没有定义；在定义缺失时建表，只会把某个临时口径固化成技术债。

**问：这个 ID 以后还能用吗？** 保留 ID 只为防冲突；要用必须另立查询态口径卡，不能复活 STAT 身份。
