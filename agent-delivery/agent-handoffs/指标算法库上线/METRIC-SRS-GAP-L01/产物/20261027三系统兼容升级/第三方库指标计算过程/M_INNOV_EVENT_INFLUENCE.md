## 摘要

事件影响力想回答「谁在报道、报道得多权威、持续了几天」。旧稿公式是 0.45×媒体层级 + 0.35×央媒报道量 + 0.20×周内跨度，输入是一个事件的报道集合。gkx 没有这个集合。

`dwd_event` 只有 20 行会议公告，没有报道明细；`dwd_industry_chain_news_info` 有 108,052 条、206 个 source，但没有 event_id、没有簇 id、没有媒体层级。要得到「一个事件的报道集合」，必须先做跨源事件聚类，再用媒体层级表打分；两者都不存在或未验收。

旧稿用标题相似度把 108,072 条聚成 6,406 簇，再按称谓规则分四级媒体。这是模型 + 人工假设，不是库内事件真值；阈值一变，簇数与影响力全变。按本批规则，不许用新闻串伪事件，故判完全不支持，只写需求。

## 一、需求定义概述

### 1.1 所属功能模块

事件影响力挂在科创事件 GIS 图层的标记点权重、重要性排序、事件详情页的「影响面」解释。它不直接展示报道列表，而是给事件一个 0—100 的传播影响力分，供排序与视觉编码。

它和关注度是两件事：关注度回答「多少人在说」，影响力回答「说话的人有多重」。一条被 500 个自媒体搬运的融资消息关注度高、影响力有限；一条只被工信部官网与人民网各发一次的产业政策关注度低、影响面广。

### 1.2 为什么需要事件影响力

没有影响力，重要性排序会退化成「唯流量」：转载最多的公关稿排第一，真正重要的政策排后面。影响力用媒体层级与央媒报道量修正这个偏差，让「谁在说」进入排序。

它也为事件详情页提供解释：用户点开一个事件，看到的不只是「98 条报道」，还有「其中 3 条央媒、覆盖 5 天」。这比单一分数更有说服力。

### 1.3 需求文档是否给出定义方法

需求只写「基于事件影响力、关注度等指标自动计算等级」，没有给影响力定义。旧稿用媒体层级/央媒量/跨度三项，是项目内口径；媒体层级靠称谓规则（央媒/全国/行业/地方），不是库内评级。

更关键的是「事件」没有定义：没有 event_id，报道无法归属到事件；没有簇 id，同一事件的多条报道无法聚合。公式再合理，没有输入也跑不了。

### 1.4 权威机构方法可行性

传播影响力在文献里通常用「媒体权威度 × 报道量 × 持续时间」合成。权威度需要媒体评级表（发行量/引用率/官方层级），报道量需要事件簇，持续时间需要发布时间。三样都是事件级数据，本件一个都没有。

另一族是社交网络传播模型（转发树、KOL 层级），需要社交平台数据；gkx 只有新闻，没有社交。因此本件连代理都做不了。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A. 媒体层级加权 | 传播学/舆情 | tier×报道量×跨度 | 不可行（无层级/簇） |
| B. 社交传播树 | 网络传播 | 转发树/KOL | 不可行（无社交数据） |
| C. 报道量基线 | 事件研究 | 异常报道量 | 不可行（无事件簇） |
| D. 人工评级 | 专家打分 | 逐事件阅读 | 不可行（无事件表） |

### 1.5 引用来源

来源 1：`code/_snapshots21/event21_probe_20261022.json`（20 行会议公告）。

来源 2：`code/_snapshots21/news21_chain_items_20261022.json`（108,052 条、206 源、无 event_id）。

来源 3：旧稿 `M_INNOV_EVENT_INFLUENCE.md`（6,406 簇 + 称谓分级，本件拒绝）。

### 1.6 推测原意与依赖维度

推测原意是给事件一个「传播重量」的分数，修正唯流量偏差。按这个原意，最小输入是「事件簇 + 报道明细 + 媒体层级 + 发布时间」，本件一个都没有。

依赖维度：D1 事件簇（无）、D2 报道明细（有表但无事件 id）、D3 媒体层级（无）、D4 发布时间（有日期无小时）、D5 去重键（无）。五层里只有 D2/D4 部分可用，不足以闭环。

|---|---|---|---|
| D1 | 事件簇 | A 类 | 无 |
| D2 | 报道明细 | A 类 | 108,052 条，无 event_id |
| D3 | 媒体层级 | A 类 | 206 源，无 tier |

## 三、数据支撑情况

本件按「事件簇 / 报道明细 / 媒体层级 / 发布时间 / 去重键」五个维度核对，五项全部缺失或不完整。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 事件簇 | 缺失 | dwd_event 20 行公告 | 建 event_cluster |
| 报道明细 | 有表无事件 id | 108,052 条、6 列 | 建 event_report 并打 event_id |
| 媒体层级 | 缺失 | 206 源只有名称 | 建 dim_media_tier 并标注 206 源 |
| 发布时间 | 不完整 | 只有日期 | 补到小时 |
| 去重键 | 缺失 | 无 URL 规范化/标题指纹 | 建 dedup_key |

事件簇缺口的修复需要先做聚类并验收。旧稿的 6,406 簇没有人工标注集，无法算准召；建议先标 500 对报道，确认「同一事件」的边界，再调阈值。没有验收的簇不能落表，更不能用来打分。

媒体层级缺口的修复是标注 206 个 source。这不是纯人工：可以先按域名/主办单位规则分四级，再人工复核。关键是层级表要版本化，因为媒体会变更主办单位与层级。

报道明细缺口最容易被低估：资讯表有 108,052 条，但没有 event_id，等于一堆散报道。没有事件 id，既不能算「一个事件多少条」，也不能算「央媒占比」，影响力公式的三个输入全部落空。

### 3.9 缺口优先级

缺口不是同等重要。本件按「是否阻断指标成立」把缺口分三档：阻断（指标算不出）、扭曲（算得出但结论会反）、披露（不影响本期结论但影响外推）。优先级如下。

| 优先级 | 缺口 | 阻断/扭曲/披露 | 处理 |
|---|---|---|---|
| P0 | 无事件簇 | 阻断 | 聚类 + 验收 |
| P0 | 资讯无 event_id | 阻断 | 建 event_report |
| P0 | 无媒体层级 | 阻断 | 标注 206 源 |
| P1 | 发布时间只到日 | 扭曲 | 补到小时 |
| P1 | 无去重键 | 扭曲 | URL 规范化 |
| P2 | 权重未签字 | 披露 | 甲方裁定 |

三个 P0 是链式的：簇 → 报道归属 → 媒体层级。缺一个，影响力公式就少一个输入；三个都缺，公式完全空转。

发布时间只到日是 P1：周内跨度还能算，日内传播曲线算不了；若甲方只要周级影响力，这一项可以降为 P2。

## 四、数据缺失情况

本件的缺失是事件级数据整体缺失，不是单字段。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 事件簇 | 无法聚合报道 | 不计算 | 聚类 + 人工验收 |
| 媒体层级 | 无法算权威度 | 不计算 | 标注 206 源 |
| event_id | 无法归属报道 | 不计算 | 建 event_report |
| 发布时间 | 无法算跨度 | 不计算 | 补到小时 |
| 去重键 | 转载重复计入 | 不计算 | URL 规范化 |

最需要警惕的是「有新闻就能算影响力」。新闻是报道，不是事件；没有事件簇，报道无法聚合，媒体层级也无法按事件加权。把 108,052 条新闻直接当事件，会得到 108,052 个「事件」，每个事件只有 1 条报道，影响力退化成媒体分。

第二类是称谓分级的风险：央媒/全国/行业/地方的边界模糊，同一媒体在不同年份可能变更层级。没有版本化的层级表，历史分数无法复现。

### 4.9 处置原则

对缺失的处置遵循三条：不补 0、不静默填充、不把模型产物当数据真值。能算的算，不能算的输出 null 并写原因；任何代理都必须在字段名与页面文案上标注「代理」。

第二条是不做「看起来完整」的补齐。缺失年份不插值、缺失城市不摊派、缺失分项不按均值填；这些操作会让下游误以为数据齐全，比 null 更危险。

第三条是可复现优先。所有外部输入都落快照，快照带来源、时间、行数；脚本只读快照，重跑不依赖网络。这样即使源库变化，历史结论仍可复算。

## 五、与旧稿的差异

旧稿用 demo 侧 108,072 条报道聚成 6,406 簇，按称谓分四级，判部分支持；本件查 gkx 后确认无事件簇、无媒体层级，判完全不支持。

事件影响力的结构缺口是事件簇与媒体层级，两者都不是「补几行数据」能解决的，需要聚类模型 + 人工验收 + 媒体标注。按四档定义，关键依赖维度不具备，判完全不支持。

## 附录 G 口径问答

**问：为什么不能直接用 108,052 条新闻算影响力？**

答：新闻是报道，不是事件。没有 event_id，报道无法聚合；每个报道都成了独立「事件」，影响力退化成媒体分。

**问：旧稿的 6,406 簇为什么不能用？**

答：没有人工标注验收。阈值一变簇数就变，影响力分也随之变；它不是数据真值，是模型输出。

**问：媒体层级能不能用域名规则？**

答：可以做初筛，但必须人工复核并版本化。206 个源里既有央媒，也有行业站、地方站，规则错会让权威度整体偏移。

**问：只到日的发布时间够不够？**

答：算周跨度够，算日内传播曲线不够。若只要「持续几天」，日期足够；若要「几小时内爆发」，需要小时级。

**问：需要哪些表？**

答：event_cluster（事件主键）、event_report（报道归属）、dim_media_tier（媒体层级）、fact_event_daily（日度报道量）。

**问：什么时候能升级？**

答：三表齐备 + 500 对聚类标注验收 + 媒体层级复核，才可能升部分支持。

## 附录 N 开发交接说明

**问：能不能先接新闻，跑一版等级给业务看？**

答：不能。新闻没有 event_id，跑出来的「等级」是单条报道的媒体分，不是事件等级；业务一旦拿去筛选，会把「转载多」当「事件重要」。

**问：事件簇能不能用规则（同标题/同公司+同周）先做？**

答：可以做基线，但必须人工验收并标 `cluster_confidence`。未验收的规则簇只能进沙箱，不能进正式表。

**问：媒体层级没有官方表，怎么办？**

答：先按主办单位/域名做四级初筛，再人工复核 206 源；层级表要版本化，历史分数才能复现。

**问：要多少事件才能上线？**

答：不是行数问题，是覆盖问题。至少覆盖 3 个事件类型、每个类型 ≥50 个事件、每个事件 ≥1 条报道，才能做分位切档。

**问：旧稿的 0.5/0.5 与 P70/P30 能直接用吗？**

答：可以作为初始参数，但要在新事件流上重跑分布；P70/P30 是样本分位，样本变了分位就变，不能硬编码。

**问：什么时候能从「完全不支持」升级？**

答：事件主表 + 报道归属 + 媒体层级三表齐备，且通过附录 M 的八项验收，才可重评为部分支持。
