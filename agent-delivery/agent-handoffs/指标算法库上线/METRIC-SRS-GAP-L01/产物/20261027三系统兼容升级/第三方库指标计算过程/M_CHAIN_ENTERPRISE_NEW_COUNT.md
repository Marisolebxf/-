| 档位 | 含义 | 本件是否适用 | 判断依据 |
| --- | --- | --- | --- |
| 完全直接支持 | **开发库+三方库（gkx）**中直接就有该指标（或 100% 语义一致指标/结果面）可用，且数据量完全支持直查/直算 | 否 | 无 `first_link_date`，无明细表 |

| 完全不支持 | 该指标及其关键依赖维度，在**开发库与三方库（gkx）**均无法构建（结构与数据均不具备可算闭环） | **是** | 真源表不存在，时间字段不存在，唯一可用时间戳是单批入库戳 |

> **数据源口径**：本件支持度按「开发库 + 三方库（gkx，183.240.141.251:3318 只读）」评估，仅排除 `demo_*`；本机开发库事实面为空壳（`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张），实际取数面为 gkx。

判“完全不支持”而不是“部分支持”，关键否定性证据有五条：

1. 注册表定的真源是 `dwd.enterprise_industry_chain`，gkx 库 `SHOW TABLES LIKE '%enterprise_industry_chain%'` 返回空集；实际承载挂接关系的是 `dwd_org_industry_tags`，它是打标宽表，不是“挂链明细”。
2. `dwd_org_industry_tags` 的 16 列中没有 `first_link_date`，也没有 `org_id`；去重只能退回 `credit_code`，与注册表的 `org_id` 去重键不等价。
3. `created_time` 全表 2,283,762 行只有 1 个不同日期，`MIN=MAX=2026-08-27 11:08:26`，是单批入库戳；用它分年，只会得到“2026 年新增 171 万家”这一条假时间轴。
4. `calc-logic` 明写“禁止 create_time 冒充业务时间”“禁止注册年分布（B 档语义偷换）”。本件如果拿成立年当新增挂链年，就是文档自己写明的禁用做法。
5. 唯一可用的代理（成立年）只覆盖 28,031 家链企业，占 1,714,457 家的 1.63%，且样本显著偏老；用它算“新增”，量级与真实挂链新增差两个数量级。

因此本件不把 3,627 写成“新增关联企业数”，只写成“代理观察：2021—2025 年成立且当前在链的企业数”。这两个说法差一个字，语义差一整条时间轴。

## 摘要

本件回答“每年有多少家企业第一次挂上产业链”。官方口径在 2026-10-14 已拍板：按 `first_link_date` 取每年最早挂链时间，按 `org_id` 去重，退出后重挂不计。复核发现 gkx 不具备执行条件：真源表不存在，`first_link_date` 不存在，`org_id` 不存在，`created_time` 是 2026-08-27 的单批入库戳（全表 1 个取值），无法分年。故本件判完全不支持，官方值为“不可得”，不是“0 家”。

为了说明缺口量级，本件做了“成立年代理观察”：把 `dwd_org_industry_tags` 的 1,714,457 家去脏链企业，与 `dwd_org_base_info` 的 189,116 行底册按信用码连接，只有 28,031 家（1.63%）能匹配到成立年；其中 2021—2025 年成立 3,627 家、2026 年成立 5 家、2020 年及以前成立 24,399 家。该代理只说明“链内企业有多新”，不说明“哪年挂链”；链内样本还比全库底册偏老（2021—2025 占 12.94% vs 20.48%），所以连“企业有多新”都被系统性压低。

## 一、需求定义概述

### 1.1 指标基本信息

| 项 | 内容 |
| --- | --- |
| 指标 ID | M_CHAIN_ENTERPRISE_NEW_COUNT |
| 中文名 | 新增关联企业数 |
| 一级模块 | 产业链分析 |
| 二级模块 | 产业链全景 / 全景概览 |
| 更新频率 | 日（目标态） |
| 对象 | 当年首次挂上链的企业 |
| 计量单位 | 家 |
| 去重键 | `org_id`（注册表锁定） |
| 时间轴 | `first_link_date`（目标态字段，现无） |
| 关联问题 | CHAIN-P0-5（业务挂链日期源级缺失） |

### 1.2 业务问题与原意

“新增关联企业”回答的是“这条链今年新进来了多少家企业”。业务用它看招商成效、看链主企业的带动效应、看某个环节是不是在快速聚集。它与“企业总数”是一对：总数看存量，新增看流量。存量可以靠一次全量打标得到，流量必须靠“每一次打标的时间”才能算出来。

这正是本件的死结：gkx 的挂接表是一次性全量快照，没有“第一次挂上”的时间。全表 2,283,762 行的 `created_time` 完全相同，说明这批数据是同一天一次性灌进来的；它能告诉你“今天谁在链上”，不能告诉你“谁是哪年进来的”。把成立年当挂链年，等于把“企业几岁”当成“企业哪年入链”，两者没有单调关系。

### 1.3 口径拆解

官方口径拆成五个要素：

| 要素 | 锁定值 | 现状 |
| --- | --- | --- |
| 真源 | `dwd.enterprise_industry_chain` | gkx 无此表 |
| 去重键 | `org_id` | 表内无此列 |
| 时间轴 | `first_link_date` | 表内无此列 |
| 重挂语义 | 退出后重挂不计，只计历史首挂 | 无退出/重挂记录，无法判 |
| 分链视图 | `(org_id, chain_code)` 链内首挂 | 无 `org_id`，只能用信用码近似 |

五个要素里四个直接缺字段，第五个只能降级近似。任何“部分支持”的判断都必须先回答“哪一部分能算”，而这里连“首挂”这件事本身都无法观测——不是精度问题，是观测量不存在。

### 1.4 与旧稿、同域指标的差异

| 来源 | 口径 | 数值 | 与本件关系 |
| --- | --- | --- | --- |
| 注册表 / calc-logic | 首挂年 + `org_id` 去重 | 0 行（未供应） | 官方口径，不可执行 |
| 本件代理 | 当年成立且当前在链 | 3,627 家 | 仅观察，不作指标 |
| 同域 `M_CHAIN_ENTERPRISE_COUNT` | 链内企业存量 | 1,714,457 家 | 存量，不是新增 |
| 同域 `M_CHAIN_ENTERPRISE_NEW_COUNT` 旧稿 | 临时运营方案：首灌批全量即首挂 | 未落数 | 把全量当首挂，等于所有企业同一年新增 |
| 底册 `dwd_org_base_info` | 成立年分布 | 189,116 行 | 代理的年份来源，不是挂链时间 |

旧稿的“临时运营方案”值得单独说：它提出“首灌批全量即首挂，后续批次按 `create_time` 分批识别增量”。这个方案在有多批入库时勉强可用，但 gkx 只有一批，且这一批的 `created_time` 全部相同；套用该方案会把 171 万家企业全部记到 2026 年，制造一个“2026 年新增 171 万”的假峰值。本件不采用该方案。

### 1.5 对象、单位与分母

单位是“家”，不是“家次”。一家企业可以挂多条链，逐链统计时会在多条链各计 1 次；注册表要求链内按 `(org_id, chain_code)` 去重，正是为了防止这种重复。本件代理观察沿用“逐链去重”，12 条链的 `chain_firms` 相加恰好等于全表去重值 1,714,457，这是多链重复与去重相互抵消的结果，不应被解读为“每家企业只挂一条链”。

分母问题在本件不存在，因为官方值是计数、不是比率。但代理观察里出现了两个比率：匹配率 1.63%（28,031 / 1,714,457）和近五年占比 12.94%（3,627 / 28,031）。前者分母是全链企业，后者分母是“有成立年的链企业”，两个分母不同母体，不能互相替代。

### 1.6 本件结论先行

1. 官方值：**不可得**。不是 0 家，是 0 行——没有 `first_link_date`，无法把企业分到年份。
2. 代理观察：2021—2025 年成立且当前在链 **3,627 家**；2026 年 5 家；2020 年及以前 24,399 家。
3. 覆盖：代理只覆盖 28,031 家（1.63%），未匹配 1,686,426 家；底册 354 行无成立年。
4. 判档：**完全不支持**；不建议把代理值对外称“新增关联企业数”。

## 二、为什么官方口径不可计算

### 2.1 目标公式

官方公式是：

$$
\mathrm{New}_y = \mathrm{COUNT}\big(\mathrm{DISTINCT}\ \mathrm{org\_id} \mid \mathrm{YEAR}(\mathrm{MIN}(\mathrm{first\_link\_date})) = y\big)
$$

它要求三个东西同时存在：明细表、`org_id`、`first_link_date`。

### 2.2 逐项验证

| 依赖 | 验证 | 结果 |
| --- | --- | --- |
| 明细表 `enterprise_industry_chain` | `SHOW TABLES LIKE '%enterprise_industry_chain%'` | 空集 |
| `org_id` | `SHOW COLUMNS FROM dwd_org_industry_tags` | 16 列无此列 |
| `first_link_date` | 同上 | 无此列 |
| 可替代时间轴 | `MIN/MAX(created_time)` | 均为 2026-08-27 11:08:26，仅 1 个取值 |
| 重挂/退出记录 | 表内无状态列 | 无法识别 |

### 2.3 结论

三个核心依赖全部缺失，且没有等价替代：`created_time` 是入库戳不是业务时间，成立年是另一件事，`updated_time` 也只是入库/更新戳。按“任何代理都不等价”的定义，本件判完全不支持；按 §3.49，“跑不出结果”写成“0 行/不可执行”，不写成“0 家/无数据”。

## 三、数据支撑情况

### 3.1 直接支撑：企业—链映射

| 支撑项 | 源字段 | 实测 | 强度 |
| --- | --- | --- | --- |
| 企业—链挂接 | `dwd_org_industry_tags.industry_code` | 2,283,762 行 | 强 |
| 非空挂接 | 同上，`industry_code` 非空 | 1,714,459 行 | 强 |
| 去脏企业 | `credit_code` 满足 `^[0-9A-Z]{18}$` | 1,714,457 家 | 强 |
| 分链企业数 | `industry_code` 前 7 位 | 12 条链 | 强 |

这三个数必须写清口径，不能混用：1,714,457 是“去脏 + 链内 + 去重”（本件默认），1,714,458 是“链内未去脏”（旧件常用），1,714,459 是“全表非空行数”。三者相差 1—2 家，看似无关紧要，但做分母时会把匹配率从 1.63% 推到 1.63% 附近的不同小数位，审计时对不上。

### 3.2 成立年覆盖

| 链企业（去脏） | 1,714,457 | 代理的分母 |

链内样本每一年的占比都低于全库底册，合计近五年 12.94% vs 20.48%。这不是“链企业更老”的可靠结论，而是“能匹配上底册的链企业更老”——匹配本身有选择性。故代理连“企业年龄”都只能做方向性参考，更不能冒充“挂链年份”。

### 3.5 354 行无成立年的披露

底册 189,116 行中有 354 行 `incorporation_date` 为空。这些行没有进入任何年份桶，也没有被摊到 0 或众数；链内匹配样本中“匹配且无成立年”为 0，说明这 354 行恰好没有落到链企业上，但这不代表它们可以被忽略。若后续扩大匹配范围，这 354 行会变成新的缺口，需在分母里单列。

这 354 行的处理方式需要在三个层面保持一致：

- 分母层面：底册有年份的行才进入年份分布，354 行不进分母，也不摊 0；
- 匹配层面：链企业匹配到底册后，若命中这 354 行，记为“匹配但无年份”，本件实测为 0；
- 披露层面：任何引用底册年份分布的正文都必须写“189,116 行、其中 354 行无成立年”，不能只写 188,761 或 188,762。

三者缺一，都会让复核者算不出同一个分母。本件把 354 写进产物 `base_distribution.base_no_year`，并在正文重复一次，目的是让“无年份”成为一个显式状态，而不是被静默丢掉的行。

### 3.6 为什么代理不能当指标

1. **语义不同**：成立年是“企业注册时间”，挂链年是“企业进入产业链标签体系的时间”。老企业可以今年才挂链，新企业也可能明年才挂链。
2. **方向不定**：代理值高低同时受“企业年龄结构”和“匹配选择性”影响，无法判断哪一头在起作用。
3. **覆盖太低**：1.63% 的覆盖率，任何分链排名都可能是匹配偏差，不是业务差异。
4. **样本偏老**：近五年占比 12.94% vs 全库 20.48%，代理系统性低估新企业。
5. **文档禁用**：calc-logic 明写“禁止注册年分布（B 档语义偷换）”，本件不能一边引用该文档一边违反它。

## 四、数据缺失情况

### 4.1 真源表缺失

注册表把真源写成 `dwd.enterprise_industry_chain`，gkx 无此表。实际表 `dwd_org_industry_tags` 是“企业—环节”打标宽表，字段是 `company_name`、`credit_code`、`industry_code`、`industry_link_code` 等，没有挂链明细应有的 `org_id`、`chain_code`、`first_link_date`、`status`。

### 4.2 时间字段缺失

| 时间字段 | 实际含义 | 能否分年 |
| --- | --- | --- |
| `created_time` | 入库戳，全表 1 个取值 | 否 |
| `updated_time` | 入库/更新戳 | 否 |
| `incorporation_date`（底册） | 企业成立日 | 能分“成立年”，不是“挂链年” |
| `first_link_date` | 目标态业务时间 | 不存在 |

### 4.3 单批入库戳的后果

2,283,762 行的 `created_time` 全部等于 2026-08-27 11:08:26。这意味着：

- 无法按批次识别“首灌”与“增量”；
- 无法用 `create_time` 分批；
- 若强行按 `created_time` 分年，只会得到“2026 年新增 1,714,457 家”一个桶；
- 旧稿的“首灌批全量即首挂”方案在本库退化为“全部企业同一年新增”，没有业务意义。

### 4.4 去重键不等价

注册表要求 `org_id`，表内只有 `credit_code` 与 `company_name`。信用码有 2 行非 18 位（去脏时剔除），名称有重名风险。用信用码去重在本库可行，但与 `org_id` 不是同一个键：同一主体换信用码、或一码多主体时，结果会不同。本件在代理里用信用码，并明确标注“非官方去重键”。

### 4.5 重挂/退出不可识别

表内无 `status`、无 `exit_time`、无 `first_link_date`，无法区分“首次挂链”“退出后重挂”“一直在线”。注册表明确“退出后重挂不计新增”，本件连“退出”都观测不到，故连近似都做不了。

### 4.6 覆盖偏差

28,031 / 1,714,457 = 1.63% 的匹配率，且分链从 0.40% 到 15.22%。这个偏差不是随机缺失，而是与底册的覆盖范围相关；用它做分链排名，等于把“底册覆盖度”当成“新增活跃度”。

### 4.7 边界总结

可交付：链企业存量 1,714,457、匹配覆盖 28,031、成立年代理分布、354 行无年份披露。
不可交付：任何年份的“新增挂链企业数”、重挂识别、分链新增排名。
判档边界：只有供应方交付带 `first_link_date` 与 `org_id` 的挂链明细后，本件才可能升档；补成立年、补 `create_time` 批次都无效。

## 五、结论、边界与复现

### 5.1 结论

1. 官方值 **不可得**：0 行，不是 0 家。
2. 代理观察 3,627 家（2021—2025 成立且当前在链），覆盖 1.63%，不能对外称“新增”。
3. 缺口根因是“业务时间字段 + 明细表 + `org_id`”三缺，不是脚本或算力问题。
4. 判档 **完全不支持**；在供应方补齐前，不建议发布任何“新增关联企业数”。

### 5.2 适用与不适用

| 场景 | 是否适用 | 说明 |
| --- | --- | --- |
| 说明链内企业存量 | 适用 | 1,714,457 可用 |
| 说明底册覆盖缺口 | 适用 | 28,031 / 1.63% 可用 |
| 回答“今年新增多少家” | 不适用 | 无业务时间 |
| 做分链新增排名 | 不适用 | 覆盖率差 38 倍 |
| 做同比/环比 | 不适用 | 只有单批快照 |
