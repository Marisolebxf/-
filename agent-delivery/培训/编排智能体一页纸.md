# GKX 编排智能体 · 一页纸

> **给谁**：第一次听介绍的人（领导、合作方、其他项目、新人）  
> **怎么用**：会前发、会后留；5 分钟讲完就停。细节进 `编排智能体对外介绍.md`。  
> **日期**：2026-08-18（补：定义/实现双轨 · 飞书看板 · 实现轨长任务）

---

**一句话。** 这不是个人 vibe coding，而是把招标范围变成可派单、可验收、可过夜连跑的工程化编排。人拍板，AI 出量。接口只有三件套：**DoD + Handoff + Evidence**。衡量：(团队人数 + Agent) 能否 ≈ 原来 3 倍人力。

**定义轨 / 实现轨。** 两条轨道，不要混。定义轨管「做什么、长什么样、口径」：PACK / UX / 指标 → 门1 梳理 → 故事入库（只提案）→ 门2 会签 → 门3 拍板。实现轨管「按 Sprint 做完、联调通」：门3 之后才把工程叶标 ready。硬边界：门3 前工程不得开工；门1 后提案不得直接标 ready；V2 准生产会签仍属定义轨。实现轨跨仓闭环或同仓 ≥3 叶预计过夜，且总控写了「不必再问」，才开 **长任务**（仍一叶一单）。跑完要迭代：结构没变走缺陷包；动契约/结构走变更总控；授权作废才另开新长任务。禁止无总控连夜私干、禁止无 ID 热修。

**飞书看板。** 人看飞书多维表格，机器认 git 里的 `task-registry`。一张表拆「定义看板 / 实现看板」。改状态走统一入口并推板，禁止只改 YAML。派单要人把飞书「派单门控」改成已确认；故事「实现状态」禁止手拖，由关联任务滚动。拖看板不能代替 git 真源。

**一张单怎么转。** `bid-reference`（不读招标 PDF）→ 58 点 ±10% → 定义三门 → registry（MCP）→ Coordinator 新会话派专项 Agent → CI/K8s → handoff → 自动验收 → **人签收** → 飞书可见。规范在 git，任务在 registry，证据在 handoff，进度在飞书——不在聊天记录里。

**人机红线。** 架构与对甲方承诺永远人拍板。AI 不接触客户。commit 标 `[agent:角色]` / `[human:真名]`。无人值守 ≠ 无单无证。
