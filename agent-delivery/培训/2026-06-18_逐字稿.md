## 第 4 页 · Vibe Coding 的「甜」（2 min）

> 我先讲为什么我们都爱 vibe coding——它确实满足了三个核心欲望。
>
> 第一，**马上能跑**。写个查天气的接口，10 秒后 AI 给你一段 Python，复制粘贴能跑。反馈即时，多巴胺暴击。
>
> 第二，**心情爽**。不用查 Stack Overflow、不用看官方文档、不用记 API 签名。大脑减负，状态心流。
>
> 第三，**产能感**。一个人一天写完一周的活，个体感受到 10 倍提升，自信爆棚，跟同事炫耀。
>
> 问大家一句：过去 1 个月，你有没有一刻觉得「有 AI 我能干 10 个人的活」？……99% 应该都会点头。
>
> 这些感觉都对，但只是「个人甜点」。下一页讲为什么这是个「团队陷阱」。

**讲者备注**：要共情，不要否定。承认了"甜"，才能让团队听进"痛"。

## 第 5 页 · Vibe Coding 的「痛」（3 min）

> 三个团队陷阱。
>
> **陷阱一：不可复用。**
> 你 prompt 出来的代码，下次只有你能 prompt 出来。张三的 AI 风格和李四的 AI 风格不一样。上周 A 同学 prompt 出一个组件，B 同学想复用，重新 prompt 一遍，结果 API 不一致。团队代码风格漂移，组件库形同虚设，3 个月后没人能维护。
>
> **陷阱二：不可审计。**
> 「这段代码谁写的？」「AI 写的。」「为什么这么写？」「AI 说要这么写。」出 bug 没人扛，架构腐化没人发现，甲方质疑无法回应。
>
> **陷阱三：不可扩展。**
> 1 个人 + AI 等于 10 倍产能，但 10 个人 + 10 个 AI 不等于 100 倍。大家提示词五花八门、产物彼此冲突、评审瓶颈、成本失控。
>
> 注意：这不是 AI 的错，是「个人用 AI」的范式不适合团队。

**讲者备注**：最后一句是关键转折，把矛头从 AI 转到「我们怎么用 AI」上，铺垫下一页升级。

## 第 6 页 · 一句话心智（2 min）

> 所以我们要升级——一句话心智。
>
> **人做：决策、评审、创意、客户沟通；**
> **AI 做：执行、起草、标准化、并行重复劳动。**
> **人与人、人与 AI、AI 与 AI，都靠「DoD + Handoff + Evidence」标准化接口。**
>
>（建议讲到这里停 5 秒，让大家消化）
>
> 这一句话已经写进 `team-collaboration-playbook.md` 第 0 节，也写进了 `.cursor/rules/00-team-constitution.mdc`——是团队公约。
>
> 三件事：
> 一，**人做高价值的事，AI 做重复的事**，分工要清楚；
> 二，**不混淆**，评审永远是人，量产永远是 AI；
> 三，**接口标准化**，DoD、Handoff、Evidence 这三件套保证人机协作不漂移。
>
> 最后给一个衡量标准：(团队人数 + AI agent) 如果不等于 3 倍原产能，就是用 AI 用错了。

**讲者备注**：这一页是全场最重要的一页，慢讲，留停顿。

## 第 7 页 · 2026 业界 SOTA（3 min）

> 我们不是闭门造车——这套打法已经被 Anthropic、GitHub、Cursor、Augment 等公开验证。
>
> 四个标杆：
>
> 一，**Anthropic 的 Orchestrator-Worker**——Lead Agent 编排不干活，Subagent 干净上下文并行。实测复杂任务提速 90%，但贵 15 倍，所以必须控成本。
>
> 二，**GitHub Spec Kit（11 万 star）**——规范驱动开发，6 阶段 constitution → specify → clarify → plan → tasks → implement，让规范成为可执行资产。
>
> 三，**Augment / Zylos 的 Git Worktree**——每个 agent 自己的工作树，文件级隔离，Cursor 2.0 原生支持 8 路并行。
>
> 四，**Speckle / Gastown 的 Mayor 模式**——Mayor 协调者从不写代码，Polecat 工人用完即弃，Refinery 合并队列，Convoy 按文件分组防冲突。
>
> 完整对标分析在 `orchestration-maturity-and-roadmap.md`，里面我们的成熟度自评 + 升级路线图都写了。

## 第 8 页 · Orchestrator-Worker（2 min）

> 第一个范式：编排者-工人。
>
> **Lead Agent 是指挥**：分析任务、规划、写 Memory、派子任务、综合结果——从不亲自写代码。在我们项目里就是 coordinator-agent。
>
> **Subagents 是工人**：每个工人拿到独立的、干净的上下文，明确的目标、输出格式、工具指引、任务边界——Anthropic 称之为四要素，缺一则漂移。在我们项目里就是 architect、ux、ui、frontend、api、algorithm、data、devops、qa、doc 这 10 个专项 agent。
>
> 三个数字必须记住：
> - **90% 提速**——这是 Anthropic 实测数据
> - **15 倍 token 消耗**——所以必须管成本，否则烧光预算还没干完事
> - **本地并发 ≤ 4**——人脑监管极限，超过 4 个 agent 一起跑你管不过来，必然漂移
>
> 这个模型我们已经在跑——后面会演示。

## 第 12 页 · 三层协作架构（2 min）

> 我们的协作架构是三层。

> **战略层**：架构委员会 = 架构师 + 各 lead + PM。决定方向，不写代码。

## 第 14 页 · 人 vs AI 边界（2 min）

> 这一页是「不能犯的错」清单。
>
> **人做的事，不可外包**：架构选型、技术选型、与甲方承诺、设计创意、评审决策、跨团队仲裁、商务沟通、招聘解雇、出问题承担责任。
>
> **AI 做的事，人来评审**：模板化代码、文档起草、数据 Mock、跨仓一致性扫描、长上下文规划起草、失败重试、不知疲倦地标准化输出。
>
> 红线一句话：**AI 输出 → 必经人评审 → 才能外发；决策永远是人拍板。**
>
> 后面 FAQ 里有个问题「AI 跟我说『做完了』，但 CI 没绿怎么办」——答案就是 DoD 不满足等于没做完，不要绕过 CI，这就是人的判断不可外包。

## 第 18 页 · 工具 3：7 条铁律（2 min）

> 这是「不能碰的电网」，不是建议、是物理约束。
>
> 7 条逐条快速过：
> 1. 算法只在 Python，Java 禁 NLP / 模型推理
> 2. 调用链：前端 → Java REST → Python `/internal/*`，不可越层
> 3. 图谱用 NebulaGraph，禁止 Neo4j
> 4. 可观测性必须全栈 OpenTelemetry
> 5. CI/CD：push → Pipeline 绿 → K8s dev rollout，对 dev 测试
> 6. demo2 只读，禁止 merge 进 lumen
> 7. 方案 A：共享聚合核心，前端只调 Java，Java 不写算法、不直连 nGQL、只读 ADS
>
> 重点解释一下 (1) 和 (7)：
> - **算法只在 Python**——这是技术栈隔离。我们之前已经踩过坑——某个早期版本 Java 写了简单的字符串规则匹配，看起来「不算算法」，但破了铁律 1，所以重构。
> - **方案 A**——展示和专题两个前端共享 gkxlumen-topic 后端，避免重复造轮子。
>
> 违反任一铁律 = architect-agent 拒绝合并 + 暂停 + 人评审。

## 第 19 页 · 工具 4：handoff + cost（2 min）

> 每个 task 完工必交两件东西。
>
> **Handoff：证据 md**。包含范围与实现、偏离说明、产物清单、验收证据（CI 绿 + dev URL + 三联查链接）、架构合规自检 7 条、阻塞与风险。
>
> **Cost：task-registry 4 字段**。`estimated_tokens` 派单前估，`actual_tokens` 完工实测，`model_used` 用了哪个模型，`actual_cost` 多少美元，`cost_warn` 等级（green / yellow / orange / red）。
>
> 预算告警阈值：单任务 $5 黄、$10 橙暂停、$20 红 hard stop + architect 评审。
>
> 缺一不收：coordinator 验收清单 7 条全过才能把 status 改为 done。
>
> 全项目预算估算在 `budget-estimate.md`——混合档约 $1230，月均 $308，人均月 $10，与 Cursor Pro 个人订阅相当。

> ui-agent 接 ux-agent 的产物，翻译成真实可跑的 React 代码。
>
> 四个隔离做得很到位：
> 一，**路由隔离**——`/sandbox` 前缀，不进主菜单；
> 二，**文件隔离**——`sandbox/` 子目录，不动现有文件；
> 三，**设计 token 复用**——保持品牌一致；
> 四，**Mock 数据驱动**——不接真实 API。
>
> 这样做的好处：随时可演示给甲方，演示完不影响生产路径。
>
> 评审通过后，frontend-agent 才把它复刻到 lumen 正式仓，加 observability 和真实 API。

## 第 25 页 · 人机协作 7 铁律（2 min）

## 第 26 页 · 5 大反模式（2 min）

> 这 4 个是最容易踩的坑。
>
> **反模式 1：AI 出活人只 review**——3 个月后会变成「废柴团队」，谁都不能独立思考。对策：月度 AI off 一天，强制手写。
>
> **反模式 2：Lead 不亲自跑 agent**——派单不准、评审不到位。对策：Lead 每周必须亲跑 ≥ 3 个任务。
>
> **反模式 3：AI 用得溜 vs 不溜的人产能差 5x**——团队张力很大。对策：把成功 prompt 沉淀进 rules，让谁用都一样。
>
> **反模式 4：Figma 与代码两套真源**——设计与代码漂移。对策：Figma 一次性导出 tokens 后弃用，代码直接维护。
>
> 完整 10 大反模式在 `team-collaboration-playbook.md` 第 7 节。

## 第 29 页 · FAQ（2.5 min）

> 这是大家心里真实的担忧，主动摆上桌。
>
> **Q1: AI 会不会取代我？**
> AI 取代不了评审、决策、创意、客户对接。它取代的是你「不想做的重复活」。拥抱它的人产能 5 倍，抗拒的被淘汰。这是事实。
>
> **Q2: AI 写的代码我看不懂怎么办？**
> 不要合并！必须看懂为止。要么让 agent 解释，要么改写到你能看懂。3 个月后维护时你会感谢现在的自己。
>
> **Q3: 我跑出来的不一致怎么办？**
> 检查三件事：rules 命中？prompt 清晰？必读到位？三者都对还跑偏，升级到 mentor / 架构师。
>
> **Q4: 多个 agent 跑出冲突怎么办？**
> Convoy 分组：同文件给同 agent 串行。Worktree 隔离（Phase 2）。出冲突由 git 标准工具识别 + 人裁决。
