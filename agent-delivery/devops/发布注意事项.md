脚本：`lumen-algo-py/scripts/apply-zhipu-llm-secret.sh`。`lumen-algo-py` 的 `.deploy` 和 `.deploy-set-image` 在 `kubectl` 可用之后、换镜像之前执行它。entan、algo、innov 的发布都会走到这两段模板之一。

2026-10-25 已写入 `lumen-algo-py` 的 CI/CD 变量。三条都是 Masked、未勾 Protected、raw、作用域 `*`。`ZHIPU_LLM_API_KEY` 与现网 Secret 的 `api-key` 相同。`ZHIPU_LLM_MODEL` 为 `glm-5.3-flash`。`ZHIPU_LLM_BASE_URL` 为 `https://open.bigmodel.cn/api/paas/v4`。密钥不进仓库、不进镜像。变量没配对时，发布脚本仍不覆盖现网 Secret。

### 改密钥或换模型

1. 在 GitLab 修改变量。人在页面改。Agent 用 MCP `gitlab-ci-var`（[用法](../gitlab-ci-var-mcp-usage-guide.md)），不要手写 curl，也不要从集群 Secret 把 `api-key` 读出来再写入。
2. 跑一次会执行上述脚本的发布（algo / entan / innov 任一即可，脚本写的是同一份 Secret）。
3. 镜像标签若没变，`kubectl set image` 不会重启 Pod，Pod 继续用启动时读入的环境变量。这时对挂了该 Secret 的 Deployment 做 `rollout restart`。
4. 确认新 Pod 的 `ENTAN_LLM_MODEL` 或 `LLM_MODEL` 已是新模型名。不要 `printenv` 密钥。

手工改集群、又要保留原密钥时，在能 `kubectl` 的机器上取出现有 `api-key`，连同新的 `model`、`base-url`、`chat-url` 再 `kubectl apply`。命令输出里不要打印密钥。

## 2. 每次发布都要核对

- 部署用提交短 SHA，不用 `:latest`。标签不变时 `set image` 不滚动。
- `lumen-algo-py` 的 api 与 worker、`lumen-svc-platform` 的 topic-chain 与 topic-async-service 在 `origin/dev` 自动发布。innov、entan worker、全量 `helm:deploy` 默认手动。
- Helm 已创建的 Deployment，热更新只 `kubectl set image`，不要再用另一份 bootstrap 清单对抗 Helm。
- algo 的 `k8s/api.yaml` 会在 `deploy:api` 里被 apply。清单里的 env 就是下一次发布后的 env。
- 密钥、kubeconfig、Harbor 口令不进 git，不打进镜像。
- 不删除仍被引用的 Secret。`tech-news-zhipu-llm` 已无上述 Deployment 引用，删除仍要人审。
