## 1. 这套机制做什么？

当上游任务（如 **PACK-L01**）在飞书看板标为 **已完成** 后，系统会**自动扫描**是否该解锁下游任务（如 **METRIC-OPEN-L01**、**UX-L01**）。

| 阶段 | 发生什么 | 谁可操作 |
|------|----------|----------|
| **扫描 scan** | 写入「待确认派单」队列（含定义轨 unlock 与门 3 实现轨 unlock） | 任务 done 时自动触发；coordinator 可手动 scan |
| **确认 confirm** | 下游任务 → `ready` + 生成 `{task-id}-派单条.md` + 同步飞书 | **仅 PM 或监管人**（见 §3） |
| **加厚** | 将派单条扩写为 `{task-id}-派单包.md`（可执行说明书） | 监管人或执行会话在开工前完成（见 §4.1） |
| **认领执行** | Agent/成员按**厚派单包** `/goal` 开工 | 执行人 + `supervised_by` 监管人 |

**重要**：confirm **不会**自动打开 Cursor Agent 会话；仍由执行人在新会话中粘贴 `/goal` 话术。  
**重要**：confirm 自动产物是 **派单条（薄）**，**不是**可直接执行的派单包；**禁止**仅凭派单条编码/验收。  
**建单 vs 解锁**：confirm **不会**在 registry 新建 task；新建 leaf 见 [`task-creation-guide.md`](task-creation-guide.md) **§15 档 C**（飞书 `gap_proposal_accept` 或 `merge` CLI）。

## 2. 谁可以做什么？（权限边界）

### 2.1 所有成员

- ✅ 在飞书看板改**自己负责任务**的状态（Ready → 进行中 → 评审 → 已完成）
- ✅ 使用 `update-task-status` 作为标准入口（推荐）
- ✅ 查看待确认队列：`node scripts/coordinator-dispatch.mjs list`
- ❌ **不要**运行 `confirm`（除非你是 PM 或该任务的监管 Lead）
- ❌ **不要**只手改 `task-registry.yaml` 绕过看板（会被 sync 拉回或造成冲突）
- ❌ **不要**把门 3（`*-DG-G3`）标 done，除非 PM/淮政玮 已拍板（门 3 会**进入待确认队列**，须 PM confirm 后才 ready 实现轨）

### 2.2 仅 PM / 监管人可 confirm

`confirm` 命令**必须**携带审批人真名：

```powershell
# Windows（在 gkx-orchestration 根目录）
node scripts/coordinator-dispatch.mjs confirm --all --approved-by human:郭万迎

# 或简写（自动补 human: 前缀）
node scripts/coordinator-dispatch.mjs confirm --all --approved-by 高颖

# 只确认部分任务
node scripts/coordinator-dispatch.mjs confirm --ids ENT-MOD-COMPARE-METRIC-OPEN-L01 --approved-by human:唐绍祖
```

**校验规则**（读取 `team-roster.yaml`）：

| 条件 | 可否 confirm |
|------|----------------|
| `team: pm`（如郭万迎） | ✅ |
| `role: project_owner`（淮政玮） | ✅ |
| `can_supervise_agent: true`（各 Lead / 监管人） | ✅ |
| 评审门默认出席人（review_gates） | ✅ |
| 普通执行成员 / 外部无监管权限 | ❌ 脚本报错拒绝 |

不带 `--approved-by` → **命令直接失败**，不会写 registry。

### 2.3 coordinator / PM 专属

- 运行 `confirm --all --approved-by human:{自己真名}`
- 维护 `dispatch-rules.yaml` 规则
- 开启/关闭全局停派：`dispatch-queue.yaml#coordinator_halt.active`

## 4. 日常协作流程（定义轨示例）

```text
1. 淮政玮/产品 完成 PACK-L01 → 飞书标「已完成」
        ↓（自动 scan）
2. pending 队列出现 METRIC-OPEN-L01 + UX-L01 提议
        ↓
3. 监管 Lead 或 PM 执行 list 查看
        ↓
4. PM/监管人 confirm（带 --approved-by 自己的真名）
        ↓
5. 任务变 Ready + 自动生成「派单条」+ 飞书监管人列更新
        ↓
6. 监管人/执行会话将派单条「加厚」为「派单包」（§4.1）
        ↓
7. 执行 Agent 新开会话，粘贴厚派单包底部 /goal 话术开工
```

### 4.1 派单条 vs 派单包（执行前加厚铁律）

| 名词 | 文件名 | 谁生成 | 内容深度 | 可否直接执行 |
|------|--------|--------|----------|--------------|
| **派单条** | `{task-id}-派单条.md` | confirm 自动链路（Node，不调 LLM） | 元数据 + title + DoD 原文 + `/goal` 骨架 | ❌ **否** |
| **派单包** | `{task-id}-派单包.md` | 监管人 / 执行 Agent 加厚 | 背景、必读、边界、步骤、完整可粘贴 `/goal` | ✅ **是** |

**铁律**：

1. 自动链路 **只**产出派单条；文首须标明「派单条 ≠ 派单包」。
2. 执行 Agent（含 Cursor 新会话）**禁止**仅凭派单条直接认领编码、联调或验收。
3. 开工前必须先完成**加厚**：落盘 `{task-id}-派单包.md`（可保留派单条作审计）；至少写清范围/不做、必读文件、环境与仓、验收证据、完整 `/goal`。
4. 若目录里已有厚派单包，confirm **不覆盖**，`design_refs` 引用既有派单包路径。
5. `git-push-registry` 白名单同时收 `*派单条.md` 与 `*派单包.md`（均须在 `agent-delivery/agent-handoffs/` 下）。

**加厚责任**：默认由 `supervised_by` 监管人在派单后补厚；也可在执行会话开头由 Agent 按本条清单先写厚包、经监管人过目后再编码。

## 5. 门 3 规则（实现轨 · 与定义轨一致须 confirm）

当 **`*-DG-G3`** 任务标为 **done** 后：

- 系统 scan 会将符合条件的 **实现轨**（`delivery_phase: implementation`）任务写入 **pending** 队列（trigger=`impl-gate3-unlock`）
- **必须**由 PM/监管人执行 `confirm --approved-by human:{真名}` 后，才 `backlog` → `ready` 并生成**派单条**
- 派单条仍须按 §4.1 **加厚为派单包**后方可执行
- 因此 **只有 PM/淮政玮** 应在 DG 拍板后标 done；标 done 后仍须 **二次 confirm** 才派单

```powershell
# DG-G3 done 后
node scripts/coordinator-dispatch.mjs list
node scripts/coordinator-dispatch.mjs confirm --all --approved-by human:郭万迎
```

## 6. 审计与追溯

confirm 成功后，registry 对应任务会写入：

- `dispatch_confirmed_by: human:{审批人真名}`
- `note` 中含 `approved_by=` 与时间戳
- `pending-dispatch.yaml` 的 `confirmed` 段保留最近 20 条归档

飞书侧（outbound，不经 inbound sync）：

| 列 | scan 后 | confirm 后 |
|----|---------|------------|
| 派单门控 | 待确认 | 已确认 |
| 确认人 | @监管Lead 或 @PM | 同左 |
| 解锁说明 | `{trigger} ← {cause_task}` | 同左 |
| 状态 | 不变（仍 Backlog） | Ready |

**飞书 confirm 路径**：改「派单门控」→ 已确认 → 自动化 POST `action=dispatch_confirm`（见 `feishu-bitable-webhook-handler.md` §4.2），**不是** Cron inbound 字段同步。

**全量补投影（三列）**：

```powershell
cd gkx-orchestration
node scripts/backfill-dispatch-feishu.mjs --rescan
# 或
node scripts/coordinator-dispatch.mjs project-feishu --rescan
```

规则：pending 队列 → `待确认`；已有 coordinator 派单条/派单包/confirm 审计 → `已确认`；其余 → `—`。

## 8. FAQ

**Q：门 3 DG-G3 标 done 了，实现轨为什么还没 Ready？**  
A：2026-07-21 起门 3 与定义轨一致，须 PM/监管人 **confirm**；请 `list` 查看 `impl-gate3-unlock` 条目。

**Q：我把 PACK 标 done 了，为什么下游还没 Ready？**  
A：定义轨需要 PM/监管人 **confirm**；请先 `list` 看队列，再请有权限的人 confirm。

**Q：我可以帮同事 confirm 吗？**  
A：只有 roster 里的 PM/监管人可以；且必须用 **自己的真名** 作 `--approved-by`，不得冒用他人。

**Q：confirm 会自动派 Agent 吗？**  
A：不会。只写 registry + **派单条** + 飞书；执行仍靠人工加厚为派单包后再 `/goal` 开新会话。

**Q：confirm 生成的是派单包吗？可以直接开工吗？**  
A：**不是**。自动产物叫 **派单条**（薄）。须按 §4.1 加厚为 `*-派单包.md` 后再认领执行；仅凭派单条编码/验收视为违规。

**Q：如何暂停全项目自动派单？**  
A：coordinator 设 `dispatch-queue.yaml` → `coordinator_halt.active: true`。

**Q：长任务过夜还要每叶 confirm / 聊天确认吗？**  
A：**总控一次授权即可。** 见 [`长任务执行规约.md`](长任务执行规约.md)。仍要 registry ID、MCP 认领、厚包、handoff；只免除逐叶问人。签收积压不挡主链。

## 9. 长任务（过夜连跑 · 仍走本体系）

日常流程（§1–§4）不变。当监管人落下 **长任务总控** 并写明「后续认领不必再问」时：

1. 总控 = 本管线的一次 confirm，**代替逐叶聊天确认**。  
2. 下游叶仍须 `task-create`（若未建）→ 厚包 → `task-claim`（`coordinator_dispatch`）→ `/goal` → handoff → AV。  
3. 解锁用规约 **联调闸门**（前序 handoff + `integration`/`pending_test` 即可），不必等 `done`。  
4. `lock_hours=24`。同仓同时只派一张 coding 单。  
5. **禁止**无 task-id 连夜改业务仓。  
6. **段 E**（规约 §11）：禁止逐叶 QA；管线末 E0+E1；QA 不改代码；**期望未发生必红**；红了先失败分类 C1–C6；C1 由 coordinator 派修（可派无提交权分诊助手）；不建 fullstack 编码角色。C1 后点名 deploy 绿 = E0，coordinator 自动调动 qa-agent 只复测（规约 §11.5.2 / §11.5.3）；`lumen-algo-py` 仅 api+worker 自动。禁止等黄敬洲领取卡住循环。

操作细节与 A–D 切法：[`长任务执行规约.md`](长任务执行规约.md)。模板：`templates/long-task-control-template.md`。

## 10. 在 Cursor 里怎么 scan / confirm？

> Cursor **没有**单独的「Scan / Confirm」按钮；通过 **Agent 对话让 AI 跑终端命令**，或自己在 **集成终端** 里执行同一套脚本。

### 10.1 前置条件

1. 工作区包含 **`gkx-orchestration`**（多根工作区已加入即可）
2. 本机已装 **Node 18+**（终端执行 `node -v` 能输出版本号）
3. `gkx-orchestration/.env` 已配置 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`（confirm 后推飞书；缺了仍写 registry，飞书软失败）

### 10.2 方式 A：Cursor Agent 对话（推荐）

在 **Agent 模式** 新开对话，用自然语言 + 明确命令。示例：

**所有人 — 查看待确认队列**

```text
请在 gkx-orchestration 仓库执行：
node scripts/coordinator-dispatch.mjs list
把 pending 里的 task id 列出来。
```

**所有人 — 某任务 done 后补扫（通常不必，update-task-status 会自动 scan）**

```text
请在 gkx-orchestration 执行：
node scripts/coordinator-dispatch.mjs scan --cause-task ENT-MOD-COMPARE-PACK-L01
```

**PM / 监管人 — 确认派单（必须带自己的真名）**

```text
请在 gkx-orchestration 执行：
node scripts/coordinator-dispatch.mjs confirm --all --approved-by human:郭万迎
（把 郭万迎 换成我自己的真名）
```

**PM / 监管人 — 先预览再确认**

```text
请先 dry-run：
node scripts/coordinator-dispatch.mjs confirm --all --approved-by human:高颖 --dry-run
确认输出无误后，再去掉 --dry-run 正式执行。
```

Agent 会在 Cursor **终端**里跑命令；你在终端输出里看 `propose confirm` / `confirm applied` / `[REJECT]`。

### 10.3 方式 B：集成终端手动执行

1. Cursor 菜单 **Terminal → New Terminal**
2. 进入编排仓：

```powershell
cd F:\gkx-lumen\gkx-orchestration   # 按本机 GKX_ROOT 调整
```

3. 执行命令（与 §7 相同）：

```powershell
node scripts/coordinator-dispatch.mjs list

node scripts/coordinator-dispatch.mjs scan --cause-task ENT-MOD-SEARCH-PACK-L01

# 仅 PM/监管人
node scripts/coordinator-dispatch.mjs confirm --all --approved-by human:你的真名
```

Windows 也可用封装脚本：

```powershell
.\scripts\coordinator-dispatch.ps1 list
.\scripts\coordinator-dispatch.ps1 confirm -All -ApprovedBy human:郭万迎
```

### 10.4 多数情况不必手动 scan

用标准入口改状态为 **done** 时，会**自动 scan**：

```powershell
.\scripts\update-task-status.ps1 -TaskId ENT-MOD-XXX-PACK-L01 -Status done
```

流程：`done` → 自动 `scan --cause-task` →（定义轨）进入 `pending` → 等 PM/监管人 **confirm**。

### 10.5 Cursor 里不要做的事

| 操作 | 说明 |
|------|------|
| 让 Agent「直接改 task-registry 标 ready」 | 应走 **confirm** / **update-task-status** / 长任务总控 + MCP，禁止手改 YAML |
| 无总控授权就连夜改业务仓 | 违规；见 §9 与 `长任务执行规约.md` |
| 仅凭自动派单条直接开工 | 须先加厚为派单包（§4.1） |
| 非 PM/监管人让 Agent 跑 `confirm` | 会 `[REJECT]`，浪费一轮对话 |
| 在 Ask 模式期望 Agent 跑终端 | **Agent 模式**才能执行命令 |
