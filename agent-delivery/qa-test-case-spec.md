# QA 测试用例与测试记录规范

> **状态**：正式版  
> **版本**：v1.0 · 2026-08-07  
> **起草 / 维护**：qa-agent · QA Owner  
> **已确认决策**：
> - 功能类型码统一 **`FUNC`**（不以总集样例行中的 `FUN` 为准）
> - GKX 扩展追溯列一律放在**主表右侧**（不另建追溯 Sheet 作为主路径）  
> **总集模板真源**：
> - `原始文档/6.国际科技信息中心项目_xx_测试用例.xlsx`
> - `原始文档/7.国际科技信息中心项目_xx_测试记录.xlsx`
> - 其中「规则 -0529」Sheet 为编号规则真源  
> **工作区模板**：
> - `templates/test-case-template.md`
> - `templates/test-record-template.md`  
> **工作原则**：日常在 git 内用 **Markdown** 维护；对外交付再转录为总集 Excel / Word（字段列：总集标准列在左，GKX 扩展列紧随其右）。

## 1. 目标与适用范围

| 项 | 说明 |
|----|------|
| 目标 | 统一用例/记录的命名、目录、字段、追溯，既满足总集交付，又支持从用户故事与原始需求反查 |
| 适用系统（本项目主责） | 科技信息展示系统、科技专题服务系统、科技专题服务算法库（及相关联调） |
| 适用测试类型 | 功能 FUNC、接口 API、兼容 COMP、集成 INT、性能 PERF |
| 不适用 | 纯开发者单元测试命名（仍可用仓内 `*.test.*` / pytest）；但关键验收场景建议同步登记本规范用例库 |

---

## 2. 设计来源优先级

写用例时按以下顺序取输入（冲突时以上游为准）：

```text
1) USM 用户故事 + 验收场景     agent-delivery/agent-handoffs/产品整体定义/**/USM-*.md
2) bid-reference 原始需求章节  agent-delivery/bid-reference/*.md
3) TRACE / acceptance-catalog  路由、功能点 ID、叶子映射
4) Design.md §14 / UX-UE §3.4  前端与交互验收补充（不扩大功能范围）
```

**禁止**以 PDF 招标原文、口头承诺、未登记 Mock 行为作为验收依据。

## 3. 用例编号规则（对齐总集「规则 -0529」）

### 3.1 格式

```text
{板块}-{系统}-{版本}-{测试类型}-{序号}
```

| 段 | 规则 | 本项目常用值 |
|----|------|----------------|
| 板块 | 拼音大写缩写 | `ZNFWJQ`（智能服务集群） |
| 系统 | 拼音大写缩写；算法等含子模块时可用 `/` | `KJXXZSXT` 科技信息展示系统；`KJZTFWXT` 科技专题服务系统；`SDWJSF/KJZTFWSFK` 科技专题服务算法库 |
| 版本 | 交付版本号 | 默认 `v1.0`（升版时改，不在序号里夹带） |
| 测试类型 | 见下表 | `FUNC` / `API` / `COMP` / `INT` / `PERF` |
| 序号 | 5 位数字，按**系统 + 测试类型**独立递增 | `00001`–`99999` |

**示例**：

```text
ZNFWJQ-KJZTFWXT-v1.0-FUNC-00012
ZNFWJQ-KJXXZSXT-v1.0-COMP-00003
ZNFWJQ-SDWJSF/KJZTFWSFK-v1.0-API-00001
```

### 3.2 测试类型码

| 中文 | 编码 | 说明 | 对应工作 Sheet |
|------|------|------|----------------|
| 功能 | **FUNC** | 页面/业务流程功能 | 功能测试用例 / 功能测试记录 |
| 接口 | API | REST / 内部接口契约与返回 | 按总集归类 |
| 兼容 | COMP | 终端类型 / OS / 浏览器 | 兼容性测试用例 / 记录 |
| 集成 | INT | 跨服务、网关、三方联调 | 集成测试用例 / 记录 |
| 性能 | PERF | 响应时间、并发等 | 性能测试用例 / 记录 |

> 总集样例数据行曾出现 `FUN`；**本规范与总集「规则 -0529」一致，统一使用 `FUNC`。**

### 3.3 板块 / 系统码（摘录）

| 中文名 | 编码 |
|--------|------|
| 智能服务集群 | ZNFWJQ |
| 科技信息展示系统 | KJXXZSXT |
| 科技专题服务系统 | KJZTFWXT |
| 科技专题服务算法库（深度挖掘算法子项） | SDWJSF/KJZTFWSFK |
| 新型高端智库系统 | XXGDZKXT |

未列出的系统编码一律从总集「规则 -0529」原表拷贝，禁止自造。

### 3.4 BUG 编号（总集）

```text
BUG-{板块}-{系统}-{日期}-{序号}
```

- 日期：`YYYYMMDD`  
- 序号：当日 3 位 `001`–`999`  
- 例：`BUG-ZNFWJQ-KJZTFWXT-20260807-001`

失败用例在测试记录中必须关联 BUG 号（无 BUG 时填「待建」并当日补齐）。

## 4. 目录与文件组织（工作区 Markdown）

```text
agent-delivery/
├── qa-test-case-spec.md                # 本规范（正式版）
├── templates/
│   ├── test-case-template.md
│   └── test-record-template.md
└── qa/
    ├── README.md
    ├── code-registry.yaml              # 系统码 / 类型码 / 当前最大序号
    ├── test-cases/
    │   └── {系统码}/
    │       └── {模块层-中文}/          # 与 catalog modules[].id 对齐，如 enterprise-企业分析
    │           └── {模块短名-中文}/    # 与 catalog entries[].title 对齐，如 SEARCH-企业查询
    │               └── FUNC-{模块}-用例.md
    ├── test-records/
    │   └── {系统码}/
    │       └── {轮次或日期}/
    │           └── FUNC-{模块}-记录-{YYYYMMDD}.md
    └── evidence/
        └── {用例编号}/
```

**约定**：

1. 一个 Markdown 文件对应「同一系统 + 同一测试类型 + 同一功能模块」的用例集或记录集。  
2. 文件内用**一张主表**承载：左侧总集列 + 右侧 GKX 扩展列。  
3. 复杂步骤可在表下用 `### {用例编号}` 展开。  
4. 证据文件名：`{用例编号}-{Pass|Fail}-{序号}.png`。  
5. **目录命名铁律**（2026-10-12 定）：`test-cases/` 下每层目录一律 `英文缩写-中文名称` 双语命名；系统码下必须先分**模块层**（对齐 catalog `modules[].id`），再放模块目录——禁止系统码下平铺几十个纯英文缩写目录。`test-records/` 同口径。

## 5. 字段规范

### 5.1 总集必选字段（功能 / 集成 / 性能）— 主表左侧

| # | 字段 | 说明 | 必填 |
|---|------|------|------|
| 1 | 用例编号 | 见 §3 | 是 |
| 2 | 功能模块 | 一级模块中文名 | 是 |
| 3 | 子功能模块 | 无则填 `/` | 是 |
| 4 | 功能项 | | 是 |
| 5 | 子功能项 | 无则留空或 `/` | 条件 |
| 6 | 页面 | 页面中文名或路由标题 | 建议 |
| 7 | 功能点 | 可对齐 catalog 中文名 | 建议 |
| 8 | 测试内容 | 一句话说明测什么 | 是 |
| 9 | 前置条件 | 编号列表 | 是 |
| 10 | 测试步骤 | 编号列表，可执行 | 是 |
| 11 | 预期结果 | 编号列表，可判定 | 是 |
| 12 | 优先级 | P0 / P1 / P2 / P3 | 是 |
| 13 | 是否通过 | 用例库可空；记录必填 | 记录必填 |
| 14 | 测试工程师 | | 记录必填 |
| 15 | 测试时间 | `YYYY-MM-DD` | 记录必填 |
| 16 | 审核员 | | 建议 |
| 17 | 测试截图 | 路径或附件名 | 失败必填 |

### 5.2 兼容性附加字段

插在「功能点」与「测试内容」之间（对齐总集）：终端类型、测试终端/操作系统、浏览器。

### 5.3 GKX 扩展追溯字段 — 主表右侧（必维护）

| 字段 | 说明 | 示例 |
|------|------|------|
| 用户故事编号 | USM 中 `US-*` | `US-E1-SCH-01` |

| 原始需求章节号 | 标题编号 | `1.1.1.2.4.2.3` |

| metric_id | D9 抽样时填 | `M_ENT_...` |
| 交付口径tier | FULL / INTEG / DEMO | `DEMO` |
| 关联任务ID | task-registry | `ENT-MOD-SEARCH-QA-ACCEPT-L01` |
| 自动化用例ID | 若有脚本 | `DS-04.1_events_list_test` |
| 实际结果 | 记录用 | |

| 备注 | | |

### 5.4 「是否通过」取值

| 取值 | 用于 | 说明 |
|------|------|------|
| 通过 | 交付总集 | |

## 6. 优先级

| 级别 | 含义 |
|------|------|
| P0 | 主路径 / Sprint Goal / 阻塞发布 |
| P1 | 重要分支、权限、关键异常 |
| P2 | 次要交互、兼容补充 |
| P3 | 体验优化、低频 |

---

## 7. 用例编写要求

1. **从用户故事出发**：每条 FUNC 用例至少挂 1 个 `用户故事编号`；纯技术 API/PERF 可填 `N/A-技术项` 并说明。  
2. **用原始需求补足**：对照 bid 章节补漏测。  
3. **步骤可执行、结果可判定**。  
4. **一条用例一个判定点**。  
5. **DEMO/Mock**：`tier=DEMO` 时写明 Mock 边界。  
6. **与自动化关系**：脚本名写入「自动化用例ID」，总集编号仍用 §3。

---

## 8. 测试记录与复测

复测**沿用同一用例编号**，只更新实际结果、是否通过、复测轮次；不得为复测新编用例号。

---

## 9. 转录交付（MD → 总集 Excel）

1. 按测试类型拆 Sheet。  
2. **主表列顺序 = 总集标准列 + 右侧 GKX 扩展列**（与工作区一致）。  
3. 标题行：`{板块中文}-{系统中文}测试用例` / `...测试记录`。  
4. 「阻塞/跳过」不得直接进入总集「是否通过」列。  
5. 报告汇编仍可用 `templates/acceptance-test-report-template.md`。
