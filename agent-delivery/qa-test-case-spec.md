## 3. 用例编号规则（对齐总集「规则 -0529」）

### 3.1 格式

```text
{板块}-{系统}-{版本}-{测试类型}-{序号}
```

| 段 | 规则 | 本项目常用值 |
|----|------|----------------|
| 板块 | 拼音大写缩写 | `ZNFWJQ`（智能服务集群） |
| 系统 | 拼音大写缩写；算法等含子模块时可用 `/` | `KJXXZSXT` 科技信息展示系统；`KJZTFWXT` 科技专题服务系统；`SDWJSF/KJZTFWSFK` 科技专题服务算法库 |
| 版本 | 交付版本号 | 默认 `v1.0`（升版时改，不在序号里夹带） |
| 测试类型 | 见下表 | `FUNC` / `API` / `COMP` / `INT` / `PERF` |
| 序号 | 5 位数字，按**系统 + 测试类型**独立递增 | `00001`–`99999` |

**示例**：

```text

ZNFWJQ-KJXXZSXT-v1.0-COMP-00003
ZNFWJQ-SDWJSF/KJZTFWSFK-v1.0-FUNC-00001
```

1. 一个 Markdown 文件对应「同一系统 + 同一测试类型 + 同一功能模块」的用例集或记录集。  
2. 文件内用**一张主表**承载：左侧总集列 + 右侧 GKX 扩展列。

6. **系统码目录写法**（2026-10-13 定）：算法库等含 `/` 的系统码，**编号内保留 `/`**（`ZNFWJQ-SDWJSF/KJZTFWSFK-v1.0-FUNC-#####`），**目录名用 `-` 连接**（`SDWJSF-KJZTFWSFK/`）；旧自造码 `KJZTFWALGO` 废弃（任务 ID `QA-KJZTFWALGO-*` 保留历史不改）。
7. **测试类型落位**（2026-10-13 定）：COMP/INT/PERF 用例与 FUNC **同模块目录混放**，文件名前缀区分（对齐总集「用例挂功能模块」交付形态）；系统级用例（登录链路/网关/性能基准）入 `{系统码}/shell-系统壳/`。
8. **算法库 B 线**（2026-10-19 修订）：方法论见 `qa/algo-lib-api-case-playbook.md` §长任务返工。在联调台 `https://edu.itic-sci.com/dma/algovwz/` 按页面操作编写；功能模块到子功能项对应需规三至六级；编号用 FUNC；功能点去掉自行添加的 A1/A2；测试内容写「验证…功能，检查…」。路径例：`…/CHAINBASIC-产业链基础指标/FUNC-产业链基础指标-用例.md`。旧 `API-00001`～`02210` 作废。
9. **展示系统开发阶段用例**（2026-11-05，`human:淮政玮`）：开发叶上的单元测试用例、主路径用例、当轮验收用例，正文放 `agent-delivery/工程过程/04-系统集成/05-展示系统集成/测试用例/{任务ID}.md`。细则见该目录 `README.md`。总集 FUNC 用例仍在 `qa/test-cases/`。仓内 pytest、JUnit、`*.test.*`、`.mjs` 自检仍留代码仓。交接写在 `agent-handoffs/`，并指向本目录的用例文件。

### 5.4 内容红线（2026-10-12 定；适用于测试内容/前置/步骤/预期四列）

1. **正文零内部引用**：四列禁止出现 USM AC / US-xx / Q0xx / GAP / 开放项 N / 归 FUNC-xxxxx / coverage # / TRACE / metric_id / 任务 ID / 文件路径（同册用例互指除外）；追溯数据进 §5.3 扩展列与备注。
2. **observed 不进预期；废弃态不验不可见**：勘察观测只作输入，可判定终态才进预期；已废弃能力不写「不可见」反向校验（归覆盖矩阵未覆盖）。
3. **步骤只写操作，校验全进预期**：步骤 = 动词短语操作序列（做）；预期 = 操作后系统状态（看）。「核对/确认/检查/观察」不进步骤，「点击/切换」不进预期。
4. **一句一事**：单条步骤/预期 ≤ 60 字且只含一个操作/校验点；步骤 ≤ 7 步，超出拆用例；长枚举放附录。
5. **场景分层**：模块内按 主流程(P0) → 备选(P0/P1) → 异常(P1/P2) → 权限态(P1) 排列，禁止混排；场景类进「功能项」列前缀。

### 5.4.1 用例级粒度铁律（2026-10-13 定，用户复审追加；优先级高于红线 4）

> 背景：378 条存量复盘发现「条目级合规、用例级超标」——单条字数与单点都合规，但预期断言密度膨胀（全库均值 5.0 点/条，极端 11 点），条数在区块级收缩（一册 10 条），失败隔离度与回归效率劣化。根因：生成时只扫可机械校验的条目级红线，把「一条用例一个判定点」架空。本节把判定点规则从原则落到可操作判据。

**定位声明**：B 线用例库（工作区 MD）的**首要定位是指导测试执行**；甲方验收阅读件是 `delivery/` 按功能点拆分与覆盖提取后的 Excel 交付物。两者不是同一件东西，文风与粒度按各自定位独立要求。

1. **一测一问一答**：一条用例 = 一次测试回答**一个问题**。通过测试步骤到达某状态，预期结果回答该问题。
   - 主断言 = 这条用例的身份；测试内容（一句话）必须能概括这个问题，概括不了 = 塞了不止一件事。
   - **预期断言常态分布 = 1～3 点**，其中 1 点为主断言；4～5 点为上限例外（如「区块构成」类结构性检查），**不得成为均值**；≥6 点必须拆条。
2. **顺带点并入三条件**（全部满足才允许写进同一条，缺一即拆）：
   - 同一路径上**零额外操作**即可观察到（不加步骤）；
   - 失败时**修复动作与主断言同域**（大概率同一个 BUG 一起修）；
   - 不跨状态转移（都在同一到达后状态上）。
   - 判别口诀：为看到它得多做一个操作 → 它就是一条新用例。
3. **回归隔离判据**（终极标准）：这条用例 Fail 时，执行者应无需通读全部断言就知道报什么 BUG、修好后重跑哪一条。一条用例 = 一次失败 = 一个明确行动。
4. **正向密度下限**：每个可见区块的主状态机（默认态 / 典型值 / 边界值）至少各 1 条正向用例；主流程条数不得低于备选+异常合计。A 线覆盖矩阵 `N≥1` 仍是底线，正向场景数不足按本条补。
5. **上限是护栏不是靶心**：红线 4 的 ≤60 字 / ≤7 步是**最大允许值**，不是写作目标。正常用例从「回答什么问题」出发，篇幅自然落在下限区间；贴上限写作视为粒度违规。
6. **金样标记**：每册的正向核心用例（对应 as-built `gold.yaml` 冒烟子集）在元信息区与「备注」列标 `金样`；金样必须正向、可独立执行、覆盖核心功能点。烟测 = 跑全部金样。

## 7. 用例编写要求

1. **从用户故事出发**：每条 FUNC 用例至少挂 1 个 `用户故事编号`；纯技术 API/PERF 可填 `N/A-技术项` 并说明。  
2. **用原始需求补足**：对照 bid 章节补漏测。  
3. **步骤可执行、结果可判定**；步骤/预期分工与粒度按 **§5.4 内容红线** 执行。  
4. **一条用例一个判定点**；场景分层（主流程/备选/异常/权限）按 §5.4 第 5 条。  
5. **DEMO/Mock**：`tier=DEMO` 时写明 Mock 边界。  
6. **与自动化关系**：脚本名写入「自动化用例ID」，总集编号仍用 §3。

## 8. 测试记录与复测

复测**沿用同一用例编号**，只更新实际结果、是否通过、复测轮次；不得为复测新编用例号。

**执行判别与时序提示（v1.3）**：

1. **allow_skip 边界（S1）**：被测功能**自身的行为缺失**（即使由数据触发，如「无命中反馈」未实现）**不适用 allow_skip**，必须判 Fail；只有「功能无法被触发」（前置数据不存在）才可 skip，且 observed 必须记录为何无法触发。
2. **跨 tick 时序（S2）**：交互后断言须跨 tick 或显式 wait（React 受控组件 setState 异步，同一次求值内交互+读态会读到旧值造成假红）；属执行工程注意，Playwright 原生 expect 自动等待可兜底。
