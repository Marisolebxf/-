## 1. 概述

### 1.1 背景

企业要素（ENT）是科技信息展示系统与科技专题服务系统的核心数据要素之一。功能侧由 `ENT-functional-design-v2.md`（v2.1.0）统领，覆盖 **门户集群服务 · 企业发展（Layer A，E-31~E-35）**、**专题战略分析 · 企业分析（Layer B，E-20~E-30）**、**内容运营（Layer C，E-36~E-37）**，共 **18 个验收点**。本说明书为上述功能提供企业要素全链路的数据库支撑。

> 说明：本说明书描述的库表是否"满足全部 18 验收点"属于验收结论，留待 qa-agent 实测 + PM 终审；本文仅陈述设计与对齐关系（来源：关联文档 5 §16 验收矩阵）。

### 1.2 设计范围

企业要素全链路数据库，包括：

- **DWD 自建标准明细层**：9 张表（企业主表 + 财务/专利历史 + 母子公司/供应链/产业链/合作/标签/资讯）；
- **ADS 应用结果层**：13 张表（直供 Java 只读，按 18 验收点对应的页面读模型组织）；
- **cfg_metric 指标注册**：注册 49 个 `M_ENT_*` 指标的 D9「8 件套」元数据；
- **NebulaGraph 图谱**：space `gkx_enterprise`（6 Tag + 8 Edge）；
- **三段映射 + 覆盖率 + DQ 规则 + Mock 策略**。

（来源：关联文档 1 表头「范围」、§4/§5/§6/§7。）

### 1.3 分层链路（ODS→DWD→DWS→ADS）

```text
三方「要素库」(186 张 dwd_* 表，归属 ODS 贴源层，只读)
        │  数据工厂清洗 / 归一 / 聚合（Python）
        ▼
DWD 自建标准明细层  gkx_dwd.enterprise / enterprise_*（字段沿用 ODS）
        │  DWS 轻聚合（行业基准/区域聚合/历年趋势）+ algorithm-agent 评分模型
        ▼
ADS 应用结果层  ads.ent_*（直供 Java 只读 / 前端，契约面，冻结）
        │
        ├──► MySQL（RDBMS：DWD / ADS / cfg）
        └──► NebulaGraph space=gkx_enterprise（供应链 / 合作 / 母子图谱）
```

| 层 | 物理位置 | 谁写 | 谁读 | 本设计交付 |
|----|---------|------|------|-----------|
| ODS | 三方要素库（命名 `dwd_*`） | 供应方 | 数据工厂（Python） | 引用，不建 |
| DWD | `gkx_dwd.*` | Python ETL | Python / algorithm | ✅ 9 张表 |
| DWS | `gkx_dwm.*` | Python + algorithm | Python | 🟦 预留（本期占位） |
| ADS | `ads.ent_*` | Python | **Java 只读** + 前端 | ✅ 13 张表 |
| cfg | `gkx_cfg.cfg_metric*` | data + algorithm | 全域 | ✅ DDL + 49 注册 |
| 图谱 | NebulaGraph `gkx_enterprise` | Python 灌数 | Python（Java 禁直连 nGQL） | ✅ tag/edge schema |

（来源：关联文档 1 §1.1。）

### 1.4 三引擎分工

| 引擎 | 承载 | 说明 |
|------|------|------|
| **MySQL 8.0**（utf8mb4） | DWD 明细、ADS 读模型、cfg 配置 | RDBMS 主存；Java 只读 ADS |

## 2. 数据库与 Schema 规划

MySQL 中「schema = database」。按总纲 §2.1 逻辑划分落地为以下 database：

| database | 归属层 | 写 | 读 | 内容 |
|----------|--------|----|----|------|
| `gkx_dwd` | DWD | Python | Python / algorithm | 企业标准明细 9 张 |
| `gkx_dwm` | DWS | Python | Python | 行业基准 / 区域聚合 / 历年趋势（本期占位预留） |
| `ads` | ADS | Python | **Java 只读** | 企业应用结果 `ent_*` 13 张 |
| `gkx_cfg` | 配置 | data / 运维 | 全域 | `cfg_metric` / `cfg_metric_lineage` / `cfg_degrade_switch` |
| `gkx_dim` | 维表 | Python | Python / Java | 区划维表 `dim_region`、产业链维表 `dim_industry_chain`（复用/扩展） |

> **Java 只读 ADS 契约铁律**：前端 → Java REST → ADS；算法 → Python `/internal/*`。Java 不写算法、不直连 nGQL、只读 `ads`（来源：团队公约 §2 铁律 2/7；关联文档 5 §14.3）。

**逻辑名 ↔ 物理名约定**：cfg_metric 种子与映射报告以 `dwd.enterprise` 引用 DWD 表，物理为 `gkx_dwd.enterprise`；以 `ent_*` 引用 ADS 表，物理为 `ads.ent_*`。

**通用列规约**（每张表，来源：关联文档 1 §2）：

- 主键 `id BIGINT AUTO_INCREMENT`；业务键 `enterprise_code VARCHAR(64)`（统一社会信用代码）。
- 系统列：`create_time` / `update_time`（`ON UPDATE CURRENT_TIMESTAMP`）。
- 批次列（ADS）：`calc_batch_id VARCHAR(64)`（Mock 阶段前缀 `mock_`）。
- 扩展列：`ext JSON NULL`（兜底三方未预见字段，避免后续改表）。
- 字符集：`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`。

## 3. 实体归一与主键策略

### 3.1 双源企业主数据归一

企业主数据存在**双源**，需以统一社会信用代码归一（来源：关联文档 1 §3.1、关联文档 4 §2）：

| 来源（ODS） | 行键 | 归一键 | 口径 |
|------|------|--------|------|
| `dwd_org_reg_info`（国内机构） | `org_id` | `external_id`（统一社会信用代码） | 机构口径，含经纬度/上市状态 |
| `dwd_company_base`（量子专题工商通用） | `id` | `credit_code`（统一信用代码） | 工商口径，含企业类型三级/实缴资本 |
| `dwd_forg_base_info`（国外机构） | `org_id` | `external_id`（当地注册码） | 跨境，主键体系不同，单独处理 |

**归一规则**：`enterprise_code = COALESCE(o.external_id, c.credit_code)`，机构口径为主、工商口径补全（`FULL JOIN ON external_id = credit_code`）。详见映射报告 §8 示例 ETL。

### 3.2 主键策略

| 键 | 类型 | 角色 | 说明 |
|----|------|------|------|
| `id` | BIGINT AUTO_INCREMENT | 物理主键/外键 | 子表 `enterprise_id` 外键引用 |
| `enterprise_code` | VARCHAR(64) UNIQUE | **业务归一主键** | 统一社会信用代码，跨表/跨图谱稳定键 |

- 子表同时携带 `enterprise_id`（FK）与 `enterprise_code`（冗余，便于直接按信用代码查询与图谱对齐）。
- NebulaGraph `vid = ent:{enterprise_code}`（**与 RDBMS `enterprise_code` 对齐**），保证 RDBMS↔图谱稳定一致、跨批次不漂移（详见 §7、§11）。

> 来源：关联文档 2（差异对比报告）。现有原型为两套独立 POC：**算法 POC（`ent-analysis-demo`，PostgreSQL + NebulaGraph `entan`）** + **展示原型（`topic_demo/enterprise`，前端内联 Mock）**，均未对接真实 ODS、均无 cfg_metric 注册。本设计是首个「ODS 真源对齐 + ADS 契约 + D9 血缘」的正式库设计。

### 11.1 关键差异

| 维度 | 算法 POC | 展示原型 | 本设计 |
|------|----------|----------|--------|
| 引擎 | PostgreSQL + NebulaGraph(`entan`) | 无 DB（前端内联） | MySQL 8 + NebulaGraph(`gkx_enterprise`) |
| 字段命名 | 自造英文短名 | camelCase | **严格沿用 ODS** |
| 业务键 | ❌ 无统一信用代码 | ❌ 无 | ✅ `enterprise_code`（统一社会信用代码）UNIQUE |
| 实体归一 | ❌ 无双源归一 | ❌ | ✅ `external_id ∪ credit_code` |
| 图谱 vid | `ent:{id}`（自增，**跨批次漂移**） | —— | `ent:{enterprise_code}`（**稳定一致**） |
| cfg_metric 8 件套 | ❌（仅算法侧 model 注册） | ❌ | ✅ 49 条 `M_ENT_*` 全注册 |

### 11.2 迁移改造清单（P0~P3）

| 优先级 | 改造项 | 目标 | 工作量 |
|--------|--------|------|--------|
| 🔴 P0 | 图谱 vid 改造：`ent:{id}` → `ent:{enterprise_code}` | 稳定关联 | 中 |
| 🔴 P0 | 字段名对齐 ODS（自造短名/camelCase → ODS 命名） | 字段映射 | 大 |
| 🔴 P0 | 引擎迁移：PostgreSQL → MySQL 8（bigserial→AUTO_INCREMENT，text→JSON） | 总纲合规 | 中 |
| 🔴 P0 | 实体归一：建双源归一 ETL（external_id ∪ credit_code） | 主键统一 | 大 |
| 🟠 P1 | cfg_metric 注册：落 49 条 8 件套 + `M_E1_*→M_ENT_*` 改名 | D9 合规 | 中（种子已备） |
| 🟠 P1 | ADS 重构为页面读模型：算法中间表 → `ent_*` 契约表 | Java 只读契约 | 大 |
| 🟠 P1 | 前端 Mock 下线：内联数据 → 调 Java 读 ADS | 调用链合规 | 大 |
| 🟡 P2 | 算法迁移复用：ENT_WEIGHTED_SCORE/中心性等 model 接新 DWD/ADS | 复用 | 中 |
| 🟡 P2 | 补 A 层门户表：panorama/star/shenzhen/map_layer/painpoint | 支撑 E-31~35 | 中 |
| 🟢 P3 | DQ 入 CI：15 条规则 | 质量门禁 | 小 |
| 🟢 P3 | 映射登记补登：`data-source-mapping-registry` 扩 DWD9+ADS13 | 血缘完整 | 小 |

> 算法与图谱可大量复用：算法 POC 的 12 个 model（`cfg_model_registry.yaml`）+ 图谱构建脚本可迁移，仅需对齐 `M_E1_*→M_ENT_*`、改 vid/space/数据源连接（来源：关联文档 2 §3、§7）。
