## 内容红线（2026-10-12 用户复审追加；378 条存量复盘中 5 类问题命中 34%~91%，禁止再犯）

用例是**给人读的验收描述**。以下是硬红线，违反任何一条 = 该条用例重写。红线 1～6 管单条怎么写；红线 7～8 管测什么、怎样才算写完。

### 红线 1：正文零内部引用

「测试内容 / 前置条件 / 测试步骤 / 预期结果」四列**禁止出现**任何内部编号引用：

- 禁止出现：`USM AC-xx-yy` / `US-xxx-01` / `Q0xx` / `GAP-*` / `开放项 N` / `归 FUNC-xxxxx` / `coverage #N` / `TRACE-*.yaml` / `metric_id` / 任务 ID / 文件路径。
- 例外（唯一）：用例编号本身（如「与用例 00169 分开验收」这类**同册互指**允许，但优先拆句到备注）。
- 需要引用的信息一律两种去向：
  - **给人看的背景** → 把具体内容直接写进正文（如 ❌「遵守 USM AC-02-02」→ ✅「视口操作不改变已选产业条件」）；
  - **给脚本/追溯用的数据** → 只进右侧扩展列（用户故事编号 / USM验收场景编号 / 功能点ID / TRACE引用 / metric_id / 关联任务ID / 备注）。
- 「开放项 / 待甲方确认」类治理标记：正文最多写**人话**（如「时间控件当前为只读，为已确认的临时形态」），编号与跟踪状态写备注（如 `备注：开放项2，Q068`）。

### 红线 2：observed 不进预期、废弃态不验不可见

- **勘察观测项（observed）禁止写成预期结果**。现场记录的「执行时以现场为准 / 记 observed / 勘察时为 X」都是**输入信息**，不是验收标准。预期只写**可判定的终态**；确实无法判定终态的观测点 → 该校验点从预期中删除，挪备注 `备注：observed-执行时记录（原勘察：…）`。
- **「现场未展开 / 执行时再看 / 勘察未点击 / 未执行确定」不是未覆盖。** 关评审后能点开的 Tab、按钮、抽屉、下拉、确认框，必须点到可判定终态再写用例。只有构造不出终态（造不出失败、没有第二种账号、名单不够翻页）才允许标 **未覆盖 + 原因**。
- **会改掉共享数据的操作**（删除、清空）：至少写一条「点操作 → 取消 → 原数据仍在」。环境允许时再写「确定 → 数据消失」。两条都没有、只写未覆盖 = 该格未写完。
- **设计后被推翻 / 已移除的形态，不写「不可见」校验**。例：旧方案有断点标记后被砍 → 不要写「页面不显示断点标记」这种反向预期（无法穷举不存在的东西）。已废弃能力只在 coverage 矩阵记 `未覆盖+原因`，不进用例。

### 红线 3：步骤只写操作，校验全进预期

- 「测试步骤」= **人对系统的操作序列**（点击 / 输入 / 选择 / 切换 / 清空 / 上传 / 等待完成）。每步一个动词短语开头。
- **禁止**在步骤里写「核对 / 确认 / 检查 / 校验 / 观察 / 比对 / 验证 / 查看是否」——这些全部是校验动作，改写成预期结果条目（「下拉含 15 个选项」而不是「核对下拉选项」）。
- **禁止**在预期里写操作（「点击切换后」「再次点击」）——预期只描述操作完成后系统**应处于的状态**，不描述怎么到达。
- 边界判不准时的口诀：**做 = 步骤；看 = 预期**。

### 红线 4：一句一事，长度上限

- 步骤 / 预期**每条编号项只含一个操作或一个校验点**。发现「且 / 并 / 同时 / ，且」串联多个点 → 拆成两条。
- 长度上限：单条步骤 ≤ 60 字，单条预期 ≤ 60 字；步骤总数 ≤ 7 步，超出 = 拆用例（拆出的用例在备注互指）。
- **上限是护栏不是靶心**：正常用例从「这条要回答什么问题」出发，篇幅自然落在 1～3 条预期、2～4 步；贴上限写作（字数压线、步数压线、断言堆满）= 粒度违规（见红线 6）。
- 长枚举（如 15 个产业集群全名）不硬塞进步骤：步骤写「展开产业下拉」，预期写「选项与生产环境一致（共 15 个产业集群）」，全量清单放用例册附录或备注。

### 红线 5：场景分层，先主后备选异常

每模块用例必须按以下顺序分组排列，禁止主流程 / 边界 / 异常 / 权限混排：

1. **主流程（P0）**：正常业务路径，默认条件直达终态；
2. **备选场景（P0/P1）**：参数边界、多状态切换、回退往返；
3. **异常场景（P1/P2）**：空态 / 失败态 / 越权 / 非法输入；
4. **权限态（P1）**：无权限、只读角色（有权限体系才写）。

分组方式：用例总表内按序排列 + 「功能项」列体现场景类（如 `异常-空态` / `备选-条件回退`），不另建 sheet。

### 红线 6：用例级粒度——一测一问一答（2026-10-13 追加；spec §5.4.1）

> 378 条存量复盘：条目级全合规，但全库均值 5.0 断言/条、极端 11 点，一册 10 条塞下 12 个主题——失败隔离度废了。本红线把「用例级粒度」从口诀变成判据。

- **一条用例 = 一次测试回答一个问题**。主断言 = 用例身份；「测试内容」一句话概括不了 = 塞了不止一件事，拆。
- **预期断言常态 1～3 点**（1 主断言 + 最多 2 个顺带点）；4～5 点 = 结构性检查类上限例外，不得成为常态；**≥6 点必须拆条**。
- **顺带点三条件**（缺一即拆）：同一路径零额外操作可见；失败与主断言同域（同一 BUG）；不跨状态转移。
- **判别口诀**：为看到它得多做一个操作 → 它是一条新用例。
- **回归隔离**：这条用例 Fail 时执行者应无需通读全部断言就知道报什么 BUG。一条用例 = 一次失败 = 一个明确行动。
- **正向密度**：每个可见区块的默认态/典型值/边界值至少各 1 条正向用例；主流程条数 ≥ 备选+异常合计。不要一个功能四五条收工，也不要为凑数写空转用例。
- **金样标记**：每册挑正向核心用例做烟测子集（对应第 2 步 `index.yaml` 的 `gold`），备注列标 `金样`；金样必须正向、可独立执行。分析工作区的金样是红线 8 里**本页实际存在的每条核心主线**（每种发起方式各一条，走到完成结果）。本页只有一种发起方式就只标这一条，不要为了凑第二条去发明名单或筛选器。金样不能代替其余控件清单。
- **本红线不是「少写」许可证。** 它禁止一条用例塞多个主题；清单上每一格仍须有自己的一条用例（红线 8）。把整页收成「能发起、表上有几列」= 漏测，不是粒度合规。

### 红线 7：内部评审模式关闭，评审层不是测试对象（2026-10-17）

交付用例验收的是**业务用户在关评审时能看见、能操作的能力**。内部评审模式（人设面板 switch，`aria-label="内部评审模式"`）是内部走查开关，不是交付内容。

- **盘点、写用例、交卷自检**都在开关为关时进行。不得为了看见某个控件去打开评审。
- **禁止单独占一条 FUNC，也禁止写成金样。** 功能项、前置、步骤或预期里出现「内部评审」「评审模式」「评审开关」「人设面板」「需求追溯」「零泄漏」「评审关闭」即违规。关评审是勘察和机跑的会话前置，不是被测能力。「打开人设面板并确认开关为关」不得占号，不得标金样。
- 只在 `reviewMode` 下出现的 `MetricSpecCard`（指标说明 ⓘ）、`PendingBadge` / Q0xx 角标、评审状态模拟下拉，不写步骤、不写预期。
- **主流程里夹带的开评审、点追溯、扫泄漏、验开关状态**：从前置、步骤和预期里删掉。业务异步（设条件 → 开始分析 → 成功 / 空 / 失败）用真实操作写；构造不出的失败态进清单「未覆盖」，不用评审下拉代替。
- 关评审后产品仍然展示的业务控件照常写。`coverage-fp` 若保留「评审增量」列，只作内部备注，**不得**据此新增 FUNC，也不得据此把该格标成已覆盖。

任务列表先写列名（禁止「状态与时间类」这种笼统说法）。行上每一种操作（恢复结果、按此配置新建、查看报告，以现场按钮名为准）与每一种发起起源（入口 A、入口 B）组成一格，**各写一条**。一条「两种起源都能恢复」不能代替「查看报告 × 入口 B」。没有该按钮或该起源才写「无」。

**列表 / 查询 / 图谱**不用上表硬套。改用短清单：筛选条件（下拉须写选项个数）、结果表列、行上每个按钮、翻页、抽屉（写出区块标题）。同样一格一条或未覆盖+原因。下拉、详情、入池三条与上表相同。

A 线功能点矩阵（过程 §3）是后置核对。矩阵全部「已覆盖」**不能**代替本清单收口。

**目录命名铁律**（2026-10-12 用户指定）：

1. 每层目录一律 **`英文缩写-中文名称`** 双语命名（如 `PANORAMA-产业链全景图谱`），纯英文缩写目录禁止——人没法找东西。

### 3. A 线覆盖检查（现在才打开功能点表）
