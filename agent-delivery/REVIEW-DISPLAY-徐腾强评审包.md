### ⚠️ C1 与本文方案的冲突（A1，本包最关键一项）

你原话：「**java 这吧只增加一个聚合服务，其他的都复用专题那边的链路？**」，李拜六回「理论上是这样的」。但调研发现三件事与该前提不符：

| 维度 | C1 的前提 | 调研实际 |
|---|---|---|
| 专题侧可供复用 | 专题链路已实装、能直接供数 | 展示所需形态（要素 count / 落点 / 热力 / 时间序列）在 `gkxlumen-topic-*` **未实装**；已实装的是检索 / 画像 / 对比篮（`gkx_search_service` 76 端点） |
| 隔离 | — | 复用 topic-* 意味着下游接专题侧 Python 门面 :8080，**与 D15 三重隔离直接冲突** |
| 供方 | 「不止咱们自己还有其他公司的」 | 展示侧供方（久新 / 燕大 / 智谱 / 深势）与专题侧不同，**通道无法共用** |

**我的判断**：C1 中「只增加一个聚合服务」在**对外暴露面**上成立（display 唯一对外，L3 全部 `@Inner` 不对外）；但「复用专题链路」不成立，故建议**新建 3 个 L3 服务**。

✅ **你已裁决：「展示侧不复用专题侧」→ A1 = (a) 新建 3 个 L3 服务。**

**连带效果**：原担心的「第三方可见性过滤污染展示侧查询结果」问题**自动消解**，不再需要确认。
