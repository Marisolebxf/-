# 端到端交付流程与人机干预宣贯

> **读者**：全员（PM / 产品 / UE / 架构 / 前后端 / 算法 / 数据 / QA / Lead）  
> **目的**：一页看清「产品定义 → 工程实现 → 测试签收 Done」全链路，以及**哪一步必须人出手、怎么出手**  
> **真源**：`产品定义评审规程.md` · `产品实现规程.md` · `task-claiming-guide.md` · `task-creation-guide.md` · `user-story-library.yaml` · `feishu/feishu-user-story-board.yaml` · 团队公约 §7  
> **维护**：PM（郭万迎）· 日期：2026-08-03  
> **修订**：2026-11-07。SDD、合规演示用例、演示样本循环收进 `产品实现规程.md` §4.1、§6.4、§6.5。

## 0. 一句话

> **AI 起草与执行；人拍板、会签、监管、测通、签收。**  
> 没有人签字的门，Agent 不得假装过关；没有 `supervised_by` 真名，Agent 不得开工。  
> **故事 Done ≠ 单任务 Done**：故事状态由关联任务自动滚动；**全部任务开发完成才能进集成测试，集成测试通过故事才算已完成。**

## 1. 全景图（两段六门 + 故事层）

```text
【定义段 · 产品定义评审规程】
  PACK 五件套草稿
    → METRIC-OPEN ∥ UX/UI（可并行）
    → （可选）V1 高保真首轮
    → 门1 PDR 完整闭合 ──► 用户故事入库（US-*）
    → 联合修订冻结
    → V2 lumen 准生产  ∥  门2 体验+语义
    → 门3 DG 拍板  ──解锁工程──┐
                                │
【实现段 · 故事驱动】            ▼
  故事拆单提案 → PM 采纳建单（leaf 挂 user_story）
    → SDD：调研 → 系统详设 → 二级四单会签（产品实现规程 §4.1）
    → 门 I1 开工（confirm → ready）
    → 认领 / 监管开发（各 leaf 并行）
    → 模块可调、库内已有数据：开发负责人写《合规演示用例》
    → 调度核对：需规每条有一行（空行退回补用例，不建循环）
    → 该模块演示样本循环（只读核对已填好的请求）
    → ★ 故事下全部 leaf 齐步「开发完成」
    → 故事级联调 / 集成测试（门 I2 + QA，走用例主路径）
    → 测通 → 故事「已完成」；leaf 待签收 → 淮政玮签收 leaf Done
```

| 层 | 管什么 | 结束标志 |
|----|--------|----------|
| **定义段** | 做什么、长什么样、口径与范围 | 门 3 DG ✅ |
| **任务 leaf** | 单仓/单域可派工单元 | leaf `done`（淮政玮签收） |
| **用户故事** | 端到端可验收价值切片 | 故事「已完成」= **关联实现任务全部测通** |

**硬边界**：门 3 之前工程 leaf **不得**标 `ready` 开工；门 1 后只允许故事入库 + 拆单**提案**（`backlog`）。

## 2. 用户故事库状态（自动绑定，禁止手改）

> **真源**：`user-story-library.yaml` → 飞书「用户故事库」只读投影  
> **推导**：`scripts/lib/story-progress.mjs`（由 leaf 的 `user_story` 关联滚动汇总）  
> **铁律**：飞书「实现状态」**禁止拖拽手改**；要改进度，只推进关联任务状态。

### 2.1 绑定关系

```text
USM 故事（US-*）
    │ 门1 后入库
    ▼
user-story-library.yaml
    │ leaf.user_story = "US-xxx"（可多故事共挂）
    ▼
task-registry 实现任务（FE/JAVA/DATA/…）
    │ 滚动汇总
    ▼
故事「实现状态」七态 → 飞书看板泳道
```

| 人要保证的 | 说明 |
|------------|------|
| **关联完整** | 承接该故事的实现 leaf 都写了 `user_story`；缺挂 = 故事永远「已定义」或进度假低 |
| **不手改故事状态** | 只改任务状态；同步脚本自动回填故事库 |
| **齐步交件** | 不要单 leaf 抢先进测试冒充故事已测 |

### 2.2 七态含义

| 故事状态 | 含义 | 何时出现（自动） |
|----------|------|------------------|
| **已定义** | 有故事，尚无实现向任务（或未排期未开工） | 无关联 impl leaf / 仅 backlog 未挂 sprint |
| **已排Sprint** | 已写入 `sprint_id`，尚未开工 | 关联任务已排期，未 claimed |
| **开发中** | 仍有 leaf 未离开开发态 | 存在 claimed / in_progress；或**参差**（有人已联调、有人还在开发） |
| **开发完成** | **齐步交件**：全部关联实现任务恰好 `integration` | ★ 此时才允许开**故事级集成测试** |
| **联调中** | 全部 ≥ `integration`，联调进行中或参差未齐测 | 门 I2 / 故事级联调 |
| **测试中** | 全部 ≥ `integration`，且已有 `pending_test` / `testing` | QA 领取后 |
| **已完成** | 全部关联实现任务 ≥ `ready_to_sign`（含 `done`） | **= 集成测试通过** |

### 2.3 故事级两道硬闸门（宣贯重点）

```text
各 leaf 开发中 ──齐步──► 开发完成
                              │
                              ▼ 闸门 A：全部任务开发完成
                     故事级联调 / 集成测试
                              │
                              ▼ 闸门 B：集成测试通过
                         故事「已完成」
```

| 闸门 | 规则 | 人怎么干预 |
|------|------|------------|
| **A. 进集成测试** | 故事下**全部**关联实现任务都到「开发完成」齐步（均为 `integration`）后，才开故事级联调/QA | Lead/PM：看飞书故事泳道是否「开发完成」；未齐步禁止把故事标成可测 |
| **B. 故事 Done** | 关联实现任务**全部测通**（均 ≥ `ready_to_sign`）→ 故事「已完成」 | QA 按**故事验收场景**测通；**单 leaf done 不算故事 Done** |

**对照**：

| 说法 | 对不对 |
|------|--------|
| 「这个 FE leaf done 了，故事就算 Done」 | ❌ |
| 「还有 JAVA leaf 在开发，先让 QA 测故事」 | ❌（闸门 A 未过） |
| 「故事下 FE/JAVA/DATA 全到联调齐步，开 I2 + QA」 | ✅ |
| 「故事关联任务全到待签收/已签收 → 故事已完成」 | ✅ |
| 「故事已完成后，淮政玮再签各 leaf → leaf done」 | ✅（故事完成可先于/并行于 leaf 签收，以滚动规则为准） |

## 3. 任务状态机（人关心的节点）

```text
backlog → ready → claimed → in_progress
                              ↓
                    integration（联调）
                              ↓
                    pending_test → testing
                              ↓
                    ready_to_sign → done
```

| 状态 | 含义 | **谁推进**（人干预点） |
|------|------|------------------------|
| `backlog` | 已建单，未解锁 | PM 建单 / 审提案；**不**等于可开发 |
| `ready` | 可认领 | **PM/监管人 confirm**（门 I1 / 门 3 后） |
| `claimed` | 已有人负责 | 执行人认领；**必填 `supervised_by: human:{真名}`** |
| `in_progress` | 开发中 | 监管人开 Agent / 自己写代码 |
| `integration` | 联调中 | 执行侧写清证据；note 含「联调通过」等关键词 |
| `pending_test` | 待测试 | 联调闭合后进入 |
| `testing` | 测试中 | **QA（qa-agent 或 监管人:黄敬洲）** 领取 |
| `ready_to_sign` | 待签收 | 机审/QA 通过后进入 |
| `done` | 完成 | **淮政玮签收**（`chore` 豁免） |

**建单 ≠ 解锁 ≠ 认领**：建单写 registry；解锁才 `ready`；认领才有负责人。

## 5. 实现段：人怎么干预

### 5.1 三道工程门

| 门 | 时机 | 人做什么 | 通过后 |
|----|------|----------|--------|
| **门 I1 开工** | Sprint Planning | PM+相关 Lead：DoR、依赖、监管人、DoD、Sprint 写入；确认 leaf 已挂 `user_story` | leaf → `ready`，允许认领 |
| **合规演示用例** | 该模块接口可调、库内已有数据之后 | 开发负责人写覆盖表和一条主路径。参数值来自界面输入 | 调度核对需规每条有行 |
| **演示样本循环** | 覆盖核对通过后 | 不编预期。只读库，并调用用例里已经填好的请求 | 可演的行对上；`覆盖不到` 的行才补数据、改查询或改算法 |
| **门 I2 联调** | 故事「开发完成」齐步后 | Lead+体验：按用例**主路径**演示；调用链铁律；角标不造假 | 可进故事级 QA |
| **门 I3 关闭** | Sprint Review | Sprint Owner+PM：对照 DoD + handoff；核对故事是否「已完成」 | leaf 具备签收条件 |

### 5.2 日常开发（每人必会）

| 步骤 | 人怎么做 |
|------|----------|
| **认领** | 飞书/CLI 认领；Agent 执行时 `supervised_by` 填**自己真名** |
| **监管** | 开 Cursor 会话；审 diff / handoff；commit 带 `[human:姓名]` 或确认 Agent 标记 |
| **推进状态** | 走统一入口（脚本/MCP），禁止只手改 YAML 结束会话 |
| **联调确认** | 人确认后在 note 写「联调通过/完成/确认」等关键词，供自动验收 |
| **成本红线** | 实际 >$10 暂停找 Lead；>$20 hard stop + 架构评审 |

### 5.3 测试与签收（关单）

| 环节 | 谁 | 怎么干预 |
|------|-----|----------|
| **合规演示用例** | 模块开发负责人 | 模块可调后提交。需规每条一行：界面、输入或选择、触发、接口、填好的请求、期望输出。演不到写 `覆盖不到` |
| **覆盖核对** | 调度（coordinator） | 没有用例或仍有空行：不建循环，不派数据单或算法单。退回补用例 |
| **演示样本循环** | QA（`qa-agent`） | 覆盖核对通过后，只读复验已填请求。步骤见 `产品实现规程.md` §6.5 |
| **故事齐步** | Lead / PM | 确认故事泳道 =「开发完成」后再开集成测试。走查走用例主路径 |
| 领取测试 | **黄敬洲** 监管或 `qa-agent` | 按故事验收；`pending_test` → `testing`。**长任务例外**：coordinator 调动 qa-agent，不等黄敬洲（`长任务执行规约.md` §11.5.3） |
| 测通结论 | QA | 故事下全部 leaf → `ready_to_sign` → 故事自动「已完成」 |
| **leaf 最终 Done** | **淮政玮** | `ready_to_sign` → `done`（业务签收；机审只到待签收） |

机审（coordinator `task-review`）检查 handoff / DoD / cost / 架构自检 → 最多推到 **`ready_to_sign`**；**leaf Done 永远是人签收**。

## 6. 「必须人出手」清单（宣贯重点）

按时间顺序，**不可外包给 AI 的动作**：

1. **范围与业务口径**：超 ±10%、删叶子、甲方口径 🟡→🟢 → PM / 淮政玮 / 甲方  
2. **门 1 / 门 2 / 门 3 会签与拍板** → 对应 Owner 到场签字  
3. **拆单提案采纳建单 + 挂全 `user_story`** → PM（或授权架构）审后入库 `backlog`  
4. **confirm 解锁 `ready`** → PM / 监管人（门 3 + 门 I1 之后）  
5. **指定并履行 `supervised_by`** → 每个用 Agent 的 leaf 必须有真名监管人  
6. **Lead 审契约 / 可实现性 / 联调主路径** → 孔东 / 侯佳伟 / 唐绍祖 / 辜少彬等按域  
7. **合规演示用例** → 模块开发负责人写覆盖表和主路径；调度核对需规每条有行后，才开演示样本循环  
8. **故事齐步后开集成测试** → Lead/PM 看泳道；QA（黄敬洲）按用例主路径测  
9. **leaf Done 签收** → 淮政玮  
10. **对甲方沟通与对外材料终审** → PM / UE（AI 产物不得直接给客户）

## 7. Agent 可以做、但人要收口的事

| Agent 做 | 人收口 |
|----------|--------|
| 起草 USM / TRACE / wireframe / 代码 / 用例 | 会签、Lead 评审、监管人 accept |
| 门 1 后故事入库与拆单提案 | PM 采纳建单；核对 `user_story` 关联 |
| 按任务状态滚动故事「实现状态」 | 人只推进任务；**不手改**故事状态 |
| scan 建议解锁、coordinator-loop 建议派单 | **confirm / 开会话仍须人审** |
| handoff 起草、cost 回填、自动验收检查 | 业务判断 + 签收 |
| 飞书看板投影 | 状态变更须走脚本；异常人工核对 |

## 8. 反模式（宣贯直接否决）

| ❌ 禁止 | 正确做法 |
|---------|----------|
| 未过门 3 把工程标 `ready` | 门 3 + 门 I1 后再 unlock |
| 把门 1 / V2 当成联调完成 | 必须过门 I2 |
| 无 `supervised_by` 开 Agent | 先认领、填真名 |
| 飞书新建一行当正式任务 | 进提案队列，PM 审后入库 |
| confirm 当成建单 | confirm 只改状态，不新增 Task ID |
| 去掉 Mock / 待确认角标充正式数 | I2 否决 |
| 业务口径由实现方「猜完就算」 | 登客户决策表，标 🟡 |
| 机审通过就改 leaf `done` | 等淮政玮签收 |
| **手改飞书故事「实现状态」** | 只改关联任务状态，等滚动汇总 |
| **单 leaf done 宣称故事 Done** | 全部关联任务测通（≥ 待签收） |
| **故事未齐步就开 QA** | 泳道到「开发完成」再测 |
| **没有合规演示用例就开演示样本循环** | 开发负责人先写；调度核对无空行再循环 |
| **需规还有空行就派数据单或算法单** | 空行退回补用例 |
| **现有数据演不到却写一条假结果** | 该行写 `覆盖不到`，并写缺哪类数据 |
