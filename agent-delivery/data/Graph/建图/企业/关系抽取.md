# 企业 · 关系抽取

给燕大配知识图谱引擎脚本时看。企业维要抽的边，以及本侧代码实际写出的边名，都在这里。点必须已经是 `enterprise`，VID 规则见 [实体识别和抽取.md](实体识别和抽取.md)。空间写 `gkx_chain`。

两端都要有稳定 ID，且对端 `org_id` 在 `enterprise_base` 里。缺 ID、对端不在主表、VID 超 80：跳过。不要用名称生成 `ent:`。

库：`gkxlumenx_dwd`。

## 两端都是企业

这三张是关联表。读出行以后还要做方向、过滤和权重，不是把列原样插入。规则在 [脚本/enterprise_rules.py](脚本/enterprise_rules.py)。

| 边 | 本侧算子 | 源表 | 读的列 | 方向 | 权重 | props |
|---|---|---|---|---|---|---|
| `supply` | `ENT_RE_SUPPLY` | `enterprise_supply_chain` | `org_id`、`related_org_id`、`relation_type`、`relation_strength` | `org_id` → `related_org_id` | `relation_strength`，空则 `0.5` | `{"type": relation_type}` |
| `parent_sub` | `ENT_RE_BELONG` | `enterprise_parent_subsidiary` | `org_id`（子公司）、`parent_org_id`、`ownership_ratio` | 母 → 子，即 `parent_org_id` → `org_id` | `ownership_ratio / 100` | `ownership` 原值 |
| `cooperate` | `ENT_RE_COOP` | `enterprise_cooperation` | `org_id`、`partner_type`、`partner_org_id`、`partner_name`、`cooperation_type`、`project_count` | 本企业 → 对方 | `project_count`，空则 `1` | `{"coop": cooperation_type}` |

`cooperate` 只取 `partner_type=enterprise`。没有 `partner_org_id` 时跳过，`partner_name` 只留在跳过原因里，不当 VID。

必须关系里的企业合作是双向：两个方向各写一条，边名仍是 `cooperate`。本侧 `ENT_RE_COOP` 只写了有向的一条，还不能当成双向已经落地。入图包第一批因此先不灌 `cooperate`。脚本里的 `cooperate_edge` 与现码一致，只出一条。

同一条边的另一份迭代在 `entan/yiji_sim/facts.py`：`iter_supply`、`iter_parent_sub`、`iter_coop`。供给和母子与上表一致。`iter_coop` 对非企业合作方用名称当键，那一段不要配进企业维。

## 企业 → 产业链环节

必须边名是 `participates`，方向企业 → 环节。企业自己的产业表写不出这条边名。

| 路径 | 源表 | 结果 |
|---|---|---|
| 企业仓 `ENT_RE_INDUSTRY` | `enterprise_industry_chain` | 边名是 `industry_belong`，不是 `participates`。读 `org_id`、`chain_code`、`chain_name`、`node_id`、`node_name`、`chain_score`。对端 VID 会试 `segment:{node_id}`、`chain:{chain_code}`、`chn:{chain_code}:{node_id}`，并且要在图上 `FETCH` 命中才写。不要把这条当成 `participates` |
| 产业链仓 `CHAIN_RE_INDUSTRY_ENTERPRISE` | `industry_chain_entity_rel` | 能写成 `participates`。`entity_type=enterprise`，且 `relation_type` 是 `belongs_to`、`participates`、`participates_in`、`所属`、`参与` 之一。VID：`ent:{entity_id}` → 优先 `segment:{node_id}`，否则 `chain:{chain_id}`。两端都要已经在图上，这条路径不造企业点，也不造环节点 |

`participates` 的类型映射在 `enterprise_rules.py` 的 `participates_edge`。环节点归产业链维度，本目录不写环节怎么入库。

`node_id` 是不是环节 VID 里的那一段，本侧还没有对库确认。对不上就跳过，不要猜。

## 本侧写了、企业维不要建

| 本侧边名 | 源 | 为什么不要 |
|---|---|---|
| `invest` | `enterprise_invest`（`org_id` → `inv_org_id`） | 投资不进必须关系。不要改名成 `cooperate` 或 `supply` |
| `research_coop` | `enterprise_cooperation`，`partner_type` 为 `research_institution` 或 `university` | 企业—科研机构不建 |
| `talent_coop` | 同表，`partner_type=talent` | 企业—人才不建 |
| `produces` | `ENT_RE_TECH` 的查询直接返回空列表 | 企业—技术不建。技术点不是七要素里的「技术」 |
| `service_provide` | 同表，`partner_type=service_org`，方向企业 → 服务 | 必须方向是服务 → 企业，归服务机构维。企业表这一行不能当成已经写对 |
| `policy_apply_to` | 企业仓 `ENT_RE_POLICY` 直接 `not_in_wave`，不读表 | 政策适用企业归政策维。企业表没有这条边 |

`nebula_loader.py` 的边白名单里还有 `located_in`。企业菜单挂产业时写的是 `industry_belong`，不是 `located_in`。
