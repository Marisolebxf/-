# 产业链 · 关系抽取

给燕大配知识图谱引擎脚本时看。环节这一端要抽的边都在这里。点的 VID 见 [实体识别和抽取.md](实体识别和抽取.md)。空间写 `gkx_chain`。

两端都要有稳定 ID，并且对端点已经在图上。缺 ID 或图上没有对端：跳过，不造点。不要用名称生成 VID。

库：`gkxlumenx_dwd`。

## 环节 → 环节

必须边名是 `depends_on`。源表 `industry_chain_node_rel`。现码读 `source_node_id`、`target_node_id`、`relation_type`、`relation_direction`、`relation_weight`、`relation_id`、`chain_id`。

`relation_type` 只有下面这些才写成 `depends_on`：`upstream`、`downstream`、`depends`、`depends_on`、`dependency`、`上下游`、`依赖`。`parent_child` 和其他值跳过，不改名。

方向默认 `source_node_id` → `target_node_id`。`relation_direction=reverse` 时对调。两端 VID 都是 `segment:`，并且都要已经在图上。起点和终点相同则跳过。

schema 上这条边有 `dependency_type`、`weight`、`props`。`dependency_type` 存原来的 `relation_type`。`weight` 取 `relation_weight`。`props` 放 `relation_id`。

正式加工目前从父节点派生的是 `parent_child`，所以这张表现码对不上必须边。入图包第一批不触发它。规则在 [脚本/chain_rules.py](脚本/chain_rules.py) 的 `depends_on_edge`，供以后白名单行出现时用。

本侧入口：`CHAIN_RE_DEPENDS_ON`，`graph_ops.py` 的 `_depends`。

## 企业或服务机构 → 环节

必须边名是 `participates`，schema 上没有属性列。不要写入 demo 里的 `chain_role`。

源表 `industry_chain_entity_rel`。`entity_type` 是 `enterprise` 或 `service_institution`，且 `relation_type` 是 `belongs_to`、`participates`、`participates_in`、`所属`、`参与` 之一。起点企业是 `ent:{entity_id}`。服务机构本侧产业链代码用 `inst:{entity_id}`，Tag 名仍是 schema 里的 `institution`，两条前缀还没收成一条。终点是 `segment:{node_id}`。两端都要已经在图上。对不上环节时不要改挂到 `chain:`。

正式加工 §3.4 只写企业行，`relation_type=belongs_to`，`entity_id` 取企业 `org_id`。服务机构行没有。企业点由企业包写入，本路径不造企业点。

本侧入口：`CHAIN_RE_INDUSTRY_ENTERPRISE`、`CHAIN_RE_INDUSTRY_SERVICE`，都在 `graph_ops.py` 的 `_hang`。类型对照在 `chainan/graph/nebula_project.py` 的 `ENTITY_REL_EDGE`。

`participates_edge` 在同目录脚本里。入图包第一批不触发这张表。

## 本侧写了、本维不要建

| 本侧 | 为什么不要 |
|---|---|
| Tag `chain`，以及 `belongs_to`（环节 → 链） | 链不是环节 |
| `CHAIN_RE_INDUSTRY_RESEARCH` | 产业链到科研机构不建 |

| `CHAIN_RE_INDUSTRY_POLICY` | 环节到政策不建 |
| 燕大 `CHILD_OF`、`BELONGS_TO_NODE`、`DOWNSTREAM_OF` | 不改名复用 |
