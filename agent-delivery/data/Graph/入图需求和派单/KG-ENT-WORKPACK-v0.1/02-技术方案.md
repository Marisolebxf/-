# 技术方案

## 读写分开

展示系统读图的路径是：浏览器 → 网关 → Java → Python → Nebula 空间 `demo_gkx_chain`。Java 不写图语句。这条路径本包不改。

燕大加工入图写到新建空间 `gkx_chain`。两个空间在同一套 Nebula 上，数据不互相覆盖，也不要从 demo 空间拷贝。

GDF 负责表加工和调度，不直接写 Nebula。哪张表成功后触发哪次入库，见 [06-GDF触发契约.md](06-GDF触发契约.md)。现有回调还没上线，那一页里的请求和回执是目标，不要当成已经能调。缺稳定 ID 时怎么补，见 [07-gapfill清单.md](07-gapfill清单.md)。本版不建缺口表，也不灌数。

## 图上有什么

七类对象和本包 schema 里的 Tag：

| 对象 | Tag |
|---|---|
| 企业 | `enterprise` |
| 产业链环节 | `segment` |
| 科研机构 | `research` |
| 技术：论文、专利、项目 | `paper`、`patent`、`project` |
| 人才 | `person` |
| 服务机构 | `institution` |
| 政策 | `policy` |

同一个边名只建一次。例如 `cooperate` 只有一条 `CREATE EDGE`。人才之间、机构之间、企业之间如果以后都用这个名字，靠数据上的两端区分，不靠再造一个边名。

没有写明类型的 Tag 或 Edge，语句里就是空括号。不要补 `weight`、`props` 或其他列。`enterprise`、`supply`、`parent_sub`、`cite`、`depends_on`、`segment`、`institution`、`policy` 的列以 [03-schema-gkx_chain.ngql](03-schema-gkx_chain.ngql) 为准。

## 和已有空间的关系

燕大平台上已有的 `gkx_local_1`、`gkx_full_1` 继续留给原有作业。本包的新数据进入 `gkx_chain`。不要把那两个空间里的点改名迁进来，也不要在那两个空间里执行本包的 `CREATE`。

`03` 里的语句从已经定稿的初始化脚本改了空间名。定稿脚本的空间名是 `demo_gkx_chain`，那份留给智树 demo，不要拿去在 demo 空间执行本包。
