# 21 — 数据血缘

> **读者**：GDF。本章是血缘追溯接口的需求，不是已接通的接口。

实时指标的计算可以不在 GDF 上展开。这时平台自身没有这条血缘，不能假装从作业日志里能直接查到。讨论结论：把计算血缘导入 GDF 的「工位」之后，GDF 用同一个接口对外提供指标血缘。

「工位」是 GDF 上承接已导入血缘的位置。本章不规定工位的画面和字段。导入之前，接口对这条指标没有血缘可返回。

## 1. 接口覆盖三类

| # | 来源 | 血缘从哪来 | 例子 |
|---|---|---|---|
| 1 | GDF 上通过配置 Python 脚本完成的指标 | 平台自己知道。脚本、源表、目标表、`metric_id` 都在本平台的作业里 | `17` 第一批 STAT。脚本进包并配上节点之后才有这条血缘 |
| 2 | 经 API 调入的血缘 | 计算不在本平台展开，血缘由对端接口给出，再导入工位 | 实体识别、关系抽取时，图上三元组与原始数据之间的血缘。GDF 仍不写 nGQL |
| 3 | 业务操作的实时指标 | 用户在页面上触发才算，计算不在 GDF。血缘同样导入工位 | `19` 的匹配、推演、摘要、实施路径。规则未签的仍然不算、不灌数 |

三类走同一个对外接口。调用方不区分血缘是平台自己产生的，还是导入工位的。

脚本未进包、API 未把血缘交来、或实时指标的血缘尚未导入工位：接口不编造血缘。
