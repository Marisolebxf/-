## 1. 概况

1. **数据分层处理**：三方源 → ODS 贴源 → 项目 DWD → ADS（业务服务只读）→ 前端；图谱使用 NebulaGraph，检索使用 Elasticsearch。  
2. **数据量级**：供应方库表数量多，下表仅列部分**主要主体**的最终规划量，便于评估产线与调度能力，**不是全库总量、也不是完整表清单**。例如：专利约 **2 亿**、国外机构约 **3000 万**、国内机构 / 医药约 **2500 万**、国内政策约 **2000 万**（详见 §3）。其余附属表、明细表、关系表另有规模。  
3. **指标**：注册表合计 **560** 条（业务域分布、算法类型与示例见 §4）。  
4. **血缘**：指数据处理血缘（表 / 字段从源库 → ODS → DWD → ADS / 算法 → ES / 图谱可追溯）。由**中台侧落地与维护**；双方需对齐各环节如何登记、贯通与验收。  
5. **分工**：中台负责贴源、Mapping，以及存量 / 增量的调度与执行；我方负责 DWD/ADS 契约、指标口径、算法、ES/图谱写入，并提供 Mapping 明细等工作包。  
6. **性能/部署要求**：需支撑单表千万～亿级、多表并行作业、全量与日常增量并存。

### 4.3 按算法类型（为何分类）

每条指标有一个 **algorithm_type（算法类型）**，用来区分**计算形态**（统计 / 二次算 / 模型 / 图谱 / 外采等），便于看依赖与排期。  
**不等于**已经约定「该类物理作业一定由某一方编写」——口径与工程实现的分工见 §4.5。

| 类型 | 含义 | 为什么单独一类 | 条数 | 典型工程落差（均待对齐，见 §4.5） |
|---|---|---|---:|---|
| **STAT** | 统计类：计数、去重、占比、分布等 | 形态简单，但量大时必须工程化 | 150 | 口径 COUNT vs 预聚合 / 分片 / 增量汇总 |
| **COMPUTE** | 二次计算：吃上游指标或中间分再算 | 有依赖顺序，不是单表 SQL | 5 | 口径公式 vs 依赖编排、中间结果落表、重算范围 |
| **MODEL** | 模型 / 指数：多维加权、评分、合成 | 步骤多、有权重与特征 | 194 | 口径步骤 vs 特征预计算、批大小、资源与失败重跑 |
| **GRAPH** | 图谱类：依赖点边结构 | 必须先有图，不能只当关系表 SQL | 32 | 口径图指标 vs 构图加载、增量点边、图查询性能 |
| **third_party** | 三方直供值，项目侧主要消费 | 数从供应方来，不是项目内「算」出来 | 103 | 字段接入 vs 对齐、去重、时效与大表关联性能 |
| **MIXED** | 多种形态叠在一条指标里 | 不能整条派同一种作业 | 31 | 先拆分子项，子项各自仍有「口径→工程」问题 |
| **UNKNOWN** | 类型未定 | 尚未判定形态 | 45 | 先定类型，再谈实现归属 |

对产线的直观含义：各类都需要上游表就绪；差别在计算形态不同，但**「谁把口径落成可跑、可运维的作业」是共同问题**，不是只有 STAT。

### 4.4 类型示例

| 类型 | metric_id | 中文名 | 摘要 |
|---|---|---|---|
| STAT | `M_ENT_TOTAL_COUNT` | 企业总数 | 国内外企业按 `org_id` 去重 |
| STAT | `M_CHAIN_ENTERPRISE_COUNT` | 产业链关联企业数 | 链上关联企业去重 |
| COMPUTE | `M_ENT_ATTRACT_SCORE` | 招引推荐评分 | 读取上游招引指数结果 |
| COMPUTE | `M_ENT_CULTIVATE_SCORE` | 培育推荐评分 | 读取上游培育指数结果 |
| MODEL | `M_CHAIN_COMPETITIVENESS_INDEX` | 区域产业竞争力指数 | 企业能力 / 学术生态 / 配套环境三维 |
| MODEL | `M_CHAIN_ACADEMIC_POWER` | 学术生态 | 论文 / 机构 / 人才三维合成 |
| GRAPH | `M_CHAIN_EDGE_COUNT` | 产业链边数 | 图谱关系边统计 |
| GRAPH | `M_ENT_NODE_CENTRALITY` | 供应链中心性 | 网络中心性，依赖建图 |

### 4.5 指标计算：口径 vs 工程实现（各类均待对齐）

**问题对所有算法类型都成立，不只 STAT。**  
此前写「我方算法实现 / 中台只保源表」过于笼统——真正要拍板的是：我方给出的是**业务口径与验收标准**，还是连同**可上线的计算作业（含性能）**一并交付。

共性落差（各类都有）：

| 我方口径侧常见写法 | 上线时通常还要解决的工程问题 |
|---|---|
| COUNT / 去重 / 占比（STAT） | 预聚合表、分片、增量汇总、窗口与并行 |
| 「在上游分上再算」（COMPUTE） | 依赖 DAG、中间结果落表、局部重算与血缘 batch |
| 多维加权 / 指数步骤（MODEL） | 特征预计算、批大小、算力配额、失败重跑与版本 |
| 中心性 / 边统计等（GRAPH） | 构图与加载、增量点边、图查询超时与资源 |
| 「取供应方字段」（third_party） | 对齐键、去重、大表关联、刷新时效与对账 |
| MIXED | 先拆分子项，子项各自重复上表问题 |

| 已相对清晰 | 说明 |
|---|---|
| 业务口径 / 验收标准 / 类型判定 | **我方**定义；中台不擅自改口径 |
| 贴源 / Mapping / 存量·增量调度 | **中台**执行 |
| ES / 图谱的**写入权**倾向 | 目前规划由我方写入；触发与资源协作仍要约定 |

| 灰区（各类通用，待对齐） | 说明 |
|---|---|
| **谁编写可跑的计算作业** | 中台按口径在产线实现，还是我方交付作业包由中台挂调度？ |
| **性能与可运维归谁** | 超时、倾斜、分片、重跑、配额——实现方负责，还是联合约定？ |
| **结果落在哪一层、谁写** | DWD 预聚合 / ADS 结果 / 临时中间表；禁止同一指标双写 |
| **按类型是否允许不同模式** | 例如 STAT 走产线 SQL、MODEL 走我方 Python——可以，但须书面清单，勿默认混用 |

可选协作方式（可按类型组合，但每类必须有唯一实现方）：

1. **业务口径给我方，工程实现给中台**：我方交口径卡 + 目标表 DDL + 验收用例；中台编写/配置作业并负责性能与运维；我方抽样验收。  
2. **我方交付可调度实现**：我方编写批处理/脚本/作业包（含性能方案）；中台负责接入调度、资源、血缘与触发，不改计算语义。  
3. **分层分包**：例如宽表/预聚合在中台，模型与图谱算法在我方；用「类型 + 表清单」写死边界，同一指标只允许一个写入方。

无论选哪条：**口径表述 ≠ 已承诺的全表直跑方案**；性能与作业形态须由实现方写进交付物，并纳入关单验收。

## 5. 数据血缘协作（数据处理血缘）

> 本节讨论的是**产线数据处理血缘**：谁从哪张表 / 哪个字段写到哪里、经何种转换与过滤、由哪次作业 batch 产出。  
> **实现与落库在中台侧**；会议重点是各环节如何协作，保证全链可追溯、可验收。  
> （我方另有指标口径与就绪度管理，用于业务解释与验收对照，**不是**本节血缘的实现载体。）

### 5.1 目标

1. 任意项目 DWD / ADS 目标列，能追溯到供应方源表列（经 ODS、Mapping）。  
2. 任意一次成功作业，能定位源、目标、过滤、转换与行数结果。  
3. 下游指标计算、ES、图谱写入，能挂接到上游作业 batch，形成「源 → 库表 → 检索 / 图谱」闭环。  
4. 上线 / 关单以血缘材料齐备为门禁，避免「数进了库但说不清从哪来」。

### 5.2 全链路切分与协作

```text
供应方源库
  → [贴源 Wave A] ODS（同名同结构）
  → [Mapping Wave B] 项目 DWD
  → [指标计算 / 批处理] 结果表（实现方见 §4.5，按类型书面约定）
  → [ES 写入] 检索索引（我方写入；触发协作见约定）
  → [图谱写入] Nebula 点边（同上）
```

| 环节 | 血缘要登记什么 | 中台 | 我方 |
|---|---|---|---|
| **贴源** | 源库.表.列 → ODS.表.列；作业 ID、batch、行数、失败分类 | 作业配置与执行时写入 / 导出血缘 | 提供承诺表清单与验收口径 |
| **Mapping** | ODS.列 → 项目 DWD.列；转换、默认值、过滤、drop 原因 | 按 Mapping 明细执行，字段级血缘落库 | 提供字段级 Mapping 工作包与 DDL |
| **指标计算** | 输入表 → 计算作业 → 结果表 | 上游就绪通知；若承接某类作业则登记该段血缘（§4.5） | 口径与验收；按对齐结果承担实现与/或回执 |
| **ES** | 来源表 / 字段 → index / 文档字段；关联上游 batch | 表任务成功后按约定触发，不直写 ES | 写入侧登记 index、字段映射与来源 batch |
| **图谱** | 来源表 / 字段 → 点类型 / 边类型 / 属性；关联上游 batch | 同上触发，不直写图谱 | 写入侧登记点边 schema 与来源映射 |

贯通约定建议：

- **粒度**：贴源、Mapping **字段级必填**；下游至少表级 + 关键字段，并带上游 `job_id` / `batch_id`。  
- **贯通键**：中台作业 `job_id` + 运行 `batch_id`（或等价字段）贯穿全链；下游回执回写同一键。  
- **落点**：血缘主数据在中台平台（或双方约定的导出格式）；我方下游节点按同一格式回填，不另起一套无法对接的体系。  
- **门禁**：无字段级 Mapping 血缘不可关 Wave B；无下游回执不可宣称「检索 / 图谱已接入」。

### 5.3 各环节需对齐的「如何做」

**贴源**

- 源端与 ODS 是否一一镜像；改名 / 拆表如何记血缘。  
- 全量与增量是否共用同一血缘模型（仅 batch 类型不同）。  
- 缺表、空跑、抽样失败时血缘状态如何标记（失败也要可查）。

**Mapping**

- 工作包字段明细与平台作业配置如何一一对应（版本号对齐）。  
- 一对多 / 多对一、常量填充、表达式转换如何表达。  
- drop / 过滤行是否计入血缘（建议：规则入库 + 本 batch 过滤行数）。

**指标计算**

- 中台如何通知「依赖表已就绪」（事件 / API / 人工工单）。  
- 实现方（按 §4.5）如何回传：输入表版本、输出表、batch、失败分类。  
- 不同算法类型（STAT / COMPUTE / MODEL / GRAPH 等）血缘节点粒度如何统一。

**ES / 图谱**

- 触发条件：整包成功才触发，还是单表成功可触发。  
- 回执最小集：来源表、目标 index / 图空间、点边类型、上游 batch、写入行数或点数。  
- 重跑与覆盖策略下，血缘如何区分「被替换的旧 batch」。

### 5.4 职责划分（产线 + 血缘）

| 事项 | 我方 | 中台 |
|---|---|---|
| 指标口径 / 公式 / 类型 | 定义与验收标准 | 不改口径；按源表清单保障上游数据 |
| 各类指标的**工程实现**（STAT/COMPUTE/MODEL/GRAPH/…） | **待对齐**（见 §4.5）：交付口径，或交付可调度作业包 | **待对齐**：按口径落地作业，或只挂调度 / 保上游 |
| 项目 DWD / ADS 结构 | 提供 DDL 与 Mapping 明细 | 按明细建表、洗数 |
| Wave A 贴源 | 提供承诺表清单 | 镜像至 `gkxlumenx_ods`，登记贴源血缘 |
| Wave B Mapping | 提供字段级 Mapping | 按明细执行，登记字段级血缘 |
| 存量 / 增量调度与执行 | 提供差集、水位规则与验收口径 | 在中台侧调度并执行 |
| **数据处理血缘（实现）** | 提供契约、Mapping 明细；补全算法 / ES / 图谱段回执 | **主责落地**：作业元数据、表/字段血缘、导出或平台查询 |
| ES / 图谱写入 | 负责写入与下游血缘回执 | 上游成功后按约定触发，不直写 |

### 5.5 存量 / 增量（调度在中台）

存量与增量均由**中台侧调度并执行**。我方提供 DDL、Mapping 明细与验收口径，不在我方侧另起一套同步调度。

**存量**

- 我方：现网 DDL 差集、Mapping 明细  
- 中台：建改、全量/纠偏作业、抽样校验，并写入字段级血缘  
- 关单：行数偏差规则确认、无假值填缺口、血缘可追溯至承诺表  

**增量**

- 中台：在既有贴源与 Mapping 作业上配置增量键、水位、软删等规则并调度执行  
- 每次增量 batch 同样写入血缘；成功后按约定通知下游（ADS / ES / 图谱）  

**共同开发**

- 以确认的工作包版本为准  
- 中台范围：ETL、调度（含存量、增量）、**血缘落地**  
- 新表 / 新作业上线须具备完整血缘材料（见下）  

### 5.6 血缘材料最小集（建议）

每次作业 / 每次关单至少具备：

| 项 | 说明 |
|---|---|
| 源 → 目标 | 库.表[.列] → 库.表[.列] |
| 转换与规则 | 表达式、默认值、过滤、drop 条件 |
| 键与水位 | 主键 / 唯一键 / 增量水位字段 |
| 运行证据 | job_id、batch_id、起止时间、成功/失败行数、失败分类 |
| 下游挂接 | 若触发算法 / ES / 图谱：下游回执 ID 或等价引用 |
| 责任人 | 作业 owner、告警接收人、重跑说明 |

格式需对齐：平台内置页面导出、或双方约定的结构化文件（如 CSV / JSON），以便联调与审计。
