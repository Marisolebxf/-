# 算法指标对项目 DWD 预聚合统计值覆盖对照（2026-08-22）

> 问题：算法这次提供的 60 个唯一 `metric_id`（王惠 2026-08-17 / `calc-logic/ENT`）有没有覆盖到项目自己设计的 DWD 指标统计值。  
> 左轴：项目 DWD 预聚合表里的**统计值**（不是工商明细，也不是 ADS 算法结果表）。  
> 右轴：王惠 60 ID。seed / readiness 多出来的 ID 只作备注，不充作“这次算法已提供”。  
> 本文件独立于 `ENT-三方数据底层支撑结论-20260822.md`，不改三类数据支撑判定。

## 0. 一页结论

王惠 60 个指标和 DWD 预聚合不是同一套：前者是分析/评分模型，后者是页面 KPI 和交叉统计。  
**没有算法 ID ≠ 真缺失。** 下面原先标成“未覆盖”的 9 项都是 COUNT / SUM / 累计 / 分组，数据 ETL 自己能算，**不要反馈成算法缺指标。**

| 算法 ID | 数量 | 是否真缺失 | 含义 |
|---|---:|---|---|
| 已覆盖 | 14 | 否 | 有同名或同语义 ID；落地仍是 ETL 预聚合 |
| 部分覆盖 | 12 | 否 | 有相关 ID，粒度不同；ETL 按 DWD 粒度自算即可 |
| 无独立 ID | 9 | **否** | 算法没给 ID，统计值仍可由 DWD 明细自算 |

另外：

- 真要算法的是 ADS 评分/排名/招引/中心性，本来就不在这 9 项里。
- `enterprise_score` 等 ADS 表不在本对照范围。
- 现在能不能灌出数，看支撑结论 A/B/C（同 cohort、关联键），不看有没有 `metric_id`。

**自己设计的 10 张 DWD 预聚合表，每一张都能被「数据侧自算 + 算法出分后再聚合」覆盖，没有缺生产者的表。**

| `enterprise_industry_summary` | 全自算 | 齐（人员/专利关联不够会空） |

## 2. 覆盖判定

两列分开看，禁止把“无 ID”写成“缺能力”：

| 列 | 取值 | 标准 |
|---|---|---|
| 算法 ID | 已覆盖 / 部分覆盖 / 无独立 ID | 王惠 60 里有没有对应或近义指标 |
| 能否自算 | **数据侧可自算** / 需算法模型 | COUNT、SUM、累计、分组、回填字段 → 可自算；评分、排名、指数、图中心性 → 需算法 |

数据侧可自算 = 不是真缺失。最多要冻枚举（在营、高价值、明星名单），不需要算法补 `metric_id`。

## 4. 无独立算法 ID 的 9 项（全部不是真缺失）

禁止把下表反馈成“算法缺指标”。全部是统计或回填，数据侧自己做。

| # | 统计值 | 所在表 | 自算方式 | 真缺失？ |
|---:|---|---|---|---|
| 1 | 在营企业数 | `enterprise_region_summary.active_enterprise_count` | `reg_status` 过滤后 COUNT | 否 |
| 2 | 区域营收合计 | `enterprise_region_summary.total_revenue` | 最新年报营收按区域 SUM | 否 |
| 3 | 区域月度新增 | `enterprise_growth_trend` | 成立年月 + 区域 COUNT | 否 |
| 4 | 明星企业数（节点/区） | `enterprise_stat_summary` | 明星名单 JOIN 后 COUNT | 否 |
| 5 | 高价值专利数 | `enterprise_stat_summary.high_value_patent_count` | 冻枚举后按专利字段 COUNT | 否 |
| 6 | 深圳年末累计企业数 | `shenzhen_enterprise_summary.yearly_growth` | 成立日期 ≤ 年末 COUNT | 否 |
| 7 | 城市平均商业力 | `sz_city_benchmark.avg_business_power` | 商业力分已有则 AVG；无分则此列空，缺的是模型分不是统计口径 | 否 |
| 8 | 深圳链中角色 | `sz_city_benchmark.chain_position` | 链节点/上下游字段回填 | 否 |
| 9 | 风险类型计数 | `enterprise_risk_summary` | 风险明细按 `org_id × risk_type` COUNT | 否 |

其中 7 的输入（商业力分）来自算法 ADS；**均值本身仍是统计**。没有商业力分时留空，不要另立“缺城市平均商业力指标”。

## 5. 已覆盖但仍要注意粒度

即使有 ID，写入 DWD 时仍要约定生产者：

| 情况 | 处理 |
|---|---|
| 同一 ID 多粒度（全国 / 区域 / 链 / 深圳） | DWD 用预聚合表承接，指标库不复制 ID |
| 算法结果进 ADS（技术力、竞争力、招引） | 不要反写进 DWD 预聚合表 |
| `M_ENT_SZ_COUNT` 算法带产业链，DWD 深圳总数可不带 | 两个口径，禁止混灌 |
| `yearly_growth` vs `M_ENT_NEW_COUNT_Y` | 累计 ≠ 新增 |

## 6. 反向：算法给了指标，我们的表有没有接住

现网核对：`gkxlumenx_dwd` 预聚合 + `enterprise_finance_history`；`gkxlumenx_ads` 的 `enterprise_score` / `ranking` / `diagnosis` / `centrality` / `type_dist` / `domain_dist` / `city_index` / `realdata_enterprise_risk`。  
正式 ADS **没有**企业招引/培育表；`svc_attraction_recommend` 只在 demo，且是服务机构域。

判定：

| 落点 | 含义 |
|---|---|
| DWD 预聚合已接 | 统计值有对应汇总列或 `stat_type` |
| DWD 明细已接 | 单企事实在财务/专利/标签表 |
| ADS 已接 / 近义接 | 有正名列，或只有 innov/operate/total 这类旧列名 |
| 不落表 | 检索运行时，不算缺表 |
| **表未承接** | 算法有 ID，DWD/ADS 都没有可写入的表或列 |

### 6.1 表未承接（要看的名单）

这些是视角反过来后，**算法提供了、项目表没有接住**的项。不是“统计值缺算法”，是“模型结果没地方写”。

| metric_id | 为什么没接住 | 建议落点 |
|---|---|---|
| `M_ENT_MARKET_SHARE` | 王惠口径=单企营收/同行业营收合计，原料在财务明细；DWD/ADS 无结果列。这和旧稿「市调采购份额」不是同一个数 | 财务或 ADS 加派生列即可，不要按采购份额建空列 |
| `M_ENT_ATTRACTION_INDEX` | 正式 ADS 无企业招引表；demo 的 `svc_attraction_recommend` 不是企业域 | 新建 `ads.enterprise_attraction` 或扩 score |
| `M_ENT_CULTIVATION_INDEX` | 同上，无企业培育结果表 | 新建 `ads.enterprise_cultivation` |
| `M_ENT_INDUSTRY_MATCH_SCORE` | 无产业匹配分表/列 | 招引结果表加列，或独立 match 表 |
| `M_ENT_PAINPOINT_COUNT` | 无痛点计数表/列 | 诊断表加结构化计数，不要只放文本 |
| `M_ENT_PAINPOINT_SEVERITY` | 无严重度列 | 同上 |
| `M_ENT_SUPPLIER_COUNT` | `enterprise_supply_chain` 是关系明细，没有供应商节点数结果列 | 有供应关系后 ETL 计数即可，不必新算法表 |
| `M_ENT_CLUSTER_INDEX` | 无集聚指数列；`city_index.sub_scores` 是 JSON 兜底，不算正名承接 | `sz_city_benchmark` 或 `city_index` 加列 |
| `M_ENT_DIVERSIFICATION_INDEX` | 无多元化指数列 | ADS 企业结果或领域表加列 |
| `M_ENT_FUTURE_INDUSTRY_COVERAGE_COUNT` | 无未来产业覆盖数 | DWD `stat_summary` 新 `stat_type` 即可 |
| `M_ENT_CHAIN_STAGE_COVERAGE` | 只有完整度，没有环节覆盖独立列 | 与 `chain_completeness` 合并或加一列 |
| `M_ENT_SHORTBOARD_COUNT` | `enterprise_diagnosis` 只有优劣势文本，没有短板条数 | diagnosis 加 `shortboard_count` |

`M_ENT_SEARCH_RESULT_COUNT` 是检索运行时，**不落表，不算未承接**。

### 6.2 ADS 只有近义列，不是正名承接

现网 `enterprise_score` 只有 `score_innov` / `score_operate` / `score_growth` / `score_total`；`enterprise_ranking.rank_dim` 为 `innov/operate/growth/overall`。

| 王惠 ID | 现网近义 | 结论 |
|---|---|---|
| `M_ENT_TECH_POWER_SCORE` / `M_ENT_TECH_SCORE` / `M_ENT_TECH_RANK` | `score_innov` / `rank_dim=innov` | 未正名。不能默认 innov=技术力 |
| `M_ENT_BUSINESS_POWER_SCORE` / `M_ENT_BUSINESS_SCORE` | `score_operate` | 未正名 |
| `M_ENT_COMPETITIVENESS_SCORE` / `M_ENT_COMPETITIVENESS_RANK` | `score_total` / `overall` | 近义，要书面确认 |
| `M_ENT_INNOVATION_INDEX` | `score_innov` | 可能撞列，要和技术创新力拆开 |
| `M_ENT_GROWTH_POTENTIAL` | `score_growth` | 近义，要确认是否同一口径 |
| `M_ENT_CITY_RANK` / `M_ENT_CITY_AVG_TECH_POWER` | `city_index` + `sz_city_benchmark` | 有表；排名维度（规模/密度/完整度）未拆成正名列 |

这类是**契约未对齐**，不是完全没表。冻结列名或加列，不要再各写一套。

| ADS 图/风险 | `NODE_CENTRALITY` | `enterprise_centrality` |
| ADS 风险近义 | `SUPPLY_CHAIN_RISK` | `realdata_enterprise_risk`（事件/评分，不是断链等级正名） |
| ADS 领域分布 | `DOMAIN_COVERAGE_COUNT` `BREADTH` `DEPTH` | `enterprise_domain_dist` 的 count/ratio/`avg_participation_depth`，粒度是领域不是单企 |

### 6.4 为什么「都来自功能/原型」还会对不上

不是「DWD 工商表一开始没对上功能」。三份真源切的是同一产品的三层，时间也不一样。

| 真源 | 时间 | 切的面 | 落点约定 |
|---|---|---|---|
| 功能设计（重点企业 / 深圳现状） | 2026-07-29 | 检索、地图、KPI 卡、领域证据 | 统计走 DWD/ES；领域证据写明**不新建表**；对标要 ADS 日更 |
| 分析任务方案 + 结果契约 | 2026-07-24～07-30 | 评估 / 风险痛点 / 招引培育 | **C-14：结果进 MinIO**，Java 只存指针，不进 DWD/ADS 宽表 |
| DWD 指标汇总 v3.1 | 2026-08-11～12 | 稳定 COUNT/SUM 预聚合 | 明确把 `enterprise_score` 踢出 DWD |
| 王惠 60 | 2026-08-16～18 | 原型上所有数字（含分析页） | 一张指标清单，没按「统计卡 / 任务 JSON」拆开 |

所以：DWD 对的是功能设计里的**统计/检索面**；王惠 60 还扫进了功能设计里规定**不落仓**的分析任务结果。对不上是分层，不是漏做工商表。

真债只有三处：功能中文名和 ADS 旧列（innov/operate）没冻；对标表从设计稿 `ent_sz_status` 漂到现网 `sz_city_benchmark`/`city_index`；市场份额旧稿当采购数、王惠当行业营收占比。

### 6.5 反向一句话

- DWD 预聚合本来就不是给招引/痛点/份额用的，这些**未承接不反向否定 §0.1 表级覆盖**。
- §6.1 那 12 个里，招引/培育/痛点/匹配按 7 月底方案应在任务 JSON，不在 DWD；只有要做日更总览时才补 ADS。
- 技术力/商业力/竞争力先做列名冻结，避免和 `score_innov/operate/total` 各算一套。

## 7. 建议

1. 深圳专题和区域 KPI 由数据 ETL 按 DWD 粒度生产，不等王惠 60 补 ID。
2. §4 的 9 项标成**数据侧统计，非真缺失**，不要派算法补指标。
3. `yearly_growth` 按累计企业数写，不要用 `M_ENT_NEW_COUNT_Y` 灌。
4. 高价值 / 在营 / 明星名单只冻枚举或配置，不进分析模型指标库。
