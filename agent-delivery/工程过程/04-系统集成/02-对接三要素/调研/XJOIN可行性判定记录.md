## 场景 1 · 学科/技术领域 ↔ 产业链产业 —— **绿**

证据（11-04 实查）：

- 双桥已核：我方 `subfield_topic_map`（390 行，LLM 关联到产业节点）+ 久新 113 条集群×子学科（`approved`，ID 同源 67/67）。
- 久新产业分类真源是 `ads_industry`：**taxonomy = `CN_GB4754_IPC`，1,971 行，编码是国标 GB/T 4754 行业码（`01`–`T`），`industry_code` 无一条 `INB%`**（实测 0 行）。
- **关键澄清**：久新库内没有我方 INB 码体系；INB 只出现在我方映射表（`industry_cluster_map` / `subfield_topic_map`）和久新的集群表产业名里（按名称挂，非码）。
- `relation_type` 语义：CORE=1.0 / SUPPORTING=0.65 / APPLICATION=0.45，`mapping_weight` 与类型一一对应（实测 min=max），是分层权重不是连续分。

**判定**：绿。条件：① 我方桥的产业侧保持 INB/CL（我方目录为锚），久新侧只用 `subfield_id`；② 不要求久新库内直接按 INB 过滤（同域化后在我方库内完成）；③ CORE/SUPPORTING 语义按「主/辅/应用」用于筛选分层，需在口径记录里写明。

**遗留**：113 条只覆盖 15 集群 67 子学科；我方 252 个子学科中约 185 个无集群映射。政策页等按子学科反查产业走 `subfield_topic_map` 不受影响；集群维度的分析只能覆盖 67 个子学科。

## 场景 2 ★ 产业链节点 ↔ 久新技术节点 —— **红 → 黄**（阶梯 2：我方建桥，WBS-02-12 承接）

证据：

- 无桥：久新全库无「技术节点↔产业」映射表（`SHOW TABLES LIKE '%industry%'` 7 张全是机构/人才侧或集群映射）。
- 候选提炼不可行：`ads_technology_application_case`（181,735 行）实测列结构是「技术节点↔科研项目」，`case_type` 固定 `RESEARCH_PROJECT`、`application_stage` 仅科研项目代理——**没有产业/应用领域维度**，提不出节点→产业对照。
- `ads_technology_commercial_value_simulation`（8 行）有 `tech_id` + 中文技术名，是「正式技术目录」的雏形（`catalog_7ac3df76…`），但只有 8 行，是 demo 规模，且为合成模拟值。
- 有利条件：`ads_technology_profile` 19,430 节点 **`technology_name_zh` 100% 已填**（重扫发现已修，10-22 时为空）——名称向量匹配的前置条件已具备。

**判定**：红→黄。我方按 WBS-02-12 用名称向量建本侧桥（`dwd_tech_node_industry_map`），候选产业节点来自我方目录。**升级条件**：久新若在正式目录（tech_id）落地时补官方「节点↔产业」映射，我方桥可退役为校验参照。久新回复该计划时间表是合规验收材料之一。

## 场景 3 ★ 人才/机构 ↔ 区域 —— **黄**（阶梯 2：桥雏形已在，补覆盖）

证据：

- 桥的雏形**存在且质量高**：`ads_location_external_id` 22,229 行，`id_namespace` 五类：GEONAMES 19,729、ROR_SUBDIVISION 2,252、ISO_3166_1_ALPHA2 232、**AMAP_ADCODE 9**、CONTINENT_CODE 7。`mapping_status`：confirmed 22,131 / **conflict 98**。
- 深圳稳定 ID 实查确认：`loc_E16782C21F18EBF8A59C1E98F9C9860B` 在 `ads_location`（`location_release_id` = `location_v1_5_20261103`，11-03 刚发过新版）。
- **缺口**：AMAP_ADCODE（高德行政区划码，与我方国标区划最接近的命名空间）**只有 9 行**（大湾区市级），覆盖不了全国区划；区划桥要靠「GEONAMES/ISO 码 → 我方区划」的间接映射或按 `name_zh` 对照。
- 98 行 `conflict` 未给处置规则。

**判定**：黄。向久新提两点（并入 51 行回复）：① 98 行 conflict 的裁决规则与责任方；② 是否会扩充 AMAP_ADCODE（或国标区划码）命名空间到全国覆盖；若不扩，我方按 name_zh+层级自建区划桥（阶梯 2，工作量可控，因为 `ads_location` 仅 2.2 万行且带层级链）。

## 场景 4 ★ 科研机构 ↔ 企业/招投标/财务 —— **红**（阶梯 4 优先：请久新出对照表）

证据：

- **无信用码**：`ads_institution_profile` 65 列中身份类只有 `homepage_url` / `image_url`，无统一社会信用代码、无注册号（实查列名+注释）。
- `institution_id` 无生成规则文档；机构类型 10 类（OpenAlex 类型体系：education 16,991 / unknown 15,516 / **company 15,392** / healthcare 11,228 / facility 9,317 / nonprofit 6,210 / government 4,312 / other 3,404 / archive 1,071 / funder 304）。
- 口径侧可确认：企业=类型 `company`，与我方产品口径一致；`unknown` 占 18.5% 是过滤精度风险。
- `ads_institution_news` 仅 63 行；招投标、司法、财务数据久新库没有（重扫确认，与总集对照结论一致）。

**判定**：红。这是六场景里最深的缺口：两侧机构 ID 体系完全不同，久新无信用码，我方总集机构表无 `institution_id`。**唯一可靠的桥是名称+地址模糊对照**，属高误报风险加工。阶梯定级：**优先阶梯 4**——正式函件已请久新评估出「机构↔信用码」官方对照宽表（他们上游 ROR/OpenAlex 有 homepage/名称，可对其国内企业库）；久新不能出则落阶梯 3（我方按名称+城市模糊对照 + gapfill 标注，误报率如实披露）。**该场景的综合分析指标在桥落地前全部按无此维度处理。**

## 场景 5 ★ 三要素 ↔ 政策 —— **红**（阶梯 5：空态等灌数，无替代阶梯）

证据：

- `ads_technology_policy_evidence` 结构已建好（technology_node_id + location_id + policy_id + 关联方法 + 审核状态），**仍 0 行**——说明久新的政策管线在搭、没数据。
- `ads_research_problem_policy_evidence` 1,252 行：`relation_type` null 1,213 / FIELD_SUPPORT 38 / DIRECT_SUPPORT 1；`statistics_year` null 1,213，有年份的仅 39 行——**字段值层面也没灌完**。
- 我方政策库（`dwd_policy_base` / 政策分析链路）是自有体系，与久新政策 ID 无对照，且久新政策证据的 `policy_id` 生成规则未知。

**判定**：红，且**这是唯一没有我方可替代阶梯的场景**——政策关联的源头数据只在久新。处置：① 技术侧政策证据按空态演示/上线，登记缺项；② 研究问题侧 39 行有年份的数据可试用，但 relation_type null 占比 97% 使其不可作为统计口径；③ 向久新要灌数时间表（附页 B 已列），没有时间表就按「阶段一不交付此场景」写进合规验收结论。

## 场景 6 · 多源指标合成 —— **黄**（阶梯 1 同域化 + 授权确认）
