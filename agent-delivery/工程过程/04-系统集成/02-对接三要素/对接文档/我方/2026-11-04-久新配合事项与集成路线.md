### 3.2 核心判定：跨库关联分析

**判定问题**：展示系统与专题系统的综合智能分析，能否**仅依靠久新提供的数据库和指标**完成合规开发需求？

综合分析的本质是把三要素与我方域的数据（产业链、企业、政策、区域）做**跨库关联**。请求链上禁止跨库实时 JOIN（架构红线），关联只能靠「同域化」或「已确认的字典桥」。逐场景判定如下（请久新对「无桥」行给出现成关联或确认由我方建桥）：

| 综合分析场景 | 需要的关联 | 现状判定 |
|---|---|---|
| 学科/技术领域 ↔ 产业链产业 | 久新 `subfield_id` ↔ 我方 INB/CL | **已有桥**：我方 `subfield_topic_map`（LLM 关联）+ 久新 113 条集群×子学科映射，双源已核 |
| 技术链全景 × 主流技术路线 | 我方产业链节点 ↔ 久新技术节点 `technology_node_id` | **无桥**。我方按 WBS-02-12 向量匹配建本侧映射（临时）；久新无此关联 |
| 人才/机构 × 区域 | 久新 `location_id` 体系 ↔ 我方行政区划 | **无桥**，需映射表（久新 `ads_location` 约 2.2 万行） |
| 科研机构 ↔ 企业/招投标/财务 | 久新 `institution_id` ↔ 我方 `org_id`/统一信用码 | **无桥**，两套 ID；总集机构表与久新机构主表同名字段 0 个 |
| 三要素 ↔ 政策 | 久新政策证据表 ↔ 我方政策库 | 久新侧 0 行未接；我方政策库自有 |
| 多源指标合成 | 久新结果表 + 我方企业/链指标 | 需同域后在同一库合成；请求线程禁跨库 |

**合规判定标准（每场景三条全绿才算「能依靠久新完成」）**：① 数据在——所需表在久新库有行；② 关联有桥——存在已确认的映射或已完成同域化；③ 口径已确认——§3.1 口径项书面落定。

## 4. 阶段二 · 上线阶段（同步进总集 TDSQL）

### 4.1 目标链路

```text
久新 Doris（15T，按需圈表）
   │ ① 同步通道 —— 久新出方案（推/拉、工具、频率、窗口、水位、重试）
   ▼
总集 TDSQL · ODS 贴源层
   │ ② GDF 数据工厂（我方）：ODS→DWD→ADS 加工、质检
   ▼
我方 ADS（展示/专题唯一读源）
   │ ③ Java 只读 / Python /internal 只读
   ▼
展示系统 / 专题系统页面
```

### 4.2 需久新出的方案内容

1. **同步通道方案**：推送到 TDSQL 或授权我方拉取；工具选型、同步频率（日增/周全）、批次窗口、失败重试与告警。
2. **圈表清单确认**：阶段一子集为基础，上线路线逐张增补/裁剪；每表给行数、字节量、水位字段语义；15T 约束下不整库同步。
3. **TDSQL 目标侧**：目标库/账号/权限，建表 DDL（TDSQL MySQL 方言），字符集/时区/类型映射规则。
4. **增量与质量约定**：全量/增量判定规则；行数对账与关键字段非空率等质量标准；水位断点续传。
5. **变更纪律（长期）**：schema 变更提前 ≥5 个工作日书面通知、维护 changelog、删列/改名/改类型给迁移窗口；过程表命名与生命周期说明。

### 4.3 我方配套（对应责任）

GDF 加工规则与质检入库（ODS→DWD→ADS）、ADS 建模、指标 8 件套维护、Java/Python 读链与页面。方案排期请久新在 **2026-11-14** 前给出（方案正文可演示后交）。

### 4.4 责任定界

- **久新**：数据从久新库完整、正确落到 TDSQL ODS 贴源层为止；贴源层以内的数据错误由久新修。
- **我方**：ODS 之后的加工（DWD/ADS）、指标、页面；加工引入的错误由我方修。
- 对账基准：以久新库为源、TDSQL ODS 为贴源镜像，逐表行数对账。
