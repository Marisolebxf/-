## 4. 上线集成路线（需久新出方案，我方拍板）

**前提**：15T 整库拉取不可行，集成范围 = 按指标需要圈定的表集合（演示子集为基础，上线路线阶段逐张增补/裁剪，每张给出行数与字节量）。

三条候选路线。**请久新按自身条件出推荐方案与工作量评估**，我方据其回复拍板；本文档不预设结论。

| 路线 | 内容 | 久新需提供的 | 我方需做的 | 特性 |
|---|---|---|---|---|
| **A · 库直连（圈表 ETL）** | 我方 ETL 定时拉取圈定表进我方 ADS | 正式库坐标与只读账号、IP 白名单、逐表**字节量**、每表**水位字段**（`update_time` / `data_version`）、连接数与并发限制、可用性与备份承诺 | `lumen-algo-py` 离线作业（增量拉取 + 质检 + 落 ADS） | 我方已有雏形；适合批量主数据与结果表 |
| **B · API 服务** | 久新把查询做成服务接口，我方经网关对接 | 42 行 API 需求的契约（路径/参数/返回/分页/鉴权/限流）、测试环境 | Java Feign 对接 + 缓存 | 适合高实时、小数据量的查询类需求 |
| **C · 数据推送** | 久新按批次把圈定数据投递到我方 ODS | 投递通道、批次格式、到达通知 | 接数 + 质检 + 入 ADS | 久新改动最小；时效受批次节奏限制 |

无论哪条路线，以下四项是**路线无关的硬性前提**，缺一不进上线轨：

1. **schema 发布纪律**：变更提前 ≥5 个工作日书面通知；维护 changelog；删列/改名/改类型必须提前告知并给迁移窗口（`tech_id` 无通知删除此类事件不得再发生）；过程表（如 `*_20261031`）命名与生命周期说明。
2. **增量机制**：每张纳入集成的表明确水位字段与语义，否则我方只能全量重拉，成本双方共担。
3. **可执行计算交付**：schema 文档里的算法描述需配套可执行 SQL 或 Python 源码（正式 `tech_id` 目录映射完成时间一并给出）。
4. **51 行接口需求逐行回复**：逐行给「确认 / 拒绝 / 改期」及理由，不允许继续整体悬置。

另有三项上线前需书面确认的业务口径：

- 企业=机构类型 `company` 过滤，企业不计入科研机构口径（我方产品口径，请久新确认数据侧一致）。
