## 2. 根因

### 根因 1 · 产业码体系混用（「没数据」的主因）

线上产业目录（Q068 `industry-clusters`）的 `industry_id` 与数据侧三张表（`enterprise_industry_summary`、`enterprise_stat_summary` 的 `one_map_*` 行、ES `industry_chain_code`）均用 `INB13xx/12xx/25xx` 码系；对接文档 v1.2 §1.5 枚举表也是这套码。**`INB17xx/INB18xx`（lumen-topic-py `meta.py` 的 `_CHAIN_FALLBACK` 旧统一码表）在数据侧无挂接**——前端若拿这套码切换，API-1/2 直接空。政策关联表恰有 INB1701 的 8 条 demo 期数据，造成「偶尔又有几条」的混乱观感。

**处置（P0，零代码）**：已在本汇总 §4 写明，需 PM/淮政玮向智谱重申：industry_code 必须取自 `industry-clusters` 目录。若智谱确需 INB17xx 产业，另立灌数/映射任务（本单未含）。

### 根因 2 · 下游端点无产业过滤（「所有产业数据一样」的主因）

被 one-map 门面复用的两个 Python 既有端点属「企业发展概况」模块，设计即**全市口径**，body 无产业字段：

- `type-scale-stats`（`enterprise_key_enterprise.py` L503）：只收 `region_level` → API-2 的 scale_dist / medium_large_ratio 恒定；
- `district-heat`（`enterprise_overview.py` L127）：只收 `region_id` → API-4 的 enterprise_count、API-6 的 enterprise 主题恒定。

Java 门面（`OneMapFacadeService`）对这两个端点**想传也没参数可传**：L129 只发 `Map.of("region_level", "city")`；districtStats/thematicMap 只发 `Map.of("region_id", "440300")`。对照：政策侧 `policy_indicators` 有 `industry_code` 入参，所以政策块全部透传且随产业变——同一文件两种行为，证明这是下游能力差异而非 Java 丢参。

背景：接口需求文档草案 v0.2（2026-11-06）的总原则是「复用既有端点、无需新算法」，§3 对这两项标了 🟡「口径待核：是否限定产业维度」但按「缺口不阻塞契约冻结」放行。现在智谱联调暴露了该口径不满足「切换产业」场景。

**处置（P2 接口改造）**：→ 任务单 `SYSINT-04-01-API-INDFILTER-L01`（Python 两端点加可选产业过滤 + Java 三处透传）。

### 根因 3 · 政策 `policy_base_info.district` 大面积为空（「区级政策无值」）

政策按产业现算后，深圳政策几乎全归「市本级」（INB1309：深圳 26 条全部 district 为空 → 兜底「市本级」），「市本级」不在九区色斑内 → API-4 policy_count=null、API-3 by_district 无九区行、API-6 policy 主题只出 1 行。

**处置（P1 灌数）**：→ 任务单 `SYSINT-04-01-DATA-POLDIST-L01`（district 补数/拆区，走 D16 gapfill 合规路线）。

### 附带发现（对接方同样可能踩）

1. **中文 body 编码假象**：排查第一轮用 PowerShell `Invoke-WebRequest` 直发中文 body（"南山区"）被按本地编码写坏，服务端收到的 district 是乱码 → 静默查空、HTTP 仍 200。**必须 `Content-Type: application/json; charset=utf-8` 且 body 为 UTF-8 字节**（curl 文件体 / Postman 默认满足）。建议向智谱同步。
2. **下游偶发慢**：INB1209 首测 15s 超时、30s 复测正常。建议对接方对一张图接口设 ≥20s 超时并做一次重试。
3. 本机直连内网网关 `10.50.69.111:30895` 不通（未接 VPN），公网链路正常。

## 6. 代码级复核附录（2026-11-12 16:30 · 徐滕强会话）

> 对两单 DoD 的可行性做了 DB 实测复核。**结论：排查三根因成立；但 API-INDFILTER 单 DoD 第 1/2 条的
> 「EXISTS enterprise_industry_chain 过滤」方案对 `type-scale-stats` / `district-heat` 不可行**，需按 §6.2 修正。

### 6.1 实测证据（demo_gkxlumenx_dwd，2026-11-12）

| 检查项 | 实测 | 含义 |
|---|---|---|
| `enterprise_industry_distribution` | **0 行** | region×chain 聚合表是空壳；「按码查区县分布」无现成表 |
| `enterprise_type_scale_stats` 列 | `company_type/enterprise_scale/region_level/region_id/stat_date`，**无 chain_code 列** | 全市聚合表，行上没有产业维度 |
| `enterprise_region_summary` 列 | `region_id/region_name/region_type/parent_region_id/enterprise_total...`，**无 chain_code 列** | 同上 |
| `enterprise_stat_summary.one_map_*` | 12 码 × 维度行齐（`one_map_industry_scale` 72 行=`12 码×6 年`；`employee_dist` 48=`12×4 档`；`district_dev_index` 9 区；`employee_total` 12） | **按码的规模/员工数据已经预聚合在库**，scale_dist 随产业变可直接换数据源 |
| `enterprise_industry_chain` | 现行码+旧码并存（INB1309=186,964 家、INB170102=同一家机构的重复挂链） | EXISTS 过滤底表本身可行，但两聚合表行上无码可挂 |

### 6.2 对 API-INDFILTER-L01 的修正建议（执行前按此更新 DoD）

| 端点 | DoD 原方案 | 问题 | 可行方案 |
|---|---|---|---|
| `type-scale-stats`（scale_dist/medium_large_ratio） | 加 `industry_chain_code` 参数 + EXISTS 过滤 | 表 `enterprise_type_scale_stats` **无 chain_code 列**，EXISTS 无从挂起；底表 `enterprise_base` 也无 `company_type/enterprise_scale` 列（实测确认），现场 GROUP BY 造不出四桶 | **换数据源**：scale_dist/medium_large_ratio 改读 `enterprise_stat_summary.one_map_industry_scale` + `one_map_employee_dist`（12 码已按码预聚合，Java 侧 `employeeDist` 已在用同表同模式）；或 ETL 给 `enterprise_type_scale_stats` 补 chain_code 维度重灌 |
| `district-heat`（enterprise_count/主题图） | 加 `industry_chain_code` 参数 + EXISTS 过滤 | 表 `enterprise_region_summary` 同样无 chain_code 列 | 两选一：① SQL 改现算——`enterprise_base`（有 `region_id/district` 列）INNER JOIN `enterprise_industry_chain`（挂链底表实测有数）GROUP BY 区县，量级 18.7 万行可接受；② ETL 补维度重灌 `enterprise_region_summary`（长期正解，短期赶工期用①） |

### 6.3 建议拆单

原 API-INDFILTER-L01（S/M）按修正方案体量升级，建议拆：
- **API-FILTER-PY**：两端点加可选参数 + §6.2 方案落库查询（type-scale-stats 换数据源；district-heat 现算 JOIN）
- **API-FILTER-JAVA**：`OneMapFacadeService` 三处透传（原 DoD 第 3 条不变）
- 或维持单干但 handoff 分两段交付

### 6.4 附带发现（复核新增）

1. `enterprise_industry_chain` 存在**新旧码并存重复挂链**（INB1309 与 INB170102 覆盖完全相同的 186,964 家）——Java 侧已有 `_resolve_chain_codes` 收敛逻辑（17xx→现行码），Python 侧新过滤若直接用原始码会双算；须复用同一收敛逻辑。
2. `one_map_employee_dist`/`one_map_industry_scale` 的 `dim_name` 是「【调试构造】机器人」等**调试前缀名**——换数据源时输出要用 `industry-clusters` 目录名，不要透传表内 dim_name。
