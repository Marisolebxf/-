## 0. 一句话结论

**这不是「选粗还是选细」的问题，是「用哪张图」的问题。** 你手上那两套结果，放同一批点上比一致性只有 0.072（满分 1），说明它们不是同一件事的不同粗细，而是在两张不同的图上各算各的。既然图只有一张（我们的 `demo_gkx_chain`），就该在自己的图上算——只是把「分多细」的旋钮调大一档，从 113 个巨块变成 178 个中等社群，成本为零，不用等任何人。

## 0.1 用比喻说一遍

想象要给 19,430 个技术点分组。

- **方案 A（久新）**：别人在他们自己的花名册上已经分好了组，把组号抄给我们。问题是**他们那份花名册和我们的不是同一本**——有 1,607 个点，他们那边算「自成一组」，但我们的图上明明画着它跟别人的连线。抄过来就会变成「页面说这个点独占一个社群，图上却有 7 条线连出去」，自己打自己。
- **方案 B（我们现在的）**：在自己花名册上分，但旋钮拧得太松，只分成 6 个大组，每组三四千人。这不像分组，像只分了 6 个学部。
- **方案 B′（升级版）**：还是自己分，把旋钮从 1.0 拧到 8.0，分出 178 个组，每组中位数 63 人。**不换数据、不换图、不找人配合，只改一个参数。**

## 0.2 术语小词典

| 词 | 意思 |
|---|---|
| **社群 / 簇** | 一批相互关系特别密的技术点，直观理解是一个「技术圈子」 |
| **成形社群** | 至少含 2 个技术点的社群。只有 1 个点的严格说不算「社群」 |
| **伪单点** | 在图上明明有邻居、却被单独算成一个社群的点。**这是划分出错最明显的特征** |
| **分辨率（resolution）** | 调「分多细」的旋钮。数值越大，分出的圈子越多越小 |
| **模块度（modularity）** | 衡量「分得好不好」的分数。**注意：分得越细分数必然越低，不同粗细之间不能直接比分** |
| **ARI（调整兰德指数）** | 衡量两套划分像不像的分数。1 = 完全一致，0 = 完全无关 |
| **写回** | 把算法算出的社群归属存进图库的 `community_id` 字段，供页面读取 |
| **血缘** | 这批数据「从哪来、用什么参数算的」的记录，验收时要能追溯 |

## 1. B′ 做了什么：只改了一个参数

不是新方案，是**在现有 B 方案上换一档参数**：

| 项 | B（现状） | B′（升级） |
|---|---|---|
| 图 | `demo_gkx_chain` 的 `tech_point` + `tech_rel` | **不变** |
| 算法 | `python-louvain` | **不变** |
| 随机种子 | 42 | **不变** |
| 加权 | 不加权 | **不变** |
| **分辨率** | **1.0** | **8.0（唯一改动）** |
| 成形社群数 | 6 | **178** |
| 成形规模中位 | 2,831 | **63** |

**口径自证**：先用 res 1.0 跑一遍，得到 113 社群 / 模块度 0.5198，与 ACCEPT 基线记录**完全一致**。说明环境、图、参数与基线同源，改的确实只有分辨率这一项。

## 2. B′ 的五个优点（对比现在的 113）

### 优点一：粒度终于落到「技术流派」级

| 口径 | 成形社群数 | 成形规模中位 | 最大社群 | 最大占比 |
|---|---:|---:|---:|---:|
| B 现状（res 1.0） | 6 | 2,831 | 5,142 | 26.5% |
| **B′（res 8.0）** | **178** | **63** | **622** | **3.2%** |
| A（久新） | 23 | 4 | 4,151 | 21.4% |

需规 434 要的是「精准发掘学术团队、技术流派、合作集群」。**6 个三千人的大组叫「学部」，178 个六七十人的组才叫「流派」。**

### 优点二：不再有巨型团

B 现状下第一个社群 5,142 个点，占全部 26.5%——点开一个社群，四分之一的技术点都在里面，等于没分。

B′ 最大 622（3.2%），前 5 大合计 12.1%，前 17 大合计 34.0%。**分布是均匀的，不存在任何一个社群吃掉四分之一数据的情况。**

### 优点三：零伪单点，每个社群点开都有人

B′ 的 285 个结果里，178 个是成形社群，107 个是图里真正一条边都没有的孤立点。**没有一个是「有邻居却被单列」的伪单点。**（A 有 1,607 个，见 §3）

### 优点四：语义站得住，抽检三个社群主题都很集中

| 社群 | 规模 | 核心节点 | 主要成员 | 主题 |
|---|---:|---|---|---|
| 57 | 622 | 偏最小二乘结构方程模型 | 评分者间信度评估 / 效用理论与风险决策 / 因果中介分析 / 结构方程建模 | 统计学方法论 |
| 133 | 486 | 营养标准的制定与应用 | 抗氧化活性测定 / 黄酮类化合物 / 甲壳素衍生物 | 营养与抗氧化 |
| 128 | 426 | 纳米石墨烯的结构与电子性质 | 石墨烯薄膜 CVD / 二维半导体外延 / 范德华异质结 | 二维材料 |

**这三点抽检很重要**：数字好看不代表分对了，主题集中才说明算法真的识别出了技术圈子。

### 优点五：成本为零

不需要新数据、不需要新表、不需要 DDL、不需要等任何外部团队。重跑一次约 2 分钟，结果已落盘。

## 3. 为什么升级，而不是直接选 A

### 理由一（最关键）：A 和 B 不是同一件事的不同粗细

这是整件事的前提。如果 A 真是「B 的更细分版本」，那选 A 也说得通。但实测不是：

| 指标 | 值 | 含义 |
|---|---:|---|
| **ARI（调整兰德指数）** | **0.072** | 1 = 完全一致，0 = 完全无关。**0.072 意味着两套划分基本互不相干** |
| NMI（归一化互信息） | 0.422 | 有部分重叠，但远低于「同一划分不同粗细」应有的水平 |

**如果 A 是 B 的细化版，ARI 应该接近 1。实际接近 0，说明它们是在不同边集上跑出来的两套无关结果。**

也就是说：选 A 不是「选一套更细的分法」，而是「放弃自己的图，改用别人图上的分法」。这个前提必须先说清，不然二选一的题目本身就设错了。

### 理由二：A 的「细」是假细——成形社群只有 23 个，中位规模 4

A 的 1,731 个社群里，**1,708 个只有 1 个技术点**（98.7%）。真实分布是断崖式：

```
4,151  3,683  3,518  2,177  1,991  1,074    ← 6 个巨块，吃掉 16,594 点（85%）
  770    165    137     22                  ← 断层：770 之后直接掉到 165
    6      4      3      3      2×8         ← 剩下 15 个都是 2–6 个点的碎块
```

**「平均每簇 11 个点」是把 1,708 个单点也算进平均得来的。成形社群的中位数是 4。**

它的形状不是「均匀分成很多小团体」，而是「6 个大桶 + 1,708 个漏网的点」。这既没做到细，也没做到分层。

### 理由三：A 贴到我们的图上会自相矛盾

A 的 1,708 个单点社群里，**有 1,607 个在我们的图上有邻居**——平均 7.2 条边，最多 68 条。

演示时的实际后果：用户点开某个技术点，页面显示「本社群：1 个技术点」，但同一张图上明明画着 7 条连线出去。**这个矛盾在现场很难解释。**

### 理由四：A 不可控、不可复现、会漂移

| 问题 | 具体 |
|---|---|
| 参数在对方 | 算法、边集、参数都由久新决定，我们只能接收结果 |
| 名称不可用 | 1,731 个社群名**全部是 `PENDING`**（未翻译），页面只能显示编号 |
| 库名带 `_dev` | `gkx_technology_analysis_dev`，开发库口径 |
| 会漂移 | 它的边集比我们多 45,824 条（587,252 vs 541,428）。我们补边后它那份就过期，还得再要一次 |
| 同分辨率下更差 | res 都是 1.0 时，我方模块度 0.5198、久新 0.4598 |

### 理由五：「A 不用写库」这个说法不成立

A 也要把 19,430 个社群归属写进 `community_id` 才能被页面读到，工作量与我们相同，**而且还要多一道跨库 ID 转换和口径核对**。

### 同时必须承认：A 有一项真实优势

| 435 要求的属性 | B′ 能否自算 |
|---|---|
| 社群规模 / 内部边数 / 密度 / 核心节点 / 平均连接强度 / 社群间关系 / 论文数 / 专利数 | ✅ 八项都能 |
| **起止年份 / 年份跨度** | ❌ **算不出来** |

实测：`tech_paper.year` 只有 **13 / 108,337** 有值，`tech_patent.year` 只有 **20 / 126,484** 有值（字段在，但几乎全空）。所以**年份跨度这一项目前只有 A 能给**。

这一项建议列为已知缺口（见 §5），不建议为了它放弃整套口径。

## 4. 对后续开发的好处

这是升级 B′ 最实际的部分。

### 4.1 不再被第三方节奏牵制

A 路线的依赖链是：久新重跑 → 重导出 → 我们转换 → 对账 → 才能用。**任何一环卡住，434/435/437 三条需规就全停。** B′ 的依赖链只有「我们自己的图在不在」，图在我们手上。

### 4.2 验收能自己复算，不靠对方背书

B′ 的全部参数都写进 `props.batch`：`algorithm=python-louvain`、`seed=42`、`resolution=8.0`、`metrics_as_of_date`、`source=tech_rel@20261107`。

**任何人拿这三个参数重跑一次，就能得到完全一样的结果。** 合规验收要的「可复现、可追溯」直接满足，不需要久新出证明。

### 4.3 写回路径与现有任务完全一致，不新增工作量

| 步骤 | B′ 需要的 | 与现有任务的关系 |
|---|---|---|
| 算社群 | 本地离线跑（已完成） | 不占 LOAD 工期 |
| 写回图库 | `community_id` 19,430 行 + `props.batch` | 与 `KG-COMPLY-LOAD-L01` 同一次批，不额外起任务 |
| 读回验数 | 按群计数核对 | 与 T05/T07 对账单同一套做法 |

**不需要新建表、不需要 DDL、不需要改结构。** 这一点很关键：T01 闸门已经因为缺 5 个 Tag + 11 条边型卡住了，B′ 不会再往关键路径上加一笔。

### 4.4 一套成员表，同时供三条需规消费

433（多算法发现）、434（结构识别）、435（属性分析）、437（可视化）四条需规读同一份成员清单：

```
社群成员表（178 个成形社群 + 107 孤立点）
  ├─ 434 结构识别    → 每个点属于哪个社群
  ├─ 435 属性分析    → 规模 / 密度 / 核心节点 / 平均强度 / 跨群边 / 论文数 / 专利数
  └─ 437 可视化      → 按社群上色分区
433 多算法对比另跑（谱聚类/K-means/LPA/Infomap），只做「算法展示」页的对比项
```

A 路线做不到这点：它没有 113 那套，我们的算法展示页还是得自己算，等于**两套并存、两套维护**。

### 4.5 演示现场可调，改参数不改代码

分辨率是运行参数，不是代码逻辑。实测可选档位：

| 分辨率 | 成形社群数 | 成形中位规模 | 最大社群 |
|---:|---:|---:|---:|
| 6.0 | 114 | 88 | 660 |
| **8.0（建议）** | **178** | **63** | **622** |
| 10.0 | 245 | 33 | 576 |

现场如果觉得「还是偏大」，改一个数字重跑两分钟即可；觉得偏碎就调回 6.0。**A 路线调不了——只能回去求久新重跑。**

### 4.6 后续补边不会让结果失效

技术点边表我们还有 45,824 条没入图（587,252 源表 vs 541,428 图中）。补进来之后：

- **B′**：重跑一次，社群自动更新，血缘记新批号。
- **A**：那份划分立刻过期，得重新向久新要一次，再走一遍转换对账。

### 4.7 社群可读名称可以自己补

A 的社群名全是 `PENDING`。B′ 现在的命名策略是「用核心节点名代表社群」（例如「纳米石墨烯的结构与电子性质」群），页面已经可读。若需要更规整的名字，可以用核心节点 + Top3 成员自动生成，不依赖外部。
