### 步骤 2 · 单个 dataId 发布

按 `gkx-orchestration/.cursor/skills/gkx-nacos-shared-config/SKILL.md` §2 执行，两种方式任选：

**方式 A（推荐，API 单发）**：在 nacos pod 内

```bash
# 1) 登录拿 accessToken（密码从 K8s Secret / 运维处取，不要写进任何文件或聊天）
curl -s -X POST 'http://127.0.0.1:8848/nacos/v3/auth/user/login' \
  -d 'username=<运维账号>' -d 'password=<口令>'

# 2) 单 dataId 发布：content 用仓库模板全文
curl -s -X POST 'http://127.0.0.1:8848/nacos/v3/admin/cs/config' \
  -H "accessToken: <token>" \
  --data-urlencode 'dataId=gkxlumen-gateway-dev.yml' \
  --data-urlencode 'groupName=DEFAULT_GROUP' \
  --data-urlencode 'namespaceId=public' \
  --data-urlencode 'type=yaml' \
  --data-urlencode "content@helm/gkxlumen-platform/configs/gkxlumen-gateway-dev.yml"
```

**方式 B（控制台）**：控制台打开该 dataId → 全量粘贴仓库模板内容 → 发布。
（用控制台也必须保证「模板 == 线上」；只改线上不改模板按规约算违规。）

**禁止**：跑 `helm:chart` 带 `FORCE_NACOS_REPUBLISH=true`；重发其他任何 dataId。

### 步骤 3 · 核对发布结果

- 接口返回 `code=0`；
- Nacos 该 dataId 的**历史版本新增一条**；
- 重新下载线上内容，与本仓模板逐行一致（无 `@@` 占位符残留——本文件本来就没有占位符，正常应完全一致）。

### 步骤 4 · 验证路由真的通了（**这是本单的核心证据**）

先确认两个服务在跑：

```bash
kubectl -n zhipu-tts get pods | grep -E 'gkxlumen-platform-(gateway|innov|topic)-'
```

然后打两条 curl（**要带正常的 dev 登录 token**，跟其他 apiview 记录同一个办法拿）：

```bash
# ① 人才域 · 实体详情（不走索引，应 200）
curl -s -X POST 'http://<dev网关>/topic/v1/person/graph/ops/PERSON_ENTITY_DETAIL' \
  -H 'Content-Type: application/json' -H "Authorization: <dev token>" \
  -H 'X-Trace-Id: <32位hex>' \
  -d '{"id":"person:tal_28a70544b6fe41fc9938a51438ed7626","dry_run":false}'

# ② 科研机构域 · 实体详情（不走索引，应 200）
curl -s -X POST 'http://<dev网关>/topic/v1/research/graph/ops/RESEARCH_ENTITY_DETAIL' \
  -H 'Content-Type: application/json' -H "Authorization: <dev token>" \
  -H 'X-Trace-Id: <32位hex>' \
  -d '{"id":"inst:ins_89bd82917fca4016865167bbe0d201ac","dry_run":false}'
```

**怎么算通**：

| 现象 | 结论 |
|---|---|
| 返回 `{"code":0,...}` 且带 `data` | ✅ 完全通 |
| 返回 5xx/503 但响应体是 Python 的 JSON（含 `reason.code`） | ✅ 路由已通，业务侧问题（索引/数据），抄下来给我即可 |
| 404 且响应像网关/`gkxlumen-topic` 的错 | ❌ 路由没生效，进步骤 5 |
| 401/403 | 路由可能已通，但 token 不对，换 token 重试 |

> `dry_run` 默认是 `true`（只做参数校验不查库），这里必须显式 `false` 才能证明端到端真的打到图库。
> 两个 VID 是从宋飞扬 11-17 的真实图库证据里取的样本，直接可用。

## 五、附录

### 5.1 已写进模板的路由块（原文）

```yaml
        # KG-GRAPH-TRIPLE-03: GlobalFilter strips topic once; Java innov relays Python /internal.
        # Only the two read-only ops paths, ahead of catch-all. No StripPrefix here.
        - id: gkxlumen-topic-entity-graph
          uri: lb://gkxlumen-innov
          predicates:
            - Path=/topic/v1/person/graph/ops/**,/topic/v1/research/graph/ops/**
          filters:
            - PreserveHostHeader
```

三个要点，发布时别改：

1. **位置必须在 `/topic/**` catch-all 之前**（现在模板里就在它上面一行）；
2. **不能加 `StripPrefix`**——网关 `GkxlumenRequestGlobalFilter` 已经剥过一次 `/topic`，再加就变成 `/person/...`，下游 404；
3. **只开 person / research 两域**。`/topic/v1/tech/graph/ops/**` 是技术链，9 个操作还没实现，**不要顺手一起开**；也不要开整个 `/topic/v1/*/graph/`，会抢 M10 维护管理路由。

### 5.2 调用链（验证时对照用）

```
前端 /knowledge-graph/person | /research
  → 网关 /topic/v1/{person|research}/graph/ops/{op_id}
  → (GlobalFilter 剥 /topic) → gkxlumen-innov  /v1/{domain}/graph/ops/{op_id}
  → Java 透传 → lumen-algo-py  /internal/{domain}/graph/ops/{op_id}
  → NebulaGraph demo_gkx_chain（只读）
```

### 5.3 回滚

1. Nacos 该 dataId 的历史版本存的是**修改前**内容：取本次发布**前**那一条历史，整份重发；
2. 或直接删掉模板里那 8 行 → 重新单发 → 重启网关；
3. **只回退这一个 dataId**，不要整批重发；本单不涉及图数据，不需要数据回滚。

| 开 `FORCE_NACOS_REPUBLISH=true` 或跑 `helm:chart` | 整批覆盖 14 个 dataId，11-07 事故就是这么来的 |
| 顺手把 `/topic/v1/tech/graph/ops/**` 也打开 | 技术链 9 个操作未实现，开了就是对外暴露 404/501 |
| 顺手改 `gkxlumen-topic-entity-graph` 的路径或加 `StripPrefix` | 口径我定过，改了要重新验 |
