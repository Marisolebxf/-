## 二、问题一：科研机构怎么从现有机构里挑出来？

### 答案

**不用挑。科研机构和服务机构是两批完全不同的数据，根本不在同一张表里。**

### 为什么

**第一，图里现有的 43,296 个机构，一个科研机构都没有。**

我把它们的类型全查了一遍：

| 类型 | 数量 |
|---|---:|
| 科技创新服务 | 29,321 |
| 服务机构 | 9,650 |
| 金融服务 | 2,062 |
| 咨询服务 | 1,387 |
| 市场营销服务 | 570 |
| 人力资源服务 | 210 |
| 知识产权服务 | 96 |

七类**全是"服务"性质**。没有"高校""科研院所""实验室"这一类。所以不是"判定口径不清"，是**这批数据里压根没有科研机构**。

**第二，真正装科研机构的是另一张表。**

久新数据仓里有一张机构表 `ads_institution_profile`，共 **83,745 行**，分类是这样的：

| 类型 | 数量 | 大致是什么 |
|---|---:|---|
| education | 16,991 | 高校、教育机构 |
| unknown | 15,516 | 未分类 |
| company | 15,392 | 企业 |
| healthcare | 11,228 | 医疗机构 |
| facility | 9,317 | 科研设施 |
| nonprofit | 6,210 | 非营利机构 |
| government | 4,312 | 政府部门 |
| other | 3,404 | 其他 |
| archive | 1,071 | 档案馆 |
| funder | 304 | 资助机构 |

这张表还带论文数、被引数、人才数、项目数这些科研指标，**整张表就是"科研机构"这个群体**。它和上面那 7 类服务机构，是两套完全不同的分类体系，也印证了我方《数据源清单与缺口》里的判断："这 242 张表里没有服务机构对应的源表，来源需单独确认"。

### 所以 T03 这么做

| 事项 | 做法 |
|---|---|
| 科研机构点从哪来 | 就是上面那张 `ads_institution_profile`，83,745 行 |
| 编号怎么造 | `inst:` + 机构号（图里没有这类点，不冲突，可以照文档来） |
| 判定规则 | **整张表 83,745 行全建**，分类原值存进属性里，不丢信息。要不要剔除"企业""未分类"这类边缘类型，交给业务侧以后在查询时筛，**灌数时不删数** |
| 和现有服务机构什么关系 | **两批独立数据，不合并、不互相指**。服务机构走 `institution`，科研机构走 `research`。同一家真实机构可能在两边都出现，本期不做对齐（对齐是正式库的事） |
| 不许做的 | 不改现有`institution`点的类型、不删点、不迁移、也不因为"看起来像科研机构"就把现有的服务机构点改标成科研机构 |

> 这也顺手回答了我方《结构与空间选定》里一直悬着的一个问题："服务机构是否有独立源表，还是和科研机构同表"——**不同表，各有各的源。**

## 三、问题二：M07 用论文署名行，还是别的地方？

### 答案

**论文署名行压根出不了 M07。M07 的数据来自"人才-项目关系表"。**

### 为什么

三条关系，三条不同的数据来源，别混：

| 关系 | 数据从哪来 | 有多少行 |
|---|---|---:|
| M07 人才参与项目 | `ads_talent_project`（人才-项目关系表） | **7,702,366** |
| M09 人才是专利作者 | `ads_talent_patent`（人才-专利关系表） | 85,069 |
| M09 人才是论文作者 | **没有数据源** | — |

`ads_talent_project` 这张表里的字段长这样：是否有首席身份（`is_lead`）、是否直接研究者（`is_direct_investigator`）、角色代码（`investigator_role_codes`）、前端展示角色（`frontend_role_label`）。**这就是"署名"的意思——但它是项目署名，不是论文署名。**

### 还有个更要紧的发现：论文署名数据根本拿不到

我查了论文表 `ads_paper_profile`，4,000,000 行、44 个字段，**没有任何一个字段是作者**，只有一个"作者数量"：

```
含 author 的字段：['author_count']   ← 只有一个作者数量
含姓名/人才/贡献者的字段：[]          ← 一个都没有
```

也就是说：

- **"人才是论文作者"这条关系（M09 的论文部分）建不出来**，没有数据；
- 图里能用的论文关系是"技术点关联论文"（那属于技术点层，不是七要素层的 M09，不能拿来顶替）；
- 专利那部分有数据（85,069 条），可以建。

### 所以 T04 这么做

| 要建的关系 | 建不建 | 数据从哪来 | 怎么处理 |
|---|---|---|---|
| M07 人才参与项目 | 建 | `ads_talent_project` | 只管项目，不管论文专利。首席和普通参与人**都算 M07**，角色差异存在属性里（`project_role`），不另开一种关系 |
| M07 人才参与论文/专利 | 不建 | 无 | 论文没有作者字段；专利那边已经由 M09 表达了，不重复挂 |
| M09 人才是专利作者 | 建 | `ads_talent_patent` | 方向是人才→专利，不许反转 |
| M09 人才是论文作者 | **不建（没数据）** | — | 在对账单里单列成"缺数据"，不造数 |

**这么做还顺手解决了一个隐患**：M07 的终点是项目、M09 的终点是专利，两条关系不会落在同一对点上，不会产生重复边。
