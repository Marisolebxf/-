## 五、派单方式（照既有范式，不改规矩）

### 5.1 派单文档的三段式

每张单一份 `派单说明-<任务号>.md`，正文是一个 ```text 代码块，给执行 agent 直接粘贴的 `/goal` 提示词，固定包含：

`身份 → 任务/标题/Epic/优先级/类型 → 负责人与监管 → 状态与依赖 → 仓与分支 → 强度 → 上下文 → 目标 → 必读 → 已锁定 → 范围 → 主文路径 → Handoff → 禁止`

参考：`派单说明-KG-COMPLY-SDD-L01.md`、`派单说明-KG-7ELEM-SCHEMA-DDL-L01.md`。

### 5.2 四条硬规矩（既有公约，本次继续执行）

| 规矩 | 内容 |
|---|---|
| 建单走登记册 | 任务只通过 MCP `task-registry` 建/改；不直接手改 `task-registry.yaml`。本会话无该 MCP，**建单由 coordinator 按本目录清单执行**，派单说明里写清字段值 |
| 认领与监管 | 燕大同学认领，`supervised_by` 按本计划指派；agent 执行时 `claimed_by=agent:*` |
| 状态只写实 | 执行到 `integration` 为止，不写「会签通过」，不自行标 `done`；done 由我或唐绍祖签 |
| 数据红线 | 只读既有库；需要落库只在 `demo_gkxumenx_ai` 建 `demo_*` 表（本计划不涉及写 MySQL）；图库只写 `demo_gkx_chain`，禁止 `DROP SPACE`、禁止第二空间 |

### 5.3 图库操作红线（本次特别加）

| 红线 | 原因 |
|---|---|
| 禁止无 Tag 锚定的全表扫/大聚合 | 内存 80%，会被拒并拖垮服务 |
| 大批量写入前先确认环境已扩容 | 2,477,802 条边写入量是现有总量的 1/3，不扩容会写失败 |
| 写边必须批量 + 分批提交 + 可断点续 | 已有 T02 344 万条的先例，分批是唯一稳妥做法 |
| 禁止 `DROP SPACE` / 清空重建 | 7,494,329 条边是全组共享成果 |
| 新边必须带 `props.batch` | 事后对账唯一依据；`batch` 不在 JSON 首位，筛选用 `CONTAINS` |

### 5.4 时间约束（来自项目总计划）

## 六、派单原则（本次采用）

1. **一个人一条线，不交叉**：5 个人 5 个包，避免出现「两人改同一份文档」的返工。
2. **派单只派「可验收的产物」，不派「调研一下」**：每张单的 DoD 必须能写成「文件路径 + 一个数 + 一句判定」。
3. **数据补齐必须带重算**：灌完边不重算，榜单和新边对不上，等于白灌 —— 所以 A/B 两包是一组，B 卡在 A 后面。
4. **接口实现必须先定案 1/案 2**：不定就两拨人各写一套。本次定为**案 2（燕大服务）**，理由见 §七。
5. **不新增「必须关系」**：M01–M24 是 L01 已签收的闭集，本次只补数据、不扩语义。三域三元组消费的是**已有边**，不是新编边。

## 七、一个必须现在拍板的架构选择：428/432/435/437 走案 1 还是案 2

| | 案 1：展示 Java + Python | 案 2：燕大服务 |
|---|---|---|
| 取数 | Java 调 `lumen-algo-py` 的 `/internal/*` | 燕大自己出 `/internal/kg/*`，Java 只透传 |
| 优点 | 与我方现有链路一致，鉴权/网关统一 | 燕大最熟数据，改口径快；不占我方人力 |
| 缺点 | `lumen-algo-py` 无人手（唐绍祖只做验收）；要新写 4 个 Python 端点 | 要过网关与 Java 透传，多一跳 |
| 本次结论 | ❌ | ✅ **选案 2** |

**理由**：11-19 前要可测，我方 Python 侧无人；燕大已有 4 域 `/internal` 成对接口的成熟范式（CHAIN/POLICY/ENT/SVC），照抄即可；T12 契约两案通用，不用改契约。
