# 调研 07 · 图库内存水位现状（11-13 空载复测 + 压测）

- 出具：淮政玮（大项目架构师）
- 时点：2026-11-13 14:32–15:20 现场只读实测
- 目的：回答两件事 —— ① 现在内存还这么满吗；② 昨天满内存是临时尖峰，还是日常任务常驻占用
- 方法：`nebula3` 只读探针（`SHOW` / `MATCH ... count` / 一条复现用 `sum` 压测），**全程无写入、无 DDL、未建 space**
- 前提：我方**没有这台机器的 SSH**，也读不到 `/proc/meminfo`；下面的结论全部来自「服务行为」推断，不用「我觉得」

---

## 一、一句话结论

**不是临时尖峰，也不是日常任务常驻占用；是数据量把内存基线顶到 80% 红线附近、余量接近零。**
空跑时服务是好的（建连 10/10、606 万条边全表 count 29 秒返回），但只要跑一条全量属性聚合，整台机器的 Nebula 立刻假死，**15 分钟不自愈**。所以「昨天满」不是偶然，今天能复现。

## 四、14:36 压测：一条 `sum()` 把整机打到假死

复跑 11-12 被拒 518 秒的那条：

```
MATCH ()-[e:cooperate]->(b) RETURN sum(e.weight)
```

| 时刻 | 现象 |
|---|---|
| 14:36 | 客户端 30 秒超时，**服务端继续跑**（`SHOW QUERIES` 可见 RUNNING） |
| 14:37 | `SHOW SESSIONS` / `SHOW QUERIES` 开始被拒：`Used memory hits the high watermark(0.800000)` |
| 14:39–15:05 | 建连直接 `BAD`；9669/19669/19559/19779 **TCP 全部可连**，但应用层 15–60 秒不返回；ping 正常 |
| 15:20 | 仍未自愈（巡检日志见 §八） |

**这不是「慢慢变满」，是「余量已经没了」**：
11-12 是「大查询被拒、服务还在」，今天退化成「大查询一跑、整机冻结」，说明红线比昨天更贴近。

> 诚实记录：这条 `sum()` 是我主动复跑的压测，目的就是验证「现在还会不会被拒」。结果不是被拒，而是把实例打到冻结。**这本身就是最硬的证据**：基线已经贴着线，任何一条大聚合都可能是最后一根稻草。

## 五、为什么判定「不是日常任务占用」

| 排除项 | 证据 |
|---|---|
| 没有业务常驻连接占内存 | 空载时 `SHOW SESSIONS` 只有我的会话，无 GDF / 算法库 / 前端的常驻 session |
| GDF 没有日常写图 | 契约 9 个枚举里实际只有 `industry_segment` 在触发；`enterprise_point`、`service_org_point`、`policy_point` 三域**未开通**，不会日常写 |
| 仓内没有写图的定时任务 | `cron` / `xxl-job` 全仓检索无 Nebula 写入入口；写图只有 T02/T03/T04 这类一次性批次脚本 |
| 没有对账/统计任务在跑 | `SHOW QUERIES` 空载时只有我自己的 1 条 |

**内存被谁吃了**：7,494,329 条边 + 约 64 万点常驻单机，加上 Nebula 内存分配后**不主动还给操作系统**（它的设计如此，不是 bug），所以基线只涨不落；再叠加一条大聚合的执行内存，就直接过线。

## 六、为什么也不能简单说「是临时尖峰」

- 昨天的**导火索确实是短时的**：T02 一天灌 3,442,271 条边（数据量 +85%），再加上对账时的大聚合；
- 但**灌完之后基线没回去**：今天空载能连、能 count，可跑属性聚合就崩，说明「写入冲高」留下的高位**变成了新常态**；
- 所以准确定性是：**短时写入是导火索，7.5M 边常驻 + 零余量是根因** —— 属于容量问题，不是负载波动问题；不扩容，下一次大查询/下一批写入一样会崩。

## 九、口径说明（避免误读）

1. **`SHOW STATS` 不可信**：返回 43 行里 `person=0`、`research=0`、`paper=0`，但实测 `count(person)=100,000`。说明 STATS JOB 停在早期批次，**不能拿 `SHOW STATS` 当数据量依据**，必须用 `MATCH ... count`。
2. **「内存满」不是「磁盘满」**：是图引擎自身分配的内存到整机内存的 80%，跟磁盘、跟 space 大小无关。
3. **建连 BAD ≠ 端口不通**：`nc` 探 9669 始终 OPEN，是应用层不响应（冻结）——昨天把它误判成「网络时通时断」会走错方向。
