## 一、先用大白话说清楚

图里每一个点（一家企业、一个产业链环节、一条政策）都有一个**唯一编号**，术语叫 VID。这个编号就像身份证号：系统不认识"这家企业叫什么"，只认这个号。两条边能不能连上，全看两头的号对不对得上。

现在的问题是：**我们文档里写的"怎么造这个号"的规则，和图里 27 万个点实际在用的规则，不是同一套。**

如果照文档去造号，等于给已经存在的 27 万个人每人又发了一张新身份证——系统会当成另一个人。新造的号下面没有任何信息，边全挂在空壳上。**更麻烦的是，系统不会报错**，它只会安静地建出一堆空壳，等我们发现时已经灌了几十万条错边。

白鑫凤查出来的就是这个，她是对的。而且我复核时发现，情况还比她写的更严重一层。

---

## 二、小词典（看不懂名词时回来查）

| 词 | 什么意思 |
|---|---|
| 点 / Tag | 图上的一类实体。比如"企业"这一类、"产业链环节"这一类。文档里写 Tag 就是指这个 |
| 边 / Edge | 点和点之间的关系。比如"企业参与某个环节"就是一条边 |
| 编号 / VID | 每个点的唯一标识，全库唯一。系统靠它认点 |
| 前缀 | 编号开头那几个字符。比如 `ent:` 代表企业，`segment:` 代表产业链环节 |
| 存量 | 图里已经存在的数据（不是本期要新加的） |
| 幽灵点 / 空壳点 | 编号造出来了，但这下面没有真实信息——只剩一个号 |
| M01–M24 | 需求里规定必须有 24 条关系，编号从 M01 到 M24。「M15」就是第 15 条，「M17」是第 17 条 |
| T01–T14 | 本项目的 14 个细任务编号 |
| 双灌 | 同一批关系灌了两遍，边数翻倍 |

## 三、她查到的：前缀不一样（我复核后一致）

| 点的类别 | 我们文档写的编号规则 | 图里实际在用的 | 图里点数 | 照文档造号的后果 |
|---|---|---|---:|---|
| 企业 | `ent:` + 统一社会信用代码 | `ent:` + 一串 32 位编码 | 208,394 | 前缀碰巧一样，但后面跟的东西不同，一样对不上 |
| 产业链环节 | `seg:` + 链条号 + 环节号 | `segment:` + 环节号 | 1,414 | 前缀和结构都不一样，全部连不上 |
| 服务机构 | `svc:` + 机构号 | `institution:` + 机构号 | 43,296 | 全部连不上 |
| 政策 | `policy:` + 政策号 | `pol:` + 政策号 | 20,000 | 全部连不上 |
| 技术点 | `tp:` + 技术点号 | `tech_point:` + 技术点号 | 19,430 | 技术点这块本期不动，仅供参考 |
| 科研机构、人才、论文、专利、项目 | `inst:` / `person:` / `paper:` / `patent:` / `proj:` | 还没建，图里没有 | 0 | 没有冲突，可以照文档用 |

她还做了一个很关键的验证：照文档的前缀去查一个真实存在的环节点，**查不到**；照图里实际的前缀查，**能查到**。

```
按文档前缀查：seg:INB120401010102      → 0 个（不存在）
按实际前缀查：segment:INB120401010102  → 1 个（就是它）
```

## 四、我复核时多发现的一层：企业的号根本不是信用代码

我们文档写的是"企业编号 = `ent:` + 统一社会信用代码"。但图里 208,394 家企业点，**信用代码这一列一条有值的都没有**：

| 字段 | 有值的点数 |
|---|---|
| 企业名称 | 208,394 / 208,394 |
| 企业信用代码 | **0 / 208,394** |
| 企业链条角色 | **0 / 208,394** |
| 其他属性（城市、行业、标签等） | 208,394 / 208,394 |

也就是说，照文档造号这个方案，**连原料都取不到**——不是造出来对不上，是根本造不出来。

那图里的号到底是怎么造的？我找到了。真正的原料藏在点的属性里，字段名叫 `org_id`：

```
点的编号：ent:0002a237784776879ffbbe8645661cbc
属性里的 org_id：0002a237784776879ffbbe8645661cbc   ← 完全一致
```

我抽了两个点逐字比对，都对得上。所以正确做法不是"用信用代码算一个号"，而是**从数据里把 `org_id` 读出来，前面加 `ent:`**。

其余几类同理，都是"读出来"而不是"算出来"：

| 点的类别 | 编号后半段从哪个字段读 |
|---|---|
| 企业 | 属性里的 `org_id` |
| 产业链环节 | 属性里的 `segment_key`（实测 `segment:INB1204010306` 对应 `segment_key = INB1204010306`） |
| 政策 | 政策源表的主键号（如 `pol:18318870`） |
| 服务机构 | 机构的 `org_id`（和企业同一种 32 位格式） |

## 五、还有个更要紧的连带问题：T02 要灌的边其实已经在了

白鑫凤这版顺手做了端点方向的全面核对，结果和我复核一致，但引出一个会出大问题的点：

| 关系 | 图里现在有多少条 | 说明 |
|---|---:|---|
| 产业链环节 → 产业链环节（M15） | **1,073 条** | 全部都是"环节到环节"，正是 T02 要灌的那批 |
| 企业 → 产业链环节（M17） | **178,731 条** | 正是 T02 要灌的那批 |

**这两批关系图里已经有了。** 而 T02 原来的任务话术写的是"按关系表灌入"——照这么执行，会把同一批关系再写一遍，边数直接翻倍，验收时对账单永远对不上。

另外，这些存量边虽然都有属性，但属性里是历史字段（关系编号、操作编号），**没有批次号 `batch`**：

```
实际属性样例：{relation_id: "er:INB133303040202:000e178d…", op_id: "CHAIN_RE_INDUSTRY_ENTERPRISE"}
```

要不要给老边补上批次号？**不能补。** 那属于改动库里已有的数据，按本项目铁律禁止。所以对账方式要换：存量边用"边数 vs 源表行数"对账，批次号只用于本期新写入的边。

## 六、裁定：五条

| 序号 | 事项 | 怎么定 |
|---|---|---|
| 1 | 本期用哪套前缀 | **用图里现在实际的**：`ent:` / `segment:` / `institution:` / `pol:`；不许用 `seg:` / `svc:` / `policy:` / `tp:` |
| 2 | 五个新建的类型（科研机构、人才、论文、专利、项目） | 图里没有、不冲突，**照文档的规范前缀用**（`inst:` / `person:` / `paper:` / `patent:` / `proj:`） |
| 3 | 编号怎么来 | **从数据里读字段拼出来，不按文档硬算，也不去重算信用代码**：企业用 `org_id`，环节用 `segment_key`，政策用政策主键，服务机构用机构 `org_id` |
| 4 | 文档里那套规范前缀怎么办 | 保留，标成**正式库 `gkx_chain` 的目标规则**；同时在文档里加一列"本期实际用什么"，两套并存、各自写清。已签收的类型定义和 24 条关系一条都不改 |
| 5 | 程序怎么落地 | 编号规则本来就已经做成可配置的参数，不用新机制。配两套方案：本期用"现场规则"，正式库用"规范规则"。**本期只准跑现场规则那一套** |

## 八、为什么这条必须在上线前定死，不能边灌边试

1. 图数据库在"给一条边指定两端点"时，如果端点号不存在，**它会自动帮你建点，而不是报错**。前缀写错不会有人告诉你，只会安静地长出几十万个空壳点，边全挂在空壳上。
2. 空壳点在按类型查询时是能查出来的（类型对、属性全空），会让后面所有数量核对、算法计算全部失真。等发现时，排查成本极高。
3. 178,731 条这种量级，一旦翻倍或写进空壳，验收对账单直接对不上，任务关不掉。

**所以这三件事必须按这个顺序：先把编号规则定死 → 再走数据库授权补结构 → 结构补完 → 才开始灌数。** 不能倒过来。
