## 二、背景：为什么会有这两对重复

需求方给的 24 条必须关系（M01–M24）是按「消费需求」编号的，不是按「物理存储」编号的：

| 编号 | 关系 | 端点 | 来源需求条目 |
|---|---|---|---|
| M01 | 人才 `cooperate` 人才（无向） | 人才—人才 | Q01（查询侧） |
| M20 | 人才 `talent_coop` 人才（双向） | 人才—人才 | A30（算法侧） |
| M02 | 科研机构 `cooperate` 科研机构（无向） | 机构—机构 | Q02（查询侧） |
| M19 | 科研机构 `research_coop` 科研机构（双向） | 机构—机构 | A29（算法侧） |

四个编号，两组端点。**同一对实体、同一份证据，被查询侧和算法侧各要了一次。** 需求文档明确写「不并进」，指的是编号不能合并登记，**不是要求物理上写两份边**——写两份就是同一批数据双灌。

这与 T06 已实测的 `apply_to` / `support` 情况同型（两条边 100% 重合 9,279 条），那次结论是「建议停读一条」。这次在灌数前就按同一原则处理，不留到 T06 再返工。

### 7.4 问答二：跨年聚合，权重禁用 `collaboration_strength`

**`collaboration_strength` 是逐年单独归一的相对分，不可跨年比较或平均。** 实测各年最大值与分母：

| 年份 | `MAX(collaboration_strength)` | 同该年 `MAX(co_paper_count)` |

| 2015 | 1.000000 | 1,593 |
| 2018 | 1.000000 | 3,610 |
| 2021 | 1.000000 | 5,586 |
| 2023 | 1.000000 | 8,235 |
| 2025 | 1.000000 | 10,873 |

**落地口径**：

1. 跨年**聚合成一条边**，不按年保留多条（技术原因见 3.2）。
2. `weight` 取**累加的 `co_paper_count`**（跨年求和），不使用 `collaboration_strength`。
3. 各年原始 strength 可保留在 `props`（如 `strength_by_year`），并标注「逐年归一，禁止跨年比较」。
4. 双向去重：取 `institution_id < collaborator_institution_id` 一侧。实测 A→B 与 B→A 严格 50/50（各 7,190,123 行）。
5. `props` 必含 `first_year` / `latest_year` / `year_count` / `co_paper_count_total` / `match_method="coauthor"` / `batch`。

## 八、2026-11-12 M04 分母修正：72,503 → 72,099

### 8.1 修正内容

宋飞扬执行后报数：M04 实入 **72,099** 条，而非本裁定 §3.4 预估的 72,503 条。差额 404 条，原因是 §3.4 只按「行」扣了 `company` 行（420 行），未按「唯一机构对」扣除 `company` 对。

**独立复算（唐绍祖，久新 Doris 只读）**：

| 指标 | SQL 复算值 |
|---|---:|
| 工作经历行（`experience_type=2`） | 84,589 |
| 唯一「人才+机构」对（未排除企业） | 72,503 |
| 其中 `company` 类型唯一对 | **404** |
| 排除企业后行数 | 84,169 |
| 排除企业后唯一对 | **72,099** |

72,503 − 404 = 72,099，与其交付 SQL 结果完全一致。**原估算 72,503 作废，改用 72,099。**

### 8.2 根因

§3.4 的减法做在「行」层（84,589 行 − 420 行 = 84,169 行），但边数取决于「唯一对」而非行数。404 个企业对分布在多于 404 行中，因此按行扣除会低估排除量。正确做法是先在「对」层排除再计数。

### 8.3 影响与口径

| 项 | 变更 |
|---|---|
| M04 应灌分母 | 72,503 → **72,099** |
