## 一、第一件事：图库内存到限载线了（要排期处理）

### 1.1 现象

今天（11-12）我复核 T02 / T03 灌入结果时，图库 `10.50.75.136:9669` 反复报：

```
Used memory hits the high watermark(0.800000) of total system memory
```

即内存占用已到总容量的 80% 限载线。

### 1.2 具体表现（都是实测，可复现）

| 我跑的查询 | 结果 | 耗时 |
|---|---|---:|
| 按 Tag 锚定的分组计数（小范围，带索引） | ✅ 正常 | 2–33 秒 |
| `MATCH ()-[e:cooperate]->() RETURN count(e)` 全表扫 | ❌ 被拒 | 73 秒后拒 |
| `MATCH (a:research)-[e:cooperate]->(b:research) RETURN e.props LIMIT 1` | ❌ 被拒 | 20 秒后拒 |
| `MATCH (a:research)-[e:cooperate]->(b:research) RETURN sum(e.weight)` | ❌ 被拒 | **518 秒后拒** |
| 建立连接（`ConnectionPool.init`） | ⚠️ 时通时断 | 需重试 1–4 次 |

**注意最后一条的细节**：`nc -z` 探端口始终保持 OPEN，但客户端 `init` 报 `BAD`。也就是说**不是网络不通，是服务端因内存压力拒服务**。这个区别很重要，排查方向完全不同。

### 1.3 规律

**不带 Tag 锚定的全表扫描 / 大范围聚合基本失效；按 Tag 锚定的小范围索引查询还能跑。**

换句话说：数据能取，但只能「一条一条地取」，不能「一次数全库」。

### 1.4 影响，按紧急程度排

**① T07 总账对账会被卡住。**
T07 要出 24 条关系的验收总表。如果对账脚本按常规写法做全表扫描式核对，会直接跑挂。我已把 T07 口径改成「按 Tag 锚定 + 分组计数」，能绕开大部分；但绕不过 `sum(weight)` 这类全量聚合。

**② 有一部分数据我无法独立核验。**
M02 的 `weight` 总和（执行方报 14,715,117）被内存水位拒掉，518 秒后失败。目前已标注「待内存释放后补验」，暂采信执行方自述，**不阻塞签收**，但这个洞是环境限制造成的，补验需要环境恢复。

**③ 后续还有任务要往里写，越往后越难写进。**
目前空间里已有 7,494,329 条边，其中 T02 一次就灌了 344 万条。这是明显的拐点。再往后（正式线、增量同步）很可能出现「写也写不进」的情况。

### 1.5 请求

1. **评估扩容或调整 `high_watermark` / 内存配额**，恢复到能做全表扫描的水平。哪怕只是临时提高限载线，也够我把补验做完。
2. **确认 graphd 地址是否仍是 `10.50.75.136:9669`。** 我注意到项目里有「旧 `10.50.75.136` 已迁走」的记录（其他服务），如果图库也有迁移计划，请提前告知——我这边对账脚本要改地址。
3. 如果需要，**我可以提供一份「哪些查询会触发拒服务」的清单和可复跑的探针脚本**，方便你们复现和验收扩容效果。

### 1.6 补充：数据正确性不受影响

- T03 的 M01 2,525,789、M04 72,099，分组计数全部跑通，与交付一致；
- T02 的 M02 3,442,271，批次覆盖率 100%，与交付一致；
- `person` 100,000、`research` 83,745 都在位。

**这是容量问题，不是数据问题。**

## 二、第二件事：正式线 `gkx_chain` 根本没有建

### 2.1 实测

今天（11-12）15:40 我在 `10.50.75.136:9669` 上跑 `SHOW SPACES`，返回结果只有一个：

```

```

**没有 `gkx_chain`。**

### 2.2 这件事的冲突在哪

| 来源 | 说法 |
|---|---|
| `architecture-baseline` v2.2.15 | **不建正式名 `gkx_chain`**，本期全部成果落在演示空间 |
| T11 任务卡 | 「对照正式线 `gkx_chain` 做结构覆盖」 |

**两者直接冲突。** T11 做完了结构覆盖清单（9 个标签 + 24 条关系，去重后 15 个边型），但它的任务前提是「已经存在一个正式线，去对照它」——而正式线不存在。

### 2.3 为什么要请你拍这句话

因为清单读法会变：

- 若「正式线本来就不建」→ 这张清单是**将来的建库规格书**；
- 若「正式线要建、只是还没建」→ 这张清单是**待办事项**。

**两种读法对下游的影响完全不同**：前者不需要任何人去补建，后者需要有人排期建。**验收的人如果读错了，会以为「清单 33 行全是欠账」。**

所以我在清单开头特意写明了：**这是结构要求，不是进度欠账。**

### 2.4 请求

**一句话决策即可**：正式线建不建？如果建，是同一套集群新建空间，还是另起一套实例？

（顺带提一下：如果确定要建，清单里列了 6 个必须提前定的技术选择，比如两个「机构」标签的前缀不一致——`research` 用 `inst:`、历史 `institution` 用 `institution:`，照抄时极易串；`project` 标签名和前缀 `proj:` 不同形；`participates` 是唯一没有 `weight` 的边型。这些不提前定，建完一定返工。）

## 三、第三件事：`tech_point.weighted_degree` 是陈旧数据

这条严格说不是图库运维的问题，但你需要知道，因为它影响对外展示。

### 3.1 现象

`tech_point` 标签上有个 `weighted_degree` 字段，实测它**跟当前边集对不上**：

| 项 | 数值 |
|---|---:|
| 榜首存储的 `weighted_degree` | 1,010.90780192 |
| 当前入边 2,347 + 出边 567 = 2,914 条，Σconfidence ÷ 100 | 1,478.05 |
| 比值 | 0.684 |
| 抽查 Top10 的逐点比值分布 | 0.519 – 0.719（**无恒定系数**） |
| 全库 Σweighted_degree / Σ(confidence÷100) | 0.752（与点级不一致） |

### 3.2 判断

逐点比值漂移说明**不是「差一个固定系数」**，而是这个字段**在更早的一版边上算出来的、之后没重算**，每个点的陈旧程度不同。

### 3.3 影响

- 428（度数中心性）整榜建立在这个字段上；
- 432（综合排名）有 25% 的分项建立在这个字段上。

**对外展示需标注「口径待确认」或改用基于当前边重算的榜。** 已记在 T09 验收记录里，等归属方处理。
