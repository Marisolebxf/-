## 三、孔东两次为什么没成功（根因，可复核）

### 3.1 关键机制：网关路由的**真源在 Nacos，不在仓库**

`gkxlumen-gateway` 的 `application.yml` 里写着：

```yaml
spring:
  config:
    import:
      - optional:nacos:application-@profiles.active@.yml
      - optional:nacos:${spring.application.name}-@profiles.active@.yml
```

`spring.application.name` = `gkxlumen-gateway` → 启动时从 Nacos 拉 `gkxlumen-gateway-dev.yml`。**网关到底认哪些路由，取决于 Nacos 里那一份，仓库里的 helm 文件只是模板。**

### 3.2 于是形成三处断点

| 环节 | 实际行为 | 结果 |
|---|---|---|
| 改 `helm/gkxlumen-platform/configs/gkxlumen-gateway-dev.yml` 并 push | 只是仓库文件变了；CI 不会自动把它推到 Nacos（`FORCE_NACOS_REPUBLISH` 默认 `false`，代码注释明确写了「日常勿开」） | 线上 Nacos 内容不变 |
| CI 跑 `deploy:gateway` | 只重建网关 pod / 换镜像；pod 启动时**照样从 Nacos 拉旧内容** | 重启了也没用 |
| 打完 curl 看 404 | 请求落到 `/topic/**` catch-all → `gkxlumen-topic`，它没有这个路径 | 表现为「配了没效果」 |

**这解释了「两次都没有成功」**：两次都停在「模板已改、dev 已推」，但**Nacos 那一步没人做**（也可能有人做过但发了别的 dataId / 发到了非 `public` 命名空间 / 没重启）。

### 3.3 我刚实测的证据（免 token 即可判定）

dev 网关 `http://10.50.69.111:30892`，参照组与实验组对比：

| 路径 | HTTP | 是否带 `X-RateLimit-*` | 结论 |
|---|---|---|---|
| `/api/topic/v1/meta/industry-clusters`（已知经 `gkxlumen-innov`） | 200 | **带** | 网关与 innov 都正常 |
| `/api/topic/v1/person/graph/ops/PERSON_ENTITY_DETAIL` | 401 | **不带** | 落到 `gkxlumen-topic`，**路由确实没生效** |
| `/api/topic/v1/research/graph/ops/RESEARCH_ENTITY_DETAIL` | 401 | **不带** | 同上 |

> 原理：`gkxlumen-innov` 的响应恒带 `X-RateLimit-Remaining`，`gkxlumen-topic` 不带。所以**这个响应头就能当「路由有没有生效」的探针**，不需要 token。工具已封装成 `gw10_verify_route.sh`，现在跑就是上面这个结果。

## 五、执行顺序（照抄即可）

### 第 1 步 · 先看线上到底有没有（只读，安全）

任何拿到 Nacos 账号的人跑：

```bash
export NACOS_USER='<账号>' NACOS_PASS='<口令>'
cd local-workspace/tools
./gw10_publish_nacos.sh          # 默认 dry-run
```

会打印「线上 vs 仓库模板」的完整 diff，并给出：

- `新增行 0 / 删除行 0` → 线上已经有了，直接跳到第 3 步验证；
- `新增行 8~12` → 正是本次路由块，进第 2 步；
- 差得更多 → 说明线上有人改过，**脚本会自己中止**，把 diff 发我，我判断后再发。

### 第 2 步 · 发布（单 dataId）

```bash
./gw10_publish_nacos.sh --publish
```

只看两行结果：`发布成功（code=0）` + `回读一致：线上内容 == 仓库模板`。

> 这一步只碰 `gkxlumen-gateway-dev.yml` 一个 dataId。**不要**用 `FORCE_NACOS_REPUBLISH=true` 跑 `helm:chart`——2026-11-07 就是用这招把 14 个 dataId 整份覆盖，冲掉 `sso` 导致展示/专题 SSO 白屏。

### 第 3 步 · 验证

```bash
cd local-workspace/tools
./gw10_verify_route.sh                  # 免 token，先看路由有没有切过去
```

- 两条都 `✅ 路由已生效` → 成功；
- 仍 `❌ 未生效` → 配置发了但网关没重新拉，此时才需要重启用第 4 步；
- 想要「打到图库」的硬证据，再补 `TOKEN=<dev token> ./gw10_verify_route.sh`。

### 第 4 步 · 必要时重启网关（只有滕强能做）

```bash
kubectl -n zhipu-tts rollout restart deploy gkxlumen-platform-gateway
kubectl -n zhipu-tts rollout status  deploy/gkxlumen-platform-gateway --timeout=180s
kubectl -n zhipu-tts logs deploy/gkxlumen-platform-gateway --tail=200 | grep -i entity-graph
```

只重启这一条 deploy，不批量重启。
