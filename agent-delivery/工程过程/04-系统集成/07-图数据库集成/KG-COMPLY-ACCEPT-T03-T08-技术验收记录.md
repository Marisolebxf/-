### 3.3 代价公式裁定

**结论：确认 `cost = 1 / relation_confidence_score` 作为 2026-11-11 批正式口径并归档，不要求重跑。**

理由：

1. 旧材料（11-07）只给了置信度字段名与算法名，**从未发布代价转换公式**，不存在「沿用旧口径」的选项——要求沿用等于要求重现一个未记录的实现。
2. `1/x` 是单调递减的标准倒数变换，语义正确：置信度越高，代价越低，Dijkstra 自然偏好高置信链路。
3. 权重确实被读入：10 对 BFS 与 Dijkstra 跳数虽全相同，但 **6 对代价严格改进**（`weighted_cost_improved_pairs=6`，容差 1e-12 + 1e-9 相对量），未出现「权重静默退化为 1.0」的失效形态。

**对 2026-11-08 会签条款的更正**：会签第 3 条原写「T08 加权与无权结果**必须有差异**，完全一致即判不通过」。该表述不严谨——加权与无权的差异应看**代价**，不是**跳数**。若两端点之间存在同跳数但置信度不同的两条路，跳数必然相同而代价不同，这是正确行为而非失效。**判据更正为：`weighted_cost_improved_pairs > 0` 且无空权重**。本批满足。

### 3.4 与 11-07 旧基线的差异

| 项 | 情况 |
|---|---|
| BFS 跳数 | 10 对**全部一致**（`baseline_json_hop_differences` 只统计 Dijkstra） |
| Dijkstra 跳数 | 3 对不同：第 **2** 对（旧 2 → 今 1）、第 **7** 对（旧 2 → 今 1）、第 **9** 对（旧 3 → 今 2） |
| 加权路径差异 | 6 对（第 1、3、5、6、8、10 对），全部为「同跳数但代价更低」 |
| 旧 Markdown 声称「4 对加权跳数更大」 | 旧 JSON 实际只有 3 对 —— **旧侧自身文实不符** |
| 旧 JSON 是否可证等价 | 不可：未保存加权路径序列、总代价、公式 |

**判定：接受差异，不返工。** 本批以「自身可复跑（快照 + 脚本 SHA + 源码提交号齐全）+ 独立复核通过」为准。旧材料缺公式、且自述与自身 JSON 矛盾，不具备作为判定基准的资格。

另需说明：跳数变**少**（2→1、3→2）本身不是缺陷——加权目标是最小总代价，代价最小时跳数不必然等于 BFS 最少跳；出现更少跳且更低代价，说明旧基线那 3 对给出的并非真正最优解。

### 3.5 后续口径建议（不阻塞本期）

`1/x` 在小置信度段会被放大：`x → 0` 时 `cost → ∞`，一条低置信边会主导整条路径。本期置信度最小 27.08，尚在安全区；若后续出现置信度 < 5 的边，建议改用有界变换（如 `1 − x/100`）或分档代价。此为口径演进，不在本期改动。
