## 1. 一句话结论

**六条算法里有四条现在就能出结果，一条（社群）卡在字段是空字符串，一条（企业合作网）能跑但数据太碎、结果无意义；四条现存边里 `apply_to` 与 `support` 是完全重复的两条边，必须合并，`participates` 混装了两种语义，必须拆开。**

## 2. 根因一：社群口径三套并存（最容易踩的坑）

| 口径 | 来源 | 数量 | 状态 |
|---|---|---:|---|
| 图内 `tech_point.community_id` | 图库字段 | **0 个有值** | ❌ 全是**空字符串**，不是 NULL |
| 源表 `ads_technology_community_member` | 久新库，每技术点一行 | **1,731 个簇群** | ✅ 有数，未入图 |
| 我方 Louvain 自算 | 本次实跑 | **113 个社群**（基线口径；**2026-11-09 定案 B′ 升级为 resolution 8.0 → 178 个成形社群**） | ✅ 结果在 JSON |

### 2.1 为什么「看起来有值」

实测 `MATCH (v:tech_point) WHERE v.tech_point.community_id IS NOT NULL` 返回 **19,430**（全量）。

原因是字段存的是**空字符串 `''`**，不是 NULL。`IS NOT NULL` 判断为真，但取值是空串。抽样 6 个技术点全部返回 `''`。

**这是本次最隐蔽的一个坑**：任何按 `IS NOT NULL` 写校验的代码都会误报「字段有值」，页面则拿到空串渲染成空白，不报错。

### 2.2 裁定

- **本期验收购社群结果 = 我方 Louvain 自算，定案 B′（2026-11-09 徐滕强确认）：resolution 8.0 → 178 个成形社群（`python-louvain` seed 42）**，跑批结果 `KG-COMPLY-COMM-L01-结果-Bprime-res8.json`；原 res1.0 的 113 簇结果文件（`KG-COMPLY-ACCEPT-L01-算法结果-20261107.json` 的 `433_434_louvain` 段）保留作基线自证，不再作验收口径。
- **源表 1,731 个簇群不是「另一套粗细」，是另一张图上的无关结果**（ARI 0.072；98.7% 伪单点，系久新 HIGH+MEDIUM 子图所致），**不得采用或混用**。详见 [COMM-L01 调研](./KG-COMPLY-COMM-L01-社群口径选型调研与建议.md)。
- **若要用 1,731 那套**：由燕大 LOAD 在灌数时把 `ads_technology_community_member` 写进 `community_id`，属 LOAD 范围，本任务不写库。
- **校验口径修正**：凡判断字段是否有值，一律用 `<> ''`，不得用 `IS NOT NULL`。

## 3. 根因二：`apply_to` 与 `support` 是完全重复的两条边

### 3.1 实测证据

| 边名 | 起点→终点 | 数量 |
|---|---|---:|
| `apply_to` | `policy`→`chain` | 1,678 |
| `apply_to` | `policy`→`segment` | 9,279 |
| `support` | `policy`→`chain` | 1,678 |
| `support` | `policy`→`segment` | 9,279 |

**两组数字逐一相等，端点类型相同。**

更强的一条证据：把两条边按「起点+终点」做连接比对——

```
MATCH (a:policy)-[e1:apply_to]->(b:segment) MATCH (a)-[e2:support]->(b) RETURN count(e1)
→ 9279
```

**结果 9,279，等于 `apply_to`→segment 的全量。即 100% 重合，不是部分重叠。**

抽样对比同一条政策（《重点新材料首批次应用示范指导目录（2018年版）》→新材料）：

- `apply_to`：终点「新材料」，weight 空，props 空；
- `support`：终点「新材料」，weight 空，props 空。

即**同一批数据被灌了两遍，只换了边名**。这会让任何按边名统计的算法重复计数（政策覆盖链数会翻倍）。

### 3.2 语义定位

这组边的实际含义是「**政策适用于哪条产业链 / 哪个环节**」，它**不属于** M01–M24：

- M12–M14 是「政策 `policy_apply_to` **企业 / 人才 / 科研机构**」，图里这三条**0 条边**；
- 所以 `apply_to`(policy→chain/segment) **不能**映射成 M12–M14，否则口径错位。

### 3.3 裁定

| 边 | 处理 | 理由 |
|---|---|---|
| `apply_to` | **保留为唯一有效边**，标注「政策适用范围（参照维度，非 M01–M24 必须边）」 | 与需规动作词一致 |
| `support` | **判为冗余，保留数据但不再读取**；建议 LOAD 后续停灌 | 与 `apply_to` 完全重复，双读会翻倍 |
| M12–M14（policy→企业/人才/机构） | **标为 0 条，本期不验** | 源表 `ads_technology_policy_evidence` 0 行 |

> 是否物理删 `support`：**不删**。按库禁改规矩，既有边一律不动；靠读取口径收口（只读 `apply_to`）。

## 4. 根因三：`participates` 混装两种语义

### 4.1 实测证据

| 起点→终点 | 数量 | 语义 |
|---|---:|---|
| `enterprise`→`segment` | 178,731 | ✅ 对应 M17「企业 participates 产业链环节」 |
| `institution`→`institution` | 34,769 | ❌ **不对应任何 M 编号** |

### 4.2 机构→机构这条为什么不成立

抽样四条：

| 起点 | 终点 | 类型 |
|---|---|---|
| 东莞市诚思生物科技有限公司 | 东莞市一粒米薄膜科技有限公司 | 科技创新服务 |
| 深圳市四海云创科技有限公司 | 深圳市前海中金鼎和金融控股有限公司 | 咨询服务 → 金融服务 |
| 东莞市婴时光硅胶科技有限公司 | 广东京奥科技有限公司 | 科技创新服务 |
| 广东鸿鸿科技有限公司 | 广州市道普科技有限公司 | 科技创新服务 |

两个问题：

1. **`institution` Tag 里装的是「科技创新服务公司」，不是科研机构**。上表四个起点全是「有限公司」。
2. 关系内容是服务/交易类关联，**不是 M02/M19 的「科研机构之间合作」**。

所以：

- **M02 / M19（科研机构↔科研机构合作）= 图里 0 条**，不能拿这 34,769 条充数；
- 这 34,769 条是「服务机构之间的关联」，属 M18 / M21 邻域，但边名 `participates` 用错了。

### 4.3 裁定

| 项 | 处理 |
|---|---|
| `enterprise`→`segment` 的 `participates` | **认定为 M17**，直接可用 |
| `institution`→`institution` 的 `participates` | **不认定为 M02/M19**；建议改名为 `service_relate`（或按陈芸飞报告定名），改名由燕大 LOAD 执行，本任务不写库 |
| M02 / M19 | **标为 0 条，本期不验** |

## 9. 复核方法（任何人可重跑）

连 `10.50.75.136:9669`，`USE demo_gkx_chain`，执行：

```sql
-- 社群字段是空串而非 NULL
MATCH (v:tech_point) RETURN v.tech_point.community_id LIMIT 5;
MATCH (v:tech_point) WHERE v.tech_point.community_id IS NOT NULL RETURN count(v);   -- 19430，误报

-- apply_to 与 support 完全重复
MATCH (a)-[e:apply_to]->(b) RETURN tags(a)[0], tags(b)[0], count(e);
MATCH (a)-[e:support]->(b) RETURN tags(a)[0], tags(b)[0], count(e);

-- participates 混装
MATCH (a)-[e:participates]->(b) RETURN tags(a)[0], tags(b)[0], count(e);

-- belongs_to 覆盖
MATCH (a)-[e:belongs_to]->(b) RETURN tags(a)[0], tags(b)[0], count(e);
```

全部为只读语句，不写任何点边。
