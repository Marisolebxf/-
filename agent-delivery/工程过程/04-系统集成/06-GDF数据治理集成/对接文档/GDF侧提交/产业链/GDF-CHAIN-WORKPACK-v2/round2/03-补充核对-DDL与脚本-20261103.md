## 2. ✅ `relation_id` 超长：已闭环（数据库侧 SHA2 可用）

### 规则原文

`09` §3.3 只给了**两条**路径，**没有提到"截取"**：

| 源字段 | 规则（原文） |
|---|---|
| `relation_id` | `node-rel:{chain_id}:{source_node_id}:{target_node_id}`。**超过 64 字符时改为这段文字的 SHA-256 前 64 位** |

即：正常拼接；超长则整体换成 SHA-256，不存在"截断拼接结果"这种写法。

### 实测：数据库支持，且结果正好 64 字符

| 库 | 版本 | `sha2('x',256)` 长度 |
|---|---|---|
| 源库 `gkx`（SRC_DB） | MySQL 9.7.0-commercial | **64** |
| 目标库 `gkxlumenx_dwd`（EDW_DWD） | MySQL 8.0.39 | **64** |

SHA-256 输出是 32 字节的十六进制串 = **64 个字符**，正好等于 `relation_id varchar(64)` 的宽度。
客户写"前 64 位"其实就是 `SHA2(expr, 256)` 的完整输出，两者一致。

> 之前本条被判为阻塞，是把"平台函数库白名单（29 个函数，无 SHA2）"当成了边界。
> 修正：映射表达式最终下发到数据库执行，**只要数据库支持即可**，平台白名单不构成限制。

### 全量实算：913 条边、82 条走哈希、全部唯一

按 09 规则（同 `chain_id` 内按 `sort_no` 相邻）回源库实算，拉全 1,220 个节点后用 Python 复现：

| 项 | 结果 |
|---|---|
| 节点行 | 1,220 |
| 相邻边 | **913** ✅ 与客户验收数一致 |
| 超 64 字符、需走 SHA-256 | **82**（全部落在 L6/L7） |
| 生成后 `relation_id` 唯一 | **是（913 条全唯一，零重复）** |
| 生成后最大长度 | **64**（正好等于列宽） |

样例：

```
原始: node-rel:INB13030101020101:INB1303010102010101:INB1303010102010102   (72 字符)
哈希: 272d5dd017519d1c713bb68eca6725dcccbdd044cce9958535c750f1739d2c79   (64 字符)
```

### 附带确认：哈希不影响下游

`relation_id` 在包内除 `09` 外只有两处出现，都是**透传**、不反解：

- `10/dwd-chain.md`：列定义 + `uk_rel` 唯一键；
- `script/graph_project.py:301/326/348`：作为 `props.relation_id` 写入图，不用于解析父子关系。

因此用 64 位哈希替代可读串，不会破坏下游。

**结论：这条不需要再问客户，按 `SHA2(concat(...), 256)` 实现即可。**

   GDF 无从判断要改多少。
