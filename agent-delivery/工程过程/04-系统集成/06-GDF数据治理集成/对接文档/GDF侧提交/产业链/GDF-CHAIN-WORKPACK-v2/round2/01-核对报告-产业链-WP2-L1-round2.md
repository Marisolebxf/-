## 2. 链树三个新问题

### 2.1 `node.chain_id` 写"直接父级码"，与列语义冲突（阻塞）

- DDL：`industry_chain_node.chain_id` COMMENT = **'所属产业链主键'**；
- 09 §3.0：`industry_link_code` → `chain_id`「原值。直接父级码」；
- `parent_node_id`：**写 NULL**。

源库实测后果：1,220 个节点里只有 **165 个（L2）** 的父级是 L1 链，其余 **1,055 个（86.5%）** 的父级是**节点**。
即 `chain_id` 会有 1,055 行填的是节点码，指向不到 53 条链中的任何一条；同时 `parent_node_id` 全空。
**结果是树没有了**：既不能按 `chain_id` 归到链，也不能按 `parent_node_id` 还原父子。

这也解释了为什么 `uk_chain_node(chain_id, node_id)` 不会撞——但代价是层级信息全丢。

### 2.2 边改成了"兄弟相邻"，不是父子（阻塞）

09 §3.3 改成：「同一 `chain_id` 内按 `sort_no` 从小到大，**相邻两条节点写一条边**」，验收 913 行。

回源库核：913 = 1,220 节点 − 307 个父组，**数值自洽**，但语义是**同父兄弟之间**的边，不是上下游父子边。
真源父子边应为 **1,055 条**（L3→L2 420、L4→L3 388、L5→L4 142、L6→L5 80、L7→L6 25）。

两点要确认：
- 兄弟相邻为什么等于 `upstream`？`relation_type` 注释是"节点关系类型编码"，兄弟是并列关系；
- round1 前的旧版 09 曾明写「不要 Demo 那种按 sort 相邻伪造 upstream，除非另拍」——现在采用的正是这种。若是"另拍"，请书面确认。

### 2.3 `stage_code` 实际由"同级第几个"决定

`sort_no` = 码末两位 = **同级序号**（1..33）。`stage_code` 按末两位 1–4 / 5–8 / 9+ 切，等于"同级前 4 个算上游"。
回源库分布：`upstream` 958、`midstream` 185、`downstream` 77（合计 1,220）。

这与业务上的"上中下游"是否等价，请确认——若同级节点的排序本就按上下游排，则成立；否则这个字段会误导下游指标。

## 3. `12` 后加工：仍不能配

### 3.1 上图：接口找到了，但状态查询不可靠（阻塞）

**先补一条**：该文档**项目仓库内一直有**（`agent-delivery/designs/亿集知识图谱/亿级科技知识图谱API文档.md`），
`§2.7`（触发）/`§2.9`（查询）/`§2.11`（轮询）都在，随时可查；包内 `23`:64 与 `12`:104 只是没给这条路径。
（待客户改进项：今后在包内写明完整路径，便于 GDF 直接定位。）内容如下：

| 环节 | 接口 | 说明 |
|---|---|---|
| 触发（方式 A） | `POST /api/v1/task-center/trigger` | 内核图谱构建；`entities` 只支持 `paper`/`scholar`/`patent`/`organization` —— **无 chain/segment**，产业链用不了 |
| 触发（方式 B） | `POST /api/v1/workflow-system/definitions/{definition_id}/execute` | **产业链只能走这条**；返回 `EXEC-*` 的 executionId，**不创建 taskId** |
| 查询 | `GET /api/v1/workflow-system/executions/{execution_id}` | 方式 B 的配套查询 |

**但发现两个新问题，都是阻塞级：**

**① 状态查询不是实时状态（决定性）** —— 文档 §2.9 末尾原话：

> 「**当前状态查询限制**：`GET /workflow-system/executions/{execution_id}` 和 `GET /task-center/tasks/{task_id}`
> 读取的是本地 SQLite 中的记录。当前代码**没有在查询时调用 Temporal Describe API，也没有工作流完成回调去持续更新**
> `RUNNING`、`taskStatus`、`output`、`completedAt` 和最终失败堆栈。因此，这两个接口目前属于"下发/任务快照查询"，
> **不是完整的实时运行状态查询**。需要最终运行状态时，应查看 Temporal UI，默认地址 `http://localhost:8233`。」

而 `12` §5.4 写的是「触发 → 轮询状态」两步。**这本身就违反我们的接口验收标准**：
本平台一个作业节点对应一次调用、一个响应，模型里无法保存中间返回值（任务号）、也无法带它再发第二次请求，
**多接口协作在现有模型里表达不出来**。

更糟的是：即使不谈建模，按现有实现也**轮询不到终态**——`RUNNING` 会一直停在 `RUNNING`，
成功/失败永不落库，要看真实终态只能开 Temporal UI（人工页面）。

**要求**：合并为一个原子接口，一次调用完成整步入图并在真正结束时返回终态。

另附文档 §2.10 的状态语义，也印证这点：
- `RUNNING` =「已成功下发给 Temporal。只表示开始运行，**不表示最终成功**」
- `QUEUED` =「Temporal 不可用，仅保存本地待下发记录」→ §2.11 明确要当作"调度服务不可用"，不得进入成功轮询

**② `definition_id`（燕大任务号）仍缺** —— `23`/`12` 写「由燕大配置后线下给 GDF，不进本包」。
这是方式 B 路径里的必填参数，包内没有、文档里也没有（属于燕大侧配置）。

**要客户定**：见 `02-提问清单` §四（问 5–8）与 `04-接口与脚本交付要求.md` §一。
