## 一、背景：为什么必须改

### 1.1 客户口径

- 有数据就跑，没数据就不跑；
- 数据没变的日常批次**直接成功**，不得重跑；
- 只有向量模型变了才需要重跑（该场景**不归日常调度管，独立调脚本**）；
- 全量做法只作临时手段，**必须改造为增量**。

### 1.2 现状：全量，且没有"变没变"的判断

三处证据（均为实读脚本原文）：

| # | 位置 | 原文/行为 |
|---|---|---|
| 1 | `industry_embed.py:365,369` | `SELECT * FROM ... WHERE IFNULL(is_deleted,0)=0` —— **无时间过滤、无批次过滤、无水位** |
| 2 | `industry_embed.py:454-459` | `MilvusHttpStore.rebuild()` = `drop(name)` → `create(name, dim)` → `insert(name, rows)` —— **整库替换** |
| 3 | `industry_embed.py:490-542` | `rebuild()` 每次都 `load_anchors()` 全量 + `embed_texts()` 全量，**不查集合里已有什么** |

**全量体量**（正式库口径，`12` §5.3 第 145 行）：

| 表 | 行数 | 生成锚点 |
|---|---:|---|
| `gkxlumenx_dwd.industry_chain` | 53 | 53 个 `chain:INB*` |
| `gkxlumenx_dwd.industry_chain_node` | 1,220 | 1,220 个 `segment:INB*` |
| **合计** | **1,273** | **1,273 条向量** |

**当前代价**（无变更日也照付）：
- embed 约 40 次 TEI 请求（`1273 ÷ EMBED_BATCH(32)`）；
- Milvus 约 10 次 REST 调用（list + drop + create + 7×insert）；
- **drop+create 秒级窗口**：窗口内 `search` 返 `code≠0`，所以 `12` §4 #6（第 87 行）强制「Job A 与灌链 rebuild 必须串行」，**政策 C1 每天都要为一次"什么都没变"的重建让路**。

## 二、关键约束：为什么不能用时间戳/批次号判变更

这是本方案的**唯一决定性约束**，必须先钉死，否则改造方向会走错。

| 证据 | 原文 |
|---|---|
| `23-核对签收与答复.md:86`（round1 问 15，**客户书面认可**） | 「**认可**。`industry_chain`、`industry_chain_node`、`industry_chain_node_rel` **每次全量清空后重灌**」 |
| `CHANGELOG.md:70` | 「正式库链树两表**清空重灌**（53/1,220）」 |

**推论**：清空重灌意味着**每一行的 `updated_time` / `etl_batch_id` / `valid_from` 每天都会变成新值**。

因此：

| 判据 | 结果 |
|---|---|
| `MAX(updated_time) > 上次水位` | ❌ **每天都成立** → 天天误判"有变更"，退化成每天全量，改造白做 |
| `COUNT(*)` 变化 | ❌ 改一个链名、行数不变 → 漏判 |
| `etl_batch_id` 变化 | ❌ 同上，每天都变 |
| **内容摘要（指纹）** | ✅ 内容没变就一样，**对上游如何写完全免疫** |

**附带好处**：指纹方案**不需要上游 B1 做任何配合**（不需要"内容没变就不刷新时间戳"这类约定），这在客户已定"清空重灌"的前提下是唯一可行路径。

## 三、方案：内容指纹 + 短路

一句话：**给"要被向量化的内容"算一个 sha256 摘要；与集合里存的上次摘要比对，相同就跳过，不同就整库重建。**

### 3.1 指纹字段：只取"真正喂给向量的字段"

这一步不能拍脑袋，必须对着脚本代码抄（`anchor_docs()` 第 310-334 行 + `map_chain_segment_vertices()` 第 190-218 行）：

| 表 | 参与指纹的列 | 依据 |
|---|---|---|
| `industry_chain` | `chain_id`, `chain_name` | `chain_id` 决定 VID（`chain:INB*`）；`chain_name` 决定 embed 文本 |
| `industry_chain_node` | `node_id`, `node_name`, `chain_id` | `node_id` 决定 VID（`segment:INB*`）；`node_name` 决定文本；`chain_id` 用于挂父链名做别名 |

**其余列（`sort_no`/`description`/`status`/`ext`/`created_time`/`updated_time`/`etl_batch_id` 等）全部不进指纹**——它们变了向量不会变，重跑纯属浪费。

> 实测验证（§12 场景⑥）：只改 `sort_no` → 判 `no_change`，0 次写库。

### 3.2 构造算法

```python
FP_VERSION = "fp-v1"          # 指纹算法版本；以后改字段/算法时升它，让全网一次性失效重算
SEP_FIELD  = "\x1f"           # 字段分隔符（Unit Separator，业务数据里不会出现）
SEP_ROW    = "\x1e"           # 行分隔符（Record Separator）

def source_fingerprint(chains, nodes, model_version, dim) -> str:
    h = hashlib.sha256()
    # 模型/维度并入指纹 → 换模型自动触发重建，无需单独判断
    h.update(f"{FP_VERSION}{SEP_FIELD}{model_version}{SEP_FIELD}{dim}".encode())
    # 排序：DB 返回行序不保证稳定，不排序会误判"有变更"
    for r in sorted(chains, key=lambda x: str(x.get("chain_id") or "")):
        h.update((SEP_ROW + "chain" + SEP_FIELD
                  + SEP_FIELD.join(str(r.get(f) or "") for f in ("chain_id", "chain_name"))).encode())
    for r in sorted(nodes, key=lambda x: str(x.get("node_id") or "")):
        h.update((SEP_ROW + "segment" + SEP_FIELD
                  + SEP_FIELD.join(str(r.get(f) or "") for f in ("node_id", "node_name", "chain_id"))).encode())
    return h.hexdigest()      # 64 位十六进制
```

三个细节都是必需的：

| 细节 | 不加的后果 |
|---|---|
| **排序** | MySQL 不加 `ORDER BY` 时行序不保证，第二天顺序一变指纹就变 → 天天误判 |
| **`\x1f` 分隔字段** | 实测：`('ab','c')` 与 `('a','bc')` 无分隔符都拼成 `abc` → **撞车**，两组不同数据得同一指纹 |
| **`\x1e` 分隔行** | 同理，防"上一行末尾 + 下一行开头"拼出相同字节流 |
| **并入 `model_version` + `dim`** | 换模型/换维度时向量全失效，必须重建；并进来即自动触发 |
| **`FP_VERSION`** | 指纹算法本身升级时，靠它让所有环境一次性失效，避免新旧指纹格式不可比 |

### 3.3 状态存放：写在集合自身，零外部状态

全量 rebuild 时，每行附带同一指纹：

```python
rows = [{..., "source_fingerprint": fp, ...} for d in docs]
```

下次跑时**只读一条**回来比对：

```jsonc
POST /v2/vectordb/entities/query
{"dbName":"gkxlumen","collectionName":"gkxlumen_industry_anchor",
 "filter":"kind == \"chain\"","outputFields":["source_fingerprint","index_version"],"limit":1}
```

**好处：状态与索引共存亡。** 集合被 drop → 指纹也一起没了 → 下次必然判"需重建"，不会出现"状态说有索引、实际没有"的不一致。无需新建状态表。

### 3.4 判定表（只有 4 种结果）

| 情形 | 判定 | 动作 |
|---|---|---|
| ① 集合不存在 / 空集合 / 无该字段 | `first_run` | 全量 rebuild |
| ② 指纹一致 | **`no_change`** | **直接成功**：不 embed、不写库、不 drop |
| ③ 指纹不一致（值改了 / 增行 / 删行 / 换模型 / 换维度） | `source_changed` | 全量 rebuild |
| ④ query 报错（Milvus 不通等） | fail-safe | 按"有变更"处理，走 rebuild；rebuild 也失败才算真失败 |

④ 是 **fail-safe（失败安全）**：读不到状态时宁可多跑一次全量，也**不能**误判成"没变"而长期静默不更新。该方向错误代价小（多跑几秒），反方向代价大（索引永久停留旧版且无人知晓）。

### 3.5 完整流程

```text
每日批：Wave B CHAIN-B1-TREE success
  ↓
读 DWD 两表（沿用现有两条 SQL）→ 现算 fp
  ↓
query 集合读 stored_fp（1 次读，不写）
  ↓
fp == stored_fp ? ──是──→ 回执 result=no_change，index_version 沿用旧值，结束（0 次写库）
  │
  否
  ↓
embed 1,273 条 → drop + create + insert（现有全量路径，一行不改）→ 回执 result=rebuild
  ↓
仅 rebuild 实际执行日：与政策 Job A 串行（drop 窗口）
```

## 四、删除如何处理：天然覆盖，不需要 delete 接口

这是本方案相比"增量 upsert/delete"的最大优势：

| 变化 | 指纹 | 处理 |
|---|---|---|
| 某链/节点被删除（行消失，或 `is_deleted=1` 被 SQL 滤掉） | 变化 | 走全量 rebuild → **新集合里自然没有该锚点** |
| 某链/节点改名 | 变化 | 全量 rebuild，写入新向量 |
| 新增行 | 变化 | 全量 rebuild |

**因此不需要 Milvus 的 `entities/delete`，也不需要 `entities/upsert`。** 删除语义由"整库替换"直接保证，零额外风险。

## 五、模型变更如何处理

客户口径：「模型变了要重跑，**这种全量重跑不归日常调度管，一个 vota 实例不可能既管增量又管全量，可独立调脚本实现**」。

两种落法，**建议按 5.1**：

### 5.1 并入指纹（推荐，零成本）

因为 `model_version` + `dim` 已并入 fingerprint 公式（§3.2），换模型后指纹必然不同 → 下一次日常批次**自动**走 rebuild。不需要人工记得去跑脚本，也不会长期停在旧模型。

### 5.2 完全隔离（若客户坚持"调用方不判模型"）

把 `model_version`/`dim` 从指纹里去掉，模型变更**只**由独立脚本触发。代价：若有人忘了跑，索引会长期停留旧模型且日常批次永远显示 `no_change`，**没有任何告警**。

> **注**：无论哪种，**维度（dim）变更必须走 drop+create**——Milvus 集合维度不可变，这是硬约束。

## 六、回执语义：需客户拍板（1 项）

改增量后，`skip` 会同时代表两件**性质完全相反**的事：

| 情形 | 索引实际状态 | 写成 `skip` 是否恰当 |
|---|---|---|
| **失败**跳过 | 可能沿用旧版，也可能已 drop 一半 | ✅ 恰当，下游应警惕 |
| **无变更**空跑 | **完全有效，就是最新版** | ❌ 不当，下游会误判成"索引没建/不可信" |

现行 `12` §4 #5、§6（第 45、171 行）只规定了「跳过时诚实写 `skip`」，未区分这两种。

**两个可选方案：**

| 方案 | 内容 | 影响 |
|---|---|---|
| **① 推荐** | 无变更时回执 `result=no_change` + **上一版真实 `index_version`**；只有真失败才写 `skip` | 语义最准；`12` 需加一条 |
| ② | 两者都写 `skip`，另加 `reason` 区分 | 改动小，但下游要同步改判定逻辑 |

**此条不定，增量方案的回执无法签字。**

## 八、另发现：2 处静默降级 + 1 个自检陷阱（建议一并修）

改造时如果不同时处理这几条，"跑通 `code=0`"依然可能是假成功。

### 8.1 `EMBED_BASE_URL` 漏配 → 写入无意义向量，且**无法从返回值识别**

`embed_texts()`（第 290-298 行）：

```python
if not _env("EMBED_BASE_URL"):
    return [_hashgram(str(t or ""), dim) for t in texts]   # 静默退化为字符 n-gram 哈希
```

**实测证据**（用一个正常返回的假 Milvus 承接，故意不配 TEI）：

```
code= 0  degraded= False  store= milvus  model_version= bge-base-zh-v1.5-tei-1.8.3
前 5 维 = [0.0, 0.2209, 0.0, 0.0, 0.0]     ← hashgram 产物，不是 bge 语义向量
返回字段 = collection, store, db_name, model_version, dim, metric_type,
           trace_id, indexed, index_version, kinds, degraded   ← 无一个字段能识别
```

**这是最危险的一条**：`store=milvus`、`degraded=false`、`model_version` 还报着 `bge-base-zh-v1.5-tei-1.8.3`（第 115-117 行是纯环境默认值，与实际用的向量化后端无关）。索引写进去了、条数也对、**检索全是噪声**。

→ **建议**：返回值增加 `embed_backend: "tei" | "hashgram"`，并把缺失 `EMBED_BASE_URL` 改为 `error`。

### 8.2 `MILVUS_URI` 漏配 → 写内存，`code=0`

`open_store()`（第 483-485 行）：空则返回 `MemoryStore`。

实测：`{"code":0, "data":{"store":"memory","degraded":true,"indexed":2,...}}`
→ 可被 `data.store == "milvus"` 拦住，但仍建议改为缺参直接 `error`。

### 8.3 自检陷阱：`python industry_embed.py` **一条数据都不写**

`__main__`（第 619-620 行）执行的是 `_self_check()`，实测输出：

```
$ python3 industry_embed.py
industry_embed self-check OK     (exit=0)
```

**自检通过 ≠ 灌了库。** 平台作业必须按**函数入口 `rebuild`** 配置；若平台只能跑脚本，需外层包一个调用 `rebuild()` 的入口。建议在脚本里加一个显式 CLI 子命令（如 `--rebuild`），避免配错。

## 十二、附：实测证据

### 12.1 指纹判定矩阵（本地实跑，复用真实 `anchor_docs`，不连任何库）

```
① 首次运行（集合里没有指纹）             → rebuild   reason=first_run       indexed=4  累计写库=1
② 只变 时间戳/批次/说明/行序（向量不变）   → no_change reason=source_unchanged indexed=0  累计写库=1  ← 没写库
③ 改 node_name（影响 embed 文本）        → rebuild   reason=source_changed  indexed=4  累计写库=2
④ 删掉一个节点行                         → rebuild   reason=source_changed  indexed=3  累计写库=3
⑤ 新增一个节点行                         → rebuild   reason=source_changed  indexed=5  累计写库=4
⑥ 只改 sort_no（不参与 embed）           → no_change reason=source_unchanged indexed=0  累计写库=4  ← 没写库
⑦ 换向量模型                             → rebuild   reason=source_changed  indexed=5  累计写库=5
```

**② 是核心验证**：时间戳、批次号、说明文字全变、行序还打乱，但指纹不变 → 判 `no_change`，一次库都没写。

### 12.2 分隔符必要性

```
无分隔符：('ab','c') 拼成 'abc'；('a','bc') 拼成 'abc' → 相同！撞车
有分隔符：('ab','c') → 'ab\x1fc'；('a','bc') → 'a\x1fbc' → 不同 ✅
```

### 12.3 指纹字段 = 实际被 embed 的文本来源

```
vid=chain:INB1303          text='半导体与集成电路 半导体 集成电路'
vid=chain:INB130301        text='半导体材料'
vid=segment:INB1303010101  text='硅材料 半导体材料'
```

（`text` = `name` + 别名，别名来自拆词与父链名，全部由 §3.1 那 5 个字段决定）
