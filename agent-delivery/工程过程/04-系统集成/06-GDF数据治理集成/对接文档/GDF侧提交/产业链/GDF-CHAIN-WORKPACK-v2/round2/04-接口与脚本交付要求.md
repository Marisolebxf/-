# 接口与脚本交付要求（GDF 侧硬性验收标准）

> 适用：本包 `12` 后加工，以及今后所有要求 GDF 调用接口或配置脚本的派单包。
> 结论先行：**按现交付形态，这两项都不满足，需客户调整。**
> 依据：`12` §5.1/§5.4（接口）、`script/industry_embed.py` / `script/graph_project.py`（脚本）。

---

## 一、接口：只接受一个原子接口，不接受多接口共同完成一个任务

### 要求

**一个业务动作 = 一个原子接口。** 该接口被调用后自行完成全部内部动作，并在真正结束时返回结果。

**不接受**任何需要多个接口配合才能完成一个任务的形态（典型如「先调触发接口拿任务号，再调查询接口取状态」）。

### 为什么：本平台无法在同一个模型里处理多接口

GDF 的作业节点与映射模型，**一个节点对应一次调用、一个响应**。这是平台的编排基本单位：

- 节点只表达「发一次请求、等一次响应、按响应结果往下走」；
- 模型里没有"保存中间返回值（任务号）→ 带它再发第二次请求 → 按返回的进度决定是否再发第三次"这种结构；
- 中间状态（任务号、进度、重试次数）没有地方持久化，也就无法在失败后恢复、无法重试、无法对账。

所以多接口协作不是"麻烦一点"，而是**在现有模型里根本表达不出来**。

| 我们要的（可建模） | 不要的（无法建模） |
|---|---|
| 一个接口，调用后完成全部内部动作，返回终态 + 结果字段 | 接口 A 返回 `taskId/executionId`，GDF 再调接口 B 取状态 |
| 成功/失败/跳过 三态在**同一个响应体**里表达 | 状态分散在另一个接口，且需要按返回内容决定下次调用 |
| 超时与幂等由接口自己保证 | 由调用方靠时间窗口、外部锁、轮询频率规避 |

### 本包的现状：违反

`12` §5.4 的编排原文：

```text
→ GDF 调用引擎入图调度任务的触发接口（立刻得到已收下 + 任务号）
→ GDF 轮询任务状态，直到成功或失败
```

这是典型的两步模式。而且雪上加霜：《亿级科技知识图谱API文档》§2.9 自述：

> 「这两个接口读取本地 SQLite 快照，**没有在工作流完成时更新状态**……**不是完整的实时运行状态查询**。
> 需要最终运行状态时，应查看 Temporal UI。」

**即：按现实现，GDF 靠查询接口永远拿不到终态。** 这已经不只是"多一个接口"的问题——
它连"用两个接口拼出一个结果"都做不到，完全无法在模型里表达。

### 要求客户提供

| # | 内容 |
|---|---|
| 1 | 一个**原子入图接口**：一次调用完成整步入图，并在真正结束时返回 |
| 2 | 响应体包含：终态（成功/失败/跳过）、失败原因、写入点数或可判定的结果标识 |
| 3 | 明确超时上限（GDF 侧按此设置节点超时）、是否支持幂等重试 |
| 4 | 若引擎侧暂时做不到阻塞，**至少也要合并成一个接口**（同步执行完再返回），而不是拆成两个 |
| 5 | 完整路径或接口文档随包给出（本包《亿级科技知识图谱API文档》在项目内可查，但包内未给路径） |

## 二、脚本：可变项必须提取为环境变量，不得写死在代码里

### 要求

脚本交给 GDF 后，**GDF 只允许通过环境变量/配置项切换环境**，不允许改代码。
凡是会随环境变化的值，一律不得硬编码。

**必须参数化的最小集合**：

| 类别 | 具体项 |
|---|---|
| 库与 schema | 数据库名（Milvus 库名 / MySQL 库名）、schema 名 |
| 表与集合 | 表名、集合名（含前缀与后缀） |
| 地址与凭据 | 服务地址、端口、口令、Token |
| 模型相关 | 模型名、向量维度、度量方式、模型版本号 |
| 行为参数 | 批大小、重试次数、超时 |

**判定标准**：把脚本拿到另一个环境（库名不同、schema 不同、集合名不同），**不改一行代码即可运行**。

### 本包的现状：违反（逐项）

#### `script/industry_embed.py`

| 行 | 硬编码内容 | 是否可配 | 影响 |
|---|---|---|---|

| 36 | `DEFAULT_COLLECTION_SUFFIX = "anchor"` | ❌ | 集合名后缀写死；只有前缀能改（`MILVUS_COLLECTION_PREFIX`） |

| 227–228 | schema 取自 `db.dwd`（`connect_chain_readonly()` 内部） | ❌ | schema 不可配，且该函数是 demo 闸门，非 demo 库直接拒 |
| 39 | `DIM = 768` | ❌ | 换模型就要改代码 |
| 38 | `METRIC_TYPE = "COSINE"` | ❌ | 同上 |
| 42 | `MODEL_VERSION = "bge-base-zh-v1.5-tei-1.8.3"` | ❌ | 同上 |
| 45 | `QUERY_PREFIX = "为这个句子生成表示…"` | ❌ | 模型相关的检索指令前缀 |

已经参数化的（这部分是好的）：`MILVUS_URI`、`MILVUS_COLLECTION_PREFIX`、`MILVUS_TOKEN`、
`EMBED_BASE_URL`、`EMBED_MODEL`、`EMBED_API_KEY`。

更根本的问题：`script/README.md` 现在的做法是**让 GDF 手工改代码**（"副本里有两处还是 demo，配到 GDF 平台时先改掉"），
这本身就是本条要求要禁止的形态。**改源码 = 每个环境一份私有副本 = 后续无法统一升级。**

> 代码里**正式空间 `gkx_chain` 是被显式拒绝的**（`FORMAL_SPACE = "gkx_chain"` 用于拒绝判断）。
> 客户答复说"正式图空间 `gkx_chain`"，与该实现相反，需确认正式化改造的进度。

### 要求客户提供

| # | 内容 |
|---|---|
| 1 | 一份**参数清单**：运行该脚本需要的全部环境变量名、含义、示例值、是否必填 |
| 2 | 脚本改为**全部从环境变量读取**，交付即可运行，**GDF 不改一行代码** |
| 3 | 若某项确实不愿外提（如模型版本），需书面说明理由，并保证换环境时不需要改 |
| 4 | 附带 `lumen_common` 等私有依赖（或给出可安装的包名/版本），否则脚本无法运行 |

## 三、这两条的文件落点

| 要求 | 落在哪个文件 | 状态 |
|---|---|---|
| 接口原子化 | `12` §5.1/§5.4（现为触发+查询两步） | ❌ 需合并为一个 |
| 脚本参数化 | `script/industry_embed.py` + `script/README.md`（现要求 GDF 改代码） | ❌ 需改写 |

**验收口径**：GDF 侧只做两件事——配环境变量、配一个原子接口地址。
任何需要 GDF 改代码、或需要多个接口配合才能完成一个任务的交付，一律退回。
