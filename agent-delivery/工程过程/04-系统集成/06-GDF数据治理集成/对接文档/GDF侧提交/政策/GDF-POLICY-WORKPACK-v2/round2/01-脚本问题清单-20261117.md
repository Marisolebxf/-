## 1. 🔴 退出码 7 被平台判成「作业失败」

### 现象

两个作业在平台上都是 **`Run Failed`**，但日志显示它们正常跑完、正常写出数据：

```
[21:00:05] done rounds=29 processed=2900 written=401 skipped=2499 stopped=deadline batch=20261116165516
[21:00:05] 脚本退出码 7，耗时 14688334ms
```

```
[17:23:46] done rounds=5 processed=100 written=43 skipped=57 stopped=max_rounds batch=20261116170943
[17:23:46] 脚本退出码 7，耗时 843147ms
```

C1、C2 两个节点状态：

```
Run Failed   SCRIPT_RUN_CDC.POLICY-C1<MainJob>
Run Failed   SCRIPT_RUN_CDC.POLICY-C2<MainJob>
Run OK       SCRIPT_RUN_CDC.CHAIN-VEC(Mirror)<MainJob>
```

### 根因：两份约定互相冲突

**政策派单包 `12` 号文规定**（原文）：

> 退出码 0 表示本批已追平。**退出码 7 表示还没追平，要再调度，不算作业失败**，也不回滚 B。退出码 1、2、3、4 才记该作业失败。

`15` 号文同样表述：「退出码 7 是未追平，再调度，**不记失败**」。

**但 GDF 执行器 `JG_RUN_SCRIPT_EXEC` 的判据是「非 0 即失败」**（源码实读）：

```java
if (code.intValue() != 0)
    throw new Exception("脚本退出码 " + code + "（非 0 即失败），详见上方运行日志");
```

两者直接冲突：脚本按设计返回 7 表示「未追平但正常」，执行器把所有非 0 一律抛异常 → 节点 `Run Failed`。

### 为什么每天必现

只要当天待处理量超过单次配额，就必然撞上限、必然退 7：

- **C1**：4 万条政策积压，单次 `--deadline-sec 14400`（4 小时）约处理 2,900 条 → 撞 deadline → 退 7
- **C2**：单次配额 `--limit 20 --max-rounds 5`（100 条）< 积压量 → 撞 `max_rounds` → 退 7

**除非某天待处理量小到一轮跑完（即追平），否则天天退 7、天天挂红。**

> 注：C2 单次配额偏小属**我方运行参数设置**（脚本支持更大值），不是脚本缺陷；
> 配额小只是让它更早撞上限，**即使调大配额，只要没追平仍会退 7**——本条的实质仍是退出码语义冲突。

### 影响

1. 平台上 C1/C2 常红，真实故障（退出码 1/3/4）被淹没在"日常红"里，失去告警价值
2. 如果投产侧配了失败重试或失败告警，会按错误信号动作
3. 下游若按「上游失败」判定，可能被误阻断
4. 交接验收时「节点成功」这一条永远过不了

### 建议（三选一，需与平台侧共同定）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 脚本把「未追平」也返回 **0**，改为在 stdout 打一行结构化标记 `POLICY_RESULT {"stopped":"deadline","processed":2900,...}`，由平台按该行判断是否再调度 | 要改客户只读脚本；退出码语义变化需客户确认 |
| **B** | GDF 侧配置**退出码白名单**：允许 7 视为成功（在 `SCRIPT_RUN_CDC` 增加「可接受退出码」属性，执行器按清单判定） | 要改平台 SUDF 与结构；影响面覆盖所有脚本作业，需回归 |
| **C** | 保持现状，在投产侧把 C1/C2 标记为「允许失败」节点 | 最省事，但"失败"信号永久失效，真故障也看不见 |

> 我倾向 **A**：语义最清楚，改动只在脚本一处，且不污染其它脚本作业。但脚本是客户只读原件，需客户点头。

## 2. 🔴 `no_match` 锁 30 天，锚点补齐后不会重跑

### 现象

C1 每判定一条「没有过线链码」，就写状态并设 30 天冷却（源码实读）：

```python
RETRY_NO_MATCH_DAYS = 30
...
save_state(..., "no_match", ..., retry_days=RETRY_NO_MATCH_DAYS)
```

待办筛选条件同时把这类行排除：

```sql
AND NOT EXISTS (SELECT 1 FROM script_state s
  WHERE s.job='c1' AND s.policy_id=p.policy_id AND s.content_hash=<hash>
    AND (s.next_try_at IS NULL OR s.next_try_at > NOW()))
```

### 当前锁定情况

```
job  status      count   locked
c1   no_match   2,756   2,756    ← 全部锁着
```

其中 **257 条是 2026-11-02 判的**（该日三个批次：248 + 1 + 8），当时产业链锚点集合还是**空的**（入向量库第一次成功灌数是 2026-11-16 14:29）。这批属于**已过时的错判**，但要等到 **2026-12-02** 才重试。

对比可见今日批次的量级完全不是一个数量级：

```
c1  2026-11-02 及更早：done 55 / no_match 257
c1  2026-11-16 今日批：done 401 / no_match 2,499
```

### 为什么这是问题

判定依据会变，但冷却期不会重置：

| 触发条件 | 现状 |
|---|---|
| 产业链扩链（53 链 → 更多）、锚点重灌 | `no_match` 不会失效，仍锁 30 天 |
| 阈值调整（0.55 / 0.45 改动） | 同上 |
| 嵌入模型升级 | 同上 |

结果：**业务事实没变，但结论该更新了，而系统按 30 天前的判断继续跳过。**

### 建议

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 状态表增记 `anchor_version`（锚点集合的 `index_version`）。判 `no_match` 时一并存下；待办筛选时，`anchor_version` 与当前索引版本不一致则视为可重试 | 改脚本 + 改状态表 DDL；客户确认 |
| **B** | 缩短 `RETRY_NO_MATCH_DAYS`（如 30 → 7） | 一行常改，成本最低；但重试次数上升，embed 开销增加 |
| **C（临时）** | 一次性清理：`UPDATE script_state SET next_try_at=NULL WHERE job='c1' AND status='no_match' AND next_try_at>NOW()` | 立即见效，但下次扩链还会重犯 |

## 3. 🟡 `no_match` 日志不打分数，无法区分原因

### 现象

日志只有一行，没有分数、没有候选：

```
[2026-11-16 17:01:28,764] 18319032 no_match 不写，已记状态
```

`no_match` 可能由两种完全不同的原因造成，但日志看起来一模一样：

| 真实原因 | 实测例子 | 该做什么 |
|---|---|---|
| **差得远**（锚点覆盖不到这个产业） | 「免征车辆购置税的新能源汽车车型目录」→ top1 `其他集成电路材料` **0.3506** | 该**扩锚点/扩链** |
| **差一点点**（阈值卡住） | 「道路机动车辆生产企业及产品（第304批）」→ `汽车整车` **0.4480**，阈值 0.45 | 该**讨论阈值** |

我为了区分这两种，额外跑了一次只读实测才得出结论——**靠日志本身分不出来**。

### 建议

把 `no_match` 那行改成带证据：

```
18319032 no_match top1=其他集成电路材料(0.3506) top2=改良型新药(0.3477) chunks=3
```

理由：
- 不泄露敏感信息（都是公开产业名）
- 运维一眼能看出「是该扩链还是该调阈值」
- 只改 `print` 一行，不动业务逻辑

## 4. 🟡 产业锚点覆盖不足（数据侧，非脚本缺陷）

### 现象

C1 命中率约 **13.8%**（401 / 2,900）。抽查根因是**锚点范围不够**，不是脚本判错：

```
gkxlumenx_dwd.industry_chain  53 条链
gkxlumenx_dwd.industry_chain_node  1,220 条环节
```

政策语料覆盖税收、人才、土地、无线电、道路机动、医药等，而产业锚点只有 53 条链的粒度。

实测对照：

| 查什么 | 结果 |
|---|---|
| `chain_name like '%汽车%'` | 只有「智能网联汽车」「智能网联汽车零部件」**两条** |
| 检索「新能源汽车」 | top1 `智能网联汽车` **0.5124**（< 0.55） |
| 检索「集成电路」 | top1 `集成电路` **0.7655** ✅ |

「新能源汽车」这样的主流产业**不在 53 条链里**，所以政策自然对不上。

### 性质说明

这是**数据覆盖问题，不是脚本 bug**。脚本按规则判 `no_match` 完全正确。

但要提醒：**这条不解决，C1 命中率会长期卡在 10% 出头**，与问题 3（锁定 30 天）叠加后，补数据的收益要等一个月才体现。

### 建议

| 顺序 | 动作 |
|---|---|
| 1 | 与产业链包确认：53 链是否就是最终粒度，是否需要按政策语料常用产业扩链 |
| 2 | 扩链后重灌锚点（`CHAIN-VEC` 会自动判 `source_changed` 并重建，已支持增量） |
| 3 | 同时处理问题 3（让 `no_match` 随锚点版本失效），否则扩完还得等 30 天 |
