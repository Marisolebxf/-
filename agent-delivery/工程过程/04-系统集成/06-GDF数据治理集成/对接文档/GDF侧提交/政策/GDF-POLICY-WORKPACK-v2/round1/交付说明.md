## 三、为什么要改（改了才有法上调度）

原脚本单独跑没问题，但要放进每天的调度里跑，有 4 个问题会导致「看起来正常、实际没干活」。

### 问题 1：做不出结果的政策会永久卡住队头 ⚠️ 最严重

原逻辑用「目标表有没有非空链码」判断增量。但检索失败、没有过线、正文切不出块的行，**库里一个字都不写**，下一轮又被选中。

**我们在真实数据上验证过**（4 万条政策，连续跑 3 轮）：

```
第 1 轮：18318860 检索失败，不写 → 本轮产出 0 → 退出码 0
第 2 轮：18318860 检索失败，不写 → 本轮产出 0 → 退出码 0
第 3 轮：18318860 检索失败，不写 → 本轮产出 0 → 退出码 0
                                    ↑ 永远是同一条，永远不前进
```

**实际后果**：调度每天跑、每天退出码 0、每天日志显示「完成」，但一条产业都没抽出来。
按 `--limit 100` 跑，就是永久卡在头部 100 条。

**改法**：新增状态表，每条政策处理完都记一行（不管有没有产出）。下一轮自动跳过，真正往后走。

改后同样的环境和跑法：
```
第 1 趟：18318860 记状态 → 18318861 记状态
第 2 趟：18318862 记状态 → 18318863 记状态   ← 推进了
```

### 问题 2：C2 正文改了也不重算

原脚本算了内容哈希、也存进了 `clause_meta`，但**判断跳过时压根没看这个哈希**：

```python
if existing and not force:
    return None          # 有条款就跳过，正文改了也不管
```

**改法**：加一个条件——有条款**并且**哈希相同才跳过。正文一变就自动重算，正文没变一律不碰模型（这是省 token 的关键）。

### 问题 3：缺配置时静默空跑

`EMBED_BASE_URL` 为空时，C1 会去 POST 到 `空地址/v1/embeddings`，每条都失败，**但退出码仍然是 0**。

**改法**：启动前检查，缺了直接退出码 3 并说清楚缺哪个。C2 的模型配置不做强制（规则路径仍能出数）。

### 问题 4：`--force` 不限定范围会全表重烧

`--force` 不带 `--policy-id` 时，等于把 4 万条全部重算一遍（C1 重烧 embedding、C2 重烧模型）。

**改法**：`--force` 必须配 `--policy-id`，否则拒绝执行（退出码 2）。

| 码 | 含义 |
|---|---|
| **0** | 本批已追平（没有待处理的了） |
| **1** | 未捕获异常（真出错，不做业务重试） |
| **2** | 参数错误 |

## 五、状态表说明

新建一张表 `gkxlumenx_dwd.script_state`，**不改你们任何现有表**。

```sql
CREATE TABLE `gkxlumenx_dwd`.`script_state` (
  `job`          varchar(16)  NOT NULL,   -- c1 / c2
  `policy_id`    varchar(100) COLLATE utf8mb4_0900_ai_ci NOT NULL,
  `content_hash` varchar(32)  NOT NULL DEFAULT '',
  `status`       varchar(20)  NOT NULL,   -- done|empty|no_match|degraded|failed|llm_unavailable
  `batch_id`     varchar(32)  NOT NULL DEFAULT '',
  `tried_at`     datetime     NOT NULL,
  `next_try_at`  datetime     DEFAULT NULL,  -- NULL = 终态，不再自动重试
  `try_count`    int          NOT NULL DEFAULT 0,
  `note`         varchar(500) NOT NULL DEFAULT '',
  PRIMARY KEY (`job`,`policy_id`),
  KEY `idx_job_due` (`job`,`next_try_at`,`policy_id`),
  KEY `idx_job_status` (`job`,`status`)
);
```

### ⚠️ 建表必须注意 collation

`policy_id` 的 collation **必须与 `gkxlumenx_dwd.policy_base_info.policy_id` 一致**。

我们踩过这个坑：两边 collation 不同时，两个 `policy_id` 列互相比较会直接报错：

```
ERROR 1267 (HY000): Illegal mix of collations
(utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_general_ci,IMPLICIT) for operation '='
```

当前 `policy_base_info.policy_id` 是 `utf8mb4_0900_ai_ci`，DDL 里已按这个写。
如果你们后续调整了主表的 collation，这张表要同步改。

### 重试策略

| status | 含义 | 下次重试 |
|---|---|---|
| `done` | 已产出 | 不再重试（除非内容变了） |
| `empty` | 无可用正文/切块 | +30 天复核 |
| `no_match` | 检索有返回但不过线 | +30 天复核 |
| `degraded` | embedding/Milvus 调用失败 | **+60 分钟** |
| `failed` | 单条异常 | +60 分钟，连 5 次转终态 |
| `llm_unavailable` | 规则切不开且未配模型 | 不自动重试（配好模型后手动放开） |

C1 的产业识别完全依赖这个集合，**它不在交付物里，也不是脚本能自己建的**：

| 项 | 要求 |
|---|---|
| 集合名 | `gkxlumen_industry_anchor`（或告知实际名称） |
| 是否已有数据 | **必须已有锚点数据**。空集合会导致每条政策都「没匹配」，产出为零但退出码正常 |

## 八、其他需要你们确认的事项

### 🔴 必须先解决，否则跑不起来

**1. Milvus 锚点集合的三个技术参数**

C1 全靠集合 `gkxlumen_industry_anchor`。请确认：

| # | 项 | 为什么必须确认 |
|---|---|---|
| a | **距离度量必须是 `IP` 或 `COSINE`** | 脚本把 `distance` 当「越大越相似」（阈值 ≥0.55 / ≥0.45）。如果集合是按 **L2** 建的，越相似值越小，**阈值方向完全相反**——而且跑起来不报错，只是结果全错 |
| b | **向量维度 768，且与灌库时用的模型一致** | 不一致则每条被丢弃 |
| c | **集合里已有锚点数据，且是谁灌的、怎么验收的** | 集合为空时每条都「没匹配」，产出为零但退出码正常 |

另外：**查询用的 embedding 模型必须与当初灌锚点用的是同一个**，否则两边向量空间不同，检索结果没有意义。

**2. 确认 `policy_support` 这一列应该是什么**

我们查了 4 万条，这一列**全都是文本 `'null'`**（不是 SQL NULL，也不是 JSON）。

影响：C2 的「要素抬升」路径（从适用对象/支持方式/申报条件直接生成一条条款）完全走不通，只能靠规则切分和模型兜底。

请确认：这一列本来就没结构化要素（那属正常），还是应该有但没同步过来？

### 🟡 建议做，影响质量与幂等

**3. 索引与唯一键**

现在的情况：

| 表 | 缺什么 | 影响 |
|---|---|---|
| `gkxlumenx_ads.policy_text_parse` | `policy_id` **无索引**（longtext） | C2 每条都全表扫；一旦有重复行，更新只打第一行、其余静默残留 |
| `policy_industry_rel`（DWD/ADS） | 无 `(policy_id, industry_link_code)` 唯一键 | 人工重跑与调度撞车时可能产生重复行 |
| `policy_base_info` | 无单列 `policy_id` 索引 | 主键是 `(source_plane, policy_id)`，单列查询用不上 |

建议（需要你们同意改表）：

```sql
ALTER TABLE gkxlumenx_dwd.policy_industry_rel
  ADD UNIQUE KEY uk_pid_code (policy_id, industry_link_code);
ALTER TABLE gkxlumenx_ads.policy_industry_rel
  ADD UNIQUE KEY uk_pid_code (policy_id, industry_link_code);
ALTER TABLE gkxlumenx_ads.policy_text_parse
  ADD UNIQUE KEY uk_ptp_pid (policy_id(64));
ALTER TABLE gkxlumenx_dwd.policy_base_info
  ADD KEY idx_pid (policy_id);
```

> ⚠️ 加唯一键**前必须先查重**（现网有历史数据）。清重口径请你们定：
> ```sql
> SELECT policy_id, industry_link_code, COUNT(*) FROM gkxlumenx_dwd.policy_industry_rel
> GROUP BY 1,2 HAVING COUNT(*)>1;
> ```

**4. 源侧删除后，目标表怎么办**

现在源表里 `is_deleted=1` 或 `is_history=1` 的政策不会进待办，但目标表里的旧行**仍标记为有效**。

我们建议的默认规则（不需要新增表）：

- **C1**：每趟先做一次补偿软删——源行已删但 `policy_industry_rel` 还有有效行 → 置 `is_deleted=1` 并同步 ADS；
- **C2**：条款是历史解析产物，**保留不删**，只在状态表备注，下游按主表过滤。

请确认是否采用。

## 十一、你们后续升级脚本时怎么办

你们的脚本如果出新版，我们的改造需要同步。因为**业务逻辑和运行层是分开的**，合并成本很低：

1. 把新版与旧版 `diff` 一下，只看业务逻辑改了什么；
2. 把本文第四节的 9 项运行层改动重新贴到新版（都是固定模式，不掺业务）；
3. 跑 `--self-check`（已覆盖增量语义）；
4. 用 `--limit 5` 小批试跑，比对状态表变化。

我们这边可以随时协助合并。
