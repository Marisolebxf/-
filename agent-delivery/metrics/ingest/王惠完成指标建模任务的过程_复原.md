## 0. 文档定位

本文件回答三类问题：

1. 王惠做指标建模时，每一步从哪里取信息、按什么顺序、得到什么中间产物。
2. 最终《XX模型指标字段清单.xlsx》每一列应填什么、怎么判定对错。

## 2. 总体流程

逆向工程原文把步骤编号写成了“1、2、4、5”，实际是四段工作内容。本文件按顺序规范为 1-5 五步，其中把“数据库调研”和“对齐状态判定”拆成独立步骤，便于复用。

| 步骤 | 名称 | 主要输入 | 主要输出 |
|---|---|---|---|
| 第 1 步 | 调研原型 UI 上的指标及依赖指标 | `repos/demo-ui-topic` 页面/组件/代码 | 指标层级草表（指标ID、模块、指标一级/二级/三级） |
| 第 2 步 | 对照需求文档补齐口径、公式和依赖指标 | `科技专题服务算法库.md` 及需求文档 | 口径定义、计算逻辑说明、计算公式 md |
| 第 3 步 | 调研 MySQL 数据支撑度 | `database_env.yaml`、`demo_gkxlumenx_ods`、`gkxlumenx_dwd` | 源表字段、待建表字段、更新频率、是否在数据库 |
| 第 4 步 | 判定对齐状态 | 需求文档、原型页面、原型代码 | 对齐状态判定、是否在需求文档/原型页面/原型代码 |
| 第 5 步 | 成表与质检 | 前四步全部中间产物 | 《XX模型指标字段清单.xlsx》 |

下面逐步骤说明操作、判断标准、填写规范和踩坑点。

## 3. 第 1 步：调研原型 UI 上的指标及依赖指标

### 3.1 调研对象

以 `repos/demo-ui-topic` 为基准，按模块逐级展开页面。企业分析的展开方式是：

```text
企业分析
├── 企业总览
│   └── 企业整体概况
├── 企业评估
│   ├── 技术力评估
│   └── 商业力评估
├── 综合竞争力
├── 创新分析
├── 供应链图谱
├── 风险诊断
└── 招引/培育推荐
```

不同模块会有不同的二级、三级页面树，但方法相同：先列页面，再在页面里逐个找“被计算的数字”。

### 3.2 逐页记录指标

对每个页面执行：

1. 打开页面，记录所有可见指标名称、单位、展示口径（如果页面已写）。
2. 到 `demo-ui-topic` 代码中搜索对应文案，确认它是静态文案还是真实计算字段。
3. 给每个指标分配 `指标ID`。企业域沿用 `M_ENT_{英文名}` 风格，例如 `M_ENT_TOTAL_COUNT`；新模块换域代码，例如产业链用 `M_CHAIN_*`、产业服务链用 `M_SVC_*`。
4. 记录层级信息：

| 字段 | 含义 | 企业分析示例 |
|---|---|---|
| 一级模块 | 最上层业务域 | 企业分析 |
| 二级模块 | 页面/子业务域 | 企业总览 |
| 三级模块 | 页面内区块 | 企业整体概况 |
| 指标一级 | 页面直接展示的指标 | 企业总数 |
| 指标二级 | 该指标的维度分组 | 技术人才 |
| 指标三级 | 维度下具体可测指标 | 研发人员占职工总数的比重 |

关键判断：`指标二级/三级` 是“依赖指标/子指标”，很多信息并不在 UI 上，而是要到需求文档补回。第 1 步允许先留空，但绝不能因为 UI 没写就认为不存在。

### 3.3 排查原型代码

页面文案可能在多个组件中，需要按名称和 `metricId` 一并搜索：

```powershell
rg -n "企业总数|TOTAL_COUNT|techPower|businessPower" repos/demo-ui-topic/src/app
```

企业分析模块常见相关文件：

```text
src/app/mock/enterprise/metricSeed.ts
src/app/mock/enterprise/readinessSeed.ts
src/app/mock/enterprise/entGapCatalog.ts
src/app/mock/enterprise/entEvalGapCatalog.ts
src/app/mock/enterprise/filterFieldSchema.ts
src/app/mock/enterprise/enterpriseList.ts
src/app/pages/development/developmentData.ts
src/app/pages/enterprise/enterpriseEvaluationModel.ts
src/app/pages/enterprise/*.tsx
src/app/pages/enterprise/*.ts
```

这些文件里既有页面指标，也有 seed/gap/schema 数据，后续第 4 步判定“是否在原型代码”时要回到这里核对。

### 3.4 第 1 步输出

形成一张只有前 7 列的草表：

| 指标ID | 一级模块 | 二级模块 | 三级模块 | 指标一级 | 指标二级 | 指标三级 |
|---|---|---|---|---|---|---|
| M_ENT_TOTAL_COUNT | 企业分析 | 企业总览 | 企业整体概况 | 企业总数 | | |
| M_ENT_TECH_POWER_SCORE | 企业分析 | 企业评估 | 技术力评估 | 技术力得分 | | |

### 3.5 第 1 步易错点

- 只记页面“大数”，漏掉构成它的依赖指标，导致后续公式没有底层支撑。
- 把页面上的排序名次、等级、雷达维度、图源等“展示字段”当成正式指标。
- 把 `repos/demo-ui-system-test` 的算法 UI 页面当成 `demo-ui-topic` 原型页面。
- 假设指标二级/三级一定出现在 UI 上；实际上它们主要在需求文档中。

## 4. 第 2 步：对照需求文档补齐口径、公式和依赖指标

### 4.1 定位需求文档

先读：

```text
gkx-orchestration/agent-delivery/bid-reference/科技专题服务算法库.md
```

同时可参考：

```text
gkx-orchestration/agent-delivery/bid-reference/科技信息展示系统和科技专题服务系统.md
gkx-orchestration/agent-delivery/bid-reference/科技信息展示系统(政策对比功能升级)核增需求.md
```

按页面名、指标名、章节编号搜索。企业分析示例中，`备注` 记录了需求文档章节位置，例如：

```text
1.1.1.2.4.2.3
算法库5.5
```

这一步必须把每个指标在需求文档里的来源章节记录下来，否则后续无法判断“是否在需求文档”和“是否对齐”。

### 4.2 判断计算过程是否足够详细

分三种情况：

| 情况 | 处理 |
|---|---|
| 需求文档有详细计算过程和依赖指标 | 直接采用；把依赖指标补入 `指标二级/三级`，把口径、公式写入对应字段，并生成计算 md |
| 需求文档只提到指标，但公式模糊 | 以需求文档为框架，补足中间步骤，必要时查文献 |
| 需求文档没有或几乎没写 | 亲自调研中国统计局、科技局、工信部以及 985/211 高校文献，形成计算逻辑后写 md |

注意：`demo-ui-topic` 当前原型脚本可能没有完全按需求文档实现。第 2 步要记录的是“需求文档要求怎么算”，而不是“原型代码现在怎么算”。原型代码与需求文档不一致，正是后续要对齐的问题。

### 4.3 补齐依赖指标

需求文档写明某个指标依赖哪些子指标时，把它们写进层级字段。例如 `M_ENT_TECH_POWER_SCORE` 技术力得分，需求文档要求五维加权：

```text
技术人才
技术创新
技术转化
技术合作
技术投入
```

每个维度下再拆 L3，例如“技术人才”下有“研发人员占职工总数的比重”“高级研发人才数量”。最终该 `指标ID` 对应 12 行（1 行 L1 + 各 L2/L3）。

### 4.4 填写口径与计算逻辑

- `口径定义`：一句话说清楚“这个数字统计什么范围、如何定义”。例如企业总数：“在选定的未来产业范围内，按企业统一社会信用代码去重的企业数量。”
- `计算逻辑说明`：用公式或步骤表达。例如企业总数：`COUNT(DISTINCT credit_code WHERE 属于目标未来产业)`。
- `计算公式-md超链接`：指向详细计算 md 的相对路径。

字段填写示例：

| 指标ID | 指标一级 | 口径定义 | 计算逻辑说明 |
|---|---|---|---|
| M_ENT_TOTAL_COUNT | 企业总数 | 在选定的未来产业范围内，按企业统一社会信用代码去重的企业数量。 | COUNT(DISTINCT credit_code WHERE 属于目标未来产业)。从 dwd_org_industry_tags 按 industry_name 正则匹配归类。 |
| M_ENT_TECH_POWER_SCORE | 技术力得分 | 企业技术力评估的综合得分，满分 0-100，综合反映技术人才、技术创新、技术转化、技术合作、技术投入五维水平。 | 采用加权平均，五维为技术人才/技术创新/技术转化/技术合作/技术投入。 |

本批实际底稿中 `计算公式-md超链接` 列为空，计算过程通过同目录 `指标计算逻辑-V3-2/{metric_id}.md` 提供。后续批次应尽量把相对路径填回该列，避免计算过程与清单失去关联。

### 4.5 计算逻辑 md 规范

目录建议：

```text
指标建模任务\王惠阶段性成果\{批次}\指标计算逻辑-V{n}\{metric_id}.md
```

命名规则：

- 一个 `metric_id` 一个文件，文件名与 `metric_id` 完全一致。
- 多级子指标全部并入同一个文件，文件内按 `L1 -> L2 -> L3` 分节，不要一行拆一个文件。

md 应包含：

```markdown
# {指标名称}（{metric_id}）

## 基本信息

- 指标ID
- 指标名称
- 使用位置
- 口径版本
- 更新频率

## 口径定义

## 计算公式

（能写 SQL 的写 SQL；不能写 SQL 的写步骤公式）

## 源库表字段

## 依赖指标

## 参考文献 / 依据

## 更新记录
```

真实样例可参考：

```text
指标建模任务\王惠阶段性成果\20260817\指标计算逻辑-V3-2\M_ENT_TOTAL_COUNT.md
指标建模任务\王惠阶段性成果\20260817\指标计算逻辑-V3-2\M_ENT_TECH_POWER_SCORE.md
```

`M_ENT_TOTAL_COUNT.md` 应包含正则映射规则、去重公式、SQL 实现和源表字段，说明计算过程不是只有一句话结论。

### 4.6 引用规范

凡是从统计局、科技局、工信部或高校文献形成的公式，必须：

1. 在 md 的“参考文献/依据”写明来源名称、发布机构、可访问链接或文档编号；
2. 在 xlsx 的 `备注` 写明“依据某某文献/机构”；
3. 不能只写“综合文献”，必须能追溯。

### 4.7 第 2 步易错点

- 直接把原型脚本当前公式当成需求文档公式，不核对需求文档。
- 需求文档模糊时不查文献，直接拍脑袋写公式。
- 只写 L1 口径，不把依赖指标补入 L2/L3，导致后续数据库调研漏项。
- 同一 `metric_id` 写多个 md，或把 L1/L2/L3 拆散。

## 5. 第 3 步：调研 MySQL 数据支撑度

### 5.1 连接信息

数据库连接在仓库根目录：

```text
database_env.yaml
```

重点调研两个库：

```text
demo_gkxlumenx_ods
gkxlumenx_dwd
```

不要凭表名猜测，必须实际连接确认。

### 5.2 必须确认的五件事

每个指标及其每个依赖指标都要确认：

1. 库是否存在；
2. 表是否存在；
3. 表是否有数据行；
4. 关键字段是否存在；
5. 关键字段非空比例是多少。

只有“表存在且有关键数据、字段非空”才算真正支撑。表结构存在但 0 行，只能写“表存在但无数据，不能支撑正式计算”。

### 5.3 常用 SQL

```sql
-- 列出库
SHOW DATABASES LIKE '%gkxlumen%';

-- 列出库中的表
SHOW TABLES FROM gkxlumenx_dwd;

-- 表行数
SELECT COUNT(*) FROM gkxlumenx_dwd.dwd_org_industry_tags;

-- 字段非空率
SELECT
  COUNT(*) AS total,
  COUNT(credit_code) AS non_null_credit_code,
  COUNT(industry_name) AS non_null_industry_name
FROM gkxlumenx_dwd.dwd_org_industry_tags;

-- 关联可行性
SELECT COUNT(*)
FROM gkxlumenx_dwd.dwd_org_industry_tags t
JOIN gkxlumenx_dwd.dwd_org_base_info b
  ON t.credit_code = b.external_id;
```

### 5.4 填写四个字段

| 字段 | 填写规则 |
|---|---|
| 源表字段 | 只写真实存在的库表字段，例如 `gkx.dwd_org_industry_tags（credit_code, industry_code, industry_name）`；不写 `ads.ent_news_stat` 这类 mock 表 |
| 待建表字段 | 现库没有、但公式需要的字段，例如“高级研发人才数字段”“新产品销售收入字段” |
| 更新频率 | 以需求文档和真实表刷新方式为准，例如“日”“年度/模型版本发布时” |
| 是否在数据库 | 只填 `是` / `部分` / `否` |

### 5.5 判定示例

`M_ENT_TOTAL_COUNT` 企业总数：

```text
源表字段：gkx.dwd_org_industry_tags（credit_code, industry_code, industry_name）；gkx.dwd_org_base_info(org_id, external_id)；gkx.dwd_forg_base_info(org_id, external_id)
是否在数据库：是
```

`M_ENT_TECH_POWER_SCORE` 技术力得分：

```text
源表字段：gkx.dwd_org_annual_financial_info(...)
待建表字段：高级研发人才数字段、新产品销售收入字段、技术合同成交额字段、外部专家参与研发人月数字段
是否在数据库：部分
```

“部分”必须能说明哪部分支持、哪部分不支持，不能只写“部分”两个字。

### 5.6 第 3 步易错点

- 只看表结构，不查数据行数和非空率，就把表当成“支持”。
- 把表结构存在但 0 行写成“数据库支持”。
- 把 mock 阶段的 `ads.*` 表当成真实库表。
- 漏查依赖指标对应的表，只看 L1 指标本身。

## 6. 第 4 步：判定对齐状态

### 6.1 四个字段

| 字段 | 填写 |
|---|---|
| 对齐状态判定 | `已对齐` / `部分对齐` / `未对齐` |
| 是否在需求文档 | `是` / `否` |
| 是否在原型页面 | `是` / `否` |
| 是否在原型代码 | `是` / `否` |

这里的“原型”指 `repos/demo-ui-topic`，不是 `repos/demo-ui-system-test`。`是否在原型代码` 表示该指标在 `demo-ui-topic` 代码中是否已有计算逻辑（即使当前实现与需求文档不一致）。

### 6.2 判定原则

- 需求文档明确给出口径和公式，且原型页面/代码一致，才可写“已对齐”。
- 需求文档有口径但公式不全，或原型实现与需求文档有出入，写“部分对齐”。
- 需求文档没有口径，或完全没有计算依据，写“未对齐”。

示例：

```text
M_ENT_TOTAL_COUNT：已对齐；是否在需求文档=是；是否在原型页面=是；是否在原型代码=是
M_ENT_TECH_POWER_SCORE：未对齐；是否在需求文档=是；是否在原型页面=是；是否在原型代码=是
```

`M_ENT_TECH_POWER_SCORE` 虽有依赖指标和来源，但需求文档要求的多项依赖字段（高级研发人才数、新产品销售收入、技术合同成交额等）当前数据库缺失，故标“未对齐”。

### 6.3 第 4 步易错点

- 把“是否在原型页面=是”当成“已对齐”。
- 忽略原型代码与需求文档的差异，只看页面文字。
- 用算法 UI（`demo-ui-system-test`）替代 `demo-ui-topic` 做原型判定。

## 7. 第 5 步：成表与质检

### 7.1 工作表与字段

工作表必须命名 `指标字段清单`，不是 `Sheet1`。固定 21 列，顺序如下：

```text
指标ID
一级模块
二级模块
三级模块
指标一级
指标二级
指标三级
口径定义
计算逻辑说明
计算公式-md超链接
源表字段
待建表字段
更新频率
对齐状态判定
关联Q编号
是否在需求文档
是否在原型页面
是否在原型代码
是否在数据库
备注
是否出现在算法demo UI
```

其中 `是否出现在算法demo UI` 是后续排查 UI 覆盖时补的工作底稿字段；生成原始王惠清单时可先统一填，后续再核对。

### 7.2 行规则

- 每一行代表一个指标层级，L1/L2/L3 各占一行。
- 同一 `指标ID` 下，L1 行留空 `指标二级/三级`；L2 行填 `指标二级`；L3 行同时填 `指标二级` 和 `指标三级`。
- 不要把一个多级指标的 L2/L3 合并到同一单元格，也不要在不同行之间合并单元格。
- `指标ID` 只代表“指标一级”，不等于“指标总数”。

### 7.3 计数口径

统计时必须同时报告：

```text
唯一指标ID数
有效指标行数（有指标ID）
指标二级非空行数
指标三级非空行数
```

本批企业分析实际值：

| 口径 | 数量 |
|---|---:|
| 唯一指标ID | 60 |
| 有指标ID的有效指标行 | 132 |
| 指标二级非空 | 77 |
| 指标三级非空 | 67 |
| 是否在数据库=是 | 48 |
| 是否在数据库=部分 | 73 |
| 是否在数据库=否 | 11 |

不要在报告中写“王惠定义了 60 个指标”。正确表述是“60 个唯一指标ID、132 个有效指标行”。这个差异后续会直接决定主仓 md 的合并方式。

### 7.4 质检清单

- [ ] 工作表名为 `指标字段清单`。
- [ ] 21 列字段名与规格完全一致，顺序一致。
- [ ] 每个有数据的行都有 `指标ID`。
- [ ] 每个 `指标ID` 只有一个 L1 行；L2/L3 行不重复、不缺失。
- [ ] 需求文档章节来源已写入 `备注` 或 `关联Q编号`。
- [ ] 每个有公式的指标都有对应计算 md，且文件名等于 `指标ID`。
- [ ] 数据库“是”的指标都有真实表字段和行数核验证据。
- [ ] 数据库“部分”的指标写清了支持/不支持字段。
- [ ] 没有把 mock 表（`ads.ent_news_stat`、`ads.ent_key_enterprise` 等）当成真实来源。
- [ ] `对齐状态判定` 与“是否在需求文档/原型页面/原型代码”三个字段逻辑一致。

## 8. 多级指标处理规范

### 8.1 层级关系

- `指标一级`：页面直接展示的指标。
- `指标二级`：构成一级指标的维度/分项。
- `指标三级`：维度下具体可测的底层指标。

例如：

```text
技术力得分（L1）
├── 技术人才（L2）
│   ├── 研发人员占职工总数的比重（L3）
│   └── 高级研发人才数量（L3）
├── 技术创新（L2）
└── ...
```

### 8.2 本批多级指标

企业分析共有 9 个 `指标ID` 含 L2/L3 子指标：

| 指标ID | 指标名称 | 子指标行数 | L2 维度数 |
|---|---|---:|---:|
| M_ENT_TECH_POWER_SCORE | 技术力得分 | 12 | 5 |
| M_ENT_BUSINESS_POWER_SCORE | 商业力得分 | 13 | 6 |
| M_ENT_COMPETITIVENESS_SCORE | 综合竞争力得分 | 10 | 4 |
| M_ENT_INNOVATION_INDEX | 创新能力指数 | 18 | 3 |
| M_ENT_CITY_RANK | 多城市对标排名 | 4 | 3 |
| M_ENT_PAINPOINT_COUNT | 痛难点反映企业数 | 7 | 4 |
| M_ENT_ATTRACTION_INDEX | 招引推荐指数 | 6 | 3 |
| M_ENT_CULTIVATION_INDEX | 培育推荐指数 | 7 | 3 |
| M_ENT_GROWTH_POTENTIAL | 成长潜力 | 4 | 3 |

### 8.3 与主仓 md 的关系

调研阶段 xlsx 中多级指标是多行；进入主仓时，同一 `metric_id` 的所有行必须合并成一个 `{metric_id}.md`。该合并动作在《指标入库操作指南.md》第 1.1 节，不在本调研阶段完成。

## 9. 指标分类与特殊情形

### 9.1 按计算性质分类

| 类型 | 特征 | 处理 |
|---|---|---|
| 简单统计类 | 计数、求和、占比、去重等 | 公式写清统计口径和 SQL |
| 复合评分类 | 多维度加权 | 必须列出全部 L2/L3 依赖和权重 |
| 排名类 | 排序名次 | 写清排序对象和排序字段 |
| 推荐/招引培育类 | 指数模型 | 写清指数构成、归一化、加权规则 |

### 9.2 需求文档与 UI 不一致

| 需求文档 | UI | 处理 |
|---|---|---|
| 有 | 有 | 正常指标，两处都要核 |
| 有 | 无 | 记录“是否在原型页面=否”，仍按需求文档保留指标 |
| 无 | 有 | 记录“是否在需求文档=否”，按文献补充口径，并标记来源 |
| 无 | 无 | 不进入正式清单；若算法 UI 出现，进“算法UI多余指标调查” |

### 9.3 mock 与真实数据

王惠清单只允许真实调研结果。凡是没有真实库表支撑的 mock 字段，必须单独标注，不能混成正式指标。典型的 mock 来源包括：

```text
ads.ent_key_enterprise
ads.ent_news_stat
```

这些表在 MySQL 中不存在时，应写“王惠 xlsx 未定义此指标；数据源为 mock 阶段虚构”，不要把它们填入 `源表字段`。

### 9.4 算法 UI 多余指标

王惠清单基于 `demo-ui-topic` 调研，算法 UI（`demo-ui-system-test`）会出现一批清单没有的展示字段、派生字段或汇总字段。这是正常现象，不是调研遗漏。这些指标单独整理到《算法UI多余指标调查.xlsx》，不要强行并入王惠正式指标。

### 10.2 复用步骤

换模块时，按下面清单逐项替换：

1. 确定模块名和域代码。
2. 在 `repos/demo-ui-topic` 中找到该模块页面树，枚举指标。
3. 在 `科技专题服务算法库.md` 和对应需求文档中找到该模块章节。

5. 使用同一套 21 列字段和同一套 md 模板。
6. 按本文件第 7 节做计数和质检。
7. 完成后按《指标入库操作指南.md》执行入仓。

### 10.3 模块间差异

- 产业链分析更依赖“产业链图谱、环节覆盖、上下游、关键节点”类指标。
- 产业服务链分析更依赖“服务环节、服务覆盖率、服务能力”类指标。
- 不同模块的源表和字段不同，不能直接复制企业分析的源表字段。
- 二级/三级模块名、页面树必须按新模块实际 UI 重新枚举。

## 附录 B：历史错误与避坑

1. **计数错误**：把 60 个唯一指标ID说成 60 个指标，忽略 132 个有效指标行和多级子指标。
2. **层级错误**：没意识到 xlsx 每行代表一个指标级，把多级指标拆散或重复。
3. **需求文档与原型混淆**：把 `demo-ui-topic` 当前脚本公式当成需求文档公式，没有补回依赖指标。
4. **文献调研缺失**：需求文档公式模糊时不查文献，直接写公式。
5. **数据库只看表结构**：表存在但 0 行、字段 0% 非空，仍写成“支持”。
6. **mock 混入真实来源**：把 `ads.ent_key_enterprise`、`ads.ent_news_stat` 等 mock 表当成真实库表。
7. **“部分”只有状态没有证据**：没写清哪些库表字段支持、哪些不支持。
8. **对齐判定不当**：把“是否在原型页面=是”直接当成“已对齐”。
9. **算法 UI 与原型 UI 不分**：用 `demo-ui-system-test` 代替 `demo-ui-topic` 做原型判定。
10. **md 命名/拆分不当**：一个指标ID拆多个 md，或 L1/L2/L3 没有合并。
11. **工作表选错**：读成 `Sheet1` 而不是 `指标字段清单`。
12. **输出范围扩大**：把“算法 UI 多余指标”当成王惠调研遗漏，强行并入正式清单。
