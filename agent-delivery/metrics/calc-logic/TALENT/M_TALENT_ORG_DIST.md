## 摘要

本件回答「重点人才集中在哪些机构、机构类型结构如何、头部集中度有多高」。以 `dwd_scholar` 21,316 行为总体，以有机构名的 20,829 人为分母，按机构原串去重后得到 2,108 个机构节点。实测高校占 91.12%（18,980 人），医疗机构占 5.64%（1,175 人），科研院所占 1.87%（389 人），企业仅 81 人（0.39%）。集中度 CR5 为 11.57%、CR10 为 18.07%、CR50 为 47.92%，HHI 71.7，属于低集中结构；1,154 个机构只有 1 人，占全部机构的 54.74%。深圳子集为 251 人、39 个机构，占全库 1.21%，首位是深圳大学 88 人。

结论是：这份库是**学术人才库**，不是产业人才库；机构维可以直接支撑「头部高校/医院」类查询，但不能用来回答「深圳企业引才」类问题。发布时建议把「高校/医疗/科研/企业」四类分开呈现，不要把 0.39% 的企业样本混进总榜。

## 一、需求定义概述

### 1.1 指标名称与业务问题

指标名：`M_TALENT_ORG_DIST`，中文名「重点人才机构分布」。它服务三类业务问题：一是「哪些机构聚集了最多的高层次人才」，用于招商引才的对标；二是「人才供给的机构类型结构是什么」，用于判断供给来自高校、医院、院所还是企业；三是「头部机构集中不集中」，用于判断人才是广布还是寡占。

「重点人才」在本库的操作定义是：`dwd_scholar` 主档中的学者记录（含院士标识者可单独切出）。本件不设论文门槛，因为一旦设门槛，机构分布就会变成「高产机构分布」，与业务问的「人才在哪」不是同一个问题。

### 1.2 指标定义

机构分布是一个「机构 → 人数」的频次表，外加由该频次表派生的三个结构量：类型结构、集中度、头部名单。

- 统计单元：`scholar_id`，同一人只计一次；
- 机构取值：`dwd_scholar.scholar_org_name_zh` 原串，去首尾空格，不做别名合并；
- 分母：有机构名的学者数 20,829；
- 类型：高校 / 医疗机构 / 科研院所 / 企业 / 其他，五分类；
- 属地：由机构名推断省、市，用于深圳切片与区域交叉。

### 1.3 计算口径与边界

三个边界必须写清楚，否则同一份数据可以算出不同的数。

第一，**原串还是合并串**。本件保留原串。若把「哈尔滨工业大学(深圳)」并到「哈尔滨工业大学」，深圳子集会从 251 人降到 241 人，头部排名不变但分校贡献被抹掉。保留原串的代价是机构数偏多（2,108），好处是每一笔归属都能指回一个字符串。

第二，**附属医院算高校还是医疗**。本件算医疗。若按「高校」优先匹配，1,175 名医疗人才会被并进高校，高校占比会从 91.12% 抬到 96.76%，类型结构失真。规则顺序在 `_talent10_common.org_type` 里固定为「高校名录精确 → 医疗机构关键词 → 高校关键词 → 科研院所 → 企业」。

第三，**中国科学院算哪类**。名录里存在「中国科学院」这一行，按「名录精确优先」它被判成高校。这是一个已知的分类瑕疵：中国科学院本部是科研机构，只有「中国科学院大学」才是高校。本件不手工改这一条，因为改了会破坏「名录优先」的统一规则；在 §四 4.3 单列，并给出修复路径。

## 二、计算过程

### 2.1 输入读取与字段选择

脚本第一步读取 `probe_a26_20261022.json` 的 `scholar_dump.rows`，得到 21,316 行五元组，其中第 2 列是 `name_zh`、第 3 列是 `scholar_org_name_zh`。这里不做任何清洗，保留空串与全角括号，因为后续的属地规则需要看到原始字符才能判断「（深圳）」这类后缀。

第二步读取高校名录 3,501 行，只为两件事：类型判定时的「名录精确优先」，以及属地判定失败时的兜底。名录不参与人数统计，它只是一个字典。

第三步把机构串去重，得到 2,108 个键。去重前先 `strip()`，不去除括号、不去除「大学」后缀，也不做繁简转换。这样做的结果是机构数偏多，但每一个键都能在原始表里找到对应行，审计时可以逐条核对。

### 2.2 主公式

设学者集合为 $S$，$|S|=21{,}316$；有机构名的子集为 $S_{org}$，$|S_{org}|=20{,}829$。对任意机构串 $o$，人数定义为：

$$n(o)=\left|\{\,s\in S_{org}:\ \text{org}(s)=o\,\}\right|$$

机构份额为 $p(o)=n(o)/20{,}829$。集中度三个量为：

$$
CR_k=\frac{\sum_{j=1}^{k} n_{(j)}}{20{,}829}\times 100\%,\qquad
HHI=\sum_{o}\left(\frac{n(o)}{20{,}829}\right)^2\times 10^4
$$

其中 $n_{(j)}$ 是按人数降序排列后的第 $j$ 个机构。Gini 用标准梯形公式，输入是 2,108 个机构的人数向量。所有量在脚本里都是一次遍历算出，没有抽样、没有加权、没有平滑。

### 2.3 分母口径

分母只有一个：20,829。它不是 21,316，因为 487 人的机构名为空；也不是 20,420，因为面板口径剔除了没有中文论文的人。把分母写成 21,316 会让所有份额系统性低 2.28%，把分母写成 20,420 会让份额高 2.0%，两种写法都不符合「机构分布」的定义。

类型结构的份额分母同样是 20,829，不是各类机构数。深圳切片的份额分母还是 20,829，所以 251 人对应 1.21%，而不是「占深圳高校的百分比」。院士切片的分母是 80（可对齐的院士数），不是 112，因为 32 个院士 id 在主档里找不到机构。

### 2.4 类型判定规则

类型判定是一个有序规则链，顺序不可交换：

1. 机构串在高校名录 3,501 行中精确命中 → 高校；
2. 含「医院 / 医学中心 / 疾病预防 / 卫生院 / 保健院」→ 医疗机构；
3. 含「大学 / 学院 / 学校」→ 高校；
4. 含「研究院 / 研究所 / 科学院 / 研究中心 / 实验室 / 工程中心」→ 科研院所；
5. 含「公司 / 集团 / 有限 / 股份 / 厂 / 企业 / 事务所」→ 企业；
6. 其余 → 其他。

第 1 条必须在第 2 条之前，否则「北京大学第三医院」会因为含「大学」被判成高校；第 2 条必须在第 3 条之前，否则所有附属医院都会并进高校。实测这两条顺序影响了 1,175 人的归类，不是小数。

### 2.5 属地判定与深圳切片

属地判定 `loc2` 分五步：高校名录精确 → 企业底册精确 → 高校名录前缀 → 企业底册前缀 → 城市名取最右。最后一步是关键：`哈尔滨工业大学(深圳)` 同时含「哈尔滨」和「深圳」，取最右命中才能落深圳；若用前缀匹配，12 人会被判回哈尔滨。`北京大学深圳医院` 同理，2 人会被判回北京。

深圳切片用 `is_sz_org`：属地城市为深圳市，或机构串含「深圳」。后者是兜底，用于接住「深圳」出现在括号里但城市名规则未命中的少数写法。切片人数 251，机构数 39，份额 1.21%。

### 2.6 集中度与长尾处理

2,108 个机构中，1,154 个只有 1 人，占 54.74%；中位数是 1 人，最大值是 728 人（中国科学院）。这是一个典型的「长尾 + 一个超级头」结构：HHI 只有 71.7，远低于 1,000 的寡占阈值，但 CR5 仍有 11.57%，说明头部五家合计超过一成。

长尾不删除、不合并、不截断。删除单例机构会让 CR10 从 18.07% 升到 18.07% 以上（分母变小），HHI 会显著上升，等于人为制造集中。本件保留全部 2,108 个机构，让长尾如实拉低 HHI，这也是判「低集中」的依据。

## 四、数据缺失情况

### 4.1 缺「第二期快照」，增长类需求不可算

需求原文提到「机构人才环比增长率」。库内只有一期 `dwd_scholar` 快照，没有历史版本，也没有 `snapshot_date` 字段可用于分组。因此任何「增长/环比/同比」都不能算。

修复路径：在 `dwd_scholar` 上增加 `etl_date` 分区，或每月落一份 `scholar_org` 快照到 `code/_snapshots21/`。有了两期之后，增长率的分母是「上期同机构人数」，分子是「本期 − 上期」，不需要改主公式。

### 4.2 缺机构主键，别名不可靠合并

`scholar_org_id` 非空 0 行，机构只能按名称串建节点。后果是「哈工大深圳」三种写法算三个机构，「中国科学院」与「中国科学院大学」算两个机构。CR/HHI 因此对写法敏感。

修复路径：建一张 `dim_org_alias`（alias → canonical_org_id），用高校名录的 2,933 个校名做种子，再补「分校/附属医院/别名」三类映射。映射表建好后，本脚本只需把 `o = org` 改成 `o = alias_map.get(org, org)`，其余公式不动。

### 4.3 中国科学院被归为高校

高校名录里存在「中国科学院」这一行，按「名录精确优先」它被判成高校，但它实质是科研机构。影响 728 人的类型归属，占 3.50%。

修复路径：在 `org_type` 里加一条前置规则「以『中国科学院』开头且不含『大学』→ 科研院所」。这条规则会影响高校占比（从 91.12% 降到 87.62% 左右），必须在改动时同步重跑本件与 `M_TALENT_STRUCT_QUERY` 的机构类型交叉。

### 4.4 缺机构属性：性质、规模、成立年

本件只能给「类型」和「属地」，不能给「公办/民办」「双一流/非双一流」「在校生规模」「成立年」。高校名录有 `est_year`（部分校名有值）和 `level`（本科/专科），但企业、医院、院所没有对应字段。

修复路径：高校侧用 `dwd_org_heis_info.est_year` 与 `level` 直接补；企业侧需要工商底册（`base_20261021.json` 已有 189,116 家企业的名称与注册资本），可按名称精确连接；医院侧需要卫健委名录，库内没有。

### 4.5 缺「人—机构」的时效

`dwd_scholar.scholar_org_name_zh` 是当前机构，不带起止时间。一个人换过单位，历史机构不会出现在主档里，只会出现在 `work_experience`。本件因此是「现职分布」，不是「历史分布」。

修复路径：用 `dwd_scholar_work_experience` 的 57,117 行做「历史机构分布」，按段计数而不是按人计数。注意那份表的机构串质量更低（61.33% 判不出属地），需要先做机构名清洗。

### 4.6 缺企业样本

企业只有 81 人、74 个机构，占 0.39%。任何「企业人才榜」在这份库上都不可信。修复路径不是改公式，而是换数据源：招聘库 `dwd_org_recruit_info` 有 670 万条岗位，可以补「企业需求侧」，但不能补「企业现有人才」。

### 4.7 缺口汇总

| 缺口 | 影响维度 | 影响量级 | 修复路径 | 优先级 |
|---|---|---|---|---|
| 无第二期快照 | 增长 | 全部增长类指标不可算 | 增加 ETL 分区或月度快照 | 高 |
| 无机构主键 | 集中度精度 | 24 个单例、3 种哈工大写法 | 建 alias 映射表 | 高 |
| 中国科学院归类 | 类型结构 | 728 人 / 3.50% | 加前置规则 | 中 |
| 无机构性质/规模 | 结构分析 | 全类型 | 接工商底册、卫健委名录 | 中 |
| 无现职时效 | 历史分布 | 全部 | 用 work_experience 重建 | 中 |
| 企业样本薄 | 产业侧 | 81 人 / 0.39% | 换数据源，非改公式 | 高 |

## 五、结论与发布建议

### 5.1 三条结论

第一，机构维的主体是高校。91.12% 的人集中在 1,204 所高校，医院 5.64%、院所 1.87%、企业 0.39%。这不是抽样偏差，是 `dwd_scholar` 的建库口径决定的——它以论文作者为主线，企业研发人员天然缺位。

第二，集中度是「低集中 + 长尾」。HHI 71.7、CR10 18.07%，没有任何一家机构超过 3.5%。单例机构占 54.74%，说明一半以上的机构只贡献 1 个人。这个结构适合做「广覆盖」类查询，不适合做「寡占/卡脖子」类判断。

第三，深圳在全库中占比很小。251 人、1.21%，首位深圳大学 88 人。深圳的高校数量与体量都远小于北京、上海、南京，这个排名符合常识，不应被解读为「深圳人才少」——它只说明这份库对深圳的覆盖薄。

### 5.2 发布建议

建议以「类型分层 + 头部名单 + 集中度」三块发布，不发布单一总榜。总榜会被中国科学院、上海交大两家的体量主导，掩盖医院与院所的分布。分层之后，每一类的头部才有解释力。

建议在页面上显式标注三个口径：分母 20,829、机构按原串去重、类型五分类。缺了这三行，甲方复核时会得到不同的数，进而怀疑整份交付。

建议把「院士 80 人」单独标注为「可对齐数」，不要写成「院士总数」。112 个 id 里 32 个无法在主档定位，这是双宇宙问题，不是数据错误。

### 5.3 与王惠方法的对照

王惠系方法在本指标上的典型做法是「先建机构主数据，再按主数据汇总」，即先做 alias 合并、再算集中度。本件的做法相反：先按原串出数，再在 §四 说明别名影响。两种做法的差别不在结果，而在可复核性——原串法的每一笔都能指回一行，主数据法的每一笔都要先信映射表。

选用建议：**本期用原串法交付，下一期建 alias 表后切换到主数据法**。切换时必须同时重跑本件与区域件，并在文档里保留两版数字的差异说明，不能静默替换。

| 部分支持 | 无论如何构建，始终有部分依赖维度无法从**开发库+三方库（gkx）**得到足够数据 | 否，主体维齐全 |
| 完全不支持 | 该指标及其关键依赖维度，在**开发库与三方库（gkx）**均无法构建（结构与数据均不具备可算闭环） | 否 |

> **数据源口径**：本件支持度按「开发库 + 三方库（gkx，183.240.141.251:3318 只读）」评估，仅排除 `demo_*`；本机开发库事实面为空壳（`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张），实际取数面为 gkx。

### C.2 转换规则是否可复核

类型规则 6 条、属地规则 5 步，全部写在 `_talent10_common.py` 的 `org_type` 与 `loc2` 里，没有隐藏分支。任何人拿一个机构串，可以手工走一遍规则得到同样的类型与城市。这是「完全转换支持」的核心条件。

### C.3 数据量是否足够

2,108 个机构、20,829 人，足以支撑 CR/HHI/Gini 与类型结构。深圳 251 人、39 个机构，足以支撑城市内头部名单，但不足以支撑「深圳企业分布」（企业仅 6 人）。因此本件在深圳切片上只给机构名单，不给企业结论。

### C.4 何时应降档

若甲方要求「机构别名合并后的集中度」或「企业人才分布」，本件应立即降为「部分支持」，因为前者缺 alias 表、后者缺企业样本。降档不是失败，是把「能算的」和「算不准的」分开，避免用一个漂亮的 HHI 掩盖 0.39% 的企业覆盖率。
