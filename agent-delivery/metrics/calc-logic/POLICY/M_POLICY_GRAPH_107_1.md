## 摘要

政策实体关系抽取是本批五件里唯一「结构上做得出来、语义上做不全」的典型：它的失败点不在行数，而在**字段的语义真空**。gkx 政策侧只有两张文本主表与两份备份，`%policy%` / `%graph%` / `%entity%` 三路扫描共命中 4 张表，想找的 `policy_graph_edge`、`policy_entity`、`policy_entity_relation` 三张边表**一张也不存在**。因此本件的全部边都是字段现建，属「本件自定义、待甲方确认」的口径。

现建之后，政策侧骨架相当健康：20,000 条政策节点、468 个发文机关、5 个层级、13 个文种、31 个省级地区、54 个城市、32 个区县、46 个产业节点，合计 89,460 条边，平均度 4.473，最大度 8，中位度 4，**孤立政策 0 条**。层级分布为省级 9,922、市级 8,622、国家级 2,174、区级 1,254、园区级 144，发文机关前三名是工信部 637、上海市企业服务云 548、上海市科学技术委员会 528，产业节点前三名是集成电路 44、智能制造 35、软件产品 34。这批数字说明：**只要关系类型够粗，图谱完全能画。**

问题出在需求点名的五类关系上。**政策主题**的载体 `theme` 只有 2 行真值，另 19,998 行是字面字符串 `'NULL'`；**政策目标**的载体 `keypoints` 整列为空；**受益对象**的载体 `policy_support` 有一个必须写进文档的陷阱——20,000 行全部是非空字符串 `'null'`，`JSON_LENGTH(CAST('null' AS JSON))` 返回 1，任何只用 `JSON_LENGTH > 0` 判非空的写法都会把 20,000 行全部误判成有值，而真值是 0 行；**监管机构**连列都没有，且不能用 `ministry` 顶替——同一条政策可以由发改委发文、由行业主管部门监管，发文方与监管方在语义上是两个位置。**实施主体**是唯一能建的，但 `ministry` 记的是发文机关，不是「谁承接、谁落地」，对企业侧的实施主体没有任何字段。

## 一、需求定义概述（指标定义与需求原意）

### 1.1 所属功能模块（要开发什么）

本指标支撑政策图谱页的「实体关系」视图。用户在页面上看到的形态是：选中一条政策，右侧浮出它的发文机关、层级、文种、适用地区、关联产业；或者反向选中一个产业节点（例如「集成电路」），列出提到它的 44 条政策。产品语义上有三层用法：其一是**检索增强**——按机关、地区、产业筛政策；其二是**关系洞察**——哪些机关在密集发文、哪些产业被政策反复点名；其三是**推理链**——从「政策—产业」边出发，结合企业侧数据回答「这条政策影响了哪些企业」。

三层用法对关系类型的要求递增：检索只要机关/地区/文种，洞察要产业节点，推理链要**受益对象**（这条政策补贴谁）。本件能交付前两层，第三层因为受益对象真值 0 行而断掉。这也是判「部分支持」而非「完全不支持」的分界线：**图谱本身是活的，断的是语义最细的那条边。**

### 1.2 为什么需要这个指标

政策数据在库里有 20,000 条，但它是**纯文本**：标题、正文、机关、地区、年份。文本本身不可计算——你无法对 20,000 段正文做聚合，也无法在图上做路径查询。关系抽取的价值就是把这堆文本变成**节点与边**，让「哪条政策提到集成电路」「哪个机关发了多少条市级政策」变成一次图遍历而不是一次全文扫描。

对本项目而言，它还有一层特殊作用：政策图谱是企业图谱与产业链图谱的**跨域连接器**。企业侧有 189,116 家企业的行业标签，产业链侧有 1,273 个节点，政策侧有 20,000 条文本——三者之间原本没有边。政策—产业边一旦建立（本件建了 282 条，覆盖 271 条政策、46 个产业节点），企业就能顺着「企业行业标签 → 产业节点 → 政策」走通，这是政策匹配度（`M_POLICY_MATCH_SCORE`）的前置条件。

### 1.3 需求文档是否给出定义方法

**给了关系清单，没给建边规则。** SRS `ALGO-POLICY-GRAPH-107` 点名五类必须抽出的关系：政策主题、政策目标、实施主体、受益对象、监管机构。这五类构成验收清单——少一类就是没做全。

但它**没有**给出：① 每条关系用什么字段/规则抽取（是正则、是词典、还是模型）；② 关系的方向定义（「实施主体」是政策→主体，还是主体→政策）；③ 节点粒度（机关用全称还是简称，产业节点用几级）；④ 一条政策可否对同一关系出多条边；⑤ 边的置信度如何表达。这五项都属于「建边规则」，必须由甲方裁决，否则同一批数据可以合法地长出十种不同的图。

本件的全部建边规则因此都写成「本件自定义」：共现节点名最小长度 `MIN_NODE_NAME_LEN=4`、标题口径（只扫标题）、长名优先去重。三条都是工程折中，不是甲方口径。

### 1.6 形式定义（本件自定义部分已标注）

设政策节点集 $\mathcal{P}$（$\lvert\mathcal{P}\rvert=20000$），实体节点集 $\mathcal{E}=\mathcal{E}_{issuer}\cup\mathcal{E}_{level}\cup\mathcal{E}_{type}\cup\mathcal{E}_{region}\cup\mathcal{E}_{ind}$，关系类型集 $R=\{r_1,\dots,r_m\}$，则

$$\mathcal{G}=(\mathcal{P}\cup\mathcal{E},\,E),\qquad E=\{(u,r,v)\mid u\in\mathcal{P},\ r\in R,\ v\in\mathcal{E}\}$$

覆盖率按「强关系计 1、弱关系计 ½」折算：

$$\text{Cov}=\frac{\lvert R_{\text{strong}}\rvert+\tfrac{1}{2}\lvert R_{\text{weak}}\rvert}{\lvert R_{\text{req}}\rvert}=\frac{0+\tfrac{1}{2}}{5}=0.2$$

其中 $R_{\text{req}}$ 为 SRS 点名的五类关系，$R_{\text{strong}}$ 为字段真值充分且方向正确的关系，$R_{\text{weak}}$ 为方向性替代的关系。

**边界**：① 本件不产出任何「政策影响力」打分，也不做中心性排序（那是 `M_POLICY_GRAPH_107_2`）；② 边的置信度一律为 1（字段现建，无概率模型）；③ 标题口径只扫标题，正文口径的抽样值不当全量（§2.8）。

## 二、计算过程

### 2.1 总体设计：为什么先建骨架再谈语义关系

建图有两种顺序。一种是**需求驱动**——先找五类关系，找到哪类建哪类，找不到就空着。另一种是**骨架驱动**——先把政策节点和所有能建的实体边建起来，再看需求清单缺什么。本件选后者，理由是：图谱的下游消费（前端图组件）要求「无孤立节点」，如果只建需求点名的边，「监管机构」类边为零会让大量政策变成孤点，图直接画不出来。

因此本件的边集分两部分：**辅助边**（层级/文种/地区/产业，让骨架可遍历）与**需求边**（五类点名关系）。这两部分在产物里分开存放（`edges.by_relation` 与 `required_relations`），因为它们对判档的贡献完全不同——辅助边再多也不能顶替需求边，这一点写在 `coverage.auxiliary_note` 里。

### 2.2 第一层｜政策节点与字段填充

政策节点来自 `dwd_policy_base`，共 20,000 行。这一层的重点是**逐列量真值**，因为「字段有没有值」在本件是判档的核心证据。九列的非空计数与占比（分母均为 20,000）：

| 字段 | 非空行 | 占比 | 语义 | 可用于建边 |
|---|---:|---:|---|---|
| `publish_year` | 19,997 | 0.99985 | 发布年 | 是（时间维度） |
| `ministry` | 19,989 | 0.99945 | 发文机关 | 是（弱建实施主体） |
| `rank` | 19,643 | 0.98215 | 层级 | 是（辅助边） |
| `type` | 18,138 | 0.9069 | 文种 | 是（辅助边） |
| `province` | 17,476 | 0.8738 | 省 | 是（辅助边） |
| `city` | 10,294 | 0.5147 | 市 | 是（辅助边） |
| `district` | 1,165 | 0.05825 | 区县 | 是（辅助边，稀疏） |
| `theme` | 2 | 0.0001 | 政策主题 | 否（做不成节点） |
| `keywords` | 0 | 0.0 | 关键词 | 否（整列为空） |
| `keypoints` | 0 | 0.0 | 政策要点 | 否（整列为空） |
| `policy_support` | 0 | 0.0 | 支持措施 | 否（字面 null 陷阱） |

前七列构成一条清晰的梯度：年份与机关几乎全覆盖，层级/文种/省八成以上，市一半，区县不到 6%。后四列则是断崖——`theme` 2 行、其余三列 0 行。**这个梯度决定了图谱能画多细：** 画到省级是实的（31 个省级节点、17,476 行有省），画到区县就只有 1,165 条边，覆盖率 0.05825，前端一按区县筛就会大面积空白。

### 2.3 第二层｜`policy_support` 的「字面 null」陷阱

这一节单独写，因为它是本件最容易出错的地方，也是本批 `DATA_FACTS` §3.4x 反复强调的类型。

`policy_support` 这一列在 20,000 行里**没有一行是 SQL NULL**。它的值是字符串 `'null'`（四个字符）。表里的判空只能靠 `JSON_LENGTH`，而 `JSON_LENGTH(CAST('null' AS JSON))` 返回 **1**——因为 JSON 的 `null` 是一个合法的标量值，长度视为 1。于是下面两种写法会得到相反的答案：

- 错误写法：`SELECT COUNT(*) FROM dwd_policy_base WHERE JSON_LENGTH(policy_support) > 0` → 20,000；
- 正确写法：`SELECT COUNT(*) FROM dwd_policy_base WHERE JSON_LENGTH(policy_support) > 0 AND policy_support <> 'null'` → 0。

产物把这个差异完整记下来了：`literal_null_rows` = 20,000、`real_value_rows` = 0、`json_length_positive_rows` = 20,000。**三者的含义完全不同**——第一个是「所有行都是字面 null」，第二个是「真值行数为零」，第三个是「按 JSON_LENGTH 判会全部误判」。任何只写第三个数字的报告，都会得出「20,000 行全部有支持措施」的荒谬结论。

同一类陷阱也出现在 `theme` 上：2 行真值、19,998 行字面 `'NULL'`（大写）。本件对 `theme` 的判据是双条件（非 NULL 且非字面），因此真值只认 2 行。

### 2.4 第三层｜五类需求关系逐一裁决

| # | 关系类型 | 载体字段 | 真值行 | 是否建成 | 裁决理由 |
|---|---|---|---:|---|---|
| 1 | 政策主题 | `theme` | 2 | 否 | 2/20000 做不成主题节点；其余 19,998 行是字面 `'NULL'` |
| 2 | 政策目标 | `keypoints` | 0 | 否 | 整列为空，无任何文本可抽 |
| 3 | 实施主体 | `ministry` | 19,989 | **弱建** | 机关可作载体，但它是**发文方**不是**实施方**；企业侧承接主体零字段 |
| 4 | 受益对象 | `policy_support` | 0 | 否 | 真值 0 行（全部字面 `'null'`）；企业侧无受益对象字段 |
| 5 | 监管机构 | 无 | 0 | 否 | 无该字段；`ministry` 不能替代（发改委发文、行业部门监管是常态） |

五类里唯一落地的是第 3 类，且产物明确写 `built: "weak"`。**「弱」这个字不是形容词，是判定**：如果甲方验收时要求「实施主体必须是承接方」，这一类也应判未建，覆盖率会从 0.2 掉到 0，判档相应上移为完全不支持。本件按「发文方尚可代表政策执行主体之一」的宽口径判弱建，并在 §5.4 把这个宽窄选择列为待裁决点。

第 5 类的驳回理由需要展开：`ministry` 在字段名上是「部委」，看起来最像监管机构。但政策文本里的机关至少有三种角色——**发文方**（谁签的字）、**执行方**（谁落实）、**监管方**（谁检查）。20,000 条里同一个机关可能同时是三种角色之一，也可能只发不管（例如「上海市企业服务云」548 条，它是服务平台不是监管机构）。用一列顶替三角色，等于把「谁发的」当成「谁管的」，这在政策匹配场景下会导致企业被匹配到不相干的监管部门。

### 2.5 第四层｜辅助边的建法

四类辅助边不在需求清单里，但它们撑起了骨架。建法都是「字段非空即连边」，一政策一值：

| 关系 | 边数 | 覆盖政策 | 节点数 | 说明 |
|---|---:|---:|---:|---|
| `policy_has_issuer` | 19,989 | 19,989 | 468 | 机关按原字符串，未做简称归一 |
| `policy_has_level` | 22,116 | 19,643 | 5 | 边数 > 政策数：一政策可挂多层级 |
| `policy_has_type` | 18,138 | 18,138 | 13 | 文种枚举 |
| `policy_applies_to_region` | 28,935 | 17,813 | 31 + 54 + 32 | 省/市/区县三层，故边数远大于政策数 |
| `policy_mentions_industry` | 282 | 271 | 46 | 产业词典匹配，最小名长 4 |

`policy_has_level` 的 22,116 大于覆盖政策数 19,643，是因为 `rank` 列是 JSON 数组（例如 `["国家级","省级"]`），一条政策可挂多级，本件逐级拆成多条边。`policy_applies_to_region` 的 28,935 同理：一条政策可以同时挂省、市、区三级，三级都保留，不做「最近一级」归并——归并会丢掉「省级政策落到具体区」的信息。

机关节点 468 个是**未归一**的结果。「工信部」「工业和信息化部」若都出现会算两个节点；本件保留原字符串，归一规则列为待裁决点（§5.4）。

### 2.6 第五层｜产业节点与最小名长阈值

产业节点来自 `dwd_industry_chain_info`，1,273 行、1,150 个不同名、12 个根节点（机器人、智能网联汽车、低空经济、集成电路、软件与信息服务、人工智能、传感器、智能终端、具身智能、数字创意、生物医药、合成生物）。

匹配前先做长度过滤：名称长度 < 4 的有 113 个（长度 2 的 22 个、长度 3 的 91 个），可用名剩 1,037 个。**为什么定 4？** 两个字的名词（如「芯片」以外的通用词）在政策标题里极易误命中；三个字的名词（如「机器人」）虽然常见，但它是根节点、出现在大量无关语境（「工业机器人产业园」与「服务机器人」都命中）。定 4 是折中：丢掉一部分真命中，换取精确率。这是本件自定义阈值，产物 `min_len_rule = 4` 明确标注。

匹配口径用**标题**，不是正文。结果 282 条边、271 条政策、46 个产业节点。前五名是集成电路 44、智能制造 35、软件产品 34、生物医药 30、人工智能 27。这里有个值得注意的落差：1,037 个可用节点里只有 46 个被命中（命中率很低），说明政策标题的产业词汇与产业链词典的词表**重合度很低**——这也是为什么本件不把产业边当成五类关系之一。

### 2.8 第六层｜标题口径与正文口径的量化差异

标题口径会低估命中。本件做了 800 条确定性抽样（`ORDER BY CRC32(id) LIMIT 800`，无随机种子，可复现），对同一样本分别按「标题命中」与「正文命中」建边：

| 口径 | 命中政策 | 命中边 | 命中率 |
|---|---:|---:|---:|
| 标题 | 12 | 12 | 0.015 |
| 正文（标题 ∪ 前 4,000 字） | 92 | 211 | 0.115 |

正文口径的边数是标题口径的 17.5833 倍——这个倍数说明「标题口径只捞到约十七分之一的关系」。那为什么交付边仍用标题？因为 20,000 条政策的正文合计约 1.1 亿字，全量跑一次会撞数据库单查询执行上限，且结果不可复用（每次都要重扫）。**抽样值只用于量化低估幅度，不当全量使用**，这一条写在 `title_vs_body.note` 里。

这段是本件工程诚实度的关键：它没有隐瞒「交付的边是稀疏的」，而是把稀疏度量化了。评审若问「为什么只有 282 条产业边」，答案不是「政策里只提了 282 次产业」，而是「标题里提了 282 次，正文里大约是十七倍」。

### 2.9 第八层｜度分布与规模校验

89,460 条边、20,000 个政策节点，平均度 4.473（89,460 / 20,000 = 4.473），最大度 8（五类辅助边全命中即 1+1+1+3+1 = 7，加上多值拆分可达 8），中位度 4。度分布：1—2 度 274 条、3—4 度 10,614 条、5—6 度 9,067 条、7+ 45 条。**孤立政策 0 条**——这是骨架驱动设计的直接收益，也是前端能画出全图的前提。

这个分布还有一个诊断价值：3—6 度占绝大多数（19,681 条），说明绝大多数政策只有「机关 + 层级 + 文种 + 地区」这四条基本面，没有产业边。产业边的覆盖率是 271/20,000，即绝大多数政策在图上只有骨架尖刺、没有语义触角。**这正是「部分支持」的图形化表达。**

### 2.10 第九层｜被否决的方向：政策—政策共现边

需求里虽然没点名「政策—政策」边，但政策图谱的常见做法是靠共现建边。本件试算后否决：

- 可用共现键只有「机关×年」（`theme` 仅 2 行、`keywords` 全空，两个本可用于共现的列都废）；
- 3,242 个组，若组内两两连边，边数 220,326；
- 最大一组「深圳市人民政府 / 2021 / 178 条政策」，组内 clique 就是 15,753 条边；
- 同组内每条边同权、无区分度，图谱退化成一个巨型 clique，不能回答「哪条政策与哪条政策相关」。

因此政策—政策边**不落库**。这一条写在 `notes` 与 `cooccur_negative.why_rejected` 里，是本件「不交付」的唯一主动取舍（其余都是客观缺字段）。

### 3.3 结构支持判定

本件是**「节点侧结构完整、关系侧结构残缺」**的混合形态，这与「完全不支持」件（四要素全缺）不同，也与「完全转换支持」件（缺结果面但依赖齐备）不同。判档口径上，混合形态一律取短板：关系侧五缺四，故部分支持。

### 3.4 与 `dwd_global_policy_base` 的关系

库内有两张政策主表。本件以 `dwd_policy_base` 为节点源，原因是它的字段集与本件探针一致（九列填充率、字面 null 陷阱都在它上面实测）；`dwd_global_policy_base` 未作为节点源，因此本件的 20,000 是 `dwd_policy_base` 的行数，不是全库政策总数。若后续要用全量政策建图，需要重跑填充率探针——**不能假设两张表的字段质量相同**。

### 3.5 字段填充率的结构含义

把 §2.2 的九列按填充率排序，能看到一条明显的「文本→结构化」衰减：年份与机关（0.99 以上）是登记时必填的行政元数据；层级/文种/省（0.87—0.98）是编辑加工字段；市（0.51）开始掉；区县（0.058）几乎失守；四个语义字段（0.0001 以下）完全失守。这条衰减线解释了为什么政策图谱在本库只能做到「行政区划级」而做不到「主题级」——**越靠近文本语义，填充率越低。**

## 四、数据缺失情况与结论边界

### 4.1 缺口后果归因

**缺 `theme`/`keypoints` → 主题与目标两类关系全断。** 这两类恰好是政策图谱最有业务价值的部分：用户想按「人工智能」筛政策、想看「这条政策的目标是什么」，都需要它们。断掉之后，图谱退化成一个「发文机关—地区—文种」的行政元数据索引，能检索不能洞察。

**缺 `policy_support` 真值 → 受益对象断。** 这一条影响下游最重：`M_POLICY_MATCH_SCORE` 要把企业匹配到政策，靠的正是「这条政策补贴谁、补多少」。受益对象为零，匹配只能退到「行业标签 → 产业节点 → 政策」的粗路径（46 个产业节点），精度受限。

**缺监管机构字段 → 第五类关系无法补。** 这一类不能靠文本抽取解决（正文里提到监管部门的句子极少），也不能靠 `ministry` 顶替。

### 4.2 若甲方坚持要五类齐备：最小补齐清单

| # | 缺口 | 补法 | 补齐后能否建 |
|---|---|---|---|
| G1 | 政策主题 | 接主题词表（如国务院政策文件库主题分类）做映射 | 能 |
