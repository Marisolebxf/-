## 摘要

「落地实效性」要回答的是：一个城市的政策，发出去之后到底有没有落地。正本把它拆成三维——落地执行启动（政策有没有开始执行）、受益覆盖（有多少类对象受益）、实施反馈（受益方怎么评价）。三维各有公式，公式都能写，问题是每一维的输入字段在库里都拿不到值。

启动维的失败最有欺骗性。公式是「实施日填写率」：`COUNT(DISTINCT id WHERE implementation_date 非空) / N_c × 100%`。`implementation_date` 是 `date` 类型，字段存在，20,000 行全有值——值是 `0000-00-00`。MySQL 的零值日期不是 NULL，所以 `COUNT(implementation_date)` 老老实实返回 20,000。如果照这个数算，启动率是 100%，四个对比城市全部满分。这个结论显然是错的：一条 1998 年的政策，实施日是 0000-00-00，不是「1998 年 1 月 0 日已启动」，而是「导入时没填」。按 `DATE_FORMAT` 归一后，有效实施日 **0 行**。

覆盖维失败得更彻底。公式要 `COUNT(DISTINCT support_object)`，而 `policy_support` 是 JSON 列，20,000 行的 `JSON_TYPE` 全部是 `'NULL'`。这里还有一个坑：`JSON_LENGTH(NULL)` 在 MySQL 里返回 1，看上去像「有一个元素」。任何用 `JSON_LENGTH` 判空的写法都会得到「每行都有支持对象」的假象。正确写法是先 `JSON_TYPE(col)='NULL'` 判空，再取子键。取出来的结果是 `support_object` **0 行**、`support_way` 0 行、`support_behavior` 0 行。

反馈维根本没有表。gkx 280 张表里，含 policy 的只有 4 张（`dwd_policy_base` 与 3 张备份），没有一张是调查、反馈、满意度表。live 侧确实有 `gkxlumenx_ads.policy_effect`（93 行）与 `gkxlumenx_ads.policy_metric_timeseries`（93 行），但注册表把这一批登记为 `Mock @ batch=mock_20260623`、`is_mock: true`，`MOCK_TABLE_REGISTRY.md` 记录的指纹是列恒值、`calc_batch_id` 全同。这是造数面，不能当证据。

三维全断之后，正本的合成规则救不了场。规则写得很清楚：「各维截面 min-max 到 [0,1]，**缺维不补 0、不进平均**」。三个维都不完整，可进平均的维是 0 个，分母为 0，综合分不存在。此时如果硬输出 0 分，等于把「字段没维护」写成「政策没落地」——这是一个事实性错误，比留空严重得多。

还有一个必须点明的口径问题：入集条件形同虚设。正本要求「`status=有效` 且 `expire_date` 空或不早于统计日」，实测 `status` 只有一个取值「有效」（20,000 行），`expire_date` 非空 0 行。两个条件都恒真，20,000 条全部入集，条件不提供任何区分度。这意味着 `N_c` 就是「该市政策条数 + 国家级 2,174」，城市之间的差异只反映政策数量，不反映有效性。

一句话收口：这不是「数据少一点、分数偏低」，是「三维的输入全空」。任何数值都是编的。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**政策分析 → 深圳政策现状分析 → 指标体系构建**，同时服务「区域政策对比」的三维之一。设计上应在城市对比页给出一个 0—100 的「落地实效」分，默认深圳，可切换北京、上海、广州。本件判定该分数**无法计算**，页面应改为「该项暂不可用」并说明缺哪三维。

### 1.2 为什么需要这个指标

第一，政策数量多不等于政策有效。一个城市一年发 500 条政策，如果都不落地，实际效果不如另一个城市发 50 条全部兑现。落地实效性是把「发文量」与「兑现量」分开的唯一手段。

第二，它是区域对比里最容易被误读的一维。用户看到「深圳政策数第一」会自然推断「深圳落地最好」，但两者没有必然关系。缺了实效维，对比页就只能比数量。

第三，它的三维设计本身是合理的：启动看流程是否开始，覆盖看受益面，反馈看对象评价。问题不在设计，在数据。把这一点论证清楚，比勉强出一个分数更有价值。

### 1.3 需求文档是否给出定义方法

**给了完整的三维公式与合成规则。** 正本（calc-logic）逐项写了公式、源表字段、待建字段，并明确两条自我约束：一是「从是否已填写实施日期评估政策落地是否启动，**是启动率不是兑现率**」；二是覆盖维「无受益企业名单，**不用企业数冒充覆盖**」。这两句说明正本作者清楚这套指标只是代理，不是真实效果。

正本还写了一句关键的降级说明：「实施反馈无表则本维缺失」。也就是说，作者已经预见到反馈维可能没有数据，并允许它缺失。但正本没有预见启动维与覆盖维**同时**失效——那是数据结构问题，不是数据完整度问题。

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设对比城市为 $c$，入集政策集合 $I_c$（该市政策 + 国家级），$N_c=|I_c|$。三维原始值

$$S^{\text{start}}_c=\frac{|\{i\in I_c:\ \text{valid}(\text{implementation\_date}_i)\}|}{N_c}\times 100,\qquad
S^{\text{cov}}_c=\left|\bigcup_{i\in I_c}\text{support\_object}_i\right|,\qquad
S^{\text{fb}}_c=\text{feedback\_score}_c$$

合成：各维截面 min-max 到 $[0,1]$，缺维不进平均，等权后 $\times 100$。

**边界**：① 本件 $S^{\text{start}}_c=0$ 的分母成立但分子为 0——这不是「启动率为 0」，是「无有效日期可计」，故不出值；② $S^{\text{cov}}_c$ 的并集为空，种类数无定义；③ $S^{\text{fb}}_c$ 无源；④ 三缺 → 可进平均维数 0 → 综合分 `null`；⑤ 不置 0、不用企业数冒充覆盖、不用造数表兜底。

## 二、计算过程（从缺：为什么不出分）

按派单书 F4，「完全不支持」档不写长计算过程，只留判定链条。本件的判定链条四步，每步都可复核。

第一步，确认字段是否存在：`implementation_date` 在表内，`policy_support` 在表内，反馈表不在任何一侧。第二步，确认每个字段的有效值：实施日归一后 0 行、`support_object` 0 行、反馈表 0 张（gkx）。第三步，按正本的维内公式算：启动维分子 0 / 分母 20,000；覆盖维并集空；反馈维无源。第四步，按「缺维不进平均」，完整维 0 个，综合分无定义。

四步的原始数字全部写在产物的 `dims`、`probes.date_probe`、`probes.json_probe` 三段里，逐项带 `why_not`。负结论也必须可复现，否则「算不出来」就只是散文——这是本件仍然需要一个脚本的原因。

|---|---|---|
| 表结构直接支持（开发库+三方库） | **否** | 两库均无 `policy_effect` 类结果面；gkx 280 表无反馈表 |
| 表数据直接支持（开发库+三方库） | **否** | 有效实施日 0 行、支持对象 0 行 |
| 依赖表结构支持（开发库/三方库） | **部分** | `implementation_date` / `policy_support` 字段在；反馈表均无 |
| 依赖表数据支持（开发库/三方库） | **否** | 三维输入全空 |

### 3.2 三维逐项证据

| 维 | 公式 | 分子 | 分母 | 判定 | 证据 |
|---|---|---|---|---|---|
| 落地执行启动 | `COUNT(DISTINCT id WHERE implementation_date 非空)/N_c×100%` | 0 | 20,000 | 不可算 | 全表 `0000-00-00` |
| 受益覆盖 | `COUNT(DISTINCT support_object)` | 0 | — | 不可算 | JSON null，子键 0 行 |
| 实施反馈 | `feedback_score` | — | — | 不可算 | 两库均无调查表 |

### 3.3 四个对比城市的 N_c 与分子

| 城市 | 该市政策行 | 国家级 | $N_c$ | 启动分子 | 若强算的启动率 |
|---|---|---|---|---|---|
| 深圳市 | 879 | 2,174 | 3,053 | 0 | 0.0% |
| 北京市 | 2,268 | 2,174 | 4,442 | 0 | 0.0% |
| 上海市 | 1,841 | 2,174 | 4,015 | 0 | 0.0% |
| 广州市 | 325 | 2,174 | 2,499 | 0 | 0.0% |

这张表是「强算会长什么样」的演示：四个城市全部 0.0%，而它们的真实落地情况绝不可能完全一致。这个「全都一样」本身就是不可算的证据——当一个指标对所有对象都取同一个值，它没有区分度，也就不构成指标。

`N_c` 的口径要说明：正本注「rank 含国家级可计入每个对比市」，所以 $N_c$ = 该市行数 + 2,174。若不把国家级计入，深圳只有 879、广州只有 325，样本量偏小且城市间不可比。

### 3.4 入集条件为什么形同虚设

| 条件 | 正本要求 | 实测 | 后果 |
|---|---|---|---|
| `status=有效` | 排除失效政策 | 20,000 行全为「有效」 | 恒真 |
| `expire_date` 空或不早于统计日 | 排除过期政策 | 非空 0 行 | 恒真 |
| `id` 去重 | 防重复 | 20,000 个不同 id | 无重复 |

三条全过，20,000 条全部入集。这不是「数据干净」，是「字段没维护」——`expire_date` 全空意味着没有任何政策被标记为过期，`status` 单值意味着没有任何政策被标记为失效。一个全部有效的政策库，本身就可疑。

### 3.5 反馈维的两库对照

| 侧 | 候选表 | 行数 | 可用性 |
|---|---|---|---|
| gkx | 无 | — | 不可用（280 表内无反馈/调查/满意度表） |
| live | `gkxlumenx_ads.policy_effect` | 93 | 造数面（`mock_20260623`） |
| live | `gkxlumenx_ads.policy_metric_timeseries` | 93 | 造数面（`mock_20260623`） |
| live | `gkxlumenx_dwd.policy_effect_eval` | 0 | 空表 |

live 侧这两张 93 行的表，行数相同、批次相同，是同一批造数的两个投影。注册表 `source_systems` 写 `Mock @ batch=mock_20260623`、`is_mock: true`；`MOCK_TABLE_REGISTRY.md` 记录的同批指纹是列恒值、`calc_batch_id` 全同。**即便不看批次标记**，两张表行数完全相等也说明它们不是独立采集的两个源。

### 3.6 与开发库 live 的差异

gkx 侧政策主表有 20,000 行，live 侧 `gkxlumenx_dwd.policy_base_info` **0 行**；gkx 侧无任何反馈表，live 侧有 2 张造数表。两边的缺口不一样：gkx 缺结果面但源数据足，live 有结果面但是假的。这正是本件需要「两侧都核」的原因——只看 gkx 会说「没有」，只看 live 会说「有 93 行」，结论完全相反。

### 3.7 三维补齐的优先顺序与成本

三维的补齐成本差异极大，这决定了补数顺序：

| 维 | 补什么 | 是补数还是建表 | 成本 | 补齐后能算什么 |
|---|---|---|---|---|
| 启动 | `implementation_date` 真值 | 补数 | 低 | 城市启动率 |
| 覆盖 | `policy_support.support_object` | 补数（JSON 内） | 中 | 支持对象种类数 |
| 反馈 | `feedback_score` 调查表 | 建表 + 采集 | 高 | 满意度分 |

启动维只需回填一个已有字段，覆盖维需要把 JSON 内容补进去（字段已在，内容为空），反馈维要从零建表并组织调查。因此建议按「启动 → 覆盖 → 反馈」的顺序推进：前两步都是补数，只有第三步是新建能力。这个顺序也符合正本的依赖关系——三维独立，任何一维补齐都不会让其他维失真，但只有三维齐全才能合成综合分。

一个容易被忽略的点：即使只补齐启动维，也不应立刻发布「启动率」作为「落地实效性」的替代。正本的口径是三合一，单维原值可以展示，但不能继承「落地实效性」这个名称，否则会造成口径漂移。

## 四、数据缺失情况

### 4.1 缺口的后果归因

后果一：**城市对比页的「落地实效」维度无法上线**。四个城市同为 0 分的图，比留空更有害。

后果二：**深圳政策现状分析的指标体系缺一角**。该体系若按三维合成总分，缺一维会让总分不可比。

后果三：**「落地」这个词在项目里暂时不可用**。任何以「落地」命名的读数，当前只能落到「发文量」上，而那是供给，不是落地。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

1. **`DATE` 零值不是 NULL**：`0000-00-00` 让 `COUNT(col)` 返回全量。
2. **`JSON_LENGTH(null)` 返回 1**：判 JSON 空必须用 `JSON_TYPE(col)='NULL'`。
3. **`policy_support` 全 null**：三子键 0 行，任何 `JSON_EXTRACT` 都返回 NULL。
4. **`status` 单值**：入集条件恒真，不提供区分度。
5. **`expire_date` 非空 0 行**：过期条件恒真。
6. **`city` 的 `'NULL'` 是字符串**：做城市切片前必须排除，否则会多出一个「NULL 市」。

### 4.3 为什么不用「政策条数」顶替

最省事的降级方案是用「该市政策条数」当落地实效。本件**明确拒绝**：条数是供给规模，落地是兑现程度，两者可以完全背离——一个城市可以发很多政策却一条不兑现。而且条数已经由 `M_POLICY_TOTAL_COUNT` 与 `M_POLICY_CITY_DIST` 交付，再用它顶替实效，等于把同一组数发布两次、贴两个标签。

### 4.4 若甲方补齐后的口径升级路径

第一步回填 `implementation_date`，启动维恢复（这是成本最低的一步，只需补数不需建表）；第二步补 `policy_support.support_object`，覆盖维恢复；第三步建调查表（`feedback_score`，按政策 × 对象 × 批次），反馈维恢复；第四步三维齐备后才谈权重（正本权重待 QPOL-02，本件不预设等权）。四步做完，本件可从「完全不支持」升级为「完全转换支持」。

## 五、王惠方法对照（V2-20260826）

### 5.1 王惠原文要点

王惠正本把本件定义在「政策分析 / 深圳政策现状分析 / 指标体系构建」与「区域政策对比三维」，更新频率季。三维与公式如下：

| 一级 | 二级 | 三级 | 公式 | 待建字段 |
|---|---|---|---|---|
| 落地实效性 | 落地执行启动 | 实施日填写率 | `COUNT(DISTINCT id WHERE implementation_date 非空)/N_c×100%` | 无 |
| 落地实效性 | 受益覆盖 | 支持对象种类数 | `COUNT(DISTINCT support_object)` | `benefit_enterprise_list` |
| 落地实效性 | 实施反馈 | 实施反馈满意度 | 待建直读 | `feedback_score` |

王惠原文另有一句关键限定：「现行综合 = (启动得分+覆盖得分)/2×100」——即在反馈维缺失时，她用两维等权出分。

### 5.2 与本件（calc-logic 正本）的差异

| 项 | 王惠 V2 | calc-logic 正本 | 差异性质 |
|---|---|---|---|
| 缺维处理 | 反馈缺则两维等权 | 缺维不补 0、不进平均；现行综合 (启动+覆盖)/2 | 表述不同，实质一致 |
| 权重 | 待 QPOL-02 | 待 QPOL-02 | 一致 |
| 反馈维 | 「现库无调查表，本维不计算」 | 同 | 一致 |
| 覆盖维约束 | 「不用企业数冒充覆盖」 | 同 | 一致 |

两版口径**没有实质冲突**。真正的差异在两版都假设「启动维可算」——而这个假设在本库不成立：实施日 100% 零值。

### 5.3 选用建议

**建议采用 calc-logic 正本的「缺维不进平均」写法，不采用王惠的「两维等权兜底」。** 理由有三：第一，王惠的两维兜底隐含「启动维与覆盖维都可用」的前提，本库两维都不可用，兜底公式的分母会变成 0；第二，正本的「缺维不进平均」在数学上更干净，缺维时直接无定义，不会诱使实现者拿 0 填充；第三，两版对反馈维的处理一致，差异只在兜底策略，而兜底在本库用不上。

需要与甲方确认的一点：若将来只补齐启动维、覆盖维仍空，是否允许「单维出分」？本件建议**不允许**——单维不是综合分，应直接显示该维原值，不要合成。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答：落地实效性这套三维，在 gkx 与 live 两侧能不能算；如果不能，缺的是哪一维、补上之后能不能算。

### C.2 需求语义锚定

「落地实效」有两种读法：**执行启动**（有没有开始）与**执行效果**（有没有兑现）。正本明确选了前者，并在公式说明里写了「是启动率不是兑现率」。这个选择是诚实的降级——库内没有兑现数据。本件要论证的是：连这个降级方案也不成立。

### C.3 权威与学术构建方法谱系

#### C.3.1 族 A：实施框架

Sabatier 的框架看目标清晰度、资源、执行结构、外部条件。它是定性分析工具，不给分数。

#### C.3.2 族 B：预算绩效评价

财政部体系分产出、效益、满意度三级。它要求项目级数据（立项、预算、决算、问卷），政策库没有。

#### C.3.3 族 C：满意度调查

政务服务「好差评」是最接近的口径。它需要调查表，库内 0 张。

#### C.3.4 族 D：兑现率

惠企政策兑现平台会记申报数、兑现数、兑现金额。库内 0 张兑现表，且政策表 33 列无金额列。

#### C.3.5 族 E：文本启动率

正本选择。理论上是「实施日是否填写」，实际上实施日全为零值。
