## 摘要

政策总数看起来是最不需要写文档的指标：一条 `COUNT(*)` 就完了。但它是本项目里**被引用次数最多的分母**——「深圳 879 条占全部政策的多少」「国家级 2,174 条占多少」「广东 1,612 条是不是最多」，每一句都要求这个分母是同一个数。分母一旦按表估算值取 18,808，后面所有占比都会整体偏大 6.37%。

本报告先验主键再计数：`COUNT(*)` = **20,000**，`COUNT(DISTINCT id)` = **20,000**，`SUM(is_deleted<>0)` = **0**。三者相等说明底表没有重复主键、没有逻辑删除残留，`COUNT(*)` 可以作为正式口径。`information_schema.TABLES.TABLE_ROWS` 报 **18,808**，比实测少 **1,192** 条（**5.96%**），它是 InnoDB 采样估算，不能当表规模，更不能当分母。

为了让这个 20,000 不是「孤数」，本件做了五条交叉校验：层级五档合计 20,000；省份 17,476 已归属 + 2,524 未归属 = 20,000；城市 10,294 + 9,706 = 20,000；类型 18,138 + 1,862 = 20,000；年份 19,997 + 3 = 20,000。五条全部闭合，说明 20,000 不是某一列的偶然合计，而是整张表的稳定基数。

结论：判**完全转换支持**。需要提醒的是，20,000 是**库内存量**，不是全国政策总量；`status` 20,000 行恒为「有效」，也不能用它筛出现行有效政策。这两个边界写进 §四，避免下游把「库里有 2 万条」读成「全国只有 2 万条政策」。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

「政策总数」挂在三个位置：科技专题服务系统的政策时序分析页顶部总卡片、科技信息展示系统的政策追踪首页、科技指数页的政策要素规模行。三处读的是同一个数，但用途不同：时序页拿它当趋势图的起点，追踪页拿它当「库里收录了多少」的说明，指数页拿它当政策要素的规模基数。

它还是政策五件（总数、级别分布、类型分布、深圳分布、全国分布）的**共同分母**。这五件必须共用同一个底数，否则会出现「级别分布加起来 20,000、总数写 18,808」这种自相矛盾。本批的做法是先落一份共用底数快照 `policy_dims_20261023.json`，五件都从它读数，从流程上消除分母分叉。

### 1.2 为什么需要这个指标

第一，它是所有政策占比的母体。政策级别分布要写「国家级占 10.87%」，深圳分布要写「深圳占 4.395%」，全国分布要写「北京占 9.66%」——三个百分比的分母都必须是 20,000。如果三份文档各自查一次库、各自拿到不同的估算值，读者会发现同一张底表有三种总数。

第二，它能暴露采集完整性。20,000 是一个整数，恰好是「两万条」的整数关口，这本身就是信号：它更像一次批量导入的上限，而不是自然增长的结果。把这一点写清楚，下游才不会把「2023 年后新增为 0」误读成「政策停止发布」。

第三，它是「表规模」类断言的最小可核验单位。需求文档没有要求「政策总数」这个指标名，但每一份政策文档都会引用它；与其让每份文档各写一个数，不如单独交付一份，把 `COUNT(*)`、主键去重、逻辑删除三件事一次说清。

### 1.3 需求文档是否给出定义方法

**需求文档给了指标名与统计对象，但没有给计数口径。** 注册表对 `M_POLICY_TOTAL_COUNT` 的定义是「纳入政策要素库的政策去重总数；统计窗口最新批次快照，对象范围全量未删除政策，按 `policy_id` 去重计数」，公式为 `COUNT(DISTINCT dwd.policy_base_info.policy_id)`。它没有规定：

- 「去重」是按主键去重，还是按标题+发文机关去重；
- 「未删除」用哪个字段判断（`is_deleted`？`status`？）；
- 是否只算「有效」政策；
- 国家级政策是否计入「政策总数」（本件计入，因为它是政策要素库的一部分）。

本件按注册表的最小解释执行：按主键 `id` 去重、按 `is_deleted=0` 过滤、不按 `status` 过滤。理由是 `status` 20,000 行恒为「有效」，用它过滤等于不过滤；而 `is_deleted` 全 0，过滤与否结果相同，但写进 SQL 能表明口径。

### 1.4 类似指标权威机构构建方法可行性分析概要

| 方法族 | 代表做法 | 口径要点 | 与本件的差 | 贴合度 |
|---|---|---|---|---|
| A 主键去重计数 | 政策库/要素库通用 | `COUNT(DISTINCT 主键)` | 本件主键无重复，等价于 `COUNT(*)` | 高 |

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设政策底表为 $P$，主键为 $id$，逻辑删除标记为 $d$，则

$$N=\mathrm{COUNT}(*)\quad\text{其中 } d=0$$

**去重校验**：

$$N_{\text{unique}}=\mathrm{COUNT(DISTINCT\ id)}$$

本件要求 $N=N_{\text{unique}}$ 才发布；若二者不等，应以 $N_{\text{unique}}$ 为准并披露重复行。

**边界**：① 20,000 是库内存量，不是全国政策总量，也不是某一年份的政策数；② 统计窗口是「当前快照」，不是「最新批次」——本库没有批次字段，无法按批次回溯；③ 不剔除通知/公示类事务文件，本件是「库内总数」，不是「产业政策数」；④ `status` 恒真，本件不声称「现行有效」。

## 二、计算过程

### 2.1 为什么先验主键，再谈计数

`COUNT(*)` 是最便宜的查询，也是最容易被误用的查询：只要表里有重复导入，`COUNT(*)` 就会把同一条政策算两次，而这个错误不会报错、不会为空、也不会被任何结构门禁发现。本件因此把「主键唯一性」放在计数之前，先证明 `COUNT(*)` 可以作为总数。

实测三件事：全表 20,000 行；`COUNT(DISTINCT id)` 也是 20,000；按 `id` 分组后没有任何一组超过 1 行。三者一起说明主键无重复。第四件事是逻辑删除：`SUM(is_deleted<>0)` = 0，说明没有「已删除但仍在表里」的记录。四件事都成立，`COUNT(*)` 才是干净的 20,000。

这一步看起来多余，但它决定了后面五条交叉校验有没有意义。如果主键有重复，层级分布加起来也会是 20,000（因为重复行会同时进入某一级），五条校验会全部闭合，却全部建立在一条脏数据上。**校验闭合只能证明内部一致，不能证明底数干净**，所以主键与逻辑删除必须先单独验。

### 2.2 主口径：`COUNT(*)` 与 `COUNT(DISTINCT id)` 双写

正式口径写两条 SQL，结果必须相等：

```sql
SELECT COUNT(*) AS n FROM gkx.dwd_policy_base WHERE is_deleted = 0;
SELECT COUNT(DISTINCT id) AS n FROM gkx.dwd_policy_base WHERE is_deleted = 0;
```

两条都返回 20,000。为什么不只写 `COUNT(DISTINCT id)`？因为 `COUNT(*)` 能同时反映「表里有多少行」这一层信息，而 `COUNT(DISTINCT id)` 只能反映「有多少个主体」。本件两者都落盘（`counts.policy_total` 与 `counts.distinct_id`），读者可以一眼看出它们相等。

也不使用 `COUNT(1)` 或 `COUNT(id)` 代替：`COUNT(id)` 会跳过 `id IS NULL` 的行，虽然本表主键非空，但换一张表就可能静默少算。`COUNT(*)` 没有这个陷阱。

### 2.3 规模口径：为什么不用 `TABLE_ROWS`

`information_schema.TABLES.TABLE_ROWS` 对 `dwd_policy_base` 报 **18,808**，实测 `COUNT(*)` 是 **20,000**，差 **1,192** 条，偏差 **5.96%**。这个字段是 InnoDB 的采样估算，`ANALYZE TABLE` 之后还会变；它既不是精确值，也不能保证是下限。用 18,808 当分母，「国家级占 11.56%」「深圳占 4.67%」都会比真值偏大，而读者无法从文档里看出偏差来自估算。

本件因此把 `TABLE_ROWS` 只作为「是否需要全表扫」的内部判断，正文一律用 `COUNT(*)`。产物里保留了 `size_trap` 对象，记录估算值、实测值与差额，目的不是引用它，而是让下一个写手知道这个坑已经踩过。

### 2.4 五条交叉校验：让 20,000 不是孤数

单看一个 20,000，无法判断它是「整张表」还是「某一列的合计」。本件用五条独立切分把它围住：

$$N=N_{\text{国家级}}+N_{\text{省级}}+N_{\text{市级}}+N_{\text{区县级}}+N_{\text{未标注}}$$

$$N=N_{\text{省已归属}}+N_{\text{省未归属}}=N_{\text{市已归属}}+N_{\text{市未归属}}$$

实测：层级 2,174 + 9,922 + 6,149 + 1,398 + 357 = 20,000；省份 17,476 + 2,524 = 20,000；城市 10,294 + 9,706 = 20,000；类型 18,138 + 1,862 = 20,000；年份 19,997 + 3 = 20,000。五条全部零差额，`cross_checks` 里逐条写了 `ok=true`。

这条校验的价值在于「分母同母体」：如果某一份文档用省份已归属的 17,476 当分母算「北京占比」，而另一份用 20,000，两个百分比会差 14.4%。本件把两个数都写出来，并要求下游明确自己用的是哪一个。

### 2.5 切片一：层级五档

层级由 `rank` 派生，派生规则与结果在 `M_POLICY_LEVEL_DIST` 里详述；本件只引用汇总值：国家级 2,174（10.87%）、省级 9,922（49.61%）、市级 6,149（30.745%）、区县级 1,398（6.99%）、未标注 357（1.785%）。

这里要说明的是：**这五档是「库内标注的行政层级」，不是「政策效力等级」**。一条市级政策可能比一条省级政策更有约束力，但在本表里它只按 `rank` 归类。把级别当效力用，会得出「省级政策比市级重要」这种无法证伪的结论。

### 2.6 切片二：省份与城市，以及字面 `'NULL'`

省份已归属 17,476（87.38%）、未归属 2,524（12.62%）；城市已归属 10,294（51.47%）、未归属 9,706（48.53%）。这两个「未归属」不是 SQL NULL，而是字面字符串 `'NULL'`。用 `province IS NULL` 查会得到 0 行，用 `province='NULL'` 才是 2,524 行。

为什么城市缺失接近一半？因为 2,174 条国家级政策的 `city` 全空，加上 7,449 条省级政策的 `city` 也全空，两者合计 9,623 条，已经占了 9,706 的 99.14%。也就是说，「城市缺失」主要不是数据质量差，而是**高层级政策本来就不属于某个城市**。这一点必须在城市级文档里说清，否则读者会以为深圳之外的城市都没采到。

## 四、数据缺失情况与结论边界

### 4.1 缺口的后果归因

**`status` 恒真 → 「现行有效」永久不可算。** 20,000 行全部标「有效」，无法识别已废止、被替代、已过期的政策。任何写「已剔除失效政策」的表述都是失真。

**城市缺失集中在高层级 → 城市级占比的分母不是 20,000。** 9,706 条无城市里，2,174 条国家级 + 7,449 条省级，合计 9,623 条（99.14%）。用 20,000 当城市占比分母，会把「国家级政策不属于任何城市」算成「城市数据缺失」，两者含义完全不同。

**类型是文种 → 「政策类型」不能按需求三分法回答。** 需求要的是产业/人才/企业扶持，本表只有其他通知/公示公告/申报通知/政策文件-…。这是语义缺口，不是行数缺口，补行数解决不了。

**2023 年后断档 → 不能做「近三年」。** 2024 年 1 条、2023 年 0 条，2025/2026 零行；表内最晚发布日 2024-02-18。任何「当前政策环境」判断都停在 2022 年。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

- **`TABLE_ROWS` 不是行数**：18,808 与 20,000 差 1,192（5.96%），用它当分母会让所有占比整体偏大。
- **`'NULL'` 是字符串**：`province IS NULL` 返回 0 行，`province='NULL'` 才是 2,524 行；城市同理 9,706 行。
- **`status='有效'` 是恒真条件**：写进 SQL 看似严谨，实则零过滤。
- **`publish_year` 缺 3 行**：这 3 行同时是 `0000-00-00` 日期，均为省级记录；不要用 `MIN(publish_date)` 直接当起始年。
- **20,000 是整数关口**：更像批量导入上限，不宜解释为自然增长结果。

### 4.3 可构建但存在缺口（不是「无法构建」）

1. **按批次统计**：补 `calc_batch_id` 后可算「本批新增/累计」。
2. **现行有效数**：补 `invalid_date` 后可算。
3. **产业政策数**：补主题分类后可算，且能与 `M_POLICY_TYPE_DIST` 共用同一份映射。
4. **按年新增**：补采 2023—2026 后可算，但需先确认 2024 年那 1 条不是脏值。

### 4.4 结论与发布建议

**建议发布，但只发布「库内政策总数」这一个语义。** UI 文案写「政策要素库收录 20,000 条」，不要写「全国政策 20,000 条」，也不要写「现行有效 20,000 条」。前者夸大了覆盖范围，后者依赖一个恒真字段。

**待甲方裁决点**：① 是否把国家级政策计入「政策总数」（本件计入）；② 是否需要「现行有效」口径（需要则必须先补状态字段）；③ 城市级占比的分母用 20,000 还是用「有城市记录」的 10,294（本件建议后者，并在文档里注明）。
