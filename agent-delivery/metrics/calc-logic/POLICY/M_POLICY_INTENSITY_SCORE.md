## 摘要

政策力度评分的设计意图是给每条政策打一个 0—100 的「实施力度」分。正本给了三维五项：效果维看「实施日是否写了」「支持方式是否写了」，覆盖维看「支持对象有几种」「政策是否落到区县」，成本维看「扶持行为是否写了」。五项各 1 分，min-max 后三维等权合成。

这个设计有一个隐含前提：`policy_support` 这个 JSON 字段里得有内容。实测下来，**它 20,000 行全是 `JSON_TYPE='NULL'`**——不是空字符串、不是空数组，是 SQL NULL。任何读子键的写法（`JSON_EXTRACT`、`->>`）都返回 NULL，`JSON_LENGTH` 甚至返回 1，看起来像「有一个元素」。这一条直接废掉三项：支持方式完备率、支持对象种类数、扶持行为完备率。

第二项「实施日完备率」失效得更隐蔽。`implementation_date` 是 `date` 类型，全表 20,000 行的值是 `0000-00-00`。它不是 NULL，所以 `COUNT(implementation_date)` 会老老实实返回 20,000——如果只看这个数，会得出「实施日 100% 完备」的荒谬结论。必须按 `DATE_FORMAT(col,'%Y-%m-%d')` 归一后再判「是否有效日期」，才看得出有效值是 **0 行**。这是本批最典型的一个「非空但无效」陷阱。

剩下唯一能算的是「区县落地标记」：`district` 有 1,165 行有值（5.825%）、872 行是字面字符串 `'NULL'`、其余为空。这 1,165 行还极不均匀——**887 行是北京**（占全部有值行的 76% 以上），上海 205、嘉兴 48、鹤壁 18、深圳只有 7。32 个不同区名里，前五个全是北京的区（通州 136、海淀 113、大兴 111、顺义 103、怀柔 83）。用这个字段做「是否落地到区县」的标记，等于给 94.175% 的政策恒打 0，且给北京的政策系统性加分。

所以结论不是「分数偏低」，而是**分数不存在**。三维里效果维 0/2 可算、覆盖维 1/2 可算、成本维 0/1 可算，没有任何一维是完整的。按正本「缺维不进平均」，可进平均的维数 = 0，$100\times\frac{1}{0}$ 无定义。本件因此 `score = null`、`publishable = false`，只发布五项子指标的逐项证据。

最后一个必须写清的边界：**不得自造「资金强度」**。正本成本维的 `待建字段` 写着 `support_amount-扶持金额`，说明设计者知道这一维本该用金额。政策表 33 列里金额类列 **0 个**（全库 123 个金额类列全在 `dwd_bid_*` 招标表）。拿招标金额顶替，或用 `abstract` 里的数字估算，都会造出一个不可解释的指标；本件一律不做。

一句话收口：这不是「数据不够、勉强能算」，是「五个子项里四个读不出来」，任何数值都是编的。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**政策分析 → 政策时序分析 → 政策力度评分**。设计上应在政策详情页顶部显示一条 0—100 的刻度条，并在政策库列表提供「按力度排序」。本件判定该刻度条**无法渲染**，页面应改为「该项暂不可用」的占位说明。

### 1.2 为什么需要这个指标

第一，政策数量多、质量参差，业务需要一个「哪条政策更硬」的排序依据。力度评分是最直观的候选。

第二，它与城市级的 `M_POLICY_INTENSITY_INDEX` 构成「微观—宏观」一对：单条政策打分后，按城市聚合就能得到城市力度。少了微观这一层，宏观那层只能靠计数。

第三，它最容易被「公式能写、代码能跑」骗过去。五项都是 `I(非空)` 或 `COUNT(DISTINCT)`，写起来毫不费力；跑出来的分数全是 0 或 0.5，看起来「有结果」。必须用否定性证据把这件事钉死。

### 1.3 需求文档是否给出定义方法

**给了五项与合成规则，且明确写了「无金额不编造拨款」。** 正本的 `成本维度` 说明里有一句关键的自我约束：「从是否写明扶持行为评估该条政策的资源投入安排；**无金额不编造拨款**」。这说明正本作者已经预见到金额缺失，选择用 `support_behavior` 是否非空来代理。

问题是这个代理也读不出来——`support_behavior` 同样在 JSON null 里。所以正本的「降级方案」在本库不成立。本件要做的判断是：降级方案失效后，是继续找第二个降级方案，还是判定不可算。本件选后者，理由写在 §四：再降一级就只能用标题词频，那已经不是「力度」而是「写作风格」。

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设政策 $i$ 的五项子指标为

$$x^{(1)}_i=\mathbb{1}[\text{valid\_date}(\text{implementation\_date}_i)],\quad x^{(2)}_i=\mathbb{1}[\,|W_i|\ge 1\,],\quad x^{(3)}_i=|O_i|,\quad x^{(4)}_i=\mathbb{1}[\text{district}_i\neq\varnothing],\quad x^{(5)}_i=\mathbb{1}[\,|B_i|\ge 1\,]$$

其中 $W_i$、$O_i$、$B_i$ 分别为 `support_way`、`support_object`、`support_behavior` 的集合。三维为效果 $\{x^{(1)},x^{(2)}\}$、覆盖 $\{x^{(3)},x^{(4)}\}$、成本 $\{x^{(5)}\}$。每维先维内平均、再截面 min-max：

$$\tilde D^{(d)}_i=\operatorname{minmax}\!\left(\frac{1}{|I_d|}\sum_{k\in I_d}x^{(k)}_i\right)$$

最终分数 $S_i=100\times\frac{1}{|D^*|}\sum_{d\in D^*}\tilde D^{(d)}_i$，$D^*$ 为完整维集合。

**边界**：① 本件 $D^*=\varnothing$，故 $S_i$ 无定义，产物写 `null`；② 不置 0、不用任何代理字段填充；③ 不发布任何金额口径的「资金强度」；④ 分母为 20,000（全表），未按城市切；⑤ 本件的产物只作**否定性证据**，不得被下游当数值使用。

## 二、计算过程（从缺：为什么不出分）

按派单书 F4，「完全不支持」档不写长计算过程，只留判定链条。本件的判定链条是四步，每步都可复核。

第一步，查子项字段是否存在：`implementation_date`、`district` 在表内，`support_way`/`support_object`/`support_behavior` 三个子键在 `policy_support` 内。第二步，查每个字段的有效值：`implementation_date` 归一后 0 行、`district` 1,165 行、三个 JSON 子键 0 行。第三步，按正本的维内平均算每维：效果 0/2、覆盖 1/2、成本 0/1，**完整维 0 个**。第四步，按正本「缺维不进平均」，分母为 0，分数不存在。

四步的原始数字全部写在 `sub_items` 与 `dims` 两段里，逐项带 `evidence`。这就是为什么本件仍然需要一个脚本：**负结论也要有可复现的证据链**，否则「算不出来」就只是散文。

### 3.1 四判定落表

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | **否** | `ads.policy_intensity` 不存在；`support_*` 三子键在 JSON 内但不可读 |
| 表数据直接支持（开发库+三方库） | **否** | 四项子指标 0 行有效值 |

| 依赖表数据支持（开发库/三方库） | **否** | 仅 `district` 有 1,165 行（5.825%） |

### 3.2 五项子指标逐项证据

| 维 | 子项 | 字段 | 有效行数 | 分母 | 判定 | 证据 |
|---|---|---|---|---|---|---|
| 效果 | 实施日完备率 | `implementation_date` | 0 | 20,000 | 不可算 | 全表 `0000-00-00`，`COUNT(col)` 会给 20,000 的假象 |
| 效果 | 支持方式完备率 | `support_way` | 0 | 20,000 | 不可算 | JSON null，`JSON_LENGTH` 返回 1 |
| 覆盖 | 支持对象种类数 | `support_object` | 0 | 20,000 | 不可算 | 同上 |
| 覆盖 | 区县落地标记 | `district` | 1,165 | 20,000 | **可算** | 872 行字面 `'NULL'`，其余空 |
| 成本 | 扶持行为完备率 | `support_behavior` | 0 | 20,000 | 不可算 | JSON null；表内无金额列可替代 |

### 3.3 区县字段的分布为什么不能当覆盖证据

`district` 是五项里唯一有值的，但它的分布让它同样不可用：

| 城市 | 有区县值的行数 |
|---|---|
| 北京市 | 887 |
| 上海市 | 205 |
| 嘉兴市 | 48 |
| 鹤壁市 | 18 |
| 深圳市 | 7 |

1,165 行里 887 行是北京（占 76% 以上），深圳只有 7 行。区名取值共 32 个，前五名全是北京的区（通州 136、海淀 113、大兴 111、顺义 103、怀柔 83），第六名是上海的普陀 54，第七名朝阳 51（北京），第八名桐乡 48（嘉兴）。

这个分布说明 `district` 不是「政策是否落地到区县」的度量，而是「哪几个城市的采集源填了区县」的度量。用它做覆盖维，实际效果是：北京政策系统性 +1、深圳政策几乎恒 0。这不是力度差异，是采集差异。

### 3.4 缺口清单（逐条给补法）

1. **`policy_support` 全 null**：补法是补 JSON 内容（三子键），三项子指标即可恢复。
2. **`implementation_date` 全零日期**：补法是回填真实实施日；现有值是导入时填的 `0000-00-00`，不是缺失标记。
3. **`district` 覆盖 5.825%**：补法是回填区县，或改用「政策标题里的区名」做代理（会引入新的假阳性）。
4. **无金额列**：补法是建「政策—扶持金额」表；这是成本维的正式口径（正本 `待建字段` 已列）。
5. **`ads.policy_intensity` 不存在**：本件产物无处落地，只到 `out.json`。
6. **`status` 单值**：入集条件恒真，`M_POLICY_VALIDITY_RATE` 已单独论证。

### 3.5 与城市级指数的交叉校验

`M_POLICY_INTENSITY_INDEX` 与本件用的是同一套五项子指标，只是聚合粒度不同。两件的探针对得上，才能说明「算不出」不是某一份脚本的 bug：

| 子项 | 本件（单条政策） | `M_POLICY_INTENSITY_INDEX`（城市） | 是否一致 |
|---|---|---|---|
| `implementation_date` 有效值 | 0 / 20,000 | 0 / 20,000 | 一致 |
| `support_way` 非空 | 0 | 0 | 一致 |
| `support_object` 非空 | 0 | 0 | 一致 |
| `support_behavior` 非空 | 0 | 0 | 一致 |
| `district` 非空 | 1,165 | 1,165 | 一致 |

两件都判「完全不支持」，但否定性证据的落点不同：那件卡在「城市级聚合没有基础」，本件卡在「单条政策的四项读不出来」。同一份源、同一组计数，两条路径都走不通，这才是「完全不支持」的充分证据。

### 3.6 与开发库 live 的差异

注册表 `source_tables` 写 `ads: ads.policy_intensity`，该表在 `gkx` 侧**不存在**（`gkx` 只有 `dwd_*` 层）。同 schema 下与 policy 相关的表只有四张：`dwd_policy_base`、`dwd_policy_base_bak_20260923`、`dwd_global_policy_base`、`dwd_global_policy_base_bak_20260923`。因此本件**不可与任何 live 数值对比**：该结果面在 `gkx` 侧不存在，属退化态、不可用，也就不存在「live 有值、本件算不出」的矛盾。

## 四、数据缺失情况

### 4.1 缺口的后果归因

后果一：**政策详情页的力度刻度条无法上线**。这一位如果硬渲染，只能显示一个常数，等于告诉用户「所有政策力度一样」——比留空更有害。

后果二：**城市级力度指数连带失效**。`M_POLICY_INTENSITY_INDEX` 按城市聚合这套子项，微观层没有值，宏观层也出不来分。两件同时判完全不支持，根因是同一个。

后果三：**「力度」这个词在项目里暂时不可用**。任何以「力度」命名的读数，在当前库内都只能落到「条数」或「层级」上（见 `M_POLICY_SUPPORT_STRENGTH`），而那是供给规模，不是力度。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

1. **`DATE` 零值不是 NULL**：`0000-00-00` 会让 `COUNT(col)` 返回全量。必须 `DATE_FORMAT(col,'%Y-%m-%d')` 归一后再判。
2. **`JSON_LENGTH(null)` 返回 1**：不是 0、不是 NULL。判 JSON 空必须 `JSON_TYPE(col)='NULL'`。
3. **`district` 的 `'NULL'` 是字符串**：872 行。`IS NULL` 判不出来。
4. **`city` 的 `'NULL'` 是字符串**：9,706 行，做城市聚合前必须排除。
5. **`rank` 的 `[""]`**：357 行，`JSON_LENGTH=1`，与上同理。
6. **金额列在招标表**：全库 123 个金额类列全在 `dwd_bid_*`；拿它顶政策金额会混淆「采购」与「扶持」。

### 4.3 为什么不再降一级：拒绝「标题词频当力度」

按正本思路，成本维在金额缺失时用 `support_behavior` 是否非空代理。这条代理失效后，理论上还能再降一级：用标题里有没有「补贴」「奖励」「资助」等词代理。本件**明确拒绝**这一步，理由有三：

第一，它与 `M_POLICY_TEXT_PARSE` 的支持工具标签完全重复——那件已经证明这类词有 57.5588% 是泛词命中，精度不够。

第二，它会把「力度」偷换成「文种」。资金申报通知的标题天然带这些词，而综合性产业规划不带，但后者的实际力度可能更大。

第三，一旦这么做，指标就无法与 `M_POLICY_INTENSITY_INDEX` 对齐——那件没有这一层代理，两件的「力度」会变成两个不同的东西。

### 4.4 若甲方补齐后的口径升级路径

第一步补 `policy_support` 三子键（`support_way`/`support_object`/`support_behavior`），四项子指标中三项可恢复；第二步回填 `implementation_date`，效果维完整；第三步回填 `district`（或明确「只统计有区县采集源的城市」），覆盖维完整；第四步建「政策—扶持金额」表，成本维从代理转正式。四步做完，三维五项才第一次全部可算，本件才能从「完全不支持」升级。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答：政策力度评分这套三维五项，在 `gkx.dwd_policy_base` 上能不能算；如果不能，缺的是哪一项、补上之后能不能算。

### C.2 需求语义锚定

「力度」有两种读法：**资源投入强度**（给多少钱）与**执行约束强度**（写没写实施日、支持对象、扶持行为）。正本选的是后者——它用「是否写明」而不是「写了多少」来度量。这个选择本身是合理的（库内无金额），但它把指标完全绑在字段完备度上，字段一空，整套就空。

### C.3 权威与学术构建方法谱系

#### C.3.1 族 A：PMC 指数

一级变量 9—10 个、二级变量若干，人工赋值后加总。优点是可解释、可加总；缺点是需要人读全文，2 万条量级不可行。

#### C.3.2 族 B：政策工具编码

按供给型/需求型/环境型工具分类赋强度。编码单位是条款，不是政策，与正本口径不同层。

#### C.3.3 族 C：金额分档

最接近「力度」本意。需要「政策—金额」表，库内无。

#### C.3.4 族 D：文本完备度代理

本件采用。它度量的是「写得全不全」，与「给得多不多」只是弱相关——这一点正本没有回避，Cost 维的说明里写了「无金额不编造拨款」。

### C.4 数据可行性详细分析

| 依赖 | 结构 | 数据 | 结论 |

### C.5 推荐构建方案（工程可执行）

1. 当前不上线该刻度条，页面用「暂不可用」占位；
