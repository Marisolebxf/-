## 摘要

本指标要回答的是「现行有效的政策占多少」。要回答它，至少需要两个信息：政策当前是否有效，以及有效到哪一天。本库表里这两件事各有一列对应——`status` 与 `expire_date`——所以从字段清单看，这个指标「应该有」。实测结果恰好相反：`status` 全表 **20,000** 行只有 **1** 个取值「有效」，`expire_date` **0 行有值**、**20,000 行全空**，`implementation_date` 同样 **0 行有值**。

注册表公式是 $\text{有效率}=\dfrac{\text{status=1 且（expire\_date 为空或 ≥ 今日）}}{\text{COUNT(*)}}\times 100$。把实测值代进去：条件一留下 20,000 行，条件二也留下 20,000 行，分子等于分母，结果恒为 **100.00%**。一个永远等于 100% 的比率不是「政策全部有效」，而是「失效这件事在库里没有被记录过」。本件因此不发布这个 100.00%，只把它登记为**构造性结果**（`constructive_validity_rate_pct`），并同时给出 `publishable=false` 与 `registered_metric_value=null`。

否定性证据共五条，逐条落在产物 `negative_evidence` 里：E1 取值域退化（1 个值 / 20,000 行）、E2 失效日整列空、E3 实施日整列空、E4 发布日虽可用但不能替代失效日、E5 「失效日早于发布日 0 行」是空列造成的假一致。这五条合起来说明：本指标缺的不是算法，是**判定失效所需的原始事实**。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

「政策有效率」挂在政策分析页的指标卡区，与政策总量、级别分布、类型分布并列。它的展示形态是一个百分比加一句注解，例如「现行有效政策 N 条，占 R%」。政策库的筛选器也依赖它：用户点「只看现行有效」时，后端需要知道哪些行已经失效。

需求把它归入「政策基础指标模型」的统计能力，属于政策多维分类统计的一部分。它与同批的政策时序、政策类型分布不同：那两件统计的是**发布行为**，本件统计的是**存续状态**——发布行为在库里留下了日期，存续状态却需要另一套字段（失效日、废止日、状态值域）才能还原。

### 1.2 为什么需要这个指标

第一，它决定政策库的可用性判断。一份 2013 年发布、2018 年已被新文件替代的政策，如果仍以「有效」出现在推荐结果里，会误导企业按旧补贴标准准备材料。有效率的业务价值不在那个百分比，而在「库里的有效性标注是否可信」。

第二，它是政策分析的基期过滤器。政策力度、政策匹配、产业适配等下游指标都写「入集：`status=有效` 且未过期」。如果有效性判定不可信，这些指标的分母就只是「全表」的别名，所谓「有效政策」的筛选等于没有筛选。

第三，它是最容易被「看起来有数」骗过去的指标。字段在、类型对、SQL 能跑、结果非空，四道检查全过；唯一的问题是结果恒为 100%。这类指标如果直接上页面，读者会得到「本市政策 100% 有效」的结论，而这个结论与政策是否真的失效毫无关系。

### 1.3 需求文档是否给出定义方法

**需求给了指标名与「有效/失效」的语义，但把判定条件留给了字段。** 注册表 `formula` 写的是：

$$\text{validity\_rate}=\frac{\mathrm{COUNT}\left(\text{status}=1\ \wedge\ \left(\text{expire\_date}\ \text{IS NULL}\ \vee\ \text{expire\_date}\ge \text{today}\right)\right)}{\mathrm{COUNT}(*)}\times 100$$

它隐含了两个假设：① `status` 至少有「有效」与「失效」两个取值；② `expire_date` 要么有值（预设截止日），要么为空（长期有效）。这两个假设在本库都不成立——`status` 只有一个取值，`expire_date` 全空。需求没有规定「当两列都退化时该怎么处理」，本件补的规则是：**不发布构造性结果，判不支持，并列出补数清单**。

### 1.4 类似指标权威机构构建方法可行性分析概要

| 方法族 | 代表做法 | 口径要点 | 与本件的差 | 贴合度 |
|---|---|---|---|---|
| A 状态字段直查 | 政策库通用 | `status` 枚举「有效/失效」，直接 `COUNT` | 本库 `status` 只有 1 个值，A 族退化 | 低（结构在、值不在） |
| B 失效日比较 | 法规库常用 | 以 `expire_date` / `abolish_date` 与统计日比较 | 本库 `expire_date` 全空、无废止日列 | 低 |
| C 版本替代链 | 法规文本库 | 新文件明确「废止」旧文号，按文号建替代图 | 本库无「被替代文号」字段，且标题不含旧文号 | 低 |
| D 发布日 + 有效期年限 | 部分地方库 | 按文种给默认有效期（如 5 年），超期视为失效 | 属自造规则，会把长期规划误判失效 | 低（不采用） |

**三句结论**：① A 族是唯一不需要外部假设的做法，但本库 `status` 取值域只有一个值，直查等于恒真；② B 族需要 `expire_date`，实测 0 行有值，无法执行；③ C/D 两族都需要本库不存在的字段或外部规则，本件不采用——尤其 D 族，用「发布满 N 年即失效」造出来的失效率看似合理，实际是把规则当数据。

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设 $V$ 为满足注册表两条件的政策条数，$N$ 为分母，则

$$V=\mathrm{COUNT}\left(\text{status}=\text{有效}\ \wedge\ \left(\text{expire\_date}\ \text{IS NULL}\ \vee\ \text{expire\_date}\ge \text{today}\right)\right)$$

$$R_{\text{validity}}=\frac{V}{N}\times 100\%,\qquad N=\mathrm{COUNT}(*)=20{,}000$$

**边界**：① 20,000 是库内存量，不是全国政策总量；② 本件算出的 100.00% 是**构造性结果**，不可作为指标值发布；③ 本件只能报告「未标注失效」的行数，不能报告「失效」的行数，因为库内没有任何一行被标为失效；④ 分母取全表 20,000，其中 **9,706 行无城市**（含 2,174 行国家级），本指标不按城市切片，故该缺口不影响分母选择，但任何后续按城市复算的件都必须把这 9,706 行单列；⑤ 不采用「发布满 N 年即失效」这类外生规则。

## 二、计算过程

### 2.1 为什么这个公式在本库必然等于 100%

公式的分子是两个条件的交集。条件一是 `status=1`（有效）：实测全表 20,000 行都取「有效」，取值域只有 1 个值，没有「已废止」「已撤销」「已修订」等对照项，因此条件一对任何一行都为真，留下的行数是 20,000。条件二是 `expire_date IS NULL OR expire_date >= today`：实测 `expire_date` 有值 0 行、空 20,000 行，因此「IS NULL」对每一行都为真，条件二留下的行数同样是 20,000。

两个条件同时恒真，交集就是全表，分子 = 分母 = 20,000，比率 $=100.00\%$。这个推导不依赖任何一行政策的具体内容：把 20,000 行换成任意 20,000 行，只要两列的填充状态不变，结果仍是 100.00%。这正是「无判别力」的定义——**输出对输入不敏感**。

### 2.2 三个容易被混用的口径

第一个口径是**失效率**：被废止、被替代、到期未续的政策占比。它需要「失效事实」——废止日、被替代文号、或至少一个「已失效」的状态值。本库三者都没有，因此失效率**不可算**，不是 0。

第二个口径是**未标注失效占比**：库内没有标注任何失效信息的行占比。按实测，这个值是 100.00%，但它的语义是「未标注」，不是「有效」。这两个词在中文里只差一个字，在业务上差一个结论：前者说的是数据状态，后者说的是政策状态。

第三个口径是**构造性有效率**：把注册表公式原样执行得到的数。本件保留它作为证据（`constructive_validity_rate_pct=100.0`），同时用 `publishable=false` 阻断发布。保留的理由是可复核——甲方拿公式跑一遍会得到同一个数，再看到「为什么不能发布」的说明，比直接删掉这个数更容易达成一致。

### 2.3 探针脚本与产物

`metrics/repro/M_POLICY_VALIDITY_RATE.py` 只读两份共用快照，不连数据库。它做四件事：读 `status` 的取值分布与 `expire_date` / `implementation_date` 的填充数；按注册表公式复算构造性比率；扫描三项一致性异常（失效日早于发布日、实施日早于发布日、发布日非法）；把五条否定性证据写入 `negative_evidence`。产物是 `metrics/repro/out/M_POLICY_VALIDITY_RATE_out.json`，正文引用的每个数都能在 `headline`、`registered_formula`、`negative_evidence`、`anomaly_scan` 里找到同名键。

### 2.4 为什么不去「造」一个失效率

最常见的补救是给不同文种配一个默认有效期，用「发布日 + 默认年限 < 今日」判失效。这条路径在技术上能跑通，本件不采用，理由有三。第一，同一文种的有效期差异极大：一份五年规划的有效期是五年，一份申报通知的有效期可能只有两周，用同一个年限会把两类都判错。第二，它会把「长期有效」的法律、条例判成失效，而这类文件在库内占相当比例。第三，也是最关键的，它把规则输出伪装成数据输出——甲方看到的是一个有零有整的百分比，无法从数字本身看出它来自假设。因此本件宁可交一个空的指标值，也不交一个由规则生成的失效率。

### 3.4 结构支持判定

两列的**结构**都成立：`status` 是枚举型字段（实测取值「有效」），`expire_date` 是 `date` 类型，`information_schema.columns` 里都能查到。所以问题不是「缺列」，而是「缺数」——这一点必须写清楚，因为它决定了补数路径：不需要改表结构，只需要回填值域与日期。

需要提醒的是：`status` 的取值域退化比 `expire_date` 全空更隐蔽。空列一眼能看出来，单值枚举看起来却像「数据质量很好，全部有效」。如果没有先跑一次 `GROUP BY status`，本件很可能被写成「政策有效率 100%，完全支持」。

### 3.5 与 live 开发库的差异

live 侧的 `dwd.policy_base_info` 在 20261019 的实测里是 0 行，`ads.policy_validity_rate` 只有演示批次的单值 92.16%。本件不引用该值：演示批次的 92.16% 对应的是造出来的「失效 7.84%」语料，与 `gkx` 底表 20,000 行没有任何对应关系。若甲方拿页面上的 92.16% 与本文的 100.00% 对照，答案是两者都不是真实有效率——一个是造数，一个是恒真式。

### 3.6 与相邻政策件对账

| 对账项 | 相邻件 | 相邻件口径 | 本件口径 | 是否一致 |
|---|---|---|---|---|
| 全表行数 | `M_POLICY_TOTAL_COUNT` | 20,000（`COUNT(*)`） | 20,000 | 一致 |

### 3.7 字段口径的传递关系

本指标是政策五件里唯一以「状态」为输入的件，但它的结论会向下游传递：政策推荐、政策匹配、政策力度三个方向都会写「入集：有效政策」。本件判「有效性不可判别」之后，这三个方向的分母必须改写成「全表」并在文档里声明，不能继续沿用「有效政策」的说法。这是本件作为负结论件的主要交付价值——它不是一个孤立的「算不出」，而是给下游三个件提供了一条统一的口径修正。

## 四、数据缺失情况与结论边界

### 4.1 缺口的后果归因

**`status` 单值 → 条件一失去判别力。** 后果是所有「按有效性筛选」的下游动作都变成全表扫描。政策推荐、政策匹配、政策力度这些指标里写的「入集：有效政策」，在本库等价于「入集：全部政策」。这不是这些指标的错，但它们必须在文档里声明这一点，否则读者会以为筛选发生过。

**`expire_date` 全空 → 条件二失去判别力，且「未过期」无法证明。** 后果是本指标只能报告「未标注失效 100%」，不能报告「现行有效 100%」。两者的差别在发布文案上必须体现：前者是数据事实，后者是政策事实。

**无废止日、无替代文号 → 失效率不可算。** 这不是「暂时算不准」，是「没有输入」。任何声称能算出失效率的做法，实际上都在用发布日加一条自造的有效期规则，这属于把假设当数据。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

- **`status` 全为「有效」不等于政策都有效**：它是采集时统一填的默认值，不是逐条核验的结果。
- **`expire_date` 全空不等于「长期有效」**：语义上「空」可能是「长期有效」，也可能是「未标注」，本库没有任何字段能区分这两者。
- **`implementation_date` 全空**：不能用「实施日 + 有效期」侧算时效，这条路同样断了。
- **「失效日早于发布日 0 行」是假一致**：因为失效日全空，这个比较永远为 0 行，不能当作数据质量通过。
- **分母 20,000 的构成**：其中 9,706 行无城市、2,174 行为国家级；本指标不分城市，但按城市复算的件不能用 20,000 当城市分母。
- **`table_rows` 的估算值低于实测**：InnoDB 估算比 `COUNT(*)` 少数个百分点，任何按估算值算的占比都会偏大，本件一律用 `COUNT(*)`。

### 4.3 可构建但存在缺口（不是「无法构建」）

1. **「未标注失效」计数**：已可算，20,000 行全部属于此类；只能作为一个数据质量指标，不能当政策有效率。
2. **按发布年分布的有效标注**：已可算，但每年都是 100%，无信息量。
3. **按城市的有效标注**：已可算，同样每年每市都是 100%，且 9,706 行无城市需单列。
4. **失效率**：不可算，缺失效事实。
5. **政策平均存续年限**：不可算，缺失效日；若用「统计日 − 发布日」代替，得到的是「库内政策年龄」，不是存续年限，本件不做这种替换。

### 4.4 结论与发布建议

**不建议发布任何「政策有效率」数值。** 若页面必须有一个位置，建议展示为「有效性标注覆盖：0 / 20,000（待补数）」，把缺口显式暴露，而不是显示 100.00%。已发布的 92.16% 一类数值应下架，因为它来自演示批次。

**待甲方裁决点**：① `status` 是否允许扩值域（现有值「有效」是否等价于「未标注」）；② `expire_date` 为空时应解释为「长期有效」还是「未标注」（这决定补数时的填写规则）；③ 是否接受用废止公告单独建一张失效事实表（若接受，本指标可在不改主表的前提下补齐）。

### 4.5 对下游指标的影响清单

| 下游件 | 原文写法 | 本件生效后的正确写法 | 影响程度 |
|---|---|---|---|
| `M_POLICY_INTENSITY_INDEX` | 入集「有效且未过期」 | 入集「全表 20,000」 | 无实质变化（原本等价） |
| `M_POLICY_INDUSTRY_FIT` | 入集「有效」 | 入集「全表」 | 无实质变化（原本等价） |
| `M_CHAIN_POLICY_MATCH_SCORE` | 入集「有效政策」 | 入集「全表」并声明有效性未标注 | 需改文案 |
| 政策推荐类 | 「现行有效」标签 | 改为「库内收录」标签 | 需改 UI 文案 |

影响程度一栏写「无实质变化」不是小事：它说明下游件此前写的「有效筛选」从未真正过滤过任何一行。这一点如果不写清楚，甲方会以为本件的负结论只影响一张指标卡。

4. 异常扫描：发布日非法 3 行，其余两项因列全空而为 0 行。

### C.3 不可算闭环

1. 失效率：缺失效事实（无值域、无失效日、无废止日、无替代文号）。
2. 现行有效条数：`status` 单值，无法区分。
3. 平均存续年限：缺失效日。
4. 按城市的有效率差异：分母可取（10,294 行有城市），但分子同样恒真，差异恒为 0。

### C.4 结论

按四档定义判**完全不支持**：结构与公式都在，但两个判定输入同时退化，指标没有判别力。不能判「完全转换支持」，因为「现在就能经转换得到」不成立——转换需要新事实；也不能判「部分支持」，因为不存在「部分可算」的维度：所有城市、所有年份的有效率都是同一个 100.00%。

### C.5 补数后的验收口径

补数一旦落地，本件不需要重写结构，只需把三个断点接上：`status` 的取值域达到 2 个以上（至少含「有效」与一种失效态）、`expire_date` 非空率达到可解释水平、废止日或替代文号至少有一个可用。验收时按三条判：① 有效率不再恒为 100.00%（若仍恒真，说明补的是空值不是事实）；② 分子分母都能按城市与年份复算，且分母之和回到 20,000（其中 9,706 行无城市者单列）；③ 任取 20 条被判失效的政策，能在原文或废止公告里找到依据。三条全过，本件可从「完全不支持」升为「完全转换支持」，升档依据是这次补数，而不是重跑脚本。
