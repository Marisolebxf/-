## 摘要

「智能摘要与结论推送」挂在《科技信息展示系统》政策分析评价→结果解读报告多维展示之下（§1.1.1.1.4.2.2.2.4），产品任务是用 NLP 自动生成报告页上**可编辑**的政策摘要与管理结论，高亮关键点与应用建议，让管理层不必读全文即可掌握政策精要，并可推送到报告页或移动端。需求原文只给了能力描述（「可编辑」「高亮」「推送」），未给任何算法、字段或评价方法。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

本指标挂接《科技信息展示系统和科技专题服务系统》**科技政策跟踪 → 政策分析评价 → 结果解读报告多维展示 → 智能摘要与结论推送**（§1.1.1.1.4.2.2.2.4）。其上位模块的任务是「将政策评估成果进行深入解读与多元呈现」，通过「数据驱动分析与智能结论摘要，高亮关键趋势及应用建议，实现报告内容的个性化展示和推送」。

产品形态是报告页上的一个**摘要卡片**：用户选定一组政策（一个评估批次、一个专题、一个区域），系统自动生成 300—500 字的政策摘要与若干条管理结论，关键信息（时间节点、金额、适用对象、关键动作）以不同颜色高亮，用户可在线编辑，编辑后的版本可推送到管理层报告页或移动端。它是「结果解读报告多维展示」四项功能中唯一涉及文本生成的一项，其余三项（热点问题看板、分主题分指标互动解读、多媒体辅助解读）都是展示层。

### 1.2 为什么需要这个指标

政策分析评价的产出通常是图表与指标：热点分布、力度评分、效果指数。但对管理层而言，图表回答「是多少」，不回答「所以呢」。一份 20 页的评估报告，决策者真正需要的是三句话：这批政策在解决什么问题、钱和措施落在哪、下一步该动什么。摘要与结论就是把指标语言翻译成管理语言的那一层。

从产品链路看，它还是「推送」的前置条件：只有先有结构化的、可编辑的摘要与结论，才谈得上按角色推送、按模板归档、按版本追溯。因此需求把「可编辑」写进功能名，指向的是一个**带版本与状态的内容对象**，而不是一次性生成的文本块。这也解释了为什么王惠口径里必须有一维叫「推送就绪」——没有状态管理，摘要就只是页面上的临时字符串，无法进入流转。

## 二、计算过程

### 2.1 方法选择：抽取式代理而非生成式黑箱

摘要生成有两条主流路径：抽取式（从原文挑句子）与生成式（模型重写）。抽取式的优点是每个输出句都能回溯到原文，用户可以核对「这句话是不是政策原文」，缺点是句子之间可能不连贯；生成式的优点是连贯、可读，缺点是可能幻觉、无法逐句核对。本件选抽取式作为代理，不是因为它效果更好，而是因为它**可复核**：在没有任何参考摘要与人工评分的条件下，唯一能证明「摘要能力存在」的方式，就是证明「系统能从原文里稳定挑出与标题相关的句子」。

具体实现是 TextRank 的轻量代理：把标题与每个候选句都拆成字符 bigram，用 Jaccard 重合度排序，取前 3 句。它不是完整的图排序（没有句子间相似度矩阵、没有迭代收敛），但保留了「与主题相关的句子得分更高」这一核心机制。这样做的代价是排序质量不如完整 TextRank，收益是脚本零依赖、可离线、每次运行结果一致（固定种子）。

### 2.2 步骤 1｜总体、去重与主料判定

总体为 `gkx.dwd_policy_base` 20,000 行，去重键 `id`，20,000 个不同值。`status` 全表单一值「有效」，不做状态过滤。主料判定为「正文长度 >100 字或摘要非空」：正文太短（<100 字）的公告类文件无法支撑 300—500 字摘要，摘要字段可作兜底；两者都空则判为「主料不可用」。

实测主料可用 18,955 条（94.77%）。这个数比正文非空 19,203 低 248 条，差在「正文非空但不足 100 字」与「正文空但摘要非空」的交叉上：前者被主料阈值排除，后者被摘要兜底救回。两个方向的差额几乎抵消，最终落在 94.77%。

### 2.3 步骤 2｜上下文齐备率

上下文取三个字段：`title`（摘要锚点）、`ministry`（发文机关，用于「谁发的」）、`publish_year`（时间，用于「什么时候」）。三项非空计数之和除以 $3N$：title 20,000、ministry 19,989、publish_year 19,997，合计 59,986 / 60,000 = 99.9767%。

这个数很高，但它只说明「上下文标签齐」，不说明「上下文够用」。摘要模板还需要「关键词 / 主题 / 要点」三类引导字段，而这三列的真实值是 0 / 2 / 0。也就是说，99.98% 是三个基础字段的齐备率，不是摘要上下文的完整度；后者要把引导字段算进来，实际只有 3/6 类可用。

### 2.4 步骤 3｜结论句抽取与归一

从 20,000 条政策中取「有正文」的 18,763 条为池，固定种子 42 随机抽 2,000 条。每条按 `。！？；` 分句，保留长度 ≥20 字的句子；用标题 bigram 与句子 bigram 的 Jaccard 重合度排序，有候选句即计「可出结论」，每篇最多取 3 句。

实测 2,000 条中 1,999 条可出结论（99.95%），共 5,554 句，平均 2.78 句/篇。按 3 句封顶归一到 0—1，得 92.61%。这个数接近满分，原因是「可出结论」的门槛很低：只要正文里有一句 20 字以上、与标题有 bigram 重合的句子，就算可出结论；绝大多数政策都能满足。它证明的是「系统不会空手而归」，不是「结论有洞察」。

### 2.5 步骤 4｜推送就绪与缺维处理

推送就绪维要求 `dwd_policy_summary(push_status)` 与 `dwd_policy_summary_edit_log` 两张表：前者存摘要正文、状态（草稿/已审/已推送）、目标渠道；后者存编辑版本与操作人。本件用 `information_schema.tables` 探针查 `gkx`，两张表都不存在，`tables_found = []`，该维不可算。

按「缺维不进平均」，合成只用 D1 与 D2：D1 = (94.77% + 99.9767%) / 2 = 97.38%，D2 = 92.61%，平均 = 94.99%。若把 D3 按 0 纳入分母，得分会掉到 63.33，等于用「表不存在」去惩罚摘要能力；这不是本件要表达的意思。

### 2.6 步骤 5｜质量证据的缺口

本件没有任何质量证据。ROUGE 需要参考摘要，库内没有；人工评分需要标注集，库内没有；推送后的阅读率、采纳率需要状态表与埋点，库内没有。三者都没有的情况下，94.99 只能读成「具备生成条件」，不能读成「生成质量高」。

这不是方法选择的问题，是数据边界的问题。即便换成生成式模型，只要没有参考摘要与人工评分，就无法证明质量。因此本件在 `out.json` 里单独放了 `quality_caveat` 字段，明确写出「三维质量证据全部缺失」，并在 §五 建议页面把该分数命名为「就绪度」而不是「质量分」。

### 2.8 结果解读：94.99 的三种误读

第一种误读是「摘要质量 94.99 分」。分数只覆盖「能不能生成」与「上下文齐不齐」，不覆盖「生成得好不好」；质量维完全没有数据。第二种误读是「推送能力 94.99 分」。推送维不可算，分数里根本没有它；推送所需的两张表都不存在。第三种误读是「所有政策都能生成高质量摘要」。1,999/2,000 只说明「能抽出一句 20 字以上、与标题有重合的句子」，不说明这句话有信息量；示例里有「附件下载：AB6201000-2011-837.pdf」这种句子，也被计为可出结论。

正确的读法是分维读：主料 94.77%、上下文 99.98%、结论 92.61%、推送不可判。四个数放在一起，能回答的是「这批政策具备生成摘要的文本条件」，不能回答「生成的摘要好不好」。

### 2.9 边界条件与异常值

第一，HTML 噪声：部分正文含 `&nbsp`、`附件下载` 等页面残留，分句后会产出无信息句，仍被计为「可出结论」，这是代理的假阳性。第二，短正文：正文 <100 字的政策被主料阈值排除，但它们的摘要可能仍有内容，本件用 `abstract` 兜底，兜底率 60.80%，仍有部分政策两者都空。第三，抽样偏差：固定种子 42 只保证可复现，不保证样本代表全库；2,000 条占 18,763 条的 10.66%，置信区间约 ±2%，足以支撑「能力存在」的判断，不足以支撑「精确比例」。第四，字段口径：上下文用 `publish_year` 而非 `publish_date`，因为快照只有年份；若用日期，20,000 行全有值，齐备率会更高，但对摘要质量没有实质影响。

### 2.10 分维拆解：94.99 是由哪两个数撑起来的

把合成过程完全摊开，可以看清分数结构：

| 步骤 | 计算式 | 结果 |
|---|---|---|
| 主料率 | 18,955 / 20,000 | 94.77% |
| 上下文率 | (20,000 + 19,989 + 19,997) / 60,000 | 99.9767% |
| D1 合成 | (94.77 + 99.9767) / 2 | 97.38% |
| D2 归一 | min(1, 2.78 / 3) | 92.61% |
| 总分 | (97.38 + 92.61) / 2 | 94.99 |

可以看到 D1 被上下文率拉高：上下文 99.98% 几乎满分，主料 94.77% 才是真正的短板。若只看主料，94.77 与总分 94.99 只差 0.22，说明上下文维在平均里几乎不提供区分度；它的作用更像「确认锚点存在」，而不是「衡量摘要质量」。

D2 的 92.61 由平均句数 2.78 除以 3 得到。这个 3 是本轮设的封顶值，依据是「300—500 字摘要通常容纳 3—5 句结论」。若把封顶改成 5，D2 会掉到 55.6，总分掉到 76.5；若改成 2，D2 满分为 100，总分升到 98.7。也就是说，**总分对封顶值高度敏感**，而这个封顶值没有行业标准支撑，是本件最大的口径不确定性。发布时必须把 3 句封顶写进注脚，否则同样的数据可以合法地算出 76 到 99 之间的任意分数。

### 2.11 敏感性：三种改口径的后果

| 改动 | D1 | D2 | 总分 | 说明 |
|---|---|---|---|---|
| 当前口径 | 97.38 | 92.61 | 94.99 | 2/3 维，3 句封顶 |
| 封顶改 5 句 | 97.38 | 55.60 | 76.49 | 更严的结论密度要求 |
| 封顶改 2 句 | 97.38 | 100.00 | 98.69 | 更松，几乎无区分度 |
| 推送维按 0 计入 | 97.38 | 92.61 | 63.33 | 用「无表」惩罚能力，不建议 |
| 主料阈值改 50 字 | 约 96.1 | 92.61 | 约 94.4 | 短公告被纳入 |

这张表的用途不是让读者挑一个好看的数，而是说明「94.99 不是唯一解」。任何单一分数都必须带口径注脚：几维参与、封顶多少、阈值多少、抽样多大。缺任何一项，分数都不可复核。

### 3.3 分布形状与阈值选择

本件的「阈值」只有两个：主料 100 字、结论句 20 字。两者都是工程阈值，不是行业标准。100 字的选择依据是「少于 100 字无法支撑 300—500 字摘要」；20 字的选择依据是「少于 20 字的句子多为标题或标点片段，信息量不足」。若甲方要求更严格的摘要质量，需另设人工评分或 ROUGE 阈值，不能用这两个工程阈值代替。

### 3.4 与产品需求的三处对不上

第一处是「可编辑」。原文写「可编辑结论与政策摘要」，隐含着编辑后的版本要留存、要有状态（草稿/已审/已推送）、要能追溯谁改了什么。库内没有任何承载这些的对象：`dwd_policy_summary` 与 `dwd_policy_summary_edit_log` 都不存在。本件能算的只是「生成前的原料是否齐」，算不了「编辑与流转是否顺」。

第二处是「高亮关键点和应用建议」。高亮要有结构化要点，通常是 `keypoints` 字段（JSON 数组）或实体抽取结果。`keypoints` 实测 0 行有值，`keywords` 也是 0，`theme` 只有 2 行。本件的结论句只按标题重合度排序，没有实体识别，也没有「应用建议」的生成逻辑；「高亮」在产品上可以前端做，但「高亮什么」目前没有数据依据。

第三处是「推送到报告页或移动端」。推送需要目标渠道、状态、回流三个要素。库内既无渠道配置，也无状态字段，更无阅读/采纳埋点。本件把这一维整体记为不可算，而不是记 0%，原因正在于此：0% 会被读成「推送全失败」，实际是「没有推送这回事」。

### 3.5 与同族「政策文本类指标」的口径差异

同批 POLICY 指标里，`M_POLICY_DEEP_166_1`（焦点）、`M_POLICY_DEEP_168_1`（效果）都从 `content` 出发，但它们的出口是「主题分布」与「效果评分」，本件的出口是「文本生成就绪度」。三者共用同一个 20,000 条分母，差别在加工层：前者做关键词/主题聚合，后者做句子抽取。共用分母的好处是同一批政策在不同卡片上的数量一致；风险是若某张卡片改了分母（例如只算有正文的 18,763），同页数字会对不上。本件在 `out.json` 里同时记录 `population.rows=20000` 与 `rows_with_content_snapshot=18763`，就是为了让读者能核对两个分母的差别。

## 四、数据缺失情况

### 4.1 缺口清单

| # | 缺口 | 影响维度 | 后果 | 修复路径 | 优先级 |
|---|---|---|---|---|---|
| 1 | 无 `dwd_policy_summary` / 编辑日志 | 推送就绪 | 整维不可算 | 建摘要表与版本表 | 高 |
| 2 | 无参考摘要 | 质量评测 | ROUGE 不可算 | 人工写 200—500 条参考摘要 | 高 |
| 3 | 无人工评分 | 质量评测 | 可读性 / 准确性不可测 | 组织专家抽样评分 | 中 |
| 4 | `keywords` 0 / `theme` 2 / `keypoints` 0 | 上下文增强 | 摘要只能靠标题与正文 | 关键词抽取 / 主题标注 | 中 |
| 5 | 无推送回流埋点 | 效果评估 | 阅读率 / 采纳率不可测 | 推送端埋点 | 低 |

### 4.2 后果归因：哪些话不能说

第一，不能说「摘要质量 94.99 分」。分数只覆盖就绪度，质量维无数据。第二，不能说「系统已支持推送」。推送表不存在，推送维不可算。第三，不能说「1,999/2,000 说明摘要准确」。可出结论的门槛是「有一句 20 字以上、与标题有重合的句子」，示例里的「附件下载：AB6201000-2011-837.pdf」也满足，这不是准确。第四，不能说「上下文完备」。3/6 类可用，关键词、主题、要点三类引导字段全空。

第五，不能把「主料 94.77%」当成「94.77% 的政策能生成好摘要」。主料只证明「有字可读」，不证明「字里有信息」。第六，不能把「平均 2.78 句」当成「每篇结论都有 2.78 条洞察」。句数是候选句数，不是有效结论数。第七，不能把「2/3 维」的 94.99 与「3/3 维」的分数直接比较。缺维不进平均会让分数偏高；一旦补上推送维（若推送表为空或状态全草稿），分数会显著下降。

### 4.3 判档说明

本件判「部分支持」而不是「完全转换支持」，核心证据是推送就绪维无表、质量维无数据。按 §〇 的定义，「完全转换支持」要求「现在就能经转换得到该指标」，而推送状态不是转换能补出来的，是要建表与埋点的数据；质量评测不是转换能补出来的，是要人工标注的数据。

若强行判「完全直接支持」，甲方按 §三 核验时会发现推送维永远不可算、质量维没有任何证据，反而损害可信度。降档并写清「就绪度 ≠ 质量」，比给一个看起来很高的分数更诚实。

### 4.4 缺口对结果的量化影响

若补上 `dwd_policy_summary` 与编辑日志，推送维会从「不可算」变成真值，三维分数才第一次有完整分母；若推送状态初始全为「草稿」，推送就绪率会接近 0，总分可能从 94.99 掉到 63 左右。若补上参考摘要，ROUGE 才能计算，质量才有可比的数；若补上人工评分，才能判断「94.99 的就绪度」是否对应「可接受的质量」。

这两项修复会改变分数的含义，而不只是增加维度。因此当前分数只能作「能力存在」的证据，不能作「质量达标」的基线；任何「摘要质量 95 分」的宣传都不成立。

### 4.5 与「智能摘要」产品承诺的差距清单

| 产品承诺 | 本件实测 | 差距性质 |
|---|---|---|
| 自动生成可编辑摘要 | 主料可用 94.77%，能出结论句 | 生成侧具备条件，编辑侧无表 |
| 高亮关键点 | `keypoints` 0 行、`keywords` 0 行 | 无结构化要点，前端无高亮依据 |
| 高亮应用建议 | 无「建议」字段、无建议生成逻辑 | 完全缺失 |
| 管理层快速获得精要 | 抽样平均 2.78 句 | 有候选句，未验证精要程度 |
| 推送到报告页 / 移动端 | 推送表与编辑日志均不存在 | 整维不可算 |
| 个性化展示 | 无用户画像、无角色配置 | 不可算 |

这张表的作用是把「指标分数」还原成「产品差距」。94.99 的就绪度掩盖不了六项承诺里有三项完全缺失（建议、推送、个性化）、一项半缺失（高亮无数据依据）。如果只汇报分数，甲方会以为功能接近完成；把差距清单摆出来，才能对齐预期。

### 4.6 一个具体样本的走查

以 `_out.json` 中 `examples` 的第一条为例：标题给出政策主题，正文分句后取与标题 bigram 重合度最高的句子，输出一句 20 字以上的原文片段。走查可以发现三个问题：一是片段可能以「附件下载」开头，说明正文含 HTML 残留；二是片段与标题重合度高，但不一定包含金额、时限、适用对象这些决策要素；三是片段之间没有逻辑连接词，拼在一起像要点罗列而不是一段摘要。

这三点都不是脚本 bug，而是抽取式方法的固有局限。要解决，需要在抽取后加一层「要素识别 + 重排」，或者直接上生成式模型。前者需要实体标注数据，后者需要参考摘要做回归测试；两者本库都没有。因此本件把这个样本作为「能力存在但不完美」的证据，而不是「摘要可交付」的证据。

## 五、结论与发布建议

### 5.1 结论

本件方法可复现、脚本可在本目录直接跑通、每个数可追溯，但**不具备发布「摘要质量」或「推送能力」的业务条件**。可发布的内容是：主料覆盖率、上下文字段齐备率、结论句可抽取率、推送维不可算的说明。不可发布的内容是：单一「摘要质量分」、推送就绪结论、任何「生成质量」评价。

### 5.2 发布建议

第一，页面把分数命名为「摘要就绪度」而不是「摘要质量」，并在旁边固定一行注脚：「质量评测缺参考摘要与人工评分，当前分数只表示能否生成」。第二，推送区块显示「待建表」而不是「0%」，0% 会被读成「推送全失败」，实际是「没有推送表」。第三，结论句展示必须带原文出处，允许用户点回政策全文核对；没有出处的句子不能进报告。第四，与 `M_POLICY_DS_11_POLICY_EVAL_012` 同页的其他解读件（热点看板、互动解读）共享同一批政策分母，避免同一批政策在不同卡片上数量不一致。

## 附录 C　构建方法可行性报告（完整版）

**一、可复制的方法路径。** 摘要生成有抽取式与生成式两条路线：抽取式可追溯到原文，适合合规与审计场景；生成式可读性更好，但需要模型与提示工程。本件选抽取式作为代理，是因为它能在零训练、零参考摘要的条件下证明「系统能从原文挑出相关句」，这是就绪度的最小证据。生成式列为二期，等有参考摘要与人工评分后再上。

**二、为什么不做质量分。** 质量评测需要参考摘要（ROUGE）、人工评分（可读性 / 准确性）或推送回流（阅读率 / 采纳率），三者本库都没有。没有这些数据，任何「质量分」都是把就绪度换个名字，属于口径造假。本件宁可给一个 94.99 的就绪度并注明「不是质量」，也不给一个看起来完整的质量分。

**三、阈值与抽样的取值依据。** 主料阈值 100 字、结论句阈值 20 字都是工程阈值，依据是「能否支撑 300—500 字摘要」与「句子是否有足够信息量」，不是行业标准。抽样 2,000 条占 18,763 条的 10.66%，固定种子 42 保证可复现；置信区间约 ±2%，足以支撑「能力存在」，不足以支撑「精确比例」。

**四、结论。** 本件方法在本库条件下可行且可复算，能支撑「摘要就绪度 + 主料/上下文/结论三维明细 + 推送不可判说明」，不能支撑「摘要质量分 / 推送能力结论」。若甲方需要后者，需先建摘要表、写参考摘要、做人工评分，届时质量维可直接接入，不需要重构生成链路。
