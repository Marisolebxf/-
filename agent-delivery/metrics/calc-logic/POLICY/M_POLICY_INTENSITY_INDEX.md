## 摘要

政策力度指数是本批唯一一个「自带正本口径」的指标：`calc-logic/POLICY` 下有成文的三维五项表，写明了效果、覆盖、成本各用哪个字段、怎么合成。结构看起来是齐的——五个字段都在表里，其中 `policy_support` 还是 JSON，理论上能放下支持方式、支持对象、扶持行为三个子键。实测把这张表打回原形：`policy_support` 全表 20,000 行都是 JSON null，三个子键一个都读不出来；`implementation_date` 整列为空；唯一有值的是 `district`，1,165 行（5.825%）。

按正本口径「缺维不补 0、不进平均」，效果维（2 项）与成本维（1 项）整块退出，覆盖维只剩「区县去重数」一项。合成后的结果不是「政策力度低」，而是「只剩一个区县计数」——深圳市 4 个区、北京市 15 个区、上海市 8 个区，其余七个对比市为 0。这个计数反映的是「该市政策文本里出现过几个区名」，不是政策力度。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

「政策力度指数」挂在政策分析页的「政策力度排名」：一张按城市排序的榜单，加一个城市 × 三维的雷达图。需求把它定义为 0—100 的分数，分数越高表示该市政策实施力度越强。它不属于政策基础指标模型的五类截面统计，而是建在那五类之上的**合成指标**——这也是它与同批另外四件的根本区别：另外四件都是「数出来的」，本件是「评出来的」。

合成指标对输入的要求比计数指标高一个量级：计数指标缺一列只是少一个切片，合成指标缺一维会让整个分数失去意义。本件的困境正在这里——它缺的不是一列，是三维里的两维。

### 1.2 为什么需要这个指标

第一，它是政策对比页的主入口。企业选址、园区招商、城市对标都需要一个「政策力度」的横向量尺，单看政策条数会被发文量大的城市误导，合成指标的设计初衷就是纠偏。

第二，它把「有没有政策」推进到「政策写得实不实」。效果维看实施日是否写明、支持方式是否写明；覆盖维看支持对象与区县的广度；成本维看扶持行为是否写明。三个维度都在问同一件事：这份政策除了标题和原则，有没有可执行的安排。

第三，它是最容易被空字段「静默糊住」的指标。`policy_support` 是 JSON 列，`JSON_LENGTH(null)` 返回 1，如果不做类型判断，会得出「20,000 行全部有值」的结论；`implementation_date` 是 date 列，`COUNT(*)` 与 `COUNT(implementation_date)` 只差一个函数调用，写错就会把 0 当成「全部有值」。这两处都是「看起来有数」的陷阱。

### 1.3 需求文档是否给出定义方法

**正本给了完整定义，是本批五件里口径最清楚的一件。** 三级指标与公式逐条列明：

| 维度 | 三级指标 | 正本公式 | 正本源表字段 |
|---|---|---|---|
| 效果 | 实施日完备占比 | `COUNT(implementation_date 非空) / N_c` | `implementation_date` |
| 效果 | 支持方式完备占比 | `COUNT(support_way 至少 1 条非空) / N_c` | `policy_support.support_way` |
| 覆盖 | 支持对象种类数 | `COUNT(DISTINCT support_object)`，空值不计 | `policy_support.support_object` |
| 覆盖 | 区县去重数 | `COUNT(DISTINCT district)`，空值不计 | `district` |
| 成本 | 扶持行为完备占比 | `COUNT(support_behavior 至少 1 条非空) / N_c` | `policy_support.support_behavior` |

合成规则也写明了：各维截面 min-max 到 $[0,1]$，缺维不补 0、不进平均，等权（权重待 QPOL-02）×100；全样本同值取 0.5；$N<3$ 标「样本不足」。它没有规定的是：**当三维里两维整块为空时，是否还允许出分**。本件的处理是：不允许，理由写在 §2.3。

### 1.4 类似指标权威机构构建方法可行性分析概要

| 方法族 | 代表做法 | 口径要点 | 与本件的差 | 贴合度 |
|---|---|---|---|---|
| A 三维等权合成 | 正本口径 | 效果/覆盖/成本各出原始值，min-max 后平均 | 两维无输入，A 族无法执行 | 低（结构可循、数据不支撑） |
| B 单维代理 | 只用覆盖维 | 以区县/对象广度代替力度 | 会把「区名多」读成「力度强」 | 低（不采用） |
| C 文本强度打分 | 政策文本量化 | 按支持方式词频、金额、工具类型打分 | 需先做文本抽取，本库无结构化字段 | 低（需新建管线） |
| D 金额加权 | 财政政策评估 | 按扶持金额加权求和 | 本表无任何金额列，且正文金额自相矛盾 | 低（禁用） |

**三句结论**：① A 族是唯一与正本一致的做法，但它要求三维都有原始值，本库只满足一维的一半；② B 族技术上能出数，但出的数会被误读，本件不采用；③ C/D 两族都需要先建字段或先做抽取，属于「补数之后」的路径，不是当前可交付的口径。

### 1.6 本报告的口径与边界（须与甲方会签）

**推测定义**：设城市 $c$ 的有效政策数为 $N_c$（正本规定国家级政策可计入每个对比市，故 $N_c=\text{该市行数}+2{,}174$），三维原始值为

$$E_c=\frac{1}{2}\left(\frac{\mathrm{COUNT}(impl\_date\neq\varnothing)}{N_c}+\frac{\mathrm{COUNT}(support\_way\neq\varnothing)}{N_c}\right)$$

$$C_c=\frac{1}{2}\left(\mathrm{COUNT}(\mathrm{DISTINCT}\ support\_object)+\mathrm{COUNT}(\mathrm{DISTINCT}\ district)\right)$$

$$K_c=\frac{\mathrm{COUNT}(support\_behavior\neq\varnothing)}{N_c}$$

合成时对各维做截面 min-max：

$$z_{d,c}=\frac{x_{d,c}-\min_c x_{d}}{\max_c x_{d}-\min_c x_{d}},\qquad S_c=\frac{1}{|D_c|}\sum_{d\in D_c} z_{d,c}\times 100$$

其中 $D_c$ 是「该市可算的维集合」，缺维不进平均。

**边界**：① 本件不产出 $S_c$，因为 $|D_c|$ 在本库只剩覆盖维的一半；② 分母 $N_c$ 按城市取，不能用 20,000——库内 **9,706 行无城市**（含 2,174 行国家级），这 9,706 行不属于任何城市的市级分母；③ 成本维不得改用金额口径，本表没有金额列，正文正则抽取会取到错值；④ 「全样本同值取 0.5」这条规则在本库会大面积触发（因为大量城市某一维全为 0），进一步说明合成没有区分度。

### 1.7 与旧稿的差异（摘要）

旧稿（20261019 版）判**完全转换支持**，理由是 `ads.policy_intensity` 有结构、`policy_support` 列存在，并直接引用了演示批次的城市分数。本件的差异是：① 打开 JSON 列看类型，确认 20,000 行都是 null；② 逐子键计数，三个子键都是 0；③ 按正本「缺维不进平均」实测可算维数，得到 0 个完整维；④ 判档降为**完全不支持**，不给分数。旧稿引用的演示分数与本件不可比，本文不引用其任何数值。

## 二、计算过程

### 2.1 第一步：确认入集

正本的入集是「`status=有效` 且 `expire_date` 空或不早于统计日，按 `id` 去重」。本库 `status` 只有一个取值「有效」、`expire_date` 全空，两个条件同时恒真，因此入集等于全表 20,000 行，主键去重后仍是 20,000。这一步不改数字，但必须写出来：它意味着后面所有分母都是 20,000 的切片，而不是「筛过有效的政策」。

### 2.2 第二步：逐项试算五项三级指标

五项里四项直接归零：`implementation_date` 非空 0 行、`support_way` 命中 0 行、`support_object` 命中 0 行、`support_behavior` 命中 0 行。第五项 `district` 有 1,165 行非空，按城市去重后：深圳市 4 个、北京市 15 个、上海市 8 个，广州、杭州、南京、合肥、成都、武汉、西安七个对比市为 0。

这里要说明为什么 4 个区县不是「少」而是「无意义」：区县去重数的量纲是「个数」，与其他四项的「占比」不同。正本把它放在覆盖维，是要与「支持对象种类数」一起构成广度；当支持对象整列为空时，覆盖维只剩一个计数，min-max 之后每个城市得到的分数只取决于「区名个数」，与政策力度无关。

### 2.3 第三步：按正本规则决定是否出分

正本写「缺维不补 0、不进平均」。效果维 2 项全不可算 → 整维退出；成本维 1 项不可算 → 整维退出；覆盖维 2 项中 1 项可算 → 该维「不完整」。三维里 0 维完整、2 维整块不可算，合成只剩一个不完整维的一项。此时若强行出分，得到的数不是「力度指数」，而是「区县个数」的单调变换。因此本件停在「判定不出分」，把五项试算结果与三维状态原样落盘，供甲方判断是否接受「单维代理」——本件不建议接受。

## 四、数据缺失情况与结论边界

### 4.1 缺口的后果归因

**`policy_support` 全 null → 三维里的两维半失去输入。** 后果不是「分数偏低」，是「分数不存在」：效果维的两项都在这个 JSON 里（支持方式）或与它同源的日期列里（实施日），成本维唯一一项也在这个 JSON 里。

**`district` 只有 5.825% → 覆盖维退化为计数。** 后果是即使强行出分，城市之间的差异也只反映区名个数。深圳市 4 个、北京市 15 个、上海市 8 个，看起来像「北京覆盖最广」，实际是「北京的政策文本里出现过的区名最多」；广州、杭州、南京等七个市为 0，不代表没有区级政策，只代表这些行的 `district` 没填。

**无金额列 → 不能用金额顶替成本维。** 这是本件最需要强调的一条边界：政策正文与 `abstract_excerpt` 里确实有金额，但同一份文件的两处金额存在相差三个数量级的样本。用正则抽金额，抽到的既可能是「补贴上限 500 万元」，也可能是「总投资 5 亿元」，两者语义不同，混在一起加权会把成本维变成噪声。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

- **`JSON_LENGTH(null)` 返回 1**：`policy_support` 全表是小写 JSON null，用 `JSON_LENGTH` 判空会得出「20,000 行全部有值」的结论。正确做法是先判 `JSON_TYPE`。
- **`COUNT(*)` 与 `COUNT(implementation_date)` 差一个函数名**：前者 20,000，后者 0；写错就等于把「全空」读成「全有」。
- **区县去重数不是占比**：它的量纲是「个数」，与其它四项的「占比」不同，不能直接等权平均（正本靠 min-max 抹平量纲，但抹平不了语义）。
- **城市分母不是 20,000**：9,706 行无城市，含 2,174 行国家级；正本允许国家级计入每个对比市，但市级分母必须用「该市行数 + 2,174」，不能直接用 20,000。
- **`status` 恒真**：所谓「有效政策」在本库等于「全部政策」，任何写着「仅统计有效」的分数都没有真正筛过。

### 4.3 可构建但存在缺口（不是「无法构建」）

1. **区县去重数**：已可算，1,165 行有值，按城市可出 10 城截面。
2. **实施日完备占比**：公式已就绪，补 `implementation_date` 即可，当前恒为 0。
3. **支持方式/对象/行为三个占比或计数**：公式已就绪，补 JSON 子键即可，当前恒为 0。
4. **三维合成分数**：需同时满足「三维各至少一项可算」且「权重已定」，当前不满足。
5. **金额加权力度**：不可算，且不建议——本表无金额列，正文金额不可信。

### 4.4 结论与发布建议

**不建议发布任何「政策力度指数」数值或排名。** 页面上现有的演示分数应下架；若必须保留入口，建议显示为「待补数：三维中两维无输入」，并链接到本件的补数清单。

**待甲方裁决点**：① 是否接受「单维代理」口径（本件不建议，理由见 §2.3）；② 权重 QPOL-02 是否先按等权冻结；③ 成本维是否允许先建 `support_amount` 字段（若允许，需要额外的文本抽取工期）；④ 国家级政策计入每个对比市这条规则是否维持（维持则分母含 2,174 行，城市间差异被稀释）。

### 4.5 对下游榜单的影响

政策力度排名是本指标唯一的消费方。它当前展示的是演示批次的城市分数，与本件实测的「四个维全 0、一个维 4/15/8/0」完全不同。若直接换成实测数据，榜单会变成「北京第一、上海第二、深圳第三、其余并列末位」，这个结果没有业务含义。因此本件的交付方式是「阻断 + 补数清单」，而不是「换一版分数」——这是负结论件与普通指标件在交付形态上的区别。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答三问：① 力度指数现在能不能出分；② 若不能，缺的是哪几项；③ 缺的项能不能用现有文本补。范围限定 `gkx.dwd_policy_base` 一张表、两份共用快照与正本口径文件。

### C.2 可算闭环

1. 区县去重数：1,165 行有值，按城市可出 10 城截面。
2. 四项「完备占比」的分母 $N_c$：城市行数可得（10,294 行有城市 + 2,174 行国家级）。
3. 三维状态的判定：五项逐项可判，结果为 0 完整维、2 整块不可算。
4. 城市级分母与国家级计入规则：可按正本执行。

### C.3 不可算闭环

1. 效果维两项：`implementation_date` 与 `support_way` 均 0 行。
2. 成本维一项：`support_behavior` 0 行，且无金额列可替代。
3. 覆盖维的支持对象种类数：0 行。
4. 完整合成分数：需三维都有输入，当前不满足。

### C.4 结论

按四档定义判**完全不支持**：五项里四项为 0，三维里两维整块为空，剩余一项不构成合成指标。不能判「部分支持」，因为「部分支持」要求至少有一条可交付的合成路径，而本库的合成结果会退化为「区名计数」；也不能判「完全转换支持」，因为转换所需的 JSON 子键与日期值都不存在。

### C.5 补数后的验收口径

补数完成后按四条验收：① 五项三级指标的非空率都能报出且不全为 0；② 三维各至少一项可算，且覆盖维两项齐全；③ 合成分数在 10 个对比市上不是单调由区县数决定（可用相关性检验，与区县数的秩相关应显著低于 1）；④ 成本维若改用金额，必须先有 `support_amount` 字段并抽样核对 20 条，确认与原文一致。四条全过，本件可从「完全不支持」升为「完全转换支持」。
