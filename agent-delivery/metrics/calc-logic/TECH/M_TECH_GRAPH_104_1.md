## 摘要

「技术实体识别构建」要回答的是：技术图谱里的节点到底是谁——是专利申请人、高校、科研机构、医院，还是企业集团下的某个主体；每个节点有哪些属性（行业、区县、专利量、授权量、主技术域、技术标签、论文、技术交易），这些属性够不够支撑后续的关系抽取与结构分析。本报告用 `gkx` 的申请人底册与专利聚合缓存，构建 **77,846 个深圳技术实体**，覆盖 **1,336,877 件专利**，并用「名称后缀规则 + 底册词典」把实体分成五类。

实体表的结构是「一名称一实体」：名称取申请人原文，不做别名归一；类型按后缀与底册 `org_type` 判定；行业取底册 `industry_l2`（GB/T 4754 二级行业）；区县取底册 `area`；专利与授权取 `star_applicant_agg_gkx.json` 的 `agg[nm][0]` 与 `agg[nm][1]`。五项基础属性的填充率是 100%、99.74%、99.99%、100%、100%，主 IPC4 填充 76.97%，技术标签只填充 16.22%。

三条限制必须同时披露。第一，**实体是「申请人名称」而不是「法律主体」**：同一集团下的「华为技术有限公司」「华为数字能源技术有限公司」是两个实体，同名不同主体的 47 个名称会被合并；名称未归一，是后续关系抽取与结构分析的主要偏差源。第二，**论文与技术交易两项缺源**：论文计数缓存只覆盖 2,070 家科研机构，深圳申请人命中 0 家；转让表只有 `pn`、日期、买卖方，没有金额列，深圳实体只命中 134 家（0.17%）。第三，**没有 NER 模型**：技术报告、论文正文、交易文本都没有进入识别语料，实体识别靠规则与词典，不是「从文本中抽取」。按 §〇 判**部分支持**。

## 一、需求定义概述（指标定义）

### 1.1 所属功能模块（要开发什么）

本指标属技术图谱构建族的实体识别件（GRAPH，序列号 104），页面挂载 TOPIC-TECH-12 / DS-02-TECHGRAPH。产品面是**技术实体库**：为技术图谱提供节点表与节点属性，供 105 的关系抽取、STRUCT 的结构分析、以及上层「企业—技术—机构」查询使用。没有一张干净的实体表，后面的边表、中心性、社区发现都无从谈起。

在这张产品图里，104 承担的是「节点定义」：105 定义边，STRUCT 定义图的性质，104 定义「谁是节点、节点有什么属性」。三者是流水线关系：104 的实体主键决定 105 的边能不能连上，105 的边决定 STRUCT 的图能不能算。104 的名称不归一，会沿着流水线放大成「同一主体被拆成多个节点」的结构噪声。

### 1.2 为什么需要「技术实体识别构建」这个指标

实体识别的价值有三层。第一层是**主键统一**：技术图谱的所有边都挂在实体主键上，主键不统一，边就会挂错。第二层是**属性补全**：只有名称没有行业、区县、专利量，图谱只能做「谁连着谁」，不能做「谁强谁弱」。第三层是**类型分层**：企业、高校、科研机构、医院的创新行为不同，混在一起算中心性会让高校被专利大户淹没。

方法上有两条路径。一条是**规则 + 词典**：用名称后缀（「有限公司」「大学」「医院」「研究院」）与底册白名单判类型，优点是可控、可解释、无需标注；缺点是无法处理简称、别名、集团合并。另一条是**文本 NER**：从技术报告、论文、新闻中识别机构名，优点是能发现底册外的新实体；缺点是需要标注语料与模型。本报告用第一条路径，第二条因语料缺失未做。

### 1.3 需求文档是否给出定义方法

**需求文档给了任务，但没有给公式。**「识别技术实体」是任务陈述；「结合专利、企业、机构数据构建实体库」是数据清单；「输出实体表与属性」是产出要求。三处都没有闭合：实体的定义（申请人？法律主体？集团？）、类型体系（几类、按什么判）、属性清单（哪些必填、哪些选填）、名称归一规则（别名、简称、更名）、最低覆盖门槛，原文均未定义。

因此本报告采用推测定义（§1.6）：以「专利申请人名称原文」为实体、以「名称后缀 + 底册」判五类、以底册与专利聚合补属性；不做别名归一、不做集团合并、不做 NER。推测定义不是甲方闭合口径，正式发布前须由需求方确认实体粒度与归一规则。

| 方法族 | 代表机构/文献 | 核心做法 | 与本指标贴合度 |

## 二、计算过程（计算步骤）

### 2.1 方法选择：先定主键，再定类型，最后补属性

104 的方法选择有一个前置判断：**实体主键必须与边表的主键一致**。105 的关系抽取用「申请人名称」做技术—企业边的端点，STRUCT 的节点也用同一套名称；如果 104 换成「统一社会信用代码」或「集团 ID」，105 与 STRUCT 都要重做。本报告选择「申请人名称原文」作为主键，是因为它是专利表里唯一天然可得、且能直接连到专利的键；代价是名称不归一，别名与更名会被拆成多个实体。

第二个前置判断是**类型判定用规则而不是模型**。企业、高校、科研机构、医院四类在名称上有稳定的后缀特征（「有限公司」「大学」「学院」「医院」「研究院」「研究所」），用后缀规则可以覆盖绝大多数；底册 `org_type` 用来兜底「事业单位」「民办非企业」等无法从名称判断的主体。规则的好处是可解释、可复现；坏处是「名称像企业但实际是事业单位」这类边界会判错，报告在 §四把误判列成已知偏差。

第三个前置判断是**属性只补能补的**。行业、区县、专利、授权四项在底册与聚合缓存里都有，直接补；主 IPC4 用「该实体专利中出现最多的 IPC4」，覆盖率 76.97%；技术标签只有 16.22% 的实体命中；论文与技术交易两项缺源，宁可留空也不造假。这个选择会让实体表「看起来不完整」，但它比「用 0 填充」诚实：0 会被下游当成「该实体没有论文」，留空则明确表示「未知」。

### 2.2 步骤 1｜实体主键：168,827 → 77,846

深圳申请人名称来自 `sz_patent_city_name_gkx.json`：全国 168,827 个名称，其中城市归属为深圳的 77,846 个。城市归属用企业底册 `name_cn` 匹配，只取 `city='深圳市'`；底册匹配不上的名称不进实体表。这个口径会漏掉「在深圳申请专利但底册登记在外地」的主体，也会漏掉「底册没有的新主体」；报告在 §四把「底册依赖」列为结构性偏差。

| 项 | 数值 | 说明 |
|---|---:|---|
| 全国申请人名称 | 168,827 | 缓存全量 |
| 深圳实体 | **77,846** | 底册 city=深圳市 |
| 实体专利 | 1,336,877 | 全期 2021—2026 |
| 平均专利/实体 | 17.17 | 受大户拉动 |
| 中位数专利/实体 | 1 | 长尾极重 |

平均 17.17 件、中位数 1 件，说明实体分布是极端长尾：少数大户（华为 81,376 件、比亚迪 29,024 件、中兴 15,634 件）拉高均值，绝大多数实体只有 1—2 件专利。这个分布决定了后续的图结构：如果按专利量加权，图会被少数大户主导；如果按实体等权，长尾会淹没结构。报告在 105 与 STRUCT 里都用「实体等权 + 专利量另列」的方式处理。

### 2.3 步骤 2｜类型判定：五类分布

类型判定顺序是：先看名称后缀（「大学」「学院」→高校；「医院」「卫生院」→医疗机构；「研究院」「研究所」「研究中心」→科研机构；「有限公司」「股份」「厂」「店」→企业），后缀无法判断时看底册 `org_type`（「事业单位」→科研机构/高校，「民办非企业」→其他主体），两者都无法判断时归「其他主体」。

| 企业 | 77,443 | 99.48% | 1,294,496 | 96.83% |

这张表最醒目的对比是「42 所高校贡献 31,660 件（2.37%），77,443 家企业贡献 1,294,496 件（96.83%）」。高校数量只占 0.05%，专利占比却是 2.37%，说明高校的平均专利量（753.8 件）远高于企业（16.7 件）。科研机构 119 家、5,961 件，平均 50.1 件；医疗机构 44 家、3,904 件，平均 88.7 件。四类的平均量差异，是后续做「机构—技术」二部图时必须分层的理由。

类型判定也有误差。名称里带「研究院」的企业（如「中广核研究院有限公司」）会被判成科研机构，但它实际是企业法人；名称里不带「大学」的独立学院可能被判成其他主体。报告没有做人工校验，误差量级未知；§四把「类型规则误判」列为待校验项，并建议用底册 `org_type` 做主判、名称后缀做辅判。

### 2.6 步骤 5｜实体—技术覆盖：59,919 家有主 IPC4

主 IPC4 覆盖 59,919 家（76.97%），覆盖的专利量是多少？把有 IPC4 的实体的专利相加，得到 1,267,241 件，占 1,336,877 的 94.79%。也就是说，**76.97% 的实体覆盖了 94.79% 的专利**：没有 IPC4 的 17,927 家实体，绝大多数是只有 1—2 件专利的长尾，合计占 5.21% 的专利。这个结构对 105 很重要：关系抽取只用有 IPC4 的实体，会丢掉 23.03% 的实体，但只丢掉 5.21% 的专利。

| 分层 | 实体数 | 实体占比 | 专利数 | 专利占比 |
|---|---:|---:|---:|---:|
| 有主 IPC4 | 59,919 | 76.97% | 1,267,241 | 94.79% |
| 无主 IPC4 | 17,927 | 23.03% | 69,636 | 5.21% |
| 合计 | 77,846 | 100.00% | 1,336,877 | 100.00% |

这张表也解释了「为什么实体表的 IPC4 填充率只有 76.97%，但技术图谱仍然可做」：图谱的边主要来自专利，专利的 IPC4 覆盖高，实体层缺 IPC4 的长尾对边的影响很小。报告在 105 的关系抽取里明确写「只用 59,919 家有 IPC4 的实体」，并在 STRUCT 里说明「节点是 IPC4 域，不是实体」，避免读者把两张图的节点数混在一起。

## 四、数据缺失情况与结果解读

### 4.1 缺口归因：往哪偏、偏多少、能否交叉验证

**往哪偏。** 第一个缺口（名称不归一）会让同一集团被拆成多个实体，方向上高估实体数、低估单实体规模；华为系、华星系是典型。第二个缺口（类型规则误判）会让「企业叫研究院」被判成科研机构，方向上高估科研机构数量。第三个缺口（论文 0 命中）会让实体表缺「学术产出」维，方向上低估高校与科研机构的创新活动。第四个缺口（技术交易无金额）会让「转化能力」只能用条数代理，方向上高估有转让记录但金额小的实体。第五个缺口（无 NER）会让底册外的新实体进不来，方向上低估新设企业与新机构。

**偏多少。** 可定量的是：底册 47 个重名（0.06%）；无主 IPC4 的实体 17,927 家（23.03%），但只占专利 1.60%；技术标签覆盖 12,628 家（16.22%）；论文 0 家；转让 134 家（0.17%）。不可定量的是「名称不归一让实体数虚高多少」——没有别名表，无法算；只能举例子（华为技术有限公司与华为数字能源技术有限公司是两个节点），不能给总量。

**能否交叉验证。** 有两条弱验证。其一，头部实体（华为、比亚迪、中兴、深圳大学、南方科技大学）与公开的深圳专利大户名单一致，说明实体表没有把大户漏掉。其二，类型分布（企业 99.48%、高校 0.05%）与深圳的创新主体结构一致，说明规则没有把企业大量误判成高校。两条都只能验证方向，不能验证「实体数 77,846 是否精确」。

### 4.2 结果与解读：三层实体，三种用法

第一层是**基础实体层（77,846 个）**：名称、类型、行业、区县、专利、授权六项，填充率 99.74%—100%。这一层的用法是「节点表 + 基础切片」：按区县看实体分布、按行业看主体结构、按专利量看头部。它是 105 与 STRUCT 的输入，不能单独当「技术图谱」展示。

第二层是**技术画像层（59,919 个）**：主 IPC4 覆盖 76.97% 的实体、98.40% 的专利；技术标签覆盖 16.22%。这一层的用法是「实体—技术」查询：某个企业主要做什么技术、某个技术域有哪些企业。主 IPC4 只留一个域，会丢多域信息；技术标签覆盖低，只能做附加展示。

第三层是**外部属性层（论文 0、交易 134）**：基本空白。这一层的用法是「知道缺什么」：不要在产品上展示「论文学者」或「技术交易额」，也不要用「转让条数」代替「转化金额」。如果甲方需要这两列，必须先补数据，不能靠现有缓存硬凑。

三层的关系是「越往下越不可靠」。基础层可以直接上线，技术画像层要标注覆盖，外部属性层不上线。报告的建议是「实体表按层发布」：基础层作为节点表，技术画像作为可选列，外部属性作为待接入项；不要把三层混成一张「全能实体表」。

### 4.3 对照需求的符合性评审

## 五、结论与发布建议

### 5.1 结论

一，深圳技术实体 77,846 个、覆盖专利 1,336,877 件；企业 77,443 家（99.48%）、高校 42 所、科研机构 119 家、医疗机构 44 家、其他 198 家。二，六项基础属性填充率 99.74%—100%，主 IPC4 填充 76.97%、覆盖 98.40% 的专利，技术标签只覆盖 16.22%。三，实体分布极端长尾：平均 17.17 件、中位数 1 件，头部华为 81,376 件、比亚迪 29,024 件、中兴 15,634 件。四，论文属性深圳 0 命中、技术交易只有 134 家且无金额、文本 NER 未训练，三项不能交付。

### 5.2 发布建议

短期以「深圳技术实体库（申请人名称口径，全期）」上线，展示节点表与六项基础属性；技术画像列（主 IPC4、技术标签）标注覆盖率；论文、技术交易额不上线。页面必须写两行注：实体按申请人名称、未做别名归一；类型由名称后缀 + 底册规则判定，未人工校验。

中期补三件事：一是别名/更名表，把华为系、华星系这类集团实体合并；二是论文作者单位匹配，把高校与科研机构的论文数补上；三是转让金额字段，把「技术交易条数」升级为「技术交易额」。三件事都需要外部数据，短期可以先做「集团视图」：按名称前缀人工维护一张小表，把已知集团合并展示，但不改主键。

## 附录 C　方法可行性报告（完整版）

### C.1 目的与范围

回答三个问题：技术实体识别的权威口径是什么；本库能识别到哪一步；识别出来的实体表能不能直接支撑图谱。范围限定在专利申请人、企业底册、机构标签、论文计数、转让记录五类数据，不涉及新闻、招聘、工商变更与知识产权诉讼。

### C.2 语义锚定

「技术实体」在知识图谱里通常指「参与技术活动的组织」。判断依据可以是专利申请人、论文作者单位、项目承担单位、技术交易买卖方，其中专利申请人最常用，因为公开、可计数、可按名称聚合。本指标的语义边界是「专利申请人名称实体」，不是「法律主体」，也不是「集团」。这个边界决定了它必须做名称归一，而本库没有别名表，所以只能做「同名合并」，不能做「异名归一」。

### C.3 方法谱系

C.3.1 规则 + 词典。用后缀规则与底册白名单判类型，优点是可控、可解释；缺点是无法处理别名与边界案例。本报告用它做主路径。

C.3.2 文本 NER。从技术报告、论文、新闻中识别机构，优点是能发现新实体；缺点是需要标注语料。本库没有，未做。

C.3.3 名称归一。用别名、简称、更名表合并实体，优点是能还原集团；缺点是需要维护表。本库只有同名合并，没有别名表。

C.3.4 图嵌入。用邻居与属性学实体向量，优点是能做相似实体推荐；缺点是依赖边表质量。本报告不做。

### C.4 数据可行性

| 方法 | 最小数据 | 本库 | 可行性 |
|---|---|---|---|
| A 规则 + 词典 | 名称 + 底册 | 77,846 + 189,116 | 可 |
| B 文本 NER | 正文语料 + 标注 | 无 | 不可 |
| C 名称归一 | 别名/更名表 | 无 | 部分（仅同名） |
| D 图嵌入 | 实体 + 边 | 105 可提供边 | 可（后续） |

### C.5 实体主键的完整证据

实体主键选「申请人名称原文」，有三个直接后果。第一，同一集团的不同法人是不同实体：华为技术有限公司与华为数字能源技术有限公司、TCL华星光电技术有限公司与深圳市华星光电半导体显示技术有限公司，都是两个节点。第二，同名不同主体会被合并：底册 47 个重名，合并后可能把两个不同机构算成一个。第三，名称中的括号、全半角、空格差异会造成同一主体多个节点；本件只做了最基本的清洗，没有做全量归一。

这三个后果的量级不同。集团拆分是「系统性」的，影响头部实体的规模；同名合并是「局部」的，影响 47 个名称；格式差异是「随机」的，影响长尾。报告选择「保留名称原文 + 披露偏差」，而不是「强行归一」，是因为没有别名表的情况下，强行归一会引入新的错误（把不同主体合并），且无法复现。

### C.6 属性填充的完整证据

六项基础属性的填充率是 100%、100%、99.74%、99.99%、100%、100%，这个结果看起来「太好」，需要解释。名称与类型是规则生成的，必然 100%；专利与授权来自聚合缓存，每个实体都有两个值，必然 100%；行业与区县来自底册，底册匹配不上的名称根本不进实体表，所以填充率接近 100%。换句话说，**高填充率是「入表门槛」造成的，不是「数据质量」造成的**：底册匹配不上的主体被排除了，剩下的自然填得满。

两项技术属性的填充率更能反映数据质量：主 IPC4 76.97%、技术标签 16.22%。主 IPC4 的缺口是「专利没有分类」，技术标签的缺口是「机构没有标签」。两项都不是「实体识别失败」，而是「属性源覆盖不足」。报告在 §2.4 把两项分开写，避免读者把「标签覆盖低」误读成「实体没识别出来」。

### C.7 推荐方案

1. 短期上线「实体节点表 + 六项基础属性」，标注名称未归一。
2. 技术画像列（主 IPC4、技术标签）标注覆盖率，不参与强筛选。
3. 建别名/更名表，先合并已知集团（华为系、华星系、平安系）。
4. 接论文作者单位，补高校与科研机构的论文数。
5. 补转让金额字段，把「交易条数」升级为「交易额」。
