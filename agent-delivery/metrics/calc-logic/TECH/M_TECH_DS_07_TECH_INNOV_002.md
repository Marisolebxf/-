## 摘要

「专利质量评估」要回答的是：某个 IPC4 技术领域的专利整体质量高不高，应该用家族规模、权利要求数、被引次数、技术宽度、法律状态稳定性五个维度合成 0—100 分，还是只用其中两三个维度。本报告按「先实测、后定档」的纪律，对四张价值附表逐一做覆盖率与可连接性核验，结论是**五个维度全部不可用**：家族表 20,593 行、覆盖 0.7005%；权利要求表 20,026 行、覆盖 0.6812%；被引表 20,515 行、覆盖 0.6978%，能回连主表的只有 475 件（0.0162%）；法律状态表 20,000 行、覆盖 0.6803%；技术宽度依赖附加分类，而主表 `other_Versions` 抽样 3,000 行 0 行非空。

三次回连主表的尝试全部在 60 秒被数据库中断（60.34 / 60.22 / 60.40 秒），说明「附表—主表」的 `patent_id` 连接在当前实例上没有可用执行计划。没有域键、没有可连接的主键、没有足够的覆盖率，任何「领域质量分」都只能靠 2 万行样本外推 294 万行总体，这不是「精度低」，而是「分母不成立」。

必须把「算不出」与「分低」分开。被引表里 17.83% 的行被引大于 0、均值 0.5258、最大值 55，这些数字描述的是 2 万行样本，不是深圳或全国的领域质量；把它当成「某领域被引低」会得出完全错误的结论。同理，样本里授权占比 63.29%、剔除撤回与终止后的稳定占比 57.37%，也只能说明这 2 万行的法律状态分布，不能外推到 IPC4 领域。按 §〇 判**完全不支持**，并明确建议：本指标不进入本期发布清单。

## 一、需求定义概述（指标定义）

### 1.1 所属功能模块（要开发什么）

本指标属技术创新度分析族的专利质量件（DS-07，序列号 002），页面挂载 TOPIC-TECH-11 / DS-07-TECHINNOV。产品面是**专利质量评估服务**：按技术领域输出质量分与分项解释，用于科技项目验收、专利资助、产业技术评价。产品期望的输入是「领域 + 年份」，输出是「0—100 分 + 五个分项 + 排名」。

在这张产品图里，002 承担的是「质量维度」：137 回答技术阶段，139 回答机会，140 回答布局，002 回答「这些领域的技术含量高不高」。四者共用同一套 IPC4 面板，但 002 比其他三件多一层依赖：它不仅需要「域 × 年件数」，还需要「每一件专利的家族、权利要求、被引、分类宽度、法律状态」，再把这些件级属性聚合到域级。件级属性缺失，域级分数就无从谈起。

### 1.2 为什么需要「专利质量评估」这个指标

质量评估的政策价值有三层。第一层是**资助导向**：专利资助如果只按件数，会鼓励「重数量、轻质量」；按质量分倾斜，可以引导申请人做高价值专利。第二层是**项目验收**：科技项目结题时，需要判断「产出的专利是不是核心专利」，而不是只看申请了几件。第三层是**产业对标**：同一产业在不同城市的专利质量差异，比数量差异更能解释技术竞争力。

方法上有两条路径。一条是**件级加权法**：先给每件专利算质量分（家族大小、权利要求数、被引、同族国家数、法律状态），再按域聚合。优点是语义贴近「专利质量」，缺点是需要件级全量数据。另一条是**域级代理法**：直接用域级的授权率、发明占比、维持年限做代理。优点是数据可得，缺点是「域级平均」会掩盖分布，且代理变量与质量不是一一对应。本报告尝试第一条路径，失败后不降级到第二条，因为需求要的是「五维质量分」，不是「授权率代理」。

### 1.3 需求文档是否给出定义方法

**需求文档给了任务，但没有给公式。**「评估专利质量」是任务陈述；「结合家族、权利要求、被引、法律状态等数据构建质量评估模型」是数据清单；「输出质量分」是产出要求。三处都没有闭合：五个维度各自的归一化方法、权重、域级聚合方式（均值/中位数/加权）、时间窗、最低覆盖门槛，原文均未定义。

因此本报告采用推测定义（§1.6）：以 IPC4 为域、以 2021—2024 为窗，五维各自归一化后等权合成 0—100 分；域级聚合用件级分数的中位数，避免极值拉动。这个定义只用于说明「需要什么数据」，不用于产出分数——因为实测五维都不可用。推测定义不是甲方闭合口径，正式发布前须由需求方确认维度、权重与覆盖门槛。

### 1.6 推测原意与推测定义（仿王惠口径写法）

**推测原意**：把每件专利的家族大小、权利要求条数、被引次数、同族国家数、法律状态折算成五个 0—1 的分项，合成单件质量分；再把同一 IPC4 域、同一申请年的专利质量分取中位数，得到领域质量分；按分数排序，输出「高质量领域」与「低质量领域」。

**推测定义（本批采用，仅供说明依赖；不产出分数）**：

$$
Q_{p}=100\times\frac{1}{5}\sum_{k=1}^{5}\tilde{x}_{k,p},\qquad
Q_{d,y}=\operatorname{median}\{Q_p:\,p\in(d,y)\}
$$

其中 $x_{1}$ 为同族成员数、$x_{2}$ 为权利要求条数、$x_{3}$ 为被引次数、$x_{4}$ 为同族国家数（技术宽度代理）、$x_{5}$ 为法律状态稳定性（授权且未终止记 1，其余记 0）；$\tilde{\cdot}$ 为域内 min-max 标准化。

本件属**完全不支持**档，按金样板契约，§二 计算过程从缺。不从缺的部分只有「证据核验」，已在 §1.6 与 §三、附录 B 完整给出：四张附表的行数、覆盖率、可连接件数、三次超时、`other_Versions` 空值率、法律状态分布。之所以不写「先算件级分、再聚合域级」的步骤，是因为第一步就过不去——附表没有 IPC4 与申请年，无法把件分归到域；按 `patent_id` 回连又在 60 秒超时。把不可执行的步骤写成「计算过程」，会让读者误以为只差调参。

| 若强行写步骤 | 需要的数据 | 实测结果 | 卡点 |
|---|---|---|---|
| 1 件级家族分 | 家族表 JOIN 主表取域键 | 60.34 秒超时 | 连接不可执行 |
| 2 件级权利要求分 | 解析 `claim_text` 条数 | 一件一行、正文 mediumtext | 条数字段缺 |
| 3 件级被引分 | 被引表 JOIN 主表 | 可回连 475 件 | 覆盖 0.0162% |
| 4 件级宽度分 | `other_Versions`/附加分类 | 3,000 抽样 0 非空 | 字段全空 |
| 5 件级法律分 | 法律表 JOIN 主表 | 60.40 秒超时 | 连接不可执行 |
| 6 域级聚合 | 域×年件级分 | 无域键、无申请年 | 分母不成立 |

六步里前五步都过不去，第六步自然不成立。这张表的用途不是「记录失败」，而是「界定修复范围」：修复第 1、5 步要动执行计划，修复第 2、4 步要动字段与解析，修复第 3 步要动数据覆盖，修复第 6 步要等前五步完成。

## 三、数据支撑情况（数据可得性与缺口，逐维 + 修复路径）

| 依赖维 | 候选资产 | 结构 | 实测覆盖 | 结论 | 修复路径 |
|---|---|---|---|---|---|
| D1 家族规模 | `dwd_patent_family` | 有 | 20,593 行 / 0.7005% | **缺** | 全量入湖 + 域键 |
| D2 权利要求 | `dwd_patent_claim` | 有 | 20,026 行 / 0.6812% | **缺** | 解析正文 + 域键 |
| D3 被引 | `dwd_patent_cited` | 有 | 20,515 行 / 0.6978% | **缺** | 扩覆盖 + 可连接 |
| D4 技术宽度 | `dwd_patent.other_Versions` | 有 | 3,000 抽样 0 非空 | **缺** | 补附加分类字段 |
| D5 法律状态 | `dwd_patent_legal` | 有 | 20,000 行 / 0.6803% | **缺** | 域键 + 可连接 |
| D6 域级聚合 | 无 | 无 | — | **缺** | 先补 D1—D5 |
| D7 基期 | 附表无申请年 | 无 | — | **缺** | 回连主表或补字段 |

逐维说明：

D1 家族表有 20,593 行、20,000 个不同 `pn`，对 2,939,895 行主表的覆盖是 0.7005%。家族表本身有 `simple_family_pn`、`pn` 两列，能算「同族成员数」，但没有 `patent_id` 之外的域键，也没有申请年；要聚合到 IPC4×年，必须回连主表。回连查询在 60.34 秒被中断，说明这条路径在当前实例上不可执行。

D2 权利要求表有 20,026 行、20,000 个不同 `patent_id`，覆盖 0.6812%。`claim_text` 是 `mediumtext`，一条权利要求可能几千字，直接 `LENGTH()` 或正则数「权利要求条数」都会产生大 IO；更关键的是同样没有域键。样本里 `claim_rows_per_pn` 为 1.0013，说明这张表基本是「一件一行」，不是「一件多条权利要求一行」，因此连「权利要求条数」都不能直接 `COUNT(*)`，还要解析正文。

D3 被引表有 20,515 行，其中被引大于 0 的 3,657 行（17.83%），被引总和 10,787，最大值 55，均值 0.5258。能回连主表的只有 **475 件**，占主表 0.0162%。这个覆盖连「样本级引用网络」都建不起来：475 件分布在 569 个 IPC4 域上，平均每域不到 1 件，任何域级被引均值都会是 0 或 1 的噪声。

D4 技术宽度的标准做法是数「同族国家数」或「附加分类数」。主表 `other_Versions` 前缀抽样 3,000 行，0 行非空；附加分类（`further_classification_ipcr`）没有进入缓存。没有这两个字段，技术宽度连单件都算不出，更不用说域级中位数。

D5 法律状态表有 20,000 行、20,000 个不同 `pn`、20,000 个不同 `patent_id`，`legal_events` 填充 20,000、`status` 填充 19,996、`expiration_date` 填充 14,513。覆盖率 0.6803%，同样无域键。样本状态分布是：授权 12,658、实质审查 4,960、撤回-视为撤回 913、公开 761、驳回 344、权利终止 104、撤回-主动撤回 103、未缴年费 82、撤回-未指定类型 43、放弃-视为放弃 20、空值 4、期限届满 4、全部撤销 2、权利恢复 1、放弃-未指定类型 1。

D6 域级聚合是五维的交汇点，也是本件失败的根因。即使四张附表各自能算件级分，只要没有域键，就无法把件分归到 IPC4；即使能回连，0.68%—0.70% 的覆盖也无法支撑 569 个域的比较。修复路径不是「再跑一次」，而是「全量入湖 + 补域键 + 补申请年」三件事一起做。

### 3.3 探测方法与复现边界

本件的探测分两步。第一步是**表级计数**：对四张附表各做一次 `COUNT(*)` 与主键去重计数，确认行数与覆盖；这一步只读聚合，不扫明细。第二步是**连接可行性**：用 `patent_id` 把附表与主表连接，取 `apdt_year` 与 `SUBSTR(main_classification_ipcr,1,4)`，加 60 秒 `max_execution_time`；三条连接分别在 60.34、60.22、60.40 秒被中断。两步都不写库、不改表，属于只读探测。

复现边界有三条。第一，探测在 20261022 的缓存上完成，脚本本身零 SQL；缓存里保存的是行数、覆盖率、超时秒数与状态分布，不是明细。第二，三次超时是独立复现，不是同一条查询重试三次；三条 SQL 的连接键相同，但聚合目标不同（家族、被引、法律）。第三，`other_Versions` 的空值率来自 3,000 行前缀抽样，不是全表统计；3,000 行 0 非空足以判断「该字段当前不可用」，但不足以给出「全表非空率 0%」的精确结论。

### 3.4 四张附表的字段可用性

| 表 | 可用字段 | 缺失字段 | 能否算件级分 |
|---|---|---|---|
| `dwd_patent_family` | `patent_id`、`pn`、`simple_family_pn` | `ipc4`、`apdt_year` | 不能（无域键） |
| `dwd_patent_claim` | `patent_id`、`pn`、`claim_text`、`lang` | `ipc4`、`apdt_year`、条数字段 | 不能（需解析正文） |
| `dwd_patent_cited` | `patent_id`、`cited_by_nums` | `ipc4`、`apdt_year` | 不能（可回连仅 475 件） |
| `dwd_patent_legal` | `patent_id`、`pn`、`status`、`expiration_date` | `ipc4`、`apdt_year` | 不能（无域键） |

这张表说明「字段可用」与「指标可算」是两件事。四张表都有 `patent_id`，都能算「单件级」的属性；但它们都没有 `ipc4` 与 `apdt_year`，无法把件级属性归到「域 × 年」。唯一能补这两个键的路径是回连主表，而回连在 60 秒超时。字段可用性因此停在「件级」，没有到达「域级」。

### 3.5 与同批指标的数据边界

本件与同批 139、140、137 共用 `dwd_patent` 主表，但依赖的附表不同。139、140 只需要「IPC4×年件数」，主表一个字段就能满足；本件需要「件级五维属性」，必须四张附表全部可用。这个差别决定了两类指标的档位差距：前者可以做到「部分支持」，后者只能「完全不支持」。

| 指标 | 依赖 | 主表能否满足 | 档位 |
|---|---|---|---|
| 137 技术阶段 | IPC4×年件数 | 能 | 部分支持 |
| 139 机遇识别 | IPC4×年件数 + 企业 | 能 | 部分支持 |
| 140 布局推荐 | IPC4×年件数 + 政策 | 能 | 部分支持 |
| 002 专利质量 | 件级五维 + 域键 | 不能 | 完全不支持 |

这张表的读法是「同一张主表，不同的依赖深度」。主表能满足「计数型」指标，不能满足「件级属性型」指标；后者需要价值附表补齐，而价值附表当前只有 0.68%—0.70% 覆盖、且无域键。把 002 判成「部分支持」会掩盖这个结构性差距，也会让读者误以为「只差一点数据」。

## 四、数据缺失情况与结果解读

### 4.1 缺口归因：往哪偏、偏多少、能否交叉验证

**往哪偏。** 第一个缺口（覆盖 0.68%—0.70%）会让任何域级分数只代表「恰好被收录的 2 万件」，方向上高估被收录较多的领域、低估被收录较少的领域。第二个缺口（无域键）会让「域级聚合」退化成「全库平均」，方向上把所有领域拉成同一个分数。第三个缺口（回连超时）会让「件级属性 + 域级归属」的组合不可执行，方向上迫使分析者放弃域级、退回全库。第四个缺口（技术宽度无字段）会让五维变四维，方向上低估「同族布局广」的领域。

**偏多少。** 可定量的是：四表覆盖 0.6803%—0.7005%；被引可回连 475 件，占主表 0.0162%；`other_Versions` 抽样 3,000 行 0 行非空；三条回连查询分别 60.34 / 60.22 / 60.40 秒超时。不可定量的是「如果全量入湖，领域分会长什么样」——没有全量数据，无法估；任何「补数据后大约会怎样」的说法都是猜测，报告不写。

**能否交叉验证。** 没有可用的交叉验证。样本画像里的授权占比 63.29% 与法律状态表的 12,658/20,000 一致，只能证明「样本内部自洽」，不能证明「样本代表总体」。被引均值 0.5258 与「82.17% 为 0」也自洽，但同样只描述样本。要验证总体，需要至少 30% 以上覆盖的随机样本，本库没有。

四类缺口的方向与量级可以并列如下。覆盖率缺口让结论偏向「被收录样本」，量级是 0.68%—0.70%；域键缺口让聚合退化为全库平均，量级是「569 域全部不可分」；连接缺口让件级属性无法归域，量级是三条查询各 60 秒；宽度缺口让五维变四维，量级是 3,000 抽样 0 非空。四个缺口不是并列关系：域键与连接是前置条件，覆盖率与宽度是充分条件；前置不满足，后置无法讨论。

| 缺口 | 方向 | 可定量部分 | 可否交叉验证 |
|---|---|---|---|
| 覆盖率 0.68%—0.70% | 偏向被收录样本 | 四表行数 2 万左右 | 否（无总体抽样） |
| 无域键 | 聚合退化为全库 | 569 域不可分 | 否 |
| 回连超时 | 件级属性无法归域 | 60.34/60.22/60.40 秒 | 是（三次复现） |
| 宽度字段全空 | 五维变四维 | 3,000 抽样 0 非空 | 是（抽样可复） |
| 无申请年 | 无法做年度分母 | 2021—2026 全缺 | 否 |

### 4.2 结果与解读：为什么不是「部分支持」

第一层判断是**结构层**：四张表都存在，字段也大致齐全（家族、权利要求、被引、法律状态），所以「表结构直接支持（开发库+三方库）」这一项在字面上是「有」。但结构有，不等于能算：没有域键、没有申请年、回连超时，三个条件把「结构支持」挡在「可执行」之外。

第二层判断是**数据层**：四表覆盖 0.68%—0.70%，不是「部分覆盖」，是「样本级覆盖」。部分支持的定义是「始终有部分依赖维度无法得到足够数据」；本件不是「部分维度缺」，而是「五个维度全部缺」。按四档口径，这只能落「完全不支持」，不能落「部分支持」。

第三层判断是**降级路径**：能不能退而求其次，只做「授权率」或「发明占比」的域级代理？技术上可以，但那就不是「专利质量评估」了：授权率受申请类型与审查周期影响，发明占比受产业结构影响，两者都不能替代「家族、权利要求、被引、宽度、法律状态」五维。报告不把代理指标包装成质量分，也不建议产品用「授权率」冒充「质量」。

第四层判断是**样本画像的边界**：2 万行样本里授权占比 63.29%、稳定占比 57.37%、被引大于 0 占比 17.83%，这些数字可以作为「本库价值附表长什么样」的证据，但不能作为「深圳专利质量」的结论。报告在 §3.2 明确标注「只作证据，不作领域分」，并在产物里把 `sample_profile.note` 写成同样的限定。

### 4.3 对照需求的符合性评审

| 需求功能要求 | 本实现 | 判定 |
|---|---|---|
| 领域质量分（0—100） | 不产出 | **不满足** |
| 家族规模 | 覆盖率 0.7005%、无域键 | **不满足** |
| 权利要求数 | 覆盖率 0.6812%、正文 mediumtext | **不满足** |
| 被引次数 | 覆盖率 0.6978%、可回连 475 件 | **不满足** |
| 技术宽度 | `other_Versions` 全空 | **不满足** |
| 法律状态稳定性 | 覆盖率 0.6803%、回连超时 | **不满足** |
| 域级排名 | 无域键，无法聚合 | **不满足** |
| 覆盖率核验 | 四表逐项实测 | **满足（证据）** |
| 样本画像 | 2 万行描述统计 | **满足（证据）** |

评审结论：作为「专利质量评估模型」**不可交付**；作为「价值附表可用性核验」**可交付**。产品侧不应展示任何「质量分」，最多展示「本库价值附表覆盖不足，质量维待数据治理」的说明。

### 4.4 如果强行出分，会得到什么

假设不看覆盖率、不看超时，硬把 2 万行样本按 `patent_id` 的前缀或哈希分到 569 个 IPC4 域，会得到「平均每域 35.15 件」的伪域级样本。这个数字看似够算中位数，但它有三个致命问题。第一，分域的依据不是真实的 IPC4，而是人为切分，域标签与专利技术内容无关。第二，被引维可回连的只有 475 件，平均每域 0.83 件，绝大多数域的被引均值会是 0 或 1，排名变成「谁恰好有一件高被引」。第三，技术宽度仍然无字段，五维只能算四维，合成分会缺一维。

| 强行出分的做法 | 表面结果 | 实际问题 |
|---|---|---|
| 按 `patent_id` 哈希分 569 域 | 每域约 35 件 | 域标签与技术内容无关 |
| 用 475 件可回连被引 | 每域 0.83 件 | 均值是 0/1 噪声 |
| 用授权率替代法律稳定性 | 每域一个比例 | 授权率≠稳定性 |
| 用主分类数替代技术宽度 | 每件恒为 1 | 宽度无方差 |
| 四维等权合成 | 0—100 分 | 缺一维，分数不可解释 |

这张表的用途是「反证」：任何一条强行出分的路径，都会让分数看起来正常、实际上不可解释。报告不采用其中任何一条，也不把「四维分」包装成「五维分」。如果甲方坚持要一个数字，正确的做法是先补数据，而不是先改算法。

## 五、结论与发布建议

### 5.1 结论

一，四张价值附表各约 2 万行，对 2,939,895 行主表的覆盖是 0.6803%—0.7005%，属样本级覆盖，不是部分覆盖。二，四表均无 IPC4 与申请年字段；按 `patent_id` 回连主表的三条查询分别在 60.34 / 60.22 / 60.40 秒超时，域级聚合不可执行。三，技术宽度的两个候选字段都不可用：`other_Versions` 抽样 3,000 行 0 行非空，附加分类未入缓存。四，被引表能回连主表的只有 475 件（0.0162%），连样本级引用网络都建不起来。五，五维没有一维能在域级闭环，本件不产出任何领域分，判**完全不支持**。

### 5.2 发布建议

短期**不发布**「专利质量分」。如果产品必须有质量相关展示，只能展示「数据可用性说明」：价值附表覆盖 0.68%—0.70%、无域键、回连超时，质量维待数据治理。不要用授权率、发明占比、维持年限做「质量代理分」，那会把「数据缺口」伪装成「质量结论」。

中期做三件事，做完再评估是否重启本指标。第一，把四张价值附表全量入湖，目标覆盖率不低于 80%，并补 `ipc4`、`apdt_year` 两个域键。第二，给 `dwd_patent` 补附加分类（`further_classification_ipcr`）与同族国家数，让技术宽度可算。第三，优化 `patent_id` 连接的执行计划（分区、索引、预聚合），把 60 秒超时降到可接受范围。三件事缺一件，本指标都仍然是「完全不支持」。

### 5.3 风险与后续

| 风险 | 影响 | 缓解 |
|---|---|---|
| 样本当总体 | 质量分严重失真 | 不发布分数；只披露覆盖率 |
| 无域键 | 无法聚合到 IPC4 | 全量入湖时补域键 |
| 回连超时 | 件级属性无法归域 | 优化执行计划/预聚合 |
| 技术宽度缺字段 | 五维变四维 | 补附加分类与同族国家数 |
| 用代理指标冒充 | 结论不可解释 | 明确禁止授权率代理 |
| 样本画像被引用 | 被当成城市结论 | 产物 note 限定；正文标注 |

### 5.4 重启验收标准

本指标从「完全不支持」回到「部分支持」或「完全转换支持」，需要同时满足五条验收标准，缺一条都不重启。第一条是覆盖率：四张附表对主表的覆盖不低于 80%，且抽样代表性可验证（随机抽样或全量）。第二条是域键：四张表都能直接提供 `ipc4` 与 `apdt_year`，或回连主表能在 10 秒内完成。第三条是宽度字段：`other_Versions` 或附加分类的非空率不低于 50%，且能区分同族国家数。第四条是权利要求条数：能从正文解析出条数，解析准确率经 200 件人工抽检不低于 95%。第五条是稳定性口径：法律状态能区分「授权且维持」「授权但终止」「审查中」「驳回/撤回」，不能只用「授权率」一个比例。

| 验收项 | 门槛 | 当前 | 差距 |
|---|---|---:|---|
| 附表覆盖率 | ≥80% | 0.68%—0.70% | 极大 |
| 域键 | 四表均有或 10 秒回连 | 无，60 秒超时 | 极大 |
| 宽度字段非空率 | ≥50% | 0%（3,000 抽样） | 极大 |
| 权利要求解析准确率 | ≥95% | 未试（mediumtext） | 大 |
| 法律状态细分 | 四类以上 | 有细分但无域键 | 中 |

这张表的作用是把「补数据」拆成可验收的工程项。当前五项全部不达标，其中前三项是硬门槛；在硬门槛达标之前，做权重调整、算法优化、可视化都没有意义。

## 附录 C　方法可行性报告（完整版）

### C.1 目的与范围

回答三个问题：专利质量评估的权威口径是什么；本库能算到哪一步；算不出的原因是「数据少」还是「结构缺」。范围限定在专利价值四表与主表，不涉及论文、市场、法律诉讼与专利运营数据。

### C.2 语义锚定

「专利质量」在专利计量里通常指「专利的技术价值与经济价值」。判断依据可以是家族规模、权利要求数、被引次数、同族国家数、法律状态、维持年限、诉讼与许可，其中前五项是需求点名的五维。本指标的语义边界是「五维合成的领域质量分」，不是「单件专利价值」，也不是「企业创新能力」。这个边界决定了它必须做「件级属性 + 域级聚合」，不能只做全库平均。

### C.3 方法谱系

C.3.1 件级加权法。给每件专利算五维分，再聚合到域，优点是语义贴近需求；缺点是需要件级全量数据与域键。本报告采用这条路径，失败。

C.3.2 域级代理法。用授权率、发明占比、维持年限做代理，优点是数据可得；缺点是代理与质量不是一一对应。本报告拒绝降级到这条路径。

C.3.3 被引网络法。用被引频次、h 指数、PageRank，优点是能反映影响力；缺点是需要高覆盖的被引数据。本库可回连 475 件，不可用。

C.3.4 同族布局法。用同族国家数、家族大小，优点是能反映布局广度；缺点是同族表覆盖 0.70%，不可用。

### C.4 数据可行性

| 方法 | 最小数据 | 本库 | 可行性 |
|---|---|---|---|
| A 件级五维 | 全量件级四表 + 域键 | 0.68%—0.70%、无域键 | 不可 |
| B 域级代理 | 域级授权/发明占比 | 有域级件数，无类型拆分 | 部分（但不合规） |
| C 被引网络 | 高覆盖被引 | 可回连 475 件 | 不可 |
| D 同族布局 | 全量同族 | 0.7005% | 不可 |

### C.5 覆盖率的完整证据

四张附表的行数都在 2 万左右，这个数字不是巧合，是「价值附表按固定样本量抽取」的结果。主表 2,939,895 行，2 万行对应 0.68%；无论抽的是哪 2 万行，覆盖率都上不去。把 2 万行当成「全量」会得出「每件专利平均 1.03 个同族成员」「17.83% 有被引」这类样本结论；把 2 万行当成「样本」则只能做描述统计，不能做域级排名。报告选择后者，并在产物里把 `sample_profile.note` 写成「不得用于排名或对外发布」。

覆盖率的第二层问题是「样本是否有偏」。四张表的主键分布没有公开的抽样规则，无法判断 2 万行是随机抽取还是按某字段截取。若是按 `patent_id` 升序截取，样本会偏向早期专利；若是按价值分截取，样本会偏向高价值专利。无论哪种，都不能代表总体。报告不做「样本代表性」的假设，也不据此推断总体。

### C.6 回连超时的完整证据

三次回连查询的 SQL 结构都是「件级表 JOIN 主表」，连接键是 `patent_id`，过滤条件是申请年与 IPC4。三次都在 60 秒被 `max_execution_time` 中断，耗时 60.34 / 60.22 / 60.40 秒。这个结果说明两件事：第一，连接没有可用的索引或分区裁剪，扫描量接近全表；第二，即使把超时放宽到 300 秒，0.68% 的覆盖也不会变，超时只是「不可执行」的表象，根因是「无域键 + 低覆盖」。

修复回连不等于修复指标。即使连接能在 5 秒内完成，2 万行样本聚合到 569 个域，平均每域 35 件，看似能算中位数，但样本是否代表总体仍然未知；而且技术宽度仍然缺字段，五维只能算四维。报告把「回连超时」列为第二层障碍，把「无域键 + 低覆盖 + 缺字段」列为第一层障碍，修复顺序也应按第一层优先。

### C.7 推荐方案

1. 本期不发布「专利质量分」，只发布「价值附表可用性说明」。
2. 全量入湖四张价值附表，补 `ipc4`、`apdt_year` 两个域键。
3. 补附加分类与同族国家数，让技术宽度可算。
4. 优化 `patent_id` 连接的执行计划，把回连降到可接受范围。
5. 三件事完成后，重跑覆盖率核验；覆盖率低于 80% 不重启评分。

### C.10 与同族指标的口径对照

同批的 `M_INNOV_TINN_PATENT_QUALITY` 与本件是同一语义的不同入口，两者都判「完全不支持」，理由一致：五维需要件级附表，件级附表覆盖不足且无域键。这个一致性不是巧合，是同一套数据约束在两个入口上的重复显现。若一个入口判「部分支持」、另一个判「完全不支持」，甲方按两个入口复核时会发现口径裂缝，因此本报告与同族件保持同档。

| 对照项 | 本件 002 | 同族 PATENT_QUALITY | 是否一致 |
|---|---|---|---|
| 对象 | IPC4 领域 | 专利/领域 | 是（域级） |
| 五维 | 家族/权利要求/被引/宽度/法律 | 同 | 是 |
| 覆盖率 | 0.68%—0.70% | 0.68%—0.70% | 是 |
| 域键 | 无 | 无 | 是 |
| 回连 | 三次 60 秒超时 | 同 | 是 |
| 档位 | 完全不支持 | 完全不支持 | 是 |

口径对照的结论是：本件的判档不是孤例，而是同族件的共同结论。要让其中一个回到「部分支持」，必须同时修四张附表的覆盖率与域键；只修一个入口，另一个入口仍然不可算。
