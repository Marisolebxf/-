## 摘要

查询结果·服务类型分布要回答的是「当前这次查询命中的服务机构，按服务类型分成哪几类、每类多少家」，用于推荐图表分析里的「服务生态多样性」图。它不是全库统计指标，也不是已废止的 `M_SVC_REC_CANDIDATE_CNT`：候选数只是 `results.length`，本件有完整六要素口径（对象、分组、度量、时机、空态、禁联），保留指标身份作查询页图表的口径唯一真源。calc-logic 明确四条：对象是当前查询命中的 `org_id` 去重集合；分组优先 `svc_type`、空值回落 `org_type`、均空归「未分类」且不丢弃；度量是每桶 `COUNT(DISTINCT org_id)`；不落 ADS、0 命中时禁止回退全库 3,525 的六类分布。

换到 gkx 后，目标态的分组列不存在：全库 280 张表、6,312 列、1,285 个列名里没有任何 `svc_type` 或 `service_type`。六类只能由 `dwd_org_base_info` 的行业与 `dwd_org_org_product_info` 的经营范围关键词重建。重建后，同一批深圳 25,597 家在「INNOV 优先」规则下是 INNOV 19,879（77.6614%）、FINANCE 2,131（8.3252%）、CONSULT 1,774（6.9305%）、UNCLASSIFIED 1,030（4.0239%）、MKT 486（1.8987%）、HR 248（0.9689%）、IP 49（0.1914%）；换成「IP 优先」则是 CONSULT 9,123（35.6409%）、FINANCE 6,932（27.0813%）、MKT 5,290（20.6665%）、INNOV 1,544（6.032%）、HR 1,256（4.9068%）、IP 422（1.6486%）、UNCLASSIFIED 1,030。两套规则都合计 25,597，但形状完全不同——这就是 Q106 未签的直接后果。

本件用四个查询集合演示「查询条件一变、分布就变」：全深圳 25,597 家 INNOV 占 77.6614%；人工智能标签集合 2,071 家升到 93.8677%；南山区 7,067 家为 79.8783%；有专利的 13,378 家升到 87.8681%。判档 **部分支持**：能交付分桶逻辑、示例分布与空态规则，不能交付一个固定的「深圳服务类型分布」——那会把查询态偷换成全库统计。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的是科技专题数据查询 → 数据智能分析 → 推荐图表分析 → 服务生态多样性图。用户在查询页输入条件（行业、区县、是否有专利等）后，系统对当前结果集自动识别语义并出图；本指标负责其中一个图：把命中的服务机构按六类（INNOV / IP / FINANCE / HR / MKT / CONSULT）分桶，画成柱状或环形分布，并在图角挂 ⓘ 卡引用本 ID 作为口径说明。

图的输入是当前结果集，不是全库；这是「查询即洞察」与「全库统计」的分界。因此本件没有固定的年度基期、没有固定的分母、也没有可预聚合的 ADS 表——它的正确态就是「查询时现算、0 行落库」。

### 1.2 为什么需要这个指标

查询页如果只给一张机构清单，用户看不出「这批结果里什么类型的机构多」。服务生态多样性图的作用是把结果集的结构一眼摊开：筛「人工智能」后 INNOV 占 93.8677%，说明这批结果几乎是技术研发型；筛「南山区」后 INNOV 降到 79.8783%，说明中心城区多了金融与咨询。没有这张图，用户只能逐条读经营范围。

它同时是口径治理的锚点。查询页最容易犯的错是「0 命中时回退全库分布」，让用户以为查到了 3,525 家；calc-logic 明文禁止这条回退，本件把它写进空态规则与验收不变量。没有这个指标身份，查询叶的分桶逻辑就没有唯一真源，四个 `*_QUERY` 件会各写一套。

### 1.3 需求文档是否给出定义方法

**给了六要素，但分组列与优先级都没签。** calc-logic 查询态口径卡（2026-10-13 徐滕强选 A；D1 draft，挂 Q106）明确：对象是当前查询命中的服务机构 `org_id` 去重；分组目标态优先主数据 `svc_type`、空值回落 `org_type`、均空归「未分类」且不丢弃；度量是每桶 `COUNT(DISTINCT org_id)`；执行时机是查询链路实时聚合、不落 ADS；空结果 0 命中时各类型全 0 / 空图、禁止回退全库 3,525；边界是不消费门户类型码、不复用 `M_SVC_ORG_CNT`、不拿 `M_SVC_PT_GLOBAL_TYPE_DIST` / `M_SVC_PT_SZ_TYPE_DIST` / `M_SVC_INDUSTRY_LAYOUT` 冒充查询结果。

未签的两处是：`svc_type` 列在 gkx 不存在（目标态无法落地）；六类多命中时取哪一个没有定论（Q106 两套候选：INNOV 优先 vs IP 优先）。本件的处置是两套规则都跑、都发布，不擅自选一个当「官方口径」，并把差异写进 §3.3。

### 1.4 指标口径与维度拆解

| 要素 | 本件口径 |
|---|---|
| 对象 | 当前查询命中的服务机构 `org_id`，去重 |
| 分组 | 六类：INNOV / IP / FINANCE / HR / MKT / CONSULT + UNCLASSIFIED |
| 度量 | 每桶 `COUNT(DISTINCT org_id)` |
| 时机 | 查询链路实时分桶，内存/会话级；不落 ADS |
| 空态 | 0 命中 → 各类型全 0 / 空图；禁止回退全库分布 |
| 禁联 | 不复用门户全库环图、深圳类型分布、产业布局 |

分桶按优先级取首个命中，两套候选规则为：

$$
规则A: INNOV \succ IP \succ FINANCE \succ HR \succ MKT \succ CONSULT
$$

$$
规则B: IP \succ FINANCE \succ HR \succ MKT \succ CONSULT \succ INNOV
$$

命中集合 $H(o)$ 是机构 $o$ 的经营范围/行业标签命中的类型集合；分桶结果为：

$$
桶(o) = \begin{cases} 首个命中类型, & H(o) \neq \varnothing \\ UNCLASSIFIED, & H(o) = \varnothing \end{cases}
$$

每桶计数与占比：

$$
n_c = \sum_{o \in Q} \mathbb{1}[桶(o) = c], \qquad 占比_c = \frac{n_c}{|Q|} \times 100\%
$$

其中 $Q$ 是当前查询命中的机构集合。验收不变量为：

$$
\sum_{c \in 六类} n_c + n_{UNCLASSIFIED} = |Q|
$$

### 1.5 与同域姊妹指标的分工

与 `M_SVC_REC_CANDIDATE_CNT` 的分工：候选数已于 2026-10-13 废止，它的全部逻辑就是 `results.length`，没有分组、没有口径；本件保留指标身份，是因为它有六要素与空态规则，是查询页图表的口径真源。两者不可互相替代：候选数给「多少家」，本件给「结构」。

与 `M_SVC_PT_SZ_TYPE_DIST` 的分工：本件按六类业务分桶，深圳类型件按三类本体（企业/高校/科研院所）分桶；本件随查询条件变，深圳类型件是固定截面。拿深圳类型环图去顶查询结果分布，会违反本件的「禁联」条款。

与 `M_SVC_INDUSTRY_LAYOUT` 的分工：产业布局件是全库的产业分布，本件是查询结果集的服务类型分布；两者都可能画环图，但分母不同、对象不同、时机不同。

### 1.6 本件的边界与不做什么

本件不做六件事：不落 ADS、不预聚合（本编号在 fact/dist 中 0 行是正确态）；不在 0 命中时回退全库分布；不把六类当机构本体类型（企业/高校/院所是另一条轴）；不把「未分类」并进任一类；不声称两套优先级中的任何一套已获甲方签署；不把示例集分布说成「深圳全库服务类型分布」。

## 二、计算过程

### 2.1 方法选择：先定对象集合，再定词表，最后把优先级差异摊开

查询态指标最容易犯两个错：一是把「全库」当对象，算出固定分布，失去查询语义；二是遇到多标签时随便取一个，导致同一批机构在两套规则下形状完全不同却只有一套数被发布。本件的方法是：对象严格取当前查询集合（示例集用快照预置的四个集合），词表只用 gkx 可核的经营范围/行业标签，优先级跑两套并同时发布。

为什么不在两套优先级里选一个？因为 Q106 未签，选任何一个都是替甲方做决定。INNOV 优先会把 19,879 家（77.6614%）压进 INNOV，CONSULT 只剩 1,774（6.9305%）；IP 优先会把 CONSULT 抬到 9,123（35.6409%），INNOV 掉到 1,544（6.032%）。这不是小数点差异，是图的形状整体换形。本件的处置是：把两套都算出来，标注「待 Q106 签署」，让甲方看到选择后果再签。

### 2.2 步骤 1｜确定查询对象集合（D1）

对象是当前查询命中的 `org_id` 集合，去重。为了让口径可复算，本件用快照预置了四个示例集合，分别代表四类查询条件：全深圳切片 25,597 家；人工智能行业标签集合 2,071 家；南山区 7,067 家；有专利的机构 13,378 家。四个集合都来自同一份族级快照，不重新连库。

四个集合不是「全库统计」，只是「四个具体查询的结果」。正文给它们的分布，是为了证明「查询条件一变、分布就变」，不是给出一张固定的深圳服务类型表。任何把 all_sz 的分布当「深圳全库分布」引用的做法，都违背本件的对象定义。

### 2.3 步骤 2｜六类词表与命中（D2）

六类词表由经营范围关键词与行业标签构成：INNOV 对应研发、技术开发、技术服务等；IP 对应知识产权、专利代理、商标代理；FINANCE 对应金融、投资、保险、融资租赁；HR 对应人力资源、劳务派遣、招聘；MKT 对应市场营销、广告、会展；CONSULT 对应咨询、管理顾问、规划。命中是多标签的：一家机构可以同时命中 INNOV 与 CONSULT，也可以同时命中 FINANCE 与 MKT。

深圳 25,597 家的命中行合计 61,864，平均每家 2.416846 类。这个数说明「六类互斥」只是分桶后的结果，不是原始标签的性质：原始标签高度重叠，必须先定优先级才能分桶。61,864 与 25,597 的差不是错误，是多标签的度量。

词表的局限必须说清：它是关键词匹配，不是主营业务分类。一家经营范围写「技术服务、技术咨询」的公司会同时命中 INNOV 与 CONSULT，按 INNOV 优先归 INNOV，按 IP 优先则可能归 CONSULT；它的真实主业可能是咨询。这是代理口径的固有误差，不是规则写错。

### 2.4 步骤 3｜规则 A（INNOV 优先）分桶（D3）

按 INNOV ≻ IP ≻ FINANCE ≻ HR ≻ MKT ≻ CONSULT 取首个命中，深圳 25,597 家的结果是 INNOV 19,879（77.6614%）、FINANCE 2,131（8.3252%）、CONSULT 1,774（6.9305%）、UNCLASSIFIED 1,030（4.0239%）、MKT 486（1.8987%）、HR 248（0.9689%）、IP 49（0.1914%）。七行合计 25,597。

这个分布的形状是「一家独大」：INNOV 占近八成，其余五类加起来不到 18%。原因不是深圳真的八成都做研发，而是 INNOV 排第一，任何同时命中 INNOV 的机构都被它吸走；IP 被压到 49 家（0.1914%）就是证据——深圳不可能只有 49 家做知识产权服务，只是它们大多同时命中 INNOV。

全池 44,153 家的规则 A 分布是 INNOV 32,294（73.1411%）、FINANCE 3,211（7.2724%）、CONSULT 3,132（7.0935%）、UNCLASSIFIED 3,680（8.3347%）、MKT 1,146（2.5955%）、HR 582（1.3181%）、IP 108（0.2446%）。形状与深圳切片一致，说明规则本身的偏向不随城市变。

### 2.5 步骤 4｜规则 B（IP 优先）分桶（D4）

按 IP ≻ FINANCE ≻ HR ≻ MKT ≻ CONSULT ≻ INNOV 取首个命中，深圳 25,597 家的结果是 CONSULT 9,123（35.6409%）、FINANCE 6,932（27.0813%）、MKT 5,290（20.6665%）、INNOV 1,544（6.032%）、HR 1,256（4.9068%）、IP 422（1.6486%）、UNCLASSIFIED 1,030（4.0239%）。七行同样合计 25,597。

换规则后，INNOV 从 19,879 掉到 1,544（差 18,335 家），CONSULT 从 1,774 涨到 9,123（差 7,349 家），FINANCE 从 2,131 涨到 6,932，MKT 从 486 涨到 5,290，HR 从 248 涨到 1,256，IP 从 49 涨到 422。唯一不变的是 UNCLASSIFIED 1,030——因为它由「六类全不中」定义，与优先级无关。

这个对比是本件最重要的证据：同一批机构、同一套词表、同一个总数，只换优先级，图的形状就从「INNOV 一家独大」变成「CONSULT/FINANCE/MKT 三分天下」。任何只发布一套数的版本，都必须说明它选的是哪套、为什么。

### 3.3 口径陷阱与规避

第一，**两套优先级不是小数差异**。INNOV 优先与 IP 优先在深圳切片上让 INNOV 差 18,335 家、CONSULT 差 7,349 家。任何只写「服务类型分布如下」而不写优先级的文档，都无法被复核。

第二，**多标签不能直接相加**。61,864 命中行对应 25,597 家，若把六类命中数当桶大小相加，会得到 61,864 而不是 25,597。必须先取首个命中再计数。

第三，**未分类要单列**。1,030 家（4.0239%）六类全不中，不能并进 CONSULT 或 INNOV；并入任一类都会让该类虚高，也会掩盖词表覆盖不足。

第四，**查询态不能落 ADS**。本编号在 `svc_metric_fact` / `svc_metric_dist` 中 0 行是正确态。若有人补了预聚合行，反而说明口径被偷换成全库统计。

第五，**0 命中不能回退 3,525**。正本明文禁止；回退会让空查询看起来有结果，是查询页最严重的口径事故。

第六，**词表是代理不是分类**。「技术服务、技术咨询」会同时命中 INNOV 与 CONSULT；「投资咨询」会同时命中 FINANCE 与 CONSULT。分桶结果只代表「按优先级取首个」，不代表主营业务认定。

### 3.7 与全库参考的差异

全池 44,153 家的规则 A 分布是 INNOV 32,294（73.1411%）、CONSULT 3,132（7.0935%）、FINANCE 3,211（7.2724%）、UNCLASSIFIED 3,680（8.3347%）。与深圳切片相比，全池 INNOV 占比低 4.52 个百分点、未分类高 4.31 个百分点，说明深圳切片的词表覆盖更好（未分类更少），也说明非深圳机构的经营范围文本质量更差。这个差异不是本件的结论，只是提示：不要把全池分布直接套到深圳查询上。

### 3.8 与其他查询态件的口径一致性

同族 `*_QUERY` 四条（TALENT_STRUCT / ORG_PERF / TECH_HEAT / COMMON_INFO_TREND）都是「查询结果上的分布/计数」，形态一致：对象是当前结果集、度量是去重计数、不落 ADS、0 命中不回退。本件与它们的差别只在分组字段（六类服务类型 vs 其他维度）。若未来统一查询态口径卡，本件的六要素可直接复用。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺口 | 位置 | 规模 | 影响 |
|---|---|---|---|
| `svc_type` 主数据 | 全库列名 | 1,285 列名中 0 个 | 目标态分桶列不存在 |
| 分桶优先级 | Q106 | 两套候选未签 | 分布整体换形 |
| ADS 承载 | `svc_metric_fact` / `svc_org_card` | 0 张 | 本编号 0 行是正确态 |
| 语义识别 | 经营范围词表 | 关键词匹配 | 未分类 1,030、多标签 2.416846 |

### 4.2 修复路径与优先级

1. **签 Q106**（P0）。两套优先级必须先定一套，否则每次出图都要解释「为什么这次 INNOV 多、上次 CONSULT 多」。
2. **建 `svc_type` 主数据**（P0）。有了主数据列，六类不再依赖关键词，未分类会大幅下降。
3. **补经营范围文本质量**（P1）。非深圳机构未分类 8.3347%，高于深圳 4.0239%，说明文本覆盖不均。
4. **建查询侧缓存**（P2）。注意：缓存是查询侧，不是 ADS 预聚合；本编号仍应保持 fact/dist 0 行。

### 4.3 降档论证（为什么不是更高/更低一档）

不能判「完全转换支持」：该档要求依赖侧表结构与数据量均足够，而本件的目标分组列 `svc_type` 在全库不存在，优先级未签，数据不足以直接转换。不能判「完全直接支持」：两库均无分桶结果面，且本编号本就不该有 ADS 行。也不能判「完全不支持」：词表重建能出四套可复算分布，六要素齐全，空态与禁联可执行。故判「部分支持」。

### 4.4 缺口对下游的影响

对查询页：用户看到的分布依赖未签的优先级，同一批结果在两套规则下形状不同，产品无法对外承诺「这就是服务类型构成」。对口径治理：`svc_type` 不建，六类永远是代理，无法与主数据对齐。对跨件：查询件与深圳类型件是两条轴，若产品把两者混在一个图例里，会出现「企业/高校/院所」与「INNOV/CONSULT」并列的错误。

## 六、结论与发布建议

**判档：部分支持。** 六要素齐全、空态与禁联可执行、四套示例分布可复算；但目标分组列不存在、优先级未签、词表是关键词代理。

发布建议分三档：

- **可发布**：四个示例集合的分布、两套优先级对照、多标签结构（61,864 / 2.416846）、未分类 1,030、空态规则。
- **须带警示发布**：任何单套分布，必须标注优先级与「Q106 待签」；任何查询页图，必须带 ⓘ 卡引用本 ID。
- **不可发布**：把示例集分布说成「深圳全库服务类型分布」；0 命中回退 3,525；把六类与本体三类混在一个图例；把本编号写进 ADS 预聚合。
