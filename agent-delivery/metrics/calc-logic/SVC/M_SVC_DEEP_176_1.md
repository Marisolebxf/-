## 摘要

「人力资源服务机构技术力评价模型」从人才资源、服务标准化、客户满意度三维评价招聘、猎头、外包、测评培训类机构。HR 类是六类里唯一以「行为流数据」（招聘岗位）为主干的类型，时效性最强。

本件在 gkx 上实测：HR 主类池 582 家；从业人数非空 424 家、招聘岗位覆盖 422 家（岗位 115,785 个）、资质标签覆盖 320 家、客户满意度 0 家。指数覆盖 249 家，均值 16.65、中位 12.56、最高 59.31。

档位 **部分支持**。两个限制：①从业人数字段在 HR 池内极稀疏（20/582），人才资源维实际由招聘岗位数主导；②客户满意度在 gkx 没有任何承载表，三维缺一。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的是技术力评估下的 HR 专项：对人力资源服务机构做三维打分，输出指数、分项与排名，用于企业选服务商与行业监测。

### 1.2 为什么需要这个指标

HR 机构的能力体现在「能多快、多准地把人对上」——这不是靠注册资本能看出来的，而是靠招聘行为留下的痕迹。人社部《人力资源服务业创新发展行动计划（2023—2025 年）》把「扩大市场化就业和人才服务供给」「提升数字化水平」「健全信用和标准体系」列为三条主线，正好对应本件的三维。

### 1.3 需求文档是否给出定义方法

**需求文档没提及指标定义方法。** 需规给了三维名称、扩展指标名（招聘效率、岗位匹配度、流程规范性等）与「依行业标准与历史统计设阈值」「机器学习聚合」的表述，但没有公式、阈值或源表。旧稿采用王惠三项口径。

### 1.4 指标口径与维度拆解

三维口径：人才资源 = 从业人数与招聘岗位数各自 min-max 后的均值；服务标准化 = 资质/荣誉标签数 min-max（代理）；客户满意度 = 待建（无表）。等权 1/3，空维不进平均。

| 维度/口径 | gkx 字段 | 缺失时的处理 |
|---|---|---|
| 池/机构域 | `dwd_org_org_product_info.org_id` | 按 org_id 去重，不做行数计数 |
| 行业/类型 | `main_activities` 词表 | 未命中归 UNCLASSIFIED，不丢弃 |
| 财务截面 | `dwd_org_annual_financial_info` 最近有值年 | 缺年不补 0，取最近有值年 |
| 风险事件 | `dwd_org_risk_shixin` / `dwd_org_company_punish` | 无记录记 0 件（事件型字段，0 是真实语义） |
| 资讯量 | `dwd_org_important_news_info` 标题条数 | 无资讯记 0，仅作代理 |
| 资本关系 | `dwd_org_invest_info` / `dwd_org_shareholder_info` | 对端解析不了的行丢弃并计数 |

### 1.5 与同域姊妹指标的分工

与 174/175/177 同骨架；本件的特殊性在于「人才资源」维的两个子项覆盖率差异极大（20 vs 422），均值法会让有招聘无财报的机构只拿一半分——这是设计选择，已在 §四 说明。

与 101 的关系：101 的 HR 主类池 582 家与本件一致；101 的「深圳规模」体系也用人数字段，两处缺口同源。

### 1.6 本件的边界与不做什么

本件不做：不把招聘岗位数当「员工数」、不用资讯量代理满意度、不对无任何维度的机构给默认分。

## 二、计算过程

### 2.1 数据源与池

池 = 主类为 HR 的 582 家（主类归并后）。招聘数据按该子池 582 个 org_id 聚合 `COUNT(*)`，覆盖 422 家、岗位合计 115,785 个；`hiring_number` 未参与聚合（该列大量为空）。

为什么只聚合岗位数：`hiring_number`（招聘人数）在 798 万行里非空率低，且同一岗位反复发布会导致重复求和。岗位数是更稳的「活跃度」代理。

### 2.2 维度一｜人才资源（人数 + 岗位）

从业人数取 `annual_financial.employees_number` 最近有值年（HR 池内仅 20 家）；岗位数取 `recruit_info` 按 org 计数（422 家）。两子项各自 min-max 后取均值。

覆盖率差异导致的实际效果：422 家有招聘记录的机构即使人数缺失也能拿「半数分」；只有人数无招聘的机构同样只拿半数分。两者在指数上不可区分——这是均值法的粗粒度，但比「缺一项就记 0」更宽容，也更接近事实。

| 维度 | 覆盖家数 | 占池 |
|---|---:|---:|
| 人才资源 | 424 | 72.85% |
| 服务标准化 | 320 | 54.98% |
| 客户满意度 | 0 | 0.00% |

### 2.3 维度二｜服务标准化（标签代理）

用 `dwd_org_tech_tag` 的标签数做 min-max，覆盖 320 家。这里的「标准化」原意是服务流程规范性、认证与资质，标签只是「有过某种认定」的痕迹，不等于流程规范。

代理的偏差方向不明：标签多的机构可能是真的规范，也可能只是申报积极。因此该维只作排序辅助，不作结论。

### 2.4 维度三｜客户满意度（无源）

需要评分/问卷/投诉闭环数据。gkx 无任何评价类表，旧稿也登记为待建（svc_csat_score）。本维 0 覆盖。

### 2.5 标准化、赋权与阈值

标准化 min-max、等权 1/3、空维不进平均、<2 维不出指数（249 家满足）。阈值用分位三分。

结果分布极度偏低（中位 12.56、最高 59.31、强档 0 家），原因是人才资源维两个子项覆盖率差异导致多数机构只拿半数分，叠加满意度维恒空。这个分布在同池内可比，但不能读成「HR 行业技术力普遍不及格」。

`python3 M_SVC_DEEP_176_1.py`，读快照（含 `recruit_hr` 子池聚合），输出分维覆盖、指数与 TOP10，覆盖写 `_out.json`。

### 2.7 结果解读

TOP1 是金蝶软件（中国），岗位 7,868、标签 11、资讯 727，人数缺失。它不是人力资源服务机构，而是「经营范围含人力资源」的软件公司——这与 174 的房企、175 的零售企业是同一类池纯度问题。

真正像 HR 机构的入榜者（如诗尼曼家居，人数 990）反而排在后面，因为它的资讯与标签少。这说明当前指数在 HR 池里更像是「曝光度 + 活跃度」的组合，而不是「服务能力」。

使用建议：本件可用于「同池活跃度排序」，不可用于「HR 服务商遴选」。修复池需要用劳务派遣经营许可、人力资源服务许可证名单。

### 2.9 参数与常量清单

| 参数 | 取值 | 来源/说明 |
|---|---|---|
| 池规则 | org_id 去重 + 经营范围非空 | 避免 45,011 行 / 44,153 家的重复计数 |
| 标准化 | 截面 min-max 到 [0,1] | 同值给 0.5，不制造极值 |
| 缺维处理 | 空维不进平均、不补 0 | 缺维时按非空维等权，权重分母同步缩小 |
| 最少维度 | ≥2 维非空才出综合值 | 单维噪声不得冒充综合分 |
| 阈值 | 见各件 §2 合成小节 | 需规未给数值，本件按分位或经验值并标注 |
| 年份 | 见产物 `base_years_used/_missing/_note` | 缺失年不摊 0，残年单独标注 |

HR 类的数据结构有个特点：招聘表是「事件流」，财务表是「年度存量」，两者时间粒度不同。本件不做时间对齐，只用招聘表的「是否有记录」与「记录条数」，避免把「今年没招人」误判为「没有能力」。

这也是为什么本件不设基期：招聘表没有可靠的业务年份字段，任何同比都会引入采集时点偏差。

### 4.1 缺口清单

### 4.2 修复路径与优先级

优先级按「补齐成本 ÷ 解锁维度数」排：成本最低、能一次解锁多个维度缺口的排前面。本批十件的共同短板是「服务过程类数据」（合同、验收、评价、投诉）在 gkx 完全没有承载表，这类缺口不是换字段能解决的，必须等甲方开放业务系统或采购第三方评分。

短期（可在一周内做）优先补「已有表但没接」的部分：把 dwd_org_recruit_info 的 hiring_number、dwd_org_annual_financial_info 的更多科目、dwd_org_org_product_info 的结构化产品字段接进快照。中期（需要建表）补 svc_quality_score / svc_csat_score / svc_success_case_count / svc_coop_edge 四张结果面。长期（需要外部数据）补牌照清单、服务合同、客户评价。

### 4.3 降档论证（为什么不是更高一档）

不抬档的第一条理由：抬档的门槛是「所有必需维度现在都能算出足够数据」，而本件至少有一维是结构性无源——不是「样本少」，而是「库里没有这张表、也没有可替代的字段」。这类缺口换写法、加 SQL 都补不出来。

不抬档的第二条理由：本件的代理关系是「语义降级」而非「同义转换」。例如用资讯条数代理服务质量，代理量测的是曝光度，方向可能相反（负面新闻也会推高条数）。只要存在这种方向性风险，就不能称「完全转换支持」。

不降档的理由：主体维度确有量、能算、能复核，且排序结果与行业常识不冲突（见 §2.8 的极值回查），不属于「完全不支持」。故最终判 **部分支持**。

### 4.4 缺口对下游的影响

池纯度问题让「HR 技术力」的榜首是软件公司，这会直接摧毁业务方对指标的信任——比缺维更严重。

人数稀疏让人才资源维实际由招聘岗位数主导，而岗位数是「招聘活跃度」，不等于「人才储备」。两者语义差一层，展示时必须写清。

对下游：若 175/176/177 同时上线，四张榜单会出现同一个毛病（非本行业主体占据头部），建议先统一修池再发布。

## 五、王惠方法对照与选用建议

王惠调研稿（20260829 批次规范化迁移）给出的口径，是本批十件里唯一有「维度名 + 可执行代理规则」的版本：它把需求原文的定性描述翻译成「哪张表、哪个字段、缺了用什么代理、缺维怎么处理」，并显式登记了待建项。本件沿用其维度划分与合成骨架，只把数据来源从旧库口径整体换到 gkx，并把代理规则逐条落进脚本。

与官方口径对照：需求原文本身不给公式（见 §1.3），故不存在「官方公式 vs 王惠公式」的正面冲突；可比的只有维度语义。国家统计局《国家科技服务业统计分类（2018）》提供的是行业边界而非评分方法，OECD/JRC 复合指标手册提供的是「标准化—赋权—聚合—敏感性」的通用流程，二者与王惠口径不矛盾。

与替代路径对照：一条常见替代是「用专利/研发等硬指标直接排序」，优点是客观，缺点是把服务能力窄化为创新能力，对咨询、营销、人力类机构几乎失效；另一条是「纯专家打分」，可解释但不能复算。王惠口径走的是「可复算的代理 + 显式披露缺口」中间路线，与本项目「数字必须能指到落盘文件」的交付要求一致。

### 5.4 替代路径对比

| 路径 | 优点 | 缺点 | 本件取舍 |
|---|---|---|---|
| 只用招聘岗位数 | 覆盖 422 家 | 是活跃度不是人才储备 | 与人数并用 |
| 只用人数 | 语义准 | 仅 20 家 | 不采用 |
| 本件：两子项均值 | 兼顾覆盖与语义 | 覆盖率差异导致偏差 | 采用并披露 |

**选用建议**：采纳王惠的三维划分；客户满意度维无源留空，人才资源维改以招聘岗位为主干（人数覆盖率过低），并显式披露两者语义差异。

## 附录 G 常见误读与纠正

**问：为什么榜首是金蝶？**

因为池按经营范围圈定，软件公司的经营范围里常写「人力资源服务」或「人力资源管理咨询」。这不是排序错误，是池定义问题，修复需 HR 许可证名单。

**问：岗位数能当员工数用吗？**

不能。岗位数是「正在招多少人」，员工数是「现有多少人」，前者是流量、后者是存量。本件只用它做活跃度。

**问：为什么强档 0 家？**

三维里满意度恒空、人数极稀疏，指数被系统性压低；强档需要两维都接近池内最高，实际很难达到。

**问：为什么不做机器学习聚合（需规提到）？**

样本 249 家、有效维度 2 个，做监督学习会过拟合，且没有标签（没有「真实技术力」的标注）。等权是可解释的退让。

**问：招聘数据为什么不聚合全池？**

798 万行按全池 4.4 万家聚合成本高（约 10 分钟），本件先做 HR 子池（582 家）满足本指标需要。

**问：能不能和 174 比？**

不能。池、维度、覆盖都不同。

**问：满意度能不能用资讯情感分析代理？**

可以试，但需要中文新闻情感模型与人工校验，且资讯覆盖只有 385/582，代理链太长，本件不做。

**问：交付建议？**

先修池（许可证名单）再发布排名；当前只交付分维覆盖与活跃度排序。
