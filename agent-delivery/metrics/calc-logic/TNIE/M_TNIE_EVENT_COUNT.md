## 摘要

本件的核心不是算一个数，而是把「为什么这个数不能算」讲清楚。事件表实测 20 行，全部落在 2026-05-13 与 2026-05-14 两天，20 个事件名中 17 个含论坛/大会/展会/博览会/交易会等词，10 个含「医药」，组织者前五全部含「国药励展」。这是单一展会系列的日程表，不是创新事件库。

| 读数 | 值 |
|---|---|
| `dwd_event` 行数 | 20 |
| 覆盖自然日 | 2 |
| 不同事件名 | 20 |
| 不同组织者 | 19 |
| 名称含展会词 | 17（85%） |
| 名称含「医药」 | 10（50%） |
| 真事件计数 | 拒拟（null） |
| 代理：活动型标题（全库） | 18,884 / 1,668,414（1.1319%） |
| 代理：活动型标题（2025 起） | 6,213 / 518,531（1.1982%） |
| 判档 | 部分支持 |

第一个事实是**20 行不是抽样，是全部**。`dwd_event` 没有分区、没有更早年份、没有其他主办方。它不是「事件表的一小部分」，而是「一张只装了一场展会系列的表」。任何按年、按地区、按类型的事件统计都无法从它得到。

第二个事实是**代理口径的量级很小**。全库 1,668,414 条报道中，标题含 10 个活动词的只有 18,884 条，占 1.1319%。这个比例说明「活动型报道」在媒体库里是稀有事件，不是主流内容。代理数只能做「活动报道密度」，不能做「活动发生密度」。

第三个事实是**代理数不能反向校验事件表**。20 行事件表对应 18,884 条活动型报道，两者不是同一层级的东西：一个是事件记录，一个是媒体报道。用 18,884 去除 20 没有任何意义，本件也不做这种除法。

## 一、需求定义概述

### 1.1 指标编号与归属

| 项 | 值 |
|---|---|
| 指标编号 | `M_TNIE_EVENT_COUNT` |
| 名称 | 抽取事件条数 |
| 一级 / 二级 | 创新分析 / 事件 |
| 更新频率 | 事件表补齐后按批复算；当前不适用 |
| 关联 Q | 创新活动密度、区域活动监测 |
| 对齐状态 | 未对齐（事件面缺失） |
| 上游 | `dwd_event`（20 行）、`dwd_org_important_news_info`（代理） |
| 下游 | 活动监测、报道密度专题 |

### 1.2 为什么需要「事件条数」

创新活动不只有专利和论文，还有论坛、展会、发布会、路演。这些活动是创新生态的「软组织」：它们不直接产生专利，但承担信息交换、供需撮合、政策宣讲的功能。事件条数是这类活动最基础的度量：一个城市一年办多少场活动，能粗略反映生态活跃度。

也正因为它基础，口径必须干净。若把「某场展会的 20 个分论坛」当成「20 场创新活动」，再乘上城市数，会得到一个完全虚构的活动总量。本件宁可判部分支持，也不做这种放大。

### 1.3 口径定义

真事件计数 $E$ 定义为事件表中满足「有名称、有开始日期、有主办方」的记录数：

$$E=\left|\{e\in \text{dwd\_event}:\ e.\text{name}\neq\varnothing \land e.\text{start\_date}\neq\varnothing\}\right|$$

本件实测 $E$ 的候选集只有 20 行，且全部来自同一展会系列，因此 $E$ 不可作为创新事件总量，判拒拟。

代理口径 $R$ 定义为媒体报道表中标题命中活动词集合 $W$ 的条数：

$$R=\left|\{r\in \text{news}:\ \exists w\in W,\ w\subseteq r.\text{title}\}\right|,\qquad W=\{\text{论坛},\text{大会},\text{峰会},\text{展会},\text{博览会},\text{发布会},\text{研讨会},\text{交易会},\text{年会},\text{仪式}\}$$

$R$ 的单位是「条报道」，不是「场活动」。一条报道可能对应一场活动，也可能对应多场，也可能只是提及。这个不确定性无法从数据中消除。

### 1.4 计算公式与本批实现式

```python
EVENT_WORDS = ("论坛", "大会", "峰会", "展会", "博览会",
               "发布会", "研讨会", "交易会", "年会", "仪式")

def is_event_like(title):
    return any(w in title for w in EVENT_WORDS)

proxy_all = sum(1 for t in titles if is_event_like(t))
proxy_since_2025 = sum(1 for d, t in rows
                       if d >= "2025-01-01" and is_event_like(t))
```

三个实现要点。第一，匹配用「包含」而不是「等于」，因为标题是自由文本，活动词通常嵌在长句里。第二，词表只收明确指向线下活动的词，不收「活动」「举办」这类泛词，否则会把大量非活动报道算进来。第三，按日期过滤用字符串比较，因为 `news_date` 是标准日期格式，字典序与时间序一致。

## 二、计算过程

### 2.1 事件表实测

`dwd_event` 逐字命中 1 张表，行数 20。字段五个：`event_name`、`organizer`、`start_date`、`end_date`、`event_url`。没有事件类型字段、没有参与人数、没有地区字段、没有行业标签。仅凭这五个字段，能做的只有「按名称/日期/主办方计数」。

20 行分布在 2026-05-13 与 2026-05-14 两天，`date_min` 与 `date_max` 分别是这两天。不同事件名 20 个，说明没有重名；不同组织者 19 个，说明有一家组织者办了两场。这个结构本身就是「一场大会的议程表」，不是「一年的活动清单」。

### 2.2 单一展会系列的证据

三条证据同时成立。第一，日期集中：20 行只覆盖两天，任何跨日、跨月、跨年的活动都不在表里。第二，主办方集中：组织者 top5 分别是「主办：国药励展」2 场、「主办：国药励展、药渡集团」1 场、「主办：国药励展；承办：药持网」1 场、「主办：国药励展、长济医疗」1 场、「主办单位：国药励展、商帅商学院」1 场，全部含「国药励展」。第三，URL 集中：`event_url` 全部指向 `mm.reed-sinopharm.com` 同一站点。

三条证据合起来说明：这不是「gkx 收录了 20 场活动」，而是「gkx 收录了一场国药励展系展会的 20 个条目」。把它当事件面，等于把一张议程表当成一个行业的活动总量。

还有一个细节值得记下：20 个事件名里 10 个含「医药」，17 个含展会词。这说明该系列的主题是医药健康展，子条目是同期论坛与专题展。换句话说，20 行内部本身还有层级关系——有的是主展，有的是分论坛，但它们在同一张表里平铺，没有父子字段可以区分。这也是「不能当事件数」的另一个理由：连表内层级都无法还原。

### 2.3 负证据：五张事件表逐字 0

除了 `dwd_event`，本件还探了五张可能承载事件或抽取结果的表：`innovation_event`、`dwd_innovation_event`、`ads_tech_news_extraction`、`ads_tech_news_event`、`sandbox_sqlite_extractions`。五张全部在 `information_schema.tables WHERE table_schema='gkx'` 下命中 0。

这五张表的命名分别覆盖了「事件主题表」「事件明细表」「新闻抽取结果表」「新闻事件宽表」「沙箱抽取结果表」五种可能形态。五种都没有，说明事件抽取链路在 gkx 侧没有落地，不是「表名不同」的问题。

### 2.4 代理口径的构造

代理数来自 `dwd_org_important_news_info` 的标题。选标题不选正文，理由是标题是编辑提炼过的，活动词出现在标题里，说明报道主题就是这场活动；正文里出现活动词，可能只是背景提及。

活动词表收 10 个：论坛、大会、峰会、展会、博览会、发布会、研讨会、交易会、年会、仪式。这 10 个词的共同点是都指向「有组织、有场地、有议程」的线下活动。不收「活动」「举办」「召开」，是因为这三个词太泛，会把「举办培训班」「召开会议」这类非创新活动也算进来。

### 2.5 代理读数

全库 1,668,414 条报道中，标题命中活动词的有 18,884 条，占 1.1319%。2025-01-01 起 518,531 条报道中，命中 6,213 条，占 1.1982%。两个比例接近，说明活动型报道的密度在近一年半略升，但幅度很小。

按 28,123 家覆盖企业摊，2025 年起每家企业平均只有 0.2209 条活动型报道。这个数低得需要解释：不是企业不办活动，而是媒体报道只覆盖「重要新闻」，大量活动没有进入报道库。代理数的分母是报道，不是活动，所以「每家 0.2209 条」不能读成「每家企业一年办 0.22 场活动」。

### 2.6 为什么不能当事件计数

三个原因。第一，单位不同：代理数的单位是「条报道」，事件计数的单位是「场活动」。第二，覆盖不同：报道库只收重要新闻，大量活动没有报道；事件表若完整，应该覆盖所有登记活动。第三，方向不同：一场大型活动可能产生几十条报道，十场小型活动可能一条报道都没有，报道数与活动数不是单调关系。

因此本件在产物里把代理字段命名为 `proxy`，并写死 `not_an_event_count=true`。任何下游要用这个数，必须同时显示「代理口径：媒体报道 ≠ 事件发生」。

## 四、数据缺失情况

### 4.1 通用事件表：不存在（拒拟维）

`dwd_event` 只有 20 行单一展会系列；`innovation_event` 与 `dwd_innovation_event` 逐字命中 0 张。没有表能承载「一场活动一行」的通用事件面。

**拒拟理由**：事件面不存在，20 行不构成可统计总体。
**替代口径**：媒体报道中的活动型标题条数。
**与原文差别**：原文要「事件条数」，本件只能给「活动报道条数」，单位与语义都不同。

### 4.2 事件抽取结果：不存在（拒拟维）

`ads_tech_news_extraction`、`ads_tech_news_event`、`sandbox_sqlite_extractions` 三张抽取结果表逐字命中 0 张。说明新闻到事件的抽取链路在 gkx 侧没有落地，不能从新闻正文反推事件记录。

### 4.3 代理口径的三个缺口

第一，无地点字段：报道表没有活动举办地，无法做城市对比。第二，无行业字段：报道表只有报道对象企业，无法判断活动属于哪个技术领域。第三，无规模字段：一条报道无法区分是千人大会还是小型研讨会。

还有一个更隐蔽的缺口：报道表的主键是报道对象企业，不是活动主办方。一条关于某企业参加展会的报道，`org_id` 指向的是参展企业，不是展会主办方。这意味着即便按企业聚合，得到的也是「哪家企业被报道参加活动」，而不是「哪家机构办了活动」。要做主办方维度，必须有活动主办方字段，而报道表没有。

这两个缺口叠加，使得代理数只能停留在「总量 + 年度」两个维度。任何更细的分组（城市、行业、主办方、活动规模）都会引入无法验证的假设，本件一律不做。

### 4.4 不得外推的四件事

1. **不得把 18,884 读成 18,884 场活动**：它是报道条数，不是事件发生数。
2. **不得把 0.2209 读成每家企业办活动数**：分母是 28,123 家覆盖企业，不是活动主办方总数。
3. **不得用 20 行乘城市数放大**：20 行是一场展会系列的条目，不是城市活动样本。
4. **不得把链新闻 108,052 与报道 1,668,414 相加**：两张表口径不同，去重逻辑不同。

### 4.5 停用与重估条件

出现以下任一情况应重估：① 通用事件表入湖，且覆盖多主办方、多日期、多地区；② 事件抽取结果表落地；③ 报道表补地点与行业字段；④ 甲方确认接受「活动报道条数」作为事件代理并改名发布。

## 五、结论与发布建议

### 5.1 可用结论

第一，`dwd_event` 20 行、覆盖两天、单一展会系列，真事件计数拒拟。第二，名称含展会词 17 行占 85%，含「医药」10 行占 50%，进一步证明是医药展会系列。第三，代理口径全库 18,884 条占 1.1319%，2025 起 6,213 条占 1.1982%。第四，代理数每企业 0.2209 条，只反映报道密度。第五，五张候选事件表逐字 0。第六，判部分支持。

### 5.2 发布口径（逐条写死）

| 项 | 必须写明的口径 |
|---|---|
| 指标名 | 若发布代理数，必须改名为「活动报道条数」 |
| 代理声明 | 媒体报道 ≠ 事件发生，逐条标注 |
| 事件表 | 20 行单一展会系列，不作总量 |
| 城市/行业 | 代理数不支持城市与行业拆分 |
| 与链新闻 | 108,052 条只作背景，不相加 |

### 5.3 与旧稿的取舍

旧稿若把 `dwd_event` 当通用事件表算出「事件总数 20」，本版不沿用——20 是一个展会系列的条目数，不是活动总量。本版把 20 行作为「事件面不足」的证据，而不是读数，这是本件与旧稿最根本的差别。

另需说明：旧稿若用「新闻事件抽取」造过一个事件库，本版也不沿用，因为 gkx 侧的五张抽取结果表逐字 0，任何事件库都无法在本目录复现。复现不了的历史产物，不能作为新件的上游。

### 5.4 后续

三条路径：① 补通用事件表，恢复真事件计数；② 补事件抽取链路，从新闻抽事件；③ 甲方确认代理口径并改名发布。第一条是根本解，第二条是规模化路径，第三条是当前唯一可发布的折中。

在三条路径落地前，本件的产物只应出现在「口径说明」类页面，不应出现在「活动数量」类看板。若必须上看板，格名要写成「活动报道条数（媒体代理）」，并附一行「媒体≠事件」。这行字不是免责声明，而是防止读者把 18,884 当成 18,884 场活动。

## 附录 C 可行性完整版

### C.1 为什么不用正文匹配

正文匹配会把「本次论坛期间」这类背景提及也算成活动报道，导致代理数虚高。标题匹配更保守，代价是漏掉「标题不含活动词但正文确为活动报道」的样本。本件选择保守，因为代理数已经很小，虚高比漏报更危险。

### C.2 为什么词表只有 10 个

词表越长，误报越多。「路演」「对接会」「训练营」都可以算创新活动，但它们也大量出现在非活动语境里。本件只收最明确的 10 个词，保证「命中即大概率是活动报道」。若甲方要扩大口径，应作为新版本重算，不能在当前结果上打补丁。

### C.3 事件面补齐后的最小字段集

至少需要：事件 ID、名称、开始日期、结束日期、主办方、举办城市、事件类型、参与人数（可选）。有这七列，才能做时间序列、地区分布、类型结构三张表。当前 `dwd_event` 只有前五列中的四列，缺城市与类型，也没有参与人数。
