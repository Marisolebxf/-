## 摘要

本件把「图谱 API 能不能做」拆成供给面与契约面。供给面统计 7 个节点域、9 类关系：节点域合计 3,570,548 行，其中论文 100,900、专利 2,939,895、企业 189,116、申请人 169,226、发明人 69,647、学者 21,316、政策 20,000。关系面 4 类可用、5 类缺失，可供给率 44.4444%。

契约面给出 10 个端点：4 个 available、4 个 partial、2 个 unavailable。完全可用的只有论文节点、企业节点、机构共著邻居、投资/股东邻居；路径、社群、中心性、专利节点只能部分实现；政策图与跨域路径直接 404。

最关键的结构性问题是「没有统一 node_id」：五套 id 空间互不相通，`graph_node` 又缺表，所以跨域最短路不可建。本件不提供「全图 API」，只提供「同域内图 API + 四域节点查询」。

### 1.2 口径定义

正本要求「图谱 API 的节点、边、查询端点、返回结构」。本批把它拆成两层：**供给面**（有哪些节点域、哪些关系、各多少行）与**契约面**（有哪些端点、返回什么、哪些不可用）。供给面是数据事实，契约面是接口设计；两者必须对得上，不能「端点写了但底下没有边」。

供给面的节点域只算 7 个：论文、专利、企业、申请人、发明人、学者、政策。高校/院所各 20,000 行是样例表，不算「可用节点域」；产业链 12 链 / 41 环节 / 1,273 叶算分类域，不算企业节点。关系面只算 9 类：投资、归属、产业所属、技术应用、科研合作、人才关系、政策适用、服务提供、合作。

契约面的端点只算 10 个，分三档：available（可直接返回真实数据）、partial（能返回但缺字段/缺域）、unavailable（404）。「部分可用」不算可用，这是本件与「能跑就算过」的口径差别。

### 1.3 计算公式与本批实现式

关系可供给率：

$$\text{Available}=\frac{4}{9}=44.4444\%$$

端点可用率：

$$\text{EndpointAvailable}=\frac{4}{10}=40\%$$

端点部分率与不可用率同为 40% / 20%：

$$\text{Partial}=\frac{4}{10}=40\%,\qquad \text{Unavailable}=\frac{2}{10}=20\%$$

节点域行数合计：

$$N=\sum_{d} n_d=3{,}570{,}548$$

这个合计只用于量级，不是「图节点数」，因为申请人、发明人、学者、政策与论文/专利/企业有重叠（一个申请人可能是企业，一个发明人可能也是学者）。正文不拿它当去重节点数。

论文图 P2 占比沿用 021 的口径：节点 15,223 / 20,436 = 74.4911%，边 36,965 / 38,208 = 96.7468%。这两个数在本件只用于「共著端点返回的是 P2 还是 P0」的说明，不重复计算。

## 二、计算过程

### 2.1 节点域盘点

7 个节点域的行数：论文 100,900、专利 2,939,895、企业 189,116、申请人 169,226、发明人 69,647（去重姓名 31,188，覆盖 20,000 件专利）、学者 21,316（姓名 18,763，关系 1,065,385，覆盖 20,015 人）、政策 20,000（城市标签 10,294）。

这 7 个域不是同一层级：论文/专利/企业是「实体」，申请人/发明人/学者是「主体」，政策是「文本」。API 返回时不能把它们都叫「节点」而不标类型；`/graph/node/{type}/{id}` 必须带 type，否则 id 会撞。

高校/院所各 20,000 行是样例表，本件不列为节点域；产业链 12 / 41 / 1,273 是分类域，单独走 `/graph/industry/{code}`，不混进实体节点。

### 2.2 关系盘点

9 类关系的可用性：

| 关系 | 状态 | 边数 | 来源 |
|---|---|---:|---|
| 投资 | available | 9,312 | `dwd_org_invest_info` |
| 归属 | available | 17,082 | `dwd_org_shareholder_info` |
| 产业所属 | available | 35,046 | `dwd_org_industry_tags` |
| 技术应用 | proxy | 523,352 | `dwd_patent` × IPC |
| 科研合作 | absent | 14 | `dwd_patent_assignees` 共同申请人 |
| 人才关系 | absent | 0 | 发明人表无 org_id |
| 政策适用 | absent | 0 | 政策表无企业外键 |
| 服务提供 | absent | 0 | 无 svc 表 |
| 合作 | absent | 0 | 无 coop 表 |

「科研合作」只有 14 条，虽然状态是 absent，但边数不是 0；这 14 条是「两个申请人同时落在底册」的共同申请人边。14 条不足以支撑端点，所以标 absent，不标 available。正文写「14 条」，不写「0 条」，避免把「极少」写成「没有」。

技术应用 523,352 条是代理边：申请人名对齐底册，同一申请人多 IPC 各计一条；名称重名 34 处不拆分。它可供给，但不是「真实技术关系」，所以标 proxy 而不是 available。

### 2.3 节点域与关系的对账

节点域行数与关系边数不能直接相加：论文 100,900 篇产生 38,208 条共著边，专利 2,939,895 件只产生 523,352 条技术应用边（因为只有部分专利有 IPC 且申请人能对齐），企业 189,116 家只产生投资/股东两类边。边/节点比在不同域差两个量级，正文不做一个「全图平均度」。

对账的关键是「边数必须能从源表复算」：共著 38,208 与 021 一致、投资 9,312 与 115 一致、股东 17,082 与 115 一致、产业 35,046 与 005 一致。四个数对不上，API 就不能发布；本件把这四个数写进 `edges`，作为跨件对账锚点。

### 2.4 端点设计与可用性判定

10 个端点分三档：

| 端点 | 状态 | 依据 |
|---|---|---|
| `/graph/node/paper/{id}` | available | 论文面板 100,900 |
| `/graph/node/firm/{org_id}` | available | 底册 + 资本边 + 产业标签 |
| `/graph/node/patent/{id}` | partial | 专利全量，但发明人仅 2 万件 |
| `/graph/neighbors/coauthor/{inst}` | available | 共著图 P2 |
| `/graph/neighbors/invest/{org_id}` | available | 资本边 |
| `/graph/path` | partial | 仅同域最短路 |
| `/graph/community/{domain}` | partial | 仅论文图 Louvain |
| `/graph/centrality/{domain}` | partial | 论文图四类，企业图仅度/中介 |
| `/graph/policy/{id}` | unavailable | 政策图 0 表 |
| `/graph/cross-domain/path` | unavailable | 无统一 node_id |

判定规则：返回的字段必须全部有源表，缺一个就降档。专利节点因为发明人只覆盖 2 万件，降为 partial；路径因为跨域不可建，降为 partial；政策图因为表不存在，直接 unavailable。

### 2.5 id 空间与跨域问题

五套 id：论文 `dwd_zh_paper.id`、企业 `dwd_org_base_info.org_id`、专利 `dwd_patent.patent_id`、政策 `dwd_policy_base.id`、产业 `industry_code`。五套之间没有映射表；`graph_node` 本来可以做统一节点表，但 gkx 没有。

没有统一 id，跨域路径就只能靠「名称精确匹配」临时拼，例如「申请人名 = 企业名」。这种拼法在 169,226 个申请人里只能对齐一部分，且重名 34 处不拆；用它做跨域最短路，会把「同名」当「同一主体」。本件因此拒拟跨域路径，只做同域。

如果甲方要跨域，必须先建 `graph_node`（统一 node_id + 类型 + 源表主键），再做边表。没有这一步，任何「跨域图谱」都是名称匹配的别名。

### 2.6 分页、限流与返回契约

`api_contract` 写死四条：第一，node/edge 端点一律 `limit≤1000`、`cursor=主键`，禁止全图导出；第二，单客户端 ≤5 req/s，全表扫类查询不开放；第三，返回必须带 `source` 与 `as_of`，让调用方知道数据来自哪张表、哪个时点；第四，`cross_domain_id=null`，明确告诉调用方「没有统一 id」。

这四条不是性能优化，是口径约束：不限流，调用方会把 API 当全表扫；不带 source，返回值无法追溯；不写 cross_domain_id=null，调用方会以为可以跨域拼。

### 2.8 CORS、缓存与版本

如果 API 要给前端页面直接调用，还要补三件事。第一，CORS：只允许白名单域名，不允许 `*`，因为图数据含企业关系，开放给任意站点会被爬。第二，缓存：节点类端点按 `id + as_of` 缓存，邻居类按 `org_id + depth` 缓存；缓存键必须带 `as_of`，否则快照更新后仍返回旧图。第三，版本：路径带 `/v1/`，破坏性变更升 `/v2/`，不允许在同一路径下改返回结构。

这三件事不在数据口径里，但属于「API 能不能上线」的一部分。本件只写契约，不实现服务；实现方按这三条做，才不会出现「前端拿到旧图」或「跨站被爬」。

## 五、结果与解读

### 五.1 四域可供给，五域不可

投资、归属、产业所属、技术应用四类有真实边；科研合作只有 14 条、人才/政策/服务/合作全 0。API 的「关系清单」必须按这个事实写，不能把 9 类都列成 available。

### 五.2 端点分档的必要性

10 个端点里 4 个 partial、2 个 unavailable；如果不分档，调用方会以为「有路径就是能查」。分档后，前端可以在 partial 端点上加提示，在 unavailable 端点上直接隐藏。

### 五.3 统一 id 是最大瓶颈

五套 id 空间 + `graph_node` 缺表，导致跨域路径不可建。这不是「再写一个 join」能解决的：名称匹配只能对齐一部分，且会把同名当同一主体。要做跨域，必须先建统一节点表。

### 五.4 与 115/021 的对账结果

共著 38,208、投资 9,312、股东 17,082、产业 35,046 四个锚点全部一致。对账通过不代表「图完整」，只代表「这四域的边数没有漂移」。

### 五.5 发布建议

先发四域节点 API + 共著/投资邻居 API；路径、社群、中心性标 partial；政策图与跨域路径 404。不要在文档里写「全图 API」，也不要给「跨域最短路」的示例。

### 五.6 后续补数优先级

第一优先是 `graph_node`（统一 id），它决定跨域能不能做；第二优先是合作边与服务边；第三优先是政策实体抽取；第四优先是发明人全量。没有第一项，后面三项都只能做同域。

### 五.7 为什么不做「全图导出」

全图导出看起来很方便，但会把「四域可供给」的边界抹掉：调用方拿到一个 JSON，会以为里面包含政策、人才、合作边，实际没有。本件在契约里写 `limit≤1000`、`cursor`，不是性能限制，是口径限制——强制调用方按域、按类型查询，避免把「部分图」当「全图」。

如果甲方确实要离线分析，可以给「按域导出」的批处理，不给「全图导出」。两者差别在于：按域导出会标明域与边类型，全图导出不会。

## 六、结论与发布建议

### 六.1 可用结论

1. 7 个节点域合计 3,570,548 行；9 类关系 4 类可用（44.4444%）。
2. 10 个端点 4 个 available、4 个 partial、2 个 unavailable。
3. 共著 38,208、投资 9,312、股东 17,082、产业 35,046 四锚点与相邻件一致。
4. 跨域路径不可建，原因是五套 id 空间 + `graph_node` 缺表。

### 六.2 不可用结论

1. 不能叫「全图 API」：只有四域可供给。
2. 不能提供跨域最短路：无统一 node_id。
3. 不能提供政策图端点：`policy_graph_node/edge` 在 gkx 不存在。
4. 不能把技术应用 523,352 条叫「真实技术关系」：它是申请人名 × IPC 的代理边。

### 六.3 发布口径建议

端点文档必须带三列：状态（available/partial/unavailable）、依据表、返回字段。partial 端点要写明缺什么（如「发明人仅 2 万件」）；unavailable 端点要写 404 原因，不要留空。

### 六.4 后续补数优先级

统一节点表 > 合作/服务边 > 政策实体 > 发明人全量。统一节点表是前置条件，没有它，其它三项只能在各自域内用。
