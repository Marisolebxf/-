## 摘要

「专利（链维/区域维）」是区域页的专利卡片，要求同时按链和按区域给出专利件数。它与 `M_CHAIN_PATENT_COUNT` 名字相近，实际是两个不同的东西：后者按「企业挂链即整件计入」的多链计位口径算，前者按「一个申请人只归一条链、每件专利只计一次」的单角色口径算。两个数不能互相校验，这是本报告首先要切割清楚的事。

实测专利主表 **2,939,895 件**，窗口 2021—2024。官方口径要求用 `enterprise_patent_org_rel`（机构—专利关系）与 `enterprise_industry_chain`（机构—链关系）两表按 `org_id` 连接，但这两张表在 gkx **都不存在**（`information_schema` 零命中，证据见 `TABLE_ABSENCE_EVIDENCE.md` 的 `enterprise_industry_chain` 节）。因此官方全键路径不可执行。

本报告按 §3.33 的重建纪律，改用名称桥：专利第一申请人名 → 企业底册名 → 链标签，得到 **12/12 链全部非零**、合计 **1,127,340 件**、深圳 **682,209 件**（占 60.515%）、有专利的申请人 **29,631 个**、人均 38.05 件。逐链区间 **7,530—368,298 件**，人工智能 368,298 居首，智能终端 250,192、软件与信息服务 169,564 次之；生物医药 7,530 最少。

三个缺口决定了「部分支持」：

第一，**关系键缺失**。官方要 `org_id`，库内只有名称字符串；名称桥能跑，但同名合并、更名漏计无法在库内解决。

第二，**单链归属偏保守**。一个申请人名称只映射到一条链，跨链企业只计入首链。这会让链间分布偏保守——真实情况可能是「一家企业同时属于三条链，专利应在三条链各体现一部分」。

第三，**城市归属是代理**。专利表没有申请人地址，城市只能取企业底册的注册城市。集团母公司在深圳、子公司在东莞时，专利会被全部算到深圳，区域分布因此偏集中。

结论：数据量足够、12 链全非零、可复现，但关系键与归属规则都是代理 → **部分支持**。数值可作链间与区域间的相对参考，不能作「按 `org_id` 精确归属」的验收值。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的功能模块是：**产业链分析 → 区域分析 → 创新产出 → 专利（链维/区域维）**。展示形态是区域页的专利卡片（本区域 N 件），加一张 12 链×区域的矩阵，每格是该链在该区域的专利件数。

它与「企业数（区域维）」「研发投入（区域维）」构成区域创新三件套。三件的区域轴必须同源：企业数用注册城市、专利用申请人城市、研发投入用企业填报城市。本报告的城市全部取企业底册 `city`，正是为了让三件套能对齐。

### 1.2 为什么需要这个指标

第一个用途是**区域创新分工**。深圳 682,209 件占 60.515%，意味着这条口径下深圳是大湾区创新的绝对主体；广州、东莞、惠州三市合计约 26%，省外可忽略。这个结构决定了招商与政策资源的投放重点。

第二个用途是**链×区域矩阵的交叉分析**。人工智能 368,298 件里深圳占 176,751（48.0%），智能终端 250,192 件里深圳占 186,609（74.6%）。同样是头部链，深圳在智能终端的控制力远高于人工智能——这类结构性差异只有矩阵能给。

第三个用途是**与专利总数交叉校验**。区域页说「深圳 68.22 万件」，链页说「深圳 187.70 万件」（`M_CHAIN_PATENT_COUNT`），两个数差 2.75 倍。若不做口径切割，用户会认为其中一个错了。本报告的任务之一就是把「为什么两个数不同」写清楚。

### 1.3 需求文档是否给出定义方法

**需求文档只给「专利（链维/区域维）」这个标题，未给口径；calc-logic 未收录。** 可从旧稿复原的实现是：

> 以 `enterprise_patent_org_rel` 按 `org_id` 连接专利与机构，再以 `enterprise_industry_chain` 按 `org_id` 连接机构与链，按链、按城市汇总专利件数。
> 口径：`COUNT(DISTINCT patent_id) GROUP BY chain, city`。

这条口径要求两张关系表存在且 `org_id` 可用。实测两张表都不存在，`org_id` 全键路径不可执行。因此必须重建。

### 1.4 类似指标权威机构构建方法可行性分析概要

「按产业×区域数专利」在权威实践里通常以「申请人代码 + 行政区划码」为双键。本节逐族说明，完整谱系见附录 C。

**A 族是正确方向，但库内没有代码。** 专利表只有申请人名称字符串，没有 `org_id`，也没有统一社会信用代码。若能从专利局拿到代码化数据，A 族应整体替代 B 族。

**B 族是当前唯一可执行路径。** 它把「机构—专利关系」退化为「名称等值」，把「机构—链关系」退化为「名称→标签表」。能跑，但精度受名称质量约束。

**C 族最准，但库内没有地址列。** 专利申请人地址能直接归到区县，不受企业注册地影响；`dwd_patent` 没有这一列，无法使用。

**D 族是本件的区域口径。** 用企业注册城市代理申请人所在地，优点是与企业数、研发投入同源；缺点是集团跨市时专利全算总部，区域分布偏集中。

**E 族需要邮编或行政区划码，库内都没有。** 统计用区划代码能精确到区县，但专利表不存这个码。

### 1.6 本报告的口径与边界（推测定义，须与甲方会签）

**推测原意**：按链与区域两个维度看专利分布，支撑区域创新分工分析与招商资源配置。

**推测定义**（非甲方闭合口径）：

设链 $c$ 的申请人名称集合 $A_c$（名称 → 链标签，单链归属），申请人 $a$ 的专利集合 $P_a$（第一申请人名精确桥接，$2021\le y\le 2024$），城市函数 $city(a)$：

$$N_{c}=\sum_{a\in A_c}|P_a|,\qquad N^{SZ}_{c}=\sum_{a\in A_c,\ city(a)=\text{深圳}}|P_a|$$

$$N_{total}=\sum_{c=1}^{12}N_c=1{,}127{,}340,\qquad N^{SZ}=682{,}209$$

约束：① 只认第一申请人；② 每个申请人名只归一条链（单链归属）；③ 每件专利只计一次，不跨链重复；④ 城市取企业底册注册城市；⑤ 申请年窗口 $[2021,2024]$。值域 $N_c\in[7530,368298]$。

## 二、计算过程

### 2.1 方法选择：为什么用名称桥、为什么单链归属

官方口径是双键连接：`patent --org_id--> org_rel --> chain`。两个箭头都要求 `org_id`，而 gkx 专利表没有这一列，两张关系表也不存在。可选的替代只有两条：名称桥，或者放弃。

名称桥的做法是把「机构—专利」退化为「第一申请人名 = 企业名」，把「机构—链」退化为「企业名 → 链标签」。它保留了口径的语义（专利归到企业、企业归到链），只把连接键从代码换成名称。这符合 §3.33 的重建纪律：卡在缺失的汇总层时，用原始表重建，而不是判死。

单链归属是第二个选择。一家企业可能挂多条链，官方口径按关系表可以一对多；名称桥只能一对多里选一条，本报告选「首链」。这会让跨链企业的专利只体现在一条链上，链间分布偏保守——某些链的专利数可能被低估，另一些被高估。这个偏差方向不确定，但可以确定它存在，所以写入 `gaps`。

### 2.2 名称桥、单链归属与城市归属规则

名称桥分两段：

1. **专利 → 企业**：`dwd_patent.first_applicant_name` 与 `dwd_org_base_info.name_cn` 精确等值。命中后，专利获得企业的 `city`。
2. **企业 → 链**：企业名在 `dwd_org_industry_tags` 中查链标签，取第一个匹配的链作为归属。

城市归属只有一条规则：取企业底册的 `city`。专利表没有地址，也没有邮编，只能代理。

三个公式：

$$N_c=\sum_{a\in A_c}|P_a|$$

$$\text{sz\_share}=\frac{\sum_c N^{SZ}_c}{\sum_c N_c}=\frac{682{,}209}{1{,}127{,}340}=0.60515$$

$$\text{per\_firm}=\frac{N_{total}}{|A|}=\frac{1{,}127{,}340}{29{,}631}=38.05$$

第三条是人均专利，分母是「有专利的申请人」而非「全部链成员」。这两个分母经常被混用：若用链成员 246 万做分母，人均只有 0.46 件，看起来像「几乎不创新」；用 2.96 万做分母是 38.05 件，看起来像「创新密集」。两个数都对，但回答的问题不同，页面必须标明分母。

### 2.3 关系表缺席的证据链

`enterprise_patent_org_rel` 与 `enterprise_industry_chain` 在 gkx 不存在，证据有三层：

1. `information_schema.TABLES` 精确同名检索：**0 行**。
2. `TABLE_ABSENCE_EVIDENCE.md` 的 `enterprise_industry_chain` 节把该表列为「精确同名不存在」，涉及 35 件指标（含本件）。
3. 专利表自身列清单里没有 `org_id`，即使关系表存在也无法连接。

三层证据的含义是：官方全键路径不是「慢」或「难」，而是「没有键」。这不是数据缺口，是结构缺口；补数据解决不了，必须补表或补代码。

按 §3.33，卡在缺失的汇总/关系层时应按原始表重建，不得直接判「完全不支持」。本报告的重建路径是：名称桥替代 `org_id` 桥，链标签替代 `enterprise_industry_chain`。重建后 12/12 链非零，说明路径是通的；精度损失写入 `gaps`。

### 2.4 计算步骤（脚本逐步实现）

1. 读专利面板快照（2,939,895 件，`apdt_year` ∈ [2021,2024]）。
2. 第一申请人名 → 链：在链标签表的 `names` 中扫描，命中即归该链；未命中不计。
3. 企业名 → 城市：在底册 `name_cn` 中查 `city`；未命中记「未知」，不计入深圳列。
4. 按链汇总专利件数、深圳件数、申请人去重数。
5. 校验：$\sum_c N_c=1{,}127{,}340$、$\sum_c N^{SZ}_c=682{,}209$、$\sum_c firms=29{,}631$，并标注名称桥偏差。

第 5 步的三条校验分别防「逐链漏算」「深圳列错位」「申请人重复计数」。三条同时成立，说明链维与区域维是同一批行算出来的。

## 四、数据缺失情况

### 4.1 缺口清单与后果归因

本件的缺口集中在「关系键」与「归属规则」，不在数据量。

| 缺口 | 影响面 | 方向与量级 | 处置 |
|---|---|---|---|
| `enterprise_patent_org_rel` 缺 | 无 `org_id` 桥 | 名称桥替代，精度下降 | 待甲方供表或代码化数据 |
| `enterprise_industry_chain` 缺 | 无机构—链关系 | 标签表替代，单链归属 | 同上 |
| 名称桥同名合并 | 不同主体同名 | 偏高；中小企业常见 | 地址/代码消歧 |
| 名称桥更名漏计 | 旧专利挂旧名 | 偏低；老企业影响大 | 建更名表 |
| 单链归属 | 跨链企业只计首链 | 链间分布偏保守 | 允许多链分摊 |
| 城市取注册地 | 集团跨市 | 区域分布偏集中 | 用专利地址（当前无） |
| 2025/2026 截断 | 无近年值 | 不定义，非偏低 | 另建观察序列 |

**两张关系表缺失 → 官方路径不可执行，只能代理。** 方向是精度下降，量级不可估。处置：按 §3.33 重建（已完成），并列为待甲方供表项。

**同名合并 → 偏高。** 两家不同主体同名时，专利被合并到同一链、同一城市。方向偏高，量级在中小科技公司常见。

**更名漏计 → 偏低。** 企业改名后旧专利桥不上，整段历史丢失。方向偏低，量级随企业年龄增长。

**单链归属 → 链间分布偏保守。** 一家企业挂三条链，专利只算首链，另外两条链少算。方向不确定（取决于首链选择），量级不可估。

**城市取注册地 → 区域分布偏集中。** 集团母公司在深圳、子公司在东莞时，专利全算深圳。方向是深圳占比偏高，量级可从「深圳 60.515% vs 四市 99.9%」的结构看出——省外几乎为零，说明区域轴实际上只有四个城市在起作用。

**2025/2026 截断 → 不是偏低，是不定义。** 与 `M_CHAIN_PATENT_COUNT` 同一处理，正式值只用 2021—2024。

**能否交叉验证：只能验证内部一致性。** 路径一：链级之和 = 1,127,340、深圳之和 = 682,209、企业之和 = 29,631，三条等式成立说明三个维度同源；路径二：与 `M_CHAIN_PATENT_COUNT` 对照只能确认「同向」，**不能互校**——一个单角色计件、一个双角色计位，量级差 2.68 倍是口径差而非错误。

### 4.2 可构建但存在缺口（不是「无法构建」）

1. **补 `org_id`**。从专利局获取代码化数据，把名称桥升级为代码桥。
2. **补关系表**。`enterprise_patent_org_rel` 与 `enterprise_industry_chain` 待甲方供表，或由代码化数据重建。
3. **补专利地址**。有了申请人地址，区域归属不再依赖企业注册地。
4. **允许多链归属**。把「首链」改为「按权重分摊」或「多链各计」，需甲方定口径。
5. **建更名表**。至少覆盖链内头部企业的曾用名。

### 4.3 数据陷阱（本批实测，须写入任何下游复用说明）

- **1,127,340 与 3,026,291 不是同一个数**：本件单角色、每件一次；`M_CHAIN_PATENT_COUNT` 双角色、多链计位。不可互校。
- **深圳 68.22 万 ≠ 链页深圳 187.70 万**：差 2.75 倍，是口径差，不是错。
- **官方路径全 0 不是「没有专利」**：是关系表不存在，键接不上。
- **人均 38.05 的分母是「有专利企业」**：用链成员做分母会得到 0.46，两个数答的是不同问题。
- **区域轴实际只有四市**：省外占比极低，本指标不是全国指标。

## 五、王惠方法对照与选用建议

### 5.1 原方法还原

calc-logic 未收录本指标独立文件，旧稿留下的口径是：

- 口径定义：「以 `enterprise_patent_org_rel` 按 `org_id` 连接专利与机构，再以 `enterprise_industry_chain` 按 `org_id` 连接机构与链，按链、按城市汇总专利件数。」
- 公式：`COUNT(DISTINCT patent_id) GROUP BY chain, city`。
- 源库表：`dwd_patent` + 两张关系表 + 企业底册。
- 依赖：`org_id` 全键路径。

实测两张关系表都不存在，`org_id` 列也不存在，官方路径不可执行。旧稿的 `official_cells_nonzero=0` 正是这一事实的体现。

### 5.2 新方法概述

新方法用名称桥替代 `org_id` 桥：第一申请人名 → 企业底册 → 链标签，城市取企业注册地。语义仍是「按链、按区域数专利」，但连接键从代码换成名称，归属从「关系表一对多」退化为「标签表单链」。

### 5.3 逐维对照表

| 维度 | 旧口径（`org_id` 双键） | 新口径（名称桥） | 数据支撑差异 | 可复现性差异 |
|---|---|---|---|---|
| 连接键 | `org_id` | 名称精确等值 | 库内无 `org_id` | 旧不可执行，新可跑 |
| 链归属 | 关系表一对多 | 标签表单链 | 新口径偏保守 | 新口径需声明 |
| 城市归属 | 机构地址 | 企业注册地 | 新口径偏集中 | 新口径需声明 |
| 去重 | `patent_id` | `patent_id` | 一致 | 一致 |
| 截断 | ≤统计年 | ≤2024 | 一致 | 一致 |
| 判档 | 部分支持 | 部分支持 | 一致 | 一致 |

### 5.4 选用建议与理由

**建议采用新口径出参考值，同时把「补 `org_id`」列为升级项**，理由：

1. 旧口径当前**不可执行**——两张关系表不存在、`org_id` 不存在，不是「慢」而是「没有键」。
2. 新口径 12/12 链非零、三条校验等式成立，说明重建路径自洽，可作为过渡方案。
3. 但新口径的链归属与城市归属都是代理，精度上限受名称质量约束；一旦 `org_id` 可得，应立刻切回官方路径。
4. 切换时指标名不变，但数值会变（单链 → 多链、注册地 → 专利地址），必须提前告知业务方，避免「同一指标两个数」的争议。

**待甲方裁决点**：① 是否接受「单链归属」（若不接受，需定多链分摊规则）；② 区域轴是否只保留四市（省外占比极低）；③ `org_id` 与专利地址能否由专利局侧提供。

## 附录 C　专利链维/区域维可行性报告（完整版）

### C.1 报告目的与范围

回答三个问题：① 按链×区域数专利在权威口径中如何建键；② 本库缺键时能否重建；③ 重建值的精度边界在哪。范围限定专利表、企业底册、链标签三表，不涉及外部专利数据库。
