> **数据源口径**：本件支持度按「开发库 + 三方库（gkx，183.240.141.251:3318 只读）」评估，仅排除 `demo_*`；本机开发库事实面为空壳（`gkxlumenx_dwd/ods/ads` 逐表实测非空 0 张），实际取数面为 gkx。

因此，本件交付的是“父子归属边”这一可验证子集，并在正文与产物中把它与“全部关系边”严格区分。把 1,261 说成“产业链边数”会在甲方按注册表复核时露馅，这是本件拒绝升档的原因。

## 摘要

本件回答“12 条产业链的图谱里到底有多少条边”。以 `gkx.dwd_industry_chain_info` 全量 1,273 行为母体，按 `industry_code` 的层级编码与 `industry_link_code` 父指针还原树结构，得到 12 个链根、319 个容器节点、954 个叶子节点和 **1,261 条父子边**；每条边都满足“子码前缀等于父码”“子深度等于父深度加一”，无自环、无孤儿、无多父。该结果可由快照逐行复算，误差为 0。

但这个 1,261 只覆盖“父子归属”一种关系。注册表要求的四类关系边中，`belongs_to` 与 `participates` 指向 NebulaGraph 图空间，`supplies` 与 `depends_on` 连目标表都没有；演示库 ADS 侧另有一个 832 行的 `chain_panorama_edges`，与本表 1,261 不一致且不可复算。故本件判部分支持：可交付“父子边 1,261 条”，不可交付“产业链全部关系边”。正文同时解释三个常见错数——331（根节点空父码被算成边）、954（叶子数被当边数）、832（演示库口径）——各自是怎么来的。

## 一、需求定义概述

### 1.1 指标基本信息

| 项 | 内容 |

| 计量单位 | 条 |

| 关联问题 | Q-CHAIN-02（全景图关系边数） |

同一 ID 在两份权威材料里名称不同：`calc-logic/CHAIN/M_CHAIN_EDGE_COUNT.md` 叫“链位关系数”，注册表叫“产业链边数”。名称差异不是文字游戏——前者指向 ADS 的 `chain_panorama.edge_count`，后者指向 NebulaGraph 的四类边。本件按“产业链图谱中所有关系边总数”的本意理解，先交付源表能证明的父子边，再逐类说明缺哪几类。

### 1.2 业务问题与原意

产业链全景图要让用户看到“这条链由哪些环节组成、环节之间怎么连”。前端的“关系边数”是一个结构丰富度指标：边越多，说明图谱对链条的刻画越细；边突然变少，说明某个环节被合并或断链。业务侧真正想知道的不是“树有几条枝”，而是“链条上的供应、合作、技术依赖关系有没有被画出来”。

这决定了本指标不能只数父子边。父子边只表达“A 环节属于 B 环节”，不表达“A 给 B 供货”“A 依赖 B 的技术”。如果只交付 1,261，业务看到的是组织架构图的边数，不是产业链的边数。本件在 §二把这两种边分表列示，避免把结构边冒充关系边。

### 1.3 口径拆解

把“边”拆成四个可核对的要素：

| 要素 | 本件取值 | 说明 |
| --- | --- | --- |
| 边的端点 | `industry_code`（子）与 `industry_link_code`（父） | 两端都是环节节点，不是企业 |
| 边的方向 | 子 → 父（向上归属） | 源表只存父指针，方向由编码隐含 |
| 边的类型 | 仅 `parent_child` 一种 | 源表无类型字段 |
| 边的权重 | 无 | 源表无权重、无置信度、无时间戳 |

注册表要求的类型是四类：`belongs_to`、`participates`、`supplies`、`depends_on`。本件只能覆盖其中与“归属”最接近的父子边，且严格说父子边也不等于 `belongs_to`——`belongs_to` 通常指企业属于环节，父子边指环节属于环节。这个细微差别在 §1.4 展开。

### 1.4 与旧稿、同域指标的差异

| 来源 | 口径 | 数值 | 与本件的关系 |
| --- | --- | --- | --- |
| 本件（源表父子边） | 子码 → 父码，逐行还原 | 1,261 | 可复算，作为交付值 |
| 旧稿 calc-logic | ADS `chain_panorama_edges` | 832 | 演示库口径，表不在 gkx，不可复算，不采 |
| 注册表 | NebulaGraph 四类边 | 未给数 | 图空间不可访问，四类边中三类无源 |
| 同域 `M_CHAIN_DEEP_117_1` | 节点/边/挂接 | 1,261 | 与本件一致，可交叉验证 |
| 同域 `M_CHAIN_KEY_NODE_COUNT` | 关键环节 | 另一口径 | 数节点，不数边，不可混用 |

与 `M_CHAIN_DEEP_117_1` 的一致性是本件最强的交叉证据：两件独立按“子码减根节点”复算，均得 1,261。差异只在该件把边作为节点表的副产物，本件把边作为主对象并补了完整性校验。

### 1.5 对象、单位与分母

本指标是计数指标，不存在除法，因此没有分母。需要特别声明的是“边数不是家次”：边的两端是环节，不是企业；`dwd_org_industry_tags` 里一家企业可挂多个环节，那是“挂接家次”，与边数不同母体，不能拿来当分母，也不能拿来当边数。§3.54 的同母体约束在本件表现为“不做任何比率”，而不是“比率选错分母”。

### 1.6 本件结论先行

1. 可交付：父子归属边 **1,261 条**，12 条链分列见 §2.6。
2. 不可交付：四类关系边总数；源表无边类型字段，图空间不可访问。

## 二、计算过程

### 2.1 数据准备与快照

本件不重扫库，直接读两份已落盘快照：

| 快照 | 内容 | 行数/规模 | 用途 |
| --- | --- | --- | --- |
| `code/_snapshots21/chain_tree_links_20261022.json` | `dwd_industry_chain_info` 窄投影：`industry_code`、`industry_name`、`industry_link_code`、`parent_code` | 1,273 行 | 还原树、数边 |
| `code/_snapshots21/probe_chain_meta_20261022.json` | 当日列结构、行数、`created_time` 批次日戳 | 16 列 / 1,273 行 | 证明无 `chain_stage`、无 `edge_type`、无时间分区 |

选择快照而不是重扫的理由：源表 1,273 行是静态维表，2026-10-22 已全量拉取并落盘；重扫只会增加网络与锁表风险，不会改变结果。快照的 `meta` 记录了库名、host、拉取时间与方法（窄投影 + `SSCursor` 分块 + `max_execution_time=0`），满足 §3.53 的取数要求。

### 2.2 对象与边界

母体是 `dwd_industry_chain_info` 全表 1,273 行，边界处理如下：

| 情形 | 处理 | 影响行数 |
| --- | --- | --- |
| 7 位链根 | 不计边（无父） | 12 |
| 9 位及以上非根节点 | 计 1 条指向 `industry_link_code` 的边 | 1,261 |
| `is_deleted` 标记 | 快照已按有效行拉取，未含删除行 | 0 |
| 重名节点 | 保留，不按名称去重 | 123 个重名节点 |
| 父码为空但非 7 位 | 视为孤儿，单独计数 | 0 |

“重名节点保留”是一个容易踩的坑：全表只有 1,150 个不同名称，却有 1,273 个节点，123 个节点与别的链/别的层级重名（例如多条链都有“原材料”“零部件”）。如果按名称去重，会少算 123 个节点，进而少算边。本件以 `industry_code` 为唯一键，名称只用于展示。

### 2.3 主计算

计算只有三步，全部是确定性的集合运算：

$$
E = \{(p_i, c_i) \mid c_i \in C,\ \mathrm{len}(c_i) > 7,\ p_i = \mathrm{industry\_link\_code}(c_i)\}
$$

$$
|E| = |C| - |R| = 1273 - 12 = 1261
$$

$$
\mathrm{leaf} = \{c \in C \mid c \notin \{p_i\}\},\quad |\mathrm{leaf}| = 954
$$

其中 $C$ 是 1,273 个节点，$R$ 是 12 个 7 位链根，$p_i$ 是节点 $c_i$ 的父码。第二式成立的前提是“每个非根节点恰好一个父、无孤儿、无多父”，这三点在 §2.5 逐项校验，均为 0 异常。

按链分列时，链归属取 `industry_code` 的前 7 位，不取 `industry_link_code[0]`。原因：`industry_link_code` 是父指针，对 9 位 L1 节点它指向 7 位根，对更深节点它指向 9 位或更长的父节点；把它当链码会在深层节点上取到 9 位父码，归错链。§3.55 对此有明确警示。

### 2.4 口径对照：为什么不是 331、954、832

**为什么不是 331。** 有人用 `COUNT(DISTINCT parent_code, industry_link_code)` 得 331，看起来像边数。拆开看：319 个真实父码各算一对，12 个 7 位根节点的 `industry_link_code` 是空串、也各算一对，合计 331。也就是说，331 里有 12 条是“根节点没有父”这一事实被误当成一条边。更隐蔽的问题是 `parent_code` 列存的不是父节点名，而是链名（全表只有 12 个取值），拿它做复合去重既漏掉真实父名，又制造了 12 个哨兵对。本件用 `industry_code` 与 `industry_link_code` 两列，得 1,261。

**为什么不是 954。** 954 是叶子节点数。叶子与边的关系是“叶子数减根数”才等于边数（954 − 12 = 942），而 942 仍不等于 1,261，因为容器节点也各自带一条入边。正确的恒等式是“节点数减根数 = 边数”，不是“叶子数 = 边数”。把 954 当边数会同时漏掉 319 个容器节点的入边、又多算了 12 个根。

**为什么不是 832。** 832 来自旧稿引用的演示库 ADS 表 `chain_panorama_edges`。该表不在 gkx，演示库连接在本目录已被禁用；即便能连，832 与源表 1,261 也相差 429 条，无法解释这 429 条是“另一种边”还是“造数截断”。在没有边类型字段的情况下，任何 832 的复算都只能靠猜，故本件不采。

**为什么不是 1,273。** 1,273 是节点数。把节点数当边数，等于假设每个节点都有一条入边；12 个链根没有父，正好多算 12 条。这个错法与 331 同源：都把“根没有父”当成了“根有一条空边”。

### 2.5 完整性与异常处理

| 校验项 | 期望 | 实测 | 结论 |
| --- | --- | --- | --- |
| `industry_code` 唯一 | 0 重复 | 0 | 通过 |
| 自环（父=子） | 0 | 0 | 通过 |
| 孤儿边（父码不在节点集） | 0 | 0 | 通过 |
| 多父节点 | 0 | 0 | 通过 |
| 子码前缀等于父码 | 1,261 | 1,261 | 通过 |
| 子深度=父深度+1 | 1,261 | 1,261 | 通过 |
| `parent_code` 与父节点名一致 | 1,261 | 41 | 不通过，但属列语义问题 |

最后一行需要解释：`parent_code` 列在 1,220 个非根行上填的是链名（如“机器人”），不是父节点名（如“零部件”）。这不是数据错误，而是列名误导；它不影响边数（边数只用 `industry_code` 与 `industry_link_code`），但会让按 `parent_code` 做自连接的人得到错误结果。本件把它作为“字段语义告警”记录，不作为计算失败。

### 2.8 为什么这么选

选择“父子边可交付、四类边不可交付”的分层写法，而不是直接判“完全不支持”，理由是父子边确实是“产业链边”的一个真子集，且是当前唯一可逐条复算的子集。判“完全不支持”会把已经能交付的 1,261 也一起否定，甲方拿不到任何可用数字；判“完全转换支持”又会把四类边的缺口藏起来。分层交付是唯一既诚实又有用的写法。

选择“按 `industry_code` 前 7 位归链”，而不是“按 `industry_link_code` 归链”，是因为后者在深层节点上指父不指链。这个选择影响所有分链数字：若按父指针归链，深层节点会被归到 9 位父码，12 条链的节点数之和会小于 1,273，且差额随链深变化，无法解释。

选择“不按名称去重”，是因为 123 个重名节点分布在不同的链与层级（“原材料”“零部件”在多条链重复出现），按名称去重会把跨链同名环节合并，直接破坏分链口径。名称只用于展示，唯一键始终是 `industry_code`。

## 四、数据缺失情况

### 4.1 四类关系边整体缺失

注册表要求的 `belongs_to`、`participates`、`supplies`、`depends_on` 四类边，在 gkx 没有任何一张表承载。`SHOW TABLES LIKE '%chain%'` 只返回两张表：`dwd_industry_chain_info`（环节树）与 `dwd_industry_chain_news_info`（资讯，108,052 行）。前者是节点表，后者是资讯表，都不是边表。

### 4.2 图空间不可访问

`calc-logic` 与注册表都指向 NebulaGraph `gkx_chain`。本环境没有图库连接串，也没有图空间导出。按 §3.49，不能把“连不上”写成“图里没有边”；正确表述是“未测”。本件因此不对图空间的边数做任何断言，只声明“未取得”。

### 4.3 演示库 832 不可复算

旧稿的 832 行来自演示库 ADS 表 `chain_panorama_edges`。该表不在 gkx；演示库连接在本目录已禁用。832 与 1,261 的差额 429 既可能是“另一种边”，也可能是造数截断，现有证据无法区分。按“禁引演示库”规则，本件不把 832 作为任何结论的输入。

### 4.4 列语义与列名不一致

`parent_code` / `parent_name` 两列名为“父码/父名”，实际存的是链名。这会让外部复核者写出 `JOIN ... ON child.parent_code = parent.industry_code` 而得到 0 行。本件在 §2.5 记录 1,220 行不一致，并在附录 B 给出反例，提醒后续复用者不要用这两列还原父子关系。

### 4.5 无版本、无时间轴

源表没有 `valid_from` / `valid_to` / `version`，无法回答“上个月有多少条边”“本月新增几条边”。本指标因此只能是截面值，不能做环比、同比、新增边数。若甲方要“新增关系边”，需要先补边表的时间戳，这不是本件能代理的。

### 4.6 边界总结

可交付边界：1,261 条父子边，12 条链分列，逐层分布。
不可交付边界：四类关系边总数、边权重、边的新增/失效、图空间口径。
判档边界：若甲方确认“产业链边数 = 父子归属边”，可升“完全转换支持”；在确认之前维持“部分支持”。

## 五、结论、边界与复现

### 5.1 结论

1. 交付值：**1,261 条父子归属边**；12 条链中集成电路最多（256 条），数字创意最少（36 条）。
2. 结构特征：边集中在深度 3—4（808 条，64.08%），说明链树是三层主轴 + 末梢分叉，不是两层目录。
3. 口径风险：注册表要四类边，源表只有一类；1,261 不能对外称“全部关系边”。

### 5.2 适用与不适用

| 场景 | 是否适用 | 说明 |
| --- | --- | --- |
| 展示链树结构丰富度 | 适用 | 1,261 就是树边数 |
| 比较多链的环节细分程度 | 适用 | 分链边数已给 |
| 回答“产业链关系边总数” | 不适用 | 缺四类关系边 |
| 做供应关系分析 | 不适用 | 无 `supplies` 边 |
| 做月度新增边 | 不适用 | 无时间戳 |

### 5.3 复现步骤

1. 读取 `code/_snapshots21/chain_tree_links_20261022.json` 的 `data` 数组。
2. 取 `len(industry_code) > 7` 的行，边为 `(industry_link_code, industry_code)`。
3. 按 `industry_code[:7]` 分组得 12 条链。
4. 用 `industry_code not in 父码集合` 得叶子，其余为容器。
5. 与 `metrics/repro/out/M_CHAIN_EDGE_COUNT_out.json` 的 `headline`、`per_chain` 逐项比对。

### 5.4 发布建议

对甲方发布时，标题写“产业链父子归属边数”，不要写“产业链边数”；正文第一句就说明“四类关系边未含”。若甲方坚持要“全部关系边”，应把本件降级为“结构边”并另开数据缺口单，要求供应方交付边表（源、目标、类型、权重、生效时间五列），而不是在文档里用 832 或 331 凑数。
