## 摘要

「产业链供应链关系数」数的是企业之间的供应关系边：谁给谁供货、供什么、供多少。它是图谱类指标里唯一能刻画「链」的东西——没有边，图谱只是环节清单。

本件判**完全不支持**，理由不是「表少」，而是**两端连不上**。gkx 的招投标数据（`dwd_bid_base_out` 39,962 行、`dwd_bid_win_candidate_out` 39,520 行）能给出「中标方」，且中标方带 `external_id`（39,403 行非空，99.70%）；采购方侧也有独立表 `dwd_bid_purchase_agency_out`（39,975 行，`credit_no` 非空 39,628 行）。**两端各自的键都齐**，缺的是连接：按 `project_number` 连接，公告侧 32,029 个不同项目号只有 106 个命中（0.331%）。

其余候选面全部为空：以 `%supply%`、`%relation%`、`%chain%rel%`、`%chain%node%` 为模式扫描 `information_schema.tables`，返回 0 张表。也就是说，库内既没有供应关系表，也没有可替代的企业—企业关系表。

结论：本指标必须靠**外部采购或甲方报送**（供应链上下游清单、核心配套企业名录、采购合同台账）才能构建；在此之前，任何数字都是编的。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**产业链分析 → 产业链图谱 → 供应链视图**。产品任务是在图谱上画出企业之间的供货关系：点开一家链主企业，能看到它的上游供应商与下游客户，以及每条边的品类与金额。

配套的还有「链主企业上下游面板」：以链主为中心，向外展开 1—2 层供应关系，用边的粗细表示采购金额。这个面板是本项目里唯一需要「边」的交互，其余图谱页面都只需要「点」。

### 1.2 为什么需要这个指标

第一，它是「链」这个字的物理含义。产业链之所以叫链，是因为企业之间存在投入产出关系；没有关系边，所谓产业链只是「同一行业的企业集合」，与产业集群没有区别。

第二，它是风险传导的唯一载体。某家供应商停产，影响哪些链主？答案只能沿供应边找。用企业数、专利数、营收都推不出来。

第三，它是补链招商的精确依据。知道「某链主的某类零部件全部外购」，才能定向招引该零部件企业；不知道边，就只能按环节猜。

### 1.3 需求文档是否给出定义方法

**没有。** 三份说明书里出现过「供应链」「上下游」的字样，但没有给出这个指标的计算公式，也没有说明数据来源。父口径仅登记了指标名与一句「统计产业链企业间的供应关系数量」。

这句「供应关系」至少留下四个未定项：① 关系粒度（企业—企业、企业—环节、环节—环节）；② 方向（是否区分上游/下游）；③ 是否要求金额或品类；④ 是否只算链内企业之间的边。四项都未定，而任何一项都会改变所需数据的形态。

### 1.4 类似指标权威机构构建方法可行性分析概要

| 方法族 | 代表机构/文献 | 口径要点 | 与本指标的差 | 贴合度 |
|---|---|---|---|---|
| A 企业间交易网络 | 各国增值税发票/税票数据（如巴西 NF-e、中国金税） | 以发票为边，采购方—供应方精确 | 需税务授权，库内无 | 高（口径）/零（可得） |
| B 投入产出表 | 国家统计局 IO 表、OECD ICIO | 部门间流量矩阵 | 部门级而非企业级，且无 IO 表 | 中 |
| C 招投标采购 | 公共资源交易平台 | 项目—中标方边 | 两端键齐、项目号连接覆盖 0.331% | 中（仅千分之四可闭合） |
| D 供应链金融/核心企业名录 | 银行供应链金融平台 | 核心企业—配套企业名单 | 需金融机构合作 | 高（形态）/零（可得） |
| E 商业供应链库 | 企查查/天眼查供应关系 | 招投标+年报客户/供应商 | 采购、编码不同源、不可核验 | 中（可采购） |

**三句结论**：① 语义最贴 A 族（税票），它是唯一能覆盖全部企业的边源；② 库内最接近的是 C 族，但只有半条边；③ 因此本件只能落到「外部采购/报送」，符合 B 类定义。

### 1.6 本报告的口径与边界（推测定义，须与甲方会签）

推测定义：**供应链关系数 = 链内企业之间可识别的「采购方 → 供应方」有向边数（按采购方+供应方+品类去重）**。

边界：① 不把「同一环节的企业」算作有关系；② 不把招投标的「项目—中标方」算作边（缺可连接的项目级采购方键）；③ 不用行业上下游顺序推断企业关系（那是环节级，不是企业级）；④ 不做 2 度以上推断（共同供应商不等于直接供应）。

## 二、依赖性质裁定（为什么必须外部数据）

### 2.1 本指标需要什么形态的数据

一条供应关系边至少要五个字段：采购方标识、供应方标识、品类、时间、金额。其中前两个是**硬键**——没有它们，边无法成立；后三个是属性，缺失只会让边变粗，不会让边消失。

gkx 的企业主档用 `external_id`（信用代码）作企业标识，因此理论上只要两张表各带这个键，边就能建。问题在于：供应方（中标企业）有键，采购方没有。

### 2.2 gkx 里到底有什么（逐表探测）

以 `information_schema.tables` 扫描四类模式，结果如下：

| 探测模式 | 命中表 | 说明 |
|---|---|---|
| `%supply%` | 0 | 无供应关系表 |
| `%relation%` | 0 | 无通用关系表 |
| `%chain%rel%` | 0 | 无链级关系表 |
| `%chain%node%` | 0 | 无节点关系表 |
| `%bid%` | 9 张（含 4 张备份） | 招投标，见 §2.3 |
| `%talent%` / `%scholar%` | 人才主表存在 | 但无「人才—链」关系表 |

这张表是本件全部结论的基础：**库内不存在任何企业—企业关系表**。不是「数据少」，是「表不存在」。

### 2.3 最近的替代面（招投标）为什么不可用

`dwd_bid_base_out`（39,962 行，32,029 个不同项目号）有项目号、公告标题、地区、行业类型、预算金额；`dwd_bid_win_candidate_out`（39,520 行）有项目号、中标方名称、`external_id`、金额、排名。

两者用 `project_number` 可关联，于是能得到「项目 → 中标方」边。但采购方在哪？

- `dwd_bid_base_out` 没有采购方字段。样本行的标题是「永青集团有限公司-供应二部O型圈及导向带」「月亮湾燃机电厂闭路电视监控设备维修保养邀请函」——采购方名字混在标题里。
- `construction_service_location` 是服务地点，不是采购方。
- `dwd_bid_purchase_agency_out`（39,975 行）**不是只有代理机构**：`relate_type=2` 的 15,162 行里有「广州市政府采购中心」这类采购/集采主体，且 39,628 行带 `credit_no`。所以「采购方不可识别」这个说法要修正为「采购方可识别、但连不上」——按 `project_number` 与公告侧连接，32,029 个不同项目号只有 106 个命中（0.331%）。

因此要在大规模上拿到采购方，仍只能从标题里做名称抽取（0.331% 的项目可以由 `relate_type=2` 直接给出，不足支撑指标）。这一步的准确率无法保证，且抽出来的名称还要再与企业主档匹配一次——两次不确定叠加，边的可信度会低到无法用于风险传导。

### 2.4 若强行用会得到什么假数

假设接受「标题抽取采购方」，能得到大约 3 万条边。这个数字的问题有三：

其一，**覆盖面错位**。公开招投标集中在政府采购、国企采购与工程类，制造业的零部件供应（本指标真正关心的部分）几乎不入库。用它算「供应链关系数」，数出来的是「招投标关系数」。

其二，**方向缺失**。招投标不给「上游/下游」语义，只给「采购/中标」。产业链分析要的是「谁在谁的上游」，这需要环节级映射，而招投标的品类是「材料配件」「能源化工」这类粗类目。

其三，**不可复核**。标题抽取的采购方名称一旦错，下游的「某链主供应商数」就错，且无法从数字本身发现错误。这类错误在验收时最难解释。

结论：宁可判不支持，也不给一个语义错位的假数。

表级证据统一引用 `_work_gkx21/TABLE_ABSENCE_EVIDENCE.md`，与上面逐表探测互为印证：

- **§`enterprise_supply_chain`**：精确同名不存在，词根候选 0 张。证据块对该簇附了一条提醒——该表曾是明细层产物，不排除由外部源装载，因此**不得只看「库内无表」就定档，必须逐件核实 gkx 是否有等价源**。本件照此做了核实：8 类词根（supply/purchase/relat/counterpart/vendor/supplier/chain_node/edge）扫描命中 5 张，全部是论文/学者关系表（`dwd_en_paper_related`、`dwd_zh_paper_related`、`dwd_scholar_paper_relation` 及采购方表的备份），无一为企业—企业边；招投标两端键齐但项目号连接覆盖 0.331%（§2.3），等价源不成立，故判零等价。
- **§`enterprise_cooperation`**：精确同名不存在，词根候选 0 张。这条用来封住「用合作关系表顶替供应关系」的退路——两者方向语义不同，且该表同样不在 gkx——该演示库合作关系表在本库**不可用**，也不得用其字段替代供应边。
- **§`enterprise_industry_chain` / §`industry_chain_entity_rel`**：实体—链关系表亦不存在，说明「用链级实体关系反推企业间边」这条路也走不通。

这三条合起来构成本件的书面凭据：不是「未检索」，而是「按证据块要求把可替代面逐条排除后，仍为零等价」。

### 2.5 裁定

本指标依赖「企业—企业有向边」，该数据形态在 gkx 零存在、在开发库零存在，且无法由任何现有表推导（招投标只有半条边）。按依赖性质三分法，属 **B 类（不可重建，须外部采购/报送）**。

推翻本裁定的唯一条件：甲方提供带**采购方信用代码**的合同/发票/供应关系台账（§附录 C 给出字段规格）。

## 三、数据支撑情况

### 3.1 四判定落表

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 无供应关系结果表 |
| 表数据直接支持（开发库+三方库） | 否 | 同上 |
| 依赖表结构支持（开发库/三方库） | 否 | 四类模式扫描 0 命中 |
| 依赖表数据支持（开发库/三方库） | 否 | 招投标缺采购方键 |
| 聚合结论 | 完全不支持 | 结构与数据均不具备可算闭环 |

### 3.2 数据量、覆盖与代表性

招投标 37,300 条项目、38,352 条中标记录，量不算小。但它覆盖的是「公开采购」这个特定场景，与「产业链供应关系」的交集很小。用它做覆盖度分析没有意义，因为分母（真实供应关系）本身不可知。

### 3.3 结构支持判定

关系边需要三元组结构（主体—关系—客体），gkx 的全部表都是「实体—属性」结构，没有一张是三元组。这不是填充率问题，是数据模型问题。

### 3.4 与开发库 live 的差异

开发库同样没有供应关系表。live 侧若有图谱库，其边也只可能来自本项目之外的数据源（采购或报送）。因此本指标在 live 上同样无法出数。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺口 | 影响面 | 处置 |
|---|---|---|
| 无采购方企业标识 | 边只有一端，无法成立 | 采购合同台账或税票数据 |
| 无供应品类/金额 | 边无权重，无法算强度 | 合同明细 |
| 无上下游方向 | 无法做传导分析 | 需环节级映射或甲方标注 |
| 无时间序列 | 无法看关系演化 | 合同签订日期 |

### 4.2 逐条影响

采购方标识是硬缺口：没有它，本指标一行都算不出来。

品类与金额决定边的「粗细」：没有它们，图谱只能画等粗的线，无法区分主供与备供。

上下游方向决定能不能做风险传导：这是本指标的核心价值，也是招投标数据最缺的东西。

时间序列决定能不能看演化：供应链关系的建立与断裂本身就是重要信号。

### 4.3 明确不做什么（禁止的替代）

- 不用招投标「项目—中标方」冒充供应关系边——缺采购方键，语义错位。
- 不用标题抽取采购方——两次不确定叠加，不可复核。
- 不用行业上下游顺序推断企业关系——那是环节级推断，不是企业级事实。
- 不用「共同供应商」推断直接关系——二度关系不等于一度。

### 4.4 若甲方补齐后的口径升级路径

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 提供合同台账（含双方信用代码） | 可算精确边数 | 可升格至完全转换支持 |
| 提供税票数据（需授权） | 可覆盖全部交易 | 可升格 |
| 提供核心企业配套名录 | 可算「链主—配套」边 | 可升格至部分支持 |
| 仅提供商业供应链库账号 | 边可算但不可核验 | 部分支持 |
