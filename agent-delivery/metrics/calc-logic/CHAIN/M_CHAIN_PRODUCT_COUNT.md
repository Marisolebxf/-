### 0.4 本报告的证据纪律

1. **零行不是零产品**：3 条链的 0 是「源表没有这些链的行」，不是「这些链没有产品」；产物用 `zero_chain_rows` 与 `zero_chain_check` 双写，值写 NULL 不写 0。
2. **「产品种数」与「清单字符串数」必须分开**：对 `product_name` 直接 `COUNT(DISTINCT)` 得 65,457，那是「企业级清单字符串」个数，不是产品种数；本件按 JSON 拆项后去重得 221,945。
3. **不合并同义词**：`伺服电机` 与 `伺服电机系统` 算两个，因此数值系统性偏大；这是已知方向，写入 `gaps`，不写成「准确」。
4. **不把链级之和当去重总数**：多链企业按链各计一次，12 链之和 480,148 > 去重 221,945，两者语义不同。

## 摘要

「产业链关联产品数」要回答「这条链上的企业一共报了哪些产品」。它听起来比专利数简单，实际是本批 5 件里口径最脏的一件：产品名由企业自主填报，没有行业标准编码，同一件东西在不同企业笔下可能写成三四种叫法。

实测产品标签表 **80,258 行**，每行是一家企业的一条「产品清单」字符串。按 JSON 列表拆项后得 **724,960 个条目**，链内去重后 **221,945 个产品**，覆盖 **78,838 家企业**。12 条链里 **9 条有产品**，合计 480,148 个（含多链重复），中位数 34,130，软件与信息服务 139,118 居首。

三个结构性缺口决定了本件只能判**部分支持**。

第一，**3 条链零行**。`INB1209` 智能网联汽车、`INB1236` 低空经济、`INB2503` 生物医药在 `industry_link_name` 中一行都没有（SQL 逐码 `LIKE` 实测为 0）。这不是解析失败，是源表没覆盖；这三条链的产品数只能留空。

第二，**产品条目无标准编码**。全表没有任何 `product_code` 或国标分类号，只有自由文本。后果是同物异名无法归并：「伺服电机」「伺服电机系统」「伺服马达」会被算成三个产品。数值因此系统性偏大，且链间不可比——一条链的产品名写得细，数字就高，与产业实际丰富度无关。

第三，**一行一清单**。表结构是「一家企业一行，产品清单塞在一个字符串里」，清单长度取决于填报习惯。头部企业一次报 200 个产品，小企业报 2 个，产品数被填报行为放大。80,258 行里还有 **1,611 行清单为空**，它们计入企业数但不贡献产品。

还有一个必须先拆的陷阱：官方 SQL 写法是 `WHERE industry_code = :chain_code`，在 gkx 上跑出来是 **0 行**。原因是 `industry_code` 存的是链名数组（如 `["智能终端"]`），链码实际在 `industry_link_name`。这不是数据缺失，是列语义与字段名不符；本件改用 `industry_link_name` 解析 INB token 才拿到数。

结论：9/12 链有数、拆项可复现，但覆盖缺 3 链、口径无标准编码、同物异名未归并 → **部分支持**。数值可作「产品丰富度」的相对参考，不能当「产品种数」的验收值。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的功能模块是：**产业链分析 → 产业总览 → 产品图谱 → 关联产品数**。展示形态是标题行「本链关联 N 个产品」，下方产品云按频次排布；点击产品可下钻到企业清单。

它与「企业数」「专利数」构成产业概况三件套。三件的口径必须同池：企业数用链标签、产品数用产品标签、专利数用专利桥，三者都按同 12 链码归链。本报告沿用 `chain21_layer_20261022.json` 的 12 链名口径，正是为了让三件套能对齐。

### 1.2 为什么需要这个指标

第一个用途是**产业覆盖的广度指标**。企业数回答「有多少玩家」，产品数回答「这些玩家做多少种东西」。软件与信息服务 13.91 万个产品、4.02 万家企业，人均 3.46；人工智能 7.68 万个产品、1.37 万家企业，人均 5.60。人均高说明单企业产品线更宽，这是「平台型」与「项目型」企业的差别。

第二个用途是**产品云的排序权重**。产品云要按「有多少家企业做这个产品」排布，这个频次来自产品条目的跨企业计数。产品数算错，云图的字号就错，用户第一眼看到的重点就错。

第三个用途是**招商补链的线索**。某条链的产品清单里如果缺少某个关键环节的产品（比如集成电路缺「光刻胶」），说明本地产业链有缺口。这类分析依赖产品名的规范化；当前同物异名严重，只能做人工排查，不能自动出结论。

### 1.3 需求文档是否给出定义方法

**需求文档只给指标名，未给口径；calc-logic 未收录。** 可从旧稿复原的写法是：

> 产业链关联产品数 = 链内企业填报的产品条目去重个数。
> 口径：`COUNT(DISTINCT product_name) WHERE industry_code = :chain_code`。

这条 SQL 在 gkx 上执行返回 **0**：`industry_code` 存的是链名数组，不是链码。即使改成按链名匹配，`product_name` 存的也是整串清单（如 `["服务器","交换机","路由器"]`），直接 `DISTINCT` 得到的是「清单字符串」个数 **65,457**，不是产品种数。两步都错，必须重写。

### 1.4 类似指标权威机构构建方法可行性分析概要

「某产业有多少种产品」在权威实践里通常以「产品目录/分类码」为锚，而不是自由文本。本节逐族说明，完整谱系见附录 C。

| 方法族 | 代表机构/文献 | 口径要点 | 与本指标的差 | 贴合度 | 开发库可迁移性 |
|---|---|---|---|---|---|
| A 国标产品目录 | 统计用产品分类目录 | 按标准码计数 | 库内无产品码 | 高（若有） | 需建映射 |
| B 自由文本拆项 | 本报告 | JSON 拆项 + 链内去重 | 同物异名不归并，值偏大 | 中 | 已落地 |
| C 文本聚类归并 | 句向量 + 聚类 | 语义相近合并 | 误合并不可控 | 中 | 可试，需人工校验 |
| D 企业主营产品 | 企业年报/官网 | 按主营产品计数 | 粒度粗、覆盖低 | 低 | 不可行 |
| E 电商/招投标品类 | 平台品类体系 | 按平台类目计数 | 类目体系与产业链不同构 | 低 | 不可迁移 |

**A 族是唯一能给出「种数」的口径，但库内没有产品码。** 统计用产品分类目录有 5 层、数万个末级码，若企业填报时挂上码，产品数就是一次 `COUNT(DISTINCT code)`。当前表只有自由文本，A 族无法执行。

**B 族是唯一当天能跑的路径。** 它的产出是「不同写法的产品名个数」，不是「产品种数」。两者差别在集成电路这类命名规范的行业小，在软件、数字创意这类命名随意的行业大。本报告明确把它标为「条目数」而非「种数」。

**C 族能逼近种数，但误合并代价高。** 「伺服电机」与「伺服电机系统」该不该合并，取决于业务定义；聚类算法按相似度合并，会把「工业机器人」与「服务机器人」也合并掉。没有人工校验预算时，C 族不比 B 族更可信。

**D 族覆盖太低。** 只有上市/规上企业有年报，中小企业没有主营产品披露，覆盖不到 10%。

**E 族的类目体系与产业链不同构。** 电商类目按消费场景分（「手机通讯」「电脑办公」），产业链按生产环节分（「集成电路」「智能终端」），两者无法一一映射。

### 1.6 本报告的口径与边界（推测定义，须与甲方会签）

**推测原意**：衡量某条产业链上企业群体的产品丰富度，用于产品云排序与补链线索排查。

**推测定义**（非甲方闭合口径）：

设链 $c$ 的企业行集合 $R_c$（`industry_link_name` 含该链 INB 码前 7 位），行 $r$ 的产品清单拆项集合 $S_r$：

$$N_c=\left|\bigcup_{r\in R_c} S_r\right|$$

$$N_{total}=\sum_{c=1}^{12}N_c=480{,}148,\qquad D=\left|\bigcup_{c}\bigcup_{r\in R_c}S_r\right|=221{,}945$$

约束：① 清单按 JSON 列表拆项，失败时按 `,`/`，`/`;`/`；` 切分；② 链内按条目字符串去重，不做同义词归并；③ 链码取 `industry_link_name` 中 INB token 前 7 位；④ 多链企业按链各计一次；⑤ 零行链写 NULL，不写 0。值域 $N_c\in[0,139118]$。

## 二、计算过程

### 2.1 方法选择：为什么拆项、为什么不归并

表里 `product_name` 不是单个产品名，而是整串清单：`["服务器","交换机","路由器","防火墙"]`。若直接 `COUNT(DISTINCT product_name)`，得到的是「有多少种不同的清单写法」，与「有多少个产品」完全两回事。实测这个错值 65,457，比正确值 221,945 小 3.4 倍——错得不算离谱，所以更危险：它看起来像个合理数字。

因此第一步必须拆项：用 `ast.literal_eval` 解析 JSON 列表，逐项 `strip`；解析失败时按四种分隔符切分。拆项后得到 724,960 个条目，链内去重后 221,945 个。

第二步选择「不归并」。归并需要判断「伺服电机」与「伺服电机系统」是不是同一个产品，这是业务判断，不是技术判断。没有标准码、没有人工标注，任何自动归并都会引入不可解释的误差。不归并的代价是数值偏大，但方向明确、可解释；归并的代价是误差方向不可知，且难以复核。两害相权，取不归并。

### 2.2 拆项规则与链归属规则

拆项分两条路径：

1. **JSON 路径**（覆盖绝大多数行）：`ast.literal_eval` 解析成 Python 列表，逐项 `strip`，丢弃空串。
2. **分隔符路径**（JSON 解析失败时）：按 `,`、`，`、`;`、`；` 四种分隔符切分，逐项 `strip`。

链归属不看 `industry_code`（它存链名数组），而看 `industry_link_name`：该列形如 `"智能终端|INB1333|..."`，用正则提取 `INB\d{7}` 前 7 位作为链码。这是本件与官方 SQL 最大的分歧点，也是官方 SQL 返回 0 的原因。

三个公式：

$$N_c=\left|\bigcup_{r\in R_c} S_r\right|,\qquad \bar n_c=\frac{N_c}{|R_c|}$$

$$\text{empty\_rate}=\frac{1{,}611}{80{,}258}=0.0201$$

第一条是链级产品数；第二条是人均产品数（$|R_c|$ 为企业行数）；第三条是空清单率，用来说明「有 2.01% 的行不贡献产品」。

### 2.3 三条链零行的成因

`INB1209` 智能网联汽车、`INB1236` 低空经济、`INB2503` 生物医药在产品表中零行。这不是解析失败，而是源表覆盖缺口，证据有三条：

1. 对 `industry_link_name` 逐码 `LIKE '%INB1209%'` 实测 **0 行**，三码皆然。
2. 三码在链标签表 `dwd_org_industry_tags` 中都有企业（智能网联汽车 11,950 家、低空经济 5,450 家、生物医药 147,881 家），说明链本身有企业，只是没填产品。
3. 产品表覆盖的链码不止 12 条，还包含 `INB0014`（13,445 个产品）等非顶层码；说明填报是按另一套码域做的，三条链恰好不在其中。

三点的含义是：**产品标签的填报范围小于链标签的覆盖范围**。这不是「这三条链没有产品」，而是「这三条链的企业没有填报产品」。因此值写 NULL，不写 0；写 0 会让用户以为「这三条链真的没有产品」。

### 2.4 计算步骤（脚本逐步实现）

1. 读 `code/_snapshots21/chain21_products_20261022.json`（80,258 行全表落地，含链码、品类、链名、产品清单、企业名）。
2. 对每行 `product_name` 拆项：先 JSON，失败则按分隔符切分；丢弃空串。
3. 从 `industry_link_name` 提取 INB 前 7 位，归到 12 条链；非 12 链的行计入 `non_top12_chains`。
4. 每条链对产品条目去重计数 $N_c$，同时统计品类数、企业数、人均。
5. 汇总：`sum_products=480,148`、`distinct=221,945`、`sum_orgs=118,428`、`zero_chains=3`，并校验 $N_c \le$ 该链条目总数。

第 5 步的校验很关键：链内去重值必须小于等于该链的条目总数，否则说明去重逻辑写反了。当日 12 链全部满足。

覆盖上，9/12 链有产品，3 条零行。零行的三条恰好是智能网联汽车、低空经济、生物医药——都是「硬科技 + 强监管」的链，产品填报率低可能与口径有关（企业更愿意报「技术方向」而非「产品型号」）。这只是推测，库内无法验证。

规范度上，全表无产品码，产品名长度从 2 字到 40 字不等，同物异名普遍。这决定了「产品数」只能作相对参考，不能作绝对种数。

### 3.4 结构支持判定

结构上有清单、有链归属、有企业名，三样够拆项与归链。缺的是「产品标准码」这一列——它不是本指标的必需字段（没有码也能数条目），但它是「种数」的必需字段。因此结构判「支持条目数、不支持种数」。

这也是本件判「部分支持」而非「完全转换支持」的核心理由：不是「算不出来」，而是「算出来的不是甲方想要的种数」。若甲方接受「条目数」，可以上调；若坚持「种数」，则必须补码或补归并。

### 3.5 与开发库 live 的差异

开发库若有产品宽表，需确认它是「一行一产品」还是「一行一清单」。若是前者，可直接 `COUNT(DISTINCT)`；若是后者，必须拆项。两种结构的数值不可直接比较。

## 四、数据缺失情况

### 4.1 缺口清单与后果归因

本件是 5 件里缺口最多的一件，逐条写清方向与量级。

| 缺口 | 影响面 | 方向与量级 | 处置 |
|---|---|---|---|
| 3 链零行 | 25% 的链无产品数 | 整链缺失（3/12），不是偏低 | 补填报或按品类映射 |
| 无产品标准码 | 无法出「种数」 | 同物异名致值偏大，量级不可估 | 建国标码映射 |
| 一行一清单 | 产品数受填报习惯影响 | 头部企业抬高数值 | 拆项已缓解，未根治 |
| 1,611 行空清单 | 企业计入、产品不贡献 | 人均被压低 | 标注空清单率 |
| 品类与清单不同源 | 无法互相校验 | 方向不可知 | 不作交叉校验 |
| 非 12 链码混入 | 有 13,445 个产品落在 `INB0014` | 12 链口径外的存量 | 明确口径边界 |

**3 链零行 → 25% 的链无产品数。** 这不是抽样误差，是源表没覆盖。方向是整链缺失，量级 3/12。不能用其他链的均值填补——三条链的产品结构与其他链不同，填补会造出假数。

**无标准码 → 无法出「种数」，且值偏大。** 「伺服电机」「伺服电机系统」「伺服马达」算三个，数值系统性偏高。方向偏高，量级不可估（取决于命名混乱程度）。处置：建国标码映射，或引入人工归并规则。

**一行一清单 → 产品数受填报习惯影响。** 头部企业一次报 200 项，小企业报 2 项，产品数被「谁更愿意填」左右。方向不定（大企业多则偏高，小企业多则偏低），量级不可估。拆项已缓解「整串当一项」的问题，但没有解决「填报深度不一致」。

**1,611 行空清单 → 人均被压低。** 这些行计入企业数、不贡献产品，人均分母偏大、分子不变，结果偏低。量级 2.01%，影响很小，但要在页面注明。

**品类与清单不同源 → 无法互校。** `industry_link_code` 是品类标签，`product_name` 是产品清单，两者由不同流程填报，不能拿一个校验另一个。方向不可知。

**非 12 链码混入 → 口径边界要写清。** 表里有 `INB0014` 等非顶层码（13,445 个产品），本件只统 12 链，这部分不进正式值。方向是「12 链口径外还有存量」，量级 13,445。

**能否交叉验证：只能验证内部一致性。** 路径一：链内去重值 ≤ 条目总数，12 链全部成立；路径二：换一种拆项规则（只按逗号切）重跑，若排序稳定说明结论对拆项方式不敏感。两条都不能验证「产品种数对不对」。

### 4.2 可构建但存在缺口（不是「无法构建」）

1. **3 链补填报**。智能网联汽车、低空经济、生物医药需补产品清单，或按品类标签映射。
2. **建产品码映射**。把自由文本映射到统计用产品分类目录的末级码，才能出「种数」。
3. **同义词表**。至少覆盖头部产品（伺服电机、工业机器人、动力电池等）的常见别名。
4. **拆分公司/产品粒度**。理想结构是「一行一产品」，当前「一行一清单」是历史包袱。
5. **口径边界文档化**。明确「12 链」是否包含 `INB0014` 这类非顶层码。

### 4.3 数据陷阱（本批实测，须写入任何下游复用说明）

- **`industry_code = :chain_code` 恒为 0**：该列存链名数组，链码在 `industry_link_name`。
- **`COUNT(DISTINCT product_name)` = 65,457 是错的**：那是清单字符串数，不是产品数。
- **3 条链 NULL 不是「没有产品」**：是源表没覆盖，写 0 会误导。
- **480,148 是计位不是去重**：多链企业重复计入，去重值是 221,945。
- **产品数偏大**：同物异名未归并，数值只能作相对参考。

## 五、王惠方法对照与选用建议

### 5.1 原方法还原

calc-logic 未收录本指标独立文件，旧稿留下的口径是：

- 口径定义：「产业链关联产品数 = 链内企业填报的产品条目去重个数。」
- 公式：`COUNT(DISTINCT product_name) WHERE industry_code = :chain_code`。
- 源库表：产品标签表（旧稿为旧演示库切片，25,258 行）。
- 依赖：产品清单 + 链归属。

这条 SQL 在 gkx 上有两处不成立：`industry_code` 不是链码、`product_name` 不是单个产品名。因此旧口径不能直接执行，必须重写。

### 5.2 新方法概述

新方法做三件事：① 用 `industry_link_name` 解析 INB 码归链；② 把 `product_name` 当 JSON 清单拆项；③ 链内去重、不归并。语义仍是「链内产品条目数」，但可执行、可复现、可逐条追溯。

| 维度 | 旧口径 | 新口径 | 数据支撑差异 | 可复现性差异 |
|---|---|---|---|---|
| 归链键 | `industry_code` | `industry_link_name` 的 INB 码 | 旧键在 gkx 上恒 0 行 | 新口径可跑 |
| 计数对象 | `product_name` 整串 | 拆项后的条目 | 旧值 65,457 是清单数 | 新口径可复核 |
| 源表行数 | 25,258（切片） | 80,258（全表） | 3.18 倍 | 新口径覆盖更全 |
| 去重产品 | 72,616 | 221,945 | 3.06 倍 | 倍率稳定 |
| 链覆盖 | 未披露 | 9/12 | 新口径披露 3 链零行 | 新口径更透明 |
| 同物异名 | 未处理 | 未归并（已声明） | 两者都偏大 | 新口径声明方向 |

### 5.4 选用建议与理由

**建议采用新口径（拆项 + `industry_link_name` 归链），但把指标名严格限定为「产品条目数」**，理由：

1. 旧口径在 gkx 上**不可执行**（归链键错、计数对象错），不是「差一点」，是「跑出来是 0」。
2. 新口径可复现、可逐条追溯，且倍率对照稳定（3.0—3.1），说明规则自洽。
3. 但新口径产出的是「条目数」而非「种数」；若沿用「产品数」这个名字，会被误读为种数。建议页面写「关联产品条目 N 个」。
4. 3 链零行必须在页面留空并注明「暂无填报」，不能用 0 或均值填补。

**待甲方裁决点**：① 是否接受「条目数」口径；② 3 条零行链是补填报还是按品类映射；③ 是否投入建产品码映射（决定能否出「种数」）。

## 附录 C　产业链产品数可行性报告（完整版）

### C.1 报告目的与范围

回答三个问题：① 「产业产品数」在权威口径中如何定义；② 本库能否得到可复现的链级产品数；③ 无标准码时数值应如何表述。范围限定产品标签表与链树，不涉及电商类目或企业年报。

### C.2 需求语义锚定

需求只有「关联产品数量」一句，三个未定义点：① 产品按标准码还是自由文本；② 一行一产品还是一行一清单；③ 多链是否重复计。本报告的选择是「自由文本拆项 / 一行一清单拆项 / 重复计」，理由在 §2.1。

### C.3 权威与学术构建方法谱系

| # | 方法 | 出处 | 输入 | 输出 | 贴合度 | 结论 |
|---|---|---|---|---|---|---|
| M1 | 国标产品目录 | 统计用产品分类目录 | 标准码 | 种数 | 高 | 库内无码，不可用 |
| M2 | 自由文本拆项 | 本报告 | 清单字符串 | 条目数 | 中 | 采用 |
| M3 | 文本聚类归并 | 句向量实践 | 产品名 | 近似种数 | 中 | 可试，需校验 |
| M4 | 企业主营产品 | 年报/官网 | 主营描述 | 粗粒度产品 | 低 | 覆盖不足 |
| M5 | 平台品类 | 电商类目 | 类目 ID | 品类数 | 低 | 体系不同构 |

#### C.3.1 方法族 M1：国标产品目录

代表实践：《统计用产品分类目录》五级编码。数据要求：产品标准码。计算步骤：`COUNT(DISTINCT code)`。局限：库内无码。为什么不能直接照搬：填报端没有挂码，映射表也不存在。

#### C.3.2 方法族 M2：自由文本拆项

代表实践：本报告。数据要求：清单字符串。计算步骤：JSON 拆项、链内去重。局限：同物异名不归并，值偏大。为什么采用：当天可跑、可复现、可逐条追溯。

#### C.3.3 方法族 M3：文本聚类归并

代表实践：句向量 + 层次聚类。数据要求：产品名语料。计算步骤：向量化、聚类、阈值合并。局限：误合并不可控。为什么暂不采用：无人工校验预算时，归并误差不可解释。

#### C.3.4 方法族 M4：企业主营产品

代表实践：企业年报「主营业务」段。数据要求：年报文本。计算步骤：抽取主营产品。局限：只有上市/规上企业有。为什么不采用：覆盖不到 10%。

#### C.3.5 方法族 M5：平台品类

代表实践：电商平台类目体系。数据要求：类目 ID。计算步骤：按类目计数。局限：类目按消费场景分，与产业链不同构。为什么不采用：无法映射到 12 链。

### C.4 数据可行性详细分析

| 维度 | 源表 | 实测 | 覆盖率 | 是否造数 | 结论 |
|---|---|---:|---:|---|---|
| D1 产品清单 | `dwd_org_industry_product_tags` | 80,258 | 100% | 否 | 可用（需拆项） |
| D2 链归属 | `industry_link_name` | 9/12 链 | 75% | 否 | 部分可用 |
| D3 企业名 | `org_name` | 非空 | 高 | 否 | 可用 |
| D4 产品标准码 | 无 | 0 | 0% | 否 | 不可用 |
| D5 品类标签 | `industry_link_code` | 有值 | 高 | 否 | 不可与清单互校 |

三点读法。第一，D1 是 100% 覆盖，但「覆盖」指行数，不指产品名质量；拆项后仍有 2.01% 空清单。第二，D2 只有 75%，3 条链零行，这是判「部分支持」的直接依据。第三，D4 缺失决定了「种数」不可得，只能出「条目数」。

### C.5 推荐构建方案（工程可执行）

1. **短期**：维持拆项 + 去重，页面标注「条目数」。
2. **补 3 链填报**：智能网联汽车、低空经济、生物医药必须先有行。
3. **建同义词表**：覆盖头部产品的常见别名，降低虚高。
4. **建国标码映射**：把自由文本映射到产品分类末级码，才能出「种数」。
5. **改表结构**：长期改为「一行一产品」，消除清单字符串。

### C.6 风险与残余不确定性

- **覆盖风险**：3/12 链零行，且缺的是三条重点链。
- **口径风险**：「条目数」被当成「种数」。
- **虚高风险**：同物异名未归并，数值系统性偏大。
- **填报风险**：清单长度受填报习惯影响，头部企业抬高数值。
- **误判风险**：3 条链 NULL 被读成「没有产品」。

### C.7 可行性总判（完整版结论）

产品清单在、量够、拆项可复现，9/12 链有数；但 3 链零行、无标准码、同物异名未归并，覆盖与口径两侧都有缺口。判**部分支持**：可出「条目数」参考值，不能出「种数」验收值。

### C.8 对甲方四问的逐条回答

**一问：这个指标现在能不能出数？** 能出 9 条链，3 条链留空；合计 480,148 个条目（计位）。

**二问：出的是不是甲方要的那个东西？** 如果甲方要「产品条目数」，是；如果要「产品种数」，不是——同物异名未归并，值偏大。

**三问：要补齐还差什么、谁能给？** 差三件：① 3 链的产品填报（业务侧）；② 产品国标码映射（数据工程）；③ 同义词表（业务 + 算法）。

**四问：如果补不齐，替代口径是什么、替代后还叫不叫这个名字？** 补不齐时保留「关联产品条目数」，页面注明「不含智能网联汽车/低空经济/生物医药」；若甲方坚持「产品种数」原名，则只能留空待补。
