## 摘要

这个指标不是一个数，而是一次**接入动作**：把图谱要用的六类实体（企业、高校、科研机构、人才、政策、专利）从源表接进图谱库，并给出每类的行数与可挂链性。

实测六类源全部在库：企业主档 **189,116**、专利 **2,939,895**、人才 **21,316**、政策 **20,000**、高等院校 **3,501**、科研机构 **2,074**。合计 **3,175,902** 行。**仅 2 类可挂链**（企业走 `industry_code`、专利走申请人名称桥），另 4 类（高校、科研机构、人才、政策）没有链码字段。

结论：接入本身没有技术障碍，判**部分支持**的原因不在「能不能接」，而在「接进来能不能挂到链上」——四类实体只能给总量，图谱的链维度会缺三分之二。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**产业链分析 → 产业链图谱 → 实体接入**。后台面板展示六类实体的接入状态（已接入/行数/可挂链），前端图谱检索按实体类型筛选。

它是图谱类指标的底座：图谱 103（关系抽取）与图谱 117（全景模型）都依赖这里的实体。三件必须共用同一套实体 id，否则关系边会指向不存在的节点。

### 1.2 为什么需要这个指标

图谱的价值在于「跨实体关联」：企业—专利—人才—机构。没有统一接入，每类实体各建一套 id，关联就无从谈起。这个指标就是把「有哪些实体、各多少、能不能挂链」摆到明面上。

第二个用途是**容量规划**。293.99 万件专利进图，边数会是百万级；不提前算清楚，图库上线就会 OOM。本件给出六类行数，正是容量估算的输入。

第三个用途是**验收基线**。图谱上线后，「实体数」是最容易被质疑的数字（少了说漏接、多了说重复）。本件给出逐类行数与口径，可作为对账依据。

### 1.3 需求文档是否给出定义方法

**需求文档给出的是表清单，不是口径。** 需求原文列了六类实体与对应源表，但没有规定「高校/科研机构如何识别」「政策算不算实体」「同一实体多源如何合并」。项目内也没有 calc-logic 正本可参照——注册表标注公式未签（`pending_cosign: human:唐绍祖`）。

本报告的处理：高校与科研机构直接取 `dwd_org_heis_info` / `dwd_research_institute_base_info` 主表行数，人才取 `dwd_scholar`，政策取 `dwd_policy_base`；同一实体多源时以信用代码为主键合并。这些选择都写进 §2.2，供会签。

### 1.4 类似指标权威机构构建方法可行性分析概要

本指标看起来只是「数一下/加一下」，但把口径拆开，权威实践里至少有五条路线，它们输出的是同名不同物的东西。本节逐族说明「它算出来的东西与我们这个指标差在哪」，完整谱系、逐族不可照搬的理由与文献出处见**附录 C**。

| 方法族 | 代表机构/文献 | 口径要点 | 与本指标的差 | 贴合度 |
|---|---|---|---|---|
| A 多源接入（本报告） | 需求原文表清单 | 六类源表分别接入，信用代码/名称作键 | 可落地；但四类无链级键 | 高（可算） |
| B 单一主数据 | MDM 主数据管理 | 先建统一实体主数据，再挂各源 | 工程量大，且库内无主数据平台 | 中（长期） |
| C 图数据库直连 | Neo4j 等 | 源表直接映射为节点 | 同上，且无链级键问题依旧 | 中 |
| D 知识图谱抽取 | NLP 实体抽取 | 从文本抽实体 | 噪声大、不可核验 | 低 |

**A 族是唯一务实的选择。** 六类源表都在库内，接入是 ETL 工作，不需要模型或采购。难点不在接入，在「键」：企业有信用代码、专利有申请号，但高校、科研机构、人才、政策只有名称或自有 id。

**B/C 两族是工程升级方向。** 若图谱要长期演进，应先建实体主数据（统一 id），再把各源挂上去。当前直接接入会让「同一家机构在不同源里 id 不同」，关系边容易断。

**D/E 两族不适用。** 文本抽取噪声大且不可核验；商业图谱与本地链编码不同源，混用会让「实体—链」关系错位。

## 二、计算过程

### 2.1 总体思路与数据流

两步：先逐类统计源表行数与键可用性，再判定「能否挂链」。第二步是本件的实质——行数只是容量，可挂链性才决定图谱能不能用。

本报告把「可挂链」定义为「有字段能落到 7 位链码」，包括名称桥接。这个定义较宽，但诚实：它说明「接得进来」不等于「挂得上」。

```text
六类源表
   ├─ 企业 189,116（industry_code → 链）
   ├─ 专利 2,939,895（申请人名称 → 链）
   ├─ 人才 21,316（无链码）
   ├─ 政策 20,000（无链码）
   └─ 高校 3,501 / 科研机构 2,074（无链码）
        ▼
 3,175,902 行，2/6 类可挂链
```

### 2.2 口径定义与公式

没有公式，只有统计：逐类 `COUNT(*)` 与「键可用性」判定。键可用性分三档：直接键（信用代码/链码）、桥接键（名称）、无键。

可挂链类数 = 有直接键或桥接键的类数。当前 2/6，缺的四类都是「只有名称或自有 id、不含链码」。

```text
entities = Σ COUNT(*) per class
chain_linkable = #classes with direct or bridge key
result: 3,175,902 rows, 2/6 linkable
```

### 2.3 链映射规则（全批一致）

本批 24 件共用一套链映射，与已归档的 `第三方库指标计算过程/M_CHAIN_SZ_REGION_COUNT.md` 一致：① 链归属只认 `gkx.dwd_org_industry_tags.industry_code` 里的 INB 码，取**前 7 位**作为顶层链码（`INB1204` 机器人、`INB1209` 智能网联汽车、`INB1236` 低空经济、`INB1303` 集成电路、`INB1306` 软件与信息服务、`INB1309` 人工智能、`INB1323` 传感器、`INB1333` 智能终端、`INB1354` 具身智能、`INB1502` 数字创意、`INB2503` 生物医药、`INB2505` 合成生物）；② 环节级口径取 `industry_link_code` 的 9 位 L1 码与最长叶码，父码 = 去末 2 位；③ 一行标签 = 一家企业（`credit_code` 全表唯一，2,283,762 行 = 2,283,762 家）；④ 城市取 `dwd_org_base_info` 主档 `city`，深圳切片只认「深圳市」全称，不用前缀模糊匹配。

实体接入本身不做链映射，只判定「能不能挂」。真正的挂链在关系抽取件（图谱 103）里做，两件必须共用同一套判定，否则会出现「这里说能挂、那里挂不上」。

链级分布（每类实体在各链的行数）在本件只作参考，正式统计在 103 件。本件的 `chains[].value` 是「该链可挂接实体数」（企业 + 专利），用于容量估算。

### 2.4 计算步骤（脚本逐步实现）

1. 按需求口名的六类实体逐一盘点 gkx 源表行数（COUNT(*) 实测）
2. 计算企业实体的六字段属性填充率（底册 189,116 行）
3. 对企业按标签表 industry_code 归链、对专利按申请人名称桥回链
4. 四类无链级关系面的实体只报总量，不计入链挂接覆盖
5. 输出六类实体规模、链挂接率与逐链实体数

四步里第 3 步（可挂链判定）是唯一有判断的步骤。它决定「2/6」这个结论，也决定图谱的链维度覆盖率。
这一步的判断标准值得展开说：直接键指源表里就有链码或信用代码，命中率高且可核验；桥接键指只有名称，需要先做名称规范化再匹配，命中率取决于命名习惯；无键指连名称都没有可用于归链的信息（例如高校名「深圳大学」不含任何产业链语义）。三类键的差别不是技术难度，而是「可核验程度」，这决定了图谱上线后每条边能不能被追到源记录。

本件还把「可挂链」与「已挂链」分开：前者是结构判断，后者是实际抽取结果。四族关系件（图谱 103）给出的是已挂链的边数，本件给出的是可挂链的类数，两者相乘才是图谱的真实规模。分开写的好处是，当抽取覆盖率变化时，能立刻判断是「键变少了」还是「匹配变差了」。

### 3.3 数据量、覆盖与代表性

六类源全部有量，没有空表。最少的科研机构（2,074）与高等院校（3,501）也足够支撑图谱展示。接入侧不存在覆盖问题。

覆盖问题在「键」：四类无链级键，意味着图谱里三分之二的实体只能挂到城市或悬空。这是本件降档的唯一原因。

### 3.4 结构支持判定

结构上六类源的主键各不相同：企业信用代码、专利申请号、人才自有 id、政策发文号、机构名称。没有统一实体 id，跨类关联只能靠名称或人工映射。

这是图谱工程的标准难题。短期解法是「按类建节点、按名称建边」；长期解法是建实体主数据。本报告采用短期解法，并把长期方向写进 §4.4。

### 3.5 与开发库 live 的差异

开发库无实体接入表，图谱目前无法从 live 直接读实体。建议先落一张实体清单表（`entity_type, entity_id, name, chain_code, city`），作为图谱的唯一实体源。

若直接让图库连源表，源表结构一变图谱就崩。中间层是必须的。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺口 | 影响面 | 处置 |
|---|---|---|
| 四类无链级键 | 三分之二实体只有总量、无逐链值 | 索要机构—链关系，或接受城市级 |
| 无统一实体 id | 跨类关联困难 | 建实体主数据 |
| 专利名称桥接覆盖 38.35% | 图谱专利节点大量悬空 | 见专利件 |
| 底册覆盖 8.28% | 属性完整度只在子集内成立 | 与标签面口径分开陈述 |

### 4.2 逐条影响

第一条是最硬的缺口：高校、科研机构、人才、政策只有名称或自有 id，都不含链信息。本报告只能把前三类挂到城市，图谱的链维度因此缺三分之二。

第二条是工程债：没有统一 id，企业节点与专利节点只能靠名称连，一旦改名就断。这个问题在数据量小时不明显，上到百万级边就会成为主要故障源。

第三、四条是口径问题：专利桥接覆盖 38.35%（见专利件），企业底册只覆盖标签面 8.28%。两者都会传导到图谱，让「实体—链」边不完整。

### 4.3 明确不做什么（禁止的替代）

- 不把「行数多」当成「图谱可用」——四类挂不上链。
- 不从文本抽实体——噪声不可控。
- 不用商业图谱替代——编码不同源。
- 不合并跨源实体（当前无统一 id）——强行合并会出错。

第一条是本件最想纠正的认知偏差：图谱项目的汇报常以「接入 X 万实体」为成绩，但真正决定可用性的是「多少实体挂上了链」。

### 4.4 若甲方补齐后的口径升级路径

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 建实体主数据（统一 id） | 跨类关联可靠 | 可升格至完全转换支持 |
| 补机构—链关系 | 六类全部可挂链 | 可升格 |
| 专利桥接补键 | 专利节点不悬空 | 可升格 |

三条都是工程/数据工作，不需要新算法；第一条是长期正确解。

## 附录 C 可行性完整版

**图谱工程的方法论核心是「实体识别」与「实体消解」。** 前者决定有哪些节点，后者决定同一实体是否被重复建点。本项目两者都未做（直接接源表），因此图谱是「六张表拼在一起」，不是「一个知识图谱」。

**权威实践（W3C RDF、Google Knowledge Graph）都强调统一 id 与本体（ontology）。**没有本体，六类实体之间无法定义合法关系；没有统一 id，同名实体无法消解。

**因此本件的定位是「图谱前置的数据盘点」，不是「图谱本身」。** 这个定位下它完全可用：它告诉工程团队「有多少节点、哪些能挂链、缺什么键」。

| 族 | 代表 | 可迁移的部分 | 不可迁移的部分 |
|---|---|---|---|
| 甲 多源接入 | 本报告 | 可落地、行数可核 | 无统一 id、无本体 |
| 乙 主数据管理 | MDM | 统一实体 id | 工程量大 |
| 丙 图库直连 | Neo4j | 查询快 | 源表变更即崩 |
| 丁 文本抽取 | NLP | 能抽隐性实体 | 噪声不可控 |
| 戊 商业图谱 | 企查查/上奇 | 现成可用 | 编码不同源 |

**落地取舍**：当前用甲族做盘点与接入；建议立项建乙族（主数据），这是图谱能长期演进的唯一路径。

### E.2 与六类全量的对账

六类实体全量 3,175,902 条（企业 189,116、高等院校 3,501、科研机构 2,074、人才 21,316、政策 20,000、专利 2,939,895），其中只有「企业」与「专利」两类能挂到链上，链内合计 2,841,798 条，占全量 **89.48%**。差额 334,104 条的构成：人才 21,316、政策 20,000、科研机构 2,074、高等院校 3,501 全部无法挂链（合计 46,891），加上企业与专利中未挂上链的部分（287,213）。

这个对账说明两件事。第一，节点数不是「6 类相加」那么简单：六类相加是 3,175,902，但真正进入链图的只有 2,841,798，前端若把两个数并列展示（「实体总量」与「链上实体」），必须标明后者是前者的 89.48% 子集。第二，未挂链的 334,104 条里，非企业与专利的四类（46,891）是结构性缺失——它们的表里根本没有链码，不是「漏挂」；企业与专利的 287,213 条才是「有链码字段但值为空/不在 12 链内」，属于可补的部分。

### E.3 两类实体的结构反差

企业与专利在链间的分布并不同步。软件与信息服务企业占 53.54%（917,842 / 1,714,458）、专利只占 15.04%（169,564 / 1,127,340）；人工智能企业占 7.69%、专利占 32.67%；集成电路企业占 0.70%、专利占 5.26%。这说明「企业多的链」与「专利多的链」不是同一批：软件链企业极多但专利密度低（大量小微企业不申请专利），人工智能与集成电路则是企业少、专利密。

这个反差对图谱的价值在于：如果只用企业数排序，会把软件链放在第一位；如果只用专利数排序，人工智能会升到第一。两个排序都「对」，但回答的问题不同（产业规模 vs 技术密度）。前端应把两类实体分列，而不是加总成一个「实体数」排序——加总会让软件链以 38.26% 的占比掩盖它在专利维度的弱势。

### E.4 专利申请人去重后的覆盖

专利 1,127,340 件对应 29,631 个「企业—链」对（逐链相加、未跨链去重），而链上企业有 1,714,458 家，即只有 **1.73%** 的企业—链位能桥接到专利。这个比例低得反常，原因是专利表的申请人名称与 tags 的企业名称做字符串桥接，名称不规范（后缀、别名、子公司）就挂不上。因此「专利实体数」应读作「能桥接上的专利数」，不是「链上企业拥有的全部专利」；真实覆盖被系统性低估，低估幅度无法从库内估计。
