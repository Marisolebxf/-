### 1.2 为什么需要「事件关注度」

事件条数回答「办了多少场」，事件关注度回答「这些活动有没有被看见」。对政策端，后者比前者更重要：一场只有几十人参加但被全网转载的发布会，与一场千人参加但零报道的论坛，传播价值完全不同。关注度就是把这种差异量化。

量化关注度有两条常见路径。第一条是事件侧：抓取每条事件的报道量、搜索指数、社交讨论量，按事件聚合。第二条是文本侧：对政策或新闻文本做主题覆盖与引用分析，用文本的丰富度代理关注度。正本走的是第二条，但它依赖的三列几乎全空；第一条则需要事件表，而事件表只有 20 行。两条路径都断。

### 1.3 口径定义

正本关注度 $A$ 定义为三维加权：

$$A=w_1\cdot V_{\text{body}}+w_2\cdot V_{\text{theme}}+w_3\cdot V_{\text{quote}}$$

其中 $V_{\text{body}}$ 是正文规模、$V_{\text{theme}}$ 是主题覆盖、$V_{\text{quote}}$ 是引用政策数。本件不复算该公式，只检查三个维度的数据可用性。

可用性判据：某维的「真值行数」必须足以支撑归一化。实测 `content` 有 19,203 行有值，可用；`theme` 真值 2 行，`quote_policy` 真值 2 行，均不可用。三维中两维不可用，公式退化为一维，不能出分。

替代口径 $M$ 定义为媒体报道条数与覆盖企业数：

$$M=(\text{rows},\ \text{orgs})=(1{,}668{,}414,\ 28{,}123)$$

$M$ 描述的是「媒体关注」，不是「事件关注」。两者不可互换，也不可相加。

### 1.4 计算公式与本批实现式

```python
def dimension_usable(real_rows, total_rows, floor=0.5):
    return real_rows / total_rows >= floor

usable = {
    "content":      dimension_usable(19203, 20000),   # True
    "theme":        dimension_usable(2, 20000),       # False
    "quote_policy": dimension_usable(2, 20000),       # False
}
assert not all(usable.values()), "三维不全，不得出分"
```

三个实现要点。第一，`floor` 取 0.5 是本件自定的可用性门槛，含义是「至少一半行有真值才配做归一化」；这不是官方阈值，但 2/20,000 远低于任何合理门槛，结论不依赖阈值选择。第二，判据用「真值行数」而不是「非空行数」，因为字面 'NULL' 是非空字符串，用 `IS NOT NULL` 会把 19,998 行全算成有值。第三，`assert` 放在出分之前，确保退化公式不会静默产出分数。

**拒拟理由**：两维不可用，公式退化，不能出 0—100 分。
**替代口径**：无。补列不是本件能做的事，需要上游重新抽取。
**与原文差别**：正本可算的前提不成立，本件只能证明不可算。

### 4.3 媒体关注：不是事件关注（禁止替代）

`dwd_org_important_news_info` 有 1,668,414 条报道、28,123 家企业，是唯一可用的关注信号。但它的对象是企业，不是事件；报道与事件不是一对一关系。

**拒拟理由**：语义不同，媒体关注不能改名成事件关注。
**替代口径**：登记为「媒体关注」，单独成件，不与本件混用。
**与原文差别**：本件无读数，替代件是另一条产品线。

### 4.4 专利被引：禁止替代（负证据）

有引文记录的论文 20,031 篇、被引 144,020 次、篇均 7.1899 次。这组数只说明论文影响，不说明任何事件被关注。本件把它列出来，是为了堵住「拿被引冒充关注」这条捷径。

**禁止理由**：被引的对象是论文，不是事件；两者没有映射关系。
**替代口径**：无。
**与原文差别**：本件不含任何「类关注度」分数。

### 4.5 不得外推的四件事

1. **不得把 20 行事件乘城市数**：它是一场展会的议程，不是城市活动样本。
2. **不得把媒体条数叫事件关注度**：媒体关注 ≠ 事件关注。
3. **不得把专利被引当事件热度**：被引是论文影响，与事件无关。
4. **不得用 policy 正文规模单独出分**：一维公式无法归一化成 0—100。

### 4.6 停用与重估条件

出现以下任一情况应重估：① 通用事件表入湖，且覆盖多主办方、多日期；② 事件级报道量或搜索指数可得；③ `dwd_policy_base` 的 theme 与 quote_policy 补齐真值；④ 甲方确认「媒体关注」可作为事件关注的代理并改名发布。

## 附录 C 可行性完整版

### C.1 为什么不用「媒体条数 / 事件数」构造关注度

这个比值看似合理：报道越多，关注度越高。但分子是报道条数，分母是事件数，而事件数只有 20 行、报道覆盖 1,668,414 条，两者根本不在同一总体。算出来的比值会是一个由分母荒谬驱动的巨大数，没有任何解释力。本件不做这种除法。

### C.2 为什么 policy 侧不能只留正文规模

正文规模确实可用（19,203 行有值），若只用它，可以算出一个「文本长度分」。但这个分与「关注度」没有语义关系：一份长政策可能无人问津，一份短通知可能全网转载。单维长度分只会给读者一个「看起来像分数」的假象，本件拒绝输出。

### C.3 最小可行的事件关注度需要什么

至少需要三张表：事件表（一场一行）、事件—报道关联表（哪条报道谈了哪场事件）、报道量表（每条报道的传播量或转载数）。有这三张表，才能算「每场事件的平均报道量」。当前 gkx 三张都没有，因此本件的结论不是「暂时算不准」，而是「结构上不可算」。
