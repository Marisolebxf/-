## 摘要

「技术市场潜力」要回答的是「这个领域的技术有没有在市场上流动」：转让多不多、许可活不活跃、有没有诉讼、质押融资多不多、开放许可有没有人用。它是一条**纯事件型**指标，五个维度全部来自专利的交易与法律事件，不来自专利本身。

实测的失败是结构性的，不是数量性的。转让表 `dwd_patent_transfer` 有 22,809 行、20,000 个互异 `pn`、22,522 条可解析的生效日，年份分布还相当漂亮（2021 年 326、2022 年 1,670、2023 年 3,770、2024 年 7,711、2025 年 5,799、2026 年 3,246），但它**只有 `pn` 与生效日**——没有 `patent_id`、没有 IPC、没有申请人。要把 20,000 件专利归到 IPC4，必须按 `pn` 回连 294 万行主表，而主表 `pn` 无索引，这条查询在本批直接 60 秒超时。换句话说，转让维的「年份」是可用的，「领域」是不可用的，而这条指标的核心恰恰是领域。

法律事件表更薄。`dwd_patent_legal` 20,000 行（覆盖 0.6803%），许可命中 56 条（0.28%）、开放许可 6 条（0.03%）、质押 104 条（0.52%）、诉讼或无效宣告 **0 条**。前三个维度的命中率是千分之几，落不到领域；诉讼维是整列为 0，它在任何领域都等于 0，不构成区分度。这四维再加上转让维，就是 calc-logic 的全部五维，五维**一个都不能出领域值**。

`dwd_market` 本来可以是兜底：它有 `market_name`、`market_share`、`measure_code`、`time_period`、`obs_status` 等字段。但实测 15 行里只有 `market_name` 有值（15 行），其余六列**全部为空**，而且 15 个 `market_name` 是 `LVA`、`POL`、`BEL`、`ITA`、`GBR` 这样的国家代码，与技术领域毫无关系。这张表连「全域市场活跃度」都支撑不了，更不用说 IPC4。

因此本文件**不产出任何领域分、不产出任何活跃度排名、不产出雷达图**。判「完全不支持」的理由与 QUALITY 一致：五维零可算，不是「某一维缺数据」，而是「五维都缺领域归属」。诉讼维的 0 命中尤其要小心——它不能被读成「这些领域没有诉讼风险」，只能被读成「这 2 万行里没有记录到诉讼事件」。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

要支撑的功能模块是：**科技信息展示系统 → 科技发展态势 → 科技创新评估 → 技术创新力指标展示 → 技术市场潜力分析**（需求原文 1.1.1.1.4.1.7.2.3）。

需求原文（第 907 行）是：「基于专利转让、许可、诉讼等市场活动数据，分析技术的市场潜力和商业化价值，用户可查看技术市场活跃度、技术成熟度、商业化前景等指标，评估技术的市场潜力。」这句话点名了三类数据（转让、许可、诉讼）与三个输出（活跃度、成熟度、商业化前景），calc-logic 把输入扩成五维（转让、许可、诉讼、质押、开放许可），输出仍是一个 0—100 的领域分。

| 页面任务 | 对指标的要求 |
|---|---|
| 五维雷达图 | 转让/许可/诉讼/质押/开放许可五率 |
| 领域活跃度排名 | 按 IPC4 出分，可横向比较 |
| 商业化前景 | 需要可解释的事件率，不是主观判断 |
| 趋势 | 需要事件按年分布 |
| 单件专利市场轨迹 | 需要 `patent_id` 级事件明细 |

### 1.2 为什么需要「技术市场潜力」这个指标

专利数量与质量都是「供给侧」，市场潜力是「需求侧」。一个领域申请了很多专利、质量也不错，但全部躺在库里没人转让、没人许可、没人质押，那它的商业化价值就没有被市场验证。需求把市场潜力单列一维，正是为了引入「市场是否买单」这个信号。

市场潜力也是三条 TINN 指标里唯一需要**交易与法律事件**的一条。这些事件不在专利主表里，而在转让表与法律事件表里；两张表都不以 `patent_id` 为主键，而是以 `pn` 为键。这个设计本身没错（专利号是外部世界的通用键），但它与主表的连接成本很高，尤其是在主表 294 万行、`pn` 无索引的情况下。

第三个理由是它必须能区分领域。如果只能算全域「转让 22,809 件、许可 56 件」，那对任何领域都没有区分度，也无法支撑「哪些领域更活跃」的页面任务。本文因此坚持「落不到 IPC4 就不出分」。

### 1.3 需求文档是否给出定义方法

**需求给了三类事件与三个输出，没给公式、没给权重、没给阈值。**

原文没有写：转让率的分母是申请量还是授权量、许可是否含开放许可、诉讼是否含无效宣告、质押是否含解押、开放许可的有效期怎么算、五维怎么归一、活跃度与成熟度如何从五个率映射出来。

calc-logic 补了五条：转让 = 转移专利数 / 专利数；许可 = 实施许可（不含开放许可）专利数 / 专利数；诉讼 = 涉及诉讼或无效宣告的专利数 / 专利数；质押 = 质押登记专利数 / 专利数；开放许可 = 声明开放许可的专利数 / 专利数；并写明「采用加权平均，五维」。这五条把分子分母写死了，本文照用。

仍未闭合的是：事件表的「一件专利多条事件」如何去重、`legal_events` 是自由文本还是结构化标签、转让表的 `pn` 与主表 `pn` 是否同格式。本文实测的答案是：`legal_events` 是自由文本（只能 LIKE 匹配）、转让表 `pn` 与主表同格式但主表无索引、事件去重只能按 `pn` 做。这三条决定了五维都只能做「全域计数」，不能做「领域率」。

**推测原意**：产品要的是一张「领域技术活跃度地图」，让决策者看到哪些领域的技术正在被交易、被许可、被资本接受。它服务领域判断，不服务单件专利估值。

**推测定义（本文拟用，但**未执行**）**：

> 对领域 $d$、专利集合 $P_d$，五维为
> $$
> T_d=\frac{\#\{p\in P_d: p\in\text{transfer}\}}{|P_d|},\quad
> L_d=\frac{\#\{p\in P_d: \text{许可}\}}{|P_d|},\quad
> X_d=\frac{\#\{p\in P_d: \text{诉讼}\}}{|P_d|}
>
$$
> $$
> P_d'=\frac{\#\{p\in P_d: \text{质押}\}}{|P_d|},\quad
> O_d=\frac{\#\{p\in P_d: \text{开放许可}\}}{|P_d|}
>
$$
> 五维极值归一后等权。本文**没有执行**，因为 $P_d$ 本身构建不出来：转让表没有 `patent_id`，法律事件表回连超时。

**为什么诉讼维 0 命中不能写成「无诉讼」**：0 命中只说明这 20,000 行文本里没有出现「诉讼」「无效宣告」字样，不说明全库没有诉讼。把 0 写成「无风险」是典型的「缺失当零」，本文明确禁止。

**为什么不用 `dwd_market` 兜底**：15 行、六列全空、`market_name` 是国家代码，与 IPC4 没有映射关系。用它算任何比率都是 0/0。

## 二、计算过程

本节从缺。五维的计算逻辑已在 §1.6 写出，但没有一维能取得分子：转让维缺领域键（只有 `pn`，回连主表超时）；许可、质押、开放许可三维的命中数分别是 56、104、6 条，无法拆到 IPC4；诉讼维 0 命中。没有分子，就没有比率；没有比率，就没有归一与合成。

本批没有用「全域率 × 领域申请量」的方式摊派：全域转让率 22,809/2,939,895 = 0.776% 乘到任何领域都得到同一个率，等于假设所有领域转让活跃度相同，这是把「没有数据」伪装成「数据均匀」。也没有用 `dwd_market` 的 15 行国家数据做时间序列：它的度量列全空，画不出任何曲线。失败证据见附录 B。

## 四、数据缺失情况

### 4.1 缺失清单

| 缺失项 | 现状 | 影响 | 修复建议 |
|---|---|---|---|
| 转让表领域键 | 只有 `pn`，无 `patent_id`/`ipc4` | 转让维落不到领域 | 增加 `patent_id`、`ipc4`、`apdt_year` 三列 |
| 转让表索引 | 主表 `pn` 无索引 | 回连即全表扫描、超时 | 建 `pn` 索引或允许按 `dwd_id` 分块 |
| 法律事件覆盖 | 20,000 行（0.68%） | 许可/质押/开放许可命中仅 6—104 条 | 扩到全量并结构化事件类型 |
| 法律事件结构 | 自由文本，需 LIKE | 无法精确分类、无法去重 | 预拆成布尔列（许可/质押/诉讼/开放许可） |
| 诉讼事件 | 0 条命中 | 诉讼维恒为 0 | 确认是「无事件」还是「未采集」 |
| 市场表 | 15 行，度量列全空 | 无法兜底 | 补度量值或确认废弃 |
| 市场表领域键 | 无 IPC4 / 产业链码 | 与专利无法关联 | 补领域键 |
| 金额字段 | 无 | 无法做交易额加权 | 补转让/质押金额 |

### 4.2 对结论的影响边界

上述缺失的后果不是「分数偏低」，而是「没有分数」。本文不产出任何领域市场潜力分，也不产出全域活跃度作为兜底；页面上这条卡片应显示「数据不足」。特别要防止两种误读：一是把诉讼 0 命中读成「无诉讼风险」，二是把转让表 2021—2026 的上升曲线读成「所有领域都在变活跃」——后者只是全域计数，没有领域分解。

### 4.3 不可外推的三件事

第一，不能把转让表的 22,809 行当成「全库转让率」。它的分母如果是 294 万行，转让率是 0.776%；但 20,000 个 `pn` 是否都在主表内、是否有重复转让，本文未能验证（回连超时）。这两个未知决定了 0.776% 只能当「数量级参考」。

第二，不能把法律事件的 56 条许可当成「许可率 0.28%」。这 56 条是 20,000 行文本里的命中，不是全库 294 万行的许可数；分母不同，率就不同。

第三，不能把 `dwd_market` 的 15 个国家代码当成「技术市场」。它们是专利局代码（LV 拉脱维亚、PL 波兰、BE 比利时等），与技术领域无关，也不能拼成时间序列。

## 五、王惠方法对照与选用建议

### 5.1 王惠原方法还原

王惠 calc-logic 的五维结构是：

| 二级 | 三级 | 口径 | 计算逻辑 | 源字段 |
|---|---|---|---|---|
| 技术市场潜力 | 转让 | 发生权利转移的专利占比 | 转移专利数 / 专利数 | `dwd_patent_transfer(pn, transfer_effective_date)` |
| 技术市场潜力 | 许可 | 实施许可（不含开放许可）的专利占比 | 许可专利数 / 专利数 | `dwd_patent_legal(legal_events)` |
| 技术市场潜力 | 诉讼 | 涉及诉讼或无效宣告的专利占比 | 诉讼专利数 / 专利数 | 同上 |
| 技术市场潜力 | 质押 | 发生质押登记的专利占比 | 质押专利数 / 专利数 | 同上 |
| 技术市场潜力 | 开放许可 | 声明开放许可的专利占比 | 开放许可专利数 / 专利数 | 同上 |

并写明「按 IPC 前 4 位入集技术领域」「不另建许可/诉讼/质押专表」。

### 5.2 新方法概述

本文没有提出新方法，只做了三件事：把五维的命中数与覆盖率逐一实测、把三条回连超时记录为失败证据、把 `dwd_market` 的 15 行数据完整 dump 出来证明它不能兜底。这三件事构成了「不可算」的可复核证据链。

### 5.4 选用建议与理由

**建议：本指标暂不发布，页面显示「数据不足」。** 理由有三：其一，五维全部落不到 IPC4，任何领域分都是编的；其二，转让表虽有 2 万个 `pn` 与漂亮的年份曲线，但没有领域键，这条曲线只能当「全域转让活动」，不能当「领域市场潜力」；其三，诉讼维 0 命中会让任何领域得分里带一个虚假的「零风险」信号。

## 附录 C　技术市场潜力类似指标权威构建方法可行性报告（完整版）

### C.1 报告目的与范围

本附录回答：在只有 22,809 行转让记录、20,000 行法律事件、15 行市场表的条件下，「五维领域市场潜力」能否以任何近似方式落地。范围限定在事件型指标，不扩展到交易金额估值。

### C.2 需求语义锚定

需求用的词是「市场活动」与「商业化价值」。市场活动的可观测代理是转让、许可、诉讼、质押；商业化价值则需要金额或估值，库内没有。因此本文只讨论前者，不假装能算后者。

### C.3 权威与学术构建方法谱系

#### C.3.1 方法族 A：专利交易事件率

USPTO 的 Assignment 数据库、EPO 的 Register 都提供转让与许可登记，标准做法是「登记数 / 专利存量」。它们的共同前提是登记记录带专利号或专利 ID，且能与专利主表连接。本库的转让表带 `pn` 但不带 `patent_id`，主表 `pn` 无索引，连接成本高到超时。

#### C.3.2 方法族 B：专利运营指数

各地知识产权运营平台用交易额、质押融资额构造指数。本库无金额字段，方法族 B 不可行。

#### C.3.3 方法族 C：诉讼强度

Lex Machina、Patexia 用诉讼案件数除以专利数。本库 `legal_events` 里诉讼命中 0 条，方法族 C 没有分子。

#### C.3.4 方法族 D：成熟度曲线

Gartner 类模型靠专家判断，不可核验，也不属事件型指标，本文不采用。

### C.4 数据可行性详细分析

#### C.4.1 转让

22,809 行、20,000 个 `pn`、22,522 条日期可解析、年份分布 2021—2026 连续上升。这是五维里唯一「有像样时间序列」的一维，但缺 `patent_id` 与 IPC，落不到领域。

#### C.4.2 许可

56 条命中（0.28%），且 `legal_events` 是自由文本，「许可」与「开放许可」还会互相包含，去重困难。

#### C.4.3 诉讼

0 条命中。这可能是「库内确实没有诉讼记录」，也可能是「采集未覆盖诉讼」，两种解释的后果完全不同，需要供应方确认。

#### C.4.4 质押与开放许可

104 条与 6 条命中，覆盖率 0.52% 与 0.03%，都落不到 IPC4。

#### C.4.5 市场表

15 行、六列全空、`market_name` 是国家代码。它连「全域市场活跃度」都支撑不了。

#### C.4.6 方法—数据对照矩阵

| 方法 | 需要的输入 | 库内状态 | 可行性 |
|---|---|---|---|
| A 事件率 | 事件 + 专利 ID + 领域 | 有事件、缺 ID 与领域 | 不可行 |
| B 运营指数 | 交易额/质押额 | 无金额 | 不可行 |

| D 成熟度曲线 | 专家判断 | 不可核验 | 不采用 |

### C.5 推荐构建方案（工程可执行）

1. 转让表增加 `patent_id`、`ipc4`、`apdt_year` 三列，或给主表 `pn` 建索引并允许分块；
2. 法律事件预拆成四个布尔列（许可、质押、诉讼、开放许可），并扩到全量；
3. 确认诉讼 0 命中是「无事件」还是「未采集」；
4. 市场表补度量值与领域键，否则确认废弃；
5. 上述完成后按 §1.6 公式直接跑，口径不变。

### C.6 风险与残余不确定性

- 转让表 `pn` 与主表是否同格式未验证（回连超时）；
- 法律事件自由文本的 LIKE 匹配会漏掉同义表述（如「让与」「权利转移」）；

### C.7 可行性总判（完整版结论）

五维全部落不到 IPC4，判「完全不支持」。修复的关键是「领域键」而不是「行数」：转让表有 2 万行但没有 IPC，加一列 `ipc4` 比补十万行更有效。
