## 摘要

重要性等级是「关注度 + 影响力」的合成结果：0.5×关注度 + 0.5×影响力，再按 P70/P30 切高/中/低。它本身只是一次加权与两次切分，难度不在算法，而在输入。

gkx 的 `dwd_event` 只有 20 行、15 列，全部是 2026-05-13/14 两天的医药论坛公告；字段只有 event_name/organizer/start_date/end_date/event_url。没有 chain_id、没有事件类型、没有关注度、没有影响力、没有报道量、没有媒体源、没有事件状态。全库 280 张表里带 event 的只有 `dwd_event` 与 `dwd_merger_acquisition_events_party_info`（并购当事方），不存在事件簇表或事件结果面。

按本批规则，没有事件流就判完全不支持，只写需求，不许用新闻或政策串伪事件。旧稿用 `dwd_policy_base` 20,000 条政策当事件代理，本件明确拒绝：政策没有发生时间线、没有传播过程、没有事件状态，不是事件。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在科创事件 GIS 图层与三档筛选器上。GIS 用颜色/大小表示等级，筛选器用高/中/低过滤事件，排序用等级优先展示高影响力事件。它不展示分数，只展示标签，因此标签必须来自可信的事件输入。

当前 gkx 没有事件流，只有会议公告。会议公告没有「发生—发酵—消退」的过程，也没有报道量与媒体层级，无法支撑「实时更新等级」这条需求。

### 1.2 为什么需要这个指标

事件是科技态势里最快的一层：融资、并购、新品、政策、专利纠纷都会先以事件形式出现。没有事件流，态势页只能展示新闻列表，无法做「哪些事件重要」的排序与筛选。

重要性等级是事件产品的核心交互：用户不会读 0—100 分，只会按高/中/低筛选。等级错了，整页的颜色、大小、排序都错。

### 1.3 需求文档是否给出定义方法

需求给了行为（自动算级、三档筛选、优先展示、实时更新），没有给算法：没说权重、没说阈值、没说事件怎么定义、没说并列怎么处理。旧稿用 0.5/0.5 + P70/P30，是项目内人工口径，不是甲方确认值。

更关键的是「事件」本身没有定义。会议公告算不算事件？政策发布算不算？报道算不算？没有事件簇 id，这些问题无法回答。

### 1.4 权威机构方法可行性

事件分级在舆情/政策监测里通常用「事件聚类 + 多指标打分 + 分位切档」。前提是有事件簇与报道明细；本件两者都没有。

另一族是规则矩阵（层级×关注度），不依赖连续分数，但仍需要事件与层级字段。本件同样不具备。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A. 复合分 + 分位 | 旧稿 | 0.5/0.5 + P70/P30 | 不可行（无输入） |
| B. 绝对阈值 | 政策分级 | 固定分段 | 不可行（无输入） |
| C. 规则矩阵 | 舆情监测 | 层级×关注度 | 不可行（无字段） |
| D. 聚类分档 | K-means | 自然断点 | 不可行（无事件簇） |

### 1.5 引用来源

来源 1：`code/_snapshots21/event21_probe_20261022.json`（dwd_event 20 行全量）。

来源 2：`_work_gkx21/GKX_INVENTORY.json`（280 张表，带 event 的只有 2 张）。

来源 3：旧稿 `M_INNOV_DS_01_EVENTS_003.md`（政策代理口径，本件拒绝）。

### 1.6 推测原意与依赖维度

推测原意是给事件一个粗粒度重要性标签，支撑地图视觉编码与筛选。按这个原意，最小输入是「事件 id + 关注度 + 影响力 + 链 + 状态」，本件一个都没有。

依赖维度：D1 事件流（无）、D2 关注度（无）、D3 影响力（无）、D4 链归属（无）、D5 状态（无）。五层全缺，所以判完全不支持，而不是部分支持。

## 三、数据支撑情况

本件按「事件流 / 事件 id / 链归属 / 关注度 / 影响力 / 状态」六个维度核对，六项全部缺失或不成立。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 事件底表 | 有表但不是事件流 | 20 行会议公告，2 天 | 接入新闻聚类/招标/融资/专利/政策五源 |
| 事件 id | 缺失 | dwd_id 是行号 | 建 event_cluster 主键 |
| 链归属 | 缺失 | 无 chain_id | 按事件标题/企业打链标签 |
| 关注度 | 缺失 | 无报道量/搜索量 | 接传播数据或按报道计数 |
| 影响力 | 缺失 | 无媒体层级 | 建 dim_media_tier |
| 事件状态 | 缺失 | 无 status/updated_at | 建流处理状态机 |

事件表的 20 行全部来自 `mm.reed-sinopharm.com`，主办方是国药励展等 19 个机构，日期只有 2026-05-13/14。这是会议名录，不是事件流；它甚至没有「事件发生」的语义，只有「会议举办」。

没有事件 id 就无法去重，没有链归属就无法按链筛选，没有关注度/影响力就无法打分，没有状态就无法实时更新。四个「无法」叠加，任何等级都是编的。

修复路径不是补一张表，而是建一套事件接入：新闻聚类、招标、融资、专利、政策五源，聚成事件簇，再建媒体层级与状态机。这是一条数据工程项目，不是本件能单方面完成的。

### 3.9 缺口优先级

缺口不是同等重要。本件按「是否阻断指标成立」把缺口分三档：阻断（指标算不出）、扭曲（算得出但结论会反）、披露（不影响本期结论但影响外推）。优先级如下。

| 优先级 | 缺口 | 阻断/扭曲/披露 | 处理 |
|---|---|---|---|
| P0 | 无事件流 | 阻断 | 接五源 |
| P0 | 无事件 id | 阻断 | 建簇主键 |
| P0 | 无关注度/影响力 | 阻断 | 接传播数据 |
| P1 | 无链归属 | 扭曲 | 打链标签 |
| P1 | 无状态 | 扭曲 | 建状态机 |
| P2 | 权重未定 | 披露 | 甲方裁定 |

前三个 P0 是串联的：没有事件流就没有事件 id，没有事件 id 就无法聚合报道，没有报道就没有关注度/影响力。修一个不够，必须整条链路一起建。

链归属与状态是 P1：它们不影响「有没有事件」，但影响「能不能按链筛选、能不能实时更新」。需求明确要求这两项，所以不能省略。

## 四、数据缺失情况

本件的缺失是整条链路，不是单字段。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 事件流 | 无法合成等级 | 不产出等级 | 接入事件源 |
| 关注度 | 输入缺一 | 不计算 | 接报道量/搜索指数 |
| 影响力 | 输入缺一 | 不计算 | 建媒体层级 |
| 事件状态 | 无法实时更新 | 不做实时 | 建状态机 |
| 链归属 | 无法按链筛选 | 不做筛选 | 补 chain_id |

最需要警惕的是「用新闻串事件」。108,052 条资讯看起来很多，但没有 event_id/簇 id；按标题相似度聚类可以得到 6,406 簇，但那是模型产物，阈值一变簇数与等级全变，且没有人工标注集做准召评估。用未验收的簇冒充事件，会把「同题转载」与「同一事件」混为一谈。

政策代理同样不成立：政策没有发生时间线、没有传播过程、没有事件状态；旧稿用主题/引用/区域字段合成关注度与影响力，得到的是「政策文件的行政位阶」，不是「事件影响」。本件明确拒绝。

### 4.9 处置原则

对缺失的处置遵循三条：不补 0、不静默填充、不把模型产物当数据真值。能算的算，不能算的输出 null 并写原因；任何代理都必须在字段名与页面文案上标注「代理」。

第二条是不做「看起来完整」的补齐。缺失年份不插值、缺失城市不摊派、缺失分项不按均值填；这些操作会让下游误以为数据齐全，比 null 更危险。

第三条是可复现优先。所有外部输入都落快照，快照带来源、时间、行数；脚本只读快照，重跑不依赖网络。这样即使源库变化，历史结论仍可复算。

## 附录 G 口径问答

**问：会议公告为什么不算事件？**

答：会议公告只有「举办」信息，没有发生—发酵—消退过程，没有报道量、媒体层级、状态；它是名录，不是事件流。

**问：能不能用新闻聚类造事件？**

答：本批规则禁止。没有标注集验收的簇是模型产物，阈值一变簇数与等级全变；用它算等级等于把模型误差当数据真值。

**问：旧稿用政策代理，为什么本件不用？**

答：政策没有事件时间线与传播过程，rank 字段在 gkx 也不存在；用它算关注度/影响力，得到的是行政位阶，不是事件影响。

**问：需要多少行才能算？**

答：至少覆盖一个完整事件生命周期，且每个事件有 ≥1 条报道、≥1 个媒体层级。行数不是核心，结构才是。

**问：接入哪五源？**

答：新闻、招标、融资、专利、政策。五源各有事件语义，聚成簇后才能做统一等级。

**问：什么时候能升级？**

答：事件簇 + 媒体层级 + 状态机三件齐备，且通过 500 对标注验收，才可能从完全不支持升到部分支持。

## 附录 N 开发交接说明

**问：能不能先接新闻，跑一版等级给业务看？**

答：不能。新闻没有 event_id，跑出来的「等级」是单条报道的媒体分，不是事件等级；业务一旦拿去筛选，会把「转载多」当「事件重要」。

**问：事件簇能不能用规则（同标题/同公司+同周）先做？**

答：可以做基线，但必须人工验收并标 `cluster_confidence`。未验收的规则簇只能进沙箱，不能进正式表。

**问：媒体层级没有官方表，怎么办？**

答：先按主办单位/域名做四级初筛，再人工复核 206 源；层级表要版本化，历史分数才能复现。

**问：要多少事件才能上线？**

答：不是行数问题，是覆盖问题。至少覆盖 3 个事件类型、每个类型 ≥50 个事件、每个事件 ≥1 条报道，才能做分位切档。

**问：旧稿的 0.5/0.5 与 P70/P30 能直接用吗？**

答：可以作为初始参数，但要在新事件流上重跑分布；P70/P30 是样本分位，样本变了分位就变，不能硬编码。

**问：什么时候能从「完全不支持」升级？**

答：事件主表 + 报道归属 + 媒体层级三表齐备，且通过附录 M 的八项验收，才可重评为部分支持。
