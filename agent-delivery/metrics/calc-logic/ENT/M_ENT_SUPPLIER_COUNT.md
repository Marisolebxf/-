## 摘要

「供应商数量」是本批五件里定义最干净、也最没有数据的一件。定义只有一行：数出某企业的直接供应商去重个数，边类型 `relation_type='supplier'`。它不涉及权重、不涉及归一化、不涉及年度窗口——只要有一张「企业 → 供应商」的边表，一个 `COUNT(DISTINCT)` 就能出数。

问题就在这张边表。gkx 280 张表逐表看过，没有供应关系表；6,312 列逐列扫过词根，`supply`、`vendor`、`采购`、`供应`、`上游`、`下游` 六个词根 0 列，`supplier` 只有 3 列，且三列都是 `dwd_bid_base_out` 及其两份备份里的 `supplier_qualification_criteria`——招标公告正文中的「供应商资格条件」一段文字，不是关系。

四张候选边面都试过了。投资边 46,967 行，方向是「投资方 → 被投方」，没有交易字段；股权边 400,286 行，与投资边只有 174 对重合，说明两表各记一类资本关系；母子公司边 178,900 行，是控制关系；招投标面 39,962 条公告 + 39,520 条中标候选人，只有中标方 `org_id`，招标方是名称字符串。四者都组不出「甲企业向乙企业供货」。

旧机开发库侧确实有一张同名表 `gkxlumenx_dwd.enterprise_supply_chain`，9 列，结构完全对得上（`org_id`、`related_org_id`、`relation_type`、`is_core_supplier`、`risk_level`），但行数是 0。表结构在、数据不在，`COUNT` 出来恒为 0——这不是「供应商数量为 0」，是「没有可数的记录」。

结论：完全不支持。三组否定性探针（词根扫描、链上节点无供应商字段、替代面语义差异实测）全部完成，证据落在产物 `probes.p1`—`probes.p6`。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业分析 → 企业供应链关系分析 → 供应商节点数**。页面形态是企业画像卡上的一个数，点开是供应链关系图：中心是企业，外圈是供应商节点。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业分析 → 供应链关系分析 |
| 页面载体 | 画像卡 + 关系图 |
| 输出形态 | 企业 → 供应商去重数 |
| 更新频率 | 周 |
| 粒度 | 企业（org_id） |

### 1.2 为什么需要这个指标

供应商数量是供应链分析的入口数。一家企业有 300 个供应商，与只有 3 个供应商，风险结构完全不同：前者要管集中度，后者要管单点依赖。

第二个用途是链上定位。供应链关系图如果只有节点没有边，就退化成企业名录；供应商数量是边的密度指标，决定了图能不能画出来。

第三个用途是风险传导。断链风险要沿边传播，没有边，风险只能停在单家企业，传不到上下游。

### 1.3 需求文档是否给出定义方法

**给了，而且把「不要什么」写得很清楚。** 正本的口径：

> COUNT(DISTINCT related_org_id) WHERE org_id = :org_id AND relation_type = 'supplier'
> Q017「直接一级」= 边自身即 1-hop。DWD / ODS 都没有 relation_level，不筛、不补列。
> 禁止读 is_core_supplier（那是 CORE 的产出）。禁止读 relation_strength（关系强度是另一条 MODEL）。

三句话对应三条边界：① 只数一跳，不做多跳展开；② 不拿 `is_core_supplier` 或 `relation_strength` 当过滤条件；③ 只国内，不造 `enterprise_forg_supply_chain`。

本件对这三条边界没有异议，问题在于它们全都建立在「边表存在」这个前提上。正本自己也写了「ODS 无供应关系表、DWD 169 行 mock」，并给了处置原则：「只记灌数 / 不升 D3 D4」。本件实测比正本记录的更差一步：DWD 同名表 0 行，连 mock 都没有。

### 1.4 类似指标权威机构构建方法可行性

「供应商数量」在业界有四种构建路径，差别在边的来源：

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 企业自报 | 上市公司年报「前五名供应商」 | 年报文本抽取 | 低：只覆盖上市，且只有前五 |
| B 招投标反推 | 政府采购/公共资源交易 | 中标记录推供货关系 | 中：有中标方，缺采购方 |
| C 发票/税务 | 金税系统进项发票 | 采购发票定向 | 高：但属税务数据，不入本库 |
| D 商业图谱 | 企查查/天眼查供应链 | 多源融合 + 推断 | 中：推断逻辑不公开 |

A 族本库没有：`dwd_org_annual_financial_info` 27 列里没有「前五名供应商」字段，只有汇总财务数。B 族本库有半边：中标方可识别，采购方不可识别（详见 §3.4）。C 族是最贴近的，但发票数据不在 gkx，也不在开发库。D 族要求外部采购。

四条路径在本库都走不通，这是判「完全不支持」的行业侧依据：不是我们不会算，是这条指标在业内本来就依赖「交易级数据」，而本库是「登记级 + 资本级」数据。

## 二、计算过程（为什么不成立）

正本公式只有一行：`supplier_count(i) = COUNT(DISTINCT related_org_id) WHERE org_id=i AND relation_type='supplier'`。

要跑通它，需要三样东西：① 一张以 `(org_id, related_org_id, relation_type)` 为行的边表；② `relation_type` 取值域里有 `'supplier'`；③ 边表有行。本件逐项核过：① gkx 0 张；② 旧机同名空表的列里有 `relation_type`，但 0 行，取值域为空；③ 0 行。

三者缺一，`COUNT` 都返回 0。而「0 个供应商」与「无法计数」是两件事：前者是结论，后者是无结论。本件拒绝把 0 当结论输出，所以不产出指标值，只产出证据。

替代路径也走不通：投资边与股权边是资本关系（方向、字段、总体三重不符），招投标面缺采购方 `org_id`。逐条实测在 §3.4。

表名扫描同时覆盖了三个「交易类」词根，结果同样是 0 张：

| 词根 | 表数 | 说明 |
|---|---:|---|
| order | 0 | 无订单表 |
| contract | 0 | 无合同表 |
| trade | 0 | 无交易表 |
| purchas | 2 | `dwd_bid_purchase_agency_out` 及其备份——招标代理机构名录，不是采购关系 |
| stage / segment | 0 | 无阶段/分层表 |

「订单、合同、交易」三类表名一张都没有，这一条比列名扫描更硬：即便某张表的列名起得不像供应商，只要它记的是交易，表名通常会带 order/contract/trade。三类全空，说明库里没有交易级事实表。

活库复核（`information_schema`，2026-10-23）：

| 检查 | gkx 侧结果 |
|---|---|
| `table_name LIKE '%supply%'` | 0 张 |
| `column_name LIKE '%supplier%'` | 3 列（同上） |
| `column_name IN ('relation_type','relation_strength','is_core_supplier','risk_level')` | 0 列 |

第三行尤其关键：`relation_type` 这个字段在 gkx 全库都不存在。旧机开发库的同名表有这四列，但那是开发库自建表，不是 gkx 的表。

旧机开发库复核（G8 的另一侧）：

| 检查 | 结果 |
|---|---|
| 表名含 supply | 3 张（其中 2 张在演示库，按铁律禁引、不参与结论） |
| `gkxlumenx_dwd.enterprise_supply_chain` 行数 | **0** |
| 该表列 | id, org_id, related_org_id, relation_type, relation_strength, is_core_supplier, risk_level, create_time, update_time |

九列结构与正本完全对得上，一行数据都没有。这是第二组否定性证据：不是「表没建」，是「表建了但没灌数」。按正本「只记灌数 / 不升 D3 D4」的处置，本件不把空表当支持。

### 3.4 探针三：替代面语义差异实测

三条候选边面逐条实测：

| 面 | 规模 | 方向 | 能表达什么 | 不能表达什么 |
|---|---|---|---|---|
| `dwd_org_invest_info` | 46,967 行 / 19,611 投资方 / 33,968 被投 | 投资方 → 被投方 | 出资关系 | 供货关系、采购金额、物料 |
| `dwd_org_shareholder_info` | 400,286 行 / 70,034 关系对 | 股东 → 被持股 | 持股关系 | 供货关系 |
| `dwd_org_subsidiary_info` | 178,900 行 / 21,909 母公司 / 150,211 子公司 | 母公司 → 子公司 | 控制关系（合并范围） | 供货关系、采购额 |
| 招投标面 | 39,962 公告 / 39,520 中标候选 / 12,528 中标方 | 中标方 → 项目 | 中标记录 | 采购方 org_id 缺失 |

投资边与股权边的重合只有 174 对，占投资边 46,967 对的 0.37%。这个数字说明两表不是同一批关系的两个副本，而是各记一类资本关系：投资边记「对外投资」，股权边记「股东构成」。两者都不是交易关系。

一个常被提出的替代方案是「用投资边做资金流向代理」。本件实测后明确拒绝，理由四条：

第一，方向相反。投资边是「投资方 → 被投方」，供应边是「供应商 → 采购方」。若照代理口径，A 投资 B 会被读成「B 向 A 供货」，方向完全颠倒。母子公司边同理：母公司 → 子公司是控制关系，若当供应边，集团会变成「最大的采购方」。

第二，字段不符。投资表 18 列里没有交易金额、采购品类、订单号、收货确认，只有出资额与出资比例。

第三，总体不同。投资边覆盖 19,611 家投资方、33,968 家被投企业；供应关系的总体应是「有采购行为的企业」，两者不是同一批企业。被投企业 33,968 家占底册 189,116 家的 17.96%，而供应关系的覆盖面理论上应远大于此。

第四，即便做代理也必须降档并改名。若某下游只需要「资金流向」这个粗信号，可以用投资边单独出一个指标，但它不能叫「供应商数量」，也不能挂在供应链关系分析下。

招投标面看似最接近，实测也走不通：`dwd_bid_base_out` 的招标方只有名称字符串，没有 `org_id`；`dwd_bid_win_candidate_out` 只有中标方标识。缺了采购方主键，就构不成 `(采购方, 供应商)` 对，只能得到「某企业中标过多少项目」，那是另一个指标。

### 3.5 与同族指标的关系

同批的 `M_ENT_CORE_SUPPLIER_COUNT` 与本件共用同一张边表，同样判完全不支持，但它的否定证据更细：核心供应商还需要「本企 → 该供应商的投资金额」这一层，本件已在那边做了代理退化实测。

`M_ENT_SUPPLY_CHAIN_RISK` 的四个维度里也有两个依赖供应链边（前五大客户、链上关联企业风险），同样不可得，但它的第四维（绩效波动）可真算，所以那一件判部分支持，与本件档位不同。三件的档位差异都写在各自文档的 §0.1，读者可以交叉核对。

### 4.1 缺口清单

| 编号 | 缺口 | 性质 | 可否补 |
|---|---|---|---|
| G1 | 无供应关系边表（gkx） | 结构性 | 需新建并灌数 |

| G5 | 无交易金额/品类/订单号 | 结构性 | 需交易级数据源 |
| G6 | 无供应商主体标识 | 结构性 | 随 G1 |

### 4.2 逐条影响

G1—G3 是同一个根：边表不存在。三者必须一起补，补一张缺字段的表没有意义。

G4 影响的是「用招投标反推供应关系」这条备用路径。补上采购方 `org_id` 后，可以从 39,962 条公告里反推出部分「采购方 → 中标方」对，作为供应关系的弱代理。但这条路径只覆盖政府采购，企业间采购仍无解。

G5 决定「核心供应商」能不能算。没有交易金额，即便有边，也只能数个数，不能排 TOP5。

G6 决定边能不能落到企业。没有供应商主体标识，边只能停在名称层，无法与 `org_id` 对齐。

### 4.3 明确不做什么（禁止的替代）

- **不把投资边当供应边。** 方向、字段、总体三重不符。
- **不把股权边当供应边。** 同上。
- **不把中标记录当供货记录。** 缺采购方主键。
- **不把空表的 0 当指标值。** 0 是「没数」，不是「零个供应商」。
- **不用 `is_core_supplier` / `relation_strength` 造边。** 那两列只存在于空表。

### 4.4 若甲方补齐后的口径升级路径

第一步，建边表并灌数。结构可以直接用旧机空表的九列（`org_id, related_org_id, relation_type, relation_strength, is_core_supplier, risk_level, create_time, update_time, id`），关键是灌数。

第二步，补 `relation_type` 的取值域，至少要有 `supplier` 与 `customer` 两类。

第三步，补交易级字段（金额、品类、期次），才能支撑核心供应商的 TOP5 排序。

三步完成后，本件可从「完全不支持」直接升到「完全转换支持」；若同时落 `enterprise_supply_summary`，可到「完全直接支持」。
