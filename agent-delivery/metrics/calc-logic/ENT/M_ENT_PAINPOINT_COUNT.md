## 摘要

「企业痛点数量」数的是企业遇到了多少件麻烦事。原设计把它定义成一个诊断结果：`enterprise_diagnosis` 表里的 `pain_point` 与 `severity`。这张表不存在，所以本件退回到原始风险流水，逐企业计数。

实测六类风险合计 699,003 条：被执行 550,334 条（占 78.73%）、失信 76,035 条、行政处罚 65,997 条、经营异常 5,862 条、税务处罚 528 条、严重违法 247 条。覆盖 73,026 个「企业×类型」对，涉及 35,000 家以上主体。

头部企业的痛点数量非常集中：恒大地产 6,410 条（失信 570 + 被执行 5,840）、深圳导氮教育 5,986 条、阿卡索 3,888 条。前 50 名里大量是地产、教育、保险分支——这三类恰好是近年风险高发行业，数字与行业直觉一致。

结论是「部分支持」：合规侧的痛点可以逐企业数出来，经营侧（现金流、人才流失、供应链）与舆情侧完全没有载体。把它叫「企业痛点数量」会让人以为覆盖全面，所以正文必须把「只覆盖合规侧」写在最前面。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业服务 → 企业诊断 → 风险痛点**。页面形态是企业画像卡上的一个数，点开可看六类明细；另有一个头部企业痛点榜。

它是一个计数指标，不是评分指标。计数意味着「一条记录算一次」，不区分严重度——这是本件最容易被质疑的口径，处置方式是在产物里写 `type_weights_note`，说明未加权。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业服务 → 企业诊断 → 风险痛点 |
| 页面载体 | 画像卡 + 头部榜单 |
| 输出形态 | 企业 → 痛点总数 + 分类型条数 |
| 更新频率 | 建议月度 |
| 粒度 | 企业（org_id） |

### 1.2 为什么需要这个指标

痛点数量是风险筛查的第一道筛子。一家企业如果有 6,000 条被执行记录，不需要看任何评分，直接就该进重点名单。计数指标的价值在于「不需要解释」——它不依赖权重、不依赖模型。

第二个用途是分层。按痛点数量分档，可以快速把企业分成「无风险、轻度、中度、重度」四层，每层的处置策略不同。

第三个用途是对账。法院、市场监管、税务各有自己的记录，本件把它们合到一个 org_id 下。合并后的数字如果与某一方的数字差异很大，说明主键归并出了问题。

### 1.3 需求文档是否给出定义方法

**需求文档给了定义，但依赖一张不存在的诊断表。** calc-logic 写的是：

> 企业痛点数量：统计企业在经营过程中遇到的痛点数量，含合规、经营、舆情三类。

三类里，合规侧有原始表，经营侧与舆情侧没有。本件只做了合规侧，并在产物 `proxy_deviation` 里写明「只有合规/司法/行政类痛点，不含经营痛点与舆情痛点」。这不是选择性忽略，是能力边界。

### 1.4 类似指标权威机构构建方法可行性

企业风险计数在业界有几套口径：法院的失信/被执行、市场监管的行政处罚与经营异常、税务的欠税公告、以及商业数据库的「风险事件」聚合。它们的共同点是「按事件计数」，差异在覆盖范围。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 官方风险流水 | 最高法/市场监管/税务 | 按事件逐条记录 | 本件采用，原始可回溯 | 高（本件采用） |
| B 商业风险聚合 | 企查查/天眼查 | 多源合并 + 评分 | 评分逻辑不公开 | 中（可对照） |
| C 信用评级 | 央行/评级机构 | 财务 + 合规综合 | 需财务数据 | 低 |
| D 舆情风险 | 媒体监测 | 情感 + 事件抽取 | 需 NLP 管道 | 低（本批无） |

**A 族是本件采用的方法**：六张表都是官方口径的原始流水，每条记录可回溯到具体日期与文号。缺点是只有「已发生」的事件，没有「潜在」风险。

**B 族（商业聚合）**的数字通常比本件大，因为它们把新闻、招聘、股权冻结也算进去。本件不做这个合并，因为合并后无法拆分。

**D 族（舆情）**需要 NLP 管道，本批没有。这一块正是「经营痛点」的主要来源，缺了它，痛点体系就只有一半。

## 二、计算过程

### 2.1 总体思路与数据流

六张表各按 org_id 分组计数，再按企业合并。合并键是 org_id，不是企业名——企业名有重名与变更，org_id 是主键。

每张表先在自己的范围内去重计数，再求和。不能先把六张表 union 再去重，因为同一条记录不会跨表重复，union 只会放大数据量。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 分表计数 | 六张风险表 | GROUP BY org_id | 六份计数 |
| 合并 | 六份计数 | FULL JOIN org_id | 企业总数 |
| 排序 | 企业总数 | DESC | 头部榜 |
| 汇总 | 六表 | SUM(records) | 699,003 |

### 2.2 口径定义与公式

`painpoint_count_i = Σ_t n_{i,t}`，其中 `n_{i,t}` 是企业 i 在类型 t 下的记录条数。六类等权，一条行政处罚与一条被执行都记 1。

`totals.records_all_types = 699,003`，`totals.org_type_pairs = 73,026`。后者是「企业×类型」的去重对数，不是企业数——一家企业可能同时出现在三类里。

为什么不等权之外再加权：加权需要严重度权重表，甲方没给。自行设定会让数字不可复现，所以本件保持等权，并在 `type_weights_note` 里写明「若甲方要按严重度加权，需给出权重表」。

| 类型 | 条数 | 企业数 | 占比 |
|---|---|---|---|
| 被执行人 | 550,334 | 35,041 | 78.73% |
| 失信被执行 | 76,035 | 13,823 | 10.88% |
| 行政处罚 | 65,997 | 19,174 | 9.44% |
| 经营异常 | 5,862 | 4,435 | 0.84% |
| 税务处罚 | 528 | 336 | 0.08% |
| 严重违法 | 247 | 217 | 0.04% |

### 2.3 累计口径与年度切分的区别

本件数的是「截至抓取时点的累计条数」，不是「今年新增」。两者差别很大：一家企业十年前有 5,000 条被执行，今年一条没有，累计口径仍然把它排在头部。

为什么不做年度切分：六张表都带发生日期，但字段名与格式不统一（有的叫 `fbsj`，有的叫 `case_date`），统一解析会引入新的口径问题。本件选择不做，并在 `base_years_note` 里写明「若要做年增量需另建按年聚合」。

这个选择会让「痛点数量」更像一个「历史包袱」指标，而不是「当前风险」指标。页面文案应避免「近期风险」这类表述。

| 口径 | 含义 | 本件是否采用 |
|---|---|---|
| 累计条数 | 截至抓取时点全部记录 | 是 |
| 年度新增 | 按发生年切分 | 否 |
| 在办案件 | 仅未结案 | 否（无状态字段） |

### 2.4 计算步骤（脚本逐步实现）

1）读六张表的计数快照；2）按 org_id 合并；3）算总数与分类型；4）取头部 50；5）算覆盖主体数；6）写 `head_sample_sizes` 记录截断。

第 6 步的截断声明很关键：逐企业明细不是全量，每张表只取了前 3,000—5,000 主体。全库记录数与涉及企业数是真值，逐企业分布是截断的，两者不能混用。

| 步骤 | 实现 | 校验 |
|---|---|---|
| 分表 | COUNT BY org_id | 六份 |
| 合并 | outer join | 73,026 对 |
| 头部 | ORDER BY count DESC | 前 50 |
| 截断 | LIMIT 3000—5000 | 已声明 |

## 三、数据支撑情况

### 3.1 依赖表与可得性

本件依赖六张风险表。六张都在、都有数，这是它能算出来的根据。但六张表都只覆盖「已发生的合规/司法事件」，不覆盖经营困难。

逐企业明细的限制来自查询时限：每张表只取前 3,000—5,000 主体，避免一次拉全量把连接打满。全库汇总数与逐企业分布因此是两种精度，不能混用。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 经营异常 | 可用 | 5,862 条 / 4,435 家 | 无 |
| 严重违法 | 可用 | 247 条 / 217 家 | 无 |
| 行政处罚 | 可用 | 65,997 条 / 19,174 家 | 无 |
| 失信/被执行 | 可用 | 626,369 条 | 无 |
| 税务处罚 | 可用 | 528 条 / 336 家 | 无 |
| 经营痛点 | 不可用 | 无载体 | 需调研或 NLP |
| 舆情痛点 | 不可用 | 无载体 | 需 NLP 管道 |

### 3.2 四判定落表

四判定里，结构与数据都过（六张表齐、有真数），但「痛点」的定义不过：需求说三类，本件只能做一类。这是口径覆盖问题，不是数据量问题。

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 无诊断结果面 |
| 表数据直接支持（开发库+三方库） | 否 | 同上 |
| 依赖表结构支持（开发库/三方库） | 是 | 六张风险表齐 |
| 依赖表数据支持（开发库/三方库） | 是（全库） | 699,003 条 |
| 聚合结论 | 部分支持 | 仅覆盖合规侧 |

### 3.3 数据量、覆盖与代表性

覆盖上，73,026 个企业×类型对分布在 35,000 家以上主体，相对 189,116 家底册约 18.5%。也就是说八成企业没有任何合规风险记录——这是正常的，不是数据缺失。

代表性上，被执行与失信两类占了 89.6% 的记录，其余四类合计只有一成。这个分布决定了「痛点数量」实际上主要是「被执行数量」，排名几乎由司法记录驱动。

### 3.4 结构支持判定

结构侧够用：六张表结构清晰、主键可归并、计数直接。

局限在「痛点」的语义：合规事件是痛点的结果，不是痛点本身。一家企业被执行 5,000 次，痛点是「资金链断裂」，被执行只是它的表现。本件数的是表现，不是原因。

### 3.5 与开发库 live 的差异

开发库无诊断结果面，live 不产出。上线需把六类计数物化成宽表（org_id, type, n），并保留 `head_sample_sizes`。

建议物化时同时存「截至时点」与「近 12 个月」两套，让使用方自己选口径。

## 四、数据缺失情况

### 4.1 缺口清单

本件的缺口是「痛点」的三分之二：经营痛点与舆情痛点完全没有载体。剩下的合规侧数据质量不错，但覆盖不了「企业经营困难」这个核心语义。

第二个缺口是截断：逐企业明细只覆盖头部 12,080 家，长尾企业的痛点数是空的。页面不能对长尾企业显示「0」，那会被误读成「无风险」。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 经营痛点无载体 | 无法回答「为什么难」 | 不做 | 企业调研或舆情 NLP |
| 舆情痛点无载体 | 同上 | 不做 | 舆情管道 |
| 逐企业明细截断 | 长尾为空 | 头部 50 展示 | 扩样本或分页查询 |
| 等权未加权 | 严重度不可比 | 声明未加权 | 需权重表 |
| 累计口径 | 老风险长期占榜 | 声明累计 | 另建年度聚合 |
| 连带被执行 | 保险分支虚高 | 不区分 | 需案件角色字段 |

### 4.2 逐条影响

「经营痛点无载体」是最根本的缺口。企业真正的痛点是订单减少、回款变慢、人才流失，这些都不在六张表里。六张表记的是这些痛点恶化之后的法律后果。

「连带被执行」是计数口径的一个具体缺陷：保险公司作为被告的连带责任人被多次执行，记录数很高，但经营未必有问题。要修正需要案件角色字段，库内没有。

### 4.3 明确不做什么（禁止的替代）

- 不把合规事件数称为「经营痛点」——它是后果，不是原因。
- 不对六类做自行加权——没有权重表，加权即不可复现。
- 不把累计条数当年度新增——两者语义不同，混用会误导。
- 不对截断样本外推全库分布——头部样本天然偏重。
- 不把长尾企业的空值显示为 0——0 是「无记录」，不是「无风险」。

五条禁令的共同点是「不要把可数的东西说成想说的东西」。六张表能数的是法律事件，需求想要的是经营困难。两者相关但不相同，说清楚比算得准更重要。

### 4.4 若甲方补齐后的口径升级路径

补齐路径分两条：一条是补经营痛点（企业调研或舆情 NLP），一条是补案件角色（区分被告、连带、担保）。前者决定指标语义是否成立，后者决定计数是否公平。

两条都补之后，档位可以从「部分支持」升到「完全转换支持」。只补案件角色不补经营痛点，仍然是部分支持，因为语义覆盖还是一半。

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 补经营痛点调研 | 三类痛点齐全 | 可升完全转换 |
| 建舆情 NLP | 舆情痛点可算 | 可升完全转换 |
| 补案件角色字段 | 连带责任可剔除 | 仍为部分支持 |
| 补严重度权重 | 可加权计数 | 另立指标 |

**基期声明**：`base_years_used` = []；`base_years_missing` = []。六张风险表都是事件流水，本件数的是「截至抓取时点的累计条数」，不是年度新增，故无基期年份；表内带发生日期，若要做年增量需另建按年聚合（本件未做，避免把累计当年度）。

## 五、王惠方法对照

王惠原稿把痛点定义为「合规、经营、舆情三类」，并假定 `enterprise_diagnosis` 已有 `pain_point` 与 `severity`。本件保留「按企业计数」的形态，把数据源换回六张原始表，覆盖范围缩到合规侧。

差异有三处：一是覆盖从三类降到一类；二是加权从 severity 降为等权；三是口径从「诊断结果」降为「事件累计」。三处都让指标变粗，但都让数字变真。

如果甲方要的是「企业经营困难程度」，本件给不了；如果甲方要的是「企业法律风险事件数」，本件给的是准的。名字叫「痛点数量」，实际交付的是后者，这个错位必须写在文档最前面。

**选用建议**：计数形态与「按企业合并」沿用王惠；痛点范围缩为合规侧并在产物声明；加权因缺 `eval_weight` 类权重表改为等权。若甲方坚持三类覆盖，应先补经营与舆情数据源，而不是用现有六表硬凑。

## 附录 G 口径问答

**问：为什么只有合规痛点？**

答：经营与舆情痛点库内没有结构化载体。六张表记的是法律后果，不是经营困难本身。

**问：一条处罚和一条被执行都算 1 吗？**

答：是。等权是默认口径，因为甲方没有给严重度权重表。

**问：为什么恒大排第一？**

答：累计口径。它历史被执行记录 5,840 条，是历年累积，不代表今年新增。

**问：长尾企业为什么是空的？**

答：逐企业明细只取头部样本。空值是「未采样」，不是「无风险」。
