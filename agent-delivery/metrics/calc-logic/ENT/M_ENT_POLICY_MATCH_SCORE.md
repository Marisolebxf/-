## 摘要

「政策匹配度」是招商与引育推荐的核心排序器：给定一家企业，从政策库里找出它最该申报的那一条，并给一个 0—100 的分。正本给了完整的三维框架——产业方向匹配、支持对象匹配、支持方式匹配，地域作为适用性门槛不进加权。本件把框架跑通了，但跑的过程里撞上一堵墙：**政策侧的三个主字段是空的。**

具体到什么程度：`dwd_policy_base` 20,000 行，`theme` 有值的只有 **2 行**（19,998 行是字符串 `'NULL'`）；`keywords` 与 `keypoints` 全表 **0 行**有值；`policy_support` **20,000 行全部**是 JSON 字面量 `'null'`，不是空数组、不是 NULL，而是六个字符的字符串。也就是说，正本设想的「企业主题 vs 政策主题」「企业标签 vs 政策支持对象」这两条匹配路径，**输入侧一行有效值都没有**。

于是本件做了降级，并把这个降级写死进产物：三个子项全部改为**政策标题文本匹配**。产业方向子项看标题里有没有链名或一级环节名（长度 ≥4），支持对象子项看标题里有没有该企业资质族的名称，支持方式子项看标题里有没有「资金/补贴/奖励/税收/人才/用地」等 17 个词。地域做门槛：政策 `city='深圳市'`、或 `city` 为空且 `level=4`（国家级）、或 `city` 为空且 `province='广东省'`，三者之一才进候选池。

政策池从 20,000 条缩到 **3,284 条**（国家级 2,174、广东省 231、深圳市 879）。企业侧取深圳 12 链的 **13,313 家**（`code/_snapshots21/chain_firm_index_20261023.json` 与底册 `city='深圳市'` 的交集），其中 6,356 家有资质标签、6,957 家没有。每家企业在池内取**单条最高分**作为它的匹配度：

$$S_i=\max_{p\in P_i}\;100\times\left(0.40A_{ip}+0.35O_{ip}+0.25W_{ip}\right)$$

结果：区间 **25—65**，中位 **40**，均值 **45.2909**，p10 **33.75**，p90 **65**，≥60 的 3,700 家，≥70 的 **0** 家。分数分布高度离散化——只有 8 个取值覆盖了绝大多数企业：40（7,166 家）、65（3,421 家）、25（1,175 家）、42.5（502 家）、33.75（458 家）、60（279 家）、36.67（232 家）、32（65 家）。

**为什么封顶是 65 而不是 100？** 因为「产业方向命中」与「支持对象命中」在 3,284 条政策里**从不同时出现**（`pool_industry_and_object_rows=0`）。产业方向命中的只有 36 条（1.0962%），支持对象命中的只有 102 条，两者零交集。一家企业的最高分只能来自「产业 0.40 + 方式 0.25 = 65」或「对象 0.35 + 方式 0.25 = 60」，拿不到 100。这不是算法 bug，是政策标题的用词结构决定的：讲产业方向的政策标题不写申报对象资质，讲申报对象的标题不写产业方向。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**企业分析 → 引育推荐 → 政策适配**。三个消费点：① 企业详情页的「政策适配」卡片，列出最匹配的 3 条政策与分数；② 招商推荐列表按匹配度排序；③ 政策详情页反查「哪些企业最匹配」。

### 1.2 为什么需要这个指标

第一，**政策找不到企业、企业找不到政策**是双向痛点。政策库有 2 万条，企业不可能逐条读；需要一把尺子把「这条政策和我有关系」量化出来。

第二，**招商话术需要可解释的理由**。「这家企业适合申报 XX 政策」如果只说结论，说服力弱；给出「产业方向匹配 + 支持方式匹配」的拆解，才像一份尽调。

第三，**它最容易被「有个分数」骗过去**。三个子项各给 0/1，加权一算就有分，跑出来的分数还挺分散（25—65），看上去很像一个可用的模型。但只要看一眼输入字段的填充率，就知道这三个 0/1 里有两个是从标题里猜的。

### 1.3 需求文档是否给出定义方法

**给了三维框架，没给子项算法。** 正本写明「跨政策域（产业方向/支持对象/支持方式）综合度量，取值 0—100」，并注明「权重与口径待 Q015 正式闭合（pending_data_lead）」。以下四项未定：

1. **三个子项各自怎么算**：命中率？覆盖率？语义相似度？
2. **权重**：0.4/0.35/0.25 是本件默认值，正本未给；
3. **地域是门槛还是子项**：正本把地域列在表里，但没说是加权项还是过滤条件；
4. **一企多政策怎么合成**：取最高、取平均、还是取 TopN 加权？

本件对四项的处理是：子项用二值命中（可解释）、权重取 0.4/0.35/0.25（产业优先）、地域做门槛（不进加权）、一企取最高分（对应 UI「推荐一条」）。

### 1.6 本报告的口径与边界（须与甲方会签）

**公式**：

$$S_{ip}=100\times\left(W_A A_{ip}+W_O O_{ip}+W_W W_{ip}\right),\qquad S_i=\max_{p\in P_i}S_{ip}$$

其中 $W_A=0.40$、$W_O=0.35$、$W_W=0.25$，三个子项定义如下：

$$A_{ip}=\mathbb{1}\left[\exists\,k\in K_{c(i)}:k\subseteq title_p\right]$$

$$O_{ip}=\frac{1}{|C_i|}\sum_{c\in C_i}\mathbb{1}\left[\exists\,k\in K_c:k\subseteq title_p\right]$$

$$W_{ip}=\mathbb{1}\left[\exists\,k\in K_{way}:k\subseteq title_p\right]$$

$K_{c(i)}$ 是企业所在链的链名与一级环节名（长度 ≥4），$C_i$ 是企业的资质族集合（11 族），$K_{way}$ 是 17 个支持方式词。$P_i$ 是地域门槛过滤后的政策池（3,284 条）。

**五条边界**：

1. **子项是标题字面匹配**，不是语义匹配。政策标题没写「人工智能」但正文大段讲人工智能的，本件判 0；
2. **权重未签**。0.4/0.35/0.25 是本件默认值，Q015 会签后必须重算并同步改正文；
3. **地域是硬门槛**。国家级（`level=4` 且 `city` 空）与广东省（`city` 空且 `province='广东省'`）入池，其他地市政策一律排除；
4. **一企取最高分**，不是平均分。UI 只推荐一条，平均分无法对应到具体政策；
5. **分母是深圳 12 链企业 13,313 家**，不是深圳全部企业 95,600 家。两者不可混用（见 §4.2 陷阱五）。

## 二、计算过程

### 2.1 为什么先做地域门槛，而不是把地域当第四个子项

正本的表格里，「企业地域 vs 政策地域匹配」被列在「产业方向匹配」下面，是一个三级项。如果按字面把它当加权项，会出现一个荒谬结果：一家深圳企业匹配一条「深圳市专属」政策得 1 分，匹配一条「广东省通用」政策得 0.5 分，但后者其实它也能申报。地域不是「匹配程度」问题，是「有没有资格」问题。

所以本件把地域做成**硬门槛**：先把 20,000 条里企业根本没资格申报的剔掉，再对剩下的算分。门槛三条：

| 政策地域形态 | 判定条件 | 池内条数 |
|---|---|---|
| 深圳市 | `city='深圳市'` | 879 |
| 国家级 | `city` 为空且 `level=4` | 2,174 |
| 广东省 | `city` 为空且 `province='广东省'` | 231 |
| 其他 | 其余全部 | 不进池 |

国家级占池子的 66.20%，这是合理的——国家级政策对全国企业普适，深圳企业当然可申报。但这也带来一个副作用：**最高分有 9,607 家来自国家级政策**（`score_source_geo.national`），市级 3,704 家、省级只有 2 家。省级政策几乎不成为最优解，因为广东省政策标题很少同时写产业方向与支持方式。

### 2.2 政策池从 20,000 缩到 3,284 的过程

第一步，读全表 20,000 条。第二步，按上述三条门槛过滤，得 3,284 条。第三步，对池内每条政策算三个子项的原始命中标记（产业方向向量、对象向量、方式标量）。第四步，对每家企业按链与资质族组合去重后算分。

为什么先按「链 × 资质族集合」去重再算？13,313 家企业只有 **469 种不同的（链，资质族组合）画像**。同一链、同一组资质的企业，在同一政策池下的分数完全一样，逐家算等于把同一个矩阵乘法做 13,313 次。去重后只算 469 次，再按画像回填，结果完全等价。

这一步也解释了分数为什么只有 8 个取值：**469 种画像共享 8 个可能的分数档**，因为产业方向与方式都是二值，对象项只取 11 族里的若干命中比例，组合空间本来就小。

### 2.3 三个子项为什么退化成标题匹配

先看政策表的字段填充率（`probes.field_degeneracy`）：

| 字段 | 有值行数 | 占 20,000 | 本件用途 |
|---|---:|---:|---|
| `theme` | 2 | 0.01% | 正本要求用它做主题匹配 → 不可用 |
| `keywords` | 0 | 0 | 正本要求用它做关键词匹配 → 不可用 |
| `keypoints` | 0 | 0 | 同上 → 不可用 |
| `policy_support` | 0（20,000 行字面 `'null'`） | 0 | 正本要求用它做对象匹配 → 不可用 |
| `status` | 20,000（单值「有效」） | 100% | 无区分度，不做过滤 |
| `city` | 10,294 | 51.47% | 地域门槛 |
| `province` | 空 2,524 行 | —— | 地域门槛 |
| `type` | 18,138 | 90.69% | 仅用于分布统计 |

四个正本点名的字段，三个是空的、一个是 2 行。这不是「覆盖低」，是**结构建好了但没灌数**——`theme` 的 19,998 行存的是字符串 `'NULL'`，`policy_support` 的 20,000 行存的是字符串 `'null'`。字符串占位符在 `COUNT(col)` 里会被算成「有值」，所以任何「非空率」统计如果不排除大小写变体，都会得出 100% 的错误结论。

标题成了唯一可用的文本。它有 20,000 行、平均长度足够、且包含产业词与对象词——这是本件降级的现实依据，也是它最大的局限。

### 2.4 产业方向子项：36 条政策命中，1.0962%

链名与一级环节名（长度 ≥4）作为关键词，在 3,284 条池内政策标题里扫描，命中 **36 条**（1.0962%）。命中的标题样本包括「国家车联网产业标准体系建设指南（智能网联汽车）」「关于征集人工智能创新应用示范项目的通知」「关于进一步深化深圳市智能网联汽车产业协同部署的议案」「关于做好落实软件和集成电路产业企业所得税优惠政策有关工作的通知」等。

36 条是什么概念？**池子里 98.90% 的政策标题不含任何链名或环节名。** 这不是说这些政策与产业无关，而是政策标题习惯写「XX 工作的通知」「关于开展 XX 申报的通知」，产业方向写在正文里而不写在标题里。

后果很直接：一家企业如果在链名上命中，直接拿 0.40；没命中就是 0。产业方向子项在绝大多数企业身上是 0，只有少数「链名恰好出现在某条政策标题里」的企业拿到 40 分——这解释了为什么 40 分是最大的一个档（7,166 家）。

### 2.5 支持对象子项：102 条命中、按族平均

企业侧有 11 个资质族（高企、科技型中小企业、创新型中小企业、专精特新、小巨人、单项冠军、独角兽/瞪羚、知识产权、研发机构、创新平台、其他示范）。政策侧看标题里有没有族名关键词，命中 **102 条**。

与产业方向不同，对象子项不是 0/1，而是**企业资质族的命中比例**：一家企业有 4 个资质族，其中 2 个族名出现在某条政策标题里，该政策下 $O=0.5$，对象项贡献即为权重 0.35 的一半。这就是 42.5、33.75、36.67、32 这些「非整数档」的来源：

| 分数 | 构成 | 企业数 |
|---:|---|---:|
| 40 | 产业 0.40 单独命中 | 7,166 |
| 65 | 产业 0.40 + 方式 0.25 | 3,421 |
| 25 | 方式 0.25 单独命中 | 1,175 |
| 42.5 | 对象项约半命中 + 方式满命中 | 502 |
| 33.75 | 对象项四分之一命中 + 方式满命中 | 458 |
| 60 | 对象 0.35 + 方式 0.25 | 279 |
| 36.67 | 对象项三分之一命中 + 方式满命中 | 232 |
| 32 | 对象项五分之一命中 + 方式满命中 | 65 |

这张表是理解本件分数结构的钥匙：**没有一个档位是「三项全中」**，因为产业命中与对象命中零交集。最高档 65 是「产业 + 方式」，次高 60 是「对象 + 方式」。

### 2.6 支持方式子项：767 条命中，最「好用」的一项

17 个支持方式词（资金、补贴、补助、奖励、资助、税收、减免、贴息、贷款、基金、人才、用地、试点、示范、项目、扶持、支持）在池内命中 **767 条**，是三子项里命中最多的一项。

原因很朴素：「支持」「项目」「示范」这三个词在政策标题里出现频率极高。这带来一个反向问题——**方式子项的区分度最低**。只要标题里有「支持」两个字（几乎每条政策都有），方式项就得 1，企业白拿 25 分。25 分这个档（1,175 家）就是「只命中方式、什么都没命中」的企业。

所以 25 分不能读成「匹配度 25%」，它是**地板分**：只要企业的链或资质在池子里能找到一条带「支持」字样的政策，就有 25 分。真正有信息量的是 40 以上。

### 2.7 取最优单条政策，以及复现结果

为什么取 $\max$ 而不是平均？两个理由：① UI 只推荐一条政策，平均分对应不到具体政策；② 池子有 3,284 条，平均会被大量「毫不相关但含支持二字」的政策拉平，所有企业挤在 25—30 分，排序失效。

## 四、数据缺失情况

### 4.1 缺口的后果归因

1. **分数不可解释为「政策适配度」**：它度量的是标题用词重合，不是申报条件满足；
2. **上限被结构性压到 65**：三项全中在数据上不可能发生；
3. **地板分 25 无信息量**：含「支持」二字的政策遍地都是；
4. **国家级政策主导**：72.16% 的企业最优解来自国家级政策，市级政策的区分度被稀释。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

**陷阱一：`'null'` 是字符串，不是 NULL。** `policy_support` 20,000 行全是六字符字符串 `'null'`，`COUNT(policy_support)` 会返回 20,000（100%），而正确结论是 0 行有值。任何统计这张表字段填充率的脚本，必须先排除 `'null'` / `'NULL'` 两种大小写变体。

**陷阱二：`level=4` 才是国家级。** 按 `level` 排序会看到 1/2/3/4 四档，只有 4 是国家级；把 `level` 当连续变量或把 1 当最高级都会错。

**陷阱三：城市必须用中文全称精确匹配。** 政策表 `city` 存的是「深圳市」，企业表 `city` 也是「深圳市」，但快照里同时存在「深圳」的简写（少量）。用 `LIKE '%深圳%'` 会把「深圳市」与「深圳」都捞进来，也会误伤「深圳路」这类地名；本件用等值匹配，`city` 为空的 9,706 行单独走国家级/省级判定。

**陷阱四：`status` 单值「有效」。** 20,000 行全是「有效」，用它做过滤等于不过滤；不要写「已剔除失效政策」这种话，本库没有失效记录。

**陷阱五：分母有两个。** 13,313 是「深圳 12 链企业」，95,600 是「底册深圳企业」。本件的 13,313 是前者，占后者的 13.9257%。任何「深圳企业政策匹配覆盖率」的表述，必须说清分母是哪一个。

**陷阱六：8 个取值不是精度问题。** 分数只有 25/32/33.75/36.67/40/42.5/60/65 这几档，是因为子项只有二值与比例两种形态；不要为了「看起来更连续」去加噪声或插值。

### 4.3 可构建但存在缺口（不是「无法构建」）

如果指标改名为「政策标题相关性排序」，本件可以判**完全转换支持**：标题 20,000 行齐全、匹配规则可复算、排序稳定。一旦要求「政策适配度」这个语义（企业是否真的符合申报条件），就必须判部分支持，因为申报条件写在 `policy_support` 里，而那一列是空的。

### 4.4 若甲方补齐后的口径升级路径

1. **先补 `policy_support`**：这是唯一能同时提升对象子项与可解释性的字段；
2. **再补 `theme` / `keywords`**：让产业子项从标题字面匹配升级为主题匹配；
3. **再定权重**：Q015 会签，按业务重要性给 0.4/0.35/0.25 或新值；
4. **最后上向量**：对 `content` 做句向量，子项改余弦相似度，并用人工标注集验证。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答「gkx 能不能算企业与政策的匹配度」。范围是政策侧三子项 + 地域门槛，不含申报成功率预测、不含政策金额测算。

### C.2 需求语义锚定

「匹配度」在业务语境里默认指「这家企业符不符合申报条件」。申报条件由政策正文的「支持对象」「申报条件」段落定义，而 gkx 的结构化字段 `policy_support` 恰好是空的。所以本附录的中心判断是：**语义要的是条件匹配，数据只能做标题匹配**。

### C.3 权威与学术构建方法谱系

#### C.3.1 族 A：规则引擎

把政策拆成结构化条件（行业、规模、资质、地域、年限），逐条布尔判断。最准、最可解释，前提是政策结构化。gkx 不具备。

#### C.3.2 族 B：检索模型

BM25 / TF-IDF，把企业描述当 query、政策正文当 doc。可用、易实现，但只能给相关性，不能给「符不符合」。

#### C.3.3 族 C：语义向量

句向量余弦相似度，能处理同义表达。需模型与验证集，本批不做。

#### C.3.4 族 D：监督学习

用历史申报成功/失败样本训练二分类。最贴业务，但没有标注数据。

### C.4 数据可行性详细分析

| 依赖 | gkx 现状 | 可行性 |
|---|---|---|
| 政策主题 | 2 / 20,000 | 不可行 |
| 政策关键词 | 0 / 20,000 | 不可行 |
| 政策支持对象 | 0 行有效（全占位） | 不可行 |
| 政策标题 | 20,000 | 可行 |
| 政策正文 | 有值，未向量化 | 可行（需加工） |
| 企业资质标签 | 32,322 家 | 可行 |
| 企业链归属 | 13,313 家（深圳 12 链） | 可行 |

### C.5 推荐构建方案（工程可执行）

第一步，按本版出标题匹配分，先让排序可用；第二步，补 `policy_support` 结构化，把对象子项从「标题猜词」换成「条件判断」；第三步，对正文做向量化，产业子项升级为语义相似度；第四步，用申报成功样本做验证与权重标定。

### C.6 风险与残余不确定性

① 权重未签，排序可能随权重变化大幅调整；② 标题匹配对「正文讲产业、标题写通知」的政策系统性漏判；③ 国家级政策主导，市级政策区分度低；④ 上限 65 会被误读为模型缺陷。

### C.7 可行性总判（完整版结论）

**标题匹配可行、条件匹配不可行。** 按需求原文的「匹配度」语义判**部分支持**；若改名为「政策标题相关性」可升为完全转换支持；若要求「申报条件符合度」，在 `policy_support` 补齐前应判完全不支持。
