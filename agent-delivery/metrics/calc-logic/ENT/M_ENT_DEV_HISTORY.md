## 摘要

「企业发展历程」在产品上是一条竖线：某年拿到融资、某年上市、某年申请了多少专利、某年营收跳涨。在数据上它是三条异构流的 UNION：年度财务、年度专利、逐条资讯。三条流的事件粒度不同（年 / 年 / 日），字段不同（金额 / 件数 / 标题），唯一共同的键是 `org_id`。

本件先把三条流各自的可算面量出来。财务流有 90,926 行、1,416 家机构有营收或净利润，其中 518 家有两年以上序列；专利流用已完成的 `app_year` 面板，275,135 个「申请年|第一申请人」对，名称命中底册后落到 137,448 家、259,338 个对、2,127,892 件专利；资讯流 1,668,414 行、28,123 家，日期空值 0 行、删除 0 行，窗口 2018-01-22 至 2026-05-08。

再算交集。四条流（把年报资产表也算一条财务补充流）两两求交：财务∩资讯 1,093 家、财务∩专利 787 家、资讯∩专利 13,882 家、资产∩专利 4,006 家。有任意一类事件的企业 153,551 家，占底册 81.1941%——这个数字看起来很高，但它是「至少有一条资讯或一条专利年」的结果，不代表时间线有内容。两类及以上只有 17,617 家（9.3154%），三类及以上 2,882 家，四类齐全 675 家。

最后是三个结构性缺口。目标表不存在，事件无处落库；专利流只有 2021—2024 四年，时间线的「早段」与「近两年」都缺专利事件；资讯占比 94.8318%，不做类型过滤的时间线实际上是一条资讯流。这三条决定了档位只能是「部分支持」，而不是「完全转换支持」。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业分析 → 企业深度 → 企业画像时间线**，页面形态是企业详情页的「发展历程」竖线，按时间倒序排列三类事件。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业分析 → 企业深度 → 企业画像时间线 |
| 页面载体 | 企业详情·发展历程 |
| 输出形态 | 每企业一条 timeline（一行一事件） |
| 更新频率 | 周 |
| 粒度 | 企业 × 事件 |
| 关联Q | 无（Q004 是软科学「难题攻关历程」，不是本条） |

产品 `.5.2` 的 CMS 历程、专家知识、明星企业故事**不消费本条**——这是 calc-logic 特意点明的边界，因为「企业发展历程」这四个字很容易被理解成「企业故事」，而本条是结构化事件流，不是叙事文本。

### 1.2 为什么需要这个指标

第一个用途是企业画像的叙事骨架。用户看一家企业，先看规模（营收）、再看成长（增长率），第三眼就想知道「它这些年发生了什么」。时间线把分散在财务、专利、资讯三处的记录按年串起来，是最低成本的叙事。

第二个用途是投研与招商的尽调入口。一家企业专利从 2021 年起断崖、资讯从 2023 年起密集，这两条线放在一起就能提示「技术产出停滞但公关活跃」——单看任何一条都发现不了。

第三个用途是事件检索。按年份、按事件类型筛选，是时间线组件的核心交互。这要求事件类型是枚举值（finance / patent_year / news），而不是自由文本。

### 1.3 需求文档是否给出定义方法

calc-logic 给了三类事件的精确定义与禁止项，没有给公式（本条不是聚合指标）。

> **每个企业一条 timeline**：三类事件 UNION 后按时间倒序。

> 1. **财务年报**：`enterprise_finance_history` 一行一事。时间 = `data_year`。只带 `revenue`、`net_profit`。**禁止读** `revenue_growth_rate` / `profit_margin` / `rd_investment_ratio` / `gross_margin`（别的指标产出）。

> 2. **专利年统计**：`enterprise_patent_history` 一行一事。时间 = `data_year` = ODS `dwd_patent.apdt_year`（**申请年**）。`patent_apply_count` = 该年申请件数；`patent_grant_count` = 该申请年专利中已有授权号的件数，不是授权发生年。

> 3. **重点资讯**：`enterprise_news` 一行一事。时间 = `publish_time`。带 `title`、`news_type`。

> 无三类任何事件：**该企空时间线**。口径能算不等于已落库。

三处细节值得展开。其一，「一行一事」对财务流意味着一年一条，对资讯流意味着一条资讯一条，对专利流意味着「一个申请年一条」——三者的「事」粒度不同，UNION 之后必须带 `event_type` 区分，否则无法解释「为什么这家企业 2023 年有三条事件，其中一条是 300 件专利」。

其二，「专利授权按申请年归桶」是硬约束：明细表没有授权日，不能按授权发生年切。所以专利事件的时间是「申请年」，事件内容是「该年申请了多少件、其中多少件后来授权了」。这与「2023 年获得 50 件授权」不是一回事。

其三，「禁止读别的指标产出列」是为了防止循环依赖：时间线只带原始金额，不带利润率、增长率这些派生值。

### 1.4 类似指标权威机构构建方法可行性

「企业事件时间线」的四种构建方式：

| 方法族 | 代表机构/实践 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 多源 UNION | 企查查「企业动态」、天眼查「企业发展」 | 工商变更 + 诉讼 + 专利 + 新闻 | **最高（本件口径）** |
| B 单一源时间线 | 交易所公告时间线 | 只取公告 | 中（覆盖窄） |
| C 事件抽取 | NLP 从新闻抽事件 | 抽取 + 归一 | 低（无模型、不可复核） |
| D 人工维护 | 投研数据库 | 编辑录入 | 低（不可规模化） |

A 族是本件口径。它与 B 族的差别在于「多源」——本件三条流分别来自财务表、专利表、资讯表，正是 A 族的简化版。C 族需要 NLP 模型与人工校验，calc-logic 明确不做（禁止把 CMS/专家知识当源）。D 族不可规模化。

### 1.6 推测原意与推测定义

推测原意是：**企业详情页要一条「这些年发生了什么」的竖线，事件来自三个可信源，按时间倒序，可分类筛选**。它不追求事件全（不可能全），追求的是每条事件都能追溯到原始行。

据此给出主定义与两个对照定义：

$$ T_i = \bigcup_{k \in \{f,p,n\}} \{(i, t_{k}, \text{type}_k, \text{payload}_k)\} $$

$$ |T| = |T_f| + |T_p| + |T_n| $$

$$ \text{cov} = \frac{|\{i: T_i \ne \varnothing\}|}{189{,}116} $$

本件交付 $|T_f| = 90{,}926$ 行、$|T_p| = 259{,}338$ 个命中对、$|T_n| = 1{,}668{,}414$ 行、$\text{cov} = 81.1941\%$。依赖维度如下：

| 代号 | 依赖维度 | 类型 | 本件实测 |
|---|---|---|---|
| D1 | 财务年度事件 | 核心 | 90,926 行 / 1,416 家 |
| D2 | 专利年事件 | 核心 | 259,338 对 / 137,448 家 |
| D3 | 资讯事件 | 核心 | 1,668,414 行 / 28,123 家 |
| D4 | 事件类型枚举 | 核心 | 可枚举（三类） |
| D5 | 目标表 | 核心 | **不存在** |
| D6 | 授权日 | 精度 | 不可得（按申请年归桶） |

D5 是本件的硬缺口：没有目标表，事件只能「现拼」，不能「已落库」。D6 决定了专利事件的语义只能是「申请年」而不是「授权年」。

## 二、计算过程

### 2.1 总体思路与数据流

三流分别取数、统一到「org_id + event_time + event_type」、本地求交、缺口核对。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 财务流 | 年报宽表 90,926 行 | 一行一事，时间 = `year` | 1,416 家 |
| 专利流 | `app_year` 面板 275,135 对 | 名称命中底册 → `org_id` | 137,448 家 |
| 资讯流 | 资讯表 1,668,414 行 | 一行一事，时间 = `news_date` | 28,123 家 |
| 求交 | 四组 `org_id` 集合 | 两两交集 + 多流计数 | §2.5 表 |
| 缺口核对 | gkx 表清单 | 精确同名检索 | 目标表 0 命中 |

财务流与资讯流都是「一行一事」，不需要额外聚合；专利流需要一次名称映射——`app_year` 面板的键是「申请年|第一申请人名称」，要落到 `org_id` 必须走底册名称等值匹配。这一步与 `M_ENT_PATENT_TOTAL` 用的是同一套映射，保证族内专利数一致。

### 2.2 步骤 1｜财务流：90,926 行、1,416 家

财务事件的时间是 `year`，内容是 `operating_revenue` 与 `pure_profit`。90,926 行里，营收非空 2,193 行、净利润非空 2,349 行，两者合计可用的「有内容事件」4,542 行（有重叠）。只看「有营收或净利润」的机构，是 1,416 家（0.7487%）。

这个数字比 `M_ENT_REVENUE_LATEST` 的 1,302 家略多，差在「只有净利润、没有营收」的机构——它们能进时间线（有一条净利润事件），但进不了营收指标（没有营收值）。族内两个数不冲突，分母不同。

1,416 家里有 518 家存在两年以上的序列，能画出真正的「财务曲线」；其余 898 家只有一条，时间线上是一个孤立点。这个比例（36.6%）决定了时间线的财务段有多稀疏：多数企业只有一年财务事件。

财务流的另一个特点是年份分布极偏：2014 年 476 家、2015 年 305 家、2016 年 172 家，三年占 953 家；2023—2025 合计 89 家。时间线在 2016 年之后基本没有财务事件。

### 2.3 步骤 2｜专利流：275,135 对、137,448 家

专利事件来自已完成的 `app_year` 面板：键是「申请年|第一申请人名称」，值是该年申请件数。面板共 275,135 个对、146,915 个申请人、2,424,684 件专利（四年的合计）。

名称等值命中底册后：137,441 个申请人名命中（93.5514%），落到 137,448 家机构（多出 7 家是因为底册有 47 组同名，每组 2 家，同名会把两家都算进来），命中 259,338 个「机构-年」对、2,127,892 件专利，占面板件数的 87.7596%。

年度分布是均齐的：2021 年 604,512 件、2022 年 601,893 件、2023 年 611,811 件、2024 年 606,468 件。四年几乎持平，说明这个面板不是「逐年增长」的专利产出，而是「同一年申请、不同年份公开」的截面——它按申请年归桶，不受公开时滞影响。

窗口边界必须说清：`app_year` 只有 2021—2024 四个键年。库内 `dwd_patent` 的 2025—2026 年虽有件数，但面板没有按申请人分年，所以时间线在 2025—2026 年没有专利事件。2018—2020 年则是零行（专利表本身不含更早申请年）。

### 2.4 步骤 3｜资讯流：1,668,414 行、28,123 家

资讯事件一行一事，时间 = `news_date`。全表 1,668,414 行，日期空值 0 行、删除标记 0 行，窗口 2018-01-22 至 2026-05-08。

机构覆盖 28,123 家，其中 28,118 家在底册内（99.9822%），名称命中 27,596 个（98.1261%），落在底册机构上的行数 1,668,408（99.9996%）。这三个比例说明资讯表的 `org_id` 与底册是同一套体系，不需要名称归一。

分布极度集中：中位数 2 行/家、P90 27 行、最大 138,222 行（一家头部车企，占全表 8.2846%），1,290 家 ≥100 行、10,776 家只有 1 行。前 10 家合计 330,331 行，占 19.7991%。

这个分布对时间线的影响是：头部企业的时间线会被资讯刷屏，长尾企业的时间线只有 1—2 条资讯。若不做分页或类型过滤，时间线组件在头部企业上会直接失去可用性。

### 3.3 数据量、覆盖与代表性

三类覆盖率的含义不同：财务 0.7487% 是「有年报的机构」、资讯 14.8708% 是「被报道过的机构」、专利 72.6792% 是「有专利申请的机构」。三者不能相加，也不能互相替代。

代表性偏差有两层。第一层是「事件类型代表的企业类型不同」：有专利的多为制造业，有资讯的多为头部或热点企业，有年报的多为规上/上市。第二层是「时间窗不同」：专利只有 2021—2024，资讯到 2026 年 5 月，财务退回 2013 年。

### 3.4 结构支持判定

第二个缺口是「事件类型枚举」在源表里不存在：财务表没有 `event_type` 列、专利面板没有、资讯表也没有。UNION 时由代码赋常量，这是可接受的，但意味着事件类型不可在源表层面校验。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| `enterprise_dev_history` | 结果无处落 | 现拼 + 明示 | 建 DDL |
| 专利 2018—2020、2025—2026 | 时间线首尾缺专利 | 明示窗口 | 补 `app_year` 分年 |
| 财务 2023—2025 薄 | 近期财务事件少 | 明示 | 上游补采 |
| 授权日 | 不能按授权年切 | 按申请年归桶 | 明细补授权日 |
| 事件类型列 | 只能代码赋常量 | 常量映射 | 建表时固化 |
| CMS/专家知识 | 不可作源 | 未用 | 不补（口径禁） |

### 4.2 逐条影响

「目标表缺失」是最硬的一条。它不影响「能不能算出事件」，只影响「能不能存下来」。calc-logic 说「口径能算不等于已落库」，本件照此表述：三流都能拼，但没有地方落，页面查询只能现算。

「专利窗口」影响时间线的两端。2021 年之前的专利事件在库内不存在（不是零，是没有行），2025—2026 年的申请数据虽在 `dwd_patent` 里，但没有按申请人分年的面板。任何「近五年专利趋势」的画法都必须先说明这个窗口。

「财务近期薄」影响「最近发生了什么」。财务事件 2023—2025 只有 89 家，而资讯在 2025 年有 421,067 行。时间线在近期几乎只有资讯。

### 4.3 明确不做什么（禁止的替代）

- 不把 CMS / `expert_knowledge` / 明星企业故事当源——calc-logic 明禁。
- 不做并购、上市、股权变更的阈值识别——那是 `M_ENT_DEEP_142_1` 的事。
- 不加曾用名（`enterprise_history_name` 现网 0 行）。
- 不把专利「授权年」当事件时间——明细无授权日。
- 不把财务的派生列（增长率、利润率）带进时间线——那是别的指标产出。
- 不把三条流的时间窗「拉平」成同一区间——那会丢掉大量真实事件。

### 4.4 若甲方补齐后的口径升级路径

| 补齐条件 | 口径变化 | 档位变化 |
|---|---|---|
| 建 `enterprise_dev_history` | 事件可落库 | 部分支持 → 完全转换支持 |
| 补 `app_year` 2018—2026 | 专利窗口对齐 | 不改变档位，提升完整度 |
| 补财务近期年报 | 财务段前移 | 不改变档位 |
| 补授权日 | 可按授权年切 | 不改变档位，扩展事件类型 |

**基期声明**：`base_years_used` = 2021—2024（专利申请年唯一窗口）；`base_years_missing` = 2018—2020、2025—2026（专利侧无「申请人-年」对）。资讯窗口 2018-01-22 至 2026-05-08、财务窗口 2013—2025 分别在 note 中说明，未按 0 补齐。

## 附录 F 口径问答

**问：81.1941% 的企业有事件，为什么还判部分支持？**

答：因为 121,946 家只有一条专利记录。有事件不等于有内容，而且目标表不存在，事件落不了库。

**问：专利为什么只有 2021—2024？**

答：`app_year` 面板只按这四年做了「申请人-年」对。2025—2026 有件数但没分年，2018—2020 库内零行。

**问：能不能把资讯压一压，让时间线好看？**

答：能，但那是 UI 规则（每类取 TopN），不是口径。口径要求「一行一事」，压不压是展示层的事。

**问：财务事件为什么不做「每企每年一条」的去重？**

答：本库一企一年一行（`uk_org_id_year`），没有重复，不需要去重。

**问：专利授权数是什么意思？**

答：该申请年的专利申请里，后来拿到授权号的有多少件。不是「这一年获得多少授权」。

**问：目标表还没建，页面现在能上线吗？**

答：可以先用「现算 + 缓存」跑通交互，但必须标注「非落库口径」。等 DDL 建好再切。
