## 摘要

本件的构造分两层：先把 41 个一级环节映射到上/中/下游，再把企业挂到环节上。两层都有自己的口径风险，所以每一层都单独落盘。

| 读数 | 值 |
|---|---|
| 链数 | 12 |
| 一级环节 | 41（全部映射，无遗漏） |
| 上 / 中 / 下游环节数 | 18 / 15 / 8 |
| 缺下游环节的链 | 4 条（集成电路、传感器、智能终端、生物医药） |
| 深圳名录企业 | 2,590 家（名录全量 4,561） |
| 上链企业 | 1,471 家（56.7954%） |
| 可判游企业 | 1,367 家（占上链 92.93%） |
| 一级环节为空 | 104 家（7.07%） |
| 上游 / 中游 / 下游 | 1,007 / 743 / 738 |
| 跨 ≥2 游企业 | 826 家（60.4243%） |
| 游归属计数之和 | 2,488（每企 1.82 个） |
| 企业—链对 | 3,485 |
| 最大链（软件与信息服务） | 704 对（20.2009%） |
| 全量深圳上链企业 | 16,875 家（名录覆盖 15.3481%） |
| 叶码计数 / 去重企业计数 | 133,037 / 92,930（膨胀 1.4316 倍） |
| 跨链叶码 | 34,085（25.6207%） |
| 判档 | 部分支持 |

第一个事实是**位置不是互斥分类**。1,367 家可判游企业产生了 2,488 个游归属，平均每家 1.82 个，60.4243% 的企业跨两个以上游。原因是一个企业可以同时挂在多个一级环节上（比如既做零部件又做整机），每个环节各有一个游标签。因此三游家数之和大于分母，占比不能相加为 100%——这一点如果不在 UI 上说明，用户会把「上游 73.665% + 中游 54.3526% + 下游 53.9868%」当成三个互斥群体，得出「深圳 182% 的企业在上游」这种荒谬结论。

第二个事实是**下游被目录机械压低**。4 条链在链树里根本没有下游一级环节（集成电路、传感器、智能终端、生物医药），涉及 909 对企业—链对，占深圳全部 3,485 对的 26.0832%。这 4 条链的企业无论做什么，都不可能被标成「下游」。所以「下游只有 738 家」是**下限**，不是真实分布。

第三个事实是**上游偏高可能是名录偏差**。名录是「授权专利 ≥50 件」的代理名单（P15），只覆盖全量深圳上链企业的 15.3481%。专利多的企业天然偏研发/制造（上游），纯下游的贸易、服务、运营类企业专利少，进不了名录。因此「深圳 73.665% 的上链企业在 upstream」这个读数，至少有一部分是名录选择效应，不能直接读成「深圳产业偏上游」。

### 1.2 为什么需要「链中角色」

产业链分析最常见的错误是把「在链上」当成「在链的同一段」。一条链的上游是材料与设备，中游是制造与集成，下游是应用与服务；三段的商业模式、风险暴露、政策工具完全不同。一家做半导体的企业和一家用半导体的企业，都在「集成电路链」上，但前者需要的是设备补贴，后者需要的是应用场景。

链中角色的作用是把「在链上」细分成「在哪一段」，让招商与政策能按段投放。它同时也是补链分析的基础：只有知道哪一段企业少，才能说「缺链」。

### 1.3 口径定义

链目录 $C$ 共 12 条，每条链有一级环节集合 $L_c$，全部链合计 41 个一级环节。映射函数：

$$\phi: L\to\{\text{up},\text{mid},\text{down}\}$$

本工程自建（P17），规则按环节在链中的功能位置：原材料/零部件/设备/基础层 → 上游；制造/集成/平台/技术层 → 中游；应用/服务/运营/整机交付 → 下游。

企业 $i$ 的游归属集合：

$$A_i=\{\phi(\ell): \ell\in L,\ \text{firm } i \text{ tagged with } \ell\}$$

三条补充约定：

第一，**一企多游都计**。$|A_i|$ 可以是 1、2 或 3，统计时每个游各计一次。这决定了三游家数之和大于企业数，`stage_assignment_sum` 与 `with_l1_n` 因此都要落盘。

第二，**空环节不猜**。104 家上链企业有一级环节为空，记 `unlabeled`，不按链均值插补、不按主营推测。

第三，**缺下游的链不补环节**。4 条链没有下游一级环节，这是目录缺口，不是企业缺口。补企业没用，必须补目录（P17）。

### 1.4 计算公式与本批实现式

```python
def stages_of(firm, stage_map):
    return {stage_map[l1] for l1 in firm["l1_list"] if l1 in stage_map}

up   = sum(1 for f in firms if "up"   in stages_of(f, stage_map))
mid  = sum(1 for f in firms if "mid"  in stages_of(f, stage_map))
down = sum(1 for f in firms if "down" in stages_of(f, stage_map))
multi = sum(1 for f in firms if len(stages_of(f, stage_map)) >= 2)
assignment_sum = sum(len(stages_of(f, stage_map)) for f in firms)
```

三个实现要点。第一，`stages_of` 返回集合而不是列表，否则同一企业挂两个同游环节会被重复计。第二，三游计数各自独立，不相加；`assignment_sum` 才是相加的那个数。第三，`multi` 用 `>=2` 而不是 `==2`，因为存在跨三游的企业。

## 二、计算过程

### 2.1 链目录与一级环节

`dwd_industry_chain_info` 有 12 条 INB 链，链树展开后一级环节共 41 个。按链分布不均：软件与信息服务 3 个、集成电路 6 个、机器人 3 个、人工智能 3 个、具身智能 3 个、数字创意 3 个、智能网联汽车 3 个、低空经济 4 个、传感器 4 个、智能终端 3 个、生物医药 3 个、合成生物 3 个。

41 个环节里没有一个是空的，全部有名称。这一点很重要：如果某个一级环节名称为空，映射就无法进行，会被迫用父节点名或 id 推测。本件没有遇到这种情况，`l1_unmapped` 为 0。

### 2.2 映射的构造（P17）

映射按「功能位置」逐条判定，不按名称关键词机械匹配。以机器人为例：零部件 → 上游、本体制造 → 中游、整机集成 → 下游。以集成电路为例：半导体材料、EDA/IP 核、半导体设备 → 上游；晶圆制造、Fabless 设计、封测 → 中游；没有下游。

三项判定值得说明。第一，**封测归中游而非下游**：封装测试是制造环节的延伸，不是应用。第二，**整机集成归下游**：对机器人、智能终端这类链，整机是把上游零部件组装成可交付产品，面向终端市场，按「接近用户」的定义算下游。第三，**人工智能的基础层/技术层/应用层**分别对应上/中/下，这是最没有争议的一条。

映射结果是 18 上 / 15 中 / 8 下。下游只有 8 个，且集中在机器人、智能网联汽车、人工智能、数字创意、具身智能、低空经济、软件与信息服务、合成生物这 8 条链上，每链恰好 1 个下游环节；另外 4 条链一个都没有。

### 2.3 企业挂链与名录口径

企业挂链用产业标签，不按主营文本推断。名录 4,561 家（专利 ≥50 件代理），其中深圳 2,590 家。深圳名录里上链 1,471 家（56.7954%），未上链 1,119 家。

上链的 1,471 家里，能对上一级环节的 1,367 家（92.93%），一级环节为空的 104 家（7.07%）。这 104 家不是「没链」，而是「有链码但链码对应的环节不在 41 个一级环节里」——链树展开到一级时可能丢失了部分中间层。本件不猜，直接记 `unlabeled`。

名录是代理口径，必须反复强调：4,561 家只占全量深圳上链企业 16,875 家的 15.3481%。它不是「深圳链上企业全量」，而是「专利多的那批」。所有基于名录的企业级读数都带这个选择偏差。

### 2.4 三游分布

1,367 家可判游企业里，上游 1,007 家（73.665%）、中游 743 家（54.3526%）、下游 738 家（53.9868%）、跨 ≥2 游 826 家（60.4243%）。游归属计数之和 2,488，平均每家 1.82 个。

这组数字必须成组读。73.665% 不是「73.665% 的企业只做上游」，而是「73.665% 的企业至少有一个上游标签」。同理中游 54.3526%、下游 53.9868%。三者相加 182%，超过 100%，因为 60.4243% 的企业同时有多个标签。

平均 1.82 个游标签说明深圳名录企业大多是「一业多环节」的：既做零部件又做整机，既做材料又做器件。这与深圳电子产业的垂直整合特征一致，但也让「按游分组」的政策含义变弱——对一家跨三游的企业，你没法只用一套工具。

### 2.5 按链的结构

深圳「企业—链」对共 3,485 对，12 条链的分布极不均衡。最大的是软件与信息服务 704 对（20.2009%），其次是具身智能 580 对、机器人 562 对、智能终端 543 对、人工智能 397 对。最小的是生物医药 16 对、合成生物 23 对、低空经济 28 对。

链内结构更能说明问题。软件与信息服务：上游 307、中游 23、下游 374——中游极薄，是一条「两头大、中间空」的链。具身智能：上游 414、中游 58、下游 108——上游独大。机器人：上游 359、中游 28、下游 175。智能网联汽车：上游 105、中游 0、下游 7——中游一个都没有，样本也小。

这些结构差异是「补链」的直接依据：机器人缺中游本体制造（只有 28 家），软件与信息服务缺中游（23 家），具身智能缺中游（58 家）。

### 2.6 缺下游的 4 条链

集成电路、传感器、智能终端、生物医药 4 条链在链树里没有下游一级环节。它们涉及深圳 909 对企业—链对，占全部 3,485 对的 26.0832%。

这个缺口的性质要说清：不是「这 4 条链的企业都不做下游」，而是「字典里没有下游这个格子」。集成电路的封测被归到中游，所以整条链只有上中两段；传感器与智能终端同理；生物医药只有原材料、药品制造、医学研发服务三个环节，没有「流通/服务」环节。

后果是下游计数被系统性压低：738 家下游企业全部来自另外 8 条链。若把 4 条链补上下游环节，下游家数会显著上升，上游占比会下降。本件不做这种「假设性补全」，只把缺口量化并披露。

### 2.7 叶码口径与跨链

除了企业级名录，本件还用叶码口径（12 个单元、133,037 条叶码计数）看链内结构。叶码计数与去重企业计数之比是 1.4316（133,037 / 92,930），即一条企业记录平均被 1.43 个叶码覆盖。这个膨胀率意味着叶码计数**不能当企业数**，只能比结构。

叶码里跨链的 34,085 条（25.6207%）：叶码所属的一级环节不在该行 `industry_code` 链下，而挂在另一条链的一级环节上。归链统一取「一级环节所属链」，与名录口径一致。若不这样归一，同一家企业会因为叶码归属不同而被算进两条链，链间比较就失去意义。

叶码的上/中/下游计数是 44,450 / 36,295 / 52,267，合计 133,012，另有 25 条无法映射（`unmapped`）。叶码口径下**下游最多**（52,267），与企业级口径（下游 738 家最少）方向相反。原因是叶码里软件与信息服务的下游标签有 38,441 条，而这家链在企业级只有 374 家下游。两个口径不可混用：企业级回答「多少家企业」，叶码级回答「标签结构有多重」。

## 四、数据缺失情况

### 4.1 链主识别：无承载（拒拟维）

calc-logic 明写「链主不进本 JSON」；gkx 无 `enterprise_industry_chain`（0 表），链主认定无字段承载；`industry_chain_node` 亦不存在。

**拒拟理由**：无链主认定表，也无官方名单。
**替代口径**：只出上/中/下游。
**与原文差别**：缺「链主 / 核心配套 / 一般参与」这一层，无法回答「谁在主导这条链」。这一层对招商很重要——招链主与招配套是两种政策。

### 4.2 官方 position 列直读：口径不匹配（拒拟维）

project 侧 `chain_node.position` 只在项目 DWD（现网 8 链 CH001—CH008），与 gkx 的 12 链 INB 码目录对不上；gkx 侧 `dwd_industry_chain_info` 的 12 条 INB 记录无 position 列。

**拒拟理由**：有 position 的数据与有链码的数据不是同一套目录。
**替代口径**：本工程自建 41 个一级环节映射（P17）。
**与原文差别**：自建映射不是官方认定。换一份映射，三游家数与占比同时变——尤其「整机集成」算下游还是中游，会直接改变 700 多家的归属。

### 4.3 全量深圳上链企业分游：只有叶码级（拒拟维）

全量 16,875 家只有叶码级计数（一企多叶膨胀 1.4316 倍），没有企业级去重游归属；企业级去重只在 4,561 家专利阈值名录上有。

**拒拟理由**：全量缺企业级去重。
**替代口径**：名录口径出企业级三游 + 叶码口径出结构排序。
**与原文差别**：企业级分布只覆盖全量的 15.3481%，不能代表全量；两套口径不可相加。名录偏向专利多的企业，即偏上游，这是「上游 73.665%」的主要解释之一。

### 4.4 4 条链缺下游环节

集成电路、传感器、智能终端、生物医药没有下游一级环节，涉及 909 对企业—链对（26.0832%）。这是目录缺口，不是企业缺口。补企业无用，必须补目录（P17）。

### 4.5 104 家空环节

104 家（7.07%）有一级环节为空，进 `unlabeled`，不猜游。若按链内多数游插补，会把它们系统性推向该链的主流段，掩盖目录问题。

### 4.6 不得外推的三件事

1. **不得把三游占比相加**：一企多游，和大于 100%。
2. **不得把名录当全量**：覆盖率 15.3481%，且偏专利多的企业。
3. **不得把下游 738 当真实下限以下**：4 条链缺下游环节，实际下游更多。

### 4.7 停用与重估条件

出现以下任一情况应重估：① 官方 position 列与 INB 目录对齐；② 链树补全 4 条链的下游环节；③ 全量企业级去重分游可得；④ 链主认定表入湖；⑤ 甲方确认 P17 映射（确认前所有三游读数都是「本工程口径」）。

## 五、结论与发布建议

### 5.1 可用结论

第一，12 链 41 环节全部映射（18/15/8），4 条链缺下游。第二，深圳名录 2,590 家，上链 1,471 家、可判游 1,367 家，上/中/下 = 1,007/743/738。第三，60.4243% 跨 ≥2 游，游归属计数 2,488，每企 1.82。第四，缺下游链涉及 909 对（26.0832%），下游被机械压低。第五，名录只覆盖全量 15.3481%，上游偏高部分是选择效应。第六，判部分支持。

### 5.4 后续

三条路径：① 甲方确认 P17；② 补全 4 条链的下游环节；③ 全量企业级去重分游。第二条最紧要——不补，下游读数永远是下限，补链分析会误判「深圳缺下游」。

## 附录 D　「上游 73.665%」该怎么读

这是本件最容易被误读的数，单独拆一层。

第一层，分母是 1,367 家「可判游的深圳名录企业」，不是深圳全部链上企业。名录是专利 ≥50 件的代理，覆盖全量的 15.3481%。

第二层，分子是「至少有一个上游标签」的企业，不是「只做上游」的企业。60.4243% 的企业同时有多个游标签，所以 73.665% 里包含大量「既做上游又做下游」的企业。

第三层，名录的专利阈值天然筛选研发型企业。上游（材料、设备、零部件）与中游（制造、集成）的专利密度高于下游（应用、服务、运营），所以名录本身就把分布推向中上游。若按全量 16,875 家算，上游占比很可能显著低于 73.665%——但全量没有企业级去重游归属，算不出来。

结论：可以说「在专利密集型深圳链上企业中，上游标签覆盖 73.665%」，不能说「深圳 73.665% 的链上企业在产业链上游」。发布时必须带「名录口径」四个字。
