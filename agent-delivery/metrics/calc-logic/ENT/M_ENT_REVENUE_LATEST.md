## 摘要

「营收」这一条在企业画像里是规模维的地基数：它决定企业在榜单上的位置、决定「大型/中型/小微」的分档、也决定上下游比对的量级。它的口径本身极简——每家企业取最近一个年度的营业收入——难点全部落在数据侧：哪一年算「最近」、金额是什么单位、没有值的企业怎么标。

本件在 gkx 侧把这件事拆成四步。第一步按 `org_id` 取 `MAX(year)` 那一行的 `operating_revenue`，得到 1,302 家。第二步把「有财务行但最新年营收为空」的 6,825 家单独识别出来，按 calc-logic 的口径置为「该企无法计算」，不写 0、不向前补年。第三步做单位审计：把年度财务宽表与年报资产表（`xsze`，文本「万元」）逐对比值，发现 70.62% 的记录相差整 10,000 倍，其中 703 对可判定为宽表漏乘、8 对为资产表标签错、724 对无外部锚不可判。第四步给出可用面：只有 ≥1 亿元的 118 家能对外排名。

结果必须分三层说。第一层是「有多少家能算」：1,302 家，占底册 0.6885%。第二层是「这些数长什么样」：中位数 16,553.27 元、P90 80,058,401.21 元、最大 29,800,924,733.43 元——中位数低到这个程度，本身就说明大量行的单位是万元而不是元。第三层是「哪些能对外用」：分档之后 ≤100 元的 66 行是明显错值、100 元—1 万元的 488 行只可能是万元口径、1 万—100 万元的 424 行同样可疑，真正落在「1 亿元以上」的 118 行才是营收该有的量级。

覆盖率的含义也要说清。0.6885% 不是「只有 0.69% 的企业有营业收入」，而是「只有 0.69% 的企业在这张表里留下了可用的营业收入数字」。年报资产表另有 6,596 家（最新年营收为正）能出数，但两表机构号未求交、单位互斥，只能给出「两表直接相加」的上界 9,040 家（4.7801%），不能宣称并集。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业分析 → 企业查询 → 企业画像**，页面形态是企业详情页顶部的基础信息卡，与「注册资本」「成立年份」「参保人数」并列。它同时被高级筛选的「企业规模」维度消费——按营收区间筛企业，是本条最直接的产品用法。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业分析 → 企业查询 → 企业画像 |
| 页面载体 | 企业详情·基础信息卡；高级筛选·企业规模 |
| 输出形态 | 每企业一个金额（附锚年） |
| 更新频率 | 年（calc-logic） |
| 粒度 | 企业（每 org 一条） |
| 关联Q | Q-E23 |

与同族三件的边界：`M_ENT_REVENUE_GROWTH_RATE` 用本件的逐年序列算同比；`M_ENT_PROFIT_MARGIN` 用本件做分母；`M_ENT_RD_INVESTMENT_RATIO` 同样以营收为分母。**本件的单位问题会传染给这三件**——分母若是万元被当成元，比率会整体放大一万倍。这是本件在族内的特殊地位：它不只是自己一个数，还是三个比率指标的分母源。

### 1.2 为什么需要这个指标

第一个用途是规模分档。政策口径里「大型/中型/小型/微型」的划分主要看营业收入与从业人数，营收是第一判据。没有这个数，企业规模只能靠注册资本猜，而注册资本与真实营收的相关性很低。

第二个用途是筛选与排序。高级筛选里「营收 1 亿元以上」这类条件是高频操作；榜单页按营收排序也是默认视图之一。这两处都要求「每企一个数 + 一个锚年」，缺锚年就会出现「2025 年的企业和 2014 年的企业排在一起」的荒谬榜单。

第三个用途是比率分母。利润率、研发强度、人均产值都以营收为分母。分母口径一错，比率全错，而且错得整齐——所有企业同向偏移，肉眼很难发现。本件因此把单位审计做成了独立章节，而不是附注。

### 1.3 需求文档是否给出定义方法

calc-logic 给了取数规则，王惠正本给了业务定义，两者在「单位」上冲突。

calc-logic：

```
SELECT org_id, revenue
FROM enterprise_finance_history t
WHERE t.data_year = (
  SELECT MAX(data_year) FROM enterprise_finance_history x
  WHERE x.org_id = t.org_id
)
```

> 无财务行或 `revenue` 空：**该企业无法计算**。不是整条指标无法执行。不挂产业。禁止抄 `enterprise_base.revenue_latest`。

王惠正本（v3.0）：

> 企业最新年度营业收入（单位：亿元），取最新报告期的营业收入。

> 源库表字段：gkx.dwd_org_annual_financial_info（org_id, operating_revenue, year）

两处差异有两处。其一，**单位**：正本写「单位：亿元」，calc-logic 不声明单位、直接取原值。库里的值两者都不是——中位数 16,553.27 若是亿元则是 1.65 万亿，若是元则是一家小卖部；实际是「部分行元、部分行万元」的混填。其二，**期间**：正本说「最新报告期」，calc-logic 说「MAX(year)」，本库只有年度行，没有季度或半年度，所以两者在本库等价，都落到年度。

本件按 calc-logic 落盘（原值、不换算），把单位问题作为独立审计项披露。换算成「亿元」是展示层的事，而且必须先定单位再除，否则会把混填放大 10,000 倍。

### 1.4 类似指标权威机构构建方法可行性

「企业年度营业收入」在官方与商业实践里有四条取法：

| 方法族 | 代表机构/实践 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 年报主表 | 国家统计局「四上」企业年报、上市公司年报 | 取企业年度利润表「营业收入」 | **最高（本件口径）** |
| B 税务申报 | 税务部门金税系统 | 按申报销售额 | 中（不可得，涉税数据不开放） |
| C 工商年报 | 市场监管总局年报公示 | 企业自主填报「营业总收入」 | 中（本库资产表即此类，占位串多） |
| D 估算模型 | 商业数据库（企查查/天眼查） | 行业均值 × 人数等 | 低（模型值，不可追溯） |

A 族是本件采用的口径，也是唯一能逐条追溯的。C 族在本库有对应表（`dwd_org_annual_report_asset`），但 527,034 行里 514,140 行是「企业选择不公示」占位串，能解析的只有 12,616 行——自主填报的天然缺陷，只能当补充。

B 族不可得：本库没有任何税务口径字段，也不应有。D 族被 calc-logic 明确排除（禁止模型估值），本件不涉及。

### 1.6 推测原意与推测定义

推测原意是：**企业详情页要一个「这家企业一年做多大生意」的规模数，允许部分企业没有，但不能用 0 冒充**。同时它要能当比率分母，所以必须带锚年。

据此给出主定义与两个对照定义：

$$ R_i = \text{operating\_revenue}_{i,\ \max(year)} $$

$$ \bar{R} = \frac{1}{|E|}\sum_{i \in E} R_i,\quad E=\{i: R_i \ne \varnothing\} $$

$$ C = \frac{|E|}{|B|},\quad |B| = 189{,}116 $$

本件交付 $|E|=1{,}302$、$C=0.6885\%$、$\bar R = 138{,}963{,}840.3824$ 元。依赖维度如下：

| 代号 | 依赖维度 | 类型 | 本件实测 |
|---|---|---|---|
| D1 | 年度营业收入金额 | 核心 | 部分（2,193 / 90,926 行非空） |
| D2 | 年度字段（锚年） | 核心 | 可得（2013—2025，13 个年份） |
| D3 | 企业主档（org_id ↔ 名称） | 核心 | 可得，189,116 行 |
| D4 | 金额单位 | 核心 | **不可得**（库内不声明，实测混填） |
| D5 | 产业归属 | 口径 | 不需要（本条不挂产业） |
| D6 | 境外营收 | 口径 | 不并（境外表 51 行，calc-logic 明示不并） |

D4 是本件的「软缺口」：表结构没有单位列，只能靠跨表比对推断。它不阻断计算，但阻断排名——这是本件判「部分支持」的第二重理由。

## 二、计算过程

### 2.1 总体思路与数据流

四步离线：取每企最新年、算覆盖与分布、做单位审计、给可用面。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 取最新年 | `dwd_org_annual_financial_info` 90,926 行 | 按 `org_id` 分组建栈，取 `MAX(year)` | 1,302 家 |
| 覆盖与分布 | 1,302 个金额 | 分位、量级分档、锚年分布 | §2.3 各表 |
| 单位审计 | 宽表 vs 资产表 2,032 对 | 逐对比值，按整倍数聚类 | 70.62% 为 10,000 倍 |
| 可用面 | 分档 + 外部锚 | 只保留 ≥1 亿元且经锚定的行 | 118 家 |

数据流上有一个取舍：宽表是 26 列，本件只投影 4 列（`org_id` / `year` / `operating_revenue` / `pure_profit`），再 `LEFT JOIN` 底册取名称与城市。之所以不用 `SELECT *`，是因为这张表带多个 text 列，宽投影会把 90,926 行的传输量放大一个量级，而本件只需要一个金额列。

分组的实现放在本地而不是 SQL：`GROUP BY org_id` 配 `MAX(year)` 在 MySQL 里要写窗口函数或自连接，而 90,926 行的窄投影拉到本地只占几 MB，本地用字典聚合更快也更好调试。这一步没有用任何近似——每家的锚年都是真实的 `MAX(year)`。

### 2.2 步骤 1｜按企取最新年与覆盖率

SQL 层面等价于：

```sql
SELECT f.org_id, f.year, f.operating_revenue
FROM gkx.dwd_org_annual_financial_info f
JOIN (SELECT org_id, MAX(year) AS y
      FROM gkx.dwd_org_annual_financial_info
      WHERE is_deleted=0 GROUP BY org_id) m
  ON m.org_id=f.org_id AND m.y=f.year
WHERE f.is_deleted=0 AND f.operating_revenue IS NOT NULL
```

结果 1,302 家。分母有三个层次，必须分开说：8,127 家（有财务行的机构）、1,302 家（有非空最新年营收）、189,116 家（底册全量）。对应的覆盖率分别是 16.0207%、0.6885%。前一个数回答「有财务记录的企业里多少能算营收」，后一个数回答「全部企业里多少能算」——产品说「覆盖率」时通常指后者。

有 6,825 家机构有财务行、但最新年营收为空。按 calc-logic 的口径，这些是「该企无法计算」，不是 0。这个区分很重要：如果按 0 入库，所有「营收为 0」的企业会在筛选器里被当成「没有生意」，而实际是「没有数据」。本件在产物里只落两种状态：有值、无值，不落 0。

年度锚点的分布同样值得看一眼：2014 年 476 家、2015 年 305 家、2016 年 172 家，三年合计 953 家，占 1,302 家的 73.2%。这说明这张表的「最新年」大量停在十年前——不是企业停业，而是数据采集在 2016 年之后就断了。2025 年只有 34 家，2024 年 28 家。

这个分布直接决定页面怎么写。如果只写「营收」，用户会以为是最新数据；实际上一半以上的企业是 2014—2016 年的数。页面必须把锚年一起显示，否则「最新营收」四个字是误导。

### 2.3 步骤 2｜金额分布与量级分档

1,302 个最新年营收的分位如下。这组数不能直接当「企业规模分布」读，因为其中混着两种单位。

| 分位 | 金额（元，原值） | 读法 |
|---|---:|---|
| P10 | 418.16 | 明显是万元口径（=418 万元？仍然偏小） |
| P25 | 2,623.55 | 同上 |
| P50 | 16,553.27 | 若是元，年营收 1.65 万，不可能 |
| P75 | 882,974.93 | 88 万元，小微企业量级 |
| P90 | 80,058,401.21 | 8,005 万元，中型企业 |
| P99 | 2,874,930,739.07 | 28.7 亿元，大型企业 |
| Max | 29,800,924,733.43 | 298 亿元（深圳市燃气集团 2025） |
| Min | -292.67 | 负值 1 家，保留原值不截断 |

按量级切五档，形状就清楚了：

| 量级段 | 家数 | 判断 |
|---|---:|---|
| < 1,000 元 | 207 | 不可能是年营收，单位必为万元或错值 |
| 1,000—10,000 元 | 346 | 同上；两段合计 553 家 |
| 1 万—100 万元 | 424 | 小微企业可能成立，也可能仍是万元 |

### 2.4 步骤 3｜单位审计：两表存同一个字面值

gkx 里有两张年报表都带「营业收入」语义：`dwd_org_annual_financial_info.operating_revenue`（double）与 `dwd_org_annual_report_asset.xsze`（文本「数值+万元」）。把同一机构、同一年份的两行配对，得到 2,032 对，逐对算比值：

| 比值形态 | 对数 | 解读 |
|---|---:|---|
| 恰好 1 倍 | 484 | 两表字面值相同，单位假设互相矛盾 |
| 恰好 10,000 倍 | 1,435 | 一方按元、一方按万元 |
| 其他 | 113 | 口径或年份错位 |
| 合计 | 2,032 | — |

10,000 倍占 70.62%。进一步拆：703 对可判定为宽表漏乘（资产表已是元，宽表字面值是万元）、8 对为资产表的「万元」标签错（该行实际是元）、724 对无外部锚不可判。典型例子：某机构 2015 年，资产表 62,650,700 元、宽表 6,265.07，比值 10,000——宽表少乘了一万。

为什么会出现这种混填？因为 `operating_revenue` 是 double 列，没有任何单位元数据，上游把「万元」的原值直接灌了进来，而另一批上游把「元」灌了进来。两种批次混在同一列，任何聚合都会把两类相加。

这也是「分档」比「均值」更可用的原因：分档只看量级，不要求精确；均值要求同单位，而本列不满足。所以本件不给「平均营收」这个数——给了就是错的。

可用面的界定据此而来：只有 ≥1 亿元的 118 家，量级上不可能是万元误填（万元口径下 1 亿元意味着 1 万亿，不存在）。这 118 家里有 3 家做过外部锚定：保利房地产（集团）2014 年 1,090.56 亿元、深圳市燃气集团 2023 年 309.29 亿元、广东海大集团 2016 年 271.85 亿元，均与公开财报同量级。

### 2.5 步骤 4｜跨表交叉验证：年报资产表能补多少

`dwd_org_annual_report_asset` 有 527,034 行、49,997 家机构，`xsze` 是「数值+万元」文本。正则 `^(-?\d+(?:\.\d+)?)万元$` 能解析 12,616 行（占 12,621 行「万元」文本的 99.9604%），覆盖 7,738 家；其中最新年营收为正的 6,596 家（85.2417%），中位数 21,082,463.52 元。

这张表的另一半是占位串：514,140 行「企业选择不公示」，占全表 97.5535%。这个比例说明它不是「营收表」，而是「工商年报公示表」——大多数企业选择不公示营收。所以它只能当补充：能补 6,596 家，但这 6,596 家是「愿意公示」的子集，系统性偏向国企、上市公司与规范经营的企业。

两表能不能相加？不能。机构号未求交，且单位互斥（§2.4）。本件只给一个上界：1,302 + 7,738 = 9,040 家，占底册 4.7801%。这个上界的含义是「即使两表完全不相交，最多也只有 9,040 家能出营收」——它比任何「约 1 万家」的模糊说法都更可靠，也不夸大成并集。

上市财务表还有 971 家能出营收（`dwd_org_stock_finance_info`，40,239 行，最新报告期 202603），但这张表被 `M_ENT_REVENUE_GROWTH_RATE` 的 calc-logic 明令禁止替代年报；本件同样不并，只作量级参照。

这张榜单暴露的不是单位问题，而是**时点不可比**：Top10 里 6 家的锚年是 2014—2016，2 家是 2025。跨 11 年意味着两行金额分属不同价格水平、不同会计年度，甚至不是同一版会计准则；把它们放进同一张榜单排序，语义上不成立。单位问题是另一条独立的病（§2.4），年份跨度只能证明时点不可比，不能拿来当单位问题的证据。

榜单可用性真正要回答的是「Top-N 能不能拉长」。把 `(org_id, year)` 配对后按 fin 侧量级分桶，看两表是否自洽（比值≈1 = asset 的「万元」标签正确；比值≈10,000 = 两表字面值相同、单位假设互斥）：

| fin 量级 | 对数 | ratio≈1 | ratio≈10⁴ | 自洽率 |
|---|---:|---:|---:|---:|
| <1 万元 | 713 | 1 | 703 | 98.74% |
| 1 万—100 万元 | 715 | 25 | 657 | 95.38% |
| 100 万—1 亿元 | 353 | 222 | 67 | 81.87% |
| 1 亿—100 亿元 | 242 | 227 | 8 | 97.11% |
| ≥100 亿元 | 9 | 9 | 0 | 100.0% |

方向就藏在这张表里。fin <1 万元的 713 对里有 703 对相差整 10,000 倍——这些行的 fin 被压小了 10,000 倍（万元当元填），按 fin 排序时只会被**挤到榜尾**，不可能「混入 Top200」。Top200 复核也印证了这个方向：191 对有 asset 配对，其中 169 对比值≈1、11 对呈 10⁴ 倍且全部是 asset 文本把元写成万元（折元后落在数千亿元以上，超过本表最大企业一个数量级），**没有一对是 fin 侧被压小的万元误填**（`top200_check.suspicious_high_value = 0`，字面可解释的合计 180 对）。

所以 Top-N 的真实风险不是「被污染」，而是**漏选**。1 万—100 万元的 657 对，两边量级都合理、无外部锚不能定向；若它们实为万元口径，真值就落在 1 亿—100 亿元，本该进榜却进不来。由此有三个结论：其一，「118 家可用面」是**下界**而不是上限，它只是「量级上确定无疑」的那一档；其二，榜单失真的方向是**漏**而不是**错**——榜上的行不会因单位被抬高一万倍，榜外的行却可能因被压小一万倍而消失；其三，对业务方要说清「榜单只到 118 名」是**分母不足叠加单位未归一导致的漏选**，不能写成「数据只支持 118 家」，前者会随单位列补齐而扩容，后者听起来像永久的容量上限。

### 3.3 数据量、覆盖与代表性

覆盖率三个口径：行覆盖 2.4119%（2,193 / 90,926）、机构覆盖（表内）16.0207%（1,302 / 8,127）、底册覆盖 0.6885%（1,302 / 189,116）。三个数的分母不同，产品说「覆盖率」时应明确指哪一个。

代表性上有一个明显偏倚：锚年集中在 2014—2016（953 家，73.2%），2023—2025 只有 89 家。也就是说，本件算出的「营收」在时间上主要是十年前的数据。用它做「当前规模」判断会系统性低估增长行业、高估衰退行业。

另一个偏倚是机构类型：能出数的 1,302 家里，Top10 全是大型国企或上市公司。中小微企业在这张表里几乎只剩「有行但无值」。这不是随机缺失，而是采集强度与披露意愿的双重筛选。

### 3.4 结构支持判定

结构侧没有硬缺口：`org_id` 是主键、`year` 是整数、`operating_revenue` 是 double，`uk_org_id_year` 保证一企一年一行。取最新年的 SQL 在任何 MySQL 5.7+ 上都能跑。

真正的结构缺口是**缺少单位列**。如果表里有一列 `unit`（元/万元），70.62% 的混填就能被机械纠正；现在只能靠跨表比对，而跨表比对有 724 对无外部锚、113 对口径错位，合计 837 对判不了。

## 四、数据缺失情况

### 4.1 缺口清单

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 6,825 家最新年营收为空 | 不可计算 | 标「无法计算」，不写 0 | 上游补采年报 |
| 单位列缺失 | 70.62% 记录量级不可判 | 只开放 ≥1 亿元 118 家 | 增加 `unit` 元数据或灌数时归一 |
| 结果表 `enterprise_finance_history` | 无现成结果面 | 现算 | ETL 落表 |
| 2023—2025 覆盖薄 | 锚年停在十年前 | 页面强制显示锚年 | 补采近三年 |
| 境外营收 | 不并 | 明示不并 | 境外表仅 51 行，无法支撑 |

### 4.2 逐条影响

「最新年为空」是最直接的缺口。6,825 家不是小数，占表内机构的 84%。它们出现在企业列表里时只能显示「暂无数据」，产品必须接受这个状态，不能用行业均值填充——填充值无法追溯，一旦被引用进政策报告就是硬伤。

「单位缺失」是最隐蔽的缺口。它不影响「有没有数」，只影响「数是多少」。66 行 ≤100 元、488 行 100 元—1 万元，这些行如果直接展示，用户看到的是「年营收 88 元」这种荒谬值。本件的处置是「原样输出 + 分档标注」，展示层按分档决定是否显示小数位。

「结果表缺失」不影响档位——部分支持本来就允许没有结果面。它只影响工程效率：每次查询都要现算，1,302 行的量级下无所谓，若覆盖扩到 10 万家就需要落表。

「锚年偏旧」是产品问题而非数据问题。数据就是十年前的，硬说成「最新」是表述错误。处置是锚年随值一起返回。

### 4.3 明确不做什么（禁止的替代）

- 不把 6,825 家空值按 0 入库——0 会被筛选器当成「零营收企业」。
- 不把资产表的「企业选择不公示」当 0——那是「拒绝披露」，不是「没有营收」。
- 不把上市财务表并进年报口径——calc-logic 明禁，且上市样本与全量法人不是同一总体。
- 不用行业均值/中位数填充缺失——填充值不可追溯，违反「每个数字都要能复算」。
- 不做单位自动换算后求和——混填下求和必错，且错得无法被发现。
- 不宣称「两表并集 9,040 家」——那是上界，不是并集。

### 4.4 若甲方补齐后的口径升级路径

| 补齐条件 | 口径变化 | 档位变化 |
|---|---|---|
| 上游补采近三年年报 | 锚年前移，时效性改善 | 不改变档位（覆盖仍低） |
| 增加单位列并归一 | 可用面从 118 家扩到 1,300 家 | 部分支持 → 完全转换支持 |
| 落 `enterprise_finance_history` | 结果面直查 | → 完全直接支持（若量足） |
| 打通工商年报全量 | 覆盖到 5 万家级 | 部分支持 → 完全转换支持 |

**基期声明**：`base_years_used` = 2013—2025（13 个年份，全部有营收行）；`base_years_missing` = []（库内财务表不含更早年份）。各企锚年不同，跨企横比必须先对齐年份；某企最新年为空时不向前补年、不写 0。

## 附录 F 口径问答

**问：1,302 家与 8,127 家差在哪？**

答：8,127 家是「有财务行」的机构，1,302 家是「最新年营收非空」的机构。中间 6,825 家只有资产、负债、利润等列有值，营收列为空。

**问：为什么中位数只有 16,553.27 元？**

答：因为这一列混着「元」和「万元」两种单位。若全是万元口径，中位数是 1.65 亿元；若全是元，则是一家小卖部。真实情况是两者混填，中位数落在中间没有意义。

**问：能不能先统一换算成万元再算均值？**

答：不能。换算需要知道每行的原始单位，而单位信息不存在。按 10,000 倍聚类只能判出 703 对，还有 724 对判不了；强行换算是给 724 行编造单位。

**问：9,040 家是什么？**

答：两张年报表直接相加的上界（1,302 + 7,738）。两表机构号未求交、单位互斥，所以不能说「并集 9,040 家」。

**问：Top10 里有 2014 年的企业，能用吗？**
