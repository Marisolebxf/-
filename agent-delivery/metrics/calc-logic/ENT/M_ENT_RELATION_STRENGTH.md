## 摘要

关系强度要回答的是「这两家企业之间的关系有多紧」。calc-logic 把它落成三档：投资金额 $>1$ 亿元为强、$1{,}000$ 万至 $1$ 亿元为中、$<1{,}000$ 万元为弱。

| 读数 | 值 |
|---|---|
| 投资边 | 46,967 行 |
| 有金额边 | 43,274 行（92.137%） |
| 金额中位 / p99 / 最大 | 500 / 300,000 / 744,013,552（元） |
| 强 / 中 / 弱（元口径） | 3 / 3 / 43,268 |
| 强 / 中 / 弱（万元口径） | 4,830 / 12,359 / 26,085 |
| 有金额边的企业 | 17,794 家 |
| 企业边数中位 / 最大 | 1 / 222 |
| 股权比例中位 | 50.0% |
| 供应链维覆盖率 | 0.0% |
| 产业链维覆盖率 | 0.0% |
| 判档 | 部分支持 |

先把最刺眼的事实放在最前面：**按「元」口径，43,274 条有金额边里只有 6 条达到「中」以上**（3 强 + 3 中），其余 43,268 条全部落在弱档，弱档占 99.9861%。这不是「企业之间的关系都很弱」，而是**分档阈值与数据分布严重错位**：金额中位数 500 元、p90 才 13,780 元、p99 才 300,000 元，整条分布被压在「1,000 万元」这条线以下四个数量级。用一把为「亿元级并购」设计的尺子去量「百元级出资」，量出来的必然是「全是弱」。

更麻烦的是单位。calc-logic 原文写「金额单位以 `investment_amount` 元为准」，但同一段又要求与 `enterprise_invest.investment_amount` 统一——而那张表在 gkx 不存在，无法对齐。如果实际单位是「万元」，同一批数字会变成 4,830 强 / 12,359 中 / 26,085 弱，结论完全反转。**同一份数据、两种单位、两套结论**，这件事必须在发布前由甲方闭合，不能由写手挑一个好看的。

第三个事实是辅证。calc-logic 明确列了两条辅证：供应链 `relation_strength` 与产业链 `chain_score`。实测两张表在 gkx 逐字命中 0、模糊词 `supply` / `supplier` / `cooperat` 表名命中 0。没有辅证，主口径就只是「按金额切三档」，无法回答「这条边是不是真的供应关系」。本件因此判部分支持，并把两维覆盖率记为 0（结构性无源），而不是拿投资边冒充供应链。

### 1.2 为什么需要「关系强度」

风险洞察场景里，「A 投了 B」这条边本身信息量很低：投 1 万元和投 7 亿元，风险传导能力差三个数量级。图谱如果不区分强度，一条边就是一条线，风控人员无法判断「哪条边值得跟」。关系强度的作用是把二值边变成有序档，让图谱能按强度着色、按强度剪枝。

它同时是「供应链风险」的替代入口：真正的供应链关系（供应商/客户）在库内没有表，风险传导只能先用资本边近似。这个替代必须在口径层声明——资本联系强不等于供应依赖强，一家企业可以被大额投资却完全不采购对方的货。

### 1.3 口径定义

calc-logic 的主口径是一个分段函数：

$$Strength(e)=\begin{cases}\text{强} & amount(e) > 1\times10^{8}\ \text{元}\\\text{中} & 1\times10^{7}\le amount(e)\le 1\times10^{8}\ \text{元}\\\text{弱} & amount(e) < 1\times10^{7}\ \text{元}\end{cases}$$

辅证两条：供应链 `relation_strength`（直接给档）、产业链 `chain_score`（作协同评分）。calc-logic 没有写「三源冲突时怎么裁决」，也没有写「辅证缺失时主口径是否仍然成立」。这两个空白是本件判档的直接原因。

本件在实现层做了三个补充约定，全部写进产物 `params`：

第一，**边界归属**：$>10^8$ 为强、$\ge10^7$ 且 $\le10^8$ 为中、$<10^7$ 为弱。恰好 1 亿元的边归中档，不归强档——与 calc-logic 的「1000万~1亿元=中」一致。

第二，**金额为空不猜**：46,967 行里 3,693 行 `investment_amount` 为空，这些边不参与分档（`n_edges_scored = 43,274`）。不按 0 摊进弱档，否则「没披露金额」会被读成「金额极小」。

第三，**单位双算**：主口径按元，另出万元口径作敏感性。两套结果都落盘（`tier_counts_yuan` / `tier_counts_wan_sensitivity`），让甲方在闭合单位时能直接看到差多少。

### 1.4 计算公式与本批实现式

```python
def tier(amount, unit_mult):        # unit_mult=1 元；10000 万元
    v = amount * unit_mult
    if v > 1e8:  return "强"
    if v >= 1e7: return "中"
    return "弱"
```

注意 `unit_mult=10000` 的写法：如果原始数字的单位是「万元」，换算成元要**乘** 10,000，不是除。这是最容易写反的一步——写反会把万元口径算成「比元口径更弱」，两套结果都变成全弱，敏感性检验就失效了。本件第一次实现就写反过，靠「万元口径应该更强」这个先验抓了回来。

## 二、计算过程

### 2.1 装载与字段核对

脚本只连一次 gkx，顺序拉两张表：`dwd_org_invest_info` 取 `org_id` / `name_cn` / `inv_org_id` / `inv_name` / `investment_amount` / `investment_ratio` 六列；`dwd_org_shareholder_info` 只取行数与 `ownership_percentage` 空值数（作辅证分布对照）。拉完先做字段级核对：金额列 46,967 行里 43,274 行非空（92.137%）、9 行为 0；比例列 46,362 行非空（98.7119%）、最大 1.0、中位 0.5。

这一步抓到一个关键事实：**`investment_ratio` 是 0—1 的小数，不是百分数**。若按百分数读，中位 0.5 会被当成 0.5%，几乎所有边都成了「极低持股」；实际中位是 50%。本件在产物里同时落 `ratio_stats_pct`（已 ×100）与 `ratio_raw_max = 1.0`，让口径不可能被误读。这类「量纲藏在取值域里」的坑，只看列名是发现不了的。

### 2.2 分档的两套口径

按元口径跑一遍：强 3 条、中 3 条、弱 43,268 条。三条强边分别是 744,013,552 元（广州市城市建设投资集团 → 广发银行）、212,099,341 元（广东粤财资产管理 → 广发银行）、122,641,550 元（广东宏禧瑞投资合伙 → 广东宏科建设）。三条中边都恰好卡在 1,000 万—2,000 万之间，其中两条是 10,000,000 元整（深圳市国资委 → 深圳市安居集团、深圳市财政局 → 深圳市引导基金）。

按万元口径跑一遍：强 4,830 条（11.1614%）、中 12,359 条（28.5599%）、弱 26,085 条（60.2787%）。同一批数字，弱档从 99.9861% 掉到 60.2787%，强档从 0.0069% 涨到 11.1614%。这不是微调，是结论反转。

两套口径谁对？本件不能替甲方决定，但可以给判据：三条强边的金额 7.44 亿、2.12 亿、1.23 亿——如果是元，这是三笔真实的大型投资（城投投广发、粤财投广发），量级合理；如果是万元，7.44 亿万元 = 7,440 亿元，超过任何一家城投的净资产，不合理。所以**头部样本支持「元」口径**。但反过来，中位数 500 元作为「投资金额」又偏小（500 元投不出一家企业），说明**列内可能混着不同量纲的行**——这正是旧稿在镜像面遇到的同一问题。

### 2.3 分布与阈值错位

| 分位 | 金额（元） |
|---|---:|
| p25 | 100 |
| p50 | 500 |
| p75 | 2,500 |
| p90 | 13,780 |
| p99 | 300,000 |
| max | 744,013,552 |

阈值 $10^7$（1,000 万元）落在 p99（300,000）之上 33 倍处。也就是说，**99% 的边在阈值下方两三个数量级**，分档实际上只区分了「头部 6 条」与「其余全部」。这不是分档算法的问题，是阈值与数据尺度不匹配。

一个可选的补救是「按分位数分档」（如 p90/p50），但那会偏离 calc-logic 的固定阈值，属于口径变更，不能在改造件里静默做。本件保留原阈值、把错位事实写进产物（`amount_stats_yuan` 与 `derived`），供甲方决定是否改阈值。

### 2.4 股权比例的位置

`investment_ratio` 分布：≥50% 共 23,719 条（51.1604%）、20%—50% 共 5,938 条（12.8079%）、<20% 共 16,705 条（36.0317%）。中位 50%、p75 100%——大量「100% 持股」的边，说明这张表里子公司/全资分支占比很高。

## 四、数据缺失情况

### 4.1 供应链辅证：结构性无源

`enterprise_supply_chain` 在 gkx 与 live 均不存在（逐字 0、模糊词 0）。calc-logic 要的 `relation_strength` 列无处可取，覆盖率 0.0%。本件不拿投资金额冒充供应链强度——那是两种完全不同的关系，混用会让「供应风险」变成「股权风险」。

### 4.2 产业链辅证：结构性无源

`enterprise_industry_chain.chain_score` 同样无表。gkx 里有产业链标签类的表（如 `dwd_org_industry_tags`），但标签是「属于哪条链」，不是「协同评分」，语义不同，不能替代。本件不拿标签冒充评分。

### 4.3 单位未闭合

calc-logic 写「元」，但列内分布（中位 500）与头部（7.44 亿）差 6 个数量级，无法排除混量纲。旧稿曾在镜像面按万元重算，得到「强 15.6% / 中 30.0% / 弱 54.4%」的旧版读数（已作废口径）；本件按元口径得到 0.0069% / 0.0069% / 99.9861%。两者差三个数量级，说明单位不是细节，是结论本身。

### 4.4 比例分档阈值未定义

calc-logic 的「股权占比分档阈值」标注为「待建」。没有阈值，比例只能作分布展示，不能进分档。本件因此没有把比例并入强度——否则等于自造阈值。

### 4.5 年度与事件时间缺失

表里只有 `created_time` / `updated_time`，没有投资事件时间。无法做「某年新增强关系」「关系存续时长」，也无法把强度变化做成序列。

### 4.6 不得外推的三件事

1. **不得读作供应链强度**：投资额大不等于采购量大。
2. **不得用 3 条强边代表全网**：99.9861% 的边在弱档，头部样本不能外推。
3. **不得跨单位比较**：元口径与万元口径的档位分布不可混用。

### 4.7 停用与重估条件

出现以下任一情况应重估：① 单位闭合（元或万元二选一）；② `enterprise_supply_chain` 入湖（辅证可加）；③ `chain_score` 有表（第二辅证可加）；④ 比例分档阈值定稿（比例可进档）。

### 6.3 与旧稿的取舍

旧稿（20261020 镜像面）判「部分支持」，理由是「底层关系表为演示图，结构可复现但无实证意义」。本版不再引用演示图，改为 gkx 真实投资边；判档仍为「部分支持」，但理由换了：旧稿缺的是「数据可信度」，本版缺的是「两条辅证维 + 单位未闭合」。同一个档位、两个不同的缺口，返工时不能照抄旧理由。

三条路径：① 甲方闭合单位；② 供应链表入湖；③ 比例阈值定稿。三者任一落地都要重跑本件并重写档位分布——不是调参，是换口径。

## 附录 D　单位问题的判定过程

单位这一步不是「查文档」能解决的，因为 calc-logic 只写了一个字「元」，而列内分布同时存在两种量级的证据。本件用了三条互证：

第一条，**头部合理性**。三条强边 7.44 亿 / 2.12 亿 / 1.23 亿，按元读是三家机构对广发银行等标的的真实大额投资；按万元读则是 7,440 亿元级别，超过任何一家城投的资产规模。头部支持元。

第二条，**中位合理性**。中位 500 按元读是「500 元出资」，作为股权投资偏小；按万元读是「500 万元出资」，更像真实交易。中位支持万元。

第三条，**列内混量纲的可能性**。两条证据指向相反方向，最可能的解释不是「整体单位错」，而是「列内混着不同来源的行」——大额行按元记录、小额行按万元记录。旧稿在镜像面已观察到同类现象（「列内混有 2 条元的行」）。

结论：单位不能靠单条证据裁定，必须由甲方给数据字典或抽样核对原始凭证。本件把两套档位都落盘，就是为了让这个裁定有据可依，而不是让写手替甲方选一个。
