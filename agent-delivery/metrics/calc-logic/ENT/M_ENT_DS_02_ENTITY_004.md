## 摘要

「技术点影响力」是科学技术全景页面的排序算子：图谱里每个技术点关联着企业、机构、人才、专利、论文，指标要给每个技术点算一个综合影响力，再按影响力把关联实体排序。正本的口径很清楚，两维加权——关联规模与关联实体影响力，权重 $w_1/w_2$ 待会签。

问题在于，**这三个词在 gkx 里都找不到落点**。

先看「技术点」。正本要求技术点是图谱节点中 `node_type` 为技术实体的节点。gkx 280 张表里没有 `graph_node`，也没有任何 node/edge/graph 语义的表（表名扫描 0 命中）。技术点连本体都不存在，谈不上节点类型。

再看「技术点—实体边」。正本给了三条路径：`graph_edge`、`enterprise_graph_rel`、`dwd_org_base_info_patent_rel`。三张表在 gkx 全部不存在（patent_rel 语义 0 命中）。也就是说，即使我们手工造出技术点，也没有边把它连到企业。

最后看「影响力」。正本要求 `AVG(tech_power_index)` 或 `pagerank_score` / `centrality_norm`。列名扫全库 5 组模式（tech_power、centrality、pagerank、influence、tech_point）全部 0 命中——**gkx 没有任何一列叫这些名字**。

三处全断，但本件没有停在「不可算」上。正本禁止用 PATH 中心度或 `M_SVC_GRAPH_INFLUENCE` 顶替，但没有禁止用**专利分类**作为技术点的代理。于是本件做了两处替换，并在产物里逐条声明：

1. **技术点 → IPC 小类（IPC4）**：`dwd_patent` 的 IPC 分类共 **634 个** IPC4，每个 IPC4 视作一个技术点；
2. **关联实体 → 该 IPC4 下的专利申请人**：去重后 **134,152** 个申请人名，其中 **122,563** 个能在底册匹配（91.3613%）；
3. **关联实体影响力 → 关联企业中持官方认定资质的占比**：用 `dwd_org_tech_tag` 的 55 类资质作质量信号，替代不存在的 `tech_power_index`。

合成公式（等权，因 $w_1/w_2$ 未定义）：

$$I_k=100\times\left(0.5\,\tilde{S}_k+0.5\,q_k\right),\qquad \tilde{S}_k=\frac{\ln(1+n_k)}{\max_j\ln(1+n_j)},\qquad q_k=\frac{m_k}{b_k}$$

其中 $n_k$ 是该 IPC4 的去重申请人数、$m_k$ 是其中有资质的企业数、$b_k$ 是其中能匹配底册的企业数。

结果：634 个技术点，影响力区间 **3.5453—70.2514**，中位 **48.4575**，均值 **47.1002**，p90 **59.1475**。最高的是 G06F（电数字数据处理），$n=17{,}599$、专利 190,077 件、$q=40.5027\%$、$I=70.2514$；其次是 G06T（69.5418）、G06V（69.1684）、G06Q（68.6104）、H04L（68.5355）。最低的 5 个技术点都是只有 1 家企业、1 件专利的冷门小类，$q=0$，$I=3.5453$。

**为什么最高只有 70.25？** 因为两项都取不到满分：规模项只有 G06F 是 1（它是最大值），质量项需要关联企业 100% 有资质，而实际最高只有 58.4388%（G06N）。$0.5\times1+0.5\times0.405=0.7025$。这不是公式写错，是代理口径的必然上限——**任何用「资质覆盖率」当质量信号的版本，都不可能到 100**。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

功能模块是**科技信息展示系统 → 科技发展态势 → 科学技术全景**（SRS 序号 27）。页面中心是一张技术点网络图，点某个技术点，右侧列出关联实体（企业、机构、人才、专利、论文），**按影响力降序**，优先展示重要实体。本件算的就是这个排序键。

### 1.2 为什么需要这个指标

第一，**全景图没有排序就没法读**。一个技术点可能关联几千家企业，全部平铺等于没有信息；按影响力排序，用户先看到的是「这个技术点上最强的玩家」。

第二，**它支撑技术点优先级判断**。哪些技术点是「热且强」的（规模大、关联企业质量高），哪些是「冷但精」的（规模小、质量高），需要两个维度一起看。

第三，**它最容易被「有张图」骗过去**。图谱页面看起来什么都有，节点、边、权重一应俱全；但图谱里的节点类型没有「技术实体」，边也没有技术点—实体关系。没有这两样，影响力就无从算起。

### 1.3 需求文档是否给出定义方法

**给了目标，没给定义。** 需求原句是「系统根据实体与技术点的关联强度、影响力等指标自动排序，优先展示重要实体」。以下五项未定：

1. **技术点是什么**：图谱节点？IPC 分类？关键词聚类？
2. **关联强度怎么算**：共现次数？边权重？专利件数？
3. **影响力怎么算**：企业技术力？中心性？还是营收规模？
4. **两个维度怎么合成**：加权？相乘？排序后取交集？
5. **权重是多少**：正本只写 $w_1/w_2$，没给值。

正本把这五项里的第 1、3 项锚定在图谱表上，但 gkx 没有那些表；第 5 项明确未签。本件对五项的处理是：IPC4 作技术点、专利件数与申请人数作规模、资质覆盖率作质量、等权合成、不做阈值判定。

### 1.6 本报告的口径与边界（须与甲方会签）

**公式（代理口径，权重等权）**：

$$I_k=100\times\left(0.5\,\tilde{S}_k+0.5\,q_k\right)$$

$$\tilde{S}_k=\frac{\ln(1+n_k)}{\max_{j}\ln(1+n_j)},\qquad q_k=\frac{m_k}{b_k}$$

| 符号 | 含义 | 代理来源 |
|---|---|---|
| $k$ | 技术点 | IPC4（634 个） |
| $n_k$ | 关联规模 | 该 IPC4 下去重申请人名数 |
| $b_k$ | 可匹配底册的关联企业数 | 申请人名 ∩ `dwd_org_base_info.name_cn` |
| $m_k$ | 其中有官方资质的企业数 | $b_k$ ∩ `dwd_org_tech_tag` |

**五条边界**：

1. **技术点是 IPC4，不是图谱技术实体**。IPC4 是专利分类的最小可比单元之一（如 G06F「电数字数据处理」），一个 IPC4 覆盖的技术范围远大于一个「技术点」；
2. **规模项与质量项的分母不同源，但不交叉相除**。$n_k$ 用全部申请人名（含未匹配底册的 8.64%），$q_k$ 的分子分母都限定在底册内主体（$m_k\subseteq b_k$）。两个子项各自归一后加权，不存在「分子分母不同母体」的除法；
3. **质量项是资质覆盖率，不是技术力**。它度量「这个技术点上，有官方认定的企业占多少」，不度量技术先进性；
4. **等权是本件默认**。$w_1/w_2$ 未签，会签后必须重算并同步改正文；
5. **不给阈值判定**。正本没有「多少算高影响力」的定义，本件只给排序与分布。

## 二、计算过程

### 2.1 技术点的三种可能载体，为什么选 IPC 小类

技术点要有三个属性：可枚举、可关联到企业、有稳定的粒度。候选有三：

**候选一，图谱节点。** 正本首选。gkx 没有图谱表，直接排除。

**候选二，专利关键词聚类。** `dwd_patent` 有关键词列，可以聚类出技术主题。问题是聚类结果不稳定——换一次聚类算法、换一个随机种子，技术点集合就变了，指标无法复算；而且聚类出的「技术点」没有标准名称，UI 上没法展示。

**候选三，IPC 小类。** 国际专利分类是国际标准，634 个 IPC4 可枚举、有官方名称、每件专利都带分类号。缺点是粒度粗（G06F 一个大类下有几十万件专利），优点是**可复算、可解释、可展示**。

本件选三。这不是最优解，是在「能算」与「算得稳」之间取交集。IPC4 到「技术点」的语义损失，必须在 UI 文案上体现——页面上应写「技术领域（IPC 小类）」，不能写「技术点」。

### 2.2 为什么不能用 PATH 中心度或图谱影响力顶替

正本有一句硬约束：「禁止用 PATH 中心度/关键节点或 `M_SVC_GRAPH_INFLUENCE` 顶替（见 ENT-D04 / ENT-B03）」。这句不是建议，是口径红线，原因是三者对象不同：

- `M_TECH_PATH_CENTRALITY` 的节点是**技术路径**（专利引用链上的位置），度量的是「这项技术在引用网络里多关键」；
- `M_SVC_GRAPH_INFLUENCE` 的节点是**服务机构**，度量的是「这家机构在服务网络里多中心」；
- 本指标的节点是**技术点**，度量的是「这个技术点关联了多少企业、这些企业质量如何」。

拿前两者的分数贴到技术点上，等于用「引用网络位置」冒充「产业关联规模」。两者可能相关，但不是同一个量，且无法验证。

### 2.3 否定性证据：表名与列名双扫

**表名扫。** `_work_gkx21/GKX_INVENTORY.json` 是 280 张表的逐表 `COUNT(*)` 清单，按语义关键词扫：

| 关键词组 | 命中表数 | 说明 |
|---|---:|---|
| graph / node / edge / central / pagerank / tech_point | 0 | 无任何图谱或中心性表 |
| patent_rel / tech_rel | 0 | 无技术点—专利关联表 |

**列名扫。** 查 `information_schema.columns`，`table_schema='gkx'`，五组列名前缀：

| 列名模式 | 命中 |
|---|---:|
| `%tech_power%` | 0 |
| `%centrality%` | 0 |
| `%pagerank%` | 0 |
| `%influence%` | 0 |
| `%tech_point%` | 0 |

两次扫描都是**全量**（280 张表全在清单里、information_schema 覆盖全库），不是抽样。所以「gkx 没有这些承载」是实测结论，不是推测。

需要说明的是：如果查询过程被信号终止或超时，本件不会把它记成「0 命中」。本次两次扫描都正常返回（表名扫是本地 JSON，列名扫是轻量元数据查询），因此结论可用。

### 2.4 关联规模：134,152 个申请人名怎么来的

`dwd_patent` 有 2,939,895 行、55 列，按 IPC 与申请人聚合后得到 581,585 行「IPC4 × 申请人名 × 件数」的组合，落在 `code/_snapshots21/patent_ipc4_by_name_20261021.json`（30 MB）。

去重后：

- **634 个** IPC4；
- **134,152 个** 不同的申请人名；
- 单点最大 **17,599** 个申请人（G06F），中位 **257** 个。

申请人名是自由文本，同一家企业可能写成「华为技术有限公司」与「华为技术有限公司深圳分公司」两个名字，本件**没有做名称归一**。后果是规模项略偏高（同一主体被计两次），但方向一致、且对所有 IPC4 同向影响，不改变排序的量级。这一条必须写进复用说明：**$n_k$ 是「申请人名数」，不是「企业数」**。

匹配底册用精确等值（`name_cn`），命中 **122,563** 个（91.3613%）。剩下 8.64% 匹配不上，主要是个人申请人、境外主体、名称变更。它们计入 $n_k$，但不计入 $b_k$——这就是 §1.6 第 2 条说的「两个子项分母不同源」。

### 2.5 关联实体影响力：为什么用资质覆盖率替代 tech_power_index

正本要的 `tech_power_index` 在 gkx 不存在（列名扫 0 命中），`enterprise_centrality` 也不存在。可选替代有三：

**替代一，专利件数均值。** 用「关联企业的平均专利数」当质量。问题是它与规模项高度共线——专利多的技术点，关联企业专利也多，两个子项会重复计同一个信号，合成后退化为单维排序。

**替代二，企业规模（注册资本/营收）。** 营收覆盖只有 11.66%（见 `M_ENT_STAR_BASIC_INFO`），缺口太大；注册资本几乎全有，但它度量的是「有钱」不是「有技术」。

**替代三，资质覆盖率。** 用 `dwd_org_tech_tag` 的 55 类资质作「官方认定」信号：一家企业如果有高企、专精特新、小巨人等标签，说明它的技术能力被政府认定过。覆盖率 $q_k$ 就是「这个技术点上，被认定过的企业占多少」。

本件选三。理由是它与规模项**不共线**：规模大不代表质量高（G06F 规模最大，$q$ 只有 40.5027%；G06N 规模只有 1,357 家，$q$ 高达 58.4388%）。两个子项一起看，才能区分「大而杂」与「小而精」。

代价也要说清：资质是**认定结果**，有滞后性（认定周期通常 1—3 年），且偏向规模较大的企业；对新兴技术点（如具身智能相关 IPC），资质覆盖会系统性偏低。这不是随机误差，是方向性偏差。

### 2.6 归一与合成：为什么用 log，为什么等权

规模项用 $\ln(1+n_k)$ 而不是 $n_k$，原因是分布极度右偏：最大 17,599、中位 257，两者差 68 倍。如果线性归一，G06F 会是 1，中位数技术点只有 0.0146（$258/17{,}600$），所有技术点挤在 0 附近，排序失去意义。取对数后，中位数技术点的归一值约 0.79（$\ln(258)/\ln(17600)$），分布被拉开到可用区间。

质量项本身就是 0—1 的比例，不需要再归一。两项等权，是因为 $w_1/w_2$ 未签，等权是唯一不带主观倾向的选择。等权的后果是：**质量项的实际影响被放大**——因为它的取值区间是 0—0.58，而规模项的区间是 0.09—1，两者对最终分的贡献量级接近，质量项的边际变化更敏感。

合成后不做二次归一，直接乘 100 输出。这样分数的含义是「两个归一子项的等权平均 × 100」，可逐项拆解、可复算。

## 四、数据缺失情况

### 4.1 缺口的后果归因

1. **技术点粒度错位**：IPC4 是「技术领域」，不是「技术点」。G06F 一个类下有 17,599 个申请人，把它称为一个技术点，UI 上会显得荒谬；
2. **影响力语义降级**：资质覆盖率度量的是「官方认定密度」，不是「技术影响力」。一个新兴技术点上全是初创企业，$q$ 会很低，但它可能正是最有影响力的方向；
3. **分数上限只有 70 左右**：两项都取不到满分，任何「影响力 90 分」的预期都会落空；
4. **申请人名未归一**：规模项偏高，且不同 IPC4 的偏高幅度不一致（大企业多写法集中在某些领域）。

### 4.2 数据陷阱（本批实测，须写入下游复用说明）

**陷阱一：不要用 PATH 中心度或服务机构影响力顶替。** 正本明文禁止，且三者对象不同（技术路径 / 服务机构 / 技术点）。

**陷阱二：`n_k` 是申请人名数，不是企业数。** 未做名称归一，同一企业多写法会被计多次。要与「企业数」对齐，必须先归一。

**陷阱三：$q_k$ 的分子分母都在底册内，不能拿 $m_k$ 除以 $n_k$。** $n_k$ 含 8.64% 底册外名字，$m_k/n_k$ 会系统性低估质量占比。本件用 $m_k/b_k$。

**陷阱四：专利年份只有 2021—2026。** `dwd_patent.apdt_year` 在 2017—2020 零行，任何「近十年趋势」的写法都会把前四年当 0，把斜率顶高。本件只做截面，不用年份做分母。

**陷阱五：IPC4 分布极度右偏。** 最大 17,599、中位 257，线性归一会让 95% 的技术点挤在 0 附近。必须取对数。

### 4.3 可构建但存在缺口（不是「无法构建」）

如果指标改名为「技术领域（IPC 小类）关联规模与资质密度」，本件可以判**完全转换支持**：634 个 IPC4、134,152 个申请人、54 万行聚合，全部可复算。

一旦要求「技术点」这个语义（图谱里的技术实体）或「技术影响力」这个语义（`tech_power_index`），就必须判部分支持。本件按正本口径判，取后者。

### 4.4 若甲方补齐后的口径升级路径

1. **先建技术点本体**：用 IPC4 + 关键词聚类生成初版技术点集，给每个点一个稳定 ID；
2. **再建边**：用专利共类、共同申请人、引用关系派生技术点—企业边；
3. **再补技术力**：建企业技术力评分表，替代资质覆盖率；
4. **最后定权重**：$w_1/w_2$ 会签后重算，并在同一版产物里保留旧权重结果作对照。

## 五、旧稿对照与选用建议

### 5.1 旧稿口径还原

上一版（20261020 开发库稿，533 行）的结论方向与本版一致（部分支持、技术实体节点缺失），但有一处**方法性硬伤**：它用**演示库** ADS 侧的图谱节点计数与 `tech_power` / `enterprise_centrality` 的演示值作为承载证据。

问题不在数字大小，在证据性质：演示库的节点计数是造数，不是生产数据；拿它证明「技术实体节点类型不存在」，逻辑上能成立（演示库里也没有 tech 类型），但它同时把「演示值」写进了论证链，读者无法区分哪句是实测、哪句是演示读数。本批铁律明确禁引演示库，这类写法必须清除。

### 5.2 本版改法

| 旧稿问题 | 本版处置 |
|---|---|
| 用演示库节点计数作证据 | 改为 gkx 280 张表名扫（0 命中）+ 全库列名扫（5 组 0 命中），全部是本地/元数据查询 |
| 只做「依赖审计」不出数 | 增加 IPC 代理口径，给出 634 个技术点的完整排序 |
| 影响力子维不可算 | 用资质覆盖率替代，落 $m_k$ / $b_k$ 两个数供复算 |
| 权重未定义 | 明写等权为本件默认，会签后重算 |

### 5.3 逐维对照表

| 维度 | 旧稿 | 本版 | 差异原因 |
|---|---|---|---|
| 技术点本体 | 图谱节点（不存在） | IPC4（634 个） | 改为可算代理 |
| 关联边 | 图谱边（不存在） | 专利申请人 | 改为可算代理 |
| 影响力 | `tech_power_index`（不存在） | 资质覆盖率 | 改为可算代理 |
| 是否出数 | 否（依赖审计） | 是（634 点排序） | 新增 |
| 判档 | 部分支持 | 部分支持 | 未变 |

### 5.4 选用建议与理由

**建议采用本版**：① 否定性证据全部来自 gkx，不依赖演示库；② 代理口径可复算，634 个技术点的排序能直接支撑 UI；③ 上限 70 的成因写清，甲方不会误判为算法缺陷。

如果甲方要的是「图谱里的技术点」，本版只能作为建图前的过渡；如果甲方接受「专利技术领域」这个粒度，本版可以立即上线，但页面文案必须改。

## 附录 C　可行性完整版

### C.1 报告目的与范围

回答「gkx 能不能算技术点影响力」。范围是技术点本体、关联规模、关联实体影响力三维，不含技术趋势预测与专利价值评估。

### C.2 需求语义锚定

「技术点」在需求里是图谱实体的一种。它必须能被枚举、被关联、被命名。gkx 没有图谱，所以任何实现都要先回答「用什么替代技术点」。本附录的立场是：替代可以，但必须在 UI 与产物里标明替代物。

### C.3 权威与学术构建方法谱系

#### C.3.1 族 A：图中心性

以 PageRank、度中心性衡量节点重要性。适用前提是有图。gkx 无图，不可行。

#### C.3.2 族 B：专利分类统计

按 IPC/CPC 小类统计专利量与申请人。数据现成、口径稳定，代价是粒度粗。本件采用。

#### C.3.3 族 C：技术生命周期

用专利年度增长曲线判技术阶段（萌芽/成长/成熟/衰退）。需要多年序列，本库只有 2021—2026。

#### C.3.4 族 D：共现网络

以专利共类、共同申请人建技术点—企业边，再算中心性。这是把 A 族救回来的可行路径，但需要重扫专利表。

### C.4 数据可行性详细分析

| 依赖 | gkx 现状 | 可行性 |
|---|---|---|
| 技术点本体 | 0 张表 | 不可行（需代理） |
| 技术点—实体边 | 0 张表 | 不可行（需派生） |
| 企业技术力 | 0 列 | 不可行（需代理） |
| 专利 IPC | 2,939,895 行 | 可行 |
| 企业资质 | 202,424 行 | 可行 |
| 申请人名 → 底册 | 91.3613% 匹配 | 可行（有损） |

### C.5 推荐构建方案（工程可执行）

第一步，用 IPC4 出代理版排序（本版）；第二步，用专利共类关系派生技术点—企业边，把图谱建起来；第三步，建企业技术力评分，替换资质覆盖率；第四步，权重会签后重算，并与本版做相关性对照。

### C.6 风险与残余不确定性

① IPC4 粒度与「技术点」差距大，UI 文案必须改；② 申请人名未归一，规模项偏高；③ 资质覆盖率对新兴技术点系统性偏低；④ 分数上限约 70，容易被误读为模型弱。

### C.7 可行性总判（完整版结论）

**代理口径可行、正本口径不可行。** 按正本「技术点」语义判**部分支持**；若甲方接受「专利技术领域」粒度，可升为完全转换支持；若坚持图谱技术点与 `tech_power_index`，在图表建成前应判完全不支持。
