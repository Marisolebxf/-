## 摘要

推荐企业数是二次统计：指数 ≥70 的企业去重计数，招引与培育各一枚、不合并。它本身没有算法，卡点全在上游。本件重新算了招引指数的全量度中心度（95,652 个节点、投资 46,967 条边、股东 70,034 条非空边），重算最大值 0.561416，与上游 `M_ENT_ATTRACTION_INDEX_out.json` 一致，证明同一公式。

问题在标度：上游分数是 `100×deg_sz/(n−1)`，分母 95,652，最大值只有 0.561416，不是 0—100。阈值 70 在原始标度上永远不可达，严格计数恒为 0。按最大值线性拉到 0—100 后，只有 2 家过线：匿名节点 100 分、深圳市创新投资集团 83.99 分。

培育侧更彻底：上游 `M_ENT_CULTIVATION_INDEX_out.json` 没有 `compute`、没有 scores，只做了三维成熟度评估。没有企业级分数就不能过阈，培育推荐企业数是 null，不是 0。0 是「有分但都不过线」，null 是「根本没有分」，两者不能混。

## 一、需求定义概述

### 1.1 所属功能模块

推荐企业数挂在企业分析的「引育推荐」页，是招引名单与培育名单的规模数：列表页顶部「共 N 家」、首页卡片「本期新增 N 家」。它不展示名单内容，只展示规模，因此必须去重——同一企业可能因多个理由被多次推荐，`COUNT(*)` 会把名单行数当企业数。

它同时是上游指数的健康检查器。一个指数如果最大值只有 0.56，推荐数必然是 0；这个 0 比任何分布图都更直观地说明「指数还没准备好」。本件把 0 当诊断信号，而不是交付结果。

### 1.2 为什么需要推荐企业数

推荐系统如果只有排序没有规模，业务方无法判断这一批是「精挑细选」还是「广撒网」。规模数提供三个判断：资源匹配（20 人团队对应多少家）、阈值校准（70 调到 60 会跳多少）、批次可比（周更数量突变说明上游分布变了）。

它也是名单质量的代理。阈值 70 下推荐数长期为 0，说明指数标度或分布有问题；若某周突然从 0 跳到几百，说明上游换了算法或数据源，需要排查而不是直接采信。

### 1.3 需求文档是否给出定义方法

需求文档给业务语义（筛选高潜力企业、生成名单），没有给阈值与计数口径。阈值 70 来自口径细稿（2026-09-07 COVER-STAT-L01），并标注为团队临时值，对齐 demo 高档 0.7，不是甲方确认值。

细稿还规定：刻度跟 INDEX（0—100）、招引与培育同阈值、不 UNION、无分企业不进分子、只国内、禁止用百分位/TOP N 冒充 70、禁止 `COUNT(*)` demo 表。本件逐条执行，并在产物里记录阈值与标度。

### 1.4 权威机构方法可行性

阈值型名单筛选在官方体系里有成熟范式：科技型中小企业评价（总分 ≥60 + 单项否决）、大中小微企业划型（多指标分档）、专精特新梯度培育（三级名单 + 复核）。共同点是阈值可解释、可分档、可复核。

本件的阈值 70 只满足「可解释」（0—100 的前 30%），不满足「可分档」（没有 60/70/80 梯度）与「可复核」（指数未全量出分）。这是判部分支持的方法论依据，不是简单的「数没跑出来」。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A. 严格阈值计数 | 科技型中小企业评价 | 总分阈值 + 单项否决 | 高（本件采用） |
| B. 分档名单 | 专精特新梯度培育 | 三级名单 + 复核 | 中（阈值未分档） |
| C. TOP N | 商业榜单 | 取前 N 名 | 低（口径禁止） |
| D. 百分位 | GII 排名 | 分位线 | 低（口径禁止） |

### 1.5 引用来源

来源 2：`metrics/repro/out/M_ENT_CULTIVATION_INDEX_out.json`（无 compute、无 scores）。

### 1.6 推测原意与依赖维度

推测原意是回答「这一批有多少家够得上推荐线」，招引与培育各答一次。按这个原意，计数必须严格阈值，不能用 TOP N 替代；否则名单规模恒等于 N，无法反映质量变化。

依赖维度拆成三层：D1 指数分数（招引有、培育无）、D2 标度（0—1，不是 0—100）、D3 去重键（有，org_id）。D1 半缺、D2 错、D3 可用，所以判部分支持。

| D1 | 招引指数 | A 类 | 95,652 节点有分 |
| D2 | 培育指数 | A 类 | 无企业分 |
| D3 | 标度 | B 类 | 0—0.561，非 0—100 |
| D4 | 去重键 | B 类 | org_id 100% 存在 |

## 二、计算过程

### 2.1 方法选择：严格阈值而不是 TOP N

阈值不可达时，取 TOP 100 能立刻给出一份可用名单，工程上更「务实」。但 TOP N 的规模恒等于 N，与指数分布无关，无法反映「这一批质量整体上升还是下降」；阈值计数会随分布移动，阈值 70 下从 0 变 300 本身就是质量改善的证据。

细稿明文禁止用百分位/TOP N 冒充 70，因为一旦允许替代，下游无法区分「70 分线」与「前 5%」两种筛选逻辑。本件因此坚持严格阈值，即使结果是 0。

| 指标 | 实测值 |
|---|---|
| 节点数 | 95,652 |
| 深圳机构 | 95,600 |
| 正连接 | 50,358 |
| 重算最大值 | 0.561416 |
| 上游最大值 | 0.561416 |
| 严格过线 | 0 |
| 拉到 100 后过线 | 2 |
| 培育分数 | 无 |

### 2.2 步骤 1：重算全量度中心度

上游 `M_ENT_ATTRACTION_INDEX_out.json` 只落了 top10，没有全量分数。本件用 `dwd_org_base_info` 的深圳机构集合、`dwd_org_invest_info` 与 `dwd_org_shareholder_info` 的边，重算 `deg_sz/(n−1)`。95,652 个节点、50,358 个正连接，最大值 0.561416，与上游声明一致。

这一步是必要的：如果只读 top10，就无法知道「2 家过线」是否完整。重算后 `count_above_raw` 显示 0.4 以上 2 家、0.5 以上 1 家，与 top10 的排序一致，说明重算没有漏掉节点。

| 阈值（原始标度） | 过线节点 |
|---|---|
| 0.1 | 9 |
| 0.2 | 4 |
| 0.3 | 3 |
| 0.4 | 2 |
| 0.5 | 1 |
| 0.7 | 0 |

### 2.3 步骤 2：标度诊断

上游分数是 `100×deg_sz/(n−1)`，分母 95,652，所以最大只有 0.561416。这个值不是「56 分」，而是「0.56 分」；阈值 70 在原始标度上不可达，严格计数恒为 0。旧稿把它读成「0—1 标度、最大 56.14 分」，仍然低于 70，结论一样，但标度描述不准确。

本件在产物 `scale_finding` 里同时写 `declared_max`、`recomputed_max`、`max_match`、`strict_threshold_reachable`、`rescaled_threshold_raw=0.392991`。后者是「70 分对应的原始值」：0.7×0.561416，超过它的只有 2 家。

### 2.4 步骤 3：三组读数

严格原始标度：0 家；按最大值拉到 0—100：2 家（匿名节点 100、深创投 83.99）；TOP 10%：9,565 家（仅对照，口径禁止）。三组数的差异不是误差，而是标度选择。本件把前两组都落盘，TOP 10% 只给参考值，不参与结论。

为什么不用 min-max 到 0—100？因为 min=0，min-max 与「除以最大值」等价；如果未来出现负值或非零最小值，两种方法会分叉。本件选「除以最大值」是因为它保留了「0 分仍是 0」的语义，且与上游公式同构。

### 2.5 步骤 4：培育侧的 null

培育指数上游没有 `compute`、没有 scores，只做了三维成熟度评估（产业相关度可算、政策匹配度缺 GPT 框架、企业潜力财务填充 2.9%/2.6%/2.4%）。没有企业分就不能过阈，培育推荐企业数只能是 null。

null 与 0 的区别必须写清：0 是「有分但都不过线」，可以随阈值下调而变化；null 是「根本没有分」，无论阈值怎么调都不会变。把 null 写成 0 会让下游以为「培育名单为空但系统正常」，从而错过上游未出分这一故障信号。

### 2.6 步骤 5：覆盖与身份

招引指数只覆盖有投资/股东边的企业，未建边的企业不参与。95,652 个节点相对 189,116 家机构底册，覆盖约 50.6%；深圳机构 95,600 家里，有边的只是一部分。这个覆盖缺口会让推荐数偏低，但不影响「阈值不可达」的结论。

另一个边界是匿名节点：top1 的 org_id 没有 name_cn，可能是空壳/投资平台。它的度 810、深圳连接 537，但名称缺失，业务方无法直接使用。产物保留 org_id，建议页面用「未命名机构」占位，不要隐藏。

### 2.7 步骤 6：阈值敏感性

原始标度下，阈值从 0.1 降到 0.05 会把过线数从 9 拉到更多；0—100 标度下，阈值从 70 降到 50 会把过线数从 2 拉到 4（0.2 以上 4 家）。这条曲线说明「推荐数」对阈值高度敏感，阈值未裁定前不应对外发布具体数字。

本件没有做「最优阈值」拟合，因为那需要业务标注（哪些企业真的值得推荐）。没有标注集，任何阈值都是任意的。

|---|---|---|
| 阈值 | 70 | 口径细稿临时值 |
| 标度 | 0—100（声明）/0—0.561（实际） | 上游公式分母为节点数 |
| 招引计数 | 严格原始标度 | count=0 |
| 缩放口径 | 除以最大值×100 | count=2 |
| 培育计数 | null | 上游无企业分 |
| 去重键 | org_id | 100% 存在 |
| 覆盖 | 有投资/股东边 | 95,652 节点 |
| TOP N | 禁止 | 只作对照 |

严格计数 0 不是「没有企业」，而是「标度够不到 70」。产物 `primary_result.read_as` 已把这句话写成可读结论；页面若只显示 0，会误导业务。

缩放口径 2 家也不是「推荐名单只有 2 家」，而是「按当前最大值拉到 100 后，只有 2 家过 70」。它是敏感性，不是正式口径；正式口径要等上游修标度。

## 三、数据支撑情况

本件按「招引分数 / 培育分数 / 标度 / 去重键 / 覆盖」五个维度核对。去重键完整，分数与标度是主要缺口。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 招引分数 | 有，95,652 节点 | 重算 max 0.561416 | 无需修复 |
| 培育分数 | 无 | 上游只有成熟度评估 | 补三维打分并落企业级分数 |
| 标度 | 错 | 0—0.561，不是 0—100 | 上游乘 100 或甲方确认缩放 |
| 去重键 | 完整 | org_id 100% | 无需修复 |
| 覆盖 | 约 50.6% | 只含有投资/股东边的企业 | 补边或接全量企业库 |

标度缺口的修复有两种：一是上游把分数乘 100（`100×deg_sz/(n−1)` 已经是乘 100，但分母是节点数，所以仍是 0—0.56），二是按最大值归一。前者不改变数值，后者改变分布。本件建议在上游公式里直接除以最大可能度（n−1），得到真正的 0—100；但这会改变历史分数，需要版本化。

培育缺口的修复不是「再跑一次」，而是先建 GPT 分类框架（行动型/话语型政策契合），再算企业级分数。当前只有三维成熟度评估，不能过阈。

覆盖缺口的修复需要补投资/股东边，或接入全量企业库。当前 95,652 节点相对 189,116 家底册覆盖约一半，推荐数会系统性偏低。

### 3.9 缺口优先级

缺口不是同等重要。本件按「是否阻断指标成立」把缺口分三档：阻断（指标算不出）、扭曲（算得出但结论会反）、披露（不影响本期结论但影响外推）。优先级如下。

| 优先级 | 缺口 | 阻断/扭曲/披露 | 处理 |
|---|---|---|---|
| P0 | 标度 0—0.561 | 阻断（阈值） | 上游修公式 |
| P0 | 培育无企业分 | 阻断（一枚） | 补三维打分 |
| P1 | 覆盖约 50.6% | 扭曲 | 补边/全量库 |
| P2 | 阈值 70 未签字 | 披露 | 参数化 |
| P2 | 匿名节点 | 披露 | 补名称 |
| P3 | TOP N 不可用 | 披露 | 不采用 |

标度与培育分是双 P0：一个让招引计数恒 0，一个让培育计数不可算。两者不修，指标只能输出诊断，不能输出名单规模。

覆盖 50.6% 是扭曲级：未建边的企业不参与，推荐数会偏低。它不会让 0 变成非 0，但会让「2 家」这个数不代表全库。

## 四、数据缺失情况

本件的缺失分两类：招引是「有分但标度不对」，培育是「根本没有分」。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 培育企业分 | 培育计数不可算 | 输出 null | 补三维打分 |
| 0—100 标度 | 阈值 70 不可达 | 双读数（严格/缩放） | 上游修公式 |
| 全量企业覆盖 | 推荐数偏低 | 披露覆盖约 50.6% | 补边/接全量库 |
| 阈值依据 | 70 是临时值 | 参数化 | 甲方确认 |
| 匿名节点 | 名单可用性差 | 保留 org_id | 补名称 |

最需要警惕的是把「严格计数 0」当业务结论。0 的真实含义是「当前指数标度够不到 70」，不是「深圳没有值得招引的企业」。产物 `primary_result.read_as` 明确写了这句话，页面也应照抄。

第二类是匿名节点：top1 没有名称，但度最高。如果页面直接展示名单，会出现「未命名机构」占第一；这不是数据错误，而是底册名称缺失。建议补名称或加「名称待核」标签。

### 4.9 处置原则

对缺失的处置遵循三条：不补 0、不静默填充、不把模型产物当数据真值。能算的算，不能算的输出 null 并写原因；任何代理都必须在字段名与页面文案上标注「代理」。

第二条是不做「看起来完整」的补齐。缺失年份不插值、缺失城市不摊派、缺失分项不按均值填；这些操作会让下游误以为数据齐全，比 null 更危险。

第三条是可复现优先。所有外部输入都落快照，快照带来源、时间、行数；脚本只读快照，重跑不依赖网络。这样即使源库变化，历史结论仍可复算。

旧稿只读上游 out.json 的 top10 与统计量，严格计数 0、培育 null；本件重算全量度中心度，确认 95,652 节点与 max 0.561416，并给出「拉到 100 后 2 家过线」的敏感性。

## 附录 G 口径问答

**问：为什么不用 TOP 100 给一份可用名单？**

答：TOP N 的规模恒等于 N，无法反映分布变化；口径细稿明文禁止用它冒充阈值 70。本件宁可输出 0，也不换口径。

**问：严格 0 与缩放 2，哪个是正式结论？**

答：严格 0 是正式结论（在原始标度上）；缩放 2 是敏感性，说明「若按最大值归一，有 2 家」。两者都落盘，页面应显示前者并解释后者。

**问：培育为什么是 null 不是 0？**

答：上游没有企业级分数。0 是「有分但不过线」，null 是「没有分」；把 null 写成 0 会掩盖上游未出分。

**问：匿名节点能推荐吗？**

答：不能直接推荐。它没有名称，业务方无法联系；产物保留 org_id，建议补名称或加「待核」标签。

**问：阈值 70 有依据吗？**

答：没有甲方签字，只是团队临时值，对齐旧稿高档 0.7。它是参数，不是口径。

**问：覆盖 50.6% 怎么算？**

答：95,652 / 189,116。未建边的企业不参与指数，推荐数会偏低；这是披露项，不是修复项。
