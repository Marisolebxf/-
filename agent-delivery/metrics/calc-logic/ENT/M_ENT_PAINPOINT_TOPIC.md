## 摘要

「痛点主题」要回答的是：企业遇到的麻烦，主要属于哪一类。原设计假定有诊断表给出主题，表不存在，所以本件改用规则归类：六张风险表按来源映射到主题，经营异常再按 `abn_reason` 原文拆成四类。

实测 699,003 条记录归入 9 个主题：债务违约 626,369 条（89.61%）、行政违规 65,997 条（9.44%）、住所失联 4,415 条（0.63%）、年报未公示 677 条、涉税违规 528 条、信息隐瞒 309 条、其他经营异常 268 条、严重违法 247 条、无照经营 193 条。

这个分布极端偏斜：一个主题占近九成，前两个主题合计 99.05%，其余七个合计不到 1%。它不是「企业痛点很多样」，而是「司法记录数量压倒一切」。任何按主题做占比的图，都会被债务违约一根柱子压平。

结论是「部分支持」：规则可复现、每条记录可回对原文，这是它的优点；主题只覆盖合规侧、无经营主题、无多标签、`abn_reason` 的企业数按记录占比分摊（估算），这是它的局限。

## 一、需求定义概述

### 1.1 所属功能模块

该指标挂在**企业服务 → 企业诊断 → 痛点归因**。页面形态是企业画像上的主题标签，以及一张主题分布饼图。用户拿它回答「这家企业/这个区域的主要问题是什么」。

它是分类指标，比计数指标多一层解释：同样是 1,000 条痛点，全是被执行和全是行政处罚，含义完全不同。分类的价值就在这层解释力。

| 项目 | 内容 |
|---|---|
| 功能路径 | 企业服务 → 企业诊断 → 痛点归因 |
| 页面载体 | 主题标签 + 分布饼图 |
| 输出形态 | 主题 → 条数、占比、企业数、来源 |
| 更新频率 | 建议月度 |
| 粒度 | 企业 → 主题；区域/行业 → 主题分布 |

### 1.2 为什么需要这个指标

主题是痛点从「数量」走向「原因」的第一步。只有数量，用户知道企业麻烦多；有了主题，用户知道麻烦是什么类型，才能决定是法律处置、行政沟通还是经营辅导。

第二个用途是区域画像。某个区的企业痛点集中在「住所失联」，说明大量空壳注册；集中在「债务违约」，说明区域资金链紧张。同一张饼图，不同的偏斜讲不同的故事。

第三个用途是政策匹配。行政违规多的区域适合加强合规培训，债务违约多的区域适合做纾困基金。主题分布是政策工具选择的依据。

### 1.3 需求文档是否给出定义方法

**需求文档给了主题概念，但没给主题体系。** calc-logic 写的是：

> 痛点主题：对企业痛点进行主题归类，输出主要痛点主题。

「主题」是什么、有几个、怎么判定，原文都没说。本件自建了一套 9 类规则主题：五个直接来自风险表（债务违约、行政违规、涉税违规、严重违法、其他经营异常），四个来自 `abn_reason` 关键词（住所失联、年报未公示、信息隐瞒、无照经营）。这套体系必须会签，因为它直接决定饼图的形状。

### 1.4 类似指标权威机构构建方法可行性

主题归类在文本分析里有三种做法：规则关键词、有监督分类、无监督聚类。三者的前提不同：规则要词典，有监督要标注，无监督要语料。库内只有结构化的原因字段，所以只能用规则。

| 方法族 | 代表机构/文献 | 核心构架 | 与本指标贴合度 |
|---|---|---|---|
| A 规则关键词 | 本件 | 按 abn_reason 关键词映射 | 确定、可回溯、覆盖窄 | 高（本件采用） |
| B 有监督分类 | 学术界 | 标注 + 训练 | 需标注集 | 低（本批无） |
| C 无监督聚类 | LDA/BERTopic | 语料聚类 | 需大语料、主题不稳定 | 低 |
| D 行业标准分类 | 市场监管总局 | 按违法类型分 | 与本件体系部分重合 | 中（可对齐） |

**A 族是本件采用的方法**：`abn_reason` 是结构化原因字段，关键词映射确定、可复现、每条记录都能回对原文。缺点是覆盖窄——只覆盖已写入原因字段的情形。

**B/C 族**需要标注集或大语料。本批没有标注资源，且痛点文本量不足以支撑稳定聚类。

**D 族（官方分类）**与本件的五类风险主题高度重合，可以作为会签时的对齐参照。本件没有直接采用，因为官方分类按违法类型，不按「企业痛点」组织。

## 二、计算过程

### 2.1 总体思路与数据流

先把五类风险表按来源映射到主题，再把经营异常表按 `abn_reason` 关键词拆成四类，最后合并统计。整个过程是确定的规则，没有模型。

这样做的原因是可回溯：每一条记录都能说出「因为它在行政处罚表，所以归行政违规」。模型分类说不清这一点，甲方追问时无法自证。

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 映射 | 五类风险表 | 表→主题 | 5 个主题 |
| 拆分 | abn_reason | 关键词四类 | 4 个主题 |
| 合并 | 九类 | SUM | 699,003 |
| 占比 | 九类 | ÷ 总数 | share |

### 2.2 口径定义与主题体系

九个主题：债务违约、行政违规、住所失联、年报未公示、涉税违规、信息隐瞒、其他经营异常、严重违法、无照经营。前两个来自记录量最大的两张表，后七个来自小表与原因字段。

`share = records / 699,003`。分母是全部痛点条数，不是「有主题的条数」——后者会把「其他经营异常」排除在外，导致占比之和不为 1。

主题之间互斥：一条记录只归一个主题。经营异常先判「住所失联」，再判「年报未公示」，再判「信息隐瞒」，都不命中则归「其他经营异常」。优先级顺序写进产物，避免复现时归类不同。

| 主题 | 来源 | 条数 | 占比 |
|---|---|---|---|
| 债务违约 | 失信 + 被执行 | 626,369 | 89.61% |
| 行政违规 | 行政处罚 | 65,997 | 9.44% |
| 住所失联 | abn_reason | 4,415 | 0.63% |
| 年报未公示 | abn_reason | 677 | 0.10% |
| 涉税违规 | 税务处罚 | 528 | 0.08% |
| 信息隐瞒 | abn_reason | 309 | 0.04% |
| 其他经营异常 | abn_reason 未覆盖 | 268 | 0.04% |
| 严重违法 | 严重违法表 | 247 | 0.04% |
| 无照经营 | abn_reason | 193 | 0.03% |

### 2.3 abn_reason 的四类拆分与优先级

`abn_reason` 有 15 类原文，本件只取四类高频：住所失联 4,415 条（占异常记录 75.3%）、年报未公示 677 条（11.5%）、信息隐瞒 309 条（5.3%）、无照经营 193 条（3.3%）。剩余 268 条（4.6%）归「其他经营异常」。

优先级是必须的：一条记录可能同时含「失联」与「未公示」，按「住所失联」优先判定，因为它更具体、对企业的含义更明确。优先级写进产物，避免两个人跑出两种结果。

四类合计 5,594 条，加上其他 268 条 = 5,862 条，与经营异常表总数一致。这条校验说明拆分没有丢记录。

| 子主题 | 条数 | 占异常记录 | 优先级 |
|---|---|---|---|
| 住所失联 | 4,415 | 75.3% | 1 |
| 年报未公示 | 677 | 11.5% | 2 |
| 信息隐瞒 | 309 | 5.3% | 3 |
| 无照经营 | 193 | 3.3% | 4 |
| 其他 | 268 | 4.6% | 5 |

### 2.4 计算步骤（脚本逐步实现）

1）读六表计数；2）五表直接映射；3）经营异常按关键词拆分；4）合并九类；5）算占比与企业数；6）排序取 rank。

第 5 步的「企业数」是估算：`abn_reason` 没有 org 去重，本件按记录占比把该类的企业数分摊到四个子主题。产物里把这类值标注为估算，不与直接计数的企业数混用。

| 步骤 | 实现 | 校验 |
|---|---|---|
| 映射 | dict 查表 | 五类 |
| 拆分 | 关键词优先级 | 5,862 条 |
| 合并 | SUM | 699,003 |
| 占比 | ÷ 总数 | 和 ≈ 1 |

## 三、数据支撑情况

### 3.1 依赖表与可得性

本件依赖六张表与一个原因字段。六张表提供五个主题，`abn_reason` 提供四个子主题。原料齐全，这是它能算出来的根据。

缺的是经营侧主题的载体。融资受阻、人才流失、供应链断供这些主题在库内没有任何字段，既不来自风险表，也不来自原因字段。

| 依赖维度 | 实测状态 | 关键证据 | 缺口与修复路径 |
|---|---|---|---|
| 五类风险表 | 可用 | 五个主题直接映射 | 无 |
| abn_reason | 可用 | 5,862 条 / 15 类 | 覆盖仅异常记录 |
| 经营异常企业数 | 部分 | 按记录占比分摊 | 原因字段无 org 去重 |
| 经营侧主题 | 不可用 | 无载体 | 需调研或 NLP |
| 多标签 | 不可用 | 单标签设计 | 需标注 |

### 3.2 四判定落表

四判定里，结构与数据都过（六表 + 原因字段），但主题体系是本件自建的，不是甲方给的。这意味着「主题定义」本身需要会签，不能当作既定口径。

| 判定项 | 结论 | 证据 |
|---|---|---|
| 表结构直接支持（开发库+三方库） | 否 | 无主题结果面 |
| 表数据直接支持（开发库+三方库） | 否 | 同上 |
| 依赖表结构支持（开发库/三方库） | 是 | 六表 + 原因字段 |
| 依赖表数据支持（开发库/三方库） | 是 | 69.9 万条可归类 |
| 聚合结论 | 部分支持 | 仅合规侧、规则主题 |

### 3.3 数据量、覆盖与代表性

覆盖上，699,003 条记录全部可归入九类，没有「无法归类」的剩余——这是规则体系闭合的证明，也是它的局限：闭合意味着它只能覆盖已有的六张表。

代表性上，债务违约占 89.61%，说明主题分布几乎由司法记录决定。行政违规 9.44% 是唯一有解释力的第二主题，其余七个主题的样本量都不足以做区域比较。

### 3.4 结构支持判定

结构侧够用：五张表可映射、原因字段可拆四类、优先级可定义。

语义侧不够：规则主题不是语义主题。它不知道「融资受阻」，也不知道「价格战」，因为这些概念不在任何结构化字段里。

### 3.5 与开发库 live 的差异

开发库无主题结果面，live 不产出。上线需把九类计数物化成宽表（topic, n, orgs, share），并保留 `abn_reason` 原文以便复核。

建议同时物化优先级规则，否则后续维护者不知道「失联 + 未公示」为什么归失联。

## 四、数据缺失情况

### 4.1 缺口清单

本件的缺口是「主题」的另一半：只有合规侧，没有经营侧。这与痛点数量是同一个根因——数据源只有法律事件。

第二个缺口是单标签：一条记录可能同时是「债务违约」与「信息隐瞒」，本件只归一个。多标签需要标注或更强的规则，本批没有。

| 缺失项 | 影响 | 当前处置 | 补齐路径 |
|---|---|---|---|
| 无经营侧主题 | 无法回答「为什么难」 | 不做 | 调研或 NLP |
| 单标签 | 多属性记录被压缩 | 优先级判定 | 多标签标注 |
| 企业数按占比分摊 | 子主题企业数是估算 | 标注为估算 | 原因字段加 org 去重 |
| 主题体系自建 | 需会签 | 文档明示 | 甲方确认 |
| 无严重度 | 主题内不可比 | 只数条数 | 补严重度字段 |

### 4.2 逐条影响

「无经营侧主题」让这套体系只能叫「合规主题」，不能叫「痛点主题」。名字与内容的错位是本件最需要说明的地方。

「单标签」是一个技术选择，也是一个信息损失。一条记录同时属于两类时，归到优先级高的那一类，另一类就消失了。要让两类都出现，必须改成多标签，而多标签的占比之和会大于 1，需要另一套展示口径。

### 4.3 明确不做什么（禁止的替代）

- 不把规则主题称为「语义聚类」——它是关键词映射，不是模型。
- 不对一条记录打多个主题——占比之和会大于 1，饼图无法解释。
- 不把子主题的企业数当精确值——它是按记录占比分摊的估算。
- 不把「债务违约 89.61%」解读为「89.61% 的企业违约」——分母是记录，不是企业。
- 不自称覆盖经营痛点——融资、人才、供应链三类都不在体系内。

五条禁令里，第四条最容易被违反。条数占比与企业占比是两个完全不同的数，前者被司法记录的数量放大，后者要看 48,864 / 189,116 = 25.8%。页面上必须写清分母。

### 4.4 若甲方补齐后的口径升级路径

补齐路径分两条：补经营侧主题（调研或 NLP），补多标签（标注）。前者决定主题体系是否完整，后者决定单条记录的信息是否被压缩。

两条都补之后，档位可以从「部分支持」升到「完全转换支持」。只补多标签不补经营侧，仍然是部分支持，因为主题体系还是半个。

| 补齐条件 | 口径变化 | 档位能否升格 |
|---|---|---|
| 补经营痛点调研 | 主题体系完整 | 可升完全转换 |
| 建舆情主题抽取 | 舆情侧主题可算 | 可升完全转换 |
| 补多标签标注 | 一记录多主题 | 需另立占比口径 |
| 补严重度字段 | 主题内可比 | 另立指标 |

**基期声明**：`base_years_used` = []；`base_years_missing` = []。风险表是事件流水，本件按「截至抓取时点的累计条数」归类，不做年度切分，故无基期年份；表内带发生日期，年度主题迁移需另做按年聚合。

## 五、王惠方法对照

王惠原稿只写了「对痛点进行主题归类」，没有给主题体系、没有给归类方法、没有给多标签规则。本件自建九类规则主题，并把体系、优先级、边界全部写进产物。

差异的实质是：原稿给的是目标，本件给的是可执行的定义。这个定义需要会签，因为换一套主题体系，饼图会完全不同。

需要强调的是：九类主题不是唯一解。它是「在只有六张结构化表的前提下，能做得最可回溯的一套」。甲方若有自己的主题体系，应替换 `taxonomy` 并重跑，而不是在本件上打补丁。

**选用建议**：主题归类的目标与「按企业痛点组织」的思路沿用王惠；主题体系、优先级与多标签规则因原稿缺失，由本件自建并在产物 `taxonomy` 中固化，交付前需甲方会签。替换体系时只改规则表，不改统计逻辑。

## 附录 M 开发交接说明

**问：页面怎么展示？**

答：主题标签 + 条数；饼图建议用对数或分面，等分饼图会被一根柱子压平。

答：能，但只有债务违约与行政违规样本足够，其余七类不宜做区域比较。

**问：多久更新？**

答：月度；主题体系变更时立即重跑。
