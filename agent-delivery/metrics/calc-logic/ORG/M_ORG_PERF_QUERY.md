## 摘要

本件把 2,074 家机构中 325 家「至少一项产出大于 0」的机构物化为查询宽表：广州 173 家、深圳 120 家、东莞 21 家、惠州 11 家；事业单位 271 家、民办非企业 54 家。有专利 219 家、有论文 236 家、有项目 53 家、有学者 29 家、有转化记录 16 家、有政策提及 47 家、有专利年度序列 181 家、有财务数据 0 家。

查询层支持四类过滤（名称子串、城市等值、机构类型等值、专利下限），返回八个区块：身份、产出（累计与年度序列）、人才、转化、影响、结构、池内百分位、数据标记。实测响应时间 0.013—0.025 毫秒（内存查询，非数据库）。三个示例查询的结果很能说明底册的边界：查「深圳大学」命中 0 家——底册只收登记为科研机构的主体，高校本部不在其中；查「中国科学院深圳先进技术研究院」命中 1 家，返回 943 件专利、422 件授权、83 篇论文、102 个项目、35 位学者；查「深圳市人民医院」命中 1 家，返回的是「深圳市人民医院（深圳市呼吸疾病研究所）」这个登记名。

年度序列的三处断裂必须一起读。专利序列只到 2024（面板 `app_year` 窗口为 2021—2024，2025/2026 为 null）；论文序列到 2025，但 2024 年有 162 家机构有记录、32,379 篇，是其他年份（6,000 篇上下）的五倍，属采集口径尖峰；项目序列只到 2022（源表不覆盖 2023 以后），2023—2025 全部为 null。任何「2025 年专利产出」「2024 年项目数」的查询都不可答，页面必须把 null 显示为「无数据」而不是画成 0 线。

审计发现两处查询层硬缺陷。第一，38 家机构有累计专利但没有任何年度序列（合计 788 件，占池内专利总量 12.02%），最大的是哈工大深圳（394 件）与电子科技大学（深圳）高等研究院（143 件），原因是累计与年度走两条不同的匹配链；第二，机构名未消歧，3 对是真正的同实体异名（如「深圳先进技术研究院」80 件与「中国科学院深圳先进技术研究院」943 件），另有 33 对是母体与下属所（如「广东省科学院」与「广东省科学院新材料研究所」），前者必须提示合并，后者不应合并。

## 一、需求定义概述

### 1.1 所属功能模块（要开发什么）

本件是「门户查询层」的一个结果面，不是独立的分析模型。页面形态是「搜索框 + 结果卡片 + 年度趋势小图」：用户在任一机构分析页点机构名，或在门户搜索框输入机构名，落到的就是这张卡。

卡片分八块。身份块给名称、城市、类型、登记年份；产出块给专利/授权/论文/项目/经费的累计值与年度序列；人才块给学者数、h 指数均值、院士标记、人员记录数；转化块给技术转入/转出；影响块给政策提及与新闻；结构块给项目学科与论文关键词；百分位块给该机构在池内的四项排名；数据标记块给每一维的覆盖年份与缺口说明。

需求给的输入是「机构基础信息 + 各类产出记录」。本件用到面板的全部字段与底册的登记字段，唯一没用的是财务表（对底册零命中）。

### 1.2 为什么需要这个指标

第一个理由是**一致性**。同批 ORG 指标有 20 多件，每件都按自己的口径算一家机构的一个侧面（149 算领域结构、154 算招引优先级、155 算扶持优先级、SZ_ADVANTAGE 算城市对比）。如果没有一张统一的结果面，用户在四个页面看到的同一家机构会有四套数字，且互相不可解释。本件把所有原始计数集中到一张宽表，其他件的分数都能回到这张表核对。

第二个理由是**可解释性**。一个「技术力 88.61 分」无法回答「为什么」，但「943 件专利、422 件授权、83 篇论文、102 个项目、35 位学者、池内百分位专利 100/论文 98.7」可以。本件给的是原始计数与百分位，不是合成分，正好补上合成分缺的那一层。

第三个理由是**可核查**。需求原文要求 API 支持「按机构查询」，而 API 的前提是有一张能按机构索引的表。当前 gkx 里没有这张表，本件物化的宽表就是它的最小可用版本；上线时可以直接落成一张 ADS 表，由 API 查询。

### 1.3 需求文档是否给出定义方法

没有。需求文档只说了「可查询」「按机构」「返回指标」，没有说返回哪些指标、年度序列取几年、缺失年份怎么显示、百分位在哪个池内算。这四件事全部由本件自己定，属于推测定义。

本件的四个选择：返回八块（身份/产出/人才/转化/影响/结构/百分位/标记）；年度序列取 2021—2025（专利实际到 2024、项目到 2022）；缺失年份返回 `null` 并附 `data_flags` 说明；百分位在「325 家有信号机构」池内算，不在全库 2,074 家里算。四个选择都写进 `query_contract` 字段，下游可直接读。

`wanghui=false`，`calc-logic` 库中无对应条目。这意味着「返回哪些指标」没有经过业务确认；若业务方认为应加「营业收入」「研发投入」，本件无法满足（见 §四）。

### 1.4 类似指标权威机构构建方法可行性分析概要

「机构画像查询」在数据产品里有三种做法。第一种是**预计算宽表**（ADS 层一张大表，按机构 ID 索引），查询最快、口径最统一，缺点是更新滞后、字段固定。第二种是**即席查询**（查询时现场 join 多张明细表），灵活但慢，且每次查询的口径可能不同。第三种是**指标中台**（每个指标一个 API，前端组合），最灵活，但要求每个指标都有稳定口径与 SLA。

本件走的是第一条，因为底册只有 2,074 家、面板字段固定，预计算成本极低（0.42 秒全量重建），而即席查询会反复踩「机构名匹配」这个坑。国际上同类产品（OECD 的 institutions profile、CWTS 的 institution explorer）也都是预计算 + 缓存。

可行性结论：**结构可行，字段不全**。查询层本身没有技术障碍，缺的是三样字段：财务（营收/研发投入/人员数）、年度序列的完整覆盖（专利 2025/2026、项目 2023 以后）、机构唯一 ID（消除同名与母子问题）。

### 1.6 推测原意与推测定义

推测原意：业务方要的是一个「输入机构名，立刻看到这家机构全部关键数字」的入口，而不是一个新的评分。这个入口服务于三类人：写材料的（要数字）、做尽调的（要看趋势）、做核对的（要看口径）。因此本件的核心不是算法，而是**字段完整性 + 缺失标注**。

形式化定义。设机构 i 在维度 k、年份 y 的取值为 $v_{i,k,y}$，则查询返回

$$\text{Card}(i)=\{\,v_{i,k,y}\mid k\in K,\ y\in Y_k\,\}\ \cup\ \text{flags}(i)$$

其中 $K$ 为八块字段集合，$Y_k$ 为维度 k 的覆盖年份集合（专利 2021—2024、论文 2021—2025、项目 2021—2022）。关键在 $y\notin Y_k$ 时返回 `null` 而不是 0：

$$v_{i,k,y}=\begin{cases}\text{计数}, & y\in Y_k\\ \text{null}, & y\notin Y_k\end{cases}$$

百分位定义为池内排名：$p_{i,k}=100\times\frac{\#\{j\in \text{pool}: v_{j,k}<v_{i,k}\}}{|\text{pool}|-1}$，并列取平均位次。池为 325 家有信号机构，不是全库 2,074 家；这一点必须在页面上写明，否则用户会以为「百分位 100」是全市第一。

## 二、计算过程

### 2.1 方法选择与总体流程

四步：先从底册与面板筛出「有信号」的 325 家，再把各维度的累计值与年度序列拼进记录，然后算池内百分位与数据标记，最后提供过滤函数并跑三个示例查询验证。全程零 SQL，只读三份快照，运行约 0.40 秒。

选择「有信号才入池」而不是「全库 2,074 家都入池」，是因为 1,749 家四项全 0 的机构进池只会把百分位稀释：如果全库入池，一家有 8 件专利的机构百分位会是 99.6，看起来「几乎最强」，实际只是「比 1,749 家零记录的机构多 8 件」。把零记录机构排除后，8 件专利的百分位是 46.6，接近中位，符合直觉。

选择「null 而不是 0」，是 DATA_FACTS §3.13 与 §3.16 的直接要求：源不覆盖的年份若按 0 摊入，趋势线会出现「断崖式下跌」，用户会读成「产出崩了」。本件在 `data_flags` 里逐维写清覆盖年份，前端只要照读就不会画错。

### 2.2 步骤 1：池的筛选与画像

池的规则是「专利、论文、项目、学者四项至少一项大于 0」。实测 325 家：广州 173、深圳 120、东莞 21、惠州 11；事业单位 271、民办非企业 54。这个分布与底册的城市分布（深圳 1,014、广州 822）方向相反——广州入池机构更多，因为广州的老牌院所论文产出多，而深圳的机构多为民非新型研发机构，论文少、专利多。

各维度的覆盖：有专利 219 家、有论文 236 家、有项目 53 家、有学者 29 家、有转化 16 家、有政策提及 47 家、有专利年度序列 181 家、有财务 0 家。八项里只有前两项覆盖超过 200 家，项目与学者不到 60 家，这意味着「绩效」这个词若按「投入产出」理解，本件无法支撑；若按「产出记录」理解，本件覆盖 325 家。

池内分布（`pool_stats`）：专利中位 8、P90 73、最大 943；论文中位 3、P90 19、最大 1,265；项目中位 3、P90 25、最大 102；学者中位 2、P90 14、最大 35；项目经费中位 82 万元、P90 1,216 万元、最大 5,472 万元。五个分布全部右偏，专利的均值（29.93）是中位（8）的 3.7 倍，论文的均值（13.21）是中位（3）的 4.4 倍。这解释了为什么页面必须同时显示中位与最大：只看均值会让用户以为「典型机构有 30 件专利」。

### 2.3 步骤 2：年度序列的拼接与断裂标注

三个序列各有自己的窗口。专利序列来自面板 `app_year`，窗口 2021—2024，实测有记录的机构数 93/113/107/120；论文序列来自 `papers_year`，窗口 2021—2025，机构数 60/69/62/162/81；项目序列来自 `projects_year`，窗口 2021—2022，机构数 16/1/0/0/0。

三个窗口的差异不是采集遗漏，而是源表结构：专利面板只做到 2024 年申请（2025/2026 的申请数据尚在公开滞后期内），项目源表止于 2022 年（2023 年以后的立项数据未接入），论文源表覆盖到 2025 年但 2024 年有一次采集扩充（32,379 篇，是 2023 年的 5.2 倍）。三处都写进 `year_series_coverage.note`，页面照读。

这里有一个必须强调的细节：**累计值与年度序列不是同一口径**。一家机构可能累计 394 件专利但年度序列全为空（哈工大深圳就是如此），原因是累计按申请人名精确匹配，年度序列还要求该专利落在面板的 `app_year` 窗口内且申请年可解析。两条链的差集就是 §2.6 审计里的 38 家、788 件。

### 2.4 步骤 3：百分位与数据标记

百分位在池内算，四项分别算，并列取平均位次。百分位的作用是给用户一个「这家机构在同类里处于什么位置」的快速判断，但它有两个陷阱：其一，池是「有信号机构」，不是全库，也不是全市；其二，不同维度的覆盖率不同，项目维只有 53 家有值，一家有 1 个项目的机构在项目维的百分位可能是 60，这不代表它的项目管理能力强，只代表「有项目的机构太少」。

数据标记（`data_flags`）逐维写四件事：覆盖年份、缺口原因、是否含采集尖峰、是否有替代口径。以深圳先进院为例，标记写的是「专利序列 2021—2024（2025/2026 为 null，不是 0）」「论文序列 2021—2025（2024 为采集尖峰）」「项目序列 2021—2022 有值，2023—2025 为 null（源表不覆盖）」「财务无（年报财务表对底册 2,074 家命中 0 行）」「学者 29/2,074 家有记录」。这五句话是页面不误读的前提。

### 2.5 步骤 4：查询契约与三个示例

查询支持四类过滤：名称子串（不分词，直接 `in` 判断）、城市等值、机构类型等值、专利下限。返回按专利降序、论文降序排。实测三个示例：

| 查询 | 命中 | 响应 | 返回要点 |
|---|---:|---:|---|
| 名称含「深圳大学」 | 0 | 0.016 ms | 底册无高校本部（只有「深圳大学龙岗创新研究院」等分支） |
| 名称含「中国科学院深圳先进技术研究院」 | 1 | 0.013 ms | 943 件专利 / 422 授权 / 83 论文 / 102 项目 / 35 学者 |
| 名称含「深圳市人民医院」 | 1 | 0.012 ms | 返回登记名「深圳市人民医院（深圳市呼吸疾病研究所）」 |

「深圳大学」命中 0 是整个查询层最值得写进说明书的案例。用户的直觉是「深圳大学是深圳最大的科研机构之一」，但底册收录的是「登记为科研机构、民非或事业单位的研究院」，高校本部不是科研机构登记类型，因此不在册。深圳大学只有「深圳大学龙岗创新研究院」「深圳大学龙华生物产业创新研究院」两个分支在册。同类情况还有南方科技大学（只有坪山生物医药研究院在册）。这不是数据错误，而是底册的收录范围；页面必须在空结果时提示「高校本部不在科研机构底册，请尝试其研究院」。

过滤查询示例：深圳 + 专利 ≥50，命中 11 家，首位深圳先进院 943 件，其后是哈工大深圳 394、鹏城实验室 281、华大生命 199、西工大深研院 174、深圳清华研究院 156、电子科大（深圳）143、西北农林深研院 115、深圳先进技术研究院（旧名）80、人工智能与机器人研究院 76、香港理工深研院 55。这 11 家合计 2,516 件，占深圳入池专利（3,425 件）的 73.46%，头部集中度极高。

### 2.6 步骤 5：两处查询层硬缺陷的审计

第一处是「有累计、无序列」。38 家机构有专利累计值但年度序列全空，合计 788 件，占池内专利总量（6,554 件）的 12.02%。前六名是哈工大深圳 394 件、电子科大（深圳）143 件、龙岗中心医院 40 件、深圳市眼科医院 34 件、广东省疾控中心 21 件、生态环境部华南所 20 件。这些机构的卡片如果画年度折线，会是一条贴着 0 的直线，而累计值显示几百件，用户必然认为数据出错。正确做法是：序列全空时不画折线，显示「该机构专利未进入年度面板（累计 394 件）」。

第二处是「同名未消歧」。按「短名被长名包含」扫描出 36 对，其中 3 对是真重复：深圳先进技术研究院（80 件）与中国科学院深圳先进技术研究院（943 件）、岭南现代农业科学与技术广东省实验室（26 件）与中国农业科学院深圳农业基因组研究所（含深圳分中心，16 件）、广东省科学院（0 件）与广东省科技图书馆（广东省科学院信息研究所，0 件）。另外 33 对是母体与下属所，如广东省科学院与它的新材料所、智能制造所、半导体所、广州地理所——这些不应合并，只应给出上卷关系。

两类必须区别处理：真重复合并后数字会变（深圳先进院合并后 1,023 件），母子关系合并后会把下属所的产出算到母体头上（广东省科学院会凭空多出 400 多件）。本件在 `audit.name_duplicates` 里把两类分开列，就是防止下游一刀切合并。

### 3.2 覆盖率对解释力的影响

325/2,074 = 15.67% 的入池率，是本件最直接的限制。它带来三个后果。第一，用户搜一家机构如果不在 325 家里，会得到空结果，但这家机构可能确实存在（只是没有产出记录），空结果的提示必须区分「不在底册」与「在底册但无记录」两种情况。第二，百分位的分母是池内机构数，不是全市机构数，「百分位 90」不代表「全市前 10%」。第三，池的构成偏广州（173 对 120），因为广州机构论文多，这会让深圳机构在论文维的百分位偏低。

覆盖率低的根因还是「机构名匹配」。本件没有做别名合并，因为合并会改变数字（§2.6 已量化 3 对真重复、33 对母子），在查询层做合并风险太大，留给上游维表解决。

| 2 | 项目序列 2023 后为空 | 无近三年项目趋势 | 不能。用累计数画趋势是错的 |
| 3 | 38 家有累计无序列 | 折线图误导 | 可以：页面不画折线，只显示累计 |
| 4 | 3 对真重复 | 同一机构两条记录 | 可以：合并展示，但需保留原名 |
| 5 | 学者 29 家 | 人才维无区分度 | 不能。样本太小 |
| 6 | 论文 2024 尖峰 | 趋势误读 | 可以：标注采集口径 |
| 7 | 高校本部不在底册 | 搜「深圳大学」空结果 | 可以：空结果提示分支名 |

### 4.2 后果归因：哪些话不能说

第一，不能说「本件是线上绩效结果面」。`result_face_status.available=false`，本件是离线物化 + 内存查询，上线需要落 ADS 表并加 API。

第二，不能说「2025 年专利产出多少」。专利序列到 2024，2025/2026 为 null；任何 2025 年的专利数字都不可答。

第三，不能说「某机构 2024 年论文翻倍」。2024 年的 32,379 篇是采集口径扩充，不是产出增长。

第四，不能说「搜不到就是没有这家机构」。深圳大学、南方科技大学的本体都不在底册，只有分支在册。

第五，不能说「百分位 90 就是全市前 10%」。百分位的分母是 325 家池内机构，不是全市 1,014 家。

### 4.3 判档说明

本件判「部分支持」：查询契约、宽表物化、百分位、数据标记四条链路都能跑通，325 家机构的卡片可以逐字段核对；但预计算绩效结果表不存在，财务维 0 命中，三处年度序列断裂。按 §0.1 的定义，这是「结构可交付、结果面需自建、投入侧缺失」的形态。

没有降到「完全不支持」，因为查询本身可用，且 325 家机构的产出记录是真实的。也没有升到「完全转换支持」，因为「绩效」通常要求投入产出比，而投入侧（营收、研发投入、人员）一项都没有。

### 4.4 补齐关键字段后的规模预估

若财务表与底册能按统一 ID 关联（假设命中率 60%），入池机构会从 325 家增到约 400 家（财务记录本身也是一条「有信号」证据），且可以新增三列：营业收入、研发投入、研发人员数。有了研发人员，才能算「人均专利」「人均论文」；有了研发投入，才能算「每万元投入的专利产出」。这两类指标是「绩效」一词的核心，当前完全缺失。

若项目数据补到 2025 年，项目序列会从 2 年（2021—2022）扩到 5 年，53 家有项目的机构才能画趋势。按当前项目表的记录密度（2021 年 16 家、2022 年 1 家），即使补齐，年度覆盖也不会高；项目维可能永远只能做「累计」而不能做「趋势」。

## 附录 D　构建方法可行性报告（完整版）

一、方法谱系。机构画像查询有三种做法：预计算宽表、即席 join、指标中台。三者的差别在「口径何时固定」：宽表在 ETL 时固定，即席在查询时固定，中台在指标定义时固定。本件选宽表，因为池子小（325 家）、重建快（0.42 秒）、口径争议多（每家件都有自己的算法），固定一次比每次查询都解释一遍更省事。

二、为什么池内百分位而不是全库。全库 2,074 家里 1,749 家四项全 0，若把它们放进分母，任何一家有 3 件专利的机构百分位都在 92 以上。这不是「强」，而是「大多数机构没有记录」。池内百分位把「无记录」与「有记录但少」分开，代价是百分位的语义变成「在有记录的机构里排第几」，页面必须写清。

三、为什么 null 而不是 0。这是 DATA_FACTS §3.13 的直接教训：专利表 2017—2020 零行，若按 0 摊入，任何「近八年趋势」都会出现四个 0 的前导段，斜率被顶高，预测结果失真（该事故已记录在 §3.19）。本件把「源不覆盖」与「值为 0」严格分开，前者返回 null，后者只在真有 0 件时出现（例如某机构某年确实没有申请，但面板不提供这种粒度，所以实际上全是 null）。

四、为什么不做别名合并。合并会改变数字：3 对真重复合并后深圳先进院从 943 变 1,023；33 对母子若合并，广东省科学院会凭空多出 400 多件。查询层是「读数」的地方，不是「改数」的地方；合并应在上游维表完成，并用 `parent_org_id` 表达母子关系。本件只把两类列出来，交给上游处理。

五、与 API 的关系。本件的宽表可以直接落成一张 ADS 表（325 行 × 约 40 列），API 只需按 name/city/org_type 做 where 过滤。响应时间在内存里是 0.02 毫秒，落库后加索引也在毫秒级，完全满足页面要求。真正的难点不是性能，是「空结果如何解释」与「null 如何展示」。

六、结论。本件在当前数据条件下已把「查询面」做到可用：325 家、八区块、四类过滤、两处审计。要升级为需求所暗示的「绩效结果面」，必须补三样东西：财务表与底册的统一 ID（投入侧）、项目数据到 2025（趋势）、机构别名与母子维表（消歧）。三样都不具备时，页面标题应写「机构画像」而不是「绩效查询」。

七、遗留事项。第一，论文 2024 采集尖峰是否要在图上做平滑，需要产品确认；第二，38 家「有累计无序列」的机构是否要在卡片上显示「年度数据缺失」标记，需要产品确认；第三，高校本部（深圳大学、南方科技大学）是否要单独建一张「高校表」并入查询，需要业务方决定。
