# DECISIONS.md

## 决策 001

问题：同一未来产业是否只能配置一家明星企业？

用户选择：用户指出每个产业不可能只有一家企业，应存在明星企业选择列表。

理由：原始需求使用“行业内的龙头明星企业”复数语义；SRS 明确为列表页和详情页；会议结论“固定明星企业表”表达运营维护的固定名单，不等于单企业。

对计划的影响：对象基数由“每产业 0..1 家”修订为“每产业 0..N 家”，E-34 需要名单选择与单企业详情两层状态。

状态：
已确认

## 决策 006

问题：每产业 0 家、1 家、2 家及以上时如何呈现？

用户选择：0 家显示业务空态；1 家直接显示企业且不显示下拉框；2 家及以上显示可搜索下拉框和“共 N 家”。

理由：避免无选择价值的控件，同时保留多企业名单的发现与切换效率。

对计划的影响：Wireframe 和 TRACE 增加按名单数量分支的展示规则。

状态：
已确认

## 决策 007

问题：用户切换明星企业后页面定位到哪里？

用户选择：返回明星企业首屏。

理由：企业对象已经改变，先重新确认企业身份、入选理由和数据时间，避免把新企业内容误认成旧企业。

对计划的影响：选择器交互需更新 URL、刷新详情并滚动到 E-34 首屏；不保留旧企业局部选中态。

状态：
已确认

## 决策 008

问题：CMS 内容不完整的企业是否进入前台选择名单？

用户选择：名单条目和基础介绍必须发布；产品、技术、团队、生态等其他区块允许部分缺失并显示业务空态。

理由：保证每个候选对象至少可识别，同时不因局部内容缺失阻塞整家企业展示。

对计划的影响：TRACE 增加前台准入门槛；Wireframe 增加部分内容缺失状态；草稿名单和基础介绍不对外展示。

状态：
已确认

## 决策 002

问题：明星企业名单采用哪种页面交互形态？

用户选择：采用“可搜索下拉框 + 当前企业详情”，保留在企业总览的明星企业介绍 Tab 内。

理由：既支持同产业多企业切换，又不把当前纵向详情重新拆成独立列表页。

对计划的影响：Wireframe 增加可搜索选择器及候选项结构；“不提供手动选择”改为“不提供名单外自由选企”。

状态：
已确认

## 决策 003

问题：切换产业后默认选中哪家明星企业？

用户选择：按 CMS `sort_order` 自动选中第一家；没有显式置顶时按名单顺序第一家。

理由：将展示优先级交给运营配置，不由前端计算排名。

对计划的影响：TRACE 和异常状态需要定义排序字段缺失、重复及空名单的降级规则。

状态：
已确认

## 决策 004

问题：当前明星企业是否写入 URL？

用户选择：增加 `enterprise_code`，支持刷新、分享和返回恢复。

理由：企业详情属于可定位页面状态，不能只保存在组件内存中。

对计划的影响：规范路由状态为 `/enterprise-center/overview?tab=star-enterprises&enterprise_code={code}`，并补充无效编码降级。

状态：
已确认

## 决策 005

问题：选择器候选项展示哪些信息？

用户选择：展示 Logo、企业名称和一句入选标签。

理由：比纯名称更容易辨识，同时避免引入评分、排名和内部阈值。

对计划的影响：Wireframe 增加候选项字段、缺失 Logo/标签的降级和禁止展示信息。

状态：
已确认
