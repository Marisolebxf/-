# 功能设计完善修改（FDE）

先读 `agent-delivery/产品实现规程.md` §4.2 全节，再动手。本技能只是入口，步骤以规程为准。审稿硬清单见同目录 [审稿硬清单.md](审稿硬清单.md)。

## 1. 先判断这句话是哪一种

按规程 §4.2.0，`product-agent` 先判断，不把原话直接写进说明书：

| 种类 | 下一步 |
|---|---|
| 需求 | 产品拆成用户故事和功能点，再出执行计划 |
| 问题 | 走缺陷修复，不进本链。核对后是设计没写到的，改判为需求 |
| 监管人自己给的方案 | 做用户故事完整性审核。有瑕疵就出决策卡，监管人选了才写进说明书、才出计划 |

完整性四问：谁在什么情况下要完成什么；做完能看见什么；没做、失败、做一半、改条件再做各自是什么；需规每个分句是否还有着落。

## 2. 收意图（不全就回问）

监管人的一句话要能回答三件事。缺哪件只问哪件，不自己补：

| 必有 | 例（602） |
|---|---|
| 改哪一叶 | 602 系统引用政策源数据清洗 · 清洗页签条件栏 |
| 改成什么样 | 演示政策 → 选择政策；智能搜索 + ID 检索；多选；候选读 ODS 贴源；规则可启停；本批结果 |
| 为什么 | 体现需规「系统引用多源数据 + 质量校验规则」 |

同时读该叶需规原文（`bid-reference/srs/...`）与现行说明书该叶。

## 3. 先出计划，确认后再跑

意图收齐后，按规程 §4.2.5 写一屏执行计划：现在到哪、这次改什么、建议档位、将要跑的波次、预计会停下来问的点。用 `AskQuestion` 给两个选项：「按此计划开始」「先改计划」。

选「按此计划开始」才建单、才开第一个身份会话。选「先改计划」只改计划。确认前只读，不改说明书、四单和代码。

确认后的链路：

```text
coordinator 建 FDE 总单（监管人 = 发话人）
  → A product-agent：功能点、界面上必须看见什么、状态清单、影响清单；ux 出线框
  → B arch-agent：定档；列要动的层；读法方案
  → C 各身份起稿 → 多身份对抗会签（审稿硬清单）→ 分歧闭合
  → D data → api → frontend 实现（同仓一单）
  → E 合规演示用例 → qa-agent 跑 §6.5 → 段 E 冒烟
```

每个身份一个会话（或 Task 子代理），只产出本身份产物。同一会话不得既起草又审稿。

每个波次收口时另开 `doc-agent` 会话（规程 §4.3）：更新说明书的图与文末变更记录；核对 `data/data-design/storage/{域}/` 与改动一致；写 `sdd/简报/{日期}-{主题}.md` 给监管人，聊天里贴要点，并按 **§8** 给可点 `file://` 打开。简报没交，波次不算收口。

整次走完（波次 E 后），`doc-agent` 按规程 §4.3 第四件向每个参与身份索要 5 行回执（身份、做了什么、产物、没闭合的、要人决定的），汇成 `sdd/简报/{日期}-{叶}-完工汇报.md`：结论一句 + 一身份一行的表 + 待决定项；聊天交付同样走 **§8**。不转抄各身份原文。

## 4. 停机与决策卡

命中规程 §4.2.5 任一停机条件：当前波次停下，写决策卡，用 `AskQuestion` 呈给监管人选；推荐项放第一位、标「（推荐）」。监管人选完，把选择与理由写回会签单或总控，再续跑。不命中就不问。

## 5. 与「需规分句闭合」审计

若监管人要先核对「需规每个分句在界面/用例是否都有着落」（未指定改成什么样），先跑 `gkx-display-srs-cover`：出矩阵 → 决策卡（Plan）→ 一屏计划。人选「按此计划开始」且缺口属设计完善时，再回本技能建 FDE。不要跳过审计直接 FDE。

## 6. 用户可见文案（实现铁律）

业务界面（非内部评审模式）**禁止**出现程序逻辑描述。写在 template / `a-empty` / `a-alert` / 脚注 / 总结段里的字，必须是业务用户能懂的话。

| 禁止出现在用户可见 DOM（关评审时） | 应放到哪 |
|---|---|
| `gapfill` / `fixture` / `mock` 表名或轨名、`USE_MOCK`、`D18`、`D4`、`ADS`/`DWD`/`ODS` 库表 | 代码注释、handoff、合规用例、评审层角标/ⓘ |
| `policy_intensity`、`sub_type`、Job 管道、metric_id、字段蛇形名 | 同上 |
| 「不造演示分」「属已知缺口」「附带列」「读列」等实现口径 | 同上；界面改成「暂无结果 / 可稍后重试」 |

**例外**：仅当 `reviewMode`（内部评审模式）开启且组件自闸时，允许评审层展示 `metric_id` / 就绪度 / GAP 等；关评审后 DOM **零泄漏**（对照仓内 `src/review/`）。

FDE 波次 D（frontend）自检：交付前对改动页搜一遍 `gapfill|fixture|policy_intensity|不造演示|附带列|已知缺口`，命中用户可见串则改掉再交。

## 7. 不做

- 监管人还在讨论、没给改动意图：只解释。
- 重档：退回定义规程，不走本链。
- 不自签人类签字项（产品复核、铁律裁定、签收、甲方口径）。
- 不把实现/数据层黑话写进业务界面文案（见 §6）。

## 8. 给人复看的本地文件（可点打开）

聊天里凡要监管人打开本机落盘文件（波次简报、完工汇报、一屏计划、决策卡落盘稿等），**必须**给 Markdown 可点链接，禁止只甩相对路径或反斜杠裸路径当「链接」。

1. 先读 `gkx-orchestration/.env` 的 `GKX_ROOT`，拼绝对路径：`{GKX_ROOT}/gkx-orchestration/{仓内相对路径}`。
2. 链接格式：`[文件名.md](file:///{盘符大写正斜杠绝对路径})`  
   例：`[2026-11-12-SIM-237-ASYNC-方案C-计划.md](file:///E:/zhipu/gkx-lumen/gkx-orchestration/agent-delivery/agent-handoffs/科技政策跟踪-POL/sdd/简报/2026-11-12-SIM-237-ASYNC-方案C-计划.md)`  
   规则：`file:///` + 盘符 + `:/` + 其余用 `/`（勿用 `\`）；中文路径保持原文。
3. 可另附一行资源管理器路径（`E:\...`），但**不能替代**可点 `file://`。
4. 入库文档正文仍写相对主仓路径（`agent-delivery/...` / `sdd/简报/...`），不把本机盘符写进仓内文件。
