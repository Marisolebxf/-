# 缺陷登记细则

## 结论

| 看到的 | 结论 |
|--------|------|
| 编码当成名称、控件变形、空壳、类名泄到页面、开发说明、500、切页后图表消失、菜单卡死 | 产品缺陷 |
| 指标、依据、清单值本身没有 | 数据缺口 |
| 环境打不开、账号进不去 | 环境不可用 |
| 用例与现网步骤对不上，但现网行为本身说得通 | 用例与现网不一致 |

用例允许空态、编码或禁用控件，而用户要求另一种行为：结论仍按上面判断，处理写「未定改产品还是改用例」，并摘一句用例原文。

## 飞书列

登记和修订都跑 `node scripts/sync-feishu-bug.mjs --id {编号}`。文字列从台账和正文来，不是只传图。

| 飞书列 | 来源 |
|--------|------|
| BUG编号 | 台账 `id` |
| 标题 | 台账 `title` |
| 结论 | 正文 |
| 模块 | 正文 |
| 入口 | 正文 |
| 环境 | 正文 |
| 预期 | 正文 |
| 实际 | 正文 |
| 状态 | 台账 `status`：`open` 待处理，`fixed` 已修复，`verified` 已复验，`closed` 已关闭，`deferred` 暂缓 |
| 关联用例 | 正文；正文没有时用台账 `source_case` |
| 发现日期 | 正文；没有时从编号里的日期取 |
| 截图 | 仅 `--image` 指向的对话附件。没有图就留空 |

登记人、登记方式不进飞书。

## 截图

文字在 git，图片只在飞书「缺陷」页的附件列。仓库不留副本。

- 有图：正文写 `飞书附件`。登记当次对每个对话附件原路径执行一次 `--image`，不 `cp` 进 `assets/`。
- 没图：正文写 `无`，同步命令不带 `--image`。
- 图里若有口令或令牌，正文不要再抄一遍。上传仍用用户给出的原文件，不改格式。
- 飞书附件被删掉后，git 里没有图可以补回。

## 编号顺延

只处理**这一次新建、还没推上去**的编号。旧编号不动。

1. `git fetch origin dev` 之后，读 `origin/dev` 上的 `qa/bug-registry.yaml`。
2. 本次某个编号在远端已有，且标题不同：从该系统该日的最大序号往后排，001、002 这样接着用，中间不留空号。
3. 编号相同且标题、正文都是这一条：说明是重复推送，不要再占新号。
4. 改两处：registry 的 `id`，以及 `items` 文件名和正文里的编号。本次新条目之间的「另见」互引一起改。飞书行由下一次 `--id` 同步按新号写入；旧号那一行若已推到飞书，不要改飞书上的旧编号。
5. 提交说明写明旧号和新号，再 `git push origin dev` 一次。

两人同时写 registry 时，合并后两份条目都留。先合并，再按上表顺延撞上的本地号。

## 推送被无关改动挡住

`git pull` 提示会覆盖不是本次缺陷的未提交文件时，停。不要 `stash`、`checkout`、`reset` 那些文件。本地提交保留，告诉用户缺的是推送，不是登记。
