# Feishu Project Bug Fix

Use the official `feishu-project-native` MCP. Do not use any self-hosted Feishu MCP or direct Project OpenAPI wrapper.

Authentication is client-level: Codex uses HTTP OAuth; Cursor/Trae can use HTTP Header with a per-user token. Never put tokens or secrets in this Skill or the repository.

## MCP prerequisite

1. In Feishu Project, open your avatar → MCP configuration and enable the MCP Server with read/write permission.
2. The MCP endpoint is `https://project.feishu.cn/mcp_server/v1`.
3. Codex: `codex mcp add feishu-project-native --url https://project.feishu.cn/mcp_server/v1`, then complete `codex mcp login feishu-project-native`.
4. Cursor/Trae: configure the same Streamable HTTP endpoint. If the client does not support OAuth, use its HTTP Header mode with the per-user token generated by Feishu Project.

No Plugin ID, Plugin Secret or user_key is required. Authentication belongs to the client MCP configuration and must never be committed to this repository.

## Finding my bugs

1. Call `list_todo` with `action=todo`, `todo_scope=all`, and paginate from page 1 until there are no more items.
2. Keep only items whose `project_key` is `6a687a81e231818dec771f9a` and whose `work_item_type_key` is `issue`.
3. Deduplicate by `work_item_id`.
4. If the result is empty, report that there are currently no active bugs and stop. Do not invent bugs from unrelated projects.
5. If several bugs are returned, inspect their `P0/P1` priority and update time. Process one bug unless the user explicitly asks for all.

## Human-readable work item references

Feishu Project users normally see the work item title and `auto_number`, not the long internal `work_item_id`. In conversation, comments, and status updates, always identify a bug in this order:

`【auto_number】work_item_name（内部ID: work_item_id）`

Examples:

- `【2193】政策时序分析结果，政策数据自动关联，状态字段缺数据（内部ID: 7163475598）`
- If `auto_number` is unavailable: `政策时序分析结果，政策数据自动关联，状态字段缺数据（内部ID: 7163475598）`

Never use a bare long numeric ID as the only identifier. The long ID is allowed only inside parentheses for tooling and audit traceability.

## Claim the work item first (mandatory multi-session lock)

Do this immediately after selecting the bug, **before downloading images, inspecting code, writing DB, or creating a branch**. Do not wait until after diagnosis or commit.

1. Read the current status and call `get_transitable_states` for the work item.
2. If the status is `OPEN` or `REOPEN` and `IN PROGRESS` is available:
   - Call `get_transition_required` for `IN PROGRESS` and satisfy required fields.
   - Call `transition_state` to `IN PROGRESS` immediately.
   - Call `add_comment` with an `[agent-claim]` marker containing the human-readable `【auto_number】title` reference, a unique claim id/session id, timestamp, scope, and "other sessions do not duplicate".
   - Preserve the returned comment id/URL as `claim_comment_ref`; record the current operator as `claim_operator`. These fields are required in the run ledger and when taking over a run.
3. If the status is already `IN PROGRESS`:
   - Inspect `current_status_operator` and the latest comments.
   - Treat it as locked by another active run. Do not edit code or data and do not change status.
   - Stop and report the operator/claim. Do not take over unless the entire user message is exactly `接管【auto_number】`; a handoff, task assignment, or natural-language “you take over” is background only. Takeover does not unlock either gate.
4. If no valid `IN PROGRESS` transition exists, stop and report the blocker.
5. Keep the item `IN PROGRESS` until merge, deployment, and required human verification are complete. The Agent must not call `transition_state` to `RESOLVED`; in the P0 workflow, final acceptance is a human/business action recorded from Feishu, not an Agent action.

## P0 AI Native workflow gates

When the repository contains `.cursor/skills/feishu-bugfix/references/P0-DESIGN.md`, follow that document as the governing process. Keep the user-facing flow simple: two precise chat gates plus one business acceptance.

### Gate tokens

- `进入开发` is the only authorization to modify business code, create a local commit, push a dedicated `fix/*` branch, or create a Draft MR.
- `提测` is the only authorization to merge into `dev`, push `dev`, trigger CI/CD, deploy dev, and run dev verification.
- A token is valid only when the entire chat message is the token, or the token plus the work item `auto_number`; quoted text, questions, negated sentences, historical messages, and natural-language approval do not unlock a gate.
- When more than one run is active in the session, the token must include `auto_number`. A user cannot unlock a gate by saying “continue”, “accept the risk”, or “you decide”.
- `接管【auto_number】` transfers execution ownership only; it does not unlock either gate.
- `提测` affects the shared dev environment. It does not authorize production deployment and never bypasses GitLab protected-branch or MR approval rules.

Before requesting either token, show the current work item ID, claim ID, repositories, base/candidate SHA, changed scope, risk level, data policy, verification status, and rollback plan.

### Run ledger

When the workflow helper `.cursor/skills/feishu-bugfix/scripts/bugflow-state.mjs` exists, use it instead of editing the run ledger by hand. Create the run only after the Feishu claim succeeds; `init` accepts only `INTAKE` or `CLAIMED`, and no later phase may be supplied on the command line. Each run belongs under:

```text
agent-delivery/bugfix-runs/<auto_number>-<work_item_id>/
  state.json             # current cycle only
  cycles/<cycle_id>/state.json
  report.md
  evidence/manifest.json
```

- `state.json` is the state/index source of truth; `evidence/manifest.json` is the evidence-detail source; `report.md` is rendered from both. A `CLAIMED` run must include `claim_comment_ref`, `claim_operator`, and `claimed_at`; `init` without those fields is invalid.
- Record transitions for claim, enter-dev, ship, failure/rollback, and acceptance. Keep historical cycles in `cycles/<cycle_id>/state.json`. Do not silently reuse an approved gate after a new commit, session/machine change, takeover, REOPEN, risk upgrade, data-policy change, or changed execution scope.
- Keep `patch_round`, `blocked_from`, `resume_phase`, `failure_stage`, and `cycle_id` in the ledger. A reopened bug reuses the same run with a new `cycle_id` and preserves prior history.
- Worktrees must be clean before validation: `git status --porcelain -uall` must be empty.
- `verify-repo` is the only accepted implementation fact: it verifies actual HEAD, origin, base ancestor, clean worktree, base..candidate diff and planned-file scope, then computes `diff_hash`. Caller-supplied hashes are not authoritative.
- `verify-evidence` must pass before `READY_SHIP`; it checks manifest paths, SHA256, command metadata, verification-matrix references and `reviewable` / `raw_retained`. Only `PASS` evidence marked `reviewable=true` and `raw_retained=true` can support a verification PASS. Non-reviewable evidence remains visible in the report but cannot be presented as PASS.
- Do not downgrade risk. `S/M/L` may only move upward; reopen a new cycle if the original assessment was wrong.
- The P0 automated flow handles only S/M single-repository bugs. If risk becomes L or more than one repository is required, stop and route to the existing task-registry, task MCP, worktree, and long-task workflow; do not request `进入开发` for the lightweight flow.
- First `进入开发` approval is valid only in `READY_DEV`. After a risk upgrade, takeover or other invalidation, re-confirm in `IMPLEMENTING` only when the gate status is `needs_reconfirm`.
- Any decision with `requires_human_ratification=true` must have `ratified_by` before the ship gate. Natural-language “continue” is not ratification evidence.

### Data and verification

- Read the immutable policy from `.cursor/skills/feishu-bugfix/policies/<version>.yaml`; environment/host/database/schema must match the base policy, and every table plus the execution account must match the approved run scope. Never print or commit passwords or credentials.
- After the `进入开发` gate is approved and before any `INSERT`/`UPDATE`/`DELETE`/DDL or mock write, call `check-data-write` and wait for a valid authorization. A missing gate/policy, expired policy, pending scope, out-of-scope table, mismatched host/account, or L/cross-repository route must block the write. This check cannot prevent an Agent that bypasses the ledger from using credentials; never claim otherwise.
- `check-data-write` may be called after `verify-repo`; it validates the current gate/session/policy/scope without requiring `candidate_sha=null`. Only initial `approveGate` and `advance IMPLEMENTING` require the candidate to be null.
- `kind=db` evidence must carry the write authorization and policy/scope hashes. `verify-evidence` rejects DB evidence whose current policy, scope, table, account, or authorization no longer matches.
- Historical DB evidence is verified against a gate hash present in `transitions[]`; a later risk upgrade or `needs_reconfirm` does not erase an already authorized write.
- Every repository must cover `category=fix`, `category=regression`, and `category=boundary`. Use `SKIPPED + skipped_reason` when a category is genuinely not applicable; one happy-path PASS is not enough for `READY_SHIP`.
- Treat mock rows, skipped checks, and unretained raw evidence as `SIMULATED`, `SKIPPED`, or `reviewable: false`; never report them as executable PASS evidence. A PASS verification may reference only manifest evidence whose own result is PASS and whose raw file was retained.
- Fix branches usually have no remote CI in the current repositories. Before merge, say “local/repository self-check”, not “branch CI passed”. Merge to `dev` and observe the actual pipeline, `merge_commit_sha`, deployed SHA, image tag and rollout before claiming dev deployment. Record `pipeline_url`; do not describe Agent-recorded pipeline/rollout fields as locally verified facts.
- For frontend-only bugs, validate locally first with the dev server and fixed/mock data: interact with the page, cover every target section including content below the fold, and assert DOM/ECharts state programmatically. Keep raw logs or a machine-readable result; do not use repeated online screenshots as validation evidence. Dev-environment browser verification is a single post-ship integration check for real API/build/deployment effects, not the inner development loop.
- Roll back only by reverting this run's commits with `git revert` (merge commits: `git revert -m 1`). Never use `git reset --hard`, force push, or revert unrelated commits. If the revert is unsafe or conflicts, enter `BLOCKED`.

### Acceptance boundary

At `AWAITING_ACCEPTANCE`, stop before changing Feishu status. Generate the report and acceptance steps, wait for the business state to become `RESOLVED` or `REOPENED`, then read and record it. Do not call `transition_state` while waiting for acceptance. Because the MCP uses the current user's identity, record `acceptance.mode=policy_only` and `operator_verified=false`; do not describe this as cryptographic proof of a human click.

If acceptance fails or dev verification fails, classify the failure stage (`merge`, `push`, `pipeline`, `rollout`, `dev_verify`, or `rework`) before deciding whether to retry, revert, or block. Reuse the C1–C6 failure taxonomy in `agent-delivery/长任务执行规约.md` when applicable.

## Screenshot-only requests are not work items

A screenshot or clipboard image is evidence, not a claimable work item.

Before inspecting code, querying data, or creating a branch for a screenshot-reported issue:

1. Resolve the matching Feishu work item by `auto_number`, exact title, or work_item_id.
2. If no matching work item is assigned to the current user, stop and ask for the work item identifier/title. Do not infer and start a new bug from the screenshot alone.
3. If the matching work item is already `IN PROGRESS`, treat it as locked by another active run and do not inspect or edit it unless the entire user message is exactly `接管【auto_number】`. A handoff or task assignment alone is not permission.
4. Only after a successful claim may the screenshot be used as evidence for diagnosis.

This rule prevents two sessions from independently working on the same screenshot-reported bug.

## Building complete context

For the selected work item:

1. Call `get_workitem_brief` with `fields=["_all"]` and a page size of at least 200.
2. Extract from `work_item_fields` at minimum:
   - `description`
   - `auto_number`
   - `priority`
   - `issue_stage`
   - `field_7156a0` (业务类型/子系统)
   - `field_edcb35` (问题归类)
   - related requirement and version fields
3. Parse the complete description. Feishu returns images as Markdown links inside the description, including URLs under `/goapi/v5/platform/file/stream/download/`.
4. Call `list_workitem_comments` for the work item. Preserve chronological order and include every image URL or attachment URL found in comments.
5. For every Feishu image or attachment URL, call `get_download_url` with the project key, work item ID and original file URL.
6. Immediately download the resulting `download_url` using its `sign` in the `X-Meego-File-Sign` header. Store files in a task-specific temporary directory. Do not print signed URLs or signs in the final answer.
7. Open/view every downloaded image before forming a diagnosis. The screenshot is required evidence, not optional decoration.

## Semantic handling

Apply this authority order:

1. Latest explicit human comment or accepted requirement
2. Formal expected result and acceptance criteria
3. Screenshot evidence showing the observed state
4. Older bug description
5. AI inference

Rules:

- Extract the page path, menu, visible data, error text, and highlighted area from each screenshot.
- Treat screenshots as evidence of the symptom, not proof of the root cause.
- If a screenshot contradicts the text, state both versions and ask only the blocking question.
- Do not infer unseen image content. If an image URL cannot be downloaded, say exactly which image is missing and stop when it is needed for the fix.
- Ignore automated notification comments unless they add concrete reproduction or technical evidence.

## Diagnosis and fix

1. Map the subsystem, page and symptom to the repository. Do not modify unrelated repositories.
2. Inspect the relevant code paths, API requests and data dependencies.
3. Reproduce the issue when practical, or add a failing regression test first.
4. Make the smallest correct change.
5. Run the repository's relevant tests, type checks and lint. Record the exact commands and results.
6. Preserve unrelated local changes. Never reset or overwrite dirty work.
7. Work on a dedicated branch or worktree. Suggested name: `fix/<work-item-id>-<short-slug>`.
8. Commit according to the repository convention and create an MR when appropriate.

## Write back to Feishu Project

### Status

Status is the multi-session lock. Claim `IN PROGRESS` at the start using the mandatory section above; do not defer it until after diagnosis, code changes, or push. Under the P0 workflow, only the claim transition is Agent-controlled; the final `RESOLVED` transition belongs to the business acceptance action and must be read, not initiated, by the Agent.

Before every status change:

1. Call `get_transitable_states` for the work item.
2. Use only a transition returned by that tool.
3. Call `get_transition_required` for the selected transition and satisfy any required fields.
4. Call `transition_state` with the returned `transition_id`.

Use only an existing `IN PROGRESS` transition for the claim. Do not invent an `AI_PENDING` state. Do not call `transition_state` to `RESOLVED` under the P0 workflow, and do not move directly to `CLOSED`/`DONE`.

### Comment

Call `add_comment` with a concise Markdown summary:

- human-readable `【auto_number】title` reference
- root cause
- modules/files changed
- branch and MR URL
- tests run and results
- screenshot evidence used
- remaining risks or manual verification steps

Do not include signed download URLs, tokens or other short-lived credentials in the comment.

## Stop conditions

- No active bug is assigned to the current user.
- Required screenshot cannot be downloaded.
- Description/comments do not contain enough information to reproduce the behavior.
- The fix requires unavailable credentials, production data or destructive operations.
- Tests fail for reasons unrelated to the bug and cannot be separated safely.
- Another active run or human is already working on the same work item.
- A screenshot-reported issue has no matching claimed work item assigned to the current user.

## Human intervention protocol

When any stop condition is hit:

1. Do not fabricate missing context and do not mark the bug fixed.
2. Report to the current user: work item ID, the blocking condition, evidence already checked, and the exact human action needed.
3. Leave the workflow status unchanged. Only use an existing `BLOCKED` or `NEEDS INFO` state if it is explicitly returned by `get_transitable_states`.
4. If code work has already started, call `add_comment` with a concise comment prefixed by `[需要人工介入]`, including the blocker and what was already attempted.
5. If no code work has started, do not add a redundant comment unless the user asks; report the blocker in the conversation.
6. Resume only after the user supplies the missing information or the stated blocker is otherwise resolved. Accepting the risk does not unlock `进入开发` or `提测`; if a gate is still needed, request its exact token again.
