# Feishu Project Bug Fix

Use the official `feishu-project-native` MCP. Do not use any self-hosted Feishu MCP or direct Project OpenAPI wrapper.

Authentication is client-level: Codex uses HTTP OAuth; Cursor/Trae can use HTTP Header with a per-user token. Never put tokens or secrets in this Skill or the repository.

## MCP prerequisite

1. In Feishu Project, open your avatar → MCP configuration and enable the MCP Server with read/write permission.
2. The MCP endpoint is `https://project.feishu.cn/mcp_server/v1`.
3. Codex: `codex mcp add feishu-project-native --url https://project.feishu.cn/mcp_server/v1`, then complete `codex mcp login feishu-project-native`.
4. Cursor/Trae: configure the same Streamable HTTP endpoint. If the client does not support OAuth, use its HTTP Header mode with the per-user token generated by Feishu Project.

No Plugin ID, Plugin Secret or user_key is required. Authentication belongs to the client MCP configuration and must never be committed to this repository.

## Default project context

- Project: `GKX 生产`
- project_key: `6a687a81e231818dec771f9a`
- Work item type: `issue` / 缺陷
- Active states: `OPEN`; add `REOPEN` only if the project actually exposes it

## Finding my bugs

1. Call `list_todo` with `action=todo`, `todo_scope=all`, and paginate from page 1 until there are no more items.
2. Keep only items whose `project_key` is `6a687a81e231818dec771f9a` and whose `work_item_type_key` is `issue`.
3. Deduplicate by `work_item_id`.
4. If the result is empty, report that there are currently no active bugs and stop. Do not invent bugs from unrelated projects.
5. If several bugs are returned, inspect their `P0/P1` priority and update time. Process one bug unless the user explicitly asks for all.

## Human-readable work item references

Feishu Project users normally see the work item title and `auto_number`, not the long internal `work_item_id`. In conversation, comments, and status updates, always identify a bug in this order:

`【auto_number】work_item_name（内部ID: work_item_id）`

Examples:

- `【2193】政策时序分析结果，政策数据自动关联，状态字段缺数据（内部ID: 7163475598）`
- If `auto_number` is unavailable: `政策时序分析结果，政策数据自动关联，状态字段缺数据（内部ID: 7163475598）`

Never use a bare long numeric ID as the only identifier. The long ID is allowed only inside parentheses for tooling and audit traceability.

## Claim the work item first (mandatory multi-session lock)

Do this immediately after selecting the bug, **before downloading images, inspecting code, writing DB, or creating a branch**. Do not wait until after diagnosis or commit.

1. Read the current status and call `get_transitable_states` for the work item.
2. If the status is `OPEN` or `REOPEN` and `IN PROGRESS` is available:
   - Call `get_transition_required` for `IN PROGRESS` and satisfy required fields.
   - Call `transition_state` to `IN PROGRESS` immediately.
   - Call `add_comment` with an `[agent-claim]` marker containing the human-readable `【auto_number】title` reference, a unique claim id/session id, timestamp, scope, and "other sessions do not duplicate".
3. If the status is already `IN PROGRESS`:
   - Inspect `current_status_operator` and the latest comments.
   - Treat it as locked by another active run. Do not edit code or data and do not change status.
   - Stop and report the operator/claim unless the user explicitly asks you to take over or supplies a handoff.
4. If no valid `IN PROGRESS` transition exists, stop and report the blocker.
5. Keep the item `IN PROGRESS` until merge, deployment, and required human verification are complete. Only then move it to `RESOLVED`.

## Building complete context

For the selected work item:

1. Call `get_workitem_brief` with `fields=["_all"]` and a page size of at least 200.
2. Extract from `work_item_fields` at minimum:
   - `description`
   - `auto_number`
   - `priority`
   - `issue_stage`
   - `field_7156a0` (业务类型/子系统)
   - `field_edcb35` (问题归类)
   - related requirement and version fields
3. Parse the complete description. Feishu returns images as Markdown links inside the description, including URLs under `/goapi/v5/platform/file/stream/download/`.
4. Call `list_workitem_comments` for the work item. Preserve chronological order and include every image URL or attachment URL found in comments.
5. For every Feishu image or attachment URL, call `get_download_url` with the project key, work item ID and original file URL.
6. Immediately download the resulting `download_url` using its `sign` in the `X-Meego-File-Sign` header. Store files in a task-specific temporary directory. Do not print signed URLs or signs in the final answer.
7. Open/view every downloaded image before forming a diagnosis. The screenshot is required evidence, not optional decoration.

## Semantic handling

Apply this authority order:

1. Latest explicit human comment or accepted requirement
2. Formal expected result and acceptance criteria
3. Screenshot evidence showing the observed state
4. Older bug description
5. AI inference

Rules:

- Extract the page path, menu, visible data, error text, and highlighted area from each screenshot.
- Treat screenshots as evidence of the symptom, not proof of the root cause.
- If a screenshot contradicts the text, state both versions and ask only the blocking question.
- Do not infer unseen image content. If an image URL cannot be downloaded, say exactly which image is missing and stop when it is needed for the fix.
- Ignore automated notification comments unless they add concrete reproduction or technical evidence.

## Diagnosis and fix

1. Map the subsystem, page and symptom to the repository. Do not modify unrelated repositories.
2. Inspect the relevant code paths, API requests and data dependencies.
3. Reproduce the issue when practical, or add a failing regression test first.
4. Make the smallest correct change.
5. Run the repository's relevant tests, type checks and lint. Record the exact commands and results.
6. Preserve unrelated local changes. Never reset or overwrite dirty work.
7. Work on a dedicated branch or worktree. Suggested name: `fix/<work-item-id>-<short-slug>`.
8. Commit according to the repository convention and create an MR when appropriate.

## Write back to Feishu Project

### Status

Status is the multi-session lock. Claim `IN PROGRESS` at the start using the mandatory section above; do not defer it until after diagnosis, code changes, or push.

Before every status change:

1. Call `get_transitable_states` for the work item.
2. Use only a transition returned by that tool.
3. Call `get_transition_required` for the selected transition and satisfy any required fields.
4. Call `transition_state` with the returned `transition_id`.

Use existing states such as `IN PROGRESS` or `RESOLVED`. Do not invent an `AI_PENDING` state. Do not move directly to `CLOSED`/`DONE` without human verification.

### Comment

Call `add_comment` with a concise Markdown summary:

- human-readable `【auto_number】title` reference
- root cause
- modules/files changed
- branch and MR URL
- tests run and results
- screenshot evidence used
- remaining risks or manual verification steps

Do not include signed download URLs, tokens or other short-lived credentials in the comment.

## Stop conditions

- No active bug is assigned to the current user.
- Required screenshot cannot be downloaded.
- Description/comments do not contain enough information to reproduce the behavior.
- The fix requires unavailable credentials, production data or destructive operations.
- Tests fail for reasons unrelated to the bug and cannot be separated safely.
- Another active run or human is already working on the same work item.

## Human intervention protocol

When any stop condition is hit:

1. Do not fabricate missing context and do not mark the bug fixed.
2. Report to the current user: work item ID, the blocking condition, evidence already checked, and the exact human action needed.
3. Leave the workflow status unchanged. Only use an existing `BLOCKED` or `NEEDS INFO` state if it is explicitly returned by `get_transitable_states`.
4. If code work has already started, call `add_comment` with a concise comment prefixed by `[需要人工介入]`, including the blocker and what was already attempted.
5. If no code work has started, do not add a redundant comment unless the user asks; report the blocker in the conversation.
6. Resume only after the user supplies the missing information or explicitly accepts the risk.
